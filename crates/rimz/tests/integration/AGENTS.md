# Integration suite

Local contract for `crates/rimz/tests/integration/` — the crate's single integration-test binary. Extends [crates/rimz/AGENTS.md](../../AGENTS.md). Test tiers and runner rules live in [rust-conventions.md](../../../../docs/contributing/rust-conventions.md#tests).

## Harness

- A negative assertion over what an attached client received first waits for evidence in that client's own recorded stream that the payload rendered: a server-side `capture_pane` says nothing about which bytes the client has been sent yet.
- A helper that reads a PTY polls until every piece it asserts is present, and only then asserts. A single `write!` to stdout can reach the pty in several `write(2)` calls, because the line-buffered stdout flushes at each format piece that holds a newline, so a read can land between them; `sidebar_supervisor::Pane::notice` waits for its whole frame. A replica built to count those calls passes runtime arguments: rustc folds a literal argument into the format string, and such a replica writes once where the product writes twice.
- CI runs the suite as root (`ci/Dockerfile` sets no `USER`), so a permission-denied path cannot come from `chmod` on a socket or file; inject the error through a seam.
- One binary: every suite is a module of [`main.rs`](./main.rs), and [`common/`](./common/mod.rs) is declared once — no per-file harness duplication. Shared remote-connect PTY and terminal-query behavior lives in `common::ssh_trace`.
- Pick the tier by what the test drives: `common::Env` runs the `rimz` binary out of process with HOME, XDG, `TMUX_TMPDIR`, and `ZELLIJ_CONFIG_DIR` scoped to tempdirs; `common::Harness` opens a real in-process `rimz::Store` for direct API tests; `common::payloads` holds the golden agent hook payloads and `common::shim` the environment probes and fake executables, both shared across tiers.
- Every `Env` and `ZellijNamespace` arms an independent stdin-keepalive reaper before spawning children. The fixture HOME/runtime values are the process-ownership marker: on orderly drop or abrupt owner death the reaper stops both private mux endpoints, terminates every marker-carrying descendant, and removes the roots, except an `Env` dropped while panicking with `RIMZ_TEST_KEEP_FAILED` on, whose reaped roots are kept (see the stress bullet). A child is identifiable only once its exec has published that environment in `/proc/<pid>/environ`, which can trail `spawn` under load, so a test that depends on the marker straight after `spawn` waits for it. A command that calls `env_clear()` must re-pin `HOME` or `XDG_RUNTIME_DIR` before it can become long-lived.
- Real tempdir, real store files — no in-memory stubs.
- A signal- or tick-fired task with only `--check` runs in a detached `rimz loop run` child that opens the root's room before the check unless a sidebar heartbeat under 5 s old exists ([external-fire behaviour](../../../../docs/internals/harness/loops.md#the-external-tick)). Signal tests seed one with `common::room::seed_sidebar_heartbeat`, which dates it ahead so it stays live for the whole test; tick-fired tests cannot, because the same heartbeat makes `rimz loop tick` skip the root, so they wait out the room birth.
- A one-shot sidebar heartbeat has no writer behind it, so a reader that judges it by file mtime against the 5 s TTL (`rimz doctor`, `rimz loop tick` and `loop list`, the external-fire check) drops it once a loaded host spends 5 s before the read. Any one-shot heartbeat a test means as live goes through `common::room::seed_sidebar_heartbeat`, or `common::room::date_heartbeat_as_live` after a write whose fields the test sets itself. The wakeup fanout reader judges the JSON `last_seen` instead and rejects a future one, so a fanout test writes its heartbeat and reads it within one short step.
- A shell runs a trap only after its foreground command returns, so a signal that lands before that command is running as a program the signal kills is held behind it. A check script that must react to a signal backgrounds its long wait before publishing readiness, blocks in the `wait` builtin, and stops the background child in its trap (a background command ignores SIGINT). A test of delivery to a process group keeps that trap in a member other than the group leader, since the leader is the PID a single-process signal would also reach.
- To emulate signal delivery outside the suite, start the subject from a non-shell launcher in its own session (Python `subprocess.Popen(..., start_new_session=True)`). A shell that backgrounds it with `&` starts it with SIGINT ignored, and every result reads as a lost signal.
- `common::Env::rimz_at` defaults stdin to null so directly spawned commands cannot inherit buffered input from a test-running shell loop. Tests that exercise stdin set it explicitly afterwards; PTY commands keep their terminal input.
- `RIMZ_BIN` redirects every detached `rimz` helper spawn; point it at a missing path to exercise a spawn failure, which unit tests cannot reach, or at an executable that exits at once (`/bin/true`) to exercise a helper that spawns but never serves.
- A test that needs two builds patches the `.note.gnu.build-id` bytes of a binary copy. Appending bytes leaves `build_id::of_file` unchanged, and staging dedups by that id. A test that needs the binary at a second path hard-links it into a `tempfile::tempdir_in` the binary's own directory: a copy of the debug binary is a cold exec and heavy I/O that slows parallel neighbours past their deadlines under gate load.
- A row created by `rimz agents exec` keeps its card only while its runtime owner lives; to produce or enforce on it, spawn the exec with `common::write_long_lived_agent_shim`. Its stand-in answers `--version` at once, because a launch plan probes `<agent> --version` under a 3 s budget before it spawns the provider and binds the pane: a stand-in that hangs there spends that budget, and a resume's sender, whose pane-bind window is also 3 s, fails under load.
- Any test that launches a provider through `rimz agents`, `rimz agents -p`, or `rimz subagents`, a resume included, sets `SHELL` to `common::write_fake_login_shell`; a real `/bin/sh` login shell reads the host profile, which on the CI image resets `PATH` and hides a fake provider. A launch a hook wakes (a workflow attempt after a lifecycle edge, a loop task fired by a lifecycle signal) runs under the `SHELL` its `hooks feed` command carried, so put the fake login shell on that feed too.
- A test that reads the wrapper pane's root process (`rimz::proc::hosted_agent_process_for_root`, `/proc/<pane_pid>/cmdline`) waits until that argv carries `--supervise`: the wrapper spawns the provider first and then execs itself into its parked image, and its cmdline reads empty while the execve runs.
- Closing an agent's pane or window in a managed worktree makes its wrapper spawn a detached `rimz worktree cleanup <path> --non-interactive` with null stdio: it waits 300 ms and removes a clean, landed checkout with no agent, pane, armed loop-task holder, or team board short of `Done`, with no captured output. An unreadable task source keeps the checkout, as does a board read failing for a reason other than not-found. The wrapper writes the agent's end record before starting cleanup, so waiting for that record does not wait for cleanup. Before changing the checkout or relaunching, wait for the wrappers to exit and their cleanup helpers to finish through `rimz::testkit::sandbox::sandbox_processes`, filtered by argv.
- A hook that ends, interrupts, or compacts a turn, and `SessionStart`, spawns a detached `message deliver` for the agent's queued head, with the hook's own environment. A notice the hook itself creates at a boundary, such as a registration re-wake (`harness::team_stage::deliver_stage` through a boundary-mode `message::dispatch`), is sent inline by the hook's apply and is already `Sent` when the hook returns, so that child races only a message queued before the hook; read the message's status straight after the hook returns before designing a forced-order proof. The test cannot await that child, so give each message one deliverer. Either the test delivers it, and queues it only after such a hook (`message::sweep_records_missing_pane_blocker_without_losing_harness_wake_pin`), or the hook delivers it: the hook carries the `zellij-trace` shim, the test's trace log, the pane fixture, and `RIMZ_MESSAGE_SETTLE_MS=0`, and the test waits until the trace holds that message's paste followed by its Enter, never delivering or sweeping it itself (`message::boundary_auto_compact_defers_prompt_until_compaction_ends`). On a live tmux pane, a receiver that appends each line it reads stands in for the trace, since a line lands only after Enter (`backend::tmux::team_stage::flip_and_registration_rewake_reach_receiver_after_done`). Waiting on `Sent` is not enough, since a deliver records `Sent` before it presses Enter. A shim alone does not remove the race: the child still takes the claim, so a deliver from the test finds the message claimed and stops without sending.
- A test that proves a hook drainer's election or idle exit does not drain from the test process. `Env::drain_hooks` runs `hooks drain --once`, which spawns a drainer with its own environment (no `RIMZ_TEST_HOOK_DRAIN_IDLE_MS`, so the 60 s default idle) when the hook's drainer has not bound yet, and that drainer can win the election. Prove election by the hook's frame being applied with no test-side drain, idle exit by `WorkspaceLock::try_acquire` on the drainer lock succeeding (the drainer unlinks its socket before releasing that lock), and succession by connecting to the socket; never by `socket.exists()` at an instant. `hooks::drain::idle_drainer_exits_and_the_next_hook_spawns_a_successor` is the shape.
- Every builder that runs `rimz` or creates a mux server scrubs the ambient session env at construction (`common::ScrubSessionEnvExt` — the `RIMZ_*` identity pin, the `ZELLIJ*`/`TMUX*` detection vars, and systemd's `INVOCATION_ID`, which would otherwise route loop ticks through `systemd-run --user` at a fixture runtime dir with no bus, and the provider home and config keys such as `CODEX_HOME` and `CLAUDE_CONFIG_DIR`, which adapters resolve ahead of the fixture `HOME` and which an agent on a named account passes to every child), so a suite run from inside a live RimZ room behaves like a clean shell; a test that needs one of these sets it explicitly afterwards. The same scrub sets `RIMZ_CODEX_BIN` to a path that does not exist, so every fixture room reads codex as not installed, as CI does: no broker pane, and no host `codex app-server` or `codex login status`. A fake `codex` on `PATH` stands in for the agent a test launches, never for those; a test about the app-server, the broker, or the login probe sets `RIMZ_CODEX_BIN` to `codex_appserver_stub()` or its own fake on the command that births the room. A session born in the test process (`open_sidebar` with `sidebar_opts` or a `SidebarPaneOptions` literal) builds no command, so the scrub never reaches it: its mux server and panes inherit the test process's environment, where `cargo xtask test` exports the same missing-path default to every nextest run. Under a bare `cargo nextest run` those in-process births are not covered and can start the host `codex`. Other host provider CLIs remain reachable on a fixture's PATH, so a test counting PATH-level forks holds the accounts cache fresh, as the `Fixture` in `performance/sidebar_diff_stats.rs` does. Every `rimz start` that does not reattach a live room also runs each reachable provider CLI's `--version` through hook detection (`cli::hooks::hook_install::ensure_detected_agent_hooks`), which on a host with several of them installed costs seconds before the session birth.
- A shim or fixture command that feeds a provider hook (`rimz hooks feed --source <provider>`) pins `RIMZ_AGENT_PID` to `Env::agent_owner_pid()`. The scrub removes it, and without it the hook resolves its owner by walking the process tree to the nearest provider ancestor. When the suite runs from an agent's shell, that ancestor is the agent itself, so the event lands on the wrong owner. A case can pass in one shell and fail in another this way, as `loop_schedule::named_resident_case`'s SessionEnd shim did. Pin the fixture's owner, not `std::process::id()`: the test process outlives every pane, so an end record keyed to it never settles the cohort.
- Every real `rimz` child pins `RIMZ_HOME` through `Env::rimz`/`rimz_at`/`pin_pty_command`, an explicit command environment, a shell or argv prefix, or inheritance from a Zellij server started through `ZellijNamespace`/`ZellijBackend::with_runtime_dir`. A tmux pane running `rimz` must re-pin the fixture home, by its command or the session environment. `cargo_bin` returns an executable path, not a spawn; follow that path to the command or server that supplies its environment.
- `Env::rimz_at` (behind `Env::rimz`) and `Env::pin_pty_command` also build the `rimz` children of the journey and live-backend tiers (`journey::`, `backend::tmux::`, `backend::zellij::`), which `gate` does not run, so a change to either builder also runs `cargo xtask test -P journey` and `cargo xtask test -P live`.
- The suite scrubs `TMUX*` on every builder, so tmux clients without `-u` choose UTF-8 from locale alone: a developer's UTF-8 `LANG` can hide the loss that CI's image, which sets no `LANG` or `LC_*` variables, exposes. Reproduce at the room birth: set `LC_ALL=C` and remove `LANG` and `LC_CTYPE` on the `rimz` child that starts the room, so its sidebar inherits the C locale, rather than changing only the test process's locale. Test-server clients pass `-u` to read the names the server actually holds.
- To prove a run leaves provider accounts alone, run the whole gate, lib unit tests included, with `CODEX_HOME`/`CLAUDE_CONFIG_DIR` pointed at sentinel copies and logging `claude`/`codex` shims first on `PATH` (each appends `$NEXTEST_TEST_NAME $*` to a log and exits 1); compare the sentinel tree and checksums before and after, and read the log for tests that start a real CLI. Checking only the sentinels, or only this binary, finds one leak per round.
- Run no CPU-saturating stress (`cargo xtask stress`, mass repeats, or parallel copies of a test) unless the user asks or allows it: the host is shared, and saturation starves other agents.
- Stress a load-only flake with `cargo xtask stress <module>::<test>`, not through nextest, whose retries and group caps hide the rate you are measuring. The command builds and locates the test's binary, runs 400 copies of it two per CPU in the test sandbox while one busy process per CPU holds the host, and prints the 1-minute load average before and after the batch beside `failed: K/N`; each failing copy's output, run with a backtrace so a helper's panic names the call in the test, stays under `--out` with `summary.txt`. Give each batch its own `--out`: the command refuses a directory that already holds kept copies. A batch the xtask budget stops still writes `summary.txt`, counting only the copies that completed; widen the budget with `RIMZ_XTASK_TIMEOUT` for a long batch. Record the load beside the count; a batch that another worktree's stress run overlapped is not a baseline. Check for one by process name, `pgrep -ax xtask`, and read the listed command lines for a `stress` argument; `pgrep -af 'xtask stress'` also matches every agent shell whose own command line quotes the phrase. When an overlapping run stresses the same test, find what it is fixing before planning: its checkout is `/proc/<pid>/cwd`, and once it has exited, its `--out` name, the open PRs, and the trunk log for the test file say. Before a loaded batch, stress a matched pre-existing test, one that goes through the same fixture helpers as the test under proof, with the same flags first: when that control itself fails most copies (one run saw about 90% at load 160 to 675 on 30 cores), the batch measures the host, so lower `--jobs` until the control passes before reading anything into the new test. When more than about one copy in ten fails in fixture setup (room birth, launch timeouts), the batch measures the host: halve `--jobs` and `--hogs` and rerun before counting the test's own signature. Count failures before and after the fix; a race that shows 1–3 in 400 loaded copies is typically 0 unloaded. A first batch started on an idle host can under-load a race, since the load is still climbing while its copies run: one flake showed 0 in 400 from load 10 and 4 in 1,200 only in a batch that started near 100. Run a second batch straight after the first to start it loaded before reading a zero as a baseline. A load-only flake first seen under ambient load (other agents' builds) may not reproduce from the batch's own hogs. Record the load at the time of the original failure, and when the baseline reads 0 at a lower load, raise `--jobs`/`--hogs` until the load matches before spending more batches; if it cannot be matched, say the fix rests on design and stop. When a flake was reported across several tests, give each candidate one loaded batch before spending a second on any; a shared cause can show in only one of them (one fix saw 0 in 800 on the first candidate and 1 in 400 on the second). Classify each failing copy by its panic before counting. A fix is shown by the bug's own signature going to zero across the after-batches; copies that fail in fixture setup (room birth, launch timeouts) are listed separately and do not count against the fix. A new test stressed beside its control is read the same way: it passes when no copy fails an assertion the test itself makes about the behaviour under proof, and failures in shared session setup are classified by their site and compared with the control's sites across batches, not by one batch's count. That zero takes two batches on the final tree at the failing baseline's own flags, each with at least the baseline's copies, before calling it 0; when the last residual was rarer than one per baseline batch (1 in N), size both batches with `--copies` to hold at least 4N between them as well. Judge an after-batch by matching the baseline's shape (copies, `--jobs`, `--hogs`), not by the load it ends at: a fixed test finishes sooner and ends lower (one run's fixed batches ended at 69 to 98 against 128 for their baseline). Avoid a load mismatch rather than explaining it: `cargo xtask stress` builds and runs the test from the checkout it is started in, so commit the fix before the baseline, check out the parent in a second checkout (another linked `git worktree` or a standalone clone: the stress sandbox's only Git setup is a `safe.directory` entry for the checkout under its own `HOME`, so either runs), and alternate baseline and fixed batches between the two checkouts (base, fixed, base, fixed) so each pair runs at the same ambient load; a fixed batch run after a long rebuild can meet a host that has gone quiet. 4N alone can come out too small to hold the jobs busy (16 to 206 copies against 60 jobs in one run). Copies run in parallel by default because a race against a spawned child's startup can stay at 0 in a serial loop, where a warm binary starts fast; `--jobs 1` is that serial loop, for a test whose copies would contend with each other rather than with the suite. To read a failing copy's store, event log, and diagnostics, add `--env RIMZ_TEST_KEEP_FAILED=1`: an `Env` dropped while panicking moves its home and runtime roots to `/tmp/rimz-test-kept-*/` and prints a `rimz-test-kept-roots:` line naming them into that copy's `run-N.out`. The copy's event log is `rimz-home/ws/<workspace>/log/events.log.jsonl` under the kept home root; each line carries a length and a CRC before the JSON, so read it with `cut -d' ' -f3- | jq`. Paths recorded inside the kept state still name the original roots, and the kept directories are yours to delete. `cargo xtask test` strips the variable; a bare `cargo nextest run` carries it. To prove a run keeps or moves an artifact, assert on the contents at the destination and make the probe test fail with an uncaught panic: a missing original path holds after removal and after a move alike, and stress keeps output only for failing copies.
- The `remote_attach` web-relay tests run `--web` without a port, so every relay child on the host scans the same 100 ports (8300..=8399). A stress copy that fails with `no free local web tunnel port in 8300..8399` under `binding local web tunnel relay` is that range exhausted by more than 100 concurrent `--web` children (one default batch on a host with over 50 CPUs, or two overlapping batches on a smaller one), not a pick-then-bind race: lower `--jobs` and rerun.
- A probe that wraps `rimz` does nothing before the command under suspicion: capture state after that command returns or alongside it, since a few tens of milliseconds of probe work can close the race being hunted (about 380 wrapped runs of one rebirth flake showed no failure for this reason). Show the probe reproducing the failure before using it to refute a cause, and count a known-positive baseline of an event before reporting it absent.
- Prove a race between two production timers with an environment override that forces the losing order before spending a stress batch on it: a 0 ms `RIMZ_REMOTE_REACHABLE_RETRY_MS` made the unreachable-endpoint hold test fail every run on the unfixed tree, while 400 loaded copies showed that race 0 times. The forced run proves the cause and must pass on the fixed tree; the loaded batches are the regression check. A timer override forces only a loser that stays lost. When the losing side recovers, as a failed `message deliver` requeues its message, hold it inside its window with a rendezvous such as `RIMZ_TEST_DELIVERY_AFTER_CLAIM` instead: settle 0 plus a sleep failed 1 of the 5 queue-before-hook tests in `message.rs` on the unfixed tree, while holding the hook's deliver after its claim failed all 5. To hold a hook's own `message deliver`, set the rendezvous variable on the `hooks feed` command: the hook copies every `RIMZ_*` variable into the environment of its detached children.
- Product durations have `testkit`-only overrides, each in milliseconds: `RIMZ_TEST_ENV_PROBE_TIMEOUT_MS` (the launch environment probe; `Env::rimz_at` and `Env::pin_pty_command` set it suite-wide to 20 s, so a test needing another value sets it on its own command. The probe times out only while still running at one of its 25 ms polls past the deadline: a short value does not reliably fail a fast probe, so force a timeout with a login shell that blocks, as `run::supervised_probe_timeout_honors_the_test_override` does, and a value below the probe's duration under load fails any launch that must succeed), `RIMZ_TEST_HOOK_REPLY_WAIT_MS` (the 1.2 s a reply-bearing `hooks feed` waits for the drainer; set it long, 30 s, on a test with a live drainer so load cannot turn the reply neutral), `RIMZ_TEST_HOOK_APPLY_TIMEOUT_MS` (the drainer's 30 s apply-child deadline), `RIMZ_TEST_HOOK_DRAIN_ONCE_WAIT_MS` (`hooks drain --once`), and `RIMZ_TEST_HOOK_REPLY_RETENTION_MS` (how long the drainer keeps an unclaimed reply). Set the hook overrides on the `Command` from `Env::hook_command` or `drain_command`, never on the test process, which the builders scrub. A late reply is neutral by design, so a test that parses the hook's stdout after a drainer reply must set the reply wait.
- To wrap `rimz` without a source edit, use the path `common::shim::cargo_bin` checks first: a `rimz` in the grandparent directory of the running test executable. A directory holding a wrapper `rimz` and a copy of the binary at `deps/integration-<hash>` intercepts the test's own calls (`Env::rimz_bin`) and the hook feeds of `common::shim::write_hook_firing_agent`; room panes run the staged build the room records at birth (`RoomContext::claim_owner`) and bypass it.
- An assertion on an event count prints the events on failure: a CI failure that names no writer cannot be traced afterwards.
- A test that kills a pane or process after polling for a readiness event checks that the event is written after the killed process installed the handlers whose behaviour the test asserts. A supervising `rimz agents exec` wrapper installs its SIGHUP/SIGTERM handlers before its first pane binding, so its own first `agent.attached` (runtime owner is the wrapper) is a valid readiness point for its hangup behaviour. Prove a new such test through the stress loop above, not one nextest run.
- A nextest `FLAKY` result's failed tries and full output are the `<flakyFailure>` elements in the `nextest-junit` artifact's `live/junit.xml`.
- A flake on a file's `(mtime, len)` identity, such as a stat-keyed parse cache serving the prior parse after a same-length republish, runs the other way: load spreads the writes across mtime ticks and hides it. Loop it unloaded a few thousand times instead. `--hogs 0 --jobs 1 --copies 4000` is that loop.
- A failure that is fast in CI needs fast local runs: compare the failing CI attempt's duration with one unloaded local run and read `uptime` first. If the local run takes several times the CI duration, or the load average is far above `nproc` before you start, the loop measures the host, so instrument the test and reproduce in CI instead.
- For a process-tree flake, first trace one run with `strace -f -tt -s 4096 -e trace=execve,clone3,wait4` (strace cuts each string at 32 bytes by default, which hides an argv marker such as `__RIMZ_ENV_PROBE_START__`), then widen the suspected child's lifetime with a PATH shim. The trace names the extra child; the shim tests whether its lifetime causes the consumer's failure.
- Before reading code for a CI-only flake, read the panic body of every failed try in the failed attempt's junit (fetched as the next bullet says). A retry that fails at a different assertion than the first try often settles a theory in one step. Each try's full output is in its `<failure>` and `<rerunFailure>` bodies, while the step log keeps only a truncated tail.
- `gh run download <run> -n nextest-junit` returns only the latest attempt, which is usually the passing one. List a run's attempts with `gh api repos/<owner>/<repo>/actions/runs/<run>/attempts/<n>` and fetch the failed attempt's report by artifact id. Fetch a failed attempt's log with `gh run view <run> --attempt <n> --job <id> --log > <file>`; the `gh api .../logs` route refuses its terminal escape codes.
- A rebirth that plans no resume for an agent prints nothing at the default log level: a skipped candidate gets a `not resumed:` line, an agent that never became a candidate gets none. Run that `rimz start` with `RUST_LOG=warn,rimz::harness::rebirth=debug,rimz::cli::room=debug` (`journey::deep`'s `REBIRTH_TRACE`) and read its stderr: it names the birth path (session already live, or inspected with the candidate count), the roster read (absent or unreadable, or its entry count and how many have an audit row), and, per agent, why it is not a candidate (`ended`, `owner live` with the pid, `no audit row`) or why a candidate got no tab. Read room state only after that start, never between a teardown and it: a probe there delays the rebirth by 20 to 150 ms, enough to hide a race a fast run loses. `records/last-death.json` lists an agent whenever the roster named it, whatever the later gates decided.
- **Invariant.** In-process workspace identity resolves through `common::Env::resolve_workspace`, under the same home as the fixture's child; an explicit root override uses `WorkspaceResolver::resolve_under` with the fixture's home. The invariant gate rejects ambient-home resolver entries and state or runtime path constructors under the test tree. Id-only constructors have one allowance: fixture binaries, which inherit their caller's pinned home. Explicit paths use `StatePaths::for_project_root_under` with the fixture's home, and runtime paths come from `RuntimePaths::for_state_under` over those state paths, as `common::Env::runtime_paths` does. A test reads the diagnostics log through `rimz::diag::DiagSink::under(state.root, state.workspace_id, ..).log_path()` on the fixture's `StatePaths`, since the gate rejects the log's file name under the test tree.
- `Env::new` creates no state root, so an id with no state is the fixture's default. Before making an id-only command refuse an unknown id, search this suite for tests that run it on a fresh `Env`; `gc::sidebar_snapshot_does_not_create_an_abandoned_state_scaffold` pins that read-only commands tolerate an absent workspace.
- A flake that shows only in some full-suite runs may depend on the runner's own state rather than on load. When the error names a derived identifier (a session or directory name), rerun `cargo xtask stress` with `--env RIMZ_HOME=<fill>`, a directory pre-filled with non-owned `ws/collide-<hex4>` directories covering all 65,536 four-hex prefixes, using a slug different from the fixture's: an unrecorded directory with the fixture's own slug is adopted, not a collision. Id-only lookups adopt only a recorded directory, so the unrecorded collision fill cannot absorb them. Any new entry under the fill after a run marks a runner-home write; inspect both machine-wide additions and children of the collision directories with `find "$F" -mindepth 1 -not -path "$F/ws/collide-*" -not -path "$F/ws"; find "$F/ws" -mindepth 2`, where `F` is the fill root used as `RIMZ_HOME`.
- A `rimz start` that births a session under the `zellij-trace` shim waits for the sidebar layout (10 s, and again after a re-birth) until `action list-panes` shows a sidebar pane and a second live terminal. The shim's `handle_action_query` supplies the materialized room for a session it has born unless `RIMZ_TEST_ZELLIJ_LIST_PANES` or `RIMZ_TEST_ZELLIJ_LIST_PANES_FILE` overrides it; an override used during birth must include the sidebar and a work terminal (`common::room::MATERIALIZED_ROOM_PANES`). A birth whose override lacks them logs `did not materialize` on stderr, re-births, and spends both 10 s ceilings, so a start that runs about 20 s slow is this case. No topology seed, before or after start, satisfies the layout wait. Hold `common::room::ShimRoom::watch` on the command's trace log across the start for topology reads that follow birth; it answers the birth and each topology dump the way the presence plugin would.
- Find where a slow command idles before reading code: run the test binary (the `binary:` line `cargo xtask stress` prints) under `strace -f -tt -s 4096 -e trace=execve,clone,clone3 -o <file> <bin> --exact <module>::<test> --test-threads=1` (the `clone` lines show which process spawned each child), keep the `execve`, `clone`, and `exited with` lines, and read the gaps between them; a gap that matches a production constant (a 25ms poll for 1.5s or 3s) is a designed wait the fixture never satisfies, not load. Add `clock_nanosleep` to the trace set and group its lines by thread id: a thread repeating one short sleep for seconds is a poll, and its run length is the wait. Read the trace past the failing step, through the test's next read of state the traced processes write: a value written after the event the test waited on is a second race in the same test. Add `openat` to the trace set and keep its `ENOENT` lines to see what the idle process polls for. Satisfy it the way the real writer would rather than raising a timeout: seed the sidebar heartbeat a live room carries, or bind the child pane the way its hook does (`common::room` holds both, for Zellij and tmux). Under strace, stop the traced child by its own PID (`pgrep -P <strace pid>`), not strace's: killing strace leaves the child running, and `wait` never returns. A one-shot `sidebar snapshot`/`frame` walks provider transcripts only when no live sidebar serves spending for the same `RIMZ_HOME` (any room on the machine counts) and no current-version `provider-spending.json` exists. It is slow only when `cache/providers/spending.json` is cold. `Env` isolates `HOME` and hides that cost, so reproduce with a scratch `RIMZ_HOME` and the real `HOME` before assuming a designed poll. A dead room needs its `workspace.json` for `--no-produce` to take the consumer read.
- A gap inside a copy is a filesystem wait, not a hang: agent `/tmp` on the dev hosts is ZFS with block cloning on, and coreutils `cp`, `install`, and `cat` clone a just-written file (`FICLONE`, `copy_file_range`), which waits for the pool's transaction-group sync, seconds under gate load. Add `ioctl,copy_file_range` to the trace set to see it. A shim that copies a fresh fixture file uses `dd`, which reads and writes, and product code that places a file it just wrote renames it within one directory.
- Rank tests by time before tracing: `cargo xtask test` prints only the summary, so run `cargo nextest run -p rimz --test integration --status-level pass -E '<filter>' > /tmp/<file>.log 2>&1`, then sort its `PASS [ Ns ]` and `LEAK [ Ns ]` lines (nextest marks a passing test that leaves a child holding its stdio as `LEAK`, most of this suite) with `grep -E '(PASS|LEAK) \[' <log> | sort -t'[' -k2 -rn`. For a serial shell loop, time with zsh `$EPOCHREALTIME` after `zmodload zsh/datetime` (unloaded, it expands empty and every duration reads zero), not `bc`, which the dev hosts lack. To report one command's duration inside a test across repeated runs (a load proof's slowest start), wrap the command in a temporary `std::time::Instant` that prints to stderr and run `env -u ZELLIJ_SOCKET_DIR cargo nextest run -p rimz --test integration --status-level pass --success-output final -E 'test(=<module>::<test>)'`; `cargo xtask test` prints only its summary, which times the whole test. The timer is not committed.
- A Zellij focus probe sets up the client before it measures. A client that has sent no input since attaching is not moved by `action focus-pane-id` and is not the client a focus-taking `new-pane` follows, so type into it first. An empty `ZELLIJ_CONFIG_DIR` opens a floating first-run wizard that takes focus, so a hand-built probe writes a `config.kdl` with `show_startup_tips false` before attaching. A focus proof for a user-run command issues the action from inside the client's pane, inheriting `ZELLIJ` and `ZELLIJ_PANE_ID`: an action from outside any pane is a different condition.
- Exact geometry assertions over repeated Zellij splits size the anchor's extent to a multiple of the resulting parts. Halving an odd extent takes a cell from a neighbour (a 39-row anchor became 20+20 while its neighbour went from 39 to 38), which reads as a placement fault.
- A live test finds a RimZ-opened Zellij tab by its name once and addresses it by `tab_id` afterwards (`PaneGeometry::tab_id`, `wait_for_tab_sidebar_pane`). With a real sidebar host, the status pass renames a RimZ tab that hosts no agent to the shell name within seconds of its first frame ([tab naming](../../../../docs/internals/multiplexers.md)), so a second name-keyed lookup races that rename and loses under load.

## Placement

- Subdirectory matches tier: `store/` durability and CAS, `backend/` live-mux parity plus the real-browser web suite (`backend/web/`: real ttyd + headless Chromium, self-skipping without them; `RIMZ_TEST_BROWSER` names a Chromium off `PATH`, such as Playwright's `chrome-linux64/chrome`, and passes through the ambient-`RIMZ_*` scrub of `cargo xtask test`), `examples/` the RimZ-authored in-process scripts running under their real interpreter (the Pi extension, the OpenCode plugin), `journey/` rendered user flows, `performance/` bounded resource use. A new suite lands where its tier says, not beside a similar-looking file.
- Host dependencies self-skip: a test that needs `zellij`, `tmux`, or `node` probes for the capability and skips when absent — a local run needs no installed mux, and the OpenCode suite additionally skips a `node` that cannot strip TypeScript syntax. Every self-skip goes through `common::skip` with a reason naming the missing capability, not the test (`tmux not on PATH`, `common::AF_UNIX_SANDBOXED`); the shared probes (`skip_if_sandboxed`, `require_tmux!`, `require_zellij!`, `require_web_stack!`, `common::git::git_missing`, the journey's `rimz_bin`) already call it. It prints the reason and records the skip, and `cargo xtask test` and `gate` list the self-skipped tests by reason after nextest's result, since nextest counts them as passed. GitHub CI runs every tier with `cargo xtask test --deny-skips`, which fails the run on any recorded skip reason that starts with no entry of `.config/allowed-test-skips.txt`, so there a missing `tmux` or `zellij` is a failure and the image must carry both: a new skip reason either gets its capability installed in `ci/Dockerfile` or an allow-list entry saying why CI cannot provide it.
- External seams are faked with the [`tests/fixtures/`](../fixtures/) shims (`zellij-trace`, `git-trace`, `ssh-trace`, `codex-appserver-stub`); mux-driving tests route `rimz` invocations at an isolated tmux server env and a private Zellij runtime so a developer's live sessions stay untouched.
- The journey's hook-firing stub agent fires no lifecycle hook for pasted text, so a message it receives stays `Sent`, never `Delivered`. To prove receipt, fire the receiving turn with `env.run_installed_hook_in_pane` (`UserPromptSubmit` carrying the rendered message text, then `Stop`). Split panes shrink the target pane, so capture with scrollback when asserting on text that may have scrolled.
- The journey `RoomHarness` is not a mux room: it runs one `rimz sidebar serve` on a PTY and stands in for the mux with a JSON pane list (`RIMZ_TEST_PANE_LIST`). There is no client and no focused pane, and replayed hooks run under `Env.runtime_root` while the renderer has its own short runtime directory.
- Time is deterministic: fixed-epoch fixtures, boundary-exact.

## Multiplexer test doubles

No in-process `MuxBackend` fake exists; a failing multiplexer call is a fake executable.

A room born through `zellij-trace` runs no sidebar and never writes a heartbeat itself, so a claimed birth waits out its full six-second sidebar-heartbeat bound unless the fixture publishes one; `common::room::ShimRoom::watch` does.
