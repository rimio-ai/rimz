Your workflow starter: start a run of a deployed workflow by name, and go on at once. A workflow is a graph of steps (`agent`, `command`, `message`) and checks that RimZ walks outside any agent's turn in one checkout. Use it when the user names a workflow to start. For a new `ralph` or `steward` run, launch the agent of that name with the user's goal instead: it writes what the run reads, picks the checkout, and starts the run itself. Authoring or editing a workflow is skill(rimz-workflow-write); a run on a clock, signal, or condition is `schedule` (or skill(rimz-loop) when not served). `rimz workflow show <name>` prints a definition's graph, and its `README.md` says what a run does.

The user owns what a run spends and does unattended: the start, its checkout, `deadline`, `give_up`, `skip_capacity`, and every later resume, extend, restart, and cancel. A request naming a workflow to start approves the start, and omitted arguments keep the definition's defaults; for anything else on that list left open, propose a value (including a dedicated `worktree` when no checkout is named) and ask one question before calling this. An agent pane in the run's checkout, yours included, holds it: an agent step waits until that session closes unless the step takes over an idle checkout or launches beside its occupant.

The answer returns once the run is created, before its first step runs, so any later failure reads through `tasks` and `join`. Tell the user the run's id, that `rimz workflow list` shows what it waits on and an agent's question waits in its pane, and, when the run shares your checkout, that your pane holds it. Unless `detach` is set, its `WORKFLOW_REPORT` reaches you at your next turn boundary and holds you (and any enclosing workflow `turn` step) open until then. To steer a run or try one node with `--once`, call `guide` with `rimz-workflow/steering`; for a stuck or failed run, `rimz-workflow/debugging`.
