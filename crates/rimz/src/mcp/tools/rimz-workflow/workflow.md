Your workflow starter: start a run of a deployed workflow by name, and go on at once. A workflow is a graph of steps and checks that RimZ walks outside any agent's turn: a step does the work (`agent` launches a fresh agent, `command` runs a command, `message` hands work to a running agent), and a check reads the result and picks the next node. A run is one walk of the graph in one checkout. Use it when the user names a workflow to start. For a new `ralph` or `steward` run, launch the agent of that name with the user's goal instead: it writes what the run reads, picks the checkout, and starts the run itself. A new or changed workflow is Skill(rimz-workflow-write), and a run on a clock, signal, or condition is Skill(rimz-loop). `rimz workflow show <name>` prints a definition's graph, and its `README.md` says what a run does.

The user owns what a run spends and does unattended: the start, its checkout, `deadline`, `give_up`, `skip_capacity`, and every later resume, extend, restart, and cancel. A request naming a workflow to start approves the start, and an argument it leaves unset keeps the definition's value. For anything else on that list the request leaves open, propose the value and ask one question before you call this.

`worktree` names the run's RimZ worktree and creates it when missing. Unless the user names a checkout, propose a worktree of its own and ask. A workflow whose `scope` is `project` runs at the project root and refuses `worktree`. An agent pane in the run's checkout, yours included, holds it: an agent step there waits until that session closes, unless the step takes over an idle checkout or launches beside its occupant. `prompt` is added to every agent and message step's prompt. `input` hands the start node a JSON object, as an answer that routed there would: a string `outcome`, and an optional `key`, a string or an integer, that becomes the run's key. `deadline` (`8h`, `fri 18:00`, `2026-11-21`) replaces the definition's; when it passes, the node the run is at fails with cause `deadline`, and a bare date is midnight at its start. `give_up` bounds the waits for capacity, and `skip_capacity` launches agent steps past them.

The answer comes once the run is created, before its first step has run: the id `workflow:<run>`, with `warnings` from the definition's validation. A failure after that reads through `tasks` and `join`. Tell the user the run's id, that `rimz workflow list` shows what it waits on and an agent's question waits in that agent's pane, and, when the run's checkout is yours, that your pane holds it. When the run ends, its `WORKFLOW_REPORT` reaches you at your next turn boundary, and you stay open until then; inside a workflow's `turn` step, that step cannot end until then either. Pass `detach` when you will not be there for the result. `join` blocks on the run, `tasks` lists it, and `stop` cancels it, which is the user's call. To steer it (resume, extend, restart), or for a try of one node with `rimz workflow run --once`, call `guide` with `rimz-workflow/steering`; for a stuck or failed run, `rimz-workflow/debugging`.
