# Integration test traps

What a test in `crates/rimz/tests/integration/` needs beyond its [suite contract](../../crates/rimz/tests/integration/AGENTS.md), by the kind of test in hand: fixture and stand-in behaviour the code does not show. The contract routes here. How to stress, force, read, and trace a flake is in [flakes.md](./flakes.md), and probes built outside the suite are in [probes.md](./probes.md).

## Fixtures and their processes

- Every `Env` and `ZellijNamespace` arms an independent stdin-keepalive reaper before it spawns children. The fixture HOME and runtime values are the process-ownership marker. On orderly drop or abrupt owner death the reaper stops both private mux endpoints, terminates every marker-carrying descendant, and removes the roots. The exception is an `Env` dropped while panicking with `RIMZ_TEST_KEEP_FAILED` on, whose reaped roots are kept ([keep a failing copy's state](./flakes.md#keep-a-failing-copys-state)).
- A test that depends on the marker straight after `spawn` waits for it. A child is identifiable only once its exec has published that environment in `/proc/<pid>/environ`, which can trail `spawn` under load.
- To show that gap, read `/proc/<pid>/environ` once, straight after `spawn`. A full `/proc` walk on a host with many processes usually outlasts the gap, so a local run seldom shows the miss that a small CI container shows. On a busy 24-core host, 942 of 1000 first reads were empty, and the environment appeared within 107 µs.
- `let Fixture { pane, .. } = Fixture::new();` drops every field it does not bind at the end of that statement. An unbound `TempDir` guard then deletes its directory while the live room still uses it.
- Bind each guard field by name (`_dir`, never `_`, which drops it the same way), or keep the whole fixture in one binding. `KeysRoom` in `backend::zellij::sidebar_keys` binds `_cwd` and `_stub_dir` by name: the first run of its split-key test failed at the check that the split opened in the work pane's directory.
- A test that hands a child a port to bind later uses `common::available_loopback_port` (`web::web_stop_stops_writable_and_broadcast_daemons`, for example). A dropped port-0 bind returns its port to the kernel's ephemeral pool, where the child's own port-0 draws (the web daemon's ttyd upstream) or any other process can take it before the child binds.
- `common::Env::rimz_at` defaults stdin to null so directly spawned commands cannot inherit buffered input from a test-running shell loop. Tests that exercise stdin set it explicitly afterwards; PTY commands keep their terminal input.
- `Env::new` creates no state root, so an id with no state is the fixture's default. Before you make an id-only command refuse an unknown id, search this suite for tests that run it on a fresh `Env`. `gc::sidebar_snapshot_does_not_create_an_abandoned_state_scaffold` pins that read-only commands tolerate an absent workspace.
- On an id with no state, a producing `sidebar snapshot --workspace-id` runs the producer only when it also names `--session-name`. Without one it prints the empty rollup ([room-less read](../internals/sidebar/sidebar.md)), so no heavy lane runs and no provider cache such as `accounts.json` is written.
- `Env::snapshot_json_with_panes` passes `--session-name`, with `--mux tmux` and a `RIMZ_TEST_PANE_LIST` fixture standing in for the multiplexer (`oauth_usage::new_pi_session_on_another_provider_moves_the_account_record_and_panel_windows`).
- A fixture that orders files by mtime gives each file a distinct mtime in the order the test means; a tie settled by a secondary key (the path) passes for a reason the test does not assert.
- `backend/web/` runs real ttyd and headless Chromium and self-skips without them: `RIMZ_TEST_BROWSER` names a Chromium off `PATH`, such as Playwright's `chrome-linux64/chrome`, and passes through the ambient-`RIMZ_*` scrub of `cargo xtask test`.
- In an `examples/` suite: a fake plugin context applies upstream's own store effect for each event before it calls the plugin's listener (eviction on delete, async re-hydration on connect), read from the pinned upstream source. A harness that proves an in-process hook module calls its host only after some step logs every fake-host call in order and asserts the log at that step, as `examples/claude_mod.rs` does: a file a spawned stub writes lands asynchronously and cannot show that a call did not start.

## The session-env scrub

Every builder that runs `rimz` or creates a mux server scrubs the ambient session environment at construction (`common::ScrubSessionEnvExt`), so a suite run from inside a live RimZ room behaves like a clean shell.

| The scrub | Effect |
| --- | --- |
| Removes the `RIMZ_*` identity pin (`RIMZ_PROJECT_ROOT`, `RIMZ_WORKSPACE_ID`, `RIMZ_CHANNEL`, `RIMZ_WORKTREE_PATH`) | The child resolves the fixture's room |
| Removes the `ZELLIJ*` and `TMUX*` detection variables | The child detects no ambient multiplexer |
| Removes systemd's `INVOCATION_ID` | Loop ticks are not routed through `systemd-run --user` at a fixture runtime directory with no bus |
| Removes the provider home and config keys, such as `CODEX_HOME` and `CLAUDE_CONFIG_DIR` | Adapters resolve these ahead of the fixture `HOME`, and an agent on a named account passes them to every child |
| Sets `RIMZ_CODEX_BIN` to a path that does not exist | Every fixture room reads codex as not installed, as CI does: no broker pane, and no host `codex app-server` or `codex login status` |
| Sets `RIMZ_PRICING_OFFLINE=1` | No child fetches live pricing lists |
| Sets `RIMZ_TEST_PRESSURE_ROOT` to a missing root | No child reads the host's pressure |

- A test that needs a variable the scrub removes sets it on its command after the builder.
- A pressure test sets its fixture root after the scrub. A test that needs prices calls `agents::pricing::testkit::seed_cache` in its own fixture home. A test that needs a real fetch sets `RIMZ_PRICING_OFFLINE` to `0` after the scrub.
- A fake `codex` on `PATH` stands in for the agent a test launches, never for the app-server, broker, or login probe. A test about those sets `RIMZ_CODEX_BIN` to `codex_appserver_stub()` or its own fake, on the command that births the room.
- A session born in the test process (`open_sidebar` with `sidebar_opts` or a `SidebarPaneOptions` literal) builds no command, so the scrub never reaches it. Its mux server and panes inherit the test process's environment.
- `cargo xtask test`, gate, coverage, and stress export the three defaults to test processes, which covers in-process births and spending walks ([test environment](./gates.md#test-environment)). Under a bare `cargo nextest run` that in-process code can start the host `codex`, fetch pricing, or read live pressure.
- Other host provider CLIs remain reachable on a fixture's `PATH`. A test that counts PATH-level forks holds the accounts cache fresh, as the `Fixture` in `performance/sidebar_diff_stats.rs` does.
- Every `rimz start` that does not reattach a live room runs each reachable provider CLI's `--version` through hook detection (`cli::hooks::hook_install::ensure_detected_agent_hooks`). On a host with several of them installed, that costs seconds before the session birth.
- A new reader of host state (PSI, `/proc/meminfo`, `statvfs`) on a path a spawned `rimz` or a fold reaches gets a testkit override, defaulted to a fixed value by `ScrubSessionEnvExt` and the xtask test-process export, as `RIMZ_CODEX_BIN` is.
- To prove a run leaves provider accounts alone, run the whole gate, lib unit tests included, with `CODEX_HOME`/`CLAUDE_CONFIG_DIR` pointed at sentinel copies and logging `claude`/`codex` shims first on `PATH` (each appends `$NEXTEST_TEST_NAME $*` to a log and exits 1); compare the sentinel tree and checksums before and after, and read the log for tests that start a real CLI. Checking only the sentinels, or only this binary, finds one leak per round.

## Waits and reads

- A negative assertion over what an attached client received first waits for evidence in that client's own recorded stream that the payload rendered: a server-side `capture_pane` says nothing about which bytes the client has been sent yet.
- A helper that reads a PTY polls until every piece it asserts is present, and only then asserts. One `write!` to stdout can reach the pty in several `write(2)` calls, because line-buffered stdout flushes at each format piece that holds a newline, so a read can land between them. `sidebar_supervisor::Pane::notice` waits for its whole frame.
- A replica built to count those calls passes runtime arguments. rustc folds a literal argument into the format string, so a replica with literals writes once where the product writes twice.
- A test that reads a spawned child's stderr or stdout only up to the line it waits for keeps the reader alive until the child exits (`lines.by_ref()`, held past `child.wait()`): a dropped reader closes the pipe, and the child's next write fails with EPIPE, which a `writeln!(..)?` turns into a non-zero exit.
- A race test builds the consumer's command before the producer's step runs. Fixture setup between them can outlast the race window, and the test then passes on the unfixed tree: `teams_flip::stop_receipt_resume_command_reopens_the_unregistered_cohort` passed there until it built its resume command before `teams stop`.
- A test that waits for an outcome the LSP broker decides at its 5 s housekeeping pass observes it through a channel that is not a request: a notification the broker pushes, or a `status` read, which counts as none. It sends no request until the outcome is seen. A recycle is skipped at every sample that finds a request outstanding, and an idle stop counts its timeout from the last request, so a test that polls with requests can postpone the outcome indefinitely.
- State that the outcome writes, such as an `lsp-history.jsonl` line, is read once after an answer that implies it, never polled inside the deadline loop. `lsp::lsp_recycles_after_an_outstanding_editor_request_finishes` polled with a `workspace/symbol` request every 2 ms and failed CI twice. With each stub reply delayed past the 5 s interval, it failed every run.
- A test that kills a pane or process after polling for a readiness event checks that the event is written after the killed process installed the handlers whose behaviour the test asserts. A supervising `rimz agents exec` wrapper installs its SIGHUP/SIGTERM handlers before its first pane binding, so its own first `agent.attached` (runtime owner is the wrapper) is a valid readiness point for its hangup behaviour. Prove a new such test through a [stress batch](./flakes.md#stress-batches), not one nextest run.
- A test that kills a process and then runs a command that judges whether that process is alive (a `workflow advance` reclaiming a dead host) first waits until `rimz::proc::process_is_live(pid, None)` reads false, bounded through the suite's own poll. `kill(2)` returns once the signal is queued, and the target reads live in `/proc` until it exits; one in uninterruptible sleep, such as the parent-directory fsync of a durable write under gate load, takes the signal only when that sleep ends. A command that reads it live in that window acts on a live process, and a fixture with no scheduler tick never retries: `dead_host_check_group` in `workflow/shells.rs` waits this way.
- A change that adds an assertion to an existing test re-reads every fixed sleep and readiness poll ahead of it against the new assertion: a wait that covered the old assertion may end before the state the new one reads exists.
- A value captured from a wait is checked against what its later comparisons assert. A wait predicate narrower than the comparison is a partial-read race.
- When an assertion on a waited-for snapshot finds a wrong or null field, list every writer that can satisfy the wait's condition before you blame the field's producer. `workflow::shells::live_group` once waited only on `attempt.child.pid`, which the `pr` check publishes as well as the `build` step after it, and returned the check's attempt with its by-design null `head_start`. It names the node whose attempt it waits for.
- A check of the state after a release (a freeze or a hold expiring) compares only with values read after the release. A capture taken while the released state held shows what the release discards. The expiry step of `backend::zellij::shared_view::two_clients_split_join_and_carry_the_sidebar_view` once compared its top card with the order captured while the freeze held, and failed on a correct sidebar when a card arrived in between.
- A fix to one instance of a test race greps the same file for that pattern and fixes every instance in the same commit. A live backend test also sweeps the other backend's tree (`backend/tmux/` or `backend/zellij/`).
- For a deadline race, the pattern is what the wait sits behind, and its value says little. List every fixed deadline in the file (`rg -n 'Instant::now\(\) \+' <file>`, plus its `#[path]` submodules) and classify each by what fills its window.
- A wall-clock bound that a fixture hold can outlast is found through its measurements. List every measurement in the file (`rg -n 'elapsed\(\)|duration_since' <file>`), follow each to the bound it is checked against, and pair that bound with every hold the test's fixture applies. Include a hold the fixture hard-codes behind a switch (ssh-trace's `RIMZ_TEST_SSH_LATE_OUTPUT`).

## Launches and provider stand-ins

- A row created by `rimz agents exec` keeps its card only while its runtime owner lives; to produce or enforce on it, spawn the exec with `common::write_long_lived_agent_shim`. Its stand-in answers `--version` at once, because a launch plan probes `<agent> --version` under a 3 s budget before it spawns the provider and binds the pane: a stand-in that hangs there spends that budget, and a resume's sender, whose pane-bind window is also 3 s, fails under load.
- A test that needs a rival the resolver sees beside an agent in its lane (another agent answering the same role) does three things before it resolves a handle. It seeds the rival's launch in another checkout of that lane, registers it with a `Registered` lifecycle append, and asserts it is in `rimz::address::addressable_agents(&env.store().snapshot_cached().unwrap())`. `loop_schedule::team_signal_payload_handles_round_trip_beside_teamless_role_rivals` is the shape.
- Without those steps the rival is gone and the test passes without the fix. In the agent's own checkout the store reaps the older of two paneless sessions on the same worktree and branch (`older_yields_pane` in `crates/rimz/src/store/session_death.rs`). An unregistered launch card yields its role to a registered holder in its lane (`prefer_claimed` in `crates/rimz/src/address.rs`).
- A pane-launched provider, a workflow judge included, leads no group: the exec wrapper spawns it in the wrapper's own process group.
- A change that adds live tests that detect a provider proves them where no real CLI answers. Before hand-off, run the live tests a change adds with the host CLI hidden: `bwrap --dev-bind / / --ro-bind /dev/null "$(readlink -f "$(command -v claude)")" -- cargo xtask test ...`. The bind names the resolved binary because bwrap cannot bind over a symlink, and a host `claude` is often one.
- A test that reads the wrapper pane's root process (`rimz::proc::hosted_agent_process_for_root`, `/proc/<pane_pid>/cmdline`) waits until that argv carries `--supervise`: the wrapper spawns the provider first and then execs itself into its parked image, and its cmdline reads empty while the execve runs.
- Closing an agent's pane or window in a managed worktree makes its wrapper spawn a detached `rimz worktree cleanup <path> --non-interactive` with null stdio. Cleanup waits 300 ms, then removes a clean, landed checkout that has no agent, pane, armed loop-task holder, team board short of `Done`, or unfinished workflow run.
- An unreadable task or workflow-run source keeps the checkout, as does a board read that fails for a reason other than not-found.
- The wrapper writes the agent's end record before it starts cleanup, so waiting for that record does not wait for cleanup. Before you change the checkout or relaunch, wait for the wrappers to exit and their cleanup helpers to finish through `rimz::testkit::sandbox::sandbox_processes`, filtered by argv.

## Hooks and message delivery

- A hook that ends, interrupts, or compacts a turn, and `SessionStart`, spawns a detached `message deliver` for the agent's queued head, with the hook's own environment. The test cannot await that child, so give each message one deliverer, in one of two ways.
- The test delivers the message, and queues it only after such a hook (`message::sweep_delivers_queued_harness_records_to_the_agents_current_pane_in_order`).
- Or the hook delivers it. The hook carries the `zellij-trace` shim, the test's trace log, the pane fixture, and `RIMZ_MESSAGE_SETTLE_MS=0`. The test waits until the trace holds that message's paste followed by its Enter (`common::wait_for_text_then_enter`), and never delivers or sweeps it itself (`message::boundary_auto_compact_defers_prompt_until_compaction_ends`).
- The same holds for a resume wrapper's detached deliverer (`teams_flip::resumed_lazy_leader_gets_its_resume_prompt_then_its_stage`).
- On a live tmux pane, a receiver that appends each line it reads stands in for the trace, since a line lands only after Enter (`backend::tmux::team_stage::flip_and_registration_rewake_reach_receiver_after_done`).
- Waiting on `Sent` is not enough: a deliver records `Sent` before it presses Enter.
- A shim alone does not remove the race. The child still takes the claim, so a deliver from the test finds the message claimed and stops without sending.
- A notice the hook itself creates at a boundary, such as a registration re-wake (`harness::team_stage::deliver_stage` through a boundary-mode `message::dispatch`), is sent inline by the hook's apply and is already `Sent` when the hook returns. The detached child therefore races only a message queued before the hook. Read the message's status straight after the hook returns before you design a forced-order proof.
- A dispatched send carries a compaction line even without `--smart-compact`: `[harness] smart_compact` defaults to 258k tokens and dispatch stores the seat's line on the record. A test of a send with no line turns `[harness] smart_compact` off first.
- A test that proves a hook drainer's election or idle exit does not drain from the test process. `Env::drain_hooks` runs `hooks drain --once`. When the hook's drainer has not bound yet, that command spawns a drainer with its own environment (no `RIMZ_TEST_HOOK_DRAIN_IDLE_MS`, so the 60 s default idle), and that drainer can win the election.
- Prove election by the hook's frame being applied with no test-side drain. Prove idle exit by `WorkspaceLock::try_acquire` succeeding on the drainer lock (the drainer unlinks its socket before it releases that lock). Prove succession by connecting to the socket, never by `socket.exists()` at an instant. `hooks::drain::idle_drainer_exits_and_the_next_hook_spawns_a_successor` is the shape.
- A shim or fixture command that feeds a provider hook (`rimz hooks feed --source <provider>`) pins `RIMZ_AGENT_PID` to `Env::agent_owner_pid()`. The scrub removes the variable, and without it the hook resolves its owner by walking the process tree to the nearest provider ancestor. When the suite runs from an agent's shell, that ancestor is the agent itself, so the event lands on the wrong owner. A case can pass in one shell and fail in another this way, as `loop_schedule::named_resident_case`'s SessionEnd shim did.
- Pin the fixture's owner, not `std::process::id()`. The test process outlives every pane, so an end record keyed to it never settles the cohort.
- The journey's hook-firing stub agent fires no lifecycle hook for pasted text, so a message it receives stays `Sent`, never `Delivered`. To prove receipt, fire the receiving turn with `env.run_installed_hook_in_pane` (`UserPromptSubmit` carrying the rendered message text, then `Stop`). Split panes shrink the target pane, so capture with scrollback when asserting on text that may have scrolled.

## Stops

This section covers a test whose stop must report stopped. The stops are `agents stop`, `teams stop`, `subagents stop`, a workflow attempt's stop or a takeover eviction, and every stop that names a run (`agents stop <run-id>`, `loop stop`, the timeout helper, orphan repair). Such a test gives each agent a pane in its `RIMZ_TEST_PANE_LIST` fixture and an owner process of its own that the stop can end.

- The owner is a file-local `dummy_agent_process` (a `sleep 30` with the session environment scrubbed, in `message.rs`, `loop_schedule.rs` and `workflow/attempts.rs`), handed to `reap_later` and stamped as that agent's `RIMZ_AGENT_PID`.
- Never use the shared `Env::agent_owner_pid` there. A stop sends one SIGTERM to an owner still alive after the pane it closed is gone, and that owner serves every other agent in the test.
- A row with no owner stops only on a recorded end (a provider `SessionEnd` or the reaper). Otherwise the stop fails with `could not confirm its process is gone`.
- To make the owner survive the SIGTERM, use `term_ignoring_process` (in `message.rs`), which ignores it.
- The stop's pane lookup answers with that pane only on evidence that the agent runs in it. The hook records the owner's parent chain, so a pane root pid that is the owner or one of its ancestors proves the pane. The test process is such an ancestor, since `dummy_agent_process` is its child. A root pid that names another live process disproves the pane, and the stop takes its no-pane path.
- A proven pane whose listed `pane_command` names another provider's program is refused the same way. A fixture pane that must bind lists a shell or the agent's own program.
- The raw Zellij listing that a `zellij-trace` stop reads carries no root pid. The pid comes from the topology cache that `common::room::seed_live_zellij_room` writes (`message::the_owners_process_chain_and_the_panes_foreground_decide_whether_a_pane_hosts_it`).
- A pane with no root pid binds only when its listed `pane_command` names the agent's provider program ([sidebar.md](../internals/sidebar/sidebar.md#the-binding-ladder), rung 1).

## Loop tests

- Every fire of a command task opens the root's room before its run starts. A delivery row opens none.
- A Scheduled fire opens the room unless the root has a workspace record and a sidebar heartbeat under 5 s old ([external-fire behaviour](../internals/harness/loops.md#the-external-tick)). A Scheduled fire is a tick's or a signal's detached `rimz loop run` child, or a test that spawns `rimz loop run <name>` itself.
- A Manual `rimz loop fire` births the room only when the root has no workspace record (the room callback `run_one` passes to `TaskFire::prepare`).
- Signal tests seed the heartbeat with `common::room::seed_sidebar_heartbeat`, which dates it ahead so that it stays live for the whole test. Tick-fired tests cannot, because the same heartbeat makes `rimz loop tick` skip the root, so they wait out the room birth.
- When the room is not the subject, seed that heartbeat after `env.record(&env.project_root)`. Without it, a later room-opening run in the same `Env` can be refused while the first room's sidebar has no fresh heartbeat, still starting or stalled past the 5 s TTL (`room::session::claim_listed_room`).
- A wait behind any such runner takes `LOOP_RUNNER_DEADLINE` from `loop_schedule.rs`, a hang guard sized for that birth under gate load.
- A delivering `rimz loop run` appends its terminal record before it releases its run lock (`Fire::record_and_release`). `loop show`, `loop list` and `loop logs` read a held run lock with no task row as a run in flight. In that gap, `loop show` on a delivered wait prints `<task> — one-shot fired · ▸ running` and exits 0 instead of refusing.
- A test that reads one of those commands after it waited on a record written by a runner it did not spawn and await (a tick's detached fire, a watcher's `loop run`) first waits until no process in its sandbox runs `rimz loop run <task>`. `common::wait::wait_for_loop_runs_to_exit` finds them through `rimz::testkit::sandbox::sandbox_processes` and the argv. The lock is `O_CLOEXEC`, so the runner's exit releases it.
- A temporary 3 s sleep after `record_transition` in `Fire::record_and_release` forces the gap. It failed both `wait` tests that assert the refusal, on every run, until they waited.
- `rimz::harness::schedule::run_control::in_flight_run` called from the test process resolves the ambient home, not the fixture's, and waits on nothing.
- A loop test waits on the exact state it reads or acts on next, never on an earlier write by the same runner: the mark's recorded result before it reads the fire mark, the launch child's pid in the mark before it kills the runner (`marked_launch_child` in `loop_kinds.rs`), the runner's exit before it reads anything the run lock gates or sends the next signal. A history row, a stand-in's pid file and a receipt line are each written before at least one of those.
- `rimz loop tick` never fires a condition on `pr` or `ci`: it passes no forge source, so every forge key reads unread (`no sidebar source`). A test fires one as the sidebar host does, `rimz loop run <name> --condition-json '<evidence>'`, after seeding `pr-state.json` and a sidebar heartbeat; `wait::forge_wait_fires_with_its_label_and_pr_reading` is the shape.
- A test asserting that a tick did not fire reads the state the tick writes in-process before it spawns the detached `rimz loop run`: `lanes/loop-fire.json` stamps a row at first sight and at each fire alike, and a condition's fire also sets its `fired` latch in `lanes/loop-when.json`. Messages and rows are written by the detached runner, so their absence right after the tick proves nothing. The first tick of `wait::arm_and_fire`'s condition case is the shape: a temporary edit that let first sight fire failed it on that latch.
- `loop_kinds.rs`, `loop_list.rs`, `loop_overlap.rs`, `loop_rows.rs` and `agents_tune.rs` are `#[path]` submodules of `loop_schedule.rs` (`loop_schedule::kind_tests`, `list_tests`, `overlap_tests`, `row_tests` and `tune_tests`), so a test in one runs as `loop_schedule::<module>::<fn>`, and they reach its private helpers through `use super::*`, so count a helper's callers with `rimz lsp refs`, not a grep of one file.

## Multiplexer doubles and heartbeats

- No in-process `MuxBackend` fake exists; a failing multiplexer call is a fake executable.
- A room born through `zellij-trace` runs no sidebar and never writes a heartbeat itself, so a claimed birth waits out its full six-second sidebar-heartbeat bound unless the fixture publishes one; `common::room::ShimRoom::watch` does.
- A one-shot sidebar heartbeat has no writer behind it, so readers drop it once a loaded host spends more than the 5 s TTL before the read. Every heartbeat reader, wakeup fanout included, judges freshness by file mtime and accepts future dates. Any one-shot heartbeat a test means as live goes through `common::room::seed_sidebar_heartbeat`, or `common::room::date_heartbeat_as_live` after a write whose fields the test sets itself.
- A `rimz start` that births a session under the `zellij-trace` shim waits for the sidebar layout until `action list-panes` shows a sidebar pane and a second live terminal. The wait is 10 s, and 10 s again after a re-birth.
- The shim's `handle_action_query` supplies the materialized room for a session it has born, unless `RIMZ_TEST_ZELLIJ_LIST_PANES` or `RIMZ_TEST_ZELLIJ_LIST_PANES_FILE` overrides it. An override used during birth must include the sidebar and a work terminal (`common::room::MATERIALIZED_ROOM_PANES`).
- A birth whose override lacks them logs `did not materialize` on stderr, re-births, and spends both 10 s ceilings, so a start that runs about 20 s slow is this case. No topology seed, before or after start, satisfies the layout wait.
- For topology reads that follow birth, hold `common::room::ShimRoom::watch` on the command's trace log across the start. It answers the birth and each topology dump the way the presence plugin would.
- `zellij-trace` stands in for the `RIMZ_TEST_PANE_LIST` fixture's multiplexer as well: unless `RIMZ_TEST_ZELLIJ_FAIL_CLOSE_PANE` fails it first, its `action close-pane --pane-id <id>` removes the row whose `pane_id` is `zellij:<id>` from that file, as it removes the row with that `id` from `RIMZ_TEST_ZELLIJ_LIST_PANES_FILE`, so a stop's later hosting read finds the pane gone.
- `RIMZ_TEST_ZELLIJ_HEALTH_PROBE_MS` replaces one 8 s budget shared by two reads RimZ makes of a live Zellij session before it uses it: the `list-panes` health probe (`ZellijBackend::live_session_health_within`), and the topology inspection that `ZellijBackend::open_sidebar` runs on a live session (`ZellijBackend::inspect_session_panes`).
- Set it on a fake meant never to answer the health probe, where it keeps the refusal fast. The unresponsive-room tests in `zellij_health.rs` do: those through `assert_unresponsive_live_room_is_preserved`, `unresponsive_foreign_zellij_session_names_native_recovery_and_bypass`, and `unresponsive_zellij_session_with_unknown_ownership_avoids_destroy_guidance`.
- A test whose shim answers `list-panes` leaves it unset. The probe's first `list-panes` attempt takes the whole budget, so under load one shim start slower than a short budget leaves no retry, reads as an unresponsive room, and fails the command. A 250 ms cap on 26 such tests failed 23 of them once each `list-panes` answer came 0.6 s late.
- Such a shim runs no presence plugin, so the inspection on a live session would wait out its whole 8 s. Without a fresh heartbeat, a command that opens the sidebar on a live session runs the `AddMissing` pass, which falls back to `open_sidebar` and that inspection whenever it defers an add for want of an attached client. A test skips both by seeding the sidebar heartbeat a live room carries (`common::room::seed_sidebar_heartbeat`), as `web::zellij_room_uses_the_same_shared_ttyd_daemon` and `zellij_health::named_attach_preserves_owner_and_records_only_a_launched_client` do.
- A fixture that answers the topology dump instead lets the inspection succeed, and `open_sidebar` then deletes and re-births the room.
- A supervised attach (`RIMZ_REMOTE_SUPERVISED`) checks session liveness at once and then every 2 s, needs a Live check followed by a Gone check, and a test driving it sets `RIMZ_REMOTE_WATCHDOG_MS` short. A pass that proves the client exiting between checks (`RIMZ_TEST_ZELLIJ_WATCHDOG_ATTACH_EXIT`) keeps the interval long enough for the client to exit before the next check: `remote_attach::supervised_remote_attach_ends_when_the_session_disappears` sets 1000 ms there.
- A `ZellijNamespace` server pins `RIMZ_HOME` to the namespace root, while `Env::rimz` pins the `Env`'s home, so a `rimz` command run through `Env` against that server sits in another process domain. Every heuristic kill passes the domain guard (`rimz::mux::domain`), which spares a process from another RimZ home, so such a command reaps none of the server's panes. A test that asserts a reap births the server with the `Env`'s `RIMZ_HOME`, as `RepairRoom::birth` in `backend/zellij/reconcile.rs` does.

## Signals and stopped processes

- A shell runs a trap only after its foreground command returns. A signal is therefore held behind that command, unless the command is already running as a program the signal kills.
- A check script that must react to a signal backgrounds its long wait before it publishes readiness, blocks in the `wait` builtin, and stops the background child in its trap (a background command ignores SIGINT).
- Before signalling that script, a test waits for the background child's executable, not only its pid. Between fork and exec the child can still carry the parent's traps and swallow an early TERM.
- A test of delivery to a process group keeps that trap in a member other than the group leader, since the leader is the PID a single-process signal would also reach.
- To emulate signal delivery outside the suite, start the subject from a non-shell launcher in its own session (Python `subprocess.Popen(..., start_new_session=True)`). A shell that backgrounds it with `&` starts it with SIGINT ignored, and every result reads as a lost signal.
- A test that SIGSTOPs a process tree keeps every stopped process from forking. `/bin/sh` may be dash, which vforks external commands, and a child stopped between vfork and exec holds its parent in `D`, never `T`, so a `sleep` poll loop can strand the stop wait under load. Block the script in a builtin `read` from a FIFO the test creates, and release it by opening the FIFO read-write and writing a line (`sandbox::sandbox_guard_restores_a_replaced_entry_while_the_view_is_stopped`).

## Builds and wrapped binaries

- `RIMZ_BIN` redirects every detached `rimz` helper spawn; point it at a missing path to exercise a spawn failure, which unit tests cannot reach, or at an executable that exits at once (`/bin/true`) to exercise a helper that spawns but never serves. A wrapper that runs the real binary and atomically records its exit status tells a test when a detached helper that leaves no durable trace has finished.
- A test that needs two builds takes them from `common::builds::RoomBuilds`, which patches the `.note.gnu.build-id` bytes of a binary copy and records the first as the room build. Appending bytes leaves `build_id::of_file` unchanged, and staging dedups by that id.
- A test that needs the binary at a second path hard-links it into a `tempfile::tempdir_in` the binary's own directory. A copy of the debug binary is a cold exec and heavy I/O that slows parallel neighbours past their deadlines under gate load.
- A test that runs `rimz reload` from the second build writes that build at its staged path, `builds/<id>/rimz` under the fixture's `RIMZ_HOME`, so staging reuses it. Otherwise staging clones a just-written binary, and that clone waits on the filesystem inside the test's window (`hooks::drain::reload_replaces_the_drainer_after_its_inflight_frame`).
- To wrap `rimz` without a source edit, use the path `common::shim::cargo_bin` checks first: a `rimz` in the grandparent directory of the running test executable. A directory that holds a wrapper `rimz` and a copy of the binary at `deps/integration-<hash>` intercepts the test's own calls (`Env::rimz_bin`) and the hook feeds of `common::shim::write_hook_firing_agent`.
- Room panes bypass the wrapper: they run the staged build the room records at birth (`RoomContext::claim_owner`).
- The same grandparent lookup serves every `cargo_bin` fixture, `zellij-trace` included.
- A wrapper names its tools by absolute path. Many tests pin `PATH` to a fixture bin directory, where a bare `sleep` fails silently and the wrapper adds no delay.

## Duration overrides

Product durations have `testkit`-only overrides, each in milliseconds.

| Variable | Replaces | Set it when |
| --- | --- | --- |
| `RIMZ_TEST_ENV_PROBE_TIMEOUT_MS` | The launch environment probe's timeout | `Env::rimz_at` and `Env::pin_pty_command` set it suite-wide to 20 s. A test that needs another value sets it on its own command |
| `RIMZ_TEST_STOP_OWNER_EXIT_MS` | The 3 s a stop waits for the processes of the agents it closed | The same two builders set it suite-wide to 50 ms, so a stop of a fixture owner that never exits returns at once with its still-running notice and no resume hint. A test that proves the stop's wait, or asserts a resume hint after a real process exits, sets its own value on its command |
| `RIMZ_TEST_CODEX_LOADED_THREADS_MS` | The whole Codex daemon loaded-threads probe: connect, WebSocket upgrade, initialize, and every `thread/loaded/list` page, for both the account-link gate and the loaded-thread reaper | It is read from the caller's login env map. Set it long (30 s) on a test whose stand-in daemon must answer |
| `RIMZ_TEST_HOOK_REPLY_WAIT_MS` | The 1.2 s a reply-bearing `hooks feed` waits for the drainer | Set it long (30 s) on a test with a live drainer, so load cannot turn the reply neutral. The drainer answers as soon as it has applied the frame, reply or not, so a long wait costs a feed that gets no reply nothing |
| `RIMZ_TEST_HOOK_APPLY_TIMEOUT_MS` | The drainer's 30 s apply-child deadline | It can only shorten the deadline, since the drainer caps each apply at its own 30 s per-frame `LOCK_WAIT` |
| `RIMZ_TEST_HOOK_DRAIN_ONCE_WAIT_MS` | The wait of `hooks drain --once` | |
| `RIMZ_TEST_HOOK_REPLY_RETENTION_MS` | How long the drainer keeps an unclaimed reply | |

- The environment probe times out only while it is still running at one of its 25 ms polls past the deadline, so a short value does not reliably fail a fast probe. Force a timeout with a login shell that blocks, as `run::supervised_probe_timeout_honors_the_test_override` does. A value below the probe's duration under load fails any launch that must succeed.
- Set the hook overrides on the `Command` from `Env::hook_command` or `drain_command`, never on the test process, which the builders scrub.
- A late reply is neutral by design, so a test that parses the hook's stdout after a drainer reply must set the reply wait.
- Before deciding which tests need a test-only duration override, list every caller of the function that reads it (`rimz lsp callers <reader>`): one override can set the budget of several reads, and a test can need it shortened for a read its fake never answers while it caps another the fake does. `RIMZ_TEST_ZELLIJ_HEALTH_PROBE_MS` sets two (see [Multiplexer doubles and heartbeats](#multiplexer-doubles-and-heartbeats)), and `rimz lsp callers` on its reader, the free function `health_probe_timeout` in `mux/zellij.rs`, lists both.

## Live backend and journey tests

- A change to a shared live fixture helper (`write_zellij_topology` in `journey/deep.rs`, the helpers in `backend/zellij/support/topology.rs`) runs every live test that calls it, listed with `rimz lsp refs` on the helper, since `gate` runs none of them.
- A Zellij client sample in a topology fixture decides which sidebars count as viewed and paint, as well as which widths prove. A fixture that gave a multi-tab room one client on its first tab left the other tabs' sidebars unpainted and failed `journey::deep::room_host::zellij_room_host_host_kill_recovers_young_then_mature`.
- A topology fixture that publishes a sidebar-only tab replaces it with the completed tab well inside the 5 s self-close confirm window, with no client attach, hook, or screen wait between the two writes. Past that window the sidebar self-closes and re-attaches. The re-attached width controller proves a topology written before it started only if it sees a pane-count change afterwards, so a fixture that publishes once can leave its completed tab unproven. `journey::deep::zellij_room_shows_agent_and_holds_width_keys` attaches its client and waits for the tab's 320-column layout before the sidebar-only write for this reason, and fails by name on any self-close record.
- A live test of a wake path ends the producer the way production does (a real process exit, not an in-process settle call), pushes every fallback that could stand in for the wake out of its window (write `workflow-tick.json` an hour ahead), and asserts the consumer acted within a bound well below that fallback, with no manual `workflow advance`. `backend::workflow::check_layout`'s stay case is the shape.
- Any live tmux test can fail its setup with `fork failed: No space left on device` on a host whose devpts caps PTYs, which reads as a product failure. The cap is about 1,026 on a shared development host, counting every other agent's panes. `backend::tmux::hidden_geometry::production_sweep_slices_hidden_windows_and_records_one_completed_run` has failed this way.
- The 250-window live tmux tests open a pane per window and hit the cap first: `backend::tmux::hidden_geometry::fit_views_batches_250_windows_preserving_order_options_and_zoom` and `backend::tmux::session::ensure_session_diffs_window_options_at_250_windows`.
- On such a host, run the live tier under a private `/dev` and one test at a time: `bwrap --dev-bind / / --dev /dev -- cargo xtask test -P live ... -j 1`.
- The suite scrubs `TMUX*` on every builder, so tmux clients without `-u` choose UTF-8 from locale alone: a developer's UTF-8 `LANG` can hide the loss that CI's image, which sets no `LANG` or `LC_*` variables, exposes. Reproduce at the room birth: set `LC_ALL=C` and remove `LANG` and `LC_CTYPE` on the `rimz` child that starts the room, so its sidebar inherits the C locale, rather than changing only the test process's locale. Test-server clients pass `-u` to read the names the server actually holds.
- A Zellij focus probe types into its client before it measures. A client that has sent no input since attaching is not moved by `action focus-pane-id` and is not the client a focus-taking `new-pane` follows.
- A hand-built probe writes a `config.kdl` with `show_startup_tips false` before attaching. An empty `ZELLIJ_CONFIG_DIR` opens a floating first-run wizard that takes focus.
- A focus proof for a user-run command issues the action from inside the client's pane, inheriting `ZELLIJ` and `ZELLIJ_PANE_ID`. An action from outside any pane is a different condition.
- A live test that moves a Zellij client with a directional key confirms through `list-clients` where the client landed before it relies on the column. One `Alt+l` from the sidebar landed in the second working column, past the one beside the sidebar, in 1 of 100 stress copies of `backend::zellij::shared_view::two_clients_split_join_and_carry_the_sidebar_view`. The cause was not traced.
- A test that must reach a given column walks one confirmed hop at a time, as that test's return to the sidebar does: one `Alt+h`, a `list-clients` poll until the client has moved, and an assertion that it is still in the agents tab.
- Exact geometry assertions over repeated Zellij splits size the anchor's extent to a multiple of the resulting parts. Halving an odd extent takes a cell from a neighbour (a 39-row anchor became 20+20 while its neighbour went from 39 to 38), which reads as a placement fault.
- With a real sidebar host, a live test identifies the tab or window that `open_tab` created by the id absent from a listing taken before the call, never by its name, on both Zellij and tmux. The host can release a RimZ tab that hosts no agent to the shell name from the first frame that sees it ([tab naming](../internals/multiplexers.md)); on tmux, `%window-add` wakes the host while `open_tab` is still running, so even the first name lookup can lose, as `two_clients_share_the_sidebar_view_through_detach` did.
- A live test that seeds N agents waits for the sidebar to show all N (for example the `⢿ N` running count) and homes the view before sending its first key.
- A test that reads an attached tmux client's raw bytes for `ESC[?2026h` waits out tmux's terminal-query timer first (about 5 s after attach; tmux 3.8's `tty_start_timer_callback` redraws the whole client inside its own sync pair), and asserts what lies outside pairs, not that some pair exists.
- The journey `RoomHarness` is not a mux room: it runs one `rimz sidebar serve` on a PTY and stands in for the mux with a JSON pane list (`RIMZ_TEST_PANE_LIST`). The renderer has a synthetic owner absent from that list and a controlled watchdog. There is no client and no focused pane, and replayed hooks run under `Env.runtime_root` while the renderer has its own short runtime directory.
