# Running gates and tests

How the gates and the test runner behave in practice: the signals each command gives and hides, the surface ratchet, what a rebase needs, how to name a test, and how to compare timings. [rust-conventions.md](./rust-conventions.md#quality-gates) defines the gate stack and the test tiers; the everyday commands are in the root [AGENTS.md](../../AGENTS.md#testing). What a given kind of change must also run is in the [change checklists](./change-checklists.md#tests-a-change-also-runs).

## Compile and lint signals

- Compile tests with `cargo xtask check`. A bare `cargo check --tests` compiles the same shape: the crate's self dev-dependency turns `testkit` on for every build that carries dev-dependencies, so editors and agent harnesses report the gate's diagnostics rather than phantom `testkit` errors.
- `cargo xtask check` and `cargo xtask lint` build with `testkit` on (lint runs only the all-features clippy, `lint_all_features` in `xtask/src/gates.rs`), so production code calling a `cfg(any(test, feature = "testkit"))` item passes both. Before hand-off, run `cargo clippy -p rimz --bin rimz --locked -- -D warnings`, the install-host shape the gate runs (`INSTALL_HOST_LINT_ARGS`).
- `cargo xtask check` prints no compiler warnings, so an edit that can leave test code with unused bindings (a removed parameter, a dropped field) runs `cargo xtask lint`, or lists them with `cargo build --tests -p rimz --message-format short`, before the first test run.
- A remove-and-compile census (delete an item, count the compile errors) measures the library alone: the unit-test target is the library built under `cfg(test)`, and the crate's self dev-dependency links the library into it, so neither `--tests` nor `--keep-going` type-checks `#[cfg(test)]` code while the library fails. Count test-side reach after the production errors are fixed, or report it as unmeasured.

## The surface ratchet

[atlas.md](./atlas.md#conform--keep-the-target) is the reference for `conform` and the `refactor-target.toml` schema.

- The pre-commit hook (`cargo xtask hooks` activates it) adds the surface-budget and dependency check, `cargo xtask atlas conform --ratchet`, which `check` and `lint` do not see; a new `pub` or `pub(crate)` item, module, or cross-module import fails it until `refactor-target.toml` admits it: a `[[verdict]]` for the item (a `pub` method on an existing type needs none but still counts toward its module's surface) and, when its module's surface is at the cap, a raised `surface-budget` with a `#` line above it naming the item and the raise (`(+1)`), every earlier line kept.
- A change that raises a budget counts every item it adds in its `(+N)`, including those that fit under the cap at the branch point: trunk can use that slack before the rebase, and the rebase sum below then comes out short.
- The ratchet indexes the worktree's untracked `.rs` files too, mounted or not: an untracked file holding one `pub fn`, never declared as a module, failed it on its module's budget and the enclosing `crates/rimz/src/harness` budget alike. So a change split into commits holds back a later commit's new file before committing an earlier one: move it out of the tree, or stash it under a unique message (`git stash push -u -m <tag>`) and restore it by its SHA.
- A change that removes or renames an item a `#` line names rewrites that line to name what remains, with no tag: `(+N)` marks a raise and nothing else. A line reworded while every item it names remains keeps its `(+N)` tag. A shrunk surface may keep its budget, which is a ceiling.
- A `pub(super)` item whose parent module sits inside the same `[[module]]` boundary (`harness::spec` inside `crates/rimz/src/harness`) escapes nothing and needs no admission, so share a helper at that visibility rather than copying it. A file with its own `[[module]]` entry (`crates/rimz/src/harness/plan.rs`) is a boundary of its own, so its `pub(super)` items count toward that entry's `surface-budget`.
- A plan that routes a call into another module first reads the calling module's `allowed-dependencies` (or `upward-dependencies`) entry there: a module missing from the list reshapes the design or needs an admission the plan names. It also reads the `layers` list at the top of `refactor-target.toml`: a call may only reach a module in an earlier layer unless `upward-dependencies` admits it. It also reads every module contract in an `AGENTS.md` that lists what the calling module reaches (``rg -n '`address` reaches' crates --glob AGENTS.md``), since atlas checks only the modules that carry a list.
- `refactor-target.toml` runs to about 8,000 lines: find your module's entries with `rg -n '<module path>' refactor-target.toml` and read around each hit, never the whole file. `[[verdict]]` keys are Rust paths (`agents::spending::publish::ProviderSpendingCache`) and `[[module]]` budgets are keyed by file or directory path (`crates/rimz/src/agents/spending`), so search both forms.
- A new `pub` item can also count toward an enclosing directory's `[[module]]` budget, and a search for its own module path does not match that entry: `WindowStarts` in `agents::spending` raised `crates/rimz/src/agents` by one as well, so search each enclosing directory path too. A new `pub` item in a `pub` module that the boundary's root module also re-exports counts twice, once at its definition and once for its `pub use` leaf: `ResetGrant` in `agents::credits` and its leaf in `crates/rimz/src/agents/mod.rs` raised `crates/rimz/src/agents` by two.
- Name the items a `(+N)` line raises from `cargo xtask atlas diff --base "$(git merge-base HEAD origin/main)" --path <boundary>`, which lists each added surface item; a `conform --ratchet` failure with the budget one lower proves the sum and not the names. `atlas diff` has run for over 20 minutes on a shared host, so run it under `rimz wait --run`; when it cannot finish, count each boundary's new `pub` and `pub(crate)` items and `pub use` leaves by hand, and prove the sum by `conform --ratchet` failing with the budget one lower.

## Rebasing

- A rebase runs no hook, so run `cargo xtask atlas conform --ratchet` and `cargo xtask invariants` yourself after one, and `cargo fmt --all --check` at every commit whose conflict you resolved (`git rebase --exec 'cargo fmt --all --check' "$(git merge-base HEAD origin/main)"`, which checks each commit in place, where `origin/main` would replay the branch onto a trunk that moved since the rebase): a resolution left unformatted passes `check`, and the next commit that formats the file carries the churn in its diff. Skip it when every resolved conflict is outside Rust files, and run it before or after a build or gate in the same checkout, never alongside one, since it checks out each commit.
- A rebase whose trunk side calls an item the branch changed, or changes an item the branch calls (a shared test fixture included), also runs `cargo xtask check` at each branch commit before any test run, the same way (`git rebase --exec 'cargo xtask check' "$(git merge-base HEAD origin/main)"`, or a detached scratch worktree per commit: `git worktree add --lock --detach "$TMPDIR/<dir>" <commit>`, `cargo xtask check` inside it, then `git worktree remove --force --force "$TMPDIR/<dir>"`): the gate builds only the head, and an earlier commit can stop compiling against the new trunk without any conflict. A brief to a check-only subagent gives the detached scratch-worktree form, since such an agent declines `git rebase --exec`, which moves the checkout.
- A branch that removes or renames a text format tests write as strings (a workflow definition field, a record key) also greps the rebased tree for each old spelling before any gate run (`git diff --name-only <old merge base> origin/main` lists the files trunk changed): trunk's new tests carry the old spelling without a conflict or a compile error and fail only when run.
- A rebase whose trunk side adds a flag, state, or refusal to a command the branch changed (`git log --oneline <old merge base>..origin/main -- <the command's files>`) rereads each message the branch adds to that command (a receipt line, a note, a refusal) against it, conflicted or not: trunk's `--once-per-checkout` arrived without a conflict, and the branch's `loop add` idle-agent note stayed false on such a task through a review round.
- A rebase that conflicts on a `surface-budget` entry, on its value or only on its `#` lines, sets the value to trunk's value plus the branch's own `(+N)` raises, with trunk's `#` lines kept before the branch's: git merges two equal raises into one without a conflict on the value. When a later commit of the branch rewords a `#` line an earlier one added, the resolution at that commit keeps the new wording alone: keeping both sides' lines leaves the old one in, and its `(+N)` is counted twice. `cargo xtask atlas conform --ratchet` fails a sum that is too low; a sum that is too high passes, so check it against the `(+N)` lines.
- A rebase of a branch that bumps `SNAPSHOT_VERSION` or `ROLLUP_CACHE_VERSION` re-checks each against trunk, even when the rebase is clean: when trunk bumped a version to the value the branch chose, git merges the two bumps into one without a conflict, and each regression test's literal pre-bump stamp still reads as older and passes. Where trunk moved a version since the branch's old base, the branch bumps again past it and moves its pre-bump stamps to trunk's value, and a conflict on the `*_contract_is_version_<N>` pin in `crates/rimz/src/store/snapshot/assemble/tests.rs` keeps a single pin at the final value.

## Selecting tests

- Batch focused tests with `cargo xtask test --name <test> [--name <test>...]`, exact names only. `--name` takes the nextest test name without the binary: an integration test is `lsp::some_test`, not `integration::lsp::some_test`; `cargo xtask test --list <fragment>` prints each binary's id (`rimz::integration`) followed by its exact names, not the binary's path; the path comes from `cargo xtask test --list <fragment> --message-format json` or the `binary:` line of a `cargo xtask stress` `summary.txt`.
- A file mounted with `#[path = "..."] mod name;` runs under the mounting module's path plus `::name`, never under its file name: a sibling `#[path = "foo_tests.rs"] mod tests;` runs as `loop_cmd::list::tests`, and the integration file `loop_list.rs` runs as `loop_schedule::list_tests`, so `test(loop_list::)` matches nothing.
- `--list` builds the test binaries first, so run a cold one under `rimz wait --run` (a cold build on a loaded host outlasts the 10-minute tool cap), never as a foreground call. During a read-only sweep, run `rimz lsp hover` on the test function instead: the module path it prints, minus the crate name (`rimz::` or `integration::`), plus `::<fn>`, is the exact name, `#[path]` mounts included.
- Run a whole module through a bare nextest filter: `cargo xtask test 'sidebar_pane::app::width_control'`. A filter and `--name` intersect rather than union, so the two run as separate calls; passing both is what "0 tests run" means.
- The default nextest profile stops at the first failure, so a test-first run that must see each new test fail passes `--no-fail-fast`.
- Integration tests live in their own binary, so a module filter has to name it: `cargo xtask test -E 'binary(integration) & test(message::)'`, where a bare `'integration::message'` matches nothing. xtask's own unit tests run in binary `xtask::bin/xtask`, and the `rimz` library has modules of the same names (`sandbox::`), so a filter for them also names the package: `cargo xtask test -E 'package(xtask) & test(/^sandbox::/)'`. `-P` and `-E` combine, so one live module runs as `cargo xtask test -P live -E 'binary(integration) & test(/^backend::tmux::team_stage::/)'`.
- `cargo xtask test` prints only its summary line. To read each test's duration, add `--no-capture`: xtask then hands the terminal to nextest (`requests_no_capture` in `xtask/src/gates.rs`), which runs the tests one at a time under `--no-capture`; its default profile prints one `PASS [   0.287s]` line per test. CI's `gate` profile prints only failures and retries and keeps no JUnit report (`[profile.gate]` in `.config/nextest.toml`; only `live` and `journey` write `junit.xml`), so a gate test's duration on trunk comes from the Coverage workflow's log (`gh run view <id> -R rimio-ai/rimz --log`).
- Library unit tests resolve RimZ roots only from the six `RIMZ_UNIT_TEST_*` keys listed in [rust-conventions.md](./rust-conventions.md#tests); xtask sets them to its sandbox roots, and with none set a test gets per-process temp roots. Nothing removes those: a bare run can leave a runtime root at `/tmp/rimz-unit-<16 hex>` and a home at `$TMPDIR/rimz-unit-test-home-<pid>-<uuid>` for each test process that wrote, so remove them after the run. A re-exec test passes a root under its unit-test key. Under `cargo xtask stress` every copy of a library test already shares the sandbox's unit-test home; `--env RIMZ_UNIT_TEST_RIMZ_HOME=<dir>` only picks which directory they share (one you keep or pre-fill), and library unit tests ignore `--env RIMZ_HOME`.
- Every test binary is built `--all-features`, so each `rimz` process a test spawns is a `sentry` build: it runs `observability::reporting::init` before dispatch, which reads the per-machine core config file. A test that pins what a process loads, prints at startup, or holds in memory describes that build; check the release feature set by hand with a binary from `cargo build -p rimz --bin rimz --features testkit`. That binary keeps the unoptimized dev profile, so a CPU or time figure a doc cites is measured on `cargo build --release -p rimz --bin rimz --features testkit`, held in a sandbox room with `RIMZ_BIN=target/release/rimz cargo xtask sandbox room`.

## Builds and scratch worktrees

- This worktree's built binary is `$(cargo metadata --format-version 1 --no-deps | jq -r .target_directory)/debug/rimz`. The target directory may be shared with other worktrees, each under its own hash directory, so resolve it this way rather than picking the newest.
- A throwaway probe test runs in a detached scratch worktree (`git worktree add --lock --detach "$TMPDIR/<dir>" HEAD`) with `CARGO_TARGET_DIR` set to the worktree's own target directory (`cargo metadata --format-version 1 --no-deps | jq -r .target_directory`), so its build reuses that cache instead of starting cold under a new hash directory, and the scratch worktree is removed after with `git worktree remove --force --force "$TMPDIR/<dir>"`. The lock keeps another agent's `git worktree prune`, which cannot see a sandbox's `$TMPDIR`, from deleting its admin directory mid-run; a single `--force` refuses to remove a locked worktree.
- A `cargo xtask` run from a scratch worktree on the shared target directory replaces `target/debug/xtask` with that tree's build, and Cargo does not rebuild it for the checkout whose target directory the scratch tree shares (your worktree, not necessarily the primary checkout), so that checkout's next `cargo xtask` and its pre-commit hook run the scratch tree's gates. Afterwards, `touch xtask/src/main.rs` in that checkout.

## Background runs

- A gate or test run started outside the terminal's foreground process group while it still holds that terminal (a command a `rimz wait --run` watcher or a trailing `&` starts from an agent pane) runs as `setsid --wait <command>`: every test that reaches the interactive shell probe of a launch (`bash_interactive_shell_argv` in `crates/rimz/src/harness/launch.rs`) starts a `bash -i` that opens the controlling terminal, and from a background group bash stops itself and the test with `SIGTTIN`. A gate run that way timed out 30 launch and sandbox tests (`did not finish within 30s; killed`, or a nextest timeout near 370 s) that pass in seconds under `setsid --wait`.

## Live tests and flakes

- Run live Zellij tests through `cargo xtask test`. A bare `cargo nextest run` from a shell that exports `ZELLIJ_SOCKET_DIR` can fail them with `There is no active session!`; prefix it with `env -u ZELLIJ_SOCKET_DIR`.
- Run `-P live` with the profile's configured retries. A test that passes on a retry is reported as flaky, with its first panic line; only a test that fails every retry is a failure, and only a failure gets compared against trunk. Before treating a trunk-comparison failure as the branch's, check that the test runs the changed code (a fixture on `sidebar_stub_alive_for` runs no sidebar host code; `git diff --stat origin/main...HEAD -- <paths the test exercises>`), and compare at least 6 `--retries 0` runs per side: 3 runs cannot tell a 1-in-3 flake from a regression.
- CI runs tests as root (the `rimz-ci` image built from `ci/Dockerfile` sets no `USER`), so a permission fixture (`chmod`) skips itself there and proves nothing. To make an atomic cache write fail for any uid, put a directory at its destination path: the final rename then fails with `EISDIR`, root included.
- A set `CI` variable turns colour on in a spawned `rimz` even under `TERM=dumb`. A PTY test that matches plain text removes it from the child (`cmd.env_remove("CI")`), and a change that adds such a test runs its module once as `CI=true cargo xtask test -E 'binary(integration) & test(/^<module>::/)'`, since the local gate runs without `CI`.
- Without that leave, triage a flake by forcing the state it needs and showing the unfixed tree fail with the original signature. Insert the stalls with a script that places each at an exact text anchor and fails when one is missing, then run the same script on the fixed tree: a saved diff misapplies once the fix moves the lines. With that leave, first read [Stress batches](./integration-tests.md#stress-batches) for the `--jobs`/`--hogs` a batch takes.
- A gate failure on a test you leave unfixed (a flake, another branch's failure) is quoted in your notes or the PR as four things: its name, its `panicked at <file>:<line>:<col>` line, its message with the assertion's printed values verbatim (or the kept log's `path:line`), and its run time. Its log under `$TMPDIR` is gone before anyone investigates, the panic line alone can say which step of a multi-step test failed, and a paraphrase of the printed values drops the state that names the cause.

## Codex agent shells

- A failure a Codex agent reports from a `rimz` command reproduces outside a Codex pane with `codex sandbox -c 'default_permissions=":workspace"' -- <command>` run from the checkout, which applies Codex's own bubblewrap and seccomp to that command; the bare `codex sandbox linux` spelling fails with `execvp linux`. A routine `rimz` command a Codex agent runs bare matches its `prefix_rule` and runs unsandboxed, so reproduce the wrapped form the agent ran.
- A gate run from a Codex agent's shell hangs the launch-path tests (`agent_launch::`, `sandbox::`, `harness::launch_plan::tests`, `harness::launch::tests`): some fail at their 30-second child deadlines and the rest at nextest's 370-second timeout, on every rerun there, while all pass in seconds from a Claude agent's shell. The cause is not diagnosed. Before reading such failures as the change's, rerun those tests by exact name (`cargo xtask test --no-fail-fast --name <test> ...`) from a Claude agent's shell or a user shell, and brief a gate subagent on Codex to list them and report the gate as incomplete.

## Cross-target checks

- `gate` compiles the host target only. A change that touches `nix`, `libc`, or platform-gated code, or adds a call to a `#[cfg(target_os = ...)]` item (a test helper included), also runs CI's four cross-target type-checks: `RUSTFLAGS='-D warnings' cargo-zigbuild check -p rimz --target aarch64-apple-darwin --locked` catches Linux-only items in the shipped library and binary on macOS, the same command with `--tests` catches them in the test targets, which build with `testkit` on, `RUSTFLAGS='-D warnings' cargo-zigbuild check -p rimz --target x86_64-unknown-linux-musl --locked` catches glibc-only items on musl, and `RUSTFLAGS='-D warnings' cargo-zigbuild check -p rimz --target aarch64-unknown-linux-gnu --locked` catches architecture-specific types on aarch64 Linux. These need `cargo-zigbuild` and `zig` on `PATH` ([setup](./rust-conventions.md#release-packaging)).

## Timing comparisons

- A change to the snapshot fold or its reducer times the touched `hotpath` fold benches (`cargo xtask perf --bench hotpath -- <bench>`) on the merge base and the head back to back, in the order base, head, head, base, before hand-off. The fold benches are `rollup_fold_warm`, `rollup_fold_unchanged`, `carryover_fold_cold`, `carryover_fold_cold_trimmed` and `carryover_fold_rebirth_warm` (`#[divan::bench]` functions in `crates/rimz/benches/hotpath.rs`). A change to `sidebar::enrich::enrich_core` or a step it calls times `enrich_cached` the same way. A single perf run on a shared host is not evidence of a regression or of its absence. When one round shows a difference on a host whose load average is above its core count, run three more rounds on the same copied binaries before reading it: one round showed `rollup_fold_unchanged` 1.9x slower with both head runs above both base runs, and the next three showed nothing.
- A change to the room spend slice (`aggregate_scoped_rollups` in `crates/rimz/src/agents/spending/aggregate.rs` and what it calls) times `spending_live_scale_additional_workspace_scope` and `spending_live_scale_additional_workspace_partial_scope` (`cargo xtask perf --bench hotpath -- <bench>`) in the order base, head, head, base. The walk benches pass `scope: None` and never reach it. A change to the walker memo build (`SpendingWalker::ensure_memo`) times `spending_walk_cold` and `spending_live_scale_cold_hydrate`, since the warm fixtures build the memo during setup.
- A base and head `hotpath` comparison on one target directory rebuilds RimZ at each switch of tree, over five minutes a time. Build each tree once with `cargo xtask perf --bench hotpath --no-run`, copy the binary its `Executable` line names, and run the copies (`<copy> --bench <bench>`) in the order base, head, head, base. This holds for a bench that stays in process. One that spawns `rimz` (`hook_stop_budget`) finds the CLI two directories above its own path: a copy outside `target/release/deps/` panics starting the sandbox reaper, and a copy inside it runs whichever tree built last, so run that bench through `cargo xtask perf` on each tree.
- A live timing probe judged against a target (a tmux or Zellij room, a sidebar latency) runs its controls (the stock mode, the off mode) in the same session, in the order base, head, head, base, before calling a miss: a miss whose controls moved with it is host load, not a regression.
- A live base-versus-head comparison runs both trees from checkouts whose paths have the same length, since a pane's shell prompt carries the cwd and its wrap can change what a capture shows.
