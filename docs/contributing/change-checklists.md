# Change checklists

What a change of a given kind lists, greps, and pins with a test before hand-off. Each rule names the kind of change it covers and what that change does first; where a rule carries an example, the example is the miss that prompted it. No gate catches a skipped rule here, so find the sections your change matches before you size the work. Running the gates is [running-gates.md](./running-gates.md), and building a probe or a live check by hand is [probes.md](./probes.md).

A new rule joins the section whose trigger it shares, as one bullet that opens with the kind of change.

## Events and time

The principle these rules apply is in the root [AGENTS.md](../../AGENTS.md#engineering-principles): an event or timing fix is proven at the consumer's decision point.

- A change that removes a later event's power to clear a state first checks whether each producer can deliver the state's opener after its own closer (separate child processes per event, unchained sends, no timestamp on the envelope), since the removed path was what made that reorder harmless.
- Work placed between a decision and the action it gates (a helper process, a lock, a network call) makes the decision stale by that work's duration: read the decision again after the work, or say why it cannot have changed. When the re-read finds the state the first read would have acted on (an occupant, a hold), it takes the first read's path: a wait stays a wait, not an error. When that later read can only defer the action, check it before the work as well, or every deferral repeats the work.
- A stamp another rule compares with is taken at the instant that rule means. It is also keyed on the state that rule reads: a stamp set on a raw status misses the rows a consumer partitions by their displayed status (a clean turn end parked on background work is raw running and displays as success).
- A floor that must expire with an existing cadence takes that cadence's own stamp, passed in, not a fresh `now()` after the pass's work, or it outlasts the cadence and skips the next due pass.
- A freshness stamp checked against later triggers is taken before the request it covers, or a trigger that lands during the request is absorbed.
- A refresh an event triggers reads its inputs at the instant the trigger fires, so a limit stated for it says what that read finds then and what next moves the trigger: an answer read too early sticks until that next move.
- A fix that changes which clock stamps a value audits every comparison against that value for its behaviour at ties, since a stamp that used to trail another may now equal it.
- A rule that orders two stamps, or compares a row stamp with one copied earlier from the same row, first lists every fold branch that writes or carries each (`rg -n -U '<field>\s*=' crates/rimz/src`) and evaluates any derived stamp, such as `last_request_at()`, on the row before and after each branch. A re-registration at rest, or a compaction close with no open bracket, moves `turn_started_at` without closing a request; a compaction that closes its bracket at rest stamps both turn stamps at the close; and a prompt into a row parked on background work moves neither turn stamp until its Stop.
- A refactor that moves time reads onto an injected clock keeps every read that followed a lock, I/O, or spawn after that work, and converts between clocks at the present, never at construction.
- A state a polling consumer reads stays published for at least one of that consumer's read intervals (its backstop tick plus one pass), or the consumer can miss it entirely; a design that withdraws such a state names that interval beside the rule that withdraws it.
- A state that changes with time alone (no event) reaches a reader that sleeps on a stored retry time only if that time is computed from the change's instant: `message::deliver::evaluate_when_condition` sets `retry_at` to the instant an auto-reviewed permission becomes visible, plus the dwell.
- A wake or deadline moved onto a record field first lists every writer of that field (`rg -n -U '<field>\s*=' crates/rimz/src`) and checks that the record still arms a wake after each writer that leaves it in the armed state.
- A change that moves a record's deadline at a new point also lists every consumer that enforces that deadline (`rimz lsp refs` on the field, plus any caller that keeps its own clock from a `--timeout` flag) and every input the new value is computed from, with the launch paths that store each: a message unpark rearmed a run's `deadline_at` while the foreground waiter still timed the run out by its own clock, and from a `timeout` only subagent launches stored.
- A cached answer reused while a key is unchanged lists every input the answer reads, configuration included, and keys its reuse on all of them.
- An event used as the moment to read a file another process writes is probed for the order of the event and the write (log the file's tail from the event's handler, then compare the row's stamp, the event's time, and the file's mtime): Claude's `turn.complete` after an Esc fires 45 to 100 ms before the interruption row is on disk, so `rimz mod feed` reads the transcript again for up to half a second.

## Defaults and stored records

- A change to a default that a stored document's parser fills (a workflow step's omitted `lifecycle`), or to what a workflow definition field means, raises nothing and reaches every in-flight run at its next engine read: `harness::workflow::spec::load` reads a deployed run's live file in the deployed directory, and an inline run's text generated at its fire, on every transition. So the change reads the committed definitions, the guide's TOML blocks, and what `command_definition` in `harness/schedule/shell_task.rs` writes for the field, and rules what an in-flight run does at the change. A change to the run record's own shape raises the record version (`store::workflow::VERSION`) so older records refuse rather than being misread. Raising it strands every unfinished run already on disk: a finished run's home has moved out of the live directory and is never decoded, while a live run of the old version is classed stranded by `store::workflow::classify`, skipped by the readers that walk live runs, refused by `resume` and `restart`, and ended as failed by the room's workflow pass, which the scheduler tick spawns, or by `workflow cancel` or `advance` on its id. So the change also lists every reader that walks run homes (`rg -n 'workflow_runs\(\)|workflow_runs_under|live_runs|unfinished_under' crates/rimz/src`) and rules what each does with a stranded run: one that fails on it holds every room until that run ends.
- A change to a default that a launch reads (a policy, an isolation level) lists every launch path that reaches the reader (`rimz lsp callers` on it, up to each entry point: agent and team launches, resumes, `-p` supervised runs, attach, rebirth) and rules what the new default does on each.
- A refactor that points readers of one table at a wider one (a new entry, a default the old table lacked) reads every predicate over the old table (`any`, `contains`, a count) against the added entries, and pins with a test each predicate whose answer the new entries could change.
- A change that makes a shared parser refuse or reclassify a class of input it used to let through greps both test trees for fixtures that write that input, as text (`rg -n "agent *= *'" crates/rimz/src crates/rimz/tests`) and as struct literals (`rg -n 'each_worktree: true' crates/rimz/src crates/rimz/tests`), and runs each module that holds one: a fixture in a module the change never touched passes only until the parser starts reading the field, and then fails first in the full gate.
- A branch that removes or renames a field of a stored record lists what trunk added that reads it before it rebases: `git diff "$(git merge-base HEAD origin/main)" origin/main -G'\.<field>\b' --stat -- crates`. A new reader is a design question for the branch, asked before the rebase, not a conflict to resolve in it: trunk's sidebar bookings read loop row fields a branch had deleted, and the rebase stopped on compile errors in a file the branch never touched.
- A field added to a serialized store record also runs its owning module's tests. Two records are named `RunRecord`: the workflow run in `store/workflow.rs` (`cargo xtask test 'store::workflow'`), where a JSON-shape snapshot pins every key, and the supervised run in `store/run.rs` (`cargo xtask test 'store::run'`), which has per-field round trips and no whole-key snapshot, so a field added there brings its own round-trip test.

## Lookups, guards, and predicates

- A change that deletes a filter from a lookup that returns its first match (a stored id, a pin, a guard argument) first lists each case where more than one candidate passes what remains, rules which one the lookup returns there, and pins it with a test: the filter may have been the only thing choosing. Deleting the stored-pane filter from `address::bind_agent` let an unregistered pane listed earlier in the lane take a message from a provisional card's own stamped pane.
- A change that deletes a guard because the state it read is no longer written first lists every writer of that state (`rimz lsp refs` on the write), bypass flags such as `--skip-capacity` included, and keeps the guard for each case a writer can still produce, pinned by a test. Deleting the start throttle's waiting state nearly dropped the guard in `harness::throttle::queue_hold` that holds a start while another admitted start in its scope sits in the queue, though a `--skip-capacity` start still writes its ticket behind one running its capacity check.
- A predicate over a status or enum value (a count, a filter, a liveness test) first lists every writer of that value (`rimz lsp refs` on the variant) and is read against each: `AgentStatus::Failed` marks both a failed launch and an errored turn on a live session. The same holds for a count a decision reads as one cause (`SidebarRecovery::deferred > 0` read as an add deferred): list every writer of the field with `rimz lsp refs` and confirm each increments it for that cause alone, or split the count.
- A rule keyed on a lifecycle signal (a clear on `TurnInterrupted`, a wake on `CompactionEnded`) first lists the adapters that emit it (`rimz lsp refs` on the variant, read for the `adapters/` files) and rules what happens for each adapter that does not: Claude and Kiro report a user interrupt only as an `Interrupted` turn settle in the context sidecar, never as `TurnInterrupted`, so the owed continue after a compaction is read as withdrawn from that settle (`AgentState::soft_compact_in_flight`) rather than cleared in the fold.
- A change that gives a reading a new state (a condition verdict gaining `unread`) lists every reader of that reading with `rimz lsp refs` and rules what each does with the new state: a count, a filter, or a display that only knows the old states will treat the new one as one of them.
- A change that lets a new class of name reach a lookup (a runtime variant such as `opencode-mini` beside kinds and profiles) lists every caller of each lookup it touches (`rimz lsp refs`) and rules, per caller, which classes of name reach it and what each must do there. A caller left on the old lookup keeps the old classes: three sites that checked a runtime name with the kind-only `find_definition` let a pack item block the runtime, skipped a broken kind base, and refused a team role.

## Agent rows and launch identity

- A change that makes a field mandatory on an agent row, or deletes the fallback that read a row stored without it, first lists every path that creates a row and rules what each stamps: the writer paths (`rimz lsp callers` on `append_agent_lifecycle_with_threshold` and `append_adoption` in `crates/rimz/src/store/writer/lifecycle.rs`) and the rows the read side synthesizes for a pane or session RimZ did not launch (`idle_agent_row` in `crates/rimz/src/store/snapshot/panes/lazy.rs`, `pane_agent_from_sessionless` in `crates/rimz/src/store/snapshot/view/live/projection.rs`, `empty_local_agent` in `crates/rimz/src/store/snapshot/view/live.rs`, `ResumeCandidate::from_observation` in `crates/rimz/src/harness/resume.rs`). It also counts the test fixtures that build a row without the field (`cargo xtask check` after the deletion, then the unit and integration runs) before sizing the work: deleting the lane-less fallback left three hook paths and three read-side builders without a lane, and about 200 tests whose fixtures had to be migrated.
- A match that decides whether two rows are the same agent (a launcher, a parent, a message's card, a peer run, a team owner) compares launch ids: `AgentState::launcher_is`, `AgentState::parent_is`, a card built with `AgentCardRef::with_launch`, `address::launch_row`, or a supervised run stamped with its launch (`RunRecord::matches_agent`). A session row's launch id is its current launch, which `absorb_provisional` moves when a fresh launch resumes the session (the earlier id stays in `prior_launch_ids`), so a record stamped with the earlier launch stops matching that row. A lookup by the earlier id still returns that row: `AgentState::answers_to` reads `prior_launch_ids` and `agents::state::launch_members` admits it, so `address::launch_row` and `HostingRead::agent_hosting` name it. A caller that acts on the row such a lookup returned for a stamped record first checks the record's own match on that row (`RunRecord::matches_agent`): a stop of an earlier launch's run closed the resuming launch's pane until `stop_run_tree` in `crates/rimz/src/cli/agents_cmd/stop.rs` filtered the holder. It never decides on `(kind, session id)` alone, since `rimz agents molt --agent` keeps the launch id and changes the kind: ten kind-keyed matchers (message cards, peer runs, the team owner lookup and a workflow pin among them) lost a cross-kind molted agent until they moved to the launch id ([agents, sessions, and epochs](../internals/agents/instances.md#agents-sessions-and-epochs)).
- A new caller of `address::launch_row` or `address::launch_occupants` over rows it loaded itself (`store.audit_rows()`, a runtime projection, a clone taken before a fold) first runs `store::agent_context::attach_rest_certificates` on those rows: the pick orders live holders by `AgentState::holds_open_turn`, which reads the row's context, and `Store::snapshot_cached`, which the address resolver reads, carries it. Its test stages two live holders of one launch, writes a context file (`agent_context::write`) that rests the one the bare rows would pick, and names the expected row outright: an expectation computed by `launch_row` over the same rows passes either way. The hosting lookup's agent question shipped its first draft without the attach and could name a different session than the one the agent's handle resolves to.
- A caller of the hosting lookup's agent question (`HostingRead::agent_hosting`, or `launcher::agent_pane::locate`, `find`, and `open_writer` over it) that then acts on a session it resolved itself (a swap, a send, an answer, a budget interrupt) compares the answer's holder (`AgentHosting::holder`, `AgentPane::holder`) with that session and refuses when they differ. One launch can be live in two panes after an exact-id resume of a cleared conversation, since `crates/rimz/src/store/snapshot/project.rs::carried_base` keeps the revived row's launch id, and the lookup answers the launch's occupant, which need not be the session the caller resolved. Restart and molt first shipped without the check and would have closed the other session's live pane. Its test stages two live rows of one launch in two listed panes and acts on the one that is not the occupant. For Claude, the non-occupant is a later-registered session: a session of the launch that registered earlier and holds an open turn wins the pick (`AgentState::compare_same_pane_owner`), so a later asker loses it; `crates/rimz/tests/integration/message/pane_acts.rs::answer_refuses_when_another_session_of_the_launch_holds_the_pane` stages it. A caller that holds a session's key rather than an agent's (a sidebar card's close and focus) asks `HostingRead::agent_hosting_of_session` instead, which answers that session itself while no swap replaced it, so the non-occupant's card acts on its own pane.

## Config keys

- A new config key stored as a string that a user can type as a bare number (a byte size, a duration, a budget) joins the always-string list in `crates/rimz/src/config/edit.rs::parse_set_value` and gets its own branch in `validate_set_value`, pinned beside the `gc.tmp_floor_min` cases in `crates/rimz/src/config/edit/tests.rs`. Otherwise `rimz config set <key> 1024` stores a TOML integer that the key's loader refuses.
- A config command that accepts a table key where `rimz config set` takes only leaves (`rimz config unset`) applies every rule keyed on a leaf or an entry path to each such path under the table as well: a whole-entry table that `crates/rimz/src/config/edit.rs::is_whole_struct_table` names goes whole, and `remote_control.claude` and `remote_control.codex` reach the running machine. Each rule gets a test that names a parent key, since a test of the named key alone passes while the parent path skips the rule.

## Rooms other than the caller's

- A `rimz` child spawned to act on an object of a named room (a loop task's launch, a stop forwarded to a task's agents) passes `--root <that room's root>` or drops `RIMZ_PROJECT_ROOT` and `RIMZ_WORKSPACE_ID` from its environment: every room pane exports that pin, `WorkspaceResolver::resolve_participant` ranks it above the directory, and `current_dir` alone resolves the caller's room. Drop the pin where the child must keep a checkout of its own (`--root` makes the root its worktree too); the loop launch child does (`crates/rimz/src/harness/schedule/launch.rs::spawn`), while the stops pass `--root`. Its test sets a pin that disagrees with the target room, since the integration builders scrub the pin (`common::ScrubSessionEnvExt`).
- A change that points an existing read at rooms or targets beyond the caller's (a per-room snapshot in a machine-wide list) traces every diagnostic record that read can emit to `classify_diagnostic` in `crates/rimz/src/cli/doctor/runtime.rs` before hand-off. A record it classes `Investigate` files a `warn` or `alarm` incident against that other room's `rimz doctor` health tally, so a read-only command run elsewhere becomes a false health warning there, written again on every run.

## Workflow engine

The engine is `crates/rimz/src/harness/workflow/`; its behaviour is [workflow.md](../internals/harness/workflow.md).

- A change to what a workflow field means, or to what a check gets by default, also reads each committed definition (`git ls-files | rg 'workflow\.toml$'`) and the TOML blocks in `docs/guide/workflows.md` against the new rule. `crates/rimz/tests/integration/workflow.rs::babysit_fixture_validates_capabilities_and_missing_script` validates the committed fixture without running it; read the guide blocks by hand.
- A change that adds a definition field or a validation rule keeps the definition strict: each node kind's table in `crates/rimz/src/harness/workflow/spec/kinds.rs` denies every field the kind does not take, and an invalid value refuses at its dotted path (`validate::validate_spec`). No value a definition writes is read as absent, so a field that rule would drop gets a refusal instead.
- A test of a new validation refusal asserts the definition's whole error list, not that some error appears at the path, so a second rule firing on the same input fails it.
- A rule about how a hosted workflow attempt settles binds every settler: its host, another advance's bounds, cancel, and the dead-host reclaim. Test it with a second advance between the host's reap and its relock (hold the host at `RIMZ_TEST_WORKFLOW_RESULT_GATE`), as `crates/rimz/tests/integration/workflow/commands.rs::exited_command` does.
- A check whose settlement leaves the evaluate loop in `workflow/engine.rs` (a pane judge settling in `engine/agent.rs::finish`) carries each step that loop runs after a result: the definition reread after the off-lock work, `fit::misfit` on the reread definition, and the woken-wait reconciliation that clears `recheck_at` and evaluates again.
- A stop the workflow engine owes off the lock (an attempt's ending, an abandoned judge's run) stays in the run record until it was attempted, and the write that clears it comes after the stop: a workflow launch sets no run timeout, so a pass that dies between a clearing write and its stop leaves a pane nothing stops. A write that makes a run terminal carries no owed stop.
- A read `engine::prepare` adds before a launch takes the start groups it already resolved through the host's `start_groups`; it does not resolve the launch again. An arm of `engine/agent.rs::launch` that withdraws the attempt and waits (`retry`, the occupancy wait, `budget`) does so only while the attempt has no staged ending; with one staged it returns a launch failure so `finish` settles it, since a cancel, a restart, or a misfit can stage an ending while the attempt launches off the lock.
- An engine route out of a step (a failure, `asked`, `errored`) replaces `record.input` (a failure with `{outcome: "failed", cause, node, reason, detail}`, an errored turn with `{outcome: "errored", reason, errored}`, each with the run's key); a rule that derives state from `record.input` at a step states what it reads when that route re-enters it, and a test drives the route.
- A caller waiting on a workflow run another process started (the runner over a workflow fire's launch child) looks for it in every home: live, finished, and deleted, which it reads as quiet. A miss in the live home is not proof the run never started or failed: a run can finish and move before the caller looks, which is why a workflow fire's child that exits 0 counts as launched with the run id it printed.
- A test of a reader over the workflow journal (`inspect::hops`, `show`'s park and history views) takes its journal from engine transitions, or copies one the engine wrote. A hand-written journal can omit a row the engine always writes, and the reader then passes on a sequence that never occurs.
- A test fixture that builds an attempt by hand takes the shape `engine::prepare` gives it: a check attempt carries no `visit`. Every engine read runs the fit check (`engine/fit.rs::misfit`), which reads a script attempt with a visit as a command step, so a check attempt copied from an agent attempt without clearing `visit` ends the run as a misfit, not the way the test means.
- A prediction of what a journal reader makes of a run shape (which node it names, whether a test fails on trunk) runs that shape's journal tail through `inspect::hop_kind` and `inspect::evaluation_target` first. An evaluation's origin decides its hop: a Check-origin answer projects to a route out of the check, while an Engine-origin one (a judge's `canceled` when a cancel or the deadline abandons it, a judge's failure, an answer an edit left unroutable) projects to none unless its following Route records the decision, so the two shapes behave differently.
- A render rule that hides or merges a journal entry because another row already states it lists every engine writer of that entry (`rg -n 'JournalEvent::<Kind> \{' crates/rimz/src/harness`) and each writer's callers, and tests each. A claim that some journal sequence occurs names the workflow definition that produces it, and that definition passes spec validation.

## Harness launches and runs

- A refusal added to `launch_plan::definition_failure` keys on what the relaunch posture consumes (`resume::resolve_posture_with_role`), never on the bare kind alone: it is the one refusal a team restore's fresh seats meet (`resume::materialize_team_restore_tab` seeds them as `ExecAction::Launch` without the CLI gate), and restart of an agent whose session is gone, and every molt, reach it as `Launch` too.
- A harness path that reports a missing team or profile name asks `MachineConfig::definition_failure_for` first, as launch planning (`launch_plan::definition_failure`), member team loading in `team_stage`, lane resume (`resume::LaneRestoreConfig::load`), and rebirth (`rebirth::plan_recovery`) do, and says the name has no definition only when that returns `None`: a definition that fails to load is absent from the loaded tables, not unresolvable, since the loader drops it and records its `path: message` failures.
- A new `LaunchRecord` field is set in `resume::resolve_posture_with_role` as well as in `plan::finalize_agent_cell`, without re-running finalization: fork, restart and plain molt reach the store through the first, which validates but never finalizes.
- A change to the keys the process compiler stamps or clears (`CompiledAgentProcess.env` and `unset`) also runs `cargo xtask test 'harness::launch_plan::tests'`: `a_provider_temp_root_follows_tmpdir` asserts the exact `unset` list and filters each compiler switch out of it by name, and the `harness::launch::tests` filter does not reach it. A provider-owned key (one the provider reads, not a `RIMZ_*` switch) is cleared only when RimZ's own marker shows an outer launch stamped it and the key still holds the stamped value, as `RIMZ_LONG_CACHE_ENV` does for `long_cache_env` and `RIMZ_CODE_MODE_ENV` for the code-mode pair (both through `launch::release_stamped_pair`), and `RIMZ_CODE_MODE_CONFIG` for a code-mode config member, which only an unset launch of the kind that wrote it clears; a key from trusted `[[agents]] env` (`secret_keys`) or from the user's environment passes through, except that a code-mode off launch sets the pair's off value, or the config member's off value, over either.
- A change that moves a child onto another spawn path compares the two `Command` setups (session, process group, stdin, environment) and keeps each one the old path set; a test of terminal detachment keeps its pty's session leader alive past the command, or it passes by timing.
- A change to when a `budget.rs` park fires or clears is tested with two rooms sharing one account ledger, one room's `enforce` running between the two rooms' passes: the account ledger is machine-shared, so the first room to evaluate rewrites the park every other room projects.
- A change that turns a run's complete-then-reopen into a park lists every field the reopen branch of `fold_lifecycle` writes (the deadline rearm, `follow_ups`, `report_to`, the cleared notices) and rules each for the park: a message park's unpark takes the reopen's deadline rearm (`rearm_deadline`) and nothing else.
- A unit test that writes the machine's loop state (a created run, the task record) re-execs itself with a private `HOME`, `CLAUDE_CONFIG_DIR` and the six `RIMZ_UNIT_TEST_*` roots, since every test process shares the unit-test home: `reexec_with_private_homes` in `crates/rimz/src/harness/schedule/test_homes.rs` sets the private homes and re-runs the test.

## CI workflows

- A change to a workflow that both `.github/workflows/` and `.gitea/workflows/` carry (`ci.yml`, `ci-image.yml`, `coverage.yml`, `release.yml`) lands in both trees; [rust-conventions.md](./rust-conventions.md#continuous-integration) says where they differ on purpose. A claim about which CI jobs build a platform first searches both workflow trees and the image build files under each of the platform's spellings (`rg -n -i -l 'arm64|aarch64|musl' .github .gitea docker ci`): the Docker matrix names `linux/arm64` and `ubuntu-24.04-arm` rather than the triple, and `docker-image.yml` builds rimz natively on arm64 at release.

## Stale wording sweep

A change greps for the sentences it makes false, across more than the lines its plan names. The rules for writing the replacement sentence are in [Doc sentences](#doc-sentences).

- A change that alters a documented rule greps the old wording across `docs/`, `crates/**/AGENTS.md`, module `//!` headers, item rustdoc and comments in `crates/**/*.rs`, and the `[[verdict]]` reasons in `refactor-target.toml` before hand-off, not only the lines the plan names. A refactor pass reads a verdict's reason as the rule its item keeps, so a stale one records a removed behaviour as pinned. When the change deletes a mechanism, the grep also covers the verbs that describe it (what it publishes, pairs, or reads), not just the names of its items. When it stops a mechanism working (an `LD_PRELOAD` interposition, an environment switch, a hook), the grep also covers the tools and procedures that ride on it, by their own names (`rg -n -i 'heaptrack|valgrind|dhat' docs`), since a procedure names its tool, not the mechanism under it. When a path stops travelling through a module (a wire, a queue, a socket), the grep also covers the doc links to that module (`rg -n 'wakeup/mod.rs' docs crates --glob '*.md'`), and each hit is read for what it says travels through it. Grep by word stem (`memoiz`, not `memoized PNG`), since a doc may name the same mechanism in another word order. When the stem is also part of code identifiers (`peek` in `peekable`), limit the grep to `docs/`, `AGENTS.md` files and comment lines, or search with `rg -w`, so that a hit means a stale sentence.
- A change that widens or narrows a named set of files (the sidebar import graph) also greps the phrases that place a file in or out of it (`rg -n -i 'outside the sidebar|sidebar graph' crates/rimz/src docs refactor-target.toml`) and reads each hit against the new set.
- A change that adds or changes a value a CLI column, detail row, or sidebar row prints greps that column's or row's name (`rg -n 'EXTRA LEFT' docs`) across `docs/reference/` and `docs/guide/`, since a page that lists the possible values does not contain the new one.
- A change that adds a new way to reach a value a command already prints (a new cause of the `canceled` status) also greps the sentences that define that value (``rg -n -i '`canceled` means' docs/guide docs/reference``) and reads each against the new cause, since a one-sentence summary of a status names neither the change's words nor the path that produces it.
- A change that adds a member to an enumerated set (a stop reason, a state, a provider) also greps two existing members together across `README.md`, `docs/`, and `crates/**/AGENTS.md`, joined by `.*` rather than as a literal pair since other members may sit between them (`rg -n -i 'idle timeout.*memory pressure' README.md docs crates --glob '*.md'`): a sentence that lists the set names neither the type nor the new member. A `.*` join matches only in the order written, so run it with the members swapped too, or grep one member alone first. A field added to a serialized record is such a member, and a set documented as a table puts one member per row, where no `.*` join matches, so also grep one existing member as a table cell (``rg -n '^\| `lifted` \|' docs``). Such a change also reads the paragraph that introduces the set or table for a spelled-out count of its members and updates it, grepping the old count beside the set's noun (`rg -n -i 'nine classes' docs crates --glob '*.md'`): a sentence that counts the members names none of them.
- A change that renumbers an ordered list another page cites by number (`check 13`) greps the citation form across docs and crates (`rg -n -i 'check [0-9]+' docs crates --glob '*.md'`) and moves each citation that pointed at a shifted item.
- A sentence that quantifies such a set or the table beside it (`most`, `every`, `only`, `all but`) is read against the set member by member before hand-off, and names the members instead where they fit: a quantifier names none of them either, and it goes stale the same way a count does.
- A public item added to or removed from a module counts as a member of the set its docs list: grep two of the module's existing items together (`rg -n 'ServeConfig.*SidebarAppErr' docs crates --glob '*.md'`).
- A change that makes one code path follow another's existing rule (a second match arm reading the same input) also greps the other path's name across `docs/` and `crates/**/AGENTS.md`: a sentence that names the path already following the rule names none of the change's words.
- A change that adds an element to a rendered line (a sidebar row, a CLI column) also greps the names of two elements already on that line, joined by `.*`, across `docs/guide/` and `docs/interface/` (`rg -n -i 'tokens.*model' docs/guide docs/interface`): a sentence that lists the line's contents names neither the new element nor any word the change introduces.
- A change that adds a field to a record a CLI view prints reads the view's fold key (the struct rows are deduped by, such as `RunRowKey` in `crates/rimz/src/cli/loop_cmd/render.rs`) and every predicate that omits the section showing it (`write_last_run`'s skip condition), and decides for each whether the new field must split a fold or keep a section that would otherwise be skipped; a test covers a record where only the new field differs and a record whose other content is empty.
- A change to what a command prints, writes, or leaves behind (what survives `teams stop`) also greps the command's name (`rg -n 'loop show' docs/guide docs/reference docs/internals`) and reads each hit against the new behaviour, since a guide or internals page describes output and effects in its own words rather than the deleted ones.
- A change to where RimZ reads or writes a file (an install target, a provider config) greps the old path as a fixed string across `README.md` and `docs/` (`rg -n -F '~/.pi/agent/extensions' README.md docs`), and reads each hit against the new resolution.
- A change that makes a new site write an existing store event greps the event's name across `docs/` (`rg -n -F 'agent.launch_warnings' docs`) and names the new writer in each row or sentence that lists who writes it.
- A change that removes or renames a key of a text format tests write as strings (a workflow definition field) greps the old key across `crates/rimz/src` and `crates/rimz/tests`, not only the modules named after the format (`rg -n "invalid *= *'" crates/rimz/src crates/rimz/tests`): a scheduler or loop test can carry a definition.
- A renamed or removed identifier (field, type, variant) is grepped across the whole tree with `rg -w <old-name> . --no-ignore-dot`, not only over the paths a plan names. Its stem is also grepped without `-w` over test function names (`rg -n 'fn <stem>_' <test paths>`), and each test whose body now calls the new item is renamed: `-w` cannot match `fn agent_breakdown_folds_tail` once `agent_breakdown` is renamed. A method that moves to another type while its old type remains is grepped by its qualified old path with `-F` (`rg -n -F 'TaskFire::finish_record' . --no-ignore-dot`), since `rg -w` on the type still matches every other use of it.
- A change to a subprocess argv greps its tokens with any separator between them (`rg -n 'attach.{1,4}--create' . --no-ignore-dot`): a test may join them with a tab, or list them as separate array elements, and a search for the space-joined words misses both.
- A change that stops, reroutes, or reorders a mux command a launch or repair issues greps the integration fixtures that wait for that command's argv (`rg -n 'split-window|new-pane' crates/rimz/tests/integration`) and runs each test that uses them.
- A change that makes a command refuse or ask where it used to proceed also greps the repository's own scripted callers of that command, its tokens joined by any separator (`rg -n 'teams.{1,6}launch' loops xtask/src scripts .github crates/rimz/tests`), and reads each call for its stdin and flags: a coordinator runs without a terminal and so takes the refusal path, and its tests that pin only the argv still pass. Read each test hit for the environment it runs under: the integration builders scrub the `RIMZ_*` identity pin and the `TMUX*`/`ZELLIJ*` detection variables (`common::ScrubSessionEnvExt`), so a refusal keyed on ambient state fires there even when every production spawn passes. Such a change also reads the command's reference section for the sentence that lists its refusals (`rg -n -i 'restart refuses' docs/reference docs/guide`), since a "refuses only when" sentence names none of the new cause's words.
- A page that gains a new kind of content updates its summary line everywhere that links to it (`rg '<page>.md'`), the documentation map included.
- When a change moves where a behaviour is triggered, search the whole tree for the behaviour's phrase (`rg -i 're-?wake' docs/ crates/`) and update every hit, not only the pages the plan named.
- A scan over Markdown never trims its output with `cut -c`: docs keep one paragraph per line, so the cut drops a match that sits past it and the hit reads as unrelated. Print each match in context instead (`rg -n -o '.{0,80}PATTERN.{0,80}' docs`).
- A new store lifetime class, or a change to what reset, teardown, or GC removes, rereads the class table, [Reset](../internals/store.md#reset), and [What survives what](../internals/store.md#what-survives-what) in `docs/internals/store.md`, plus reset step 2 in [maintenance.md](../reference/cli/maintenance.md): each lists the classes a boundary drops.

## Doc sentences

What a sentence, recipe, or procedure of a given kind is checked against before it lands in a doc. The rules every doc edit follows are in the [documentation contract](../AGENTS.md#mechanics).

- A phrase that restates a code condition (which pane takes a path, when a branch fires) is checked against the condition's source line before commit, every `&&` and `||` kept: a gloss that turns an AND into an OR reads as true and is wrong for the case it drops.
- A sentence that lists the commands that trigger a behaviour takes them from `rimz lsp callers` on the function that performs it, followed up to every CLI `run` that reaches it: one shared entry (`RoomContext::birth`) can sit under several commands.
- A sentence that describes a path through several functions (a walk, a chain, a pipeline) must hold for each of them: list them with `rimz lsp callees` on the path's entry and check the sentence against every one, not only the one the change touched.
- A sentence that groups several mechanisms under one shared property (an LSP recycle and an idle stop as outcomes withheld while a request is outstanding) is checked against each mechanism's own decision function, since a plan's grouping is a claim, not a reading: the idle stop's `idle_expired` waits out a timeout from the last request instead.
- A sentence rewritten to widen or narrow a list keeps every other claim it made: diff the old and new sentence clause by clause and carry each clause that is still true.
- A process command line a doc states (argv0, a script path, a parent and child) comes from a probe or a live `/proc` read of each way the program is launched (a `PATH` lookup through a linked bin entry, a direct path, a launcher), never from a package's file layout or a teammate's finding.
- A doc that cites the code a measurement ran names the trunk commit it was built on (a merge base, which trunk keeps) plus the branch commit's subject, never a branch hash: a rebase renames every branch hash, and a later fix changes the commit's tree.
- A sentence that gives the cause of a measured change cites the figure, from the same run, that rules out the other readings. A mechanism that would produce the change, without that figure, is a hypothesis: write it as one, or leave it out.
- In a recipe spread over several `sh` blocks, every file argument names the path an earlier block created (`"$ROOT/tmp/replay/..."`), never a bare filename that depends on the reader's directory.
- A procedure a change writes or rewrites (relaunch this, attach that, then read this) runs once end to end before hand-off, on the setup it names. A run of its build command, or of its tool on a one-shot command, does not cover it.
- A sentence that gives a figure RimZ prints in more than one place names the surface it means, since each form is correct only where it appears:
  - `◇` is `↘` plus `↗` in the sidebar (`SpendWindow::add`) and adds `◌` in `rimz stats` (`SpendWindow::display_tokens`).
  - A crossed cap reads `fleet budget: $50.21 of $50.00/day` on an agent card (`agents/state.rs::BudgetPark::label`, two decimals always) and `$50.21 of $50/day` in the cockpit and provider headline (`theme/fmt.rs::dollars_cap`, whole-dollar cents dropped).

## Console blocks

A `console` block carries output as the command printed it, so a new or changed one is grounded in one of two ways.

**Capture it.** To get output under a home that reads like a reader's, run the built binary inside a nested bubblewrap, which touches nothing on the machine:

```sh
bwrap --dev-bind / / --tmpfs /home --bind "$TMPDIR/<dir>" /home/me \
  --setenv HOME /home/me --setenv RIMZ_HOME /home/me/.rimz --chdir /tmp \
  -- "$TMPDIR/rimz" <args>
```

`home_relative` then prints `~/...` while the copy-paste lines print `/home/me/...`. Copy the binary out of `target/debug/` first: the tmpfs hides the worktree.

**Recompute it from the renderer.** `cli/render/mod.rs` is the authority. For a `render::Table`, column width is the widest cell including the header, columns join with two spaces, right-aligned columns are the ones named by `.right(&[...])`, a section emits a leading blank line, consecutive cards are separated by a blank line, card detail indents two, and the last column is padded only when it is right-aligned. For a `render::KeyVals`, the value column sits at `indent + longest_key + 2`. For a `render::roster::Roster`, the handle column pads to `handle.len() + 1` before the two-space separator, so `@planner` under a roster holding `@reviewer` carries four spaces, not three. Recompute, never eyeball.

A change that moves one cell of an existing block regrounds the whole block, by capture when the branch binary can run the command. Recomputing only the changed cell keeps every other column's padding as trunk had it, and trunk's block may already be stale.

A block for a command you cannot run may be derived from the error type's format string plus the `error: ` prefix `write_report` adds, as long as you say in the change that it was derived rather than captured.

## CLI commands and flags

- A new free-text positional (a note, text, prompt, instruction, or message body) sets `allow_hyphen_values = true`; its reference page names `--` as the escape for a value that is exactly one of the command's flags, `-h`/`--help` included. Exception: agent and subagent launches reserve `--` for provider passthrough; an interactive agent launch cannot take such a prompt, a print run can read it from `agents -p --stdin`, and subagents can use `--prompt-file`. Launch prompts guard prefixes matching value-taking short flags so attached values cannot silently become prompts; document the spaced option spelling and the guard's application after `--`.
- A new, removed, or renamed flag updates the `cli_surface_is_stable` snapshot in the same commit: `cargo xtask test --name cli::surface_tests::cli_surface_is_stable`. Accept the change with `cargo insta accept`; never copy the `.snap.new` over the snapshot, since its header differs. The snapshot records command and argument shapes only; a help-text change moves no snapshot.
- A doc comment on an `Args` struct flattened into several subcommands prints in each one's `--help`; when the verbs take different input, set each one's help per verb and assert it per verb.
- A new mode that refuses flags another mode accepts lists every clap constraint on those flags first (`rg -n 'requires|conflicts_with|required_unless' <the Args file>`): a clap `requires` or `conflicts_with` fires before the mode's own check, with exit 2 and a fix that is wrong for the mode. A refusal moved out of clap into code also greps the clap parse tests for each flag (`rg -n -F -e '"--<flag>"' crates/rimz/src/cli/tests.rs`): they assert `clap::error::ErrorKind`, so a grep for the message text misses them.
- A new `rimz agents` verb also joins `help::AGENTS_GROUPS` and the verb list in `crates/rimz/src/pane.rs::command_is_launch_chrome`, and gives every positional a help line. Three tests fail otherwise: `cli::help::tests::agents_verbs_are_grouped_exactly_once`, `cli::agents_cmd::tests::launch_chrome_excludes_every_agents_subcommand_and_alias_except_launch`, and `cli::help::tests::agents_verb_positionals_are_described`.
- A new, removed, or renamed visible top-level command also updates `GROUPS` in `help.rs`, which places every visible command in exactly one help group: until it does, three `cli::help::tests` fail with `missing visible command`, and only the full gate runs them. A new top-level name is first checked against the retired names `reject_removed_top_level_tokens_from` in `mod.rs` answers before clap: a name listed there never reaches its handler until the arm is removed, and removing it drops the hint users of the old command were given.
- A change to a visible top-level command's doc comment in `Subcmd` runs `cargo xtask test 'cli::help'`: the command's grouped help line must fit 80 columns, and only the full gate otherwise runs `cli::help::tests::top_level_command_lines_fit_eighty_column_help`.

## Rendered output

- A change to human rendering checks it at its edges as well as at the snapshot sizes. At the narrowest width its docs support, strides, labels, and truncation run out of room. With colour off (`NO_COLOR`, `CLICOLOR=0`, `--color never`), `anstream` strips every SGR, so a mark told apart by tone alone (an overlay, a forecast, a muted span) reads as the data beneath it. Such a mark states what it draws then.
- A change that alters rendered text runs the merge base's binary and the head's on the same input in each mode it changes and reads the diff, not just the figures. Before building a base binary, read `rimz --version` on the installed one: a `+g<hash>` suffix without `.dirty` names the commit it was built from, and when that commit is the merge base it is the base binary. A bare release version gives no such shortcut. A change that lengthens a label inside a fixed-width layout (a heading padded to a name column, a one-line tab rail, a padded section title) renders each layout with every value the label takes and asserts that header columns still line up with row values and that no value is clipped; a line-width bound alone passes a clipped line.
- A render test of a value that more than one column can carry asserts how many times it appears (`matches(..).count()`), not only that it appears.
- A new or changed `doctor` row's cells name the problem, at most with its consequence, in a short phrase; the remedy goes only in the `fix` its tally records, so the table stays narrow and the closing block states each fix once.
- A finding or notice built from a template is rendered once per cause, and with one and with several members, before hand-off; read each result as a sentence.
- A change to the words or clocks of `cli::workflow_view::detail` changes the text of the `detail` string in `workflow list --json` and of `workflow_runs[].detail` in `loop list --json` and `loop show --json`, which the same function feeds: a plan that changes the phrase says so.
- A command a view prints for the user to copy names its target through the same resolver the command runs, and falls back to the stable id when the readable name would select something else. It carries `--root` when the target is in another room, and puts every flag before `--`. Another room is decided with the resolver the printed command runs (`WorkspaceResolver::resolve_participant`, which ranks the room pin above the directory), or the command carries `--root` always; `WorkspaceResolver::resolve` ignores the pin. It is offered only while the precondition its command checks holds, judged by that command's own gate: a `rimz agents` launch needs a running room (`room::require_live_mux`), which a readable workspace record (`open_existing_store`) does not prove, since the record outlives the room. A view that prints a new `rimz` command has a test that feeds the printed target back through the resolver the command runs, and feeds it back again after each change the product allows between the print and the user's run: a lone try's readable address selects it until a plain run starts beside it, so a try's commands name it by id.

## Refusals and warnings

- A change to when a command's refusal or warning fires, in either direction, greps its message text across `crates/rimz/src` and `crates/rimz/tests`, and for a refusal the error variant's typed fields (`rg -n 'field: "<name>"' crates/rimz/src crates/rimz/tests`), since unit tests assert the typed value, and runs each module that asserts either. A change to a refusal's, error's, or warning's wording greps the old text the same way, fixed-string, across `crates/rimz/src` and `crates/rimz/tests`: an integration test asserting the old words fails only in the full gate. A change that adds a refusal, error, or warning, or widens the cases one covers, also rereads its message against each case it covers, including what any command the message tells the user to run does in that case (`rimz packs update` skips linked and pinned packs, so one update hint was wrong for both), and each case's test asserts wording true of it, not another case's text. A message that promises a later effect (stays pending, will retry, runs later) is tested by asserting the persisted state that delivers it, not the wording alone.
- A change that decides whether a broken or unusable setting refuses, warns, or falls back applies the root [fail-fast rule](../../AGENTS.md#engineering-principles) as the settled cases do. Each sits in its subsystem contract as a `Fail-fast, settled` bullet: what the room still refuses for ([room](../../crates/rimz/src/room/AGENTS.md)), profile skills, the `sandbox` level, and scoped isolation off Linux ([sandbox](../../crates/rimz/src/sandbox/AGENTS.md)), `empty-dir` and tuning settings a provider cannot express ([agents](../../crates/rimz/src/agents/AGENTS.md)), and hibernation ([harness](../../crates/rimz/src/harness/AGENTS.md)).
- An optional language server is enrichment, so its configuration errors warn with the fix; `policy = "required"` makes it a precondition.

## Tests a change also runs

- A change to what a command prints (text or `--json`) or what it does to durable state (a run it cancels, a record it clears) also runs every integration module that invokes it, not only the one named after it: list the files with `rg -l -U '"<cmd>",\s*"<verb>"' crates/rimz/tests/integration`; a hidden helper (`run-timeout`, `park-notice`, `orphan-subagent`) is invoked through `agent_helper_argv`, which that pattern cannot match, so list its callers with `rg -l -U 'agent_helper_argv\(\s*"<helper>"' crates/rimz/tests/integration` as well; map a `#[path]`-mounted file to its mounting module, and run each as `cargo xtask test -E 'binary(integration) & test(/^<module>::/)'`. A smoke test in another command's module can assert a line of the output (`loop_schedule.rs` asserts `loop list --all` lines), and several tests compare whole JSON rows. Update each whole-row golden in place so its only diff is the new key, and never drop a key from a comparison to make it pass. Anchor the module name: `test()` matches a substring, so an unanchored `test(stats::)` also runs `performance::sidebar_diff_stats::` tests and `test(wait::)` runs `teams_wait::`. `[profile.gate]` in `.config/nextest.toml` runs every test outside the `live` and `journey` profiles, so when the hand-off runs `cargo xtask gate`, these per-module runs are for iteration, and a plan or brief names only the modules the gate leaves out.
