# Workflow CLI

`rimz workflow` starts, inspects, and steers durable workflow runs: a sealed graph of checks and steps under `~/.rimz/workflows/<name>/`, driven by the run record rather than by any agent's memory. The [workflows guide](../../guide/workflows.md) teaches the format and a full example; how the engine decides is [workflow internals](../../internals/harness/workflow.md).

```sh
rimz workflow schema                              # the spec's JSON Schema
rimz workflow validate                            # every machine workflow
rimz workflow validate ~/.rimz/workflows/babysit-pr --json
rimz workflow run babysit-pr                      # in the current checkout
rimz workflow run babysit-pr -w feat-x --prompt 'merge before Friday'
rimz workflow list                                # active and parked runs, every room
rimz workflow show 'babysit-pr#feat-x'
rimz workflow show 'babysit-pr#feat-x' --history     # detailed history, folded repeats
rimz workflow show babysit-pr                      # definition rail, then live runs
rimz workflow show babysit-pr pr                   # one definition node in full
rimz workflow resume 'babysit-pr#feat-x' --at pr --extend visits=+1
rimz workflow restart 'babysit-pr#feat-x' --continue
rimz workflow cancel 'babysit-pr#feat-x'
```

The [global flags](../cli.md#global-flags) apply. Every subcommand except `run` works from any directory: a run id resolves across every room on the machine.

`show`, `resume`, `restart`, and `cancel` accept a run address `<workflow>#<lane>`, a workflow name, or a full run id (`wf_` and 32 hexadecimal digits). The lane is the basename of the recorded scope path, even after that checkout is removed. Root-checkout and project-scoped runs use the project directory's name. A requested `feat/x` also matches `feat-x`. When a target begins with `-`, put options before `--` and the target after it.

An address selects its live run; `show` falls back to the newest finished run when none is live. Two live runs sharing an address refuse and list their ids and checkouts. A workflow name in `show` draws its definition, then lists that workflow's live runs, never one run's detail; a known workflow with none ends with `no active or parked runs of <name>`. For `resume` and `cancel`, a workflow name prefers the caller's checkout or its project's project-scoped run, then the only live run, otherwise lists commands to choose one. Matching runs in the caller's room take precedence; without a local match, several rooms refuse with `--root` commands. Each command a refusal lists names its run by address, or by id where another candidate in the same room shares that address, and carries `--root` when the run is outside the current directory's room. The global `--root` chooses the caller's room. Run ids remain unambiguous across rooms.

## Run a workflow

`rimz workflow run <NAME|DIR> [-w <WORKTREE>] [--prompt <TEXT>]`

| Argument or flag | Meaning |
| --- | --- |
| `<NAME\|DIR>` | A single path component is a name under `~/.rimz/workflows/`; anything else is a directory, which must lie inside `~/.rimz/workflows/`. `.` is the current directory. |
| `-w, --worktree <WORKTREE>` | Select an existing RimZ-owned worktree instead of the current checkout. It never creates one. Project scope overrides this selection. |
| `--prompt <TEXT>` | Stored unchanged, appended to every agent step's prompt, and exposed as `prompt` in `context.json`. |

Before creating a run, the command validates the definition and refuses on any error. Warnings alone do not refuse; each prints to stderr as `warning: <workflow>: <path>: <reason>` before starting, including [ignored fields](#validate-and-schema). It needs an existing room (`rimz start` creates one). With `scope = "worktree"`, nodes run in the selected checkout; with `scope = "project"`, they run at the project root, even when invoked from an owned worktree. One active or parked run holds each `(workflow, scope path)` pair; a second start refuses and names the existing run. The CLI validates before it asks for that slot, so a broken definition still refuses on validation first. On success it prints the run id, then the run's work directory (`RIMZ_WORKFLOW_DIR`), then a `workflow show` hint for that run. The first two lines keep their scripting format. The first advance starts in the background. The work directory includes `notes/` for node-owned cross-node scratch and `signs/` for step guidance. Every evaluation and attempt takes a new `seq`, a retry included, so name a scratch write after the item it records to make a repeat overwrite it.

When `-w` selects a project-scoped workflow, stderr prints `note: <workflow> has scope = project; the run is at <project root>, not <worktree path>`. The command still exits 0 and stdout is unchanged.

The step leader's Workflow launch note describes its listed checks in order. Scripts and shells show their command and optional summary, explain their execution/path rules, and say the agent may run them itself. A judge shows only its summary, never its prompt filename; a sealed judge without one gets a fixed agent-judge description.

`[workflow] start` must name a check or a step, not a special target such as `@done` or `@user`. A step at the start runs through the same admission as any later visit. Its first `context.json` has `input`, `key`, and `prev_attempt` set to null, with `visit` and `visits` both 1; that visit counts against `max-visits-per-outcome` under the null outcome and null key.

Workflow agents, judges, script and shell checks, and command steps receive `RIMZ_WORKFLOW_RUN` (run id), `RIMZ_WORKFLOW_DIR` (work directory), and `RIMZ_WORKFLOW_DEFINITION` (absolute definition folder). Every workflow agent gets an Environment `- workflow:` line even with `env_reminder` off. Non-workflow agent launches unset all three variables. If the agent launch cannot read the run record, it warns and omits the definition variable and line.

A step selects exactly one of `agent`, `run`, or `shell`, and requires `then` naming a check or a nonempty list of checks. A run or shell step requires `timeout` and accepts the common visit bounds and `on.cap`. `run` is a literally passed argv, with slash-containing words confined to the definition directory; `shell` runs through `sh -c` without path confinement. Command steps warn and ignore `prompt-file`, `lifecycle`, `keep`, `window`, `takeover`, `throttle`, `limit`, `capacity-wait`, `on.capacity`, and `on.asked`, even explicit default values, and never wait for checkout occupancy or capacity. Their stdin is closed, both streams go to `work/<seq>.step.log`, and they inherit the workspace pin and workflow environment.

An agent step requires `prompt-file`. Its `agent` accepts the fresh-launch layout grammar, including agent and command cells. `lifecycle` defaults to `until`: check `then` at each eligible leader turn end and leave the step when its route is neither this step, `@wait`, nor another listed check, closing the layout by default. Set `turn` for one turn, or `stay` to keep the attempt live until the leader's session exits. A staying step (`stay` or `until`, including an omitted lifecycle) warns and ignores `timeout` and `on.asked`; set `lifecycle = "turn"` to use them. An `until` step cannot use a sleep as its `then` check; `turn` permits it. An `until` answer routed back to its step becomes the next prompt in that session, updates input/key and spends one visit in the answer's bucket; a cap follows `on.cap` instead, closing the agent by default. A held `@wait` spends no visit and rechecks on subscribed signals and the minute tick while the leader rests. A new turn abandons that wait and any check in flight. Teams, command-only layouts, and ambiguous prompt leaders refuse with a field-specific fix. Judge checks still take one profile. An agent step's `window` gates every agent cell's provider.

`then = ["tests", "review"]` enters the first listed check. Every entry must be a check, and each except the last must have a direct route to the next. Empty lists refuse; until lists cannot contain sleeps. A route between listed checks on a held until session keeps it open, preserves input/key, resets check retry and starts the destination check's clock. The next eligible turn end starts again at the first check. A list of two or more checks on a `turn`, `stay` or command step warns that only an until step keeps its agent open across it. Delays between listed checks warn and are ignored; closing routes from any listed check may have a delay. A listed check reached without a held session routes normally.

Failed or interrupted turns, live provider limits, and budget parks keep every workflow agent step open. A turn step finishes on a later clean end; an until check judges only a cleanly rested turn. Providers that report an interrupt as a clean end still let the check judge. A turn step's timeout pauses during blocking asks, limits, errors, and budget parks, counting overlaps once; silence and interrupts do not pause it. Deadlines never pause. Provider exit still follows `then` as `died` for a turn run or `ended` for a registered staying run. A budget refusal before launch still follows `then` as `limited`.

`keep = true` on a `turn` or `until` agent step leaves the leader and companions open, outside the workflow, on a natural attempt end or a closing check route. Default false retains cleanup. Cancel, restart, deadline, a turn step's timeout, and a push-back cap parked at `@user` still stop them; a cap routed elsewhere detaches them. A `turn` check returning to the step can leave the old agent beside the new one; occupancy and `takeover` still apply. `stay` steps and non-agent nodes warn and ignore `keep`, including an explicit false value.

A check's `on.<outcome>` accepts a target string or `{ to = "<target>", delay = "30m" }`. `to` is required; `delay` is optional and uses a nonzero `s`/`m`/`h`/`d` duration, at most `365d`. The delay applies only while an until session is held at that check, measured from the saved answer's instant. It defers closing without rerunning the check or triggering its timeout. A new turn discards the verdict; cancel, restart, deadline, and provider exit still interrupt. Signals and active-run extensions do not shorten it. Without a held session the route goes at once, including after `resume --at` the check. Expiry rides the minute tick, so closing can be about a minute late. Node details and validate print `outcome → target after 30m`, and definition and run rails `outcome target after 30m`; node detail states the held-only rule.

A check selects exactly one of `run`, `shell`, `agent`, `sleep`, or nonempty `cases`. A sleep check takes required `sleep` (nonzero `s`/`m`/`h`/`d` duration, at most `365d`) and `then` (node, `@done`, `@failed`, or `@user`, never `@wait`), optional `when` (a nonempty ANDed loop-condition array) and `for` (a continuous hold shorter than `sleep`). It may take `provider` and `account` for window terms. Expiry follows `then` even during a hold; a true condition follows it early. Unread data, including under negation, never wakes it. Re-entry or a parked resume restarts its clock. A sleep forwards its incoming input and key unchanged and needs no timeout. An until step's `then` cannot name a sleep.

`[workflow.limit]` limits open agents started by that workflow name across rooms; `[steps.<name>.limit]` limits agents started for that step. Each takes at least one of the fields below. An unknown key or an invalid value warns and is ignored, and a limit left with neither field is ignored whole, with `set max-parallel or stagger`:

| Field | Rule |
| --- | --- |
| `max-parallel` | Integer at least 1. Counts open agents, including idle staying sessions, companions, RimZ-launched children and peers, and live agents whose last turn errored. Ended or dead agents, failed launches, and provider-built-in subagents do not count. An automated step larger than a cap fails with the fix, without waiting or taking `on.capacity`. |
| `stagger` | Positive duration in `s`, `m`, `h`, or `d`, at most `365d`. Minimum gap between launches at this scope, stamped at launch and shared across rooms and restarts. |

Limits use each run's sealed definition, but count open agents of that workflow name even after their runs finish. Waiting, paused, hibernated, and compacting agents count. The whole incoming agent group must fit, including starts admitted but not yet launched. Limits apply after window and occupancy, before the two machine caps and other machine checks, even with no `[throttle]` table. No workflow or step limit bypasses a machine cap. Earlier Active capacity waiters held by a workflow limit go first across all steps; a step-limit waiter holds only its step. Ties use run id. A freed slot waits for the earlier run's next retry. Limits never stop an existing turn or pane.

Agent steps of automatically loop-started runs also ask the [start throttle](./loop.md#the-start-throttle) before taking over a checkout. `throttle = "off"` skips the machine turn, stagger, resource limits, and capacity check, not the machine caps or applicable workflow and step limits. `capacity-wait` accepts a positive `s`, `m`, `h`, or `d` duration, or `forever` (the default). A held step spends no visit and retries about once a minute. Giving up follows `on.capacity`, default `@failed`, for machine and workflow limits alike; it may instead name `@done` or a node, but not `@user` or `@wait`, since capacity give-up never parks a run. A window or occupancy wait restarts the capacity clock. The run deadline still applies. Runs created by `workflow run` or `loop fire`, and runs detached by `loop remove`, skip waits but claim any applicable workflow limit, count as automated afterwards, and restart workflow and step stagger, never machine stagger. Without limits these starts take no ticket. Checks, command steps, and already-open staying sessions never ask for admission.

Limit holds are self-clearing (`workflow_limit` or `step_limit`), shown last in their workflow group. Reasons start with `workflow <name>: ` or `step <name>: `, followed by `N of M agents open (@a, @b, +K)`, `next start in <duration>`, `N earlier starts waiting` (singular `1 earlier start waiting`), or `N starts launching` (singular `1 start launching`) while a launch of the same workflow is not yet counted. Names list at most two handles, then `+K` for the rest; the suffix is omitted when empty.

## Inspect definitions

`rimz workflow show <WORKFLOW>` draws the current definition in walk order, with returning steps hung beneath their earlier sending check. Checks draw `◇`, steps `○`. `→` points to a later node and `↑` to an earlier node or itself. Unreached nodes follow under `unreachable from <start>`. The header names the summary, scope, loop tasks that start this workflow in the caller's project (machine tasks only outside a room), and any configured deadline route. Without a loop task it gives the by-hand command.

Each node shows its runner, summary when set, routes, and routing limits. Condition cases retain their order and hold durations, followed by `none true`; the note names where an unread term goes. Timeouts, visit caps, windows, takeover, bounded capacity waits, and staying lifecycles stay beside their nodes. Edges that cannot fire are omitted; uniform turn-end, invalid-check and unset-deadline defaults are stated once in the footer, only when used. `validate` shows the omitted edges with their marks. The footer names the source file and a command for one node in full. The live-runs table follows the definition.

A missing or unloadable definition prints `definition unavailable` with a `workflow validate` command, then still lists its runs and exits 0. An unknown workflow with neither a definition directory nor runs refuses. `show <WORKFLOW> --json` keeps its live-runs array and does not include the rail.

`rimz workflow show <WORKFLOW> <NODE>` prints one definition node in full: runner kind and summary, predecessors with the outcomes that reach it, check subscriptions (derived for conditions, explicit otherwise) and the minute tick, ordered condition cases with holds, every resolved edge with its source and fireability mark, then the configured command text, agent layout, prompt path, lifecycle, keep, takeover, window, throttle, limit, capacity wait, visit bounds (including reset-on), timeout, provider and account. A limit reads `max-parallel=N · stagger=<duration>`, omitting unset fields; the definition header prints its workflow limit in the same form. Commands keep their full text, including multiple lines. Never-firing edges appear here even though the rail omits them. Predecessors omit never-firing routes; conditional ones carry the shared mark.

The two-positional form takes a workflow name only, not an address or run id (usage error, exit 2), and conflicts with `--json` and `--history` in clap. An unknown node refuses with the definition's node names (exit 1). A missing or unloadable definition refuses with its validation command (exit 1); there is no runs-table fallback for a node view.

## Inspect runs

A held run with a future delayed close adds ` · checking <check>: closing in 23m → <target>` to its with-you detail and show headline. Once due but still ineligible, it returns to the ordinary checking/wait phrase. The same countdown appears in JSON `detail` in `workflow list`, `loop list`, and `loop show`.

`rimz workflow list [--json]` prints every active and parked run across rooms, without column headers. NEEDS YOU holds parked runs, active runs with a blocking ask, and capacity holds needing a fix (`check_failed`, `disk`, `store`), longest waiting first, with full addresses and a `workflow show` hint for its first run. The rest group by workflow name, each heading reading `<workflow> · N active[ · M held]`. Self-clearing capacity holds sort last in their group; each part sorts by address. NEEDS YOU rows are `? <address>  <detail>  <age>`. Grouped rows are `<glyph> #<lane>  <detail>  <age>`: `◉` for capacity holds, `⢿` for with-you sessions and active work, `☾` for other active waits, from the configured glyph set. A group names `started by <origin>` when all its runs share the loop task and manual-fire flag; otherwise each row adds ` · by <origin>`. An origin is `hand` or `loop task <task>[, fired by hand]`. Age starts at the park, at the opening of an ask, at the first capacity hold, or at node entry otherwise. Detail truncates before age at narrow terminal widths. Every row has the horizontal rail described below. Several rooms get headings, the caller's room first, and hints for other rooms carry `--root`. Finished runs are omitted.

When the sealed definition loads with ignored fields, the row adds ` · N ignored` to its detail, without changing JSON `detail`. The mark is omitted if it cannot fit the terminal width. The live-runs table under `show <WORKFLOW>` uses the same mark. A clean run has no mark. Single-run `show`, including `--history` and finished runs, prints each ignored field's path and reason as a `warning:` line below the rail, before `visits`; `--history` keeps warnings below the headline. These warnings are recomputed from the sealed definition with the current binary; they are not copied into the run record. Environment warnings such as auto-continue being off do not mark a run. Loop views, the sidebar, resume receipts, and definition rails do not show ignored-field marks.

Detail is `asking you: <handle> (<kind>): <one-line text>` for a blocking ask; otherwise a live staying session reads `with you in @<handle>`, with ` · checking <check>` while held and `: <wait phrase>` at that check, or ` · <check>: <wait phrase>` after it when waiting. The handle matches its agent card, without the channel already named by the row; if unavailable, it falls back to the recorded pet name. A capacity hold reads `held · <reason>`; other runs print the [park phrase](#park-reasons), [wait phrase](#the-waiting-line), `running` (with ` · visit <n> of <max>` when capped), or `checking`. A cached PR number adds ` · PR #N` once per row; no cached number means no badge. Each room supplies its own agent names and PR cache. JSON reads neither that enrichment nor the journal: its keys and shape stay unchanged, and `detail` retains `with you` without an agent or PR and `held <age>[, gives up <clock>] · <reason>` for capacity waits, without node or the separate age column. A single-run `show` says `<step> is asking you` while asking, otherwise `<step> is with you` for a live staying attempt. Its session attempt is `held.attempt` while checking, otherwise `attempt`; its `lifecycle` is `stay` or `until`, omitted for turn attempts. An open blocking ask is stored in `asking`; `asked_ms` is the total closed pause time in milliseconds. Both are omitted when empty or zero. While held, the rail marks both the session step and its check current.

`rimz workflow show <RUN> [--history | --json]` opens with `<address>[  PR #N]`, then the activity glyph and current state on a second line. Only the state phrase takes the state tone; agent context uses body tone and the bound forecast is muted. A live agent uses its full card handle, including the channel, with the recorded pet name as fallback; `--history` keeps pet names. A with-you headline adds the same check/wait suffix as the list, without repeating it below. A wait names its node, elapsed time, recheck and the next bound's time and target; a hold names its outcome, duration and the next bound's time and target. The forecast picks the earliest unfired deadline, timeout or hold completion, in that order on ties. A running step shows its visit limit and agent handle when available. Asking reads `<step> is asking you · <handle> (<kind>)` and says to answer in the pane or with `rimz answer`; a turn step's timeout pauses while asking. A parked headline reads `parked at <node> <age> · <reason>`, leaving its explanation to the block below. Finished runs say `done`, `failed`, or `canceled`, aged from termination, and show no PR badge, including under `--history`. The origin line names when and how the run started (by hand or by loop task), the number of completed attempts, and their known total cost, including judge evaluations. It omits cost when none is recorded, and never estimates a live attempt's spend.

On an active run, the current check's latest evaluation since entry supplies one saved readings line below the headline: `key=value` pairs separated by two spaces, null as `key=unread`, then ` · read <clock>`. Script and condition readings use the same line, with no per-case value annotations.

Alongside the saved readings, a human live or parked run shows one `now <check> · <outcome>` line for its condition check or sleep with `when`. On an agent step it reads the first listed check; on a parked check it reads that check. The line uses current `key=value` readings, null as `key=unread`, and the evaluator's unread reasons. A winning case with `for` shows the remaining hold from its open wait for that case, or the full duration without one. Forge keys add ` · read <clock>` for the cached probe; board-only checks omit it. The freshness floor is the step or parked node entry, or the held session entry while held. It launches no check, writes nothing and refreshes no probes; the CI fence may make read-only Git calls. Script, shell, judge and plain-sleep checks have no now line. JSON and history are unchanged.

The block below the origin shows the full ask text when asking. A takeover wait adds `takeover:` lines naming the agents that hold the scope path (`blockers unavailable` when the agent roster or the project's worktrees cannot be read). A parked run instead explains [why it stopped](#park-reasons) and prints `you can` commands. These commands, history footers, receipt hints and NEEDS YOU hints use the address when it selects this run, otherwise the run id, and add `--root` for another room. A visit cap lists the capped step's session ends, push-backs and the refused visit; a per-outcome cap lists only that outcome/key bucket's attempts since the last reset. A timeout shows the flushed wait as `<node> said <outcome>` with a folded count and span when present, and the last shell-check log; `invalid` shows the recorded stderr tail.

Active runs paint the definition rail after the block below the origin and before `visits`, using the run's sealed definition, never the edited source. Reached steps draw `●`, reached checks `◆`, with green glyphs and body-tone names. Unreached steps draw `○`, checks `◇`, in muted tone. Current nodes use the headline's glyph, bold in the state tone, including both the session step and check while held. Reached nodes add their last check outcome or completed attempt (outcome, duration, known cost, recorded HEAD before and after), its local clock, and `×N` for repeat entries. A capped step adds `visit <used> of <max>`, including the run's grant. For a per-outcome-only cap, a past step uses its last attempt's routed outcome and key; a current or held attempt uses its live bucket. Equal recorded commits read `HEAD <a>, no new commits`; different commits keep `HEAD <a> → <b>`. The current check names its outcome, `since <clock>`, `last checked <clock>` from its latest evaluation, wake selectors and the minute tick, with no advance count. False cases are faint; the winning or held case reads `│ ▸ N`, bold blue except green for `@done` and alarm for `@failed`. The first unread case keeps `?` and `<key> unread: <reason>`. Later cases are unmarked and muted, except that `@done` and `@failed` cases keep their definition tone. A held case shows its elapsed and required duration and target, with a completion clock only when that completion is the next bound. Marks remain visible with `NO_COLOR=1`.

Parked runs put a horizontal rail after `you can`; finished runs also use it, with no current node. Steps draw `●` when reached and `○` otherwise; checks draw `◆` and `◇`. The current node uses the headline's activity glyph. Reached glyphs are green with body-tone names, current nodes are bold in the state tone, and unreached nodes are muted. A finished run's ending node is where it stopped: alarm-colored for failed runs, green for done or canceled runs. With colour off, the ending node has no mark of its own and draws as any other reached node, `●` or `◆`. Nodes join with ` ─ ` in walk order. A visited, current, or terminal-ending detour hangs below its sending check as `╰─ <glyph> <step>[ ×N] ↑`, with the visit total above one. Unreachable nodes appear after the main rail only when current or reached, including after `resume --at`. To fit a terminal, the rail drops nodes from the left as `… `, then from the right, regardless of whether they were reached, always keeping the current or ending node. Next, nodes between a held run's two current nodes drop as ` ─ … ─ `, and then the predecessor, which stays only while it fits. If that still does not fit, visited detours under the kept nodes drop, except those that are current or ending, and dropped nodes return wherever they fit. A detour drops with its parent unless it is current or the ending, which keeps its parent visible. Names are never shortened, so a current or ending node or detour wider than the terminal is drawn whole. Piped rails are not shortened. Capped visit totals remain in the `visits` rows below.

`visits  <step> <used> of <max>` lists each visited capped step, with the run's grant included in the limit. A per-outcome cap adds `<step> <used> of <max> for <outcome>`, followed by `key <json key>` when set, in recorded bucket order. A missing outcome prints `null`. Outcome rows count since the step's last reset; total rows count since its last manual restart or cap resume. A per-outcome cap park lists only the bucket's session ends and push-backs after its last reset; a total cap park lists those since the step's last full reset. Uncapped steps print no visit rows. The `trail` projects routing decisions from the sealed specification and journal, folding consecutive matching check answers as `×N`. It includes `<step> visits reset on <outcome>`, resumes, restarts, parks and termination, keeps at most the newest eight hops with `+N earlier` for the rest, and ends in `now` while live. The footer names the home-relative work directory and the command for full history.

`--history` replaces the compact view with the same headline and detailed journal history in recorded order, using local clocks and readable facts rather than raw JSON. Check answers read `<node> said <outcome>` and, only when they routed, `→ <target>`, along with readings, reasons, shell logs, judge cost, and invalid stderr tails. An abandoned check reads `<node> said nothing · <outcome>` because it returned no answer. A route that repeats the preceding check answer takes no row. Attempts show visits, handles or command exits, duration, cost, short HEAD before and after, logs, reasons, stopped and live children, provider reset, questions, and digests. Other routes show targets and input fields; waits show outcome, count and span; turn ends show action, check, outcome and target. A park keeps its `park <reason>` marker but omits its text when the newest printed said or route row at the same node already printed that text as its object's `reason`; other parks keep their text. Resumes, cancellation, terminal states and wake signals retain their recorded facts. `--history` requires an address or id, not a workflow name, and conflicts with `--json` (usage error, exit 2).

Adjacent check answers with the same node, origin, outcome, and condition case index fold into one row, regardless of changes to their reason or other answer fields. Adjacent wakes fold when their node and signal agree; a wake between answers keeps its own row and breaks their run. A folded row uses the newest time, `#first–last` (or `#—` without sequences), `×N over <span>`, the newest answer, and the judge cost its members recorded, summed. The span runs from the oldest to the newest member; `over <span>` is omitted under one second. A closing check-wait summary takes no row when any earlier answer row at its node with its outcome overlaps the wait's inclusive span. Other waits, including step waits and waits whose answers are missing, print `×N over <span>` when N > 1, using the wait's first and last times and omitting the span under one second, followed by ` · <detail>` when present. Omitting a summary does not break an answer run. `--json` keeps every journal entry, including closing waits and duplicate routes, without folding.

### The waiting line

Status phrases do not print `said` or an advance count: an advance can find the run waiting without evaluating its check. The JSON shapes are unchanged; this text change also applies to `workflow list --json` `detail` and `loop list --json` / `loop show --json` `workflow_runs[].detail`. History and park answer rows keep `<node> said <outcome>` and their journal-fold counts.

A run at a wait carries a shared phrase without the node; capacity waits carry a held age. A single-run `show` puts the phrase in its state headline, after the check a `with you` headline names. Every instant, including capacity bounds, uses local `HH:MM` today, `Mon HH:MM` within six days in either direction, and `YYYY-MM-DD HH:MM` beyond that.

```console
$ rimz workflow list
review · 1 active · started by hand
  ☾ #project  pending, recheck 04:37  0s
      ☾ pr
```

| Part | Meaning |
| --- | --- |
| `<outcome>` | A check answered an outcome routed to `@wait`. |
| `holding <outcome> <elapsed>/<for>` | A condition case keeps winning while its hold duration runs. |
| `sleeping <elapsed>/<sleep>[ when <terms>] → <then>` | A sleep's entry-based clock, replacing every sleep wait phrase, including unread and held conditions, without a recheck clock. A plain sleep waits until its stored end; a conditional sleep re-samples about once a minute and on matching signals. |
| `unknown: <keys and reasons>` | A condition cannot read enough data to choose its first matching case. Bare `ci` can name a local HEAD not on the PR or CI read at a different PR head; see [JSON shapes](#json-shapes) for the reason forms. |
| `window <term>` | An agent step or judge whose provider `window` is closed, with the failing term and its reading. |
| `takeover` | The checkout holds an agent mid-turn, so the step cannot evict it yet. |
| `occupied` | The checkout holds an idle agent and the step has no `takeover = true`. |
| `held <age>[, gives up <clock>]` | An automatic loop-started agent step is held by machine capacity or a workflow/step limit. Its give-up time is absent for `forever`; the reason follows ` · `. |
| `recheck` | The check's `recheck_at`, before which nothing evaluates; a signal matching that check's subscription clears it. For a `for` hold it is when the hold completes, and subscribed signals and the minute tick re-sample the case before then. |

## Cancel and resume

`rimz workflow restart <RUN> [--continue]` replaces the current agent step, including a held `until` session or a run parked at an agent step. It stops the owned layout, keeps input and key, resets that step's total and every outcome/key count, and starts at visit 1. It skips the step's usage window and capacity waits as a manual start; oversized layouts still refuse, and checkout occupancy and takeover still apply. Other steps' counts and run-wide grants are unchanged.

Restart cancels any unconsumed push-back from the abandoned attempt, including one already sent to the pane, so it cannot delay judgment of the replacement's next clean turn. Other messages are unchanged.

Without `--continue`, the replacement starts fresh. With it, the leader resumes the current attempt's recorded conversation under the room's current account; from a parked agent step, it uses the previous attempt only when that attempt belongs to the same step. A still-live previous card is stopped before relaunch, and companions start fresh. A missing conversation, unsupported provider resume, or a different account history pool refuses before anything stops, naming a fresh `workflow restart` or `rimz accounts use` fix. If resume preparation fails after the stop, the run parks at the step with reason `invalid`, and the park text names `rimz workflow restart <RUN>` for a fresh replacement. The receipt shows the park when the launch has already settled, and otherwise `awaiting launch`. Finished runs, checks without a held agent, and command steps refuse without stopping anything.

The receipt names the run, step, new agent, fresh or resumed mode (and session), and `visits restarted at 1`. A restart waiting for occupancy or a stop already in progress instead reports `awaiting launch`; `workflow show` follows its progress. History records the canceled live attempt, a full visit reset, and `<step> restart · fresh|continued · visits restarted at 1`; stopping a previous attempt again does not repeat its end or cost.

The journal records `{event: "restart", step, continued}` and `{event: "visits_reset", step, outcome: "restart" | "cap", all: true}`. A missing `all` means false for older outcome-only reset rows. A total-cap explanation starts after the last full reset; a per-outcome explanation starts after either reset kind.

`rimz workflow cancel <RUN>` ends a run as `canceled` and stops its live script, shell, judge, or step attempt. It prints `canceled <address>`. An already-finished run id prints `<address> is already <state>; unchanged` and still exits 0. Both receipts end with a `workflow show` hint.

A cancellation journal row may carry `reason`; `show --history` prints `cancel canceled · <reason>` when present, otherwise `cancel canceled`. Older rows without a reason still read.

An unfinished run holds its scoped worktree against removal, even while parked with no agent. `rimz worktree remove NAME --force` removes the checkout and then cancels its unfinished runs with reason `worktree removed`. A failed cancellation leaves the removal standing, exits non-zero, and prints the run id's `rimz workflow cancel` command to finish it.

`rimz workflow resume <RUN> [--at <NODE>] [--extend <GRANT>]...` puts a parked run back to work, at its current node or at `--at <NODE>`, with a fresh timeout clock and a cleared check retry. `--extend` repeats:

| Grant | Effect |
| --- | --- |
| `visits=+N` | Adds N to every step's `max-visits` and `max-visits-per-outcome` for this run, for every outcome/key bucket. The grant survives resets; per-outcome counts start from the last reset. |
| `deadline=<WHEN>` | Replaces the run's deadline and arms it again. `WHEN` is an RFC 3339 instant or a local date or date-time; a bare date is local midnight. |

An active run accepts `--extend` alone; `--at` needs a parked run. A finished run refuses. The definition stays sealed: grants live on the run record.

The receipt says `resumed <address> at <node>`, with the current step's used and granted visit limit when capped, any added visit grant, and its armed deadline. Extending an active run says `extended <address>` instead. Both end with a `workflow show` hint. Resuming a cap park resets the capped step's total and every outcome/key count, even with `--at`. Either receipt warns about an armed deadline already past, naming its immediate destination and the matching `--extend`. A fired deadline stays disarmed on plain resume; use `--extend deadline=<WHEN>` to arm it again.

```console
$ rimz workflow resume 'repair#feat-x' --extend 'visits=+1'
resumed repair#feat-x at work · work 2 of 3 visits, every capped step +1
→ rimz workflow show 'repair#feat-x'
```

## Validate and schema

`rimz workflow validate [DIR] [--json]` checks one directory, or every directory under `~/.rimz/workflows/`. A single normal path component names a workflow under that home, as in `run`; any other path is checked where it is, inside that home or not, and its name must still be a valid workflow name. Profiles and teams resolve from the machine's definitions either way. The table has `WORKFLOW`, `NODE`, `KIND`, `RUNNER` (the run command, shell text, step layout, judge profile, `condition`, or `sleep`), `BACKGROUND` (whether the step's leader reports background work), and `EDGES`. An edge prints `outcome → target (source)`, or `outcome → target (source, mark)` when conditional or unable to fire; `source` is `explicit` or `default`. A step's `asked` edge appears only when `on.asked` is set, always as explicit; staying steps have none. Errors and `warning: <workflow>: <path>: <reason>` lines follow. Any error exits 1; warnings alone exit 0. Condition and sleep stage names use the caller's effective teams plus `Done`; without a resolved workspace, a warning says stage names were not checked. Run admission always checks against the run's project.

Unknown fields at every table depth warn and are ignored. A wrong-typed or invalid optional value also warns and reads as absent, even when it limits an agent (`window`, `throttle`, or `max-visits`). Live route targets and `on` tables are an exception: wrong types refuse instead of selecting defaults. The warning's reason starts with `ignored field:` and explains why. Paths are dotted, with zero-based array indices, such as `checks.review.wake.0` or `checks.pr.cases.1.for`. Dropping a value restores its omitted-field behavior, including `lifecycle = "until"` and `capacity-wait = "forever"`.

| Optional value | Ignored when |
| --- | --- |
| `summary` on the workflow, a check, or a step | Blank or multiline. |
| `workflow.deadline` | Not a supported date or datetime. |
| `timeout` | Not a supported `s`/`m`/`h`/`d` duration, or over `365d`. |
| `window` | Not a supported provider-window expression. |
| A `wake` entry | Wrong-typed, an invalid selector or match, an agent lifecycle selector, or a team selector other than exact `team.stage`. Only that entry is dropped; other entries stay. Unknown keys in a wake table are ignored individually. |
| `max-visits` | Not a positive integer. |
| `max-visits-per-outcome` | Not a positive integer or `{ limit = N, reset-on = "outcome" }` table (`reset-on` is optional and accepts one outcome or a nonempty list). A missing or invalid `limit`, an invalid `reset-on`, or a limit at least `max-visits` drops the whole cap. Unknown inner fields warn at their dotted path and are ignored individually. |
| A case's `for` | Unparsable, zero, over `365d`, or on an outcome routed to `@wait`. |
| A sleep's `for` | Wrong-typed, unparsable, zero, over `365d`, without `when`, or not shorter than `sleep`. |
| A check route's `delay` | Wrong-typed, unparsable, zero, over `365d`, on a check not listed by an until step's `then`, targeting `@wait`, returning to an owning until step, or routing to another check in that step's list. Only the delay is dropped; the route remains. |
| Workflow or step `stagger` | Wrong-typed, unparsable, zero, or over `365d`. |
| A condition or conditional sleep's `provider` | Unknown, or no term reads `window.*`. |
| A condition or conditional sleep's `account` | No provider remains after ignoring. |

Fields on the wrong node kind also warn and are ignored: `else` on non-condition checks; `provider` and `account` on checks without conditions; `prompt-file` and `window` on non-agent checks; `wake` on conditions and sleeps; `when`, `for`, and `then` on non-sleep checks; and the command-step and staying-step fields listed under [Run a workflow](#run-a-workflow). A sleep also ignores `timeout`, `else`, and every `on` route as dead, with warnings at each dotted path. Combining `sleep` with another runner still refuses.

A dead check route warns and is ignored even if its value has the wrong type: shell outcomes other than `pass`, `fail`, `timeout`, and `invalid`; condition outcomes not declared by a case or `else`, except `unknown`, `timeout`, and `invalid`; and other reserved check routes such as `on.hold` or `on.cap`. A bad target on a remaining route still refuses: a value other than a target string or route table with string `to`, an unknown node, `on.timeout = "@wait"`, `on.capacity` to `@user` or `@wait`, a step edge to `@wait`, or `on.cap` targeting its own step. Unknown route-table keys warn and are ignored individually. A step's `then` must name a check or a nonempty list of checks.

Required fields still refuse when absent or invalid: `[workflow]`, `workflow.scope`, `workflow.start`, a case's `when` and `outcome`, and a wake table's string `signal`. A malformed case or `cases` array refuses, except an unknown field or invalid optional `for`. A sleep's invalid or zero duration, missing or invalid `then`, or malformed, empty, unknown-valued, or invalid-stage `when` refuses at that field. Invalid TOML refuses too. Kind-conditional requirements also remain: exactly one runner per node, a nonempty shell, confined `run` paths, a confined `prompt-file` on agent nodes, a one-line `summary` on judge checks, a condition's `else` and routes for every declared outcome, shell checks' `on.pass` and `on.fail`, non-sleep waiting checks' and command steps' `timeout`, and a provider for window terms. Agent profiles, step layouts, judge headless support, names, and graph rules are still validated.

Cross-field rules run after ignoring. An invalid command-step timeout therefore warns, then refuses as missing; a discarded `max-visits = 0` cannot bound a step cycle. A surviving per-outcome cap's `reset-on` requires `max-visits` and names only non-reserved outcomes on checks' edges; violations error at `steps.<step>.max-visits-per-outcome.reset-on`. A dropped cap gets no reset-on errors. A cap without `reset-on` warns when its step is not the start, no `then` reaches it, and only one outcome reaches it: it repeats `max-visits` unless a check answers keys. A check-only cycle still needs `@wait`, and a step cycle still needs a total `max-visits` bound. Live runs use the same tolerance when rereading their sealed definition, without repeating admission validation.

Rows follow the graph from `start`, with a returning step immediately below the earlier check that sends it. Nodes reachable only through `workflow.on.deadline` follow the start component; unreachable nodes come last in name order. Edges follow case order without repeats, then `else`, then other explicit outcomes in name order, then engine triggers: `unknown`, `timeout`, `invalid`, `deadline` for checks; `then`, `asked`, `cap`, `capacity`, `deadline` for steps. These row and edge orders also apply to JSON.

| Mark | Meaning |
| --- | --- |
| `never: no timeout` | The check has no timeout clock. |
| `never: no max-visits` | The step has neither visit bound. |
| `never: capacity-wait is forever` | Capacity admission never gives up. |
| `never: a judge retries once, then parks at @user` | A judge never follows its `invalid` edge, even an explicit one. |
| `only with a deadline` | No deadline is sealed; a run needs a deadline grant. |
| `only when a loop task starts the run` | Capacity can give up in an automatic loop-started run, not a by-hand run or `loop fire`. |

`--json` prints `{rows, warnings, errors}`, each error and warning carrying `path` and `message`. Each row has `runner = "run" | "shell" | "agent" | "condition" | "sleep"`, nullable `summary`, `run`, `shell`, and `agent` fields, `workflow`, `node`, `kind`, `do_background`, and resolved `edges`. Each edge keeps `outcome`, `target`, and `source`, and adds `fires`: `"yes"`, `"never"`, `"with-deadline"`, or `"in-loop-runs"`. A delayed edge alone carries `delay`, the configured duration string such as `"30m"`; other edges omit the field. Only `"never"` edges carry `because`: `"no-timeout"`, `"no-max-visits"`, `"capacity-wait-forever"`, or `"judge-retries"`. A bounded capacity edge remains reachable in loop runs even with `throttle = "off"`, because machine caps can hold it. Marks explain edges; they do not add validation warnings or relax admission rules.

A sleep's edges are explicit `then → <then>`, default `sleeping → @wait`, default `unknown → @wait` only with `when`, default `invalid → @user`, and the header's `deadline`, in that order. There is no timeout edge. Definition rails and node details show `sleep`, `when`, `for`, and `then`, never the generated waiting edges or a generated case. A plain sleep journals `{outcome: "sleeping", recheck_at: "<entered_at + sleep>"}` at entry and `{outcome: "then", reason: "slept <sleep>"}` at expiry, inheriting the key into each object. Conditional sleeps use condition answers with `case: 0` for an early win; false is `sleeping`, unread is `unknown`, and an unfinished `for` rewrites a win to `hold`. These answers never replace the run's input or key. History hops show `sleeping → @wait` and `then → <then>`.

Command-step validation rows have `kind = "step"`, `runner = "run" | "shell"`, the command in the corresponding field, `agent = null`, and `do_background = false`. Their edges are `then`, `cap`, and `deadline`, never `asked` or `capacity`; `BACKGROUND` prints `—`. Agent-step rows include a `capacity` edge to `@failed` by default, marked according to `capacity-wait`. Agent-only warnings do not apply to commands.

Turn and `until` steps warn when the leader adapter has no background reporting: a turn end may finish the attempt while provider background work remains. When auto-continue is off, agent steps warn that a step paused on a provider limit waits for you. Agent judge checks instead warn that a provider limit ends their attempt as `limited`.

`rimz workflow schema` prints the JSON Schema of `workflow.toml`. Its tables keep `additionalProperties: false`, so editors flag unknown fields even though the loader ignores them with warnings. The `[workflow]` header accepts an optional `summary`: one nonempty line describing the graph. Blank or multiline values warn and are ignored at `workflow.summary`; omission never warns. Checks and steps accept their own summaries under the same rule, except that a judge requires one at admission. A blank or multiline judge summary is dropped, then refuses at `checks.<name>.summary` with `add summary = "..."`. Older sealed judges without one keep running with the fallback launch description.

## Loop tasks

A [loop task](./loop.md) starts a workflow with `workflow = "<name>"` in place of `agent` or `wait`:

```toml
[tasks.babysit-pr]
workflow      = "babysit-pr"
each-worktree = true
when          = ["pr=open"]
for           = "3m"
```

| Field | Meaning on a workflow task |
| --- | --- |
| `workflow` | The definition name under `~/.rimz/workflows/`. Conflicts with `agent` and `wait`. |
| `prompt`, `prompt-file` | The run's prompt. |
| `each-worktree` | Expand each fire over RimZ-owned checkouts. With `when`, launch once per checkout. A worktree-scoped run without it scopes to the task's `dir`, else its root; a project-scoped condition launch covers all checkouts permanently, while other triggers skip only a live held run. |
| `when`, `for`, schedules, `root` | As on any task. |
| `budget`, `budget-per-day` | Ignored: a workflow fire is not gated on spend, and step costs are not counted against the task. The turn, room, and account caps still park a step agent like any agent in the room. |

Loop-started runs do not print validation warnings; ignored fields remain visible in `workflow show` and `workflow list`. `loop show` joins each checkout to its recorded run, finished runs included. `loop list` keeps only active and parked runs; its launched-worktree count includes finished entries.

`stay`, `takeover`, `subscribe`, `check`, `judge`, `throttle`, and `capacity-wait` are refused, each with the workflow node that owns the concept. A `when` task launches its workflow once per checkout: subsequent scheduled fires start nothing and record nothing, whether that run is active, parked, or finished. Project-scoped launches cover all of the task's checkouts, including later ones. `rimz loop fire <task>` bypasses this memory and replaces the entry only when a new run starts. `rimz workflow run` starts an independent run without changing the task's entry. Task replacement preserves the entries; rename moves them and removal clears them. Removal also detaches the task's active and parked workflow runs, which continue as independent runs.

An unrecorded checkout retries a sustained-true condition every five minutes. A fire that finds an active or parked run records `workflow skipped` with its id and adds no strike, checking before it reads the definition or prompt. If that run belongs to this task, the fire repairs its launch entry, so later scheduled fires are silent. A run started independently or by another task is not adopted, and the task retries until that run ends. Schedule, signal, and watch workflow tasks keep admitting a new run on each fire unless a live run holds the scope; finished runs do not block them.

## Park reasons

A parked run appears under NEEDS YOU in `workflow list` and, when it belongs to a loop task, `loop list`. A dismissable sidebar notice names its address, or the parked-run count, and points to `rimz workflow list` without giving a reason. A new park raises the notice again after `x` dismisses it; `show` explains why and prints the available next commands.

The list's park phrase is `<reason>[: <text>]`. Cap, timeout, and deadline phrases derive `cap: <used> of <max> visits`, `timeout: waited <timeout>`, and `deadline: passed <clock>` from the sealed spec and record; other reasons keep the recorded text on one line.

| Reason | Cause |
| --- | --- |
| `user` | An edge routed to `@user`; the text is the check's `reason`. |
| `cap` | A step reached `max-visits` or `max-visits-per-outcome`, and `on.cap` defaults or routes to `@user`. |
| `deadline` | The run's deadline passed, and `on.deadline` defaults or routes to `@user`. |
| `timeout` | A check's `timeout` passed, and `on.timeout` defaults or routes to `@user`. |
| `invalid` | A script or shell check could not evaluate (including invalid script output), and `on.invalid` defaults or routes to `@user`; or a continued restart failed after stopping the old agent. |
| `asked` | A turn step's leader or child blocked on a question or permission prompt and `on.asked` routes to `@user`; the text is the prompt. |
| `check` | A check evaluation failed twice. |

Script process failures say `<script> exited N` or `<script> killed by SIGTERM` (using the signal's name when known). `<script>` is the first `run` word containing `/`, or its first word when none does. Judge process failures say `judge exited N` or `judge killed by SIGKILL`; provider errors or invalid provider output take precedence over the exit status. Existing runs retain their recorded text.

Routes, step launches, parks, and ends append `workflow_*` assists ([stats](./stats.md#the-assist-timeline)). A merged wait appends one route assist when it closes, with its final `count`; an open wait has no route assist yet. Stats renders a closed wait as `workflow <workflow> <node> waited <outcome> ×<count>`.

## JSON shapes

`list --json` and `show <workflow> --json` print arrays of `{id, address, workflow, scope, state, node, since, detail}`, with optional `hold` for a known capacity cause and `warnings: [{path, message}]` only when the sealed definition loads with ignored fields. Clean rows and rows whose sealed definition cannot load omit `warnings`. `scope` is the scope path: the checkout, or the project root for `scope = "project"`. `since` remains node entry, not the human row's state-specific age. `detail` is the shared phrase above, without the human ignored-field mark, so its capacity bounds follow the same day-qualified clock as rechecks and passed deadlines. No existing key is removed, but consumers matching the old `waiting: <node>,` prefix must use the separate `node` and `since` fields instead.

`show <RUN> --json` prints `{address, dir, record, journal}`: the short run address, work directory, run record, and history entries. When the sealed definition loads, it adds `warnings: [{path, message}]`, empty when clean; when loading fails, it omits `warnings` and still prints the record and journal. Each warning's `path` is dotted and its `message` includes that path and the ignored-field reason. An active attempt's optional `asking` is `{since, text, kind, handle}`, with `kind` one of `question`, `permission`, or `plan_approval`; `asked_ms` accumulates closed pauses. These fields pause a turn step's timeout, not the run deadline. Evaluation rows carry `origin = "check"` for a check's answer or `"engine"` for an engine-decided outcome.

Optional `attempt.held_since` opens the shared pause at the earliest ask, limit, error, or budget-park evidence, clamped to the attempt's start and the observation time. It remains open through overlaps; `asked_ms` credits the interval once all such evidence clears. A legacy open `asking` without `held_since` supplies its original `since`. In-flight version-1 and version-2 records advance to version 3 before publishing this field.

Optional `record.restart` is `{resume: "session-id" | null, settled?: N}` while a manual replacement is pending. Null means a fresh start. `settled` names a previous attempt being stopped again whose end and cost are already journaled. The field disappears when the launch is published or the run parks or terminates. Older records omit it.

`record.visits.<step>` is `{total: N, outcomes: [{outcome: "name" | null, key: "text" | integer | null, visits: N}]}`. A bucket is the routed outcome plus the run's key, not the sending check's name. It uses `input.outcome`, except at the step named by a cap object's `step`, where `input.routed_by` preserves the refused outcome. `total` counts since the last manual restart or cap resume; `outcomes` holds counts since the last full or outcome reset. Older records with `{total, keys: [{key, visits}]}` still load, with a null outcome for each old row. Attempt journal rows and `record.prev_attempt` carry `routed_by` (the admitted outcome) beside `key`, defaulting to null on older entries. A check that clears nonempty rows journals `{event: "visits_reset", step, outcome}` on its check entry. Repeated reset answers with nothing to clear write no reset event.

A capacity wait has `record.wait.outcome = "capacity"`, provider `kinds`, optional `hold` (the [typed cause](../../internals/harness/loops.md#the-start-throttle), absent in older records), and optional `gives_up_at` (absent for `forever`), alongside the usual `node`, `detail`, `first`, `last`, and `count`. Closing the wait carries `hold` into its history entry. Giving up journals a `capacity` route with input `{outcome: "capacity", step, reason, kinds, waited_ms}` and any inherited `key`.

New runs use `record.version = 3`; the loader also accepts versions 1 and 2. While checking an open session, optional `held` is `{attempt, entered_at, verdict?}`: the session attempt, the step's entry time, and the saved check verdict. A step's `attempt.visit` records its outcome/key bucket count at admission, including that launch or push-back. The context, `live_attempt`, `prev_attempt`, and attempt journal row keep that latest number through resets alone. Older attempts without a visit stamp use the current bucket count. Optional `attempt.push = {message, queued}` persists the push-back message id before delivery; `queued` means the host has confirmed enqueue, including an id already in live or retained history. Optional `attempt.judged` is `{agent_id, started_at, ended_at}`, the consumed leader turn end. A verdict is `{node, entered_at, at?, target, object, reason}`; every new verdict writes `at`, the instant its evaluation was journaled. Older verdicts have no `at`, so a wait merged from one uses the merge instant. A closing attempt carries the verdict in optional `attempt.ending.route` until the stop settles. Older binaries refuse version 3 and skip those runs in lists.

Each turn-end decision or held-wait answer writes a journal row with `event = "turn_end"`, the session's `seq` and step `node`, `action = "kept" | "pushed" | "closed" | "discarded" | "interrupted"`, `turn = {agent_id, started_at, ended_at}`, and `check`. A saved verdict supplies optional `outcome` and `target`; `reason` explains an interruption or a moved-turn discard. A `pushed` row also carries optional `visit` and `message` and counts as a visit in history, the trail and cap inspection. Text history prints the action and any outcome, and the target only for `kept`, `pushed` and `closed`, since a discarded or interrupted verdict routed nowhere.

`work/context.json` adds `live_attempt` while an `until` session is open with no staged ending: `{step, seq, visit, visits, key, started_at, handle, run_id, claim_path, head_start, turn_end}`. `turn_end` is the last consumed turn identity, or null. There is no outcome or end evidence in `live_attempt`; `prev_attempt` still describes the last ended attempt. During evaluation, the top-level context describes the check, without `visit` or `visits`; a push-back or discard rewrites it to the session's step view, a held `@wait` keeps the check view, and a close leaves it until the next publication.

Command-step attempts and `record.prev_attempt` carry nullable `code` (exit code, null after a signal or an unobserved exit) and `log` (the absolute `work/<seq>.step.log` path when the file exists). Agent attempts write both as null; records predating these fields still decode. Command steps have null `handle`, `run_id`, `children`, `limited`, `asked`, and `cost_usd`. The hosting process samples `head_start` before the command and `head_end` after reaping it; `head_end` is null when another process settles it. `claim_path` still names `work/<seq>.claim.json`.

A command step records `ended` on exit 0, `died` on another exit, signal, spawn failure, or log-open failure, and `timeout` when its step timeout interrupts it; these follow `then`. A run deadline records `canceled` and follows `on.deadline`. Cancel records `canceled` and ends the run. A lost host records `canceled` with a reason and follows `then`, without rerunning the action. An interrupted command whose bound is no longer due follows `then` as `canceled`. A child that exited on its own keeps its exit outcome even if a bound fell due before settlement. The next check receives the original routed input; the command's evidence is in `prev_attempt`.

Text history keeps the attempt event line and adds `    exit <code|—> HEAD <start8|—> → <end8|—>` for a command step, followed by `    log: <path>` when present. An agent attempt names its handle instead of the exit. Any attempt with a reason adds `    reason: <text>`. A running command's headline has no agent handle.

A visit cap routes `on.cap` with `{outcome: "cap", step, bound: "max-visits" | "max-visits-per-outcome", visits, max, routed_by: "name" | null}`, plus the inherited `key` when present. `routed_by` is the capped bucket's outcome. A cap park retains its bucket; resume resets that step's total and every bucket, while `visits=+N` still raises the limits run-wide; routing into a different step counts there under `cap`. The total cap is checked first and wins when both trip. `visits` is the tripped bound's count (since the last reset for the per-outcome bound); `max` is its limit plus the run's visit grant. The journal's route input carries the same object. The number form of `max-visits-per-outcome` resets only on manual restart or cap resume. The table's `reset-on` clears that step's outcome rows when a valid check answers a listed outcome, regardless of its target. A held case resets only when it fires; invalid answers and engine routes never reset counts.

A shell answer is `{outcome, code, log}` plus an inherited `key` when present. Exit 0 is `pass`; another exit or signal is `fail`. `code` is an integer, or null after a signal. `log` is the absolute `work/<seq>.check.log` path, containing stdout and stderr together. Only `fail` has `reason` (`exited N` or `killed by signal`); output tails are not journaled. Both `on.pass` and `on.fail` are required. The only additional routes are `on.timeout` and `on.invalid`, each defaulting to `@user`; command spawn or log-open errors are `invalid`. The check's optional timeout spans waits and evaluations, without inheriting the loop's default timeout. A timeout routes `timeout`; a run deadline follows `workflow.on.deadline`. Both stop the shell's process group rather than answering `fail`. A `fail` routed to `@wait` shows `said fail` in the waiting line.

A run check keeps stdout as its JSON answer and writes complete stderr, including an empty stream, to `work/<seq>.check.log` once it settles. Invalid answers still journal the stderr tail. A child check's until push-back names its answering check, then its reason, then `output: <path> (<size label>)`, or `no output` for an empty or missing file, before the closing instruction. Run and shell checks use `.check.log`; a judge uses its whole saved `.check.json` answer. No tail or file content is copied into the prompt. Condition push-backs keep their term explanations.

A condition's answer has `outcome`, `readings` (a map from term key to string or null), and the winning zero-based `case` (omitted for `else` and `unknown`). The inherited run key is included when present; cases do not set keys. `unknown` includes a `reason` naming each unread key. While a case's `for` hold runs, the outcome is `hold`; `record.wait` carries `case`, `detail` (the case's outcome), `first`, `last`, `count`, and `recheck_at`. Without a hold, `wait.case` is omitted. `unknown` defaults to `@wait`; `timeout` and `invalid` default to `@user`. Explicit `on` entries override those defaults. `hold`, `unknown`, `timeout`, `invalid`, `cap`, `capacity`, and `deadline` are reserved outcome words; `on.hold` is a dead route, so it warns and is ignored.

The bare-`ci` commit fence sets `readings.ci` to null. When that makes the answer `unknown`, `reason` includes one of these, using the first seven characters of each commit OID (or all of a shorter OID):

- `ci (local HEAD <l7> is not on the PR, PR head <p7>)`
- `ci (read at <c7>, PR head <p7>)`

The local-HEAD reason takes precedence over the CI-commit reason; the pre-entry-probe reason takes precedence over both. The same text follows `unknown: ` in the waiting line and JSON `detail`, and remains in the journaled evaluation answer printed by `show` history.

`rimz loop list --json` carries `workflow_runs` for a workflow task: one object per active or parked run the task started in that room, `{id, address, checkout, state, node, since}` plus `reason` and `text` on a parked run. Both list and show add the shared `detail` when nonempty. `since` stays node entry; a human parked summary's age starts at the park.

`rimz loop show --json` also includes every run named by the task's condition launch memory, each once, including terminal runs whose task was renamed. A run canceled while parked keeps its recorded `reason` and `text` in JSON, without appearing as parked in human output. A run whose record is gone has only `id`, `checkout` (the launch entry's key), `state: "gone"`, and `since` (the launch time). Fan-out `worktrees[].run` repeats the matching `workflow_runs` object; project-scoped launches share one run across checkout rows. The human WORKTREES table names those runs, and RUNS lists only runs no worktree row names, folded rows included.

## Exit codes

`0` on success. `1` when a command refuses (an unknown run id, a duplicate start, a terminal resume, a validation error) or fails. `2` on a usage error.
