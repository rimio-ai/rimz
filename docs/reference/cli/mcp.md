# `rimz mcp`

`rimz mcp serve` is the MCP server a Claude, Codex, Antigravity, OpenCode, or Pi launch starts over stdio. It gives the agent RimZ's own commands as tools. You do not run it yourself: started with a terminal on stdin, it prints a short note to stderr naming the commands that show what it serves and what a launch passes it, and exits 0 without serving. `rimz mcp tools` lists what it serves.

```sh
rimz mcp serve [--only <capability>]... [--always <capability>]... [--deferred <capability>]... [--parent-env]
rimz mcp serve --launch-env [--parent-env]
```

`--only` repeats. Its values are the twelve capability names below, and without it the server serves every capability. Any other value is a usage error (exit 2). The server is named `rimz`, so Claude spells a tool `mcp__rimz__<tool>`.

`--always` and `--deferred` repeat and take the same values as `--only`. Each adds `_meta: {"anthropic/alwaysLoad": true, "antigravity/alwaysLoad": true}` (`--always`), or both keys `false` (`--deferred`), to the `tools/list` entry of every tool of that capability. The first key tells Claude to load the tool into the agent's context up front or to leave it behind its tool search; the second tells Antigravity to bind the tool directly or to leave it behind its `call_mcp_tool` tool. A capability given to both refuses with exit 1.

`--launch-env` serves what the launch that started the provider names in two variables of the server's environment, for a provider that starts one fixed server entry for every session of an account (Antigravity, through the rimz plugin, and Pi, through the `rimz.ts` extension). `RIMZ_MCP_SERVE` lists the served capabilities, comma-separated, each with an optional `:always` or `:deferred` that works as `--always` or `--deferred` does (`rimz-lsp:always,rimz-wait`). `RIMZ_MCP_CWD` is the directory the agent launched in: a tool acts there, and a relative `cwd` argument is read from there. An entry that is not a capability, carries any other mark, or names a capability a second time exits 1 with an error naming the entry. With `RIMZ_MCP_SERVE` unset or empty, the server writes `rimz mcp serve: RimZ serves no tools in this session, as expected in an Antigravity session RimZ did not launch or a launch whose profile serves none` to stderr and exits 0. Pi registers no server without `RIMZ_MCP_SERVE`, so it never starts one that serves nothing. `--launch-env` conflicts with `--only`, `--always`, and `--deferred`.

`--parent-env` restarts the server once, at its start, with every variable of the parent process's environment that its own environment lacks; a name both hold keeps the server's value. Its tools then act as the agent, in the home and room, that this environment names, and the server reads the [replacement files](#replace-the-wording) from that home. It reads the parent's environment on Linux and macOS. Where that read or the restart fails, or on another platform, the server writes one line to stderr and runs with its own environment.

## Tools

Each tool call but `guide`'s does the job of one `rimz` command, inside the server, as the agent that started the server, in that agent's home and room, and answers with what the job returns ([calls](#calls)). A capability shares its name with the skill that teaches the same commands (every one but `rimz-blackboard`, which has no skill), a launch that serves the capability withholds that skill from the model, on Antigravity and Pi only under scoped isolation ([configuration](../../guide/configuration.md#rimz-tools-over-mcp)), and its tools' descriptions carry what spans fields for each tool: the `lsp` target forms and result cap, the `wait` triggers, when to use `subagent`, `agent`, or `team` and how their reports and follow-ups work, what a `workflow` start leaves to the user, what a `schedule` booking fires and its misfire rules, which `message` mode fits and how to read and answer a prompt that opens with a `From:` header, when a turn's reply is a question to the user for `ask`, what `tasks`, `join`, and `stop` answer and refuse, and when to book a stop. Material few calls need is a guide the agent loads on demand: the `wait` description points to `rimz-wait/conditions`, the `when` condition grammar, and `rimz-wait/traps`, edge cases for truncated logs, hanging checks, and bounding a `when`, the `subagent` description to `rimz-subagents/delegating`, what to delegate and how to brief and read a subagent, the `agent` and `team` descriptions to `rimz-agents/launching` and `rimz-teams/launching`, what to launch, where it works, and how to brief it, the `workflow` description to `rimz-workflow/steering` and `rimz-workflow/debugging`, the `rimz workflow` commands that steer a run and what each waiting line and failure cause means, the `schedule` description to `rimz-wait/conditions`, which a launch serving `rimz-loop` loads without `rimz-wait`, and to `rimz-loop/targets`, `rimz-loop/signals`, and `rimz-loop/managing`, what differs at a fire from a direct launch, the signal names, and the `rimz loop` commands that list, pause, test-fire, and debug a task, and the `self_molt` description to `rimz-control/fresh-eyes`, how to write the note for a fresh-eyes review. The server's `instructions` open with a short line saying what the served tools are for, which RimZ builds from the served tools and no file replaces; then one line per served capability says when to reach for it, then one line stating what every start returns and naming `tasks`, `join`, and `stop` when those tools are served and one naming `guide` when it is served, then how a call runs. `rimz agents explain <profile> --mcps` prints all of that text as one launch is served it.

`guide` belongs to no capability. The server lists it when it serves a capability that has a guide (`rimz-wait`, `rimz-subagents`, `rimz-agents`, `rimz-teams`, `rimz-workflow`, `rimz-loop`, and `rimz-control`), gives it no load mode of its own, and answers a call itself: the text of the named guide, or, for a name of a guide the launch does not serve, an error result whose `error` is `no guide "<name>"` and whose `hint` is `this launch has: <names>`.

`tasks`, `join`, and `stop` belong to no capability either. The server lists them when it serves `rimz-wait`, `rimz-subagents`, `rimz-agents`, `rimz-teams`, `rimz-workflow`, or `rimz-loop`, the capabilities whose tools start things, gives them no load mode of their own, and they act on what the agent started through RimZ, each named by an id `<kind>:<name>`: `subagent:` or `agent:` and the handle, `team:` and the team instance (`team#lane`), `workflow:` and the `wf_` run id, `schedule:` or `wait:` and the task name. `tasks` lists those ids. `stop` and `join` act on a thing the agent started, or that an agent it started started; any other id is refused. Cancelling a workflow run is the user's call, and the `stop` description says so.

## List the tools

```sh
rimz mcp tools [--only <capability>]... [--json]
```

`rimz mcp tools` prints each tool the server offers with its capability (`-` for `guide`, `tasks`, `join`, and `stop`) and the estimated tokens of its `tools/list` entry (compact JSON, counted with the `o200k_base` tokenizer, so Claude's own count runs somewhat higher), then the total. That entry is what a provider puts in the agent's context for the tool when it loads it up front. `--only` takes the same values as `serve --only` and refuses any other the same way. `--json` prints the server's `tools/list` result for the same `--only`, unchanged. Both read the [replacement files](#replace-the-wording) as the server does, and print a warning on stderr for each one that is not used.

## Replace the wording

Each text the server sends is a Markdown file built into `rimz`, and a file at the same path under `mcps/` in the RimZ home replaces it:

| Path under `~/.rimz/mcps/` | Text |
| --- | --- |
| `instructions.md` | The instructions' last part: how a call runs and what its result holds |
| `guide.md` | The `guide` description |
| `<capability>/instructions.md` | The capability's line in the instructions, below the first line |
| `<capability>/<tool>.md` | The tool's description (`rimz-wait/wait.md`) |
| `<capability>/guides/<guide>.md` | A guide `guide` loads (`rimz-wait/guides/conditions.md`) |

The built-in files are under `crates/rimz/src/mcp/tools/` in the source tree. The server reads the folder once, when it starts, so a running session keeps the text it started with and an agent launched afterwards gets the new file; a provider that restarts the server inside a session (a resume, a server it respawns) reads the folder again. An argument's description is part of the tool's schema and has no file. Per-field rules and defaults live in those argument descriptions rather than the tool's `.md` file, so a replacement file written before a rule moved into the schema can repeat what the schema already says.

A replacement never switches a tool off. RimZ serves the built-in text in its place, and warns with the file's path and the reason, when the file cannot be read, is not UTF-8, is empty, or breaks a limit a provider keeps:

- a tool's description and its arguments' descriptions over 4,096 characters;
- a capability's sentence on more than one line;
- the instructions with every capability over 4,096 characters: a replaced `instructions.md` falls back.

The limits are checked with every capability, so a file passes or fails the same way in every launch. A `.md` file at any other path is ignored with a warning, which names the path it belongs at when exactly one built-in file has its name (`rimz-lsp/wait.md` belongs at `rimz-wait/wait.md`); a file cannot add a tool or a guide. Files that do not end in `.md` are not read.

A launch that hands the server over carries the warnings of the capabilities it serves, of the shared files, and of every misplaced file: they print in the agent's pane before the provider starts, stay on the agent's record for `rimz agents show`, and print on stderr under `rimz agents explain`. `rimz mcp tools` prints every warning on stderr, and `rimz agents explain <profile> --mcps` ends the line of each tool, and the instructions' heading, with `text <path>` for each part whose text is a replacement.

## Calls

- Each call but `guide`'s runs inside the server, on a thread of its own, through the library function its command calls. No `rimz` process starts for a call, except the watcher a `wait` detaches, as `rimz wait` does, the language-server broker (`rimz lsp serve`) an `lsp` call starts again when the checkout's has died, as `rimz lsp` does, the pane a `subagent` opens for its child, as `rimz subagents` does, the tab an `agent` or `team` call opens for its seats, as `rimz agents --bg --new-tab` and `rimz teams launch` do, the detached advance a `workflow` call spawns for the run it starts, as `rimz workflow run` does, the pane a `message` to the caller's ended subagent resumes it in, as `rimz message` does, and what a `stop` of a workflow run starts as `rimz workflow cancel` does: the loop runs subscribed to the run's signals, the advance of the run whose `runs` step started it, and the next waiting fire of the schedule that fired it. Every direct call's argument reaches that function as a value, so no string an agent passes is read as a flag; `schedule` stores its fire's launch tail as argv on the task row, refusing NUL and values a fire would read as a flag or verb and writing option values in `--flag=value` form.
- `cwd`, on `lsp`, `wait`, `subagent`, `agent`, and `schedule` (`arguments.cwd` when `tool` is `agent`), names the directory the call acts on, relative to the directory the agent launched in unless it is absolute; without it the call acts on that directory: the server's own directory, or `RIMZ_MCP_CWD` on Antigravity, whose server runs in the plugin directory, and on Pi. A `subagent` call always acts in the room of that directory: its `cwd` names the child's working directory, and without it the child starts where `rimz subagents` without `--cwd` does: the caller's own checkout, or the profile's empty directory. An `agent` call acts in that room the same way, and its agent without `cwd` starts where `rimz agents` without `--cwd` does. An `agent` booking on `schedule` resolves `arguments.cwd` at booking time (translating a scoped caller's `/tmp` to its host temp unit) and stores it absolute on the task row so each fire runs in that directory. An `agent` or `team` `worktree` is created in the repository of the caller's own checkout, as `rimz agents` run from the caller's pane does, and a checkout in another repository than the room's is refused. A `cwd` that is not a directory returns an error result. `blackboard_flip` and `blackboard_record` take no `cwd`: they write the board of the caller's own live cohort, which the caller's recorded launch names.
- `lsp` answers the text `rimz lsp` prints, `blackboard_record` the line `recorded <Section> @<role>`, and `guide` the guide's text. Every other tool answers a JSON object in the shape of its `outputSchema`, as the result's `structuredContent` and, the same JSON, as its one text item: `wait` `{id, status, stop, report}` (`id` is `wait:<name>`, `status` is `running`, `stop` is the `stop` call that cancels it, and `report` says how its result arrives); `subagent` the same four fields, with `id` `subagent:<petname>` and a `report` naming the `SUBAGENT_REPORT` message, plus `warnings`, a list of the notices `rimz subagents` would print for the launch, left out when there are none; `agent` and `team` the same five fields, with `id` `agent:<handle>` or `team:<team>#<worktree>` and a `report` naming the `AGENT_REPORT` or `TEAM_REPORT` message, or saying that none comes and `join` on the id is the way to the answer (a seat of a team that `agent` launches says so, with the team id `tasks` lists it under), and `warnings` holding the notices `rimz agents` or `rimz teams` would print; `workflow` the same four fields, with `id` `workflow:<run>`, plus `warnings`, the definition's validation warnings, left out when there are none; `schedule` the same four fields, with `id` `schedule:<name>` and a `report` saying no message arrives when it fires, plus `warnings`, left out when there are none: a workflow definition's validation warnings, the note that an idle agent holds later fires of a repeating booking with no `overlap`, and the note that a booking with no place (`worktree`, `from_pr`, or `cwd`) runs at the project root when the caller's checkout is another; `message` `{messages}`, a row per message with `to`, `message_id`, `status` (`sent` when it was typed into the receiver's pane, `queued` when it waits, `not_sent` when a `steer` or `interrupt` found the receiver waiting on input), and `detail`, why it waits or was not sent, when RimZ knows, plus `compacted`, the agents compacted before the send, and `warnings`, an `interrupt` the receiver did not confirm and the notices of a resume, each left out when empty; `ask` `{id, status}`, the armed ask's id and `status` `armed`, which a clean end of the turn opens; `tasks` `{tasks}`, a row per thing with `id`, `kind`, `status` (`running`, `done`, or `disabled`), `on_your_stop` (`holds`, `closes`, or `outlives`), and when known `age`, `about`, and `detail`; `join` `{id, status}` with `status` `done` and the `result` and any `detail` (for a workflow run, `result` is its notes path, absent when it has none, and `detail` its end state and checkout), `running` at its timeout or with a `report` for a schedule or a wait (a wait's outcome comes as a message, and a schedule's fires send none), `disabled` for a schedule switched off, or `ended` with a `hint` for a wait, schedule, or team RimZ holds no record of; `stop` `{id, status}` with `status` `stopped`, plus `still_running`, a list that may be empty, of the ids a stopped schedule or workflow run leaves running, or `ended` for a thing that had ended, with a `hint` when RimZ holds no record of it; `self_stop` `{booking}` (`withdrawn`, `none_pending`, or `booked` with `after_secs`, `replaces_after_secs`, and `started`, which holds the rows the command's receipt prints under `holding`, `closing`, and `outliving`: what holds the stop, what closes with the agent, and what outlives it, or `unread` with why they could not be read); `self_compact` `{message_id, status, continues}` (`status` is `sent`, `queued`, or `joined` when the call joined the compaction already queued for the agent, which `message_id` names); `self_tune` `{agent, settings}`, with `keep_warm_while` when one is set and `budget` when no setting is named; `self_molt` `{agent, successor_kind, closes_after_secs, notices}` (the agent's handle, the kind its new session runs, the rest this session takes after its turn ends before its pane closes, and the notices the command would print); `notes` `{path, dropped_meta, unresolved_project}`; `blackboard_flip` `{stage, owner}` (`owner` is `you` for a stage the caller owns, the owner's handle for another's, and left out at `Done`).
- A call that cannot do its job returns an error result whose text is a JSON object `{"error": ..., "hint": ...}`, with `hint` only where RimZ knows the fix, and which carries the same object as `structuredContent`: arguments that do not fit, no room at the call's directory, a refusal of the job (an id that is not `<kind>:<name>`, a thing another agent started, a duration that does not parse, a `wait` `label` that is not one line of 1 to 60 characters, a `when` condition that cannot be read in the checkout, a `subagent`, `agent`, or `team` launch the launcher refuses, such as one from a subagent, of a profile the caller may not launch, or over budget, an `agent` spec that is a team or more than one seat, a `team` that is not a configured team, a repeating `schedule` of a team seat with `from_pr`, a bad `name`, a closed worktree, a worktree in another repository than the room's, or a cohort already live in the worktree, a `message` `to` that matches no agent, whose `hint` lists the live agents, or several without `all`, a `blackboard_flip` or `blackboard_record` from a caller with no recorded launch or on no live team, whose `hint` names the shell command, and a `reply_wanted` from a caller RimZ cannot identify as an agent), or an `lsp` call on one target that fails. A failed `subagent`, `agent`, or `team` launch adds `warnings`, the notices collected before the failure, left out when there are none. A verdict is an answer, not a failure: an `lsp check` that flags anchors, `no results`, and a failed target among several `lsp` targets come back as text. `show` is stricter on one target: any outcome that shows no code is an error result, an unknown or ambiguous name included, which `def` answers as text; the candidates are in `error`.
- The server checks the shape of the arguments (their types, required fields, and enum values), so a `wait` without its `trigger` or its `value` never runs. It also refuses what `rimz` would refuse in the command's flags: a `self_tune` `value` without a `setting`, a `self_molt` with a blank `prompt`, a `notes` with both `body` and `file`, a `notes` `meta` key containing `=`, a `subagent` or `agent` with a blank `profile` or `prompt`, an `agent` with more than one of `worktree`, `from_pr`, and `cwd`, or `fresh` without `worktree`, a `team` with a blank `team` or `prompt` or without exactly one of `worktree` and `from_pr`, a blank `worktree` or `from_pr`, a `schedule` with `match` off `signal` or an empty `match` key, `for` off `when`, `repeat` off `signal` or `when`, `overlap` on a one-shot trigger, `arguments.worktree`, anything the carried tool's parser refuses, `workflow` `input` or `detach`, `from_pr` on a repeating `team`, `#lane` on a team name, NUL in any string reaching the task row, or a value a fire's launch reads as a flag or a `rimz agents` verb, a `message` with a blank `to` or `text`, a `blackboard_flip` with a blank `stage` or `note`, a `blackboard_record` with a blank `text`, and an `lsp` call with no `targets`, `hints` without `fix`, `limit` with `all`, a `limit` of 0, or a field the verb's command has no flag for (`all`, `limit`, and `external` off `refs`, `callers`, `callees`, `impl`, and `find`; `no_tests` off `refs` and `callers`; `full` off `show`; `fix` and `hints` off `check`). Such arguments return an error result whose `error` starts `invalid arguments:`, and nothing runs.
- Calls run at the same time, so a later call can answer first. A cancelled call gets no reply, and its work runs to its end, except a `join`, which stops waiting within half a second. A `join` that finds a message queued for the agent answers `running` with a hint to read it. A call that panics returns an error result, and the server goes on answering.
- The server adds no timeout and no output cap beyond `join`'s own.

## Protocol

The server speaks newline-delimited JSON-RPC 2.0 on stdin and stdout, and writes its logs to stderr. Anything else written to its stdout, by a tool's path, lands on stderr, so the protocol carries only its own lines.

| Method | Reply |
| --- | --- |
| `initialize` | The tools capability with `listChanged`, `serverInfo` named `rimz`, `instructions` whose first line says what the served tools are for, then a line per served capability saying when to reach for it, then a line for `tasks`/`join`/`stop` when served and one for `guide` when served, then how a call runs and what its result holds, and the client's protocol version when it is `2025-06-18` or `2025-11-25`, else `2025-11-25` |
| `ping` | `{}` |
| `tools/list` | The served tools, each with its JSON Schema, an `outputSchema` on each tool that answers data, and `_meta` on the tools of a capability `--always` or `--deferred` names |
| `tools/call` | The call's result, which for `guide` the server writes itself; an unknown or unserved tool is error `-32602` |
| `notifications/cancelled` | No reply; the named call gets no reply, and its work runs to its end, except a `join`'s, which stops waiting |
| Any other request, `server/discover` included | Error `-32601` |

A line that is not JSON gets error `-32700`, and the server goes on reading. The server exits 0 when stdin ends or on SIGINT or SIGTERM, and a call still running ends with it. A watcher that a `wait` call detached keeps running.

A server started with a room pin (`RIMZ_WORKSPACE_ID` and `RIMZ_PROJECT_ROOT`, which every room pane exports) follows `rimz update`: once the room records another build, the server replaces itself with that build at its first moment with no call in flight, keeping its process and its pipes, and the new build first sends `notifications/tools/list_changed`, so the client reads the tool list again. Codex rereads it only with its `mcp_tool_list_changed` feature on. A server with no room pin stays on the build it started with.

## Launch registration

RimZ hands its server to a Claude, Codex, Antigravity, OpenCode, or Pi launch when `[agents] rimz-mcp-server` is on (the default, set in the [machine config](../../guide/configuration.md#rimz-tools-over-mcp)) and the profile's `capabilities:` grant names a capability with MCP tools or, for a profile with no grant, its `mcps` list is absent or holds `*`, `rimz`, or at least one capability. On Claude, Codex, and OpenCode the server's command is the room's `rimz` link, so it survives `rimz update`, and a running server in a room follows the update ([protocol](#protocol)). Every spawn path does the same, and `rimz agents explain <profile> --mcps` prints the servers, tools, load modes, and arguments one launch gets, then the instructions and each tool's description and schema as the server sends them ([explain a launch](./agents.md#explain-a-launch)).

- **Claude** gets one `--mcp-config` holding the `rimz` server, after every other provider argument and before the `--` that precedes a prompt, since the flag takes several values. A launch whose profile `tools` list renders `--tools` gains `ToolSearch` in that list once, code mode on or off: without it Claude turns tool search off and loads every MCP tool up front, whatever load mode a mark sets. A rendered list holding Claude's `default` preset passes as written, since the preset holds `ToolSearch` ([tools to provider arguments](../definitions.md#tools-to-provider-arguments)). A `--tools` written in the profile's raw `args` passes as written. With [`allow-routine-rimz`](../../guide/configuration.md#routine-rimz-commands) on, `mcp__rimz__*` joins `permissions.allow` in the launch's `--settings`, so the tools run without asking; with it off, Claude asks before each call.
- **Codex** gets `-c mcp_servers.rimz.*` overrides: the command and its arguments, `--parent-env` among them, `env_vars` naming every variable RimZ spawns Codex with (Codex clears a server's environment to a few names otherwise), `tool_timeout_sec=600`, and `default_tools_approval_mode` set to `"approve"` with `allow-routine-rimz` on and `"prompt"` with it off. The `env_vars` names are collected before the user's login shell runs its startup files, so on Linux and macOS `--parent-env` takes what those files export from Codex's own environment; elsewhere the server has the `env_vars` set alone.

- **Antigravity** starts the server itself, from the `tools` entry of the rimz plugin's `mcp_config.json` that `rimz hooks install antigravity` writes, which agy shows as `rimz_tools` (it names a plugin's server `<plugin directory>_<server>`): `rimz mcp serve --launch-env`, never in argv or the agent file. Every launch that hands the server over, a resume included, sets `RIMZ_MCP_SERVE` to the served capabilities with their marks and `RIMZ_MCP_CWD` to the launch directory in agy's environment, and every other launch of any kind removes both, so a session RimZ did not launch serves nothing. agy binds the tools from a conversation's first turn, so a scoped Antigravity launch withholds the `rimz-*` skill of each capability it serves, as Claude and Codex do; a host launch keeps the skills callable, since agy has no per-launch skill switch on the host. With `allow-routine-rimz` on, every launch that serves RimZ's tools merges `mcp(rimz_tools/*)` into `permissions.allow` of its one `--settings` document, so the tools run without asking, and a definition's [`allowed-tools`](../definitions.md#tools-to-provider-arguments) entry `mcp__rimz` or one of its tools also reaches agy as an `mcp(rimz_tools/...)` rule; with the switch off, RimZ omits `mcp(rimz_tools/*)` and agy asks before each call. Install saves no permission rule in `~/.gemini/antigravity-cli/settings.json` and strips any leftover `mcp(rimz_tools/*)` rule written by an older install. An account whose plugin lacks the current `mcp_config.json` reads as missing its hooks, so its launches refuse until `rimz hooks install antigravity` runs again.
- **OpenCode** gets the server through the launch's inline config, `OPENCODE_CONFIG_CONTENT`, which RimZ composes over the value the launch inherits: `mcp.servers.rimz` is a `local` server whose `command` holds the room's `rimz` link, `mcp serve`, and the server's `--only` arguments. With `allow-routine-rimz` on, one `{"action":"rimz_<tool>","resource":"*","effect":"allow"}` per served tool joins the config's `permissions`, so the tools run without asking, while a server of the user's named `rimz_docs` or `rimz.dev` gets no grant; with it off, OpenCode's own permission rules decide. An OpenCode launch inside an OpenCode agent first removes the `rimz` server, policies, and permissions its parent's launch wrote, unless the launch's own environment sets `OPENCODE_CONFIG_CONTENT`. OpenCode cannot mark a skill user-only, so a launch keeps each served capability's `rimz-*` skill callable beside its tools, on the host and in scoped mode.
- **Pi** gets the server from the installed `rimz.ts` extension that `rimz hooks install pi` writes, never in argv: when `RIMZ_MCP_SERVE` and `RIMZ_PI_MCP_EXPOSURE` are set, the extension registers a `rimz` server running `rimz mcp serve --launch-env` (`$RIMZ_BIN` when set) with Pi's `registerMcpServer` and a 600-second call timeout, past `join`'s longest wait (Pi's own default is 60 seconds), so Pi spells a tool `mcp__rimz__<tool>` and lists the server in `/mcp`. Serving needs Pi 1.0.4 or later: on an older Pi the extension registers no server and shows a notice in the session naming the Pi version and asking to upgrade Pi to 1.0.4 or later. Every launch that hands the server over, a resume included, sets `RIMZ_MCP_SERVE`, `RIMZ_MCP_CWD`, and the Pi-only `RIMZ_PI_MCP_EXPOSURE` (the load modes, below); every other Pi launch removes all three, and the extension removes them from its own process as it loads, so a Pi tool or a child Pi inherits none. A registration Pi refuses (a server of the user's own named `rimz`) loses only the server, and the extension's other hooks keep running. On a launch whose [code mode](../agent-support.md#code-mode) is `on`, served or not, `RIMZ_PI_CODEMODE_ONLY=1` has the extension register Pi's codemode tool in its `only` mode in place of Pi's built-in one, and Pi's startup lists that replacement under its extension issues. A launch whose profile renders a `--tools` list gains `mcp__*`, `list_mcp_resources`, `list_mcp_resource_templates`, and `read_mcp_resource` in it, so the list limits only Pi's own tools, plus `codemode` when a served tool loads through codemode and code mode is not `off`, and `tool_search` when one is deferred; a list that maps to no Pi tool renders these alone in place of `--no-tools`, which would also switch MCP off. A scoped launch withholds the `rimz-*` skill of each capability it serves; a host launch keeps the skills callable, since Pi has no per-launch skill switch. Pi asks before no tool call. An installed `rimz.ts` that differs from the one this `rimz` ships may not register the server, so the launch warns with `rimz hooks install pi` as the fix, serves nothing, and reaches RimZ through its skills. `--no-mcp`, `--no-extensions`, or `-ne` in a profile's arguments switches the server off, and the launch keeps its skills: `--no-extensions` loads no `rimz.ts` and none of Pi's MCP.

### The `mcps` profile key

For a profile that writes `capabilities:`, the grant chooses RimZ's capabilities ([capabilities to tools](../definitions.md#capabilities-to-tools)) and `mcps` only the user's own servers, absent keeping every one. For any other profile, its [`mcps`](../definitions.md) list chooses both RimZ's capabilities and the user's own MCP servers:

| `mcps` | RimZ's server | The user's servers |
| --- | --- | --- |
| Absent | Every capability | As without RimZ |
| A list holding `*` | Every capability | As without RimZ |
| Any other list | Every capability when it names `rimz`, else only the named capabilities, as `--only` arguments; none when it names neither | Only the named servers, within each provider's reach below |
| `[]` | Not handed over | None, within each provider's reach below |

A subagent child and a workflow judge are never served `rimz-subagents`, `rimz-agents`, `rimz-teams`, or `rimz-loop`, whatever the list says, and a subagent child is also never served `rimz-ask` since its question goes in its result for its launcher: every capability is the other seven on a child and the other eight on a judge, and a list that names only denied capabilities hands such a launch no RimZ server. A launch whose profile sets `subagents: []` is never served `rimz-subagents` and keeps the other eleven, since that list limits its children only. A team seat other than its leader (the declared `leader`, else the first role) is never served `rimz-ask`, since only the leader asks the user. A child or a judge keeps the `rimz-loop` skill its skill policy allows, which runs `rimz loop add` only with a permission prompt.

A list's entries are `*` (every server), `rimz` (every capability), the capability names (`rimz-lsp`, `rimz-wait`, `rimz-subagents`, `rimz-agents`, `rimz-teams`, `rimz-workflow`, `rimz-loop`, `rimz-message`, `rimz-ask`, `rimz-control`, `rimz-notes`, `rimz-blackboard`), and the names of the user's servers. Every entry but `*` takes an optional mark, `:always` or `:deferred`, written without a space (`rimz-lsp:always`); a Markdown definition quotes `'*'`, since YAML reads a bare `*` as an alias. A name that matches no configured server is ignored, since accounts and projects define different servers. An empty entry, a mark on `*`, any other mark, any other name starting `rimz-`, and one name listed with two different marks refuse the definition at load. The same entry listed twice refuses in TOML and counts once in a Markdown definition. RimZ never switches a server on: a listed server the user's config disables stays off.

A mark sets how the provider loads a server's tools: `always` puts them in the agent's context up front, `deferred` leaves them behind the provider's tool search until the agent looks for them. A mark the launch cannot apply does not warn: the launch proceeds without it, and `rimz agents explain <profile> --mcps` says beside the load it concerns that the mark is not applied and why ([explain a launch](./agents.md#explain-a-launch)). A launch that carries a team's consensus layer loads `rimz-blackboard`, where it serves it, as if its entry were marked `always`, unless an entry naming `rimz-blackboard` carries its own mark; Codex, which sets a load mode per server, loads it as the `rimz` server does. On Antigravity, a mark on a capability or on `rimz` reaches the server through `RIMZ_MCP_SERVE` on every launch that hands it over.

- **Claude**: a list without `*` sets `allowedMcpServers` in the launch's `--settings` to exactly `rimz`, when the server is handed over, plus each of the user's servers it names. Claude applies it to servers from every source (`--mcp-config`, a project's `.mcp.json`, claude.ai connectors) and prints `Warning: MCP server blocked by enterprise policy: <name>` for each one it blocks. A profile's `tools` list limits no MCP server. A mark on `rimz` sets the server entry's `alwaysLoad`: `true` for `rimz:always`, and `false` for `rimz:deferred` unless a capability is marked `always` or loads `always` beside a consensus layer. A mark on a capability becomes `--always <capability>` or `--deferred <capability>` in the server's arguments. A mark on one of the user's servers is not applied: Claude reads that server's load mode from the user's own config. With [code mode](../agent-support.md#code-mode) on, no mark of RimZ's applies either: Claude offers the model only `REPL` and `Poll` and no MCP tool up front, though the argv still carries the marks. `rimz agents explain --mcps` follows the profile's `code-mode`, so a code mode your environment turns on under `auto` still shows the marks applied.
- **Codex** has no allowlist. A list without `*` sets `enabled = false` for each server defined under `mcp_servers` in the account's `config.toml` or the profile file that `--profile`, `-p`, or `-p<name>` selects that the list does not name. Servers from Codex plugins, connectors, trusted project config, managed config, `-c` arguments, and Codex's built-ins stay on. A config file that cannot be read or parsed switches nothing off, and the launch warns. A mark on `rimz` sets `mcp_servers.rimz.omit_tools_from`: `["deferred"]` for `always`, which declares the tools to the model directly (under Code Mode Only, as eager tools nested inside `exec`), and `[]` for `deferred`, which leaves them to Codex's default (behind tool search on a model that has it). A mark on one of the user's servers passes the same value as `-c mcp_servers.<name>.omit_tools_from=...` when the account's `config.toml` or the selected profile file defines that server and its name holds neither `.` nor `=`, and is not applied otherwise. A mark on a capability is not applied: Codex sets a load mode per server, so the capability loads as the `rimz` server does. Under Codex's strict Code Mode Only (`features.code_mode_only` with `code_mode_only_strict_3p_tools`), Codex ignores `omit_tools_from`, so marks do nothing, and `rimz agents explain --mcps` still reports a server's mark applied, since a launcher cannot tell that strict mode is in effect.
- **Antigravity** applies the list to the user's servers only through its agent file: `inheritMcp: false` and a name-only `mcpServers` item for each of the user's servers the list names. agy refuses a call to a tool of a server the agent does not list, though that server's process still starts. A list that limits nothing (absent, or holding `*`) writes no MCP key, so the account's servers load as configured. A fresh launch with no prompt sources writes no file, so a limiting list refuses there before any pane opens (a layout launch, a molt, or a restart whose conversation cannot resume), naming the fix: write the home kind base `agents/antigravity.md` or pass another prompt source, or remove `mcps`. A definition on Antigravity always has a prompt source, since the [built-in kind base](../definitions.md#kind-bases) sends its body there, so the refusal reaches a bare launch. A resume keeps the user's servers its conversation started with. RimZ's capabilities and their marks reach the server through `RIMZ_MCP_SERVE`, and a mark on `rimz` applies to every served capability that has no mark of its own. A mark on one of the user's servers is not applied and keeps its name-only item, since agy takes a load mode only for RimZ's capabilities.
- **OpenCode**: a list without `*` puts at the head of the inline config's `policies` an `integration.use` deny on `mcp:*`, then an allow on `mcp:rimz` when the server is handed over, then an allow on `mcp:<name>` for each of the user's servers it names, so from OpenCode 2.0.29 it connects only those; an older release keeps every server. A policy of the user's own in the inherited inline config's top-level `policies` follows RimZ's and still decides, so a server it denies stays off even when the list names it. One under its `experimental.policies` comes before RimZ's and does not decide. A mark sets how OpenCode's code mode loads RimZ's tools. With code mode off, or for `rimz:always` under `auto`, the `rimz` server entry carries `codemode: false`, so its tools load as native tools. Otherwise the RimZ plugin sets each tool's load from `RIMZ_LAUNCH_MCP_TOOLS`: `always` under `auto` loads the tool native, `always` with code mode on pins it in `execute`'s listing, and any other tool stays behind `execute`. A capability's own mark wins over the mark on `rimz`. With code mode off, a `deferred` mark is not applied, since every RimZ tool is native and OpenCode has no tool search outside `execute`. A mark on one of the user's servers is not applied, since OpenCode takes a load mode only for RimZ's server and its capabilities.
- **Pi** cannot limit its own servers per launch: a list without `*` chooses RimZ's capabilities and warns at launch that Pi loads every server it configures. A mark becomes the Pi exposure of a RimZ tool, carried in `RIMZ_PI_MCP_EXPOSURE`: `always` is `direct`, declared to the model (under code mode `on`, reached inside `codemode` instead, inlined within Pi's `codemode.inlineBudget`), and `deferred` is `deferred`, behind `tool_search`. A mark on a capability wins over one on `rimz`. A tool with no mark keeps Pi's default `codemode`, callable from the `codemode` tool, except under code mode `off`, where it is `deferred`. A mark on one of the user's servers is not applied, since Pi takes a load mode only for RimZ's server and its capabilities.
- **Other kinds** get no server. A list warns at launch that it is not applied, unless it holds only `*`, and the launch proceeds.

### Cases RimZ does not handle

In each case, `[agents] rimz-mcp-server = false` keeps RimZ's server out of every launch (agy still starts the plugin's `rimz_tools`, which serves nothing, and a resumed Antigravity conversation whose agent file named an inline `rimz` server still starts that one); a profile's `mcps` list still filters the user's servers, except on Pi, which loads every server it configures.

- A user's own server already named `rimz`.
- A user's own server whose name holds a `:`: an entry naming it reads the text after the last colon as a mark, and refuses the entry unless that text is `always` or `deferred`.
- A `--strict-mcp-config` in a profile's or launch's arguments: RimZ passes it to Claude, which then ignores the account's and project's servers whatever the `mcps` list names.
- A user's own Codex `-c mcp_servers={...}` table in a profile's or launch's arguments: it replaces the table RimZ places first, so the switch-offs a `mcps` list adds are lost. The `rimz` server stays: its dotted keys follow every user argument, and Codex merges dotted keys given after a table.
- A user's Codex `shell_environment_policy`: it filters what Codex's shell commands see, not what the server sees, so a `wait` command armed through the tool can read a variable the policy withholds from the shell.
- Variables Codex sets for itself after it starts, such as those in the `.env` file of its home: the server gets one only when the `env_vars` list names it, since `--parent-env` reads the environment Codex was started with.
- Claude run with `CLAUDE_CODE_MCP_ALLOWLIST_ENV=1`, which keeps the room pin out of the server's environment.
- Claude under a managed MCP policy.
- A user's own Claude settings file that sets `allowedMcpServers`: how Claude combines it with the launch's list is untested.
- Two Antigravity sessions of one account at once: agy writes each server's tool schemas to one folder per server name under `~/.gemini/antigravity-cli/mcp/`, so two sessions serving different capabilities share the `rimz_tools` folder.
- An Antigravity session RimZ did not launch: the rimz plugin still starts `rimz_tools`, which serves nothing and shows in agy's `/mcp` as a red `✗ rimz_tools` row with the server's stderr line as its error.
- A Codex launch forced to a never-ask approval policy with a sandbox while `allow-routine-rimz` is off: Codex refuses every tool call that needs approval, so every call is refused.
