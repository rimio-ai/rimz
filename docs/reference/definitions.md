# Markdown definitions

RimZ reads machine agent, subagent, and team definitions directly from Markdown with YAML frontmatter. Edit the source, then run `rimz agents validate`; there is no generation step. Machine preferences and command shortcuts remain in `config.toml`. Trusted project `.rimz/config.toml` keeps its TOML schema and trust rules.

## Trees and format

The definitions root is the RimZ home, `~/.rimz` by default, which `RIMZ_HOME` relocates; `RIMZ_AGENTS_HOME` overrides it for these trees, the skill library, and installed packs:

```text
agents/<name>.md       direct profiles and kind bases
subagents/<name>.md    supervised-child profiles
teams/<name>.md        team roster and pipeline
traits/<name>.md       plain Markdown fragments
skills/<name>/SKILL.md shared skill library
workflows/<name>/     workflows run by name
packs/                installed pack sources and record
```

The four definition trees (`agents/`, `subagents/`, `teams/`, `traits/`) are scanned non-recursively for `.md` files, in sorted order, in the home and in each installed pack. Subdirectories and `AGENTS.md`, `CLAUDE.md`, and `README.md` are skipped. These contributor-note names are valid only in the home's `traits/`; pack copies remain documentation. Trait contents are read when referenced. A missing tree is empty. Symlinked trees work too. A dangling home `.md` symlink still claims its name and reports its own read error instead of loading a pack fallback.

The first line must be exactly `---`; another exact `---` line closes a YAML mapping. Unknown keys and wrong value types fail. The remaining Markdown is the prompt body, trimmed at its edges. String-list keys accept YAML lists; an explicit null list means `[]`, not inheritance. Signals have their own rules below.

For example, `agents/planner.md`:

```markdown
---
description: Plan changes without editing files
agent: claude
model: fable
tools: [Bash, Read, Grep, Glob, AskUserQuestion]
subagents: []
---
Read the surrounding code and propose a bounded plan before implementation.
```

Because this example has a body, it also needs `agents/claude.md`:

```markdown
---
description: Shared Claude instructions
---
Follow the project's instructions and report what you verified.
```

## Definition tiers

[Installed packs](./cli/packs.md) supply the same trees below your own home files. Names resolve after the tiers merge, not relative to the pack that supplies a definition or team.

- A home file claims its name even when it fails to load. It hides every pack item of that name in its claim namespace; a broken home override never falls back to a pack copy. A dangling home-library skill symlink also claims its name: pack copies stay overridden, and listing the unavailable skill fails at the home path. An unlisted dangling library link does not itself fail validation or a launch.
- Without a home claim, one non-excluded pack item loads. Two pack items claiming the same name conflict: neither loads by bare name, and the error names both packs, both files, and the fixes. Exclude one with `rimz packs exclude <pack>:<name> --type <type>`, or supply your own home file of that name. Install order never breaks a tie.
- Agents, subagents, and teams share one launch-name claim across tiers. A home definition hides a same-named pack item in any of those trees, and a configured command hides a same-named pack team. A pack profile and pack team of one name conflict, even within one pack. Traits and kind bases (keyed by kind) have separate claims. Duplicate names within a tier's agent/subagent trees still fail together. A pack team named like a kind, `term`, a virtual agent cell, or a profile's `-fast` form fails as that pack's problem, with an exclusion fix. A failed pack item named like a kind blocks that kind only when it is a kind base.
- Excluded items claim nothing. Excluding an item or a whole type does not remove references to it; dependents can fail until another tier supplies the name or the reference is removed.

Bare parents, kind bases, traits, child allowlists, and team seats all use the merged names. A pack team's `coder` seat therefore binds your home `coder` when present, and the pack's otherwise. A pack team named `peer` replaces the built-in team of that name. Skills follow their own [provider, library, then pack order](../guide/configuration.md#skills).

## Agent and subagent keys

Boolean keys accept `true` and `false` and the YAML 1.1 spellings `on`/`off`, `yes`/`no`, and `y`/`n`, unquoted and in any letter case; any other value is a load error. Repository TOML profiles take only `true` and `false`. `fast` and `code-mode` also take `auto`, which TOML writes as the string `"auto"` beside `"on"` and `"off"`, and which stops an inherited or kind-base value and renders nothing.

| Key | Meaning |
| --- | --- |
| `name` | Optional public name; defaults to the filename stem. |
| `description` | Required nonempty, single-line listing description; not inherited. |
| `agent` | Registered runtime (kind or variant such as `opencode-mini`), a bare definition name, or `<pack>:<name>` in the same namespace. Native Claude/Codex kinds are family preferences for tiers; Pi/OpenCode keep their engine. May be omitted with `tier` or when `model` identifies a kind. |
| `model` | Concrete model alias or provider model ID. OpenCode [picks a full name, first matching ID, or nearest name](../internals/agents/adapter_opencode.md#model-selection) before launch. Tier names are refused; use `tier:` instead. |
| `tier` | [Model tier](../guide/configuration.md#model-tiers): `intern`, `junior`, `senior`, or `principal`. Mutually exclusive with `model`. |
| `mode` | `ask`, `auto`, `plan`, or `yolo`. |
| `isolation` | `host`, `scoped`, or `sandbox`; overrides machine policy unless `--isolation` is recorded. Inherited through definitions, unavailable on team roles or repository profiles. |
| `empty-dir` | Boolean opting a solo agent or subagent into its own empty working directory. Inherited through `agent:` chains; `false` clears it. Also accepted in repository TOML `[profiles]` and `[subagents.profiles]`; machine profiles remain Markdown definitions. Team roles refuse it, including through a selected definition or profile, because teams share the worktree. |
| `effort` | Provider-specific absolute effort (YAML integer or string), or omit for the selected model's default. OpenCode checks the chosen model's live variants; without a model it warns and launches without effort. Relative `+N` / `-N` values are refused. |
| `fast` | On, off, or `auto` for the provider's [fast mode](./agent-support.md#fast-mode). On renders the fast switch and off the provider's off switch where it has one; `auto` renders nothing. Absent takes the kind base's value, else renders nothing. On a kind with no fast switch, on warns at launch and runs without it. |
| `code-mode` | On, off, or `auto` for the provider's [code mode](./agent-support.md#code-mode). Supported on Claude and Pi, where on adds tool names or a flag to the rendered tools, on Codex, where on adds a `-c` setting, and on OpenCode, where on sets a member of the composed config; off renders the provider's off switch. `auto` renders nothing, and absent takes the kind base's value, else renders nothing. On other kinds, on warns at launch and runs without it. Also accepted in repository TOML `[profiles]` and `[subagents.profiles]`; team roles have no override. |
| `auto-compact` | Auto-compaction ceiling (provider-native or RimZ-enforced): integer or string token count from `100k` through `1M`, inclusive; no percentages or decimals. |
| `smart-compact` | RimZ [smart compaction](#smart-compaction) threshold: a token count such as `200k`, a percentage such as `70%`, or `off`. Accepted on agents and subagents. |
| `budget` | Dollar cap as a string or number, with an optional leading `$`. A bare amount such as `20` caps the session, and `20/day` caps each day. Any other value refuses the definition at load. |
| `timeout` | Subagent definitions only: the child's run deadline, one whole number and a unit (`s`, `m`, `h`, or `d`) such as `90m`, the grammar of `--timeout` and `[agents.subagents] timeout`. A launch's `--timeout` (or a fanout task's or flag's) wins over it, and it wins over `[agents.subagents] timeout`; warning offsets and grace never read it. Refused on an agent definition; team roles refuse it as an unknown key. Markdown only, not a repository TOML key. |
| `keep-warm` | Prompt-cache [keep-warm](#keep-warm) maximum for a solo seat: `off`, a duration such as `2h`, or a block with `max` only. |
| `idle-compact` | [Idle compaction](#idle-compaction) token floor: `off` or a positive token count such as `100k`. Refused on a subagent definition. |
| `model-reminder` | Boolean controlling the model identity in the launch reminder for solo agents and subagents. Defaults on; team members never show model names. |
| `traits` | Trait names substituted into this definition's body. |
| `capabilities` | What the agent may do, for every kind: the words `bash`, `read`, `write`, `ask`, and `web`, the RimZ capabilities with MCP tools (`rimz-lsp`, `rimz-wait`, `rimz-subagents`, `rimz-agents`, `rimz-teams`, `rimz-workflow`, `rimz-loop`, `rimz-message`, `rimz-control`, `rimz-notes`, `rimz-blackboard`), and `rimz` for all eleven, each RimZ entry with an optional `:always` or `:deferred` load mark. A capability's own mark wins over `rimz`'s, as in `mcps`. The words [lower](#capabilities-to-tools) to tool names; a granted capability reaches the agent as the tools of RimZ's MCP server where the launch serves them, else as `skill(rimz-x)` (every capability but `rimz-blackboard`, which has no skill), even beside `skills: []`, and a capability left out reaches it neither way. Any other `rimz-*` name is a skill and goes in `skills`. A definition, kind base, or role entry sets `capabilities` or `tools`, never both. Beside it, `skills` governs every skill but the eleven capabilities', and `mcps` holds only your own servers. `[]` grants nothing. |
| `tools` | Tool-name list, translated to provider arguments below. Used where `capabilities` is not. |
| `subagents` | Direct profiles only: allowed RimZ child profiles; `[]` permits none. |
| `skills` | Bare skill-directory names allowed for model invocation. Claude also adds exact invocation permissions for listed names without `*`, in all isolation levels and independently of `allow-routine-rimz`. Scoped views and host Claude keep unlisted skills user-only; host Codex hides them. Other host providers warn and run unrestricted. `[]` lists none. |
| `mcps` | MCP servers for Claude, Codex, Antigravity, OpenCode, and Pi launches: `'*'` (every server), `rimz` (every RimZ capability), RimZ capability names (`rimz-lsp`, `rimz-wait`, `rimz-subagents`, `rimz-agents`, `rimz-teams`, `rimz-workflow`, `rimz-loop`, `rimz-message`, `rimz-control`, `rimz-notes`, `rimz-blackboard`), and names of your own servers, each but `*` with an optional `:always` or `:deferred` load mark (`rimz-lsp:always`). Beside a `capabilities` list, the grant chooses RimZ's capabilities ([capabilities to tools](#capabilities-to-tools)) and `mcps` names only your own servers, absent keeping every one. Otherwise: absent, or a list holding `*`, serves every capability and keeps your servers, except that a subagent child and a workflow judge are never served `rimz-subagents`, `rimz-agents`, `rimz-teams`, or `rimz-loop`, and a launch whose profile sets `subagents: []` is never served `rimz-subagents`; another list keeps exactly the named ones; `[]` hands over no RimZ server and keeps none of your servers, except that Codex keeps its plugin, connector, project, managed, and built-in servers. A mark a provider cannot apply is ignored without a warning, and `rimz agents explain --mcps` says why. Antigravity hands the RimZ capabilities to the rimz plugin's server through the launch's environment and applies the list to your servers only through the agent file of a fresh launch with a system prompt, refusing a limiting list on a fresh launch without one. OpenCode applies the list to your servers through `policies` in the launch's inline config. Pi hands them to the server its `rimz.ts` extension registers, through the launch's environment, and cannot limit your servers: a list without `*` warns at launch and Pi keeps every server it configures. Other kinds warn at launch, unless the list holds only `*`, and keep their servers. See [launch registration](./cli/mcp.md#launch-registration). |
| `allowed-tools` | Permission rules such as `["Bash(git *)", Read]`. Claude pre-approves matching calls in all isolation levels, and Antigravity pre-approves the rules it can [translate](#tools-to-provider-arguments) and warns for each one it cannot, both independently of `allow-routine-rimz`; other kinds warn and do not apply them. Available only in Markdown definitions, not repository TOML. `[]` or null clears inherited rules. |

Names must match `[A-Za-z0-9_-]+` and be unique across both definition trees. Registered kinds and their aliases (`agy`, `mcode`) are reserved for kind bases; registered variant names such as `opencode-mini` cannot name a Markdown definition. `general` and model aliases are not reserved by the definition parser. The final namespace checks also reject command-verb and address collisions, such as `all`, kind ordinals, or a profile colliding with a team.

### Chains and defaults

`agent: opencode-mini` selects OpenCode's mini interface while keeping kind `opencode`. It shares `agents/opencode.md`, needs no `subagents/opencode-mini.md`, and passes through definition chains and team seats. A child explicitly naming `agent: opencode` drops mini. `--agent opencode-mini` adds it to another profile without changing that profile's prompt; `--agent opencode` removes it. Model and tier overrides keep mini. Restart re-reads the current definition, so editing its runtime changes the interface on the same session.

The nearest definition setting `tier:`, `model:`, or a registered `agent:` kind decides the runtime. A `tier:` needs no `agent:`. A concrete `model:` normally runs exactly on its own family, whether listed in the machine [tier table](../guide/configuration.md#model-tiers) or not, with no tier stamp or usage fallback. Definitions on Pi or OpenCode keep their engine even when a concrete model names another family, so `agent: pi` with `model: sonnet` runs Sonnet on Pi. Otherwise, if the model's family cannot build the definition, it fails with the path, build error and fix; a listed model also gets a `tier:` hint for allowing a move. Only a `tier:` routes: on Claude or Codex, an explicit kind on the deciding definition prefers that family's entries first, followed by remaining entries in list order, then higher tiers with the preferred family first, never lower. Families unable to render the definition's tools, skills, supported fields, or kind base are excluded with reasons reported by `rimz agents validate`; passes ahead of the chosen entry are recorded with their full errors. No eligible entry at or above the requested tier is an error. Pi and OpenCode keep their engine under tiers and try models in list order, including names with no native owner; Claude and Codex skip unowned names.

`tier` and `model` inherit as one setting: setting either inherits neither. A child still inherits its parent's absolute effort if present; otherwise the chosen model's default applies. Relative effort is refused even when inherited, with the source named. Project TOML profiles and roles cannot set `tier` or tier-named `model`: define the tiered profile in Markdown or name a concrete model in TOML. Project models run exactly, even when listed in the table. For tier selection guidance, see [choosing a model tier](../guide/configuration.md#choosing-a-model-tier).

A direct profile's `agent:` follows only `agents/` definitions and registered kinds (an agent cannot inherit a subagent). A subagent's `agent:` checks `subagents/` first, then accepts a registered kind or an `agents/` definition (bare or `<pack>:<name>`); a direct profile entering a child's chain drops `subagents`, `idle-compact`, and `keep-warm`, and its own `subagents:` list is not validated on the child's behalf. Without `agent:`, a recognized model alias, model ID, or prefix determines the kind: Claude's roster and `claude-` prefix, Codex's roster and `gpt-` prefix, and Antigravity's roster and `gemini-` prefix. Unknown models use the chain's kind or require `agent:` when none exists. Except on Pi and OpenCode, a model implying a different kind from a registered `agent:` in the same definition is an error (a `claude-` ID under `agent: antigravity` or `agent: agy` runs on Antigravity instead), and a child model may change its ancestor's kind. Pi and OpenCode chains keep their engine under concrete models, including a team role's explicit `model:`; use `agent:` or `--agent` to select another engine. OpenCode resolves against its configured catalog in [full-name, first-ID, then nearest-name order](../internals/agents/adapter_opencode.md#model-selection), announcing non-unique and near-miss picks, and a `provider/model` name read as another provider's model ID, on the card. A `tier:` also keeps Pi and OpenCode on their engine, including a team role's tier override.

Children inherit `tier` or `model`, `mode`, `isolation`, `empty-dir`, `effort`, `fast`, `code-mode`, `auto-compact`, `smart-compact`, `budget`, `timeout`, `keep-warm`, `idle-compact`, `capabilities` or `tools`, `allowed-tools`, `skills`, `mcps`, `subagents`, and `model-reminder`. An explicit child field replaces the inherited value, except a list that adds to it (below). `capabilities` and `tools` inherit as one setting: the nearest layer that writes either (role entry, then the chain from child to parent, then the kind base) decides which one the profile uses, and takes neither from above it. A `+` list counts as writing, and a `+` list of the other key written nearer the child skips that layer and everything above it to add to the kind base's list. A team seat resolves these lists exactly as its definition does alone, and a role entry's `+` list adds to that result. Every other list inherits as written whatever the form, and a `tools` definition reads it by the `tools` rules. Under a `capabilities` parent that wrote `skills` or `mcps`, which name none of the eleven capabilities, the child reads that list as the whole list: it loses those capabilities' skills or RimZ's servers, and `rimz agents validate` names each `rimz(x)` it can no longer reach. Where the parent left `skills` or `mcps` absent, or wrote `mcps: ['*']`, the child reaches every RimZ skill or capability, whatever the parent's `capabilities` named. Below the whole chain, a field it leaves unset comes from the [kind base](#kind-bases). Descriptions and trait lists are local. Parent prompt bodies are retained in order before the child's body. A bodyless definition adds no craft, so it can serve as a model-only preset on its kind base.

In a Markdown definition, a kind base, or a team role entry, a `capabilities`, `tools`, `allowed-tools`, `skills`, `mcps`, or `subagents` list whose every entry starts with `+` adds to the inherited list instead of replacing it: `skills: [+review]` keeps every skill the parent or kind base lists and adds `review`. The list adds to the nearest list below it: the parent chain first, then the kind base. A `+` list over another `+` list stays pending and keeps looking further down until it reaches a list without `+`. Inherited entries keep their order and new ones follow in written order, except that an added entry replaces every inherited entry that is the same entry, in the place of the first: same base before `(` for `tools` (Pi's names count as their RimZ spelling), same rule for `allowed-tools`, same name for `skills` and `subagents`, and same name before the load mark for `mcps` and `capabilities`. So `+rimz-lsp:deferred` over `rimz-lsp` gives `rimz-lsp:deferred`, `+rimz-lsp` over `rimz-lsp:deferred` gives `rimz-lsp`, `+rimz:always` over `rimz:deferred` gives `rimz:always`, `+rimz-lsp` beside an inherited `rimz:deferred` adds a `rimz-lsp` that takes `rimz`'s mark, and `+Agent(general-purpose)` over `[Bash, Agent(Explore), Agent(Plan)]` gives `[Bash, Agent(general-purpose)]`. An added entry is matched only against the inherited list: inside one `+` list an exact repeat collapses, and one `mcps` or `capabilities` name under two marks is refused, as in a plain list. When nothing below lists the field, a `+` list of `skills`, `mcps`, or `subagents` leaves the field absent, which already admits everything (a `+` `subagents` entry naming a subagent that failed to load still fails the definition, while an unknown name loads), and a `+` list of `capabilities`, `tools`, or `allowed-tools` is refused: write the full list. A list that mixes `+` entries with plain ones, holds a bare `+`, or holds an entry with a second `+` (`++github`, `+ +github`) is refused; `[]` is a plain list. Repository TOML profiles take no `+` entries: a skill or `mcps` name that starts with `+` is refused there and on every other surface that parses these names.

`agent: crew:coder` selects the installed pack `crew`'s `coder`, including a copy hidden by a home override or a pack conflict. An agent selects the pack's `agents/` item; a subagent checks the pack's `subagents/` first and then its `agents/` (dropping `subagents`, `idle-compact`, and `keep-warm`). A home `agents/coder.md` can inherit the shipped parent this way and replace only its chosen fields; [`rimz packs customize`](cli/packs.md#customize-an-item) creates that layer. The parent's own bare parent, kind base, traits, child names, and skills still use the merged chains, not an own-pack-first lookup. Qualified keys never become launchable profiles; launch specs and team role `agent:` fields take bare profile names, not `crew:coder`.

An unknown qualified pack names the installed packs and `rimz packs list`; a missing item points to `rimz packs show <pack>`. An excluded parent points to `rimz packs include <pack>:<name>` (include its whole type first if excluded). A failed parent keeps its failure cause. Cycles through qualified and bare parents are diagnosed like other inheritance cycles.

Defaults apply after inheritance, for the kind and model the launch finally runs on, including `--agent`, `--tier`, and `--model` overrides. Written fields from the launched profile's chain carry across an override; any field left unset falls through to the `--agent` chain and then the final kind's base, so no other provider's base contributes. Kind defaults, a kind base's `effort`, `fast`, `code-mode`, and `auto-compact` included, always come from the final kind's base. Permission mode uses the common launch-time [mapping and defaults](./agent-support.md#permission-modes), for Markdown and TOML profiles alike. A kind base's `effort` comes first; without one, Claude defaults to effort `xhigh`, except `fable` defaults to `high` (also when a machine pin maps it to an ID the catalog does not list), and Codex and Pi default to effort `xhigh`. Antigravity's roster (`hydrogen`, `neon`, `carbon`, `argon`, and `flash`, and their IDs `gemini-4-<name>` and `gemini-3.8-flash`) defaults to effort `high`; any other `gemini-` ID, effort-suffixed IDs such as `gemini-4-hydrogen-high` included, launches as written with no built-in effort, and a differing effort beside a suffixed ID is left to agy's own launch refusal. The Orchestrator IDs `gemini-pro-orchestrator-neon`, `gemini-pro-orchestrator`, and `gemini-pro-orchestrator-argon` have no short name and take no effort: when the launch finally runs on one of them, a written effort, `max` included, warns and launches without one, since agy runs another model when `--effort` comes with them. An Antigravity short name launches its `gemini-` ID, and a machine pin takes precedence. On Antigravity, effort `max` launches at the model's highest level, `xhigh` on hydrogen, neon, and `gemini-` IDs outside the roster and `high` on carbon, argon, flash, and `claude-` IDs, with a launch warning. The level is the one the launch's final model takes, after a `--model` override or a machine pin. Codex aliases `astra`, `sol`, `luna`, and `terra` follow their account catalog's newest family model at fresh launch, subject to effort support; definitions retain the requested alias. Machine [model alias pins](../guide/configuration.md#model-aliases) take precedence. Recorded launches resolve the requested alias again on relaunch; legacy sessions without a launch record replay their observed model when available. Pi and OpenCode instead restore their native session's model on plain resume or restart; Pi also does so on fork. A kind with a native or RimZ-enforced auto-compaction ceiling uses its kind base's `auto-compact`, then the machine [`[harness] auto_compact`](../guide/configuration.md#auto-compaction-ceiling) default (`272k` when unset; `"off"` applies none); other kinds have no default ceiling. Definitions are rejected at load if their resolved kind cannot render a supplied or inherited `model`. An `effort` outside Hermes's or Antigravity's level list loads and refuses at launch, naming the allowed levels; a team seat resolves while teams load, so a seat with such a level fails the load (`rimz agents validate` exits 1 naming the seat). Other unsupported `effort`, `fast: on`, `code-mode: on`, and `auto-compact` load normally and warn at launch, which runs without the setting. Invalid auto-compact counts still refuse. Defaults are filled only when supported and silently dropped on a switch to an unsupported kind.

### Kind bases

`agents/<registered-kind>.md`, or the file named by one of the kind's aliases (`agents/agy.md` for antigravity, `agents/mcode.md` for minimax), is a special base, not an ordinary definition. It accepts every profile key, requires a nonempty body, and supplies the system prompt in both namespaces. It is the root parent of every Markdown definition, trusted project profile, and team seat on its kind: a field the definition's chain leaves unset takes the base's value at load, in the render for that kind, so the stored profile, `rimz agents explain`, and every launch of it carry the value. A tier definition takes each candidate kind's base in that kind's render, and a child inherits its parent's chain, not the base its parent took. The base's `model` fills only a chain that sets neither `model` nor `tier`. Its `description` and `traits` stay its own; the traits render into its body. A subagent skips the base's `idle-compact`, `keep-warm`, and `subagents`, and a direct profile skips its `timeout`; a definition that writes one of those itself still refuses (or warns for `keep-warm` on a subagent). A definition whose chain lists the `Agent` tool (on Claude, `default` lists it) skips the base's `subagents`, while one that writes `subagents` beside an `Agent` tool from the base refuses. `tier:` refuses on a base, and `agent:` may name only its own kind or an alias of it. Every other key is checked as on a profile of the kind and `subagents` names as on a direct profile, each refusal naming the base file. The base's launch defaults `fast`, `code-mode`, `effort`, and `auto-compact` are not inherited at load. They fill only what no definition in the chain, team role, or launch flag writes, for the kind the launch finally runs on: Markdown and repository TOML profiles on the kind, team seats, subagents, the bare kind, and a `<kind>-fast` cell take them (the suffix still forces fast on), and `--agent` onto another kind takes that kind's base instead. A repository TOML profile cannot take a provider kind's name: it fails with rename advice without replacing or breaking the kind base. A kind that takes no system prompt has no base and so no base defaults. A kind takes a system prompt when its adapter declares a prompt channel: claude, codex, opencode, pi, omp, qwen, minimax (appended to its own prompt), antigravity (on a fresh launch, through an agy agent file), and process plugins declaring `system-prompt-file-flag`. See [launch-prompt replacement](./agent-support.md#launch-prompt-replacement) for how each receives it. Every definition, trusted project profile, and team seat on such a kind runs on that kind's base, body or not.

Where neither the home nor an installed pack has a base for a kind that takes a system prompt, the built-in kind base RimZ compiles in stands in for it: a home base comes first, then a pack base, then the built-in one. Claude, Codex, OpenCode, Pi, and Antigravity each have their own built-in body; every other such kind, process plugins included, takes Claude's, and MiniMax, whose prompt appends to its own, takes none, so its crafts and team layer reach its append channel alone. Every built-in base grants `capabilities: [bash, read, write, ask, web, rimz]`. A built-in base is a parent only: it adds no profile row, so it is not listed and the bare kind launches with the provider's own prompt. Its body is sent only where something stands on it, judged once the launch's prompt flags and team layer are applied: a launch with nothing composed onto the built-in body (no craft, appended prompt file, or team layer) sends no RimZ prompt and keeps the provider's own. So a bodyless definition launched with no prompt flag and outside a staged team runs on the provider's prompt, while a chain with a craft, the same definition launched with `--append-system-prompt-file`, and a seat of a staged team get the built-in body, then the crafts and appended files, then the team layer; a `system-prompt-file` replaces it. On Antigravity, whose tools list rides the agent file its prompt writes, the built-in body is always sent. A home or pack base always sends its body. Wherever a base's path shows (a prompt's origin, an error naming the base, the `rimz agents explain` chain and its source marks), the built-in one reads `built-in kind base <kind>`. A home `agents/<kind>.md` or a pack base replaces it for that kind only. While a recorded pack fails to resolve or to list its `agents/`, no kind takes a built-in base, since that pack may ship the base: a definition on a kind with no home or loaded pack base refuses, naming the pack problem, until the pack is repaired or removed or the home base is written.

The base comes from the merged kind-base tier, so a home base reaches pack definitions in both namespaces. A pack kind base is excluded with `--type agents`, just like an agent definition, under its kind's name whichever file name it has (`rimz packs exclude crew:antigravity --type agents` excludes the pack's `agents/agy.md`); there is no separate base type. A base claims its kind under either file name: a home base replaces a pack base, two packs shipping one for the same kind conflict, and two base files for one kind in the same tree are refused, naming both.

A kind that takes no system prompt carries no RimZ prompt. Validation refuses its kind base (delete the file), a definition with a craft body on it (remove the body or choose a kind that takes a system prompt), and a team seat on it (choose a definition on a kind that takes a system prompt). A bodyless standalone definition on such a kind needs no base. A definition on a kind whose base failed to load fails too, naming that base rather than asking you to create it.

Overriding a definition's kind with `--agent` or `--model` builds the chain under that kind. If the chosen kind cannot receive the definition's prompt (or takes no system prompt and so has no kind base, or rejects its tools or skill policy), launch refuses with the loader's error before any pane opens.

### Traits

`traits: [careful, concise]` reads `traits/careful.md` then `traits/concise.md`, deduplicating first-seen names. Names cannot be empty, `.` or `..`, or contain path separators. These files are plain Markdown: their complete trimmed contents are joined with blank lines and replace the first `${traits}` in the body. Later tokens collapse to a blank line. With no traits, the token disappears. Naming traits without a token is an error. Other `${...}` placeholders survive unchanged; the team pipeline is not trait-substituted.

Each trait comes from the merged trait tier. A home trait override reaches every definition that names it, including a qualified pack parent's body. A team's `consensus` key names traits too, composed after the consensus instead of into a craft; see [consensus pieces](#consensus-pieces).

## Tools to provider arguments

Tool entries use Claude-style names; the Pi aliases below normalize to those names before deduplication. The base before `(` is trimmed and deduplicated in first-seen order; it must begin with an ASCII letter and contain only ASCII letters, digits, or underscores. Parentheses must balance without nesting. Only `Agent(...)` interprets its suffix, as a comma-separated native child-type allowlist. Other suffixes do not restrict calls; Pi warns when it cannot enforce a suffix on a mapped tool. This is not a permission-pattern language.

Quote entries containing commas in a YAML flow list: `tools: ["Agent(Explore, Plan)", Bash]`.

`tools` decides which tools exist; `allowed-tools` pre-approves calls to them. Rules are trimmed and deduplicated, keeping the first occurrence. A rule starts with an ASCII letter, followed by ASCII letters, digits, `_`, `*`, or `-`, optionally followed by a nonempty `(specifier)` closing the rule. Control characters are refused. MCP names such as `mcp__my-server__*` are accepted. Claude auto mode drops some broad rules, including `Bash`, `Bash(*)`, wildcarded interpreters, package-manager run commands, `Agent`, and `Monitor`; use narrow rules such as `Bash(git *)`. Claude's drop list is best-effort and may change.

Antigravity takes each rule in agy's permission grammar, so RimZ translates it and merges the results into `permissions.allow` of the launch's one `--settings`, beside any `--settings` the profile passes. Because a `--settings` `permissions.allow` replaces the account's saved allow list for the session, RimZ copies the login's saved `permissions.allow` rules into that same document whenever the saved file can be read, beside the room and note-store write rules and, for a launch at a Git checkout's root, the checkout common-Git-directory read rule ([what RimZ adds and what that read rule exposes](./agent-support.md#permission-modes)); saved deny rules, global and project, stay in force ([observed on agy 1.5.14](../externals/agent-adapter/antigravity-reference.md#permission-resources)). A rule with no row below is left out and named in a warning at launch and in `agents validate`; it is never passed through, since agy accepts a rule it cannot read and matches nothing.

| Rule | agy rule |
| --- | --- |
| `Bash`, `Bash(*)` | `command(*)` |
| `Bash(P)`, after one trailing `:*` or ` *` is removed from P | `command(P)`, when P is non-empty, holds no other `*`, and does not start with `regex:` |
| `Read` | `read_file(*)` |
| `Edit`, `Write` | `write_file(*)` |
| `Read(T)` | `read_file(T')` |
| `Edit(T)`, `Write(T)` | `write_file(T')` |
| `WebFetch` | `read_url(*)` |
| `WebFetch(domain:H)` | `read_url(H)`, when H is `*` or a hostname with no scheme, port, path, or `*` |
| `mcp__S__T` | `mcp(S/T)`, when T holds no `*` |
| `mcp__S`, `mcp__S__*` | `mcp(S/*)` |

T' is T with one trailing `/**` removed, then `//abs` becomes `/abs` and `/x`, `./x`, or `x` becomes the workspace-relative `x`. A T that starts with `~`, a T' that still holds `*`, `?`, `[`, or `{`, a T' that still starts with `/` (`.//x`, `///x`), and an empty T' are untranslated. A rule whose specifier holds a parenthesis is untranslated, and so is a `Bash(regex:...)` rule, which agy would read as a pattern rather than a prefix. S is the server name agy knows: `rimz_tools` for RimZ's own server (`mcp__rimz` and `mcp__rimz__T` become `mcp(rimz_tools/*)` and `mcp(rimz_tools/T)`), and the configured name for yours. Every other rule is untranslated, `Glob`, `Grep`, `Agent`, `Skill`, and `WebSearch` included.

agy matches differently from Claude, so a translated rule can admit more. `command(P)` matches P word by word with any trailing arguments, so an exact `Bash(git status)` also admits `git status --short`. A file rule names a directory and covers everything under it. A file rule also opens its path to agy's terminal sandbox, so under `isolation: sandbox` a sandboxed command can read or write it, and `Edit` or `Write` alone lets sandboxed commands write anywhere ([observed on agy 1.5.14](../externals/agent-adapter/antigravity-reference.md#permission-resources)).

| Kind | Rendering |
| --- | --- |
| Claude | Requires `tools`, even if empty. Emits optional `--disallowedTools`, then `--tools` with comma-joined bases. `default`, in any case, is Claude's preset of every built-in tool: a list of `default` alone renders as written, and `default` beside other names renders as `preset:default` ahead of them, the one spelling Claude reads inside a list (such a list loses Claude's embedded `Glob` and `Grep` unless it names them: [Claude reference](../externals/agent-adapter/claude-reference.md#tool-preset)). Bare `Agent` adds no type restriction. With [code mode](./agent-support.md#code-mode) on, `REPL` and `Poll` end a list without `default`, each once. | Codex | Requires `tools`, even if empty. Emits `--strict-config` and the ordered `-c` settings below. Native `Agent(...)` type names do not restrict Codex child types. | Antigravity | Requires `tools`, even if empty. A resume keeps the tools its conversation started with. A fresh launch with `tools` and no prompt sources refuses ([the agent file](../internals/agents/adapter_antigravity.md#the-agent-file)). |
| OMP | Accepts or omits `tools`; ignores the list silently. |
| Other kinds | Accepts or omits `tools`; a supplied list warns at launch and is not applied. |

An explicit `[]` wins over anything below it. A provider that cannot apply a supplied list warns and launches without it; OMP stays silent. Generated tool flags are not part of a profile's `args` in `rimz config get`. ## Delegation and skills

Omitting `subagents` leaves RimZ delegation unrestricted; a list replaces that policy with named children, and `[]` denies all. Names are trimmed and deduplicated, must be nonempty, and must name a subagent definition that loads, an `[agents.commands]` entry, or a registered kind; a repository TOML `[profiles]` row takes the same names. Naming a subagent that failed to load fails the listing definition, and in a trusted project a subagent fails to load when its `[subagents.profiles.<name>]` row does, even over a machine subagent of that name. A subagent definition cannot set or inherit this field. A direct profile cannot combine any `subagents` list with the native `Agent` tool: choose the RimZ doorway or native delegation. On Claude a `tools` list holding `default` carries the `Agent` tool, so `subagents` beside it refuses: drop `subagents`, or list the tools by name without `Agent`.

At launch, RimZ delegation plus an available child catalog switches off provider-native delegation wherever the provider has a verified switch, even when `tools:` lists `Agent`. RimZ delegation is either the callable `rimz-subagents` skill or the `subagent` tool of RimZ's MCP server, which a Claude, Codex, Antigravity, OpenCode, or Pi launch serves when its [`mcps`](./cli/mcp.md#the-mcps-profile-key) selection includes `rimz-subagents`, as an absent `mcps` and a list holding `*` or `rimz` do (beside a `capabilities` list, when the grant names `rimz-subagents`), except on a subagent child, a workflow judge, and a profile with `subagents: []`, which are also withheld the skill; the two are equivalent, and the skill is the fallback where the tool is not served. Omitting `skills` makes every skill callable (beside a `capabilities` list, every skill but those of the capabilities the grant leaves out) unless an applied `tools:` list excludes `Skill` (Claude, Codex, Pi, and Antigravity; on Claude a list holding `default` includes it); then none is callable, skill reminder sections disappear, and native delegation and native LSP tools stay as the tools list renders them unless the launch serves the `subagent` tool (with an available catalog) or the `lsp` tool of RimZ's MCP server, which switches off the native counterpart. Tools lists on other kinds do not change skill callability. To retain native delegation, leave `rimz-subagents` out of a `capabilities` list; without one, omit `rimz-subagents` from an explicit `skills` list and, on Claude, Codex, Antigravity, and OpenCode, also set an explicit `mcps` list that names none of `rimz-subagents`, `rimz`, or `*`, or set `[agents] rimz-mcp-server = false`; or have no launchable child: a home or pack [kind base](#kind-bases) counts as one, beside subagent definitions and `[agents.commands]` entries, and a built-in base does not. A disabled catalog (`subagents: []` included) does not switch native delegation off. Children still have native delegation disabled. See [delegation policy](../internals/harness/subagents.md#native-delegation-policy).

A prompt names one of RimZ's own capabilities as `rimz(x)`, a skill as lowercase `skill(name)`, and a subagent profile as `subagent(profile)`. Each form is case-sensitive and requires no letter, digit, or underscore right before the keyword; capitalised `Skill(x)` and `Agent(profile)` are plain text, unparsed, and code spans count like other text. `rimz(x)` takes a lowercase name of letters, digits, and hyphens starting with a letter (`rimz(wait)` means `rimz-wait`). `skill(name)` takes any valid skill directory name without `(` or `)`. `subagent(profile)` takes any nonempty profile, command, kind, or runtime-variant name without whitespace or `,`, `+`, `/`, `(`, `)`. At launch, RimZ rewrites each `rimz(x)` and each `skill(rimz-x)` for one of the eleven MCP capabilities in the composed system prompt to how this launch reaches it: `mcp(<tool>)` when served on RimZ's MCP server (`mcp(lsp)`, `mcp(subagent)`, `mcp(agent)`, `mcp(team)`, `mcp(schedule)`, the four comma-separated `mcp(self_*)` tools for `rimz-control`, and the two `mcp(blackboard_*)` tools for `rimz-blackboard`), else `skill(rimz-x)` when callable as a skill on disk ([launch reminders](../internals/harness/fleet.md#launch-reminders)). Other `skill(name)` references and author-written `mcp(...)` forms stay as written. A `rimz(x)` or capability `skill(rimz-x)` the launch cannot reach stays written as authored and warns on stderr and the agent card while the agent starts. `rimz agents validate` errors on unreachable or unknown `rimz(x)`, `skill(x)`, and `subagent(x)` references (see [Validation and failures](#validation-and-failures)).

A `skills` list requires the `Skill` tool on Claude, Codex, and Antigravity (a `capabilities` list adds it, and on Claude `default` carries it), and on Pi whenever the definition supplies a `tools` list. Entries are trimmed and deduplicated bare directory names, never paths, whitespace, or `<name>:<mode>` strings, and start with `+` only to [add to an inherited list](#chains-and-defaults). At config load from a host process, a list is checked only when the definition resolves to scoped isolation on Linux or runs on a provider with a host skill switch (Claude or Codex). For a checked list, each skill must have a readable `<name>/SKILL.md`, searched in the provider root (RimZ-owned links skipped), then the home library, then installed packs. This is the same chain as the [scoped skill view](../internals/sandbox.md#skill-roots-and-user-only-markers); the winning copy's marker is checked, a missing name lists the searched paths and the fix, and a conflicted pack name fails with the conflict. A skill marked user-only for the selected provider is rejected: frontmatter `disable-model-invocation: true` for frontmatter-based providers, or `policy.allow_implicit_invocation: false` in `agents/openai.yaml` for Codex. The error names the marked file and both fixes: drop the skill from `skills:` or remove the marker. Invalid marker metadata or unreadable files also fail.

Host isolation enforces the list through Claude's or Codex's per-launch switch; providers without a switch warn and run unrestricted. The load-time decision uses the inherited profile isolation default, then machine policy; host definitions without a switch skip both skill lookup and marker checks. The check reads the host's skill roots, so it runs only from a host process: inside a scoped pane, where an agent's own unlisted skills appear as RimZ's user-only copies, config loading and `rimz agents validate` skip it (validate says so on stderr). Validation resolves the provider root from the ambient environment; a named account whose login home holds a different skill set is checked when that account launches. Scoped launch also requires provider support for skill views. See [configuration: skills](../guide/configuration.md#skills) and [host switch limits](../internals/sandbox.md#host-mode).

Role fields override inherited definition fields. Unlike standalone chains, a seat's recognized model may select a different runtime kind; an unrecognized model keeps the original kind. The seat runs on the selected kind's base, the built-in one where neither the home nor a pack has one. Tools are rendered again for the selected kind. Traits combine leaf-definition → role → team, deduplicated; ancestor crafts remain unchanged. Added traits require `${traits}` in the leaf body. Nonleaders lose `AskUserQuestion`, or the word `ask` on a `capabilities` seat. Every Markdown team runs the built-in consensus, which names `rimz(message)` (a project TOML team may replace it with `consensus-file`, and its seats get no seat edits). Right after any consensus, built in or a `consensus-file`, RimZ composes a Board writes section, which names the `blackboard_flip` and `blackboard_record` tools where the launch serves `rimz-blackboard`, and `rimz teams flip` and `rimz teams record` otherwise; a launch that carries the consensus loads served `rimz-blackboard` tools as if marked `always`, unless an entry naming `rimz-blackboard` carries its own mark. So every Markdown team seat admits `rimz-message` and `rimz-blackboard`. A `capabilities` seat gains each in `capabilities` whenever it lists neither that name nor `rimz`, even beside `skills: []` (where that implies `Skill`). A non-`capabilities` seat gains each in `mcps` whenever `mcps` is set and lists none of that name, `rimz`, or `*`, and an optional `rimz-message` entry in `skills` (an empty `[]` list included) when absent. Load marks that seat-added entry without looking it up on disk, and launch settles it against the launch's kind, login, trusted project `[[agents]]` env, and skill inventory: it stays listed when installed and model-callable there, and drops silently when missing, unreadable, conflicting, or marked user-only, so a seat-added `rimz-message` never refuses load or launch, whereas an author-written `rimz-message` in `skills` keeps every load and launch check. When the team lists the shipped `reflect` [consensus piece](#consensus-pieces), every seat whose authored skill list is nonempty gains `rimz-reflect`, a `capabilities` seat's included, and `rimz-reflect` passes the library checks; an authored `skills: []` list never gains `rimz-reflect`, and omitted skill lists stay omitted.

Prompt order is kind base → ancestor crafts → seat craft → built-in consensus → its Board writes section → consensus pieces → team pipeline, separated by blank lines. Markdown teams cannot replace the consensus or set scratch files; `consensus` only adds pieces after it. Their staged workflow keeps its board and stage notes through `.rimz/team/`, a link to the run's archive in room state; see [teams](../guide/teams.md).

### The built-in consensus copy

RimZ writes a read-only copy of the built-in consensus to `teams/consensus.md` under the definitions root, for reading and linking. `rimz setup` writes or refreshes it, and launching a team seat that runs under the built-in consensus refreshes it too, so an upgrade replaces a stale copy at the next team launch. A header line names the RimZ version that wrote it. RimZ never reads the file back: teams always run under the text compiled into the binary, and an edit to the copy changes nothing and is overwritten at the next refresh. To change a team's consensus, set `consensus-file` in a project TOML team; to add to it, list [consensus pieces](#consensus-pieces). Every seat needs a base prompt, supplied by `system-prompt-file` on the role or its profile chain, or by its kind base (`agents/<kind>.md` under the definitions root, a pack's, or the built-in one). A seat without a base refuses the team's launch; the project still loads.

Because the definitions loader skips it, `teams/consensus.md` is never a team definition, and `consensus` is not available as a Markdown team file name.

### Consensus pieces

`consensus: [reflect, house-rules]` gives every seat each named piece, in list order and each name once, after the consensus and before the team pipeline. A name is a trait name, read from the merged trait tier as `traits:` reads it (home over pack), and it needs no `${traits}` token. A name that is invalid, has no trait, cannot be read, or is claimed by two packs refuses the team with the trait wording. The pieces are scanned for `@` mentions with the pipeline. A team that lists no pieces gets none, so it gets no reflection text and no reflection skill.

RimZ ships one piece, `reflect`: the reflection practice of running `skill(rimz-reflect)` at the end of every stage and distilling those entries in a last `Reflect` stage. It is used only when no home or pack `traits/reflect.md` claims the name; such a file replaces its wording for every team that lists `reflect`. Two rules follow the shipped wording alone. A team that lists it must declare a stage named `Reflect`, or it is refused at load with both fixes: add the stage, or drop `reflect` from `consensus`. And every seat with a nonempty authored skill list gains `rimz-reflect`, a `capabilities` seat's included. A team whose `reflect` is a home or pack file gets neither: its seats list what that file names. Because the skill name starts with `rimz-`, a seat listing it also gets the launch reminder's skills section, and on Claude a routine `Skill(rimz-reflect)` allow, as every RimZ skill does.

RimZ writes a read-only copy of the shipped piece to `teams/consensus/reflect.md` under the definitions root, with the consensus copy and by the same two writers: `rimz setup`, and a seat launch that composes the built-in consensus or the shipped piece. Nothing reads it back. To change the wording, copy its text to `traits/reflect.md`; a copy under `traits/` is itself the replacement, which is why RimZ keeps its own outside that tree.

A project TOML team takes the same key, `consensus = ["reflect"]`, resolved against the same trait tier; its pieces follow the consensus or its `consensus-file` and come before its `append-system-prompt-files`. A refusal names the project config file. The list is part of the [project trust hash](../internals/harness/trust.md).

### Stages and handles

Every declared stage must have exactly one owner. Ownership of an undeclared stage or duplicate ownership fails. `Implement` and `Review`, when both present, must have different owners. `Done` is implicit and cannot appear in `stages` or `owns`. Stage names match exactly; declaration order is not an enforced transition order.

The leader must name a declared handle. Handles must satisfy the shared address grammar and cannot shadow broadcast, reserved sender, kind, or kind-ordinal addresses. A layout must place every declared role exactly once. The pipeline, consensus pieces, and built-in consensus are scanned for `@` mentions beginning with an ASCII letter; each must name a declared role, `all`, `rimz`, or a registered kind. See [addresses](./cli/agents.md#addressing-agents).

### Signals

Signals belong on roles, never standalone definitions or the team root:

```yaml
signals:
  - ci.failed
  - signal: agent.idle
    match: {handle: reviewer}
    prompt: Read the review and continue the plan.
```

A selector is `family.event` or `family.*`: the family begins with a lowercase ASCII letter, and words contain only lowercase ASCII letters, digits, `_`, or `-`. No multi-dot or partial-wildcard selectors are accepted. Mapping entries accept only `signal`, `match`, and `prompt`. `match` maps payload field names to nonempty strings; all fields must match. An `agent.*` binding requires a `handle` or `session` match whose value is not a wildcard. A supplied prompt must be nonblank and is trimmed. An omitted signals field has no bindings; a supplied field must be a nonempty list, so null and `[]` are refused. Launch also validates event scope. See [team signal delivery](../guide/teams.md#send-events-to-the-responsible-role).

### Smart compaction

`smart-compact` accepts a nonnegative token count (`200k`, `120000`, `1m`), a percentage from `0%` through `100%`, or `off`. TOML profiles and team roles take strings, for example `smart-compact = "200k"`; Markdown agent, subagent, and role frontmatter also accepts bare token counts and `off`.

Resolution follows the team role's TOML override, then the first setting in the seat's profile chain, then [`harness.smart_compact`](../guide/configuration.md#smart-compaction), whose default is `258k`. A Markdown role's override belongs to its generated seat profile. A supervised child uses its launch profile's namespace, normally the subagent table. An explicit `off` stops inheritance. Unlike `auto-compact`, this field controls RimZ's reminder and compact-first policy rather than the hard ceiling.

[`rimz agents tune <AGENT> smart-compact <VALUE>`](./cli/agents.md#tune) replaces this configured resolution for one session; `reset` restores it. An explicit message threshold takes precedence over that override.

The same line drives the [mid-turn compaction reminder](../guide/loops.md#smart-compaction) and compact-first message delivery to a resting agent. Mid-turn detection resolves current definitions; a queued message retains the line selected at enqueue. `rimz message --smart-compact` changes only that send's line.

### Idle compaction

`idle-compact` accepts `off` or a positive token count: an integer or a string in digits or `k` such as `100k`, `250000`, or `1000k`, with no `m` suffix and no percentages. A bare YAML `off` (the boolean `false`) means `off`; `true` and `0` are refused. An idle seat compacts once its occupied context reaches the floor; see [idle compaction](../guide/configuration.md#idle-compaction) for the timing, provider defaults, and eligibility.

On a standalone definition it sets the floor for an agent launched from that profile and is inherited through `agent`; a TOML profile inherits it through its `agent` base the same way, and an explicit `off` stops the walk. On a team role it overrides the floor the role's definition carries. Omitted everywhere, the seat uses `harness.idle_compact`, whose default is `100k`. A subagent definition that sets it is refused, since a `rimz subagents` child has no configured idle-compaction floor; an explicit runtime tune can supply one.

[`rimz agents tune <AGENT> idle-compact <VALUE>`](./cli/agents.md#tune) replaces this configured floor for one session, including a pane-backed child; `reset` restores it.

### Keep-warm

`keep-warm` accepts a block with optional `max` and `while`. `max` takes `off` or a positive duration (units `s`, `m`, `h`, `d`). `while` takes the [loop `--when` condition grammar](./cli/loop.md#conditions), restricted to `team.stage` without a branch selector, or `off`. The stage values are this team's stages plus `Done` (`team.stage=unknown` refuses, since an unread board is already unknown); stage words use ASCII letters, digits, `_`, `.`, or `-`, so names with spaces cannot appear in a condition. Unknown readings (missing or unreadable board, no `Stage:` line, or no checkout path) permit the hold, including before the first flip. A known reading is evaluated anew on every pass; reopening a stage can restore a hold only while the cache remains warm.

Shorthand `6h` means `{ max: 6h }`; shorthand `off` means `{ max: off, while: off }`. Bare YAML `off` or `false` works at the top level and in either field. `true`, numbers, and unitless durations are refused. TOML accepts the same string shorthand or an inline table, for example `keep-warm = { max = "6h", while = "team.stage!=Done" }`.

For team seats, resolve each field separately: role, then team. An unset `max` then takes machine-wide `harness.keep_warm` (default `off`); `while` has no global default. An explicit `off` cancels that field, including the global maximum. A role duration still inherits the team's `while`. Neither field reads the profile behind the seat. No resolved fields means no hold. `max` alone continues through `Done`; add `while: team.stage!=Done` to stop there. A `while` with no resolved maximum uses `harness.cache_keepalive_max` as a finite maximum, including when `max: off` cancels the global; with that cap `off` it holds nothing, and validate warns to set `max`.

Standalone definitions and TOML profiles accept shorthand or a `max`-only block, inherited through `agent`, then fall back to `harness.keep_warm`; a nearer explicit `off` stops inheritance. A seat with no profile name also takes the global value. The global key accepts only duration or `off` shorthand, not a block. Any `while` field is refused on solo profiles, or on an unstaged team: they have no board. Other keys (forge or window readings), undeclared stage values, and malformed conditions are refused at load for teams and roles too. The horizon holds only when the agent's resolved prompt-cache lifetime exceeds `harness.prompt_cache_margin` and is at least `harness.keep_warm_min_ttl` (default `30m`). `rimz agents validate` checks the effective policy, including the global default, against settings, defaults, and the fallback, naming sign-in modes when they differ. It warns at the definition when the lifetime is off or under the floor, or `harness.cache_keepalive` is off; an unknown lifetime means the fallback is off. Lifetime warnings say this is a static check: an agent's own cache writes can change its lifetime. Validate also notes a resolved `max` longer than `harness.cache_keepalive_max`, which caps subsequent pings. A `subagents` definition may carry `max` but no seat reads it, and validate says so; children never inherit the global hold. See [keep-warm](../guide/configuration.md#keep-warm) for what a horizon does and costs.

[`rimz agents tune <AGENT> keep-warm <DURATION|off>`](./cli/agents.md#tune) replaces the complete configured rule for one session, including a pane-backed child; `reset` restores it.

For Pi, an enabled declared horizon also requests the one-hour Anthropic prompt cache at the next launch or restart when cache keepalive is on, unless the user sets the retention. Launched children do not request it. See [keep-warm configuration](../guide/configuration.md#keep-warm) for overrides, native-child inheritance, and cache-write pricing.

### Flip compaction

`flip-compact` accepts nonnegative integer token counts, strings such as `120k` or `1m`, percentages from `0%` through `100%`, or case-insensitive `off`; decimals, repeated suffixes, and overflowing counts fail. Omission inherits `harness.flip_compact`; when that is unset, a seat owning `Plan` gets `120k` and other seats get `180k`. An explicit role value overrides both, including a machine `off`. A provider without a manual compact command requires `off` on the role or machine-wide.

```yaml
flip-compact: off
```

YAML boolean `false` is also accepted as `off`; `true` is refused.

This is separate from the `auto-compact` ceiling. A role leaving its stage for another owner's stage compacts at its next turn boundary only when occupied context reaches the threshold. Flips to `Done`, user flips, same-stage re-fires, and moves between self-owned stages do not compact. See [stage handoff](../guide/teams.md#hand-off-with-one-command).

## Validation and failures

```sh
rimz agents validate
rimz agents validate --json
```

Validation reads the merged home and pack definition trees without launching agents or writing generated files. Human output prints three sections, `agents`, `subagents`, and `teams`, each a table with columns `NAME`, `KIND`, `MODEL`, `EFFORT`, `KEEP-WARM`, `ORIGIN`, and `SOURCE`. Kind bases appear in both the `agents` and `subagents` tables. Each team opens with a line `<team>: stages <A> → <B>; leader <role>`, followed by its seat rows. `EFFORT` appends `· fast` for a fast-mode definition. Errors follow the tables as `path: message`, then warnings as `path: warning: message`. Warnings cover unknown manifest keys, tier entries whose family cannot run a definition, `sandbox` isolation on a kind with no sandbox flags, `sandbox` isolation, set on the definition or by the machine default, beside a `mode` whose flags override the provider's sandbox (Antigravity's `yolo`), skill lists a host provider cannot enforce, `allowed-tools` on a kind that cannot apply them, each `allowed-tools` rule a kind cannot translate, language-server settings, and keep-warm horizons that will not hold. A `note: <kind> definitions run on the built-in kind base; write <home>/agents/<kind>.md to replace it` line follows the warnings once for each kind whose definitions run on the [built-in kind base](#kind-bases); JSON output carries no notes. Warnings and notes never change the exit status.

`--json` prints `{rows, warnings, errors}`, where each warning and error is `{path, message}`. A row carries `name`, `namespace` (`agents`, `subagents`, or `team`), `kind`, `model`, `effort`, `source`, `origin`, `team`, `role`, `owns`, and `signals`. It adds `pack` and `inherits` as described below, `tier` and `tier_fallback` for a tiered definition, `fast: true` for fast mode, and `keep_warm` (`max`, plus `while` on a team seat) when a hold resolves. Any error exits 1 after the output, with `error: <N> definition error(s)` on stderr. From a host shell, enforced skill lists use the provider, library, and pack chain; missing roots are empty. Host definitions without a provider switch warn rather than checking the list. Inside a scoped pane the skill check is skipped and validate says so on stderr. Validation also reports every error the launch path's config load records, commands from `config.toml` included.

Validation and profile listings report provenance independently of the defining path. JSON `origin` is `mine` for an agents-home definition or machine command, `pack` for a shipped definition, or `project` for a trusted project profile. Only `origin: "pack"` adds `pack`, the pack name. A definition whose own `agent:` is a qualified pack parent adds `inherits`, such as `crew:coder`; indirect inheritance does not add it. Human labels use `mine`, the pack name, or `project`, followed by ` → <parent pack>` when `inherits` is present. A team seat takes its team file's provenance, not its underlying agent's. Validation reads Markdown only, so never reports `project`. Project rows appear in `subagents profiles`; `agents profiles` and `teams profiles` read machine sources only.

An unreadable or newer installation record, a missing or invalid manifest, a recorded pack absent from its manifest, a missing pack directory, a pack tree read error, or a name conflict is a source-attributed definition error. Pack items also pass the launch namespace and team checks before loading: a reserved profile name, reserved team name, or invalid team layout fails at that item with `rimz packs exclude <pack>:<name> --type <type>` as the fix. These diagnostics make validation fail, but do not refuse unrelated launches. A qualified parent's failure belongs to the dependent that selected it. Trait conflicts fail definitions that name the trait, not unrelated profiles or kinds with that name. A pack skill read error withholds that pack's skills and names `rimz packs exclude <pack>:<skill> --type skills` as the fix; the library and other packs remain available. Excluded or overridden skill copies are not read. Pack-skill conflicts are reported machine-wide against the home library; a provider's own skill of that name can still win for its launches. Use `rimz packs show <pack>` for item fates and exclusions.

The loader collects independent errors rather than stopping at the first file, and one broken definition never fails the config load. Every command keeps the definitions that loaded; a launch that selects a failed name refuses, with that definition's `path: message`, instead of silently substituting another profile. A launch looks for that failure only in the tables it resolves from, `[subagents.profiles]` under `--subagent-profile` and the agents table otherwise (an `--agent` base on a subagent launch also reads the agents table), so a healthy row there launches whatever the other table holds under its name, and a name only the other table holds refuses with that table's failure, its project row over the machine file it shadows, unless that table holds a healthy row by the name, which shadows the broken file and draws the refusal that names the table to launch it from. A name the launch resolves, such as a profile, a `-fast` or permission-mode cell, a kind or one of its variants, or a team, is never refused by a failure that another reading of it names, with `--tier` or without. When it failed because another definition did, a `caused by: path: message` line follows for each failure it rests on, down to the file to fix; a `tier:` definition with no model left follows only the first failed dependency in the order its tier tries models. That covers `rimz agents` launch, resume, restart, and fork, `rimz subagents`, `rimz teams` launch and flip, loop tasks, and the exec wrapper. A definition that selects a failed one (a definition on a failed kind base, an agent allowing a failed subagent, a team with a failed seat or layout cell) fails too. Trusted project TOML profiles in `.rimz/config.toml` resolve through the same loader per row: a broken row fails on its own name and shadows any machine namesake without breaking passing project rows or unrelated teams, and a project row named after a provider kind fails with rename advice, so a launch from that row's table (`[profiles.*]` for agents, `[subagents.profiles.*]` for subagents) of that kind's name or of a variant of it such as `opencode-mini`, bare or as `--agent`, refuses in the project until the row is removed or renamed, while machine and sibling definitions on that kind keep using its kind base. A machine definition, team seat, or kind base that allows a subagent whose project row failed fails in that project the same way, naming its own file with the project row as its `caused by:` line (a `subagents:` entry spelled as a kind alias, such as `agy`, counts as the kind it names): a team with such a seat refuses with the seat's detail, a kind base refuses its bare kind name and its variants, and a launch that takes its list refuses whether the definition inherits it or `--model`, `--tier`, or `--agent` moves the definition onto that kind. A `--tier` walk tries the tier's other models first, but a `tier:` definition whose own pick runs on that kind fails as a whole row, so it refuses on its name and under `--tier` or `--model` even when its tier holds another model. Outside the project, or while it is untrusted, each launches. `rimz doctor` names only the project row. A team whose seat or layout cell rests on a profile that failed in a trusted project, a project team or a machine team such as the built-in `peer`, likewise fails on its own team name in that project without breaking other teams or profiles (a project team's structural errors, such as an unknown leader or bad layout, still fail the project load). A machine team's layout cell resolves against the machine tables only, as any layout cell does (a machine definition or team seat, an `[agents.commands]` entry, a kind or one of its variants, `term`, or an executable on PATH, among others), so a profile only a trusted project defines is no cell for it. A machine team's own errors, such as a cell the machine tables do not hold or a role the layout places twice or never, fail that team and its seats on its own name with its file's `path: message`, in every directory. That failure owns the team's name ahead of the built-in team it shadows and of an executable on PATH, with `--tier` or without, so a broken home `peer.md` refuses `peer` instead of launching the built-in `claude,codex`; only an `[agents.commands]` entry by the name still launches, and a trusted project's team by the name takes it over. A pack team that fails because its name is reserved owns nothing, and the name keeps its other reading. An unowned definition-set failure, such as an unreadable home definition tree or a home team named like an `[agents.commands]` entry or home profile, still refuses every launch until it is fixed; pack-scoped diagnostics do not. A home team named `<x>-fast` also retains that reservation when a pack supplies profile `x`. Resuming a lane degrades a member whose recorded profile failed to a bare resume with a warning, as it does for a deleted profile. Beside live members, closed team members keep their resolvable role and team prompt layers. A missing team or role, or a layer that cannot apply while the solo profile resolves, falls back to the solo profile with one warning per team and cause naming the affected resumed handles; a failed team definition supplies its `path: message`. When every member is closed, a team whose definition is gone or cannot be restored resumes its members as individual agents without the team's layout and prompt layers, with a warning naming the team and why; with `--fresh`, those members are skipped instead. `rimz doctor` and startup notices direct you here.

To check a definition by hand without touching your own home, validate it in a scratch one. Point `RIMZ_HOME` and `RIMZ_AGENTS_HOME` at a temporary directory, write nonempty [kind bases](#kind-bases) `agents/claude.md` and `agents/codex.md`, and give every Claude or Codex definition a `tools:` list such as `tools: [Bash]`. With no `packs/installed.json` there, this also isolates the pack tier; provider skill roots still come from the shell environment:

```sh
export RIMZ_HOME="$(mktemp -d)"
export RIMZ_AGENTS_HOME="$RIMZ_HOME"
mkdir -p "$RIMZ_HOME/agents"
printf -- '---\ndescription: Claude base\n---\nBase prompt.\n' > "$RIMZ_HOME/agents/claude.md"
printf -- '---\ndescription: Codex base\n---\nBase prompt.\n' > "$RIMZ_HOME/agents/codex.md"
printf -- '---\ndescription: Scratch seat\nagent: claude\ntier: senior\ntools: [Bash]\n---\n' > "$RIMZ_HOME/agents/scratch.md"
rimz agents validate
```

Validation does not prove that provider executables, accounts, sandbox preconditions, or a particular live launch will work. Those remain launch checks.

## Moving existing machine configuration

Move agent launch preferences, `[agents.commands]`, `[agents.worktree]`, attention settings, and `[agents.subagents] timeout` into `config.toml`. Put direct profiles, children, teams, and traits in the trees above. Old `agents.toml`, `profiles/*/agent.toml`, and `teams/*/team.toml` are no longer read; setup does not convert or delete them. `agents.d/*/agent.toml` plugin manifests are a separate, unchanged format. Project `.rimz/config.toml` remains TOML. Validate the Markdown sources before launching.
