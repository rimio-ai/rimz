# Pi adapter

> The agent-agnostic boundary, state machine, and context read-path are in [model.md](./model.md); the account, balance, spend, and pricing model is in [providers.md](./providers.md). The raw upstream protocol — the in-process extension API, the session JSONL, the headless RPC/JSON modes, and the auth file — is in [pi-reference.md](../../externals/agent-adapter/pi-reference.md).

This doc is the single home for everything Pi-specific. Pi's integration surface is in-process TypeScript extensions, so the adapter ships one — [`extension.ts`](../../../crates/rimz/src/agents/pi/extension.ts), embedded at compile time — that forwards each event below to `rimz hooks feed --source pi` as a fire-and-forget child. The child direction inverts: Claude and Codex run RimZ as a hook child and read its stdout; pi's extension runs RimZ as *its* child. One event blocks: `tool_call`, pi's pre-tool gate, whose handler pi awaits — there the extension reads the child's stdout as the decision and applies it through the handler's return value. Every envelope also stamps the session name, model, thinking level as `effort`, context gauge (`context_pct` / `context_window` / `total_tokens`, rounded) from the in-process `ctx.getContextUsage()`, latest per-call token split, cumulative `total_cost_usd`, and latest captured rate-limit windows, so a pi row's live context is payload-first with no transcript tail read. Pi 0.80.4's `agent_settled` is the final turn boundary; the extension carries the preceding `agent_end` verdict into it so retries and queued continuations do not flash idle.

## Hooks and lifecycle

Native event → internal mapping; the upstream extension API, payloads, and session JSONL are in [pi-reference.md](../../externals/agent-adapter/pi-reference.md).

| Native event             | Channel   | `observe_lifecycle` → [`LifecycleSignal`](../../../crates/rimz/src/agents/lifecycle.rs) | Normalized fields                          |
| ------------------------ | --------- | ------------------------------------------------ | ------------------------------------------ |
| `session_start`          | lifecycle | `Registered`                                     | worktree from `cwd`                        |
| `before_agent_start`     | lifecycle | `TurnStarted`                                    | sanitized `prompt` (labels the row)        |
| `agent_end`              | lifecycle | — (low-level run ended; automatic work may remain) | captures `stopReason`, `errorMessage`, `model`, and tokens for `agent_settled` |
| `agent_settled`          | lifecycle | `TurnEnded { errored, parked_on_background: false }` or `TurnInterrupted` | clean/error/aborted after retries, compaction, and queued continuation settle |
| `turn_end`               | lifecycle | —                                                | publishes the completed LLM call's usage and newly accrued cost immediately |
| `after_provider_response` | lifecycle | —                                               | publishes newly captured provider rate-limit windows immediately |
| `message_update`         | lifecycle | —                                                | enrichment-only streaming activity; context/cost changes push at most once per second |
| `session_info_changed`   | lifecycle | —                                                | publishes the `/name` session title immediately |
| `tool_execution_end` | lifecycle | `ToolUsed { mutates, edits, native_key }` | mutating `edit`/`write`/`bash` calls prove work; `ask_user_question` is the read-only resolution boundary that clears waiting; `tool_call_id` carries Pi's `toolCallId`; other read-only tools stay silent |
| `model_select`           | lifecycle | —                                                | `model` enrichment-only marker          |
| `thinking_level_select`  | lifecycle | —                                                | `effort` enrichment-only marker         |
| `tool_call`              | **awaiting-user** (`Question`) for `ask_user_question`; every other tool stays neutral | `AwaitingInput { native_key }` for the questionnaire | `tool_name`, `tool_input`, `has_ui`, and `tool_call_id` from Pi's `toolCallId`; absent `has_ui` assumes an interactive older RimZ extension |
| `subagent_started`       | lifecycle | `SubagentStarted`                                | normalized child `subagent_id`, parent `session_id`, `subagent_label`, source, and `cwd` |
| `subagent_stopped`       | lifecycle | `SubagentStopped { errored }`                    | the same child identity plus outcome and optional `total_tokens` |
| `session_before_compact` | lifecycle | `Compacting`                                     | a leading signal, like Claude's `PreCompact` |
| `session_compact`        | lifecycle | `CompactionEnded { auto }`                         | `manual` → false; `threshold` / `overflow` → true; unknown/older Pi → unknown |
| `session_shutdown`       | lifecycle | `Ended` → removed (`ends_session`)               | fires on quit incl. Ctrl+C/SIGHUP/SIGTERM and on `/new`/`/resume` replacement |

Pi's vocabulary distinguishes a *turn* (one LLM call) from a low-level `agent_start`/`agent_end` run. That run may still lead to an automatic retry, overflow compaction-and-retry, or queued follow-up; `agent_settled` fires only after none remains, so RimZ maps `before_agent_start` → `agent_settled` as its user-visible turn. The final assistant message carries `stopReason: "error" | "aborted"` plus optional `errorMessage`; the extension retains that verdict and visible text for `agent_settled`, mapping errors to failed completion and aborts to `TurnInterrupted`/idle while preserving supervised-run output without transcript forensics. An interrupted signal alone creates no success-shaped durable assistant entry. Pi's compaction lifecycle is a true bracket (`session_before_compact`/`session_compact`), and releases from 0.79.10 carry `reason: "manual" | "threshold" | "overflow"` plus `willRetry`; older or future unknown reasons degrade to trigger-unknown. Root identity is direct: the extension runs in-process in the pane, the session id exists from launch (no lazy-registration window), and there is no daemon or remote mode, so every root pi session is standalone and stamped.

**The extension-provided questionnaire.** Pi itself intentionally ships no permission prompts, plan approvals, or questions — ordinary tools run unasked and their `tool_call` gate stays neutral. When the user installs [`@juicesharp/rpiv-ask-user-question`](https://github.com/juicesharp/rpiv-mono/tree/main/packages/rpiv-ask-user-question), that extension registers `ask_user_question` and draws its structured questionnaire in pi's pane. RimZ's own extension sees the awaited `tool_call`, forwards its Claude-compatible `questions` / `options` / `multiSelect` input plus `has_ui` and Pi's `toolCallId`, and records a `Question` ask only when UI exists. The matching `tool_execution_end` carries the same key, so parallel sibling completions leave the questionnaire open. A completed questionnaire also forwards `result.details`: native answers create the structured Answer transcript entry, while Esc cancellation or validation failure only clears waiting. `rimz answer` drives zero-based option focus with Down and Enter, toggles multi-select rows with Space before committing the appended Next row, enters free text through the appended Type something. row, and confirms the final Submit tab for multi-question asks. Preview-carrying and multi-select questions suppress free text; cancel and Chat about this stay pane-only.

## Subagents

Pi supplies no built-in subagent lifecycle, so the managed RimZ extension listens to the shared event bus used by [`pi-subagents`](https://github.com/nicobailon/pi-subagents/tree/v0.34.0) and [`@tintinweb/pi-subagents`](https://github.com/tintinweb/pi-subagents/tree/v0.14.1). It normalizes both families into lean `subagent_started` / `subagent_stopped` payloads containing child id, parent session id, label, source, and worktree without copying the parent's model, context, or cost envelope onto the child. The extension caches Pi's current UUID for that parent link: nicobailon's native `sessionId` is a full session-file path, while tintinweb emits no parent field, and nicobailon's current-session watcher makes the cache authoritative for both start and completion.

Nicobailon's async `parallel` runs fan out to one child row per agent, keyed as `<run-id>#<index>`; async `single` and `chain` runs stay one row per run, with chains labeled by their agent sequence. Its foreground runs emit no bus lifecycle, so they remain visible only as work inside the parent's running turn. Tintinweb emits one started and terminal event per in-process agent, which maps directly to one child row; terminal token totals ride the stop payload when available. A failed event marks the child errored, while nicobailon uses each parallel result's failed status or the run-level outcome and treats a paused run as a clean resolution.

The bridge leaves control, steering, scheduling, compaction, nested fan-out, foreground synthesis, and artifact-log tailing in the extensions' own UIs. Each child event feeds through its own process, so a stop may reach the durable log before its start; the terminal stop verdict absorbs that late start while its label and other enrichment still fold. The bridge drains its shared-bus subscriptions on every session shutdown before applying the `/reload` tombstone skip, so hot reload installs one active handler set. A pi restart during a nicobailon async run prevents that extension's current-session watcher from forwarding its later completion; the existing lost-session reap retires the stranded child the same way it retires a killed Claude Task child.

Pi supplies the final-idle `agent_settled` event; the descriptor keeps `idle` `Partial` only because the shared concern also covers an idle-timeout Notification nudge, which Pi does not expose. Subagents are `Partial` because the two extension bus surfaces cover native per-agent and nicobailon async runs but not nicobailon foreground runs. Rich context is `Wired`: every value-changing native event pushes an extension envelope, streaming `message_update` pushes are change-deduplicated and throttled to one per second per session, and resume hydrates usage and cost from the active branch before registration. Each envelope feeds `observe_context` the session name, model, effort, cost, tokens, and account/rate-limit windows. Background tasks, plan approval, permission prompts, and remote control carry no native signal and no derivation, so they stay `Unsupported` and the absences render deliberately. A single pi session can also switch provider accounts mid-session, so the provider dashboard keys the panel by the agent kind — *pi* — and aggregates whatever accounts pi used.

**Neutral output.** `render_neutral` prints nothing — empty stdout lets ordinary tools run and lets `ask_user_question` proceed into the rpiv extension's native questionnaire.

**Install.** Install is whole-file ownership keyed on the first-line `_rimz_managed` marker: a marked file (RimZ wrote it, however edited since) is reclaimed verbatim on re-install; an unmarked file at the path is the user's own extension and install, preview, and uninstall all refuse to touch it. Interactive setup compares a marked file byte-for-byte with the source embedded in the running RimZ build and offers a consented refresh when they differ; the older file remains installed until accepted. The managed file is removed whole on uninstall and hot-reloads via `/reload`; the spawned child needs `rimz` on `PATH` (or `RIMZ_BIN`), and the extension skips the `reason: "reload"` shutdown so a `/reload` never tombstones the session it is about to re-register. The extension reads Pi's exported `VERSION`: 0.80.4+ waits for native `agent_settled`, while older releases normalize their historical `agent_end` boundary to the same RimZ event so they continue to finish turns.

**Resume.** `pi --session <session_id>` restores a rollup-recorded session (a partial UUID suffices); before re-firing `session_start` with `reason: "resume"`, the extension walks `sessionManager.getBranch()` to hydrate cumulative assistant cost, the latest usage split, and the session name. Older Pi releases without that read surface degrade to sparse enrichment and reconcile at the settled spend pass.

**Integration-blind modes.** `--no-extensions` disables discovered extensions (an explicit `-e` still loads). `-p` / `--mode json` run extensions without a UI; the RimZ extension stamps `has_ui: false`, so `ask_user_question` errors with `no_ui` without creating a stranded ask row.

## Context and transcript

Pi needs no transcript tail for live token context: RimZ authors pi's hook wire ([pi-reference.md](../../externals/agent-adapter/pi-reference.md)), so the extension stamps the gauge onto every hook envelope — `context_pct` / `context_window` / `total_tokens` from the in-process `ctx.getContextUsage()` (rounded on the wire), plus `session_name`, `model`, the thinking level (`off` through opt-in `max`) as `effort`, the latest per-call usage split (`◌` cache-read, `◍` cache-write, `↘` fresh input, `↗` output), and cumulative `total_cost_usd`. Optional upstream `usage.reasoning` is already a subset of `output`, so the normalized output total needs no adjustment. `observe_lifecycle` reads the row fields straight off the payload, and `observe_context` publishes the same envelope as `AgentContext.session_name`, `AgentContext.tokens`, `AgentContext.cost`, `model_id`, `effort`, and rate-limit windows. The extension pushes immediately on model, thinking-level, session-name, completed-call usage/cost, and provider-window changes; streaming context changes push at most once per second and only when the gauge or cost differs. The sidebar reads the rich path for decimal context percentages while the lifecycle row still carries the fallback split. The extension accrues dollars on `turn_end` and publishes the new sum in that event; `agent_end` reuses the final turn's message and does not add cost. The settled-boundary spend walk remains authoritative: when `agent_settled` lands, RimZ resolves the current session file by the UUID in `<ISO-timestamp>_<uuid>.jsonl`, runs the same `parse_spend` path as history, and reconciles `AgentContext.cost` to the session sum. The descriptor declares `live$` as `Wired`: resume hydration preserves the active branch's running sum, and every turn reconciles the dollar to the authoritative session-spend sum.

## Account and balance

[`pi/account.rs`](../../../crates/rimz/src/agents/pi/account.rs) reads [`auth.json`](../../externals/agent-adapter/pi-reference.md#auth-file): oauth → metered subscription, api_key → unmetered. The plan names the sub the fleet uses (`Anthropic OAuth`, `OpenAI API Key`) — the freshest session's `message.provider` picks among several credentials, else the first OAuth entry — and the raw credential key rides `sub_provider`; supported OAuth credentials also carry a normalized `openai` or `anthropic` quota scope, while API-key and unsupported providers carry no quota scope. The shared display-only `pi --version` probe is the panel header's fallback for a provider whose sessions report none. The account probe reads `~/.pi/agent/auth.json` (absent file → `LoggedOut`, unparseable → `Unavailable`); the arms and TTLs are [provider.md → The out-of-band probe](./providers.md#the-out-of-band-probe).

Balance is self-reported under the `pi` kind and keyed by the selected backing credential's normalized scope plus non-secret owner identity. [`delegated_account.rs`](../../../crates/rimz/src/agents/delegated_account.rs) selects the credential once for each usage result, preferring an OpenAI `accountId` and otherwise hashing the refresh token or access-token fallback under Pi's domain. The extension captures `after_provider_response` headers and publishes best-effort windows immediately on that event: Codex-style `x-codex-primary-*` / `x-codex-secondary-*` headers map to 5h and 7d windows, and Anthropic `anthropic-ratelimit-unified-*` variants are parsed tolerantly when present. Missing best-effort headers do not claim a lifted duration. The claimed uniform helper delegates Anthropic tokens to Claude normalization and OpenAI tokens to Codex normalization, writing authoritative windows plus extra credits under `pi`; OpenAI therefore receives Codex's lifted 5h completion while Anthropic does not. API-key credentials remain unmetered and get the API paid-usage row.

## Cost

Pi's provider-native transcript is JSONL, so the adapter normalizes visible `user` text and assistant `content[type = "text"]` blocks for `agents history`, reply streaming, and transcript-backed consumers; thinking, tool calls, tool results, summaries, and extension records stay out of that conversation stream. Full-history spend rides the shared spend pass ([provider.md → Cost history](./providers.md#cost-history)): one `<ISO-timestamp>_<uuid>.jsonl` per session under `~/.pi/agent/sessions/--<cwd-with-dashes>--/`, parsed by [`pi/spend.rs`](../../../crates/rimz/src/agents/pi/spend.rs). A present non-negative `usage.cost.total` is authoritative, including zero under a subscription login; a token-bearing record where the direct cost is absent falls back to model pricing, and an unpriced model still contributes tokens while scheduling a price-table chase. `totalTokens` fills a missing output component so sparse records retain their known total. Token and cost fields accept JSON numbers or numeric strings, and malformed nested usage values become absent fields instead of dropping an otherwise usable record. Pi sessions are single-file and need no cross-file dedup. Nicobailon child processes write standard Pi session JSONL below the same sessions root, so the recursive `pi_session_files` walk already ingests them for spend and stats; tintinweb children persist only when their agent config sets `persist_session: true`, then land in Pi's normal session location and follow the same path, while the stop event's `total_tokens` remains the live-visibility fallback. The extension pushes a live cumulative sum between turns, and the live-card dollar supplement uses the same parser for the current session on turn end, so history and row-level `$` converge on one cost interpretation.
