# OpenCode adapter

> The agent-agnostic boundary, state machine, and context read-path are in [model.md](./model.md); the account, balance, spend, and pricing model is in [providers.md](./providers.md). The raw upstream protocol — the in-process plugin API, bus events, SQLite store, server API, and auth file — is in [opencode-reference.md](../../externals/agent-adapter/opencode-reference.md).

This doc is the single home for everything OpenCode-specific. OpenCode's integration surface is an in-process TypeScript plugin, so the adapter ships [`plugin.ts`](../../../crates/rimz/src/agents/opencode/plugin.ts), embedded at compile time and installed as `~/.config/opencode/plugin/rimz.ts`. The plugin subscribes to OpenCode hooks and bus events, flattens them into a RimZ-authored snake-case envelope, and spawns `rimz hooks feed --source opencode` with `RIMZ_AGENT_PID` set to the OpenCode server process. OpenCode 1.17.20 publishes native permission and question prompts as `permission.asked` and `question.asked`; their `*.replied`/`question.rejected` outcomes clear waiting and record the native answer while OpenCode's UI remains responsible for collecting it. The published `permission.ask` compatibility hook remains wired for older releases and reads RimZ's stdout to set OpenCode's `output.status`.

## Hooks and lifecycle

Native surface → internal mapping; the upstream hooks, bus payloads, SQLite schema, and auth shape are in [opencode-reference.md](../../externals/agent-adapter/opencode-reference.md).

| `chat.message` | `chat_message` | lifecycle | `TurnStarted` | sanitized `prompt`, `model`, `effort` |
| `session.idle` root after a `plan`-agent turn | `session_idle` + `plan_proposed: true` | **awaiting-user** (`PlanApproval`) | `AwaitingInput { PlanApproval }` → `waiting` | latest token gauge; the native TUI owns review and mode switching |

| `permission.replied` | `permission_replied` | lifecycle | `ToolUsed { mutates: false, edits: false }` → clears `waiting` | request id and `once`/`always`/`reject` answer recorded |
| `question.replied` | `question_replied` | lifecycle | `ToolUsed { mutates: false, edits: false }` → clears `waiting` | request id and per-question choices recorded |
| `question.rejected` | `question_rejected` | lifecycle | `ToolUsed { mutates: false, edits: false }` → clears `waiting` | request id and rejected outcome recorded |

OpenCode registers lazily: a pane can run `opencode` before a session id exists, and the first prompt creates the session. The descriptor sets `registers_lazily`, so the sidebar can synthesize an idle row for a wired-but-unprompted OpenCode pane and bind the later session by cwd. Subagents are bracket-grained: the plugin turns child `session.created` into `SubagentStart` and child `session.idle`/`session.error` into `SubagentStop`; child tool events are skipped so parent state does not move while a child runs.

**Blocking gates use native prompts.** The current bus emits `permission.asked` and `question.asked` after OpenCode has opened an awaited request. RimZ records the corresponding `awaiting_input` observation, and the sidebar's `?` row routes you to OpenCode's own dialog. Question asks retain each question and its labeled options for the ask card and `rimz asks --json`; the joined first-line title remains the compact row detail. When the user responds in OpenCode, reply/rejection events reconcile `waiting` to running, append the choices to the transcript as a native answer, and expire the pending ask. The legacy `permission.ask` hook keeps its neutral `{"status":"ask"}` behavior for releases that still invoke it. The descriptor declares `native_ask_ui: true`; `rimz answer` remains unsupported because no RimZ-to-OpenCode answer transport exists.

**Plan mode derives an approval gate.** `rimz agents opencode-plan` launches `opencode --agent plan`. The plugin remembers the agent selected by `chat.message` and assistant `message.updated`, then stamps `plan_proposed: true` when a root `session.idle` closes a plan-agent turn. RimZ raises a `PlanApproval` waiting row; the next `chat_message` clears it after the user reviews the plan and switches modes with Tab in OpenCode's TUI. `rimz agents opencode-yolo` maps to OpenCode's `--auto`; Ask and Auto retain the provider default because OpenCode has no accept-edits analogue.

**Wired end; partial idle; wired live dollars.** OpenCode's `session.deleted` ends one root directly. The plugin also tracks every root seen through creation and root lifecycle hooks, then turns server-scoped `dispose` into a bounded per-root `session_ended` sweep; pane liveness and the rollup reaper remain the crash backstop. `SessionEnd` is therefore `Wired`. There is no idle `Notification` event; idle attention is reconstructed from turn boundaries, native permission/question prompts, and the stall window. Live dollars are reconciled on `session_idle`/`session_error`: RimZ reads the SQLite spend store, filters rows by `session_id`, sums the current session through the shared `parse_spend` path, and merges that sum into `AgentContext.cost`. The descriptor declares `live$` as `Wired`: the figure lands at each turn boundary rather than from a provider-pushed realtime transport, but that sum is authoritative and visually full to the user, not a half-built surface. Background parking, remote control, and RimZ-driven prompt answering remain unsupported in OpenCode 1.17.20.

**Install.** Install is whole-file ownership. A marked `rimz.ts` is reclaimed byte-for-byte on reinstall; an unmarked file at the path is user-authored and install/preview refuse to overwrite it. Interactive setup compares a marked file byte-for-byte with the source embedded in the running RimZ build and offers a consented refresh when they differ; the older file remains installed until accepted. Uninstall removes only a marked file. The plugin needs `rimz` on `PATH`, or `RIMZ_BIN` set in the OpenCode process environment.

**Binary detection.** OpenCode's installer drops the `opencode` binary in `~/.opencode/bin` and appends that dir to `PATH` through a shell rc, so a non-login environment often runs without it on `PATH`. RimZ's detection (`rimz doctor`/`rimz setup` and the install offer) searches the descriptor's `extra_bin_dirs` — `~/.opencode/bin` — after `PATH` through [`locate_binary`](../../../crates/rimz/src/agents/mod.rs), so an installed OpenCode reads as found (`found at …`) rather than missing.

**Resume.** `opencode --session <session_id>` restores a recorded session; the launching pane sets cwd and the plugin re-emits lifecycle events from the resumed server.

## Context and transcript

The plugin keeps an in-memory token gauge per session from assistant `message.updated` and `message.part.updated` step-finish events, then stamps the latest gauge onto every forwarded lifecycle envelope. OpenCode reports `tokens.input`, `tokens.output`, `tokens.cache.read`, `tokens.cache.write`, and `tokens.total`; RimZ stores those as distinct `fresh_input_tokens`, `cache_read_input_tokens`, `cache_write_input_tokens`, and `output_tokens`, so the context numerator is exact (`input + cache.read + cache.write`) and the card can render the `◍` cache-write column when a model reports it.

[`opencode/transcript.rs`](../../../crates/rimz/src/agents/opencode/transcript.rs) reads the provider-native conversation directly from the shared SQLite store. Every query binds the typed agent-session id, joins `message` metadata to ordered `part` rows, and emits only visible user and assistant text; reasoning, tools, ignored parts, synthetic parts, and other sessions stay out of the normalized stream. `rimz agents history` combines those timestamped messages with the same session-scoped spend rows described below.

Incremental assistant output uses completed assistant-message `rowid` as its cursor. A message remains behind the cursor while OpenCode updates its text part in place, then becomes readable when `time.completed`, `finish`, or `error` marks it terminal; this emits the final accumulated text once instead of losing later updates behind an early part-row cursor. Transcript cursor identity includes both database path and session id, so two agents sharing `opencode.db` retain independent positions. The turn-end hook reads the newest completed assistant message through the same path, which supplies the durable room transcript and a supervised run's final message.

OpenCode messages carry no context-window divisor, so the plugin resolves one from OpenCode's own model catalog. The divisor is the model's max **input** tokens — the gauge counts input-side tokens only (`input + cache.read + cache.write`, never output), so the window it scales against is the input capacity, the uniform context-window meaning across agents (see [agent.md → Enrichment](./model.md#enrichment)). The plugin reads `client.config.providers()` once per server launch — the models.dev catalog the embedded server already holds — builds a `${providerID}/${modelID}` → `Model.limit.input` map (falling back to the total `Model.limit.context` for a model that publishes no separate input cap), and stamps the resolved `context_window` onto the gauge for every model family. The read is best-effort and off the hook critical path: a failed or empty fetch clears the memo so a later event retries, and until one resolves the field is omitted. When the catalog read is unavailable the adapter falls back to a Claude-family local table (`200k`, or `1M` for `[1m]`/`1m` Claude ids — already the input window); every other model then stays unknown and the card renders the visible zero/unknown state per the shared enrichment rules in [model.md](./model.md#enrichment).

The plugin stamps its owning server's `serverUrl` onto every lifecycle envelope, and registration/turn-boundary events spawn `rimz opencode refresh-context` detached with fresh stdio. That helper reads the embedded HTTP server out of band: `GET /global/health` fills `agent_version`, `GET /config/providers` maps the lifecycle model hint to `model_display_name`, and `GET /session/:id` fills the session title. Each read is independent and best-effort; failed reads omit their field, and an empty observation leaves plugin-owned tokens/cost untouched. The helper honors `OPENCODE_SERVER_USERNAME` / `OPENCODE_SERVER_PASSWORD` for basic auth, throttles rich-field reads with the sidecar's `rich_observed_at` stamp, and wakes sidebars only after a write.

This transport is display-only today, and the fields it fetches are also visible inside the plugin. Its product value is that Rust now has a real OpenCode rich-context lane, matching the Codex split between push/local usage and app-server-owned metadata, and the same HTTP channel is the foundation for a later remote-control subsystem. The plugin still sees no provider response headers, so OpenCode has no realtime balance transport; its budget bars come from the out-of-band OAuth usage probe ([Account and balance](#account-and-balance)).

## Account and balance

[`opencode/account.rs`](../../../crates/rimz/src/agents/opencode/account.rs) reads `auth.json` from the OpenCode data dir (`RIMZ_OPENCODE_DATA_DIR` for tests, else `XDG_DATA_HOME/opencode`, else `~/.local/share/opencode`). The credential `type` maps to the account fact OpenCode exposes: `oauth` → metered subscription, `api`/`api_key` → unmetered API key, `wellknown` → unknown metering. The selected credential is the newest used provider from the SQLite message tail when available, else the first OAuth credential, else the first provider by name. The raw provider key rides `sub_provider` so the dashboard can label which provider OpenCode used; supported OAuth credentials also carry a normalized `openai` or `anthropic` quota scope, while API-key, wellknown, and unsupported providers carry no quota scope.

Balance comes from the OAuth usage probe ([`oauth_usage.rs`](../../../crates/rimz/src/agents/opencode/oauth_usage.rs)) — OpenCode's only window source, since the plugin exposes no realtime headers. The probe reads `auth.json` through the same data-dir ladder as the account read, selects the active credential by the newest used provider (else the first OAuth entry), and delegates by backing provider: `anthropic` reuses Claude's OAuth usage fetcher, `openai`/`openai-codex` reuse Codex's, and any other provider returns silently with nothing to fetch. Preflight and the delegated result derive the same normalized scope and non-secret owner from that credential, preferring an OpenAI `accountId` and otherwise hashing the refresh token or access-token fallback. Authoritative 5h/7d windows and extra credits cache under `opencode`, distinct from every other kind's entry; OpenAI OAuth gains the conceptual lifted 5h row when an authoritative response reports only 7d, while Anthropic and unsupported scopes do not. The producer keeps them current with the uniform `rimz agents refresh-usage --kind opencode` helper on `OAUTH_USAGE_TTL`. An API-key or `wellknown` credential has no OAuth token, so the probe finds nothing and the panel shows account identity and spend without budget bars. Provider retry/status events remain uncontracted enrichment and are not part of the account probe.

## Cost

[`opencode/spend.rs`](../../../crates/rimz/src/agents/opencode/spend.rs) treats the SQLite database as the transcript file for the shared spend pass. Discovery returns `opencode.db` when present, else the first sorted `opencode-<channel>.db` in each data dir. The parser opens SQLite read-only with `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_URI`; failures produce an empty parse and keep the pass best-effort.

The cursor is SQLite `rowid`, stored in `SpendCursor.offset`, so incremental parses read `message` rows with `rowid > offset`. Each row's `data` JSON must carry `tokens`, `modelID`, and `providerID`. Token, timestamp, and cost fields accept JSON numbers or numeric strings, and malformed nested token/cache/time values become absent fields instead of dropping the whole row. Positive `cost` is used verbatim; zero cost is priced from tokens through `PriceBook`, including cache-read and cache-write rates. Missing token splits drop the row unless `tokens.total` is present, in which case the total is attributed to output as a conservative fallback. Unknown priced models keep their tokens and session with zero dollars, are recorded for the existing pricing-refresh chase, and recover dollars on a later cold reparse.

OpenCode's whole database is one spending file, so the parser stamps each row with the table's `session_id`; `SpendWindow.sessions` counts those ids rather than collapsing the DB to one thread. The live-card dollar supplement uses that same stamped `session_id` to select only the current session from the multi-session database.
