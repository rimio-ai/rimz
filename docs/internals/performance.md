# Performance

> Mechanisms live in their own docs — this one is the performance model over them. The render loop and snapshot are detailed in [sidebar.md](./sidebar.md), durability and wakeups in [ledger.md](./ledger.md), the `list-panes` round-trip in [multiplexers.md](./multiplexers.md). This doc says where the milliseconds go, which optimizations bound them, and the rules the next change follows.

Perceived latency lives on one thread: the sidebar's render/input loop. Correctness lives in the ledger, off that thread entirely. So every performance change has one job — keep the render thread free — and one guardrail — never trade a correctness invariant for it. The UI may show stale-by-a-tick data; it may never block, drop a keystroke, or freeze the spinner.

## The hot path

`rimz sidebar serve` runs a single event loop that blocks only in `recv` on its wakeup socket (`app::serve`). Three things drive it: the animation tick (advance the spinner on the current snapshot), input (apply in place), and a finished background fetch (fold the new snapshot). Nothing on this thread forks a subprocess or fsyncs.

The expensive work is offloaded:

- The snapshot fetch happens on a background **fetch worker** thread and runs at two speeds. Every cycle first folds the event-fresh ledger rollup over the published pane frame entirely **in process** (`read_published_snapshot` — no fork, no `list-panes`, no git) and posts it, so a status flip or a cost update paints in single-digit milliseconds. The forked `rimz sidebar snapshot` child — workspace resolve, `list-panes`, git, spend — runs as the cycle's second, reconciling post only when its caches are due: on the producer it is gated to the data tick, so a ledger-delta storm paints per delta but forks at most once per tick. The worker posts a `snapshot` wakeup datagram per post, so the loop folds each without polling.
- A jump runs on a **detached thread**: the native sidebar focuses the snapshot-bound pane in process (`rimz::mux::backend_for(..).focus_pane`), which still forks the mux client (`zellij action focus-pane-id` / the tmux equivalent) but skips the `rimz pane focus` child and its per-click `list-panes` re-validation. The highlight is already redrawn, so the jump is fire-and-forget; a pane recycled since the snapshot self-corrects on the next refresh.

Two kinds of update reach the loop: a **push** (a `ledger_delta` datagram after any ledger write, or a context-sidecar write) collapses to one refetch; a **poll** (the ~1s tick) is the backstop that catches drift no write announced — pane and git changes the multiplexer never signals. The render layer is a fixed-timestep frame loop: an event folds into the cached model and marks the frame dirty, and the loop paints at most once per `ANIMATION_FRAME` (100ms) boundary for dirty or fast-motion frames — coalescing every change that landed mid-frame into one paint — while slow cosmetic motion (`?`/`!` breath, empty-idle dots) uses a 300ms cadence and a fully idle room relaxes to the backstop. It never forks a fetch, so the render layer and the data layer run on independent cadences; input is the one synchronous exception, painting on the keystroke so a click or key feels instant.

## Principles

The rules every performance change here follows. They are ordered: an earlier rule outranks a later one when they conflict.

1. **The render thread never blocks.** No subprocess fork, no fsync, no synchronous `list-panes` on the loop. Offload to a worker and wake the loop when it finishes. A single in-flight fetch is the unit of work; the loop stays interactive while it runs.
2. **Decouple the frame from the fetch.** What the user perceives as responsiveness — the spinner advancing, the cursor holding steady, a click highlighting — is a redraw from the *cached* snapshot, not a data refresh. The render layer is a fixed-timestep loop: an event folds into the cached model and marks the frame dirty, and the loop paints at most once per `ANIMATION_FRAME` boundary (in-process, no fork), coalescing every change that landed mid-frame into one paint and gated on dirty-or-animating so an idle frame is a bare timer wake with no recompose. Dirty frames and fast work animation run at 100ms; slow cosmetic attention/loading motion runs at 300ms because its visible state is already held for several base phases; a dirty fold clamps back to the 100ms budget so freshness never waits on the cosmetic cadence. Input is the one synchronous exception — a keypress or click paints immediately so it feels instant rather than waiting up to a frame. Data arrives on its own slower, event-driven cadence and folds in when ready. The two never share a clock: a smoothness change tightens the frame interval and costs only in-process paints, while a freshness change rides the push/backstop data layer (principle 3). Never invert it — letting the frame drag a `list-panes`+git fetch behind it (the removed `ACTIVE_REFRESH`, which refetched every 500ms purely to keep a spinning agent's `$`/tokens current) spends a subprocess fork per frame to move a spinner, and on Zellij the periodic `list-panes` action even resets unrelated panes' cursor blink. The cost it was buying is already covered by the statusline push (principle 3).
3. **Push over poll.** A change that a writer knows about posts a wakeup; the loop folds it within one wakeup. Polling is the missed-wakeup backstop, never the primary channel. When a datasource feeds the UI but is not the ledger (the statusline sidecar), give it a wakeup of its own rather than waiting for the next tick.
4. **Cache the disposable; fsync the durable.** Crash-durability is for the truth alone: the event log (per-record `sync_data` — the correctness contract) and the feed files (decision CAS state). Everything derived — the ledger rollup caches (`latest.json`, `rollup.json`), the snapshot cache, diff-stats cache, agent-context sidecar — is rebuilt from truth on the next read, so it renames atomically *without* fsync (`write_temp_then_rename_cache`). A torn read is impossible either way; only "survives a power cut" is traded, and for a rebuildable file that buys nothing while costing two fsyncs on a path the UI (or a hook) waits on.
5. **Single-flight, then coalesce.** One outstanding fetch at a time. A burst of deltas collapses to one fetch (`in_flight`); a delta that races an in-flight fetch defers exactly one follow-up (`pending_refetch`), never a queue, preserving the strongest freshness request. The same lock+poll election (`ledger::single_flight`) sits on both shared external reads so concurrent sidebars across a fleet share one producer instead of stampeding: the snapshot cache producer (`snapshot.lock`, `SNAPSHOT_CACHE_TTL` 750ms) for the ledger rollup + `list-panes`, and the per-worktree git probes (`diff-stats.lock`, `DIFF_STATS_TTL` 5s) — one sidebar forks git for the fleet while the rest read its `diff-stats.json` write.
6. **Pay the round-trip once per window.** `list-panes` and the git probes are the snapshot's cost; bound them with a short TTL cache and reuse the last good result. A degraded read (an empty body, a live pane missing its command/cwd) backfills the missing fields per pane id from the last good read rather than flashing a corrupt frame, and the renderer holds the last good frame rather than commit a regression while the pane set is unchanged — see [sidebar.md → Presence model](./sidebar.md#presence-model).
7. **Cheapest correct read.** The snapshot catch-up is O(delta bytes) from the persisted fold base on the common path, O(active-events + items) at worst, never O(history); archives are touched only at rotation. Skip work that cannot matter — an idle room with no agents skips both sidecar directory scans entirely.
8. **One producer per workspace, one renderer per tab.** The fetch cost above is per *production*, so production must stay at one while every tab keeps its own renderer (the documented per-tab model — see [sidebar.md → Launch model](./sidebar.md#launch-model)). The eldest live instance is elected the producer (UUIDv7 ids sort by birth, so the lowest id wins; `elder_sidebar_present`); it forks `list-panes`/git and publishes the shared cache — and even on the producer the fork is the cycle's *second* speed: every wakeup first paints from the same in-process published-frame fold consumers use, and the fork runs only when forced or when the frame outlived one data tick (`run_fetch_cycle` → `produce_this_cycle`). Every younger renderer is a consumer: it reads that published pane frame **in process** (`rimz::sidebar::snapshot::read_published_snapshot`, folding its own-pane exclusion over the event-fresh `latest.json` rollup) — no subprocess fork, no `list-panes`/git, and it never exits, so a per-tab pane never goes dark. This bounds the mux server to one round-trip per workspace *and* the fork count to at most one per workspace per tick: production, not renderer count, is capped, so even a stray duplicate that slips the launch lock costs one in-process cache read, not a second `list-panes` or even a second process spawn. A launch lock still serializes concurrent attaches so they don't each spawn a daemon (`launch_sidebar_if_needed`), and the orphan sweep reaps a SIGKILLed instance. Trust the heartbeat TTL exactly as the launch gate does: a just-SIGKILLed elder is honoured for at most one TTL before the next-eldest renderer takes over production. The `--no-produce` CLI path stays the consumer read for an external caller (the plugin rail), sharing `read_published_snapshot`. Staleness recovery belongs to the election, not the consumers: a dead, wedged, or protocol-split elder drops out of the eldest scan within one heartbeat TTL (stale or version-mismatched heartbeats are never honoured), the next-eldest renderer *becomes* the producer on its next cycle, and every other consumer keeps folding the held pane frame with the event-fresh rollup — status stays live the whole handoff, only pane presence ages by a few seconds. A consumer never produces on staleness alone (`produce_this_cycle`): the old per-consumer self-heal raced its single-flight loser wait (~200ms) against the `list-panes` floor (200–680ms), so every loser timed out into its own uncached produce — an N-way fork storm on exactly the tick the room was already degraded.

### Latency budgets

The two end-to-end paths the cost map rolls up into, with the dominant term named so a change that regresses one is visible at review time.

- **Keypress → pixel: one in-process paint.** Input applies synchronously and marks the frame dirty; a jump hands its target pane to the mux focus fork on a detached thread and paints nothing. Nothing on this path takes a lock, forks, or reads the ledger.
- **Write → pixel: bounded by the 100ms frame bucket.** Commit under the flock (1–3 fsyncs, single-digit ms) → wakeup datagram (µs) → consumer folds the published frame in-process (O(1) cached, O(delta) on a race) → next dirty frame paints. The frame bucket dominates; everything upstream of it is already an order of magnitude smaller.

## Deferred candidates

Real wins the pass identified but did not take, because each changes a contract or crosses a backend-parity boundary and deserves its own change with tests. Ranked by expected payoff.

1. **Event-triggered pane updates on Zellij.** The tmux half is taken (see the 2026-06 row below): the elder sidebar streams control-mode topology nudges and pulls fresh panes per event, poll as backstop. Zellij still needs application-state pane manifests, which only its plugin API exposes cleanly — the CLI `subscribe` stream is pane-content oriented and not a sidebar presence source. This remains the rail's path (see [multiplexers.md](./multiplexers.md)).
2. **Opt-in async / group-commit event-log fsync.** The per-record `sync_data` is the durability floor; a workspace that tolerates bounded event loss could batch it for throughput. Risk: correctness — this stays opt-in and documented, never the default (principle 4). The 2026-06 pass reaffirmed it: with the snapshot publish off the lock, the lifecycle critical section is already a single fsync, so the residual win is small. The 2026-06 ledger review deferred it again with an explicit gate: take it only when profiling on real hardware shows the lifecycle flock tail surfacing in user-perceived latency — it is a throughput win on a path the user never sees.
3. **Dir-mtime-gated transcript discovery.** The fleet spending walk still readdirs every provider's session tree per refresh to discover files. With the parse now O(appended bytes), the walk is the residual cost — warm readdirs measure in low single-digit ms at realistic fleet sizes, producer-side, once per data tick, so caching the directory set behind dir mtimes buys little for the bookkeeping it adds. Revisit if fleet history outgrows it.

Evaluated and **rejected** by the 2026-06 ledger review — recorded so the next pass does not re-litigate them:

- **Lock-free `O_APPEND` event appends.** The recovery model assumes the flock makes the log single-writer-at-a-time, so only the trailing frame can be torn; concurrent appenders' independent dirty pages can be written back out of order, and a crash then leaves a zeroed *middle* frame — which rebuild correctly treats as a hard error rather than silently dropping the events behind it. Making it safe needs per-frame magic + checksum resync (a new on-disk format) plus a rotation-epoch re-stat, all to shave a lock tail the user cannot perceive. See [ledger.md](./ledger.md#durable-state).
- **Binary snapshot format.** The `(path, mtime, len)` parse cache already removes the re-parse on delta storms; the residual single parse per actual change is sub-frame-bucket, and JSON keeps `rimz sidebar snapshot --json` inspectable.
- **Caching the wakeup heartbeat scan.** N is live sidebars (one per tab), the reads are page-cache-hot, and the whole fanout already runs after the lock releases, below the write's fsync floor. A cache would have to live cross-process and re-validate exactly what the 5s TTL + re-stat already validate.
- **Eliminating the producer's snapshot fork.** Consumers already read the published frame in-process; the producer's residual `fork+exec` (~10ms) is noise against the 200ms+ `list-panes` floor it exists to pay, and moving the producer in-process would drag write-side machinery into the sidebar's import graph.

*Taken:* the **persistent Codex app-server connection** — a per-session broker ([codex::broker](./transcript.md#appendix--codex)) holds one warm, already-handshaked `codex app-server` and serves it over a unix socket, so each datapoint skips the cold-spawn handshake. Lifecycle and ownership (the flagged risk) live in the broker: it runs as a pane in the `rimzd` daemon tab, respawns a dead child once, and always leaves a cold-spawn fallback so enrichment never depends on it.

*Taken (2026-06):* **the `latest.json` serialize moved off the workspace-lock critical section** — the former #1 candidate. The blocker it named (the mtime staleness contract) was retired by the `(generation, offset)` freshness stamp; the publish is single-flighted, cache-class, and re-folds to the live log end after winning. See the 2026-06 pass table above.

*Taken (2026-06, sidebar quality pass):* **DRY the status and hit-test helpers** — the former #3 candidate. The attention predicate folds to `AgentStatus::{is_attention,is_actionable}` in `feed.rs` (the two intentional flavors — the ranking class spans the parked `RateLimited`, the actionable triage/heat subset does not — both now one authority every dispatch site delegates to), and the mouse hit-test geometry is locked to the single `compose_lines`-built `line_map`, read only by `app::selection::row_index_at_screen_position`. Quality, no throughput change.

### The election, assessed

Is the eldest-UUIDv7 + flock + staleness design robust enough? **Yes — the flock is the real election; the eldest rule is a "don't even try" optimization; the TTL carries liveness.**

- **The flock is the actual election.** Correctness never depends on who believes it is the elder: every shared external read single-flights through `ledger::single_flight::coalesce` (`snapshot.lock`, `diff-stats.lock`, `accounts` probe), so two renderers that both produce still collapse to one `list-panes` per TTL window. The system is safe with zero, one, or many self-declared producers.
- **The eldest rule is the efficiency layer.** UUIDv7 ids sort by birth, so `elder_sidebar_present` lets every younger renderer skip the fork before ever contending the lock — N tabs become one producer plus N−1 in-process cache reads. It is justified precisely because it is *only* an optimization: a wrong pick is bounded by the flock and healed by the TTL.
- **Takeover latency, as the user perceives it.** On a producer death the next-eldest's scan flips within one heartbeat TTL (5s) and it produces on its next cycle (~+1 tick) — fresh panes in well under ten seconds, while **status flows the entire time** through the rollup fast lane, which needs no producer. A window open/close lagging a few seconds during a rare producer crash sits comfortably inside principle 1's staleness tolerance.
- **The one rough edge is fixed above:** the consumer staleness path used to duplicate the election's job by letting everyone produce; delegating recovery back to the next-eldest removed the storm and made "exactly one producer at any moment" structural.

## Adding a performance change

1. Name the thread the cost lands on. If it is the render/input loop, the change is wrong until the work moves off it.
2. Prefer a push (a wakeup the writer already posts) over shortening a poll interval. A tighter poll burns cycles in the idle case; a wakeup costs nothing until something changes.
3. Decide durability explicitly: durable state fsyncs, a next-tick-rebuilt cache does not. Do not reach for `write_temp_then_rename` on a disposable file.
4. Keep single-flight: a new fetch trigger routes through `request_fetch`, never a bare spawn, so it coalesces with the rest.
5. Measure the idle case too — an optimization that speeds the busy path by adding idle work is usually a loss; the fleet is idle most of the time.
6. The gate is the proof. `cargo xtask ci` stays green — including the invariant that the sidebar never imports a ledger-writer module and never forks `pane capture`/`send` on the render path.

## Optimizing perceived response time

Responsiveness is what the user feels, not what the profiler measures: a frame that paints now with slightly-stale data beats a fresh frame that arrives late. The UI/UX levers, in the order to reach for them.

1. **Acknowledge before you finish — except where one source of truth is worth the wait.** Where the local intent *is* the truth, redraw it the instant the input lands: an arrow-key browse pick and the help overlay paint synchronously in `app::apply_input`, so the keypress feels instant while the data layer stays untouched. The jump is the deliberate counter-example: it fires the focus command on a detached thread (`app::spawn_pane_focus`), changes no local state, and lets the **derived** selection — the view's active pane, re-queried every fold and held by **pane identity** (`UiState::selected_pane`, `app::reconcile_selection`) — catch up on the next fold. Trading the optimistic echo away buys a model with no reconcile protocol: there is no echo to confirm or expire, so a stale frame can never roll the highlight back. Reach for the optimistic redraw before trying to make an action faster; reach for the derived-only model when the echo would need its own protocol to stay honest.
2. **Animate on wall-clock, never on I/O.** The spinner and cursor advance from `wall_clock_phase` on a fixed frame interval, independent of whether a fetch is in flight. Motion that stalls when data is slow reads as hung even when nothing is wrong; a steady 100ms tick from cache reads as alive. Drive any future animation off the same monotonic base so a refetch or delta can never reset its phase.
3. **Tune smoothness and freshness on separate dials.** A smoother UI shortens the frame interval — cheap, in-process paints (principle 2). Fresher data adds a push, not a tighter poll (principle 3). Conflating the two is how a cosmetic tweak (a faster spinner) becomes a CPU regression (a fetch per frame) — the `ACTIVE_REFRESH` mistake this pass removed. If a "make it feel snappier" request lands, ask first whether it is a frame-rate problem or a data-latency problem; they are fixed in different layers.
4. **Keep session-wide effects off the frame path.** A redraw writes only to the sidebar's own pane and is safe at any rate. A mux *action* — `list-panes`, a `pipe` broadcast — touches the whole session and can reset an unrelated pane's cursor blink, so it belongs on the slow, event-driven data layer, never on the animation tick. When perceived smoothness and a session-wide side effect pull in opposite directions, the side effect moves to a slower cadence; the frame does not.
