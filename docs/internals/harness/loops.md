# Loop scheduling

This page is for a contributor changing the loop scheduler (`crates/rimz/src/harness/schedule/`), a wait, a signal, a recovery helper, or the assist log. It covers where tasks live, who keeps time, what one fire does, how signals and waits reach the same machinery, the start gates workflow agent starts share, and the recovery the host runs. [fleet.md](./fleet.md) maps the area, and [workflow.md](./workflow.md) owns the run a command fire starts. Users read the [loops guide](../../guide/loops.md) and the references [cli/loop.md](../../reference/cli/loop.md), [cli/wait.md](../../reference/cli/wait.md), and [cli/events.md](../../reference/cli/events.md).

## What the scheduler does

`rimz loop` decides when a command runs. A fire either delivers a prompt to an agent that is already running (a `wait` row, which only `rimz wait` and team role bindings write) or starts a workflow run through `harness::workflow::create` whose one `test` check, named `command`, runs the row's argv under its `timeout` ([The compiled graph](#the-compiled-graph)). The trigger is a clock, a signal selector, a watch spec, or a state condition. `rimz wait` is the agent-facing front end over the same task rows, for delays, one-shot clock instants, once conditions, and watches.

There is no RimZ scheduler daemon. The room host already owns shared data work ([state.md § The room data plane](../sidebar/state.md#the-room-data-plane)), and the host keeps time for loop tasks on its ordinary data tick. For schedules that must run with the room closed, a user can install one OS timer that launches a one-off `rimz loop tick` and exits. It yields every root whose room is open ([The external tick](#the-external-tick)).

Four rules follow from having no daemon, and they explain most of the module.

**Arming is not firing.** A task the host has never seen is stamped with the current time and does not fire. A room opened hours late never replays the occurrences it missed. The one exception is a `fire-at` row already past its instant, which fires on first sight ([Host firing](#host-firing)).

**A timekeeper fires each occurrence at most once.** It writes the fire stamp before it spawns the runner, so a hot tick cannot spawn the same occurrence twice, and a per-task advisory run lock serializes the fire helpers. The run lock covers admission only: once `create` returns it is released, and workflow admission (`engine::refuse_existing`) keeps two runs of a task from overlapping ([One fire](#one-fire)). No lock spans the read, plan, and write of the stamp, so the guarantee rests on one timekeeper per root: a room's single host, or the external tick for a root with no fresh heartbeat ([The external tick](#the-external-tick) names the one window where both act). A start that fails keeps its stamp and the failure is recorded instead: a periodic occurrence is spent and the next tick does not retry it, while a `fire-at` row, which has no later occurrence, is dispatched again once its runner counts as lost ([Host firing](#host-firing)), as is a fired one-shot condition row that still reads true ([Condition planning](#condition-planning)).

**An event fires in the process that produced it.** A clock needs a timekeeper and an event does not: whoever emits a signal resolves the subscribers and spawns their runs itself. Signal and watch triggers therefore work with no room open and never touch `lanes/loop-fire.json`. A signal is never replayed to later subscriptions, but an existing busy task can retain its trigger through its overlap policy ([The signal vocabulary](#the-signal-vocabulary)).

**A fire that reaches a decision leaves at most one history row.** A fire that is gated, skipped, overlapped, deferred, expired, delivered, or errored records one `LoopRunRecord` itself, and that log is the durable trace of what automation did. A fire that starts a workflow run writes no row at launch: the run's report is its row, and a quiet run writes none and goes to the task's quiet summary instead ([Run reports and quiet runs](#run-reports-and-quiet-runs)). A deferred trigger gets a separate terminal row when served, and absorbed triggers are counted on that run. A fire whose helper never started gets a `start failed` row from the launch site, in-process.

Some exits write nothing:

- the runner's early returns before `TaskFire` takes over, listed under [The external tick](#the-external-tick), where a systemd tick reads them as `start failed`
- a scheduled fire of a task that remembers its checkout whose launch memory already holds a run ([Launch memory](#launch-memory)), which can occur with the run lock already held
- a drained trigger that goes back to wait for the run still holding its scope (`TaskFirePlan::Waiting`)
- a drainer that finds a held lock, an empty backlog, an ineligible task, or a task no longer live after claiming a trigger ([Waiting-trigger backlog](#waiting-trigger-backlog))
- a fire that starts a workflow run, whose run's report is the fire's one row, and a quiet run, which writes none ([Run reports and quiet runs](#run-reports-and-quiet-runs))

Failures outside the CLI's terminal-error path can also leave a lock tenure unrecorded, for example a failed backlog save after acquiring the lock in `TaskFire::take_backlog`. Ordinary preparation and effect errors go through `record_task_error` instead. Refused fires of an unrecorded holder are spent in `rimz loop show` once later logged evidence of another tenure of the same lock proves that holder gone: they take no row, add no count, and take no part in the verdict's warning.

## The task

A task is a name, one action, and one trigger. `TaskAction::from_entry` derives the action from the persisted entry.

| Action | Entry fields | What a fire does |
| --- | --- | --- |
| `Shell` | `kind = "shell"` (or no `kind`), `args = [<argv>...]`, `timeout` | starts a run of the one-check graph that execs the argv in the fire's checkout ([The compiled graph](#the-compiled-graph)) |
| `Launch` | `kind = "workflow" \| "agent" \| "team"`, `target`, `args`, optional `worktree` | spawns the launch child `rimz workflow run <target>`, `rimz agents <target>` or `rimz teams launch <target>` with `-w <worktree>` after the target when the row names one and `args` unchanged after that (`TaskLaunch::argv`), in the fire's checkout (`schedule/launch.rs`), and records its outcome by kind ([reference](../../reference/cli/loop.md#what-a-task-launches)) |
| `Deliver` | `wait = { kind, session, handle }` | sends the prompt to one live agent, pinned by its launch id, through the [message](./messaging.md) path ([Waits](#waits)) |

A row's `worktree` (from `loop add -w`, covered by the trust hash through `ExecutableTask`) places every fire. `loop add` stores it only when the launch's arguments do not already name the same tree (`cli/loop_launch.rs`), so one name lives in one place; a hand-edited row carrying both passes `-w` twice and the launch child refuses the repeat, a strike each fire. `from_entry` refuses it beside `each-worktree`, on a `wait` row, and when it is empty or not a name `loop add -w` accepts (`worktree::parse_requested_name`). A workflow task's hand-started-run overlap reads the row's tree when it has one (`Fire::hand_started_run` in `schedule/runner/launch.rs`). A shell fire resolves the tree itself before it opens the fire (`Fire::prepare_row_tree` in `schedule/runner.rs`), after the admission an agent launch's `-w` takes (a readable core config, then `harness::lanes::admit_launch_worktree_name`), through `worktree::resolve_launch_checkout` with the configured base, emitting `worktree.created` and stamping the fire on the tree's marker when it made one, and runs only its command there (`Fire::fire_dir`): the fire mark, the condition scope, the run lock and the history stay keyed to `TaskEntry::run_dir()`. An unowned directory of that name fails the fire with the resolver's reason, since a fire has no terminal to ask on. A shell fire takes no start-throttle turn, so no disk floor reads that tree; a workflow fire's agent steps measure their own run's checkout.

`TaskAction::from_entry` refuses the rest with a `TaskActionErr`. A launch row (`kind` or `args`) and `wait` conflict, and one of them is required. A row that still carries the old `command` key, or the retired `fresh-worktree` key, is refused alone with the re-add text. A shell row requires `timeout`; a workflow, agent or team row requires `target` and refuses `timeout`. Every launch row refuses `prompt`, which belongs to a delivery row. `overlap` is refused on a wait delivery, an `each-worktree` task, and any one-shot ([Waiting-trigger backlog](#waiting-trigger-backlog)); `overlap = "allow"` is also refused on a shell, workflow or team row and beside `once-per-checkout = true` (`TaskAction::refuse_allow`), each with its own reason; and `overlap-limit` requires `overlap = "queue"` and a value of at least 1. An `each-worktree` row that does not repeat is refused with `TaskActionErr::OneShotFanOut`, since its first fire would remove the task after one checkout. `TaskEntry` denies unknown fields, so a row carrying any key outside it, or a key of the wrong type, decodes to a `RefusedRow` that keeps the row as stored: `from_entry` refuses that row alone, `rimz loop list` shows it under NEEDS YOU as `invalid: <message>`, and a rewrite of its file writes it back unchanged.

A manual `rimz workflow restart <run>` restarts only that run's current step, not the loop task.

`TaskShape::compile` compiles each persisted row into an action result and a timing result independently. A row with a valid action and a malformed schedule stays visible and can be fired by hand, while scheduled firing skips it.

## Where tasks live

Three sources back the catalog.

| Source | File | Holds |
| --- | --- | --- |
| `Config` | `~/.rimz/loop.toml` | per-machine automation, like a crontab. Never inherited by a clone |
| `Project` | `<root>/.rimz/config.toml` under `[tasks.*]` | shared automation that travels with the repository. Inert until trusted and enabled on this machine |
| `Instance` | `~/.rimz/ws/<workspace-dir>/records/loop-instances.json` | RimZ-owned runtime rows: one-shots, rows with a `deadline`, signal and condition rows without `repeat`, and every session-pinned delivery, including recurring clocks and standing signals |

The instance store keeps runtime churn out of user config. An agent that arms `rimz wait --in 30m` writes an instance row, not `loop.toml`, and the row retires itself after it fires. `TaskCatalog::load(Some(root))` reads that workspace's instances and `load(None)` reads machine tasks only. Wait rows found in `loop.toml` stay `Config` rows, and machine-scope `rimz gc --all` reaps them.

The machine loader requires an absolute `root` after expanding `~` and `~/` against `HOME` (`/` when unset), without reading the cwd or filesystem. Rows with a missing, empty, or relative root leave `LoopConfig.tasks` for its serde-skipped `skipped_tasks`. Strict and lenient whole-config loads retain one warning per skipped row in `ConfigNotices.skipped_loop_tasks`, and room judgment records it under `loop.tasks.<name>` for the sidebar and doctor. The catalog keeps skipped machine rows outside its visible and runnable maps, retaining their task records and a name-only remove/rename fallback. A same-named visible row still wins. A skipped name remains taken for rename.

Instance mutation requires a readable room record. Without one, `crates/rimz/src/harness/schedule/instances.rs::mutate` treats removal, rename, and session retirement as empty no-ops before taking a lock. Inserts and delivery inserts refuse.

A project task cannot make machine-local claims, so loading (`crates/rimz/src/config/effective.rs::reject_project_task_state_fields`) rejects any of `root`, `dir`, `wait`, `wait-meta`, `deadline`, `watch`, `when`, `for`, `each-worktree`, `loop-task`, and `booked-by` that is present, whatever its value, so `each-worktree = false` refuses too. Conditions are machine-local, so none of their fields enters the project trust hash. Project rows must repeat (`every`, `cron`, or `signal` with `repeat = true`), because a one-shot would have to delete itself from a trust-hashed file.

The [booker record](../../reference/cli/loop.md#where-tasks-are-stored) is built once, when the task is added. `crates/rimz/src/cli/loop_cmd/add.rs::booking_chain` opens the task room's store and resolves the caller against its Audit rows, so a launcher that has ended still reads, and `crates/rimz/src/harness/ancestry.rs::booking_chain` walks `launched_by`, then the subagent parent, and splices in the chain a loop fire stamped on a row (`AgentState::loop_booked_by`), ending the walk there. That chain travels with the launch rather than being looked up by task name, so a fired row that was since consumed, removed, or re-added by another agent still yields the chain of the booking that fired: `crates/rimz/src/harness/schedule/runner.rs` freezes the task's `booked-by` into the run record's fire (`RunFire::booked_by`). The run's command check gets that chain as `RIMZ_LOOP_BOOKED_BY` beside `RIMZ_LOOP_TASK` (`crates/rimz/src/harness/workflow/script.rs`), and an agent the command launches takes it from there (`crates/rimz/src/harness/loop_task.rs::read_fire_env`), since such a launch runs with no agent identity and so has no `launched_by` either. The chain is recorded rather than walked when read because ended rows leave the runtime snapshot the sidebar folds. The stamp is set just before `TaskCatalog::replace_machine`, after the workspace and the action are chosen, and every read failure counts as no caller, so it cannot fail the add or move it. A caller from another room is not among the task room's rows and records nothing.

`rimz loop add` writes `root` as the project root and never writes `dir` (`crates/rimz/src/cli/loop_cmd/add.rs::build_task_entry`), so a command runs at the project root. Added from a linked worktree, it prints a note naming the project root. A stored `dir`, which waits keep writing from the arming checkout (`arm::build_entry`), is the condition and history scope (`TaskEntry::run_dir`).

A project task runs commands on whoever pulls it, so it enters the project trust hash ([trust.md](./trust.md)) and needs two approvals. Trust approves the config contents. The machine-local enablement record ([History, strikes, and arming](#history-strikes-and-arming)) approves that task for unattended execution here. `rimz loop add --project` writes an enabled record for its author, and a clone has no record, so the task starts disabled.

### Visible and runnable precedence

The catalog resolves two maps, and the split keeps an untrusted project task honest.

The visible map is what `rimz loop list` shows. A project definition replaces a same-named instance or machine row regardless of trust, rendered under NEEDS YOU as `blocked · project untrusted` or `blocked · project stale`, so the list shows the definition that would win.

The runnable map is what firing reads. A trusted project row replaces a same-named base row. An untrusted one never does, so the base row keeps running. The base is instance rows overlaid by machine rows only within the same resolved root. A machine row rooted elsewhere never displaces a room's same-named instance row.

On durable machine replacement, `config_edit::set_entry` compares the existing and incoming `TaskEntry::resolved_root()` values in the file being edited and refuses a different root, before writing or clearing any instance or task-record state. A missing, empty, or relative existing root takes the remove-first refusal. The root comparison comes first, so re-adding from a directory that the relative root resolves to can still replace it with an absolute root.

An untrusted project row with no same-named base row enters the runnable map, so the refusal happens where tasks execute. Three places drop it. `fire::runnable_tasks_for`, which the host's clock pass and `probe::probe_demand` call, drops every untrusted project row. `fire_signal_with_wait` loads `workspace_runnable_tasks` and drops untrusted rows itself (`is_untrusted`). The trust gate in `rimz loop run` refuses one, except that a manual fire on a terminal offers an inline grant. During the untrusted window the user sees the project task, the machine task keeps running, and the two never both fire.

## Triggers

`parse_trigger` compiles the timing half of a row into one `Trigger`.

| Trigger | Entry | Fired by |
| --- | --- | --- |
| `Schedule` | `every`, `cron`, or `fire-at` | the host tick or the external tick, when `due` says so |
| `Signal` | `signal = "<selector>"`, optional `match = { k = "v" }` | the process that emits a matching signal |
| `Watch` | `watch` as a command string or a PID, check, or file spec | the detached `rimz wait watch` process, or the host's watch-lost rule |
| `Condition` | `when = ["team.stage=Done", "ci=passed"]`, optional `for = "30m"`. `provider = "claude"` when a term reads a window | the clock planner, once per true period, or once total with `once` |

A `SignalSelector` is `Exact(SignalName)` or `Family(String)`, parsed from `a.b` or `a.*` and serialized back to the same string. `*`, `a.b.*`, and `a*` are rejected, and emission refuses wildcards outright.

`parse_trigger` rejects the shapes that cannot mean anything, as `ScheduleErr` variants. The selector errors (`BlankMatch`, `BadSignal`, `ObsoleteCiSignal`) are `crates/rimz/src/harness/signal.rs::SelectorErr` variants wrapped in `ScheduleErr::Selector`:

| Error | Shape |
| --- | --- |
| `TriggerConflict` | two trigger families on one row, or `when` with a `deadline` |
| `MatchWithoutSignal` | `match` with no `signal` |
| `RepeatWithoutSignal` | `repeat` with neither `signal` nor `when` |
| `ForWithoutWhen` | `for` with no `when` |
| `BadFor` | a `for` that is not a positive `s`/`m`/`h`/`d` duration |
| `BadWhen` | a `when` clause the condition grammar refuses |
| `WindowWithoutProvider` | a `window.<span>.left` term on a row with no `provider` |
| `BlankMatch` | a match value empty after trimming. The error names the task and key |
| `BadSignal` | a selector that does not parse |
| `BadWatch` | an empty watched command or check command, an empty file path, or an empty `grep` pattern |
| `BadCheckWatch` | an invalid or zero check interval, or check polarity `any` |
| `ObsoleteCiSignal` | `ci.finished`, or a `conclusion` match on a `ci` selector. The message names `ci.passed` and `ci.failed` |

The clock shapes have their own variants from `parse_schedule`: `NoTime`, `TimeConflict`, `BadEvery`, and the cron errors `BadCron`, `BadCronToken`, `UnsupportedCron`, and `CronNeverFires`. `BadOnceAt` and `PastOnceAt` come from `schedule::resolve_once_at`, which resolves `--at` when a task is added, never from a stored row.

A `Watch` row is always one-shot, and a `signal` or `when` row is one-shot unless it sets `repeat = true` or carries `team`: team arming writes only standing bindings, so `schedule::repeats` reads a binding as standing whether or not an older RimZ stored `repeat` on it. `ephemeral_lifetime` names the rows that retire themselves: any row that does not repeat (`every`, `cron`, or `signal` or `when` with `repeat` or `team`), plus any row carrying a `deadline`, a `watch` spec, or a `fire-at` instant. `TaskCatalog::replace_machine` stores a row that `ephemeral_lifetime` names, or a row with a `wait` target, in the room's instance store and every other machine row in `~/.rimz/loop.toml` ([Where tasks live](#where-tasks-live)), while `TaskCatalog::replace_project` keeps a project row in `<root>/.rimz/config.toml` whatever its lifetime.

`Trigger::resolve` is the whole matching rule, with four outcomes:

| Trigger | `Deliver` | `Excluded` | `Skip` | `Ignore` |
| --- | --- | --- | --- | --- |
| `Signal` | every `match` key passes, and the selector is this exact name or this signal's family | the selector is this exact name or this signal's family, and a `match` key fails | every `match` key passes, but an exact selector names another member of the same family | a different family, or an exact selector on another member whose `match` key fails |
| `Watch` | the internal `wait.<task-name>` signal for this row | never | never | everything else, so one watcher's completion never fires another wait |
| `Schedule`, `Condition` | never | never | never | always. Clocks and conditions are not signals |

An `Excluded` task records nothing and is not fired. `harness::schedule::signal::fire_signal` lists it in `SignalFire::excluded`, which `rimz events emit` names in its receipt.

A `match` key compares a JSON string payload value to the raw text and any other JSON value to its compact encoding. The whole value `"*"` instead requires that the payload carries the top-level key, including when its value is `null`. Missing keys never match. Every other value is exact, so `feat/*` matches only that literal text. Thus `from = "*"` on `team.stage` excludes the first flip, whose payload omits `from`.

## Schedule shapes

| Shape | Entry | Due when |
| --- | --- | --- |
| One-shot | `fire-at = "<RFC 3339>"`, written by `rimz loop add --in`, `rimz loop add --at`, `rimz wait --in`, and `rimz wait --at` | the stamp is before the instant and the instant is at or before now. The task then removes itself once a scheduled fire records a result, whatever it is, and a dispatch that records none is dispatched again after five minutes |
| Interval | `every = "15m"` | elapsed time since the last arm or fire reaches the interval |
| Raw cron | `cron = "*/15 * * * *"` | the expression `CronSpec::parse` read once into per-field bit sets matches the current minute, and the last fire was in an earlier minute. `next_after` searches day by day for 8 years (the span that reaches any 29 February), then minute by minute in the first matching day |

Cron evaluates in the configured `timezone`, or the system zone when it is unset. `--in` does not read the zone: `schedule::delayed_instant` adds the delay to the add instant and rounds up to the next whole minute, and an `every` interval rounds its seconds up to minutes (`parse_interval_minutes`).

The arming stamp sets the edge each shape reads: a cron task first seen past a matching minute waits for the next match.

`Schedule::next_after` is the display counterpart of `due`. It can return a time at or before now, which means the host fires on its next tick. `TaskTiming::evaluate` layers the display states on top, and the first row that applies wins:

| State | Meaning |
| --- | --- |
| `Blocked(trust)` | a project task awaiting or stale on its trust grant |
| `Disabled(reason)` | a manual or strike disable, or a project task not yet enabled on this machine |
| `Paused(t)` | a bounded pause whose deadline is still ahead |
| `Invalid` | the timing half of the row failed to parse |
| `Listening { name }` | a signal subscription, which has no next time, stamped or not |
| `Watching { spec }` | a watch spec, whose watcher owns the timing, stamped or not |
| `Unarmed` | neither a room host nor the external tick has stamped it. An unstamped `fire-at` row reads its instant instead |
| `Due(t)` | the next occurrence is at or before now |
| `Upcoming(t)` | the next occurrence is in the future |
| `NoOccurrence` | parsed and armed, but no next time: any stamped condition row, and a `fire-at` row already dispatched (its stamp at or after the instant). A cron whose day of month no selected month has fails to parse when its day of week is `*`. With both day fields restricted, cron matches either (OR), so `0 0 31 2 mon` is valid and fires on February Mondays (`CronSpec::matches_day`). |

These are `TaskTimingState` values. For a condition row, `TaskTiming::with_condition` refines `NoOccurrence` from the current verdict and hold state: `Waiting { readings }` for a false verdict, `Unknown { readings }` for an unknown one, `Fired` once the stretch has fired, `Holding { elapsed, hold }` for a true, unfired row with a `for` hold, even once `elapsed` reaches `hold` (the display never promotes it), and `Due(now)` for a true, unfired row with no hold.

## Host firing

`fire::fire_due_tasks` runs on the host's data tick:

1. Load the runnable tasks for the room's project root, dropping untrusted project rows.
2. Keep only tasks whose normalized `root` maps to this room's `WorkspaceId`, so each room fires only its own tasks. `rimz loop add` writes a canonical absolute root. The machine loader has already skipped roots that are not absolute after home expansion. Accepted roots are expanded and canonicalized before the ownership check, display, and execution.
3. Plan every task against `lanes/loop-fire.json`, the per-room map from task name to last-fire timestamp in the workspace runtime directory.
4. Write the new state, then spawn a detached `rimz loop run <name>` with null stdio for each fire. A spawn that fails records a `start failed` row for that task and is left off the fired list. The stamp written in this step stays as it is, and a later pass reads a stamped `fire-at` row by the lost-runner row below, and a fired one-shot condition row by its lost-runner row under [Condition planning](#condition-planning).
5. Spawn a detached `workflow advance` for each workflow run of the root that is due, paced by `lanes/workflow-tick.json` ([workflow.md § The tick](./workflow.md#the-tick)). A run is a candidate while it is active, or once finished while it still owes its loop task, its starting agent or its starting `runs` step a report (`RunRecord::owes_report`), in which case its `workflow advance` command only collects it (`run_log::collect_run`), retried with a doubling gap of one minute up to an hour while the report fails to land.
6. Spawn a detached `rimz loop run <name> --drain` for each task with waiting triggers in `records/loop-backlog.json`, at most once a minute per room (`tick_backlog_with`, paced by `lanes/loop-backlog-tick.json`). This is the crash-recovery path of the [waiting-trigger backlog](#waiting-trigger-backlog).

The plan decides each task from its stamp, first matching row wins:

| State | Action |
| --- | --- |
| no stamp, `fire-at` at or before now | fire when live (record now). Otherwise keep no stamp |
| no stamp | arm: record now, do not fire |
| stamped, disabled or pause active | keep the stamp unchanged |
| stamped, schedule due | fire: record now |
| stamped `fire-at` row, stamp at or after its instant and at least five minutes old, no run-lock holder, and no scheduled history row but `start failed` since the stamp | lost runner: fire again, record now |
| stamped, watch row with no lock holder after the 30-second grace | watch lost: record now and fire the `Lost` outcome |
| stamped, not due | keep the stamp |

A `fire-at` row is the exception to arm-then-fire: it has no later occurrence, so arming it past due would strand it. `--in` resolves through `schedule::delayed_instant` (the add instant plus the delay, rounded up to the next minute) and `--at` through `schedule::resolve_once_at` (the first matching instant strictly after the add instant), once per add. A scheduled fire records `late_ms` on its history row when `TaskFire::new` receives a `now` two minutes or more past the instant, one tick plus spawn time. It fires on its first live sight past the instant, and its due check reads the raw stamp rather than `effective_last_fire`, so a pause or disable through the instant fires at the next live tick instead of skipping it. The stamp is written at dispatch, before anything shows the runner ran, and only a recorded attempt removes the row, so a runner lost without a record (a start failure, a scheduled runner that found the row not live, an early error in `run_one`, a crash) would leave the row listed and dead. `fire_tasks` therefore reads the runner of each live stamped `fire-at` row whose stamp is at or after its instant and at least `FIRE_AT_RETRY_SECS` (five minutes) old: the row counts as lost when nothing holds its bare-name run lock (`run_lock::held`, the gated lease probe) and no scheduled row but `start failed` was recorded since the stamp (`run_log::has_recorded_attempt_since`), where a `scheduled` stamp on the task's record at or after it also counts, for a launch whose run left no row. A manual launch is never stamped. The planner fires a lost row and stamps now, so a cause that recurs costs one spawn, and one strike-neutral `start failed` row under the transient-scope host, every five minutes, with no cap.

### Condition planning

Conditions use the same planner pass, and only the clock tick evaluates them: a signal never does. `fire_tasks` evaluates readings before the pure planner. The host supplies `CiSource`, and the external tick supplies none. Scope is `TaskEntry::run_dir()`. Board stages come from `scratch::board_stage`, through `when::TeamStageKey`, the one parse of a `team.stage` key. Its branch form reads the board of the checkout `worktree::checkout_on_branch_cached` finds on that branch in the same 60-second `git worktree list` rows `discover_owned_cached` keeps, so evaluation spawns no git per term. CI uses the cache's exact path key: an Open or Merged PR with CI wins, then branch CI, then `none` once a successful probe found neither (unread before one). The host keeps last-known-good CI on failed probes, but a condition does not decide on it. Grammar and unknown/negation semantics are in [Conditions](../../reference/cli/loop.md#conditions).

#### Condition state

`lanes/loop-when.json` is a runtime-class map from task name to `{fingerprint, since, fired}`, retained only while true (or held by arming policy), rebuilt from runnable rows each pass. The fingerprint holds the canonical expression, parsed hold duration, and run directory. A missing or mismatched fingerprint starts a new true period. First sight creates only the fire stamp. A condition task with `repeat = true` is not ephemeral. Without it, its first fire consumes the row.

| Stamp / arming | Verdict / hold state | Action |
| --- | --- | --- |
| none | any | Stamp now, no evaluation or hold state. |
| stamped, not Live | any | Carry both maps unchanged. |
| stamped, Live | unknown (an unread key of any kind leaves it unsettled) | Carry both maps unchanged. No fire. |
| stamped, Live | false | Drop hold state, carry stamp. |
| stamped, Live | true, no state | Start `{since: now, fired: false}`. Apply the next row. |
| stamped, Live | true, not fired | Fire at `now - since >= hold` (absent hold is zero), stamp now, set fired. |
| stamped, Live | true, fired, a task that remembers its checkout (`once-per-checkout = true`) | Retry once `RESIDENT_RETRY_SECS` (5 minutes) have passed since the last fire stamp: stamp now, keep the hold start and fired bit. |
| stamped, Live | true, fired, a one-shot task (no `repeat`) that neither remembers its checkout nor fans out (`each-worktree`), its last fire stamp at least `FIRE_AT_RETRY_SECS` (5 minutes) old, and its runner lost by the `fire-at` test ([Host firing](#host-firing)) | Lost runner: fire again, stamp now, keep the hold start and fired bit. |
| stamped, Live | true, fired, any other condition task | Carry. No repeat until a false tick. |

A remembering task whose launch memory holds an entry for the scope never reaches this table: `scoped_tasks` drops that scope from the pass before planning.

Write `loop-fire.json`, then `loop-when.json`, before any spawn. A fire-stamp write failure aborts the pass without spawning. A condition-state write failure suppresses only condition fires, which retry on the next tick. Already-stamped clock fires and lost-watch actions still proceed. Runtime teardown resets both holds and the CI cache. One timekeeper per root ([What the scheduler does](#what-the-scheduler-does)) is the synchronization boundary.

`ConditionEvidence` travels in hidden `--condition-json`, renders through `Evidence::Condition`, and is stored as the optional `LoopRunRecord.condition`: canonical `when`, optional `hold`, `held_ms`, and readings (unknown is JSON null). A condition delivery is `Type: WAIT`, never a synthetic signal, and dispatches as [Delivering to a live instance](#delivering-to-a-live-instance) says: a self wait steers, any other row waits for the Done boundary.

#### Forge freshness

`fire_tasks` then holds each verdict to the forge freshness rule with `crates/rimz/src/harness/when.rs::Verdict::freshen`, the floor and commit fence workflow checks use (`crates/rimz/src/harness/when.rs::forge_unread`). The floor is the task's stamp in `lanes/loop-fire.json`, its first sight or last planned fire, compared inclusively with `CiSource::checked_at`. Every forge key is unread without a `CiSource`, without a successful latest probe, or with one before the floor. Bare `ci` is also unread under the commit fence, whose git reads (`CiSource::ci_fence`) run only for a true verdict on a fresh probe with a known open PR head.

`fire_tasks` also skips them for a task whose carried `WhenState` records a fire on the same condition and that cannot fire again on a retry (it does not dedupe its checkout, and it is not a one-shot row whose runner counts as lost), since a fenced reading and a true one plan alike there. `fanout::inspect` and the CLI readers always run them.

Each unread key lands in `Verdict.unread` with its reason and reads `None`, and `freshen` takes the Kleene truth over what remains: a known term that settles the expression still decides it, so `ci=passed || pr=merged` fires on passed CI while `pr` is stale. `plan` fires on true alone and holds an unknown verdict, whichever key is unread (a forge key, `team.stage`, or a window): no fire, its fire stamp and `WhenState` carried unchanged, as for a task that is not live. A false verdict drops the `WhenState`. `fanout::inspect` and the CLI's condition readers call `freshen` with the same stamp (keyed by `fire::scope_key` for a checkout), so `loop show` and `loop list` show a held task as unknown with each unread key's reason. `RoomReadings::observe` keeps those reasons on the task's `TaskTiming` (`with_unread`), in the room-closed words (`when::condition::ROOM_CLOSED`) when it has no forge source, together with the first key, in the condition's order, whose probe reads `UnreadReason::NoForge`; `crates/rimz/src/harness/schedule/wait.rs::read_condition` does the same in `ConditionReading::unread` for receipts and `wait list`. A detached checkout is recorded in `PrStateCache.detached` beside its `<unsupported>` binding, so it reads `UnreadReason::Detached` instead.

#### Forge keys and probe demand

`probe::probe_demand` reads the runnable catalog and the tasks' arming to select existing directories of Live condition tasks naming a forge key (`ci`, `pr`, `pr.queue`, `pr.mergeable`, or `pr.review`) and each directory's demanded branch selectors. It also selects Active workflow runs whose definitions have a forge-reading condition case, a sleep's forge-reading `when`, a run, shell, or agent check declaring a default-scoped `ci`/`pr` wake, or a step subscribing to one, through `crates/rimz/src/harness/workflow/definition.rs::Definition::forge_branches`. Conditions and conditional sleeps contribute their branch selectors. Declared wakes and step subscriptions contribute checkout demand only, and an explicit `path` or `branch` match contributes none. Each run demands its canonical `record.scope.path` throughout its Active life, including steps, not only while evaluating that check. A missing project root, failed run listing, or unreadable spec warns and contributes no workflow demand. A Live signal task whose selector is in the `ci` or `pr` family and whose `match` holds a literal `branch` (not `*`) demands that branch under the project root (`crates/rimz/src/harness/schedule/probe.rs::signal_branch`); team role bindings arm as such tasks and demand the same way. Workflow step subscriptions and wakes with an explicit `branch` match still demand nothing.

Both git-fact and PR producers union these scopes with pane-derived paths, using the same path keys. The PR producer also deduplicates branch targets by origin repository and branch. Their rows live in `PrStateCache.branches[repo][branch]`, independent of checkout rows, and are pruned when no loop or workflow condition, no live signal task, and no unfinished booking demands them (`crates/rimz/src/sidebar/refresh/pr.rs::add_booking_demand`). A missing branch row makes the repo due. Pending branch CI or a queued branch PR selects its hot tier. Branch rows never enter the path maps. They emit `ci.*` and `pr.*` without a `path` ([branch-row signals](../sidebar/state.md#transitions-become-signals)), so a subscription with a `path` match never hears them, while an empty match, a `repo`-only match, and a `branch` match do. Only a team role's binding gets a default `path` match (`crates/rimz/src/harness/schedule/arm.rs::default_signal_matches`, called by `crates/rimz/src/harness/schedule/team.rs::binding_spec`); a `loop add` or `wait` subscription keeps the match it was given. A scope without a pane survives target reconciliation while its task is live or its workflow run is Active. Demand ends when neither needs it. Activity and focus are pane-driven, but pending CI or a queued PR also selects the hot PR-refresh tier.

The `pr` condition reads the link's Open, Merged, or Closed state directly. A missing link after a successful probe reads `none`, a missing source leaves it unread, and there is no branch-CI fallback. `pr.queue` reads the open link's merge-queue fact as `queued` or `dequeued`. Without one, an open link whose facts record an auto-merge request reads `armed`, and any other link, including one no longer open, reads `none`, so `pr=open` stays true for a queued or dequeued PR.

`when::ForgeKey` parses the optional selector and is the one list of the keys that read the forge cache: the parser and `evaluate` use it directly. `probe_demand` and the CLI's no-room hint ask `WhenExpr::reads_forge`.

`pr.mergeable` reads only a settled mergeability stamped with the open PR's current nonempty head. A carried answer for an older head is unread. The stamp does not include the base: an `UNKNOWN` response after only the base moves can retain a settled reading at the same head. `pr.review` reads the cached draft-first review fact, with never-fetched distinct from `none`. Both require open facts and are unread on Gitea. A successful probe that found no PR, or a merged or closed one, reads `none` for both. PR-fact keys explain a terminal link as no open PR, and unsettled or absent facts on an open link as not reported, never as no CI. The selector, parser suggestions, and wake derivation all use `when::ForgeKey`'s key set. Neither key adds a signal or changes probe cadence.

#### Window readings

A `window.<span>.left` term reads through `when::WindowReadings`, which both callers build (the CLI renderers too, room open or not): it reads the room's logins and every account's stored kind-wide windows once, on the first window term of a pass and never on a pass without one, reads each term on the row's `account` when it has one and on the kind's room default login otherwise, and projects `ProviderCapacity::window_of_span` to the pass instant, so a window whose reset has passed reads 100 under the external tick with no fresh cache. A lifted window reads 100. The kind comes from the row's `provider` field, recorded at add by `window::window_condition_provider` (the CLI's `add`, from `--provider`) or by `arm::build_entry` (deliveries), so the host reads it without resolving anything per tick. `parse_trigger` refuses a window term on a row without one. The add-time resolver, `window::window_at_add`, owns every refusal, in this order: no provider, managed account selection probed through `unresolved_managed_state`, unresolvable login, no reading, no window of that span, then an expired window. It reads the stored window unprojected, since projection would turn a stale cache into a full window.

### The external tick

`rimz loop timer install` writes one user-level systemd timer on Linux or a launchd agent on macOS. Once a minute it runs the hidden `rimz loop tick`, which exits after one pass. The timer is only a clock host: it re-reads configuration every pass and leaves arming, trust, overlap locks, execution, and history to the paths above.

The tick finds roots from machine and instance task entries, the trust grants that contain project tasks, every room holding a nonterminal workflow run, and every room holding a fire mark with no recorded outcome (`run_log::open_fire_roots`), so a dead fire of a consumed or removed task still reaches its settle pass. Trust grants are the project-root registry, because an ungranted project task cannot run anyway. For each root it derives the same `WorkspaceId` and runtime paths a room would. A fresh sidebar heartbeat means a host owns the root, and the tick skips it. Otherwise the tick prepares the runtime directories and calls the same planner with the root supplied explicitly, so a root that has never been opened needs no workspace record for its task to arm.

The runners must outlive the tick. Under systemd the tick starts each one through `systemd-run --user --scope`, moving it out of the timer service's cgroup so the runner and any multiplexer server it births survive, and waits up to five seconds to see the child's cgroup change. That route needs the systemd user manager, which a system-level unit, a container, or a sandbox does not have, so before it walks any root the tick asks `systemctl --user show-environment`. That is the same bus connection `systemd-run --user` makes, so it tracks systemd's own rules instead of re-deriving them from the environment. Failing that, the whole pass refuses with the fix named, rather than falling back to a host the runners would not survive: no stamp moves and no row is written, so every due task fires on the first tick after the host is fixed. External runners also get their own process group, on launchd too. Host and signal fires keep their inherited process group, so interactive launch probes cannot stall on background-terminal job control.

An external fire opens the room it needs, through the callback `run_one` passes to `TaskFire::prepare`, which `Fire::prepare_shell` calls after the deadline, launch memory, and run lock, and before `create`. A scheduled command fire births its room unless the root has a workspace record and a fresh sidebar heartbeat. A manual one births it only for a root with no room record. A `Deliver` fire opens none, and still requires its pinned live session. Even a never-roomed root takes its runtime-only run lock first. The birth receives the fire's shell-lookup policy before later attempts lose its run mode. It uses the normal detached room entry (durable ownership, the `rimzd` dashboard, closed-agent resume off, no confirmation prompt). That birth ends no top-level agent: the ones the dead session lost stay parked for a later rebirth or explicit resume, while their non-live subagents are closed (`rimz.child-not-resumed`), because a resumed parent relaunches any children it still needs. The room is born before the command runs, so a `rimz agents` launch in the command finds it open. These paths leave the room open, so later ticks yield to its host. A manual `rimz loop fire` returns once its run starts or, for a workflow, agent or team task, once its launch child exits.

A hand-off that fails records what happened. Because `systemd-run --scope` enrols its own pid and execs in place, a runner that loaded is indistinguishable by pid alone from one that never started: the poll is 25 ms, so a fire that ends at once (overlapped, gated, expired) migrates and exits inside a single poll window, and the tick sees the same "child gone" it sees when the scope was never created. The run log settles it. After a child-gone the tick looks for a scheduled row for that task and root stamped at or after the instant it captured before spawning, and, for a task that remembers its checkout, for a launch-memory entry for the scope (`crates/rimz/src/harness/schedule/fire.rs::recorded_launch`). Either means the run happened and nothing is added. Neither means the run did not start, and one `start failed` row is appended. One fire, one row, in both directions. The row records that observation, not a cause: no row means either that the runner was never spawned or that it exited before it could record anything. The second case is real. `run_one` (`cli/loop_cmd/run.rs`) returns without a row on these early exits:

- an undecodable `--signal-json` or `--condition-json`
- a strict `task_catalog` load rejecting an instance the tick's lenient load tolerated
- the task missing from the catalog
- a `resident_checkout` refusal
- a project-trust refusal
- a scheduled fire finding the task not `Live` because a `rimz loop pause` landed mid-tick
- an action that does not parse
- a `TaskFire::new` error

Each of those reads as `start failed` on the systemd tick. The five-second cgroup timeout is a warning only: the child is alive there and its outcome is unknown, so claiming either result would be a guess.

A room can be born between the tick's heartbeat check and its state write. In that one-tick window the host and the tick both plan the root against the same `lanes/loop-fire.json`. A planner that reads the stamp after the other's write sees the occurrence spent. When both read before either writes, both spawn a runner: the per-task run lock keeps the two runs from overlapping, but it does not stop the occurrence from running twice.

## One fire

`rimz loop run <name>` is hidden. After CLI trust and action validation it hands the fire to `schedule::runner::TaskFire`, which owns one fire from its start time through exactly one history transition. `TaskFire::prepare` takes one of two paths by the row's `TaskAction`, and the CLI reports the typed result back.

A `Command` row walks `Fire::prepare_shell`, which starts a workflow run, through the gates in the table below, in order. A `Deliver` row walks `Fire::prepare_delivery` in another order: the room-fleet and provider-account [scope caps](./budget.md#the-fail-fast-gate) on the room's login (`Fire::scope_refusal`, recording `budget skipped`), then the run lock (row 4), the stored `deadline` (row 2), a watch's verdict (row 1), then the delivery. Rows 3 and 5 to 7 are command-only. Either way, everything that can refuse cheaply refuses before anything expensive or observable happens.

| # | Gate | Records on refusal |
| --- | --- | --- |
| 1 | a watch's terminal verdict against the row's `on` | `skipped` |
| 2 | a stored `deadline` | `expired` |
| 3 | launch memory, on a scheduled fire of a task that remembers its checkout | nothing (`AlreadyLaunched`) |
| 4 | the per-task run lock, the admission lease | `overlapped`, or `deferred` under a retaining policy |
| 5 | room birth, then launch memory again | nothing (`AlreadyLaunched`) |
| 6 | a stop mark naming this holder (`reconcile_backlog`) | `canceled` |
| 7 | `create`, which refuses while the task's run is live in the scope (`WorkflowErr::Exists`) | the `overlap` policy's `overlapped` or `deferred` (`prepare_overlap`) |

A refused fire is spent. Only a scheduled trigger that found the lease held, or found the task's run live at `create` can enter the [waiting-trigger backlog](#waiting-trigger-backlog), and only under a retaining `overlap` policy. With `overlap` unset, `skip` or `allow`, that trigger is spent too. A retaining trigger that finds no room in the queue records `overlapped` with `queue full (<count>/<limit>), skipped`. Manual fires never enqueue. The lease covers admission alone: the fire writes its facts (`RunRecord.fire_facts`: kind, signal, absorbed count, run lock) into the record `create` writes. Once `create` returns it notes the run on the fire's open mark and, for a scheduled fire, stamps the task's scheduled launch, in one write (`fires::launched`, a failure only a warning), and releases the lease, writing no `launched` row and no assist, so the live run, not the lease, is what a later fire overlaps. `replace` cancels a blocking shell run in a detached `rimz workflow cancel` helper (`Fire::cancel_blocker`), and the waiting trigger starts when that cancel command collects the run's report. A blocking launch is stopped by `Fire::stop_launch`: SIGTERM to its launch child and each alive run or agent carrying the fire forwarded to its own stop in a detached helper; the waiting trigger drains through `rimz loop run <task> --drain` once nothing carrying the old fire is alive. A drained trigger whose blocker still runs goes back to the head of its queue and writes no row.

A workflow, agent or team row walks `Fire::prepare_launch` instead, whose overlap rung asks whether the checkout's last fire's launch is still alive (`Fire::alive_launch`) and answers through `prepare_overlap`. An agent row under `overlap = "allow"` skips that rung, scheduled and manual fires alike, and launches beside what earlier fires left alive; it retains no trigger anywhere, so a run-lock collision still records `overlapped`.

A fire takes no [start throttle](#the-start-throttle) turn itself, and neither does a shell fire's command check ([workflow admission](./workflow.md#admission)) or an agent or team fire's launch, nor an agent a shell command launches: only workflow agent steps call `throttle::try_admit`, so a workflow fire's steps take their turns as any run's do. A manual fire creates its run with `manual` set, and it bypasses launch-memory dedupe.

A closed gate adds no strike.

### Waiting-trigger backlog

`schedule/backlog.rs` is the strict sidebar-safe reader of `records/loop-backlog.json` (version `1`), resolved through `StatePaths::class_path` with `Class::Records`. `schedule/backlog_store.rs` owns locked mutation through `paths.lock_path("loop-backlog.lock")` and `write_temp_then_rename`. Each task key carries `triggers` (`arrived_at`, optional `signal` with name and payload, `absorbed`, and optional `from_arrived_at`) plus optional `stopping` (`pid`, `started_at`, `cause`: `stop`, or `replace` on a mark an older RimZ wrote). Empty tasks with no stop mark are pruned. A stop persists its mark before cancellation or signaling. Both the runner and ladder compare the whole holder identity, ignoring stale marks.

Under a retaining policy (`coalesce`, `queue`, `replace`), every run-lock acquisition, enqueue decision, and release shares that backlog lock. An arrival probes the run lock inside the critical section: a lock now free is acquired rather than treating an earlier observation as a refusal. `arrived_at` is the trigger's firing time, not the moment its runner took the backlog lock: racing runners reach the lock out of firing order, and ordering by the lock would merge a range with the wrong `from` or `to`. `signal::fire_signal_with_wait` stamps each emit once and hands that stamp to every subscriber's runner inside `--signal-json`, where `TaskFire::with_arrived_at` carries it. A clock fire, or a signal from an emitter without the stamp, falls back to the runner's start. `TaskBacklog::enqueue` keeps triggers sorted by that stamp, stably, so equal stamps keep lock order. Queue arrivals insert by firing time and run the earliest pending trigger. Coalescing arrivals run as the newest, absorbing the slot. Manual fires acquire and release through the same protocol without enqueueing or consuming an existing slot. Under a retaining policy, no check or effect runs before acquisition, including in a never-roomed root.

Coalesce and replace retain one newest trigger. Queue retains up to `overlap-limit`, default `10`. Replace records its `deferred` row naming the blocking run, then cancels that run at once, with no TERM grace, through a detached `rimz workflow cancel` (`crates/rimz/src/harness/schedule/runner.rs::Fire::cancel_blocker`, reason `replaced by a newer trigger`). The run's report drains the waiting trigger once the run is terminal, so the replacement never starts beside it. A parked run is canceled the same way, strike-neutral, while coalesce and queue wait for its report. Merging counts absorbed triggers and keeps the newest signal and payload, except that matching signal names and payload keys other than `from`/`to` preserve the oldest `from` when both carry those two keys. `WaitingTrigger::absorb` orders the pair by firing time whichever arrived second, and records the kept `from`'s firing time in `from_arrived_at`: the slot's own `arrived_at` is the newest trigger's, so a third trigger arriving out of order compares against the `from` already kept rather than overwriting it. The fire reconciles the slot before `create` (`Fire::reconcile_backlog`). The trigger the fire serves once the run lock and the reconcile have settled it is the one the run's history row names and the one its launch prompt carries: its signal and payload, with the absorbed count only on the row.

On release, a lock-holding runner whose fire neither created a run nor met a live one spawns one fresh `rimz loop run NAME --drain` when triggers wait, then unlocks while still holding the backlog lock, even when nothing waits. This closes the empty-backlog/release gap. A fire that created a run, or deferred behind one, leaves the drain to that run: `run_log::report_run` spawns the drainer once the run reports (`drain_waiting`). The drainer takes the run lock and pops the head under the same lock (`TaskFire::take_backlog`), rechecks arming and trust, then walks the same fire ladder as any fire at its own time. The command runs inside the run it starts. A non-Live task drops the trigger with no row. A busy or empty drainer also exits without a row. A paced scheduler tick reads the durable backlog and spawns drainers for crash recovery without probing run locks or importing runner mutations into the sidebar graph. Removal and redefinition clear backlog entries. Rename moves them. If hand-editing its file removes a task, makes its action fail to compile, or leaves it a task that could not have retained triggers (no `overlap`, `skip`, `allow`, or a shape that refuses the setting), the next drain drops its entire backlog entry, including any stop mark, under the backlog lock and exits successfully without a history row. Pause and disable keep the record for drain-time disposal.

### The run lock

The run lock is `locks/loop-run-<name>.lock`, separate from `lanes/loop-fire.json`, holding the holder's `{pid, started_at}`. An `each-worktree` fire locks per launch checkout instead, as `locks/loop-run-<name>-<workspace id of the checkout>.lock`, so launches into different checkouts do not overlap. The kernel releases a lock when the runner exits or crashes, and display probes read it without rewriting it. Claims, probes, and GC removal share the directory's `lease-gate.lock`, so a transient probe or GC attempt never makes a fire see `Overlapped`. One snapshot answers for a root: `run_control::RunLocks::list` lists the root's `locks/` directory once and probes each `loop-run-*.lock` entry once, keeping every outcome per file, so one entry that cannot be probed costs only the names that claim it. A task claims its bare name and every per-checkout name whose suffix parses as a workspace id, and it is running when any file it claims is held. With several held the snapshot reports the earliest-started holder, a holderless lock last. A held file that none of the root's rows claims is a row-less run, named by the file's whole stem: a supervised one-shot holds only the bare lock, so the stem is the name `show`, `logs`, and `stop` resolve back to that file. The display state, `in_flight_run`, and `stop_task` all answer from the snapshot, and one function spells the file name for the acquiring side and the lookup alike.

### Stopping a run

`rimz loop stop` runs two stops (`crates/rimz/src/cli/loop_cmd/stop.rs::stop`). `run_control::stop_task` first stops a fire still holding the admission lease. Then `stop_alive_launches` stops everything alive that any of the task's fires launched, read by `crates/rimz/src/harness/schedule/launches.rs::alive` from the fire stamps alone (`loop_fire`, whose fire id names the task), through each launch's own public stop: a workflow run through `rimz workflow cancel`, a `-p` run through the run stop `rimz agents stop <run-id>` takes (`launcher::stop::stop_run_agent`: the cancel, then the stop of the run's agent), and an agent or team member through `rimz agents stop`. Alive is durable state: a workflow run whose state is not terminal, a supervised run whose status is not terminal, an agent whose launch has not ended (`agent_end`), an idle one included. A launch whose environment dropped `RIMZ_LOOP_FIRE` carries no stamp and is never stopped. (Only the lease holder's ladder below selects by name, and only while the lease is held.) A launch that fails to stop does not stop the others: once all are tried, the stop fails with every such error. Each workflow run's own report records its end and starts the next waiting trigger; a `-p` run's end records nothing, since its fire recorded `launched` at the run's publish. `stop_task` is keyed by task name and root rather than a loaded row, and the CLI passes a supervised cancellation in as a closure:

1. Look the task's held lock up, including runtime-only locks before room birth. With none held it reports no active run. Re-probe under the backlog lock and persist the holder's stop mark. Every wait follows the marked identity, so an immediate drainer taking the file does not hide the old holder's release.
2. Cancel the newest active supervised run that carries the task's name and started once the holder took the lock (`run_control::newest_active_run`), through the CLI's closure, and wait up to five seconds. An earlier fire's run, which an `allow` task can leave alive, is left to `stop_alive_launches`.
3. Recheck the holder, send SIGTERM, and wait up to five seconds after the signal. The lock stays held throughout.
4. A holder that still owns the lock is not escalated to SIGKILL: the error names its PID and the lock path, and waiting triggers remain. After a release the ladder waits out the rest of the signal grace for the holder to read dead, then reaps the throttle queue.

A mark records that a stop was asked for, not that it took effect. The lease holder reads it under the backlog lock after admission and before `create` (`Fire::reconcile_backlog`): a mark naming its holder there starts no run and absorbs no waiting trigger, and the fire records `canceled` and releases, so the drainer serves the trigger. A mark written after that read finds the run created, and `stop_alive_launches` stops it.

The runner writes its terminal row and releases under the backlog lock, so a stop cannot mark an already-recorded fire in the record/release gap. That writer always clears a matching mark. The ladder writes only if its mark survives release, through the strike-neutral `record_stopped`, which settles the task's open launch mark with that row, whether or not the stop canceled a `-p` run. Private run-lock metadata retains the task kind, so the stopped row names the holder's own kind even after its catalog row changes or disappears. The writer spawns a drainer when triggers wait, and `loop stop` reports the waiting count without clearing it.

### Consuming a one-shot row

An ephemeral task removes its own row once `create` returns its run, so a one-shot whose run then fails is not retried. A row with a stored `deadline` (`--until`) instead lives until a scheduled fire's run reports `completed`, its command having exited 0 (`run_log::consume_until`), or its deadline passes. A delivery removes the row once dispatch returns, whether it succeeded or errored, so the wake's message record exists before its row disappears and turn-completion waits never see the agent rested in between ([messaging.md § The shared turn reader](./messaging.md#the-shared-turn-reader)). A crash between dispatch and removal leaves the row to fire again. A scheduled fire of a `fire-at` row removes the row in `Fire::finish_record`, whatever its result, so a gate skip or an overlap ends it too. A manual `rimz loop fire` leaves it. A spawn that never starts records `start failed` without reaching the runner, and a runner that exits before recording records nothing. Either way the row stays, and the pass dispatches it again once the runner counts as lost ([Host firing](#host-firing)). A deadline row expires without delivery once its deadline passes. A watch check-in is nonterminal and leaves the row in place. The final outcome consumes it.

### Where a scheduled run lands

A command fire's run has no agent step. A launch in the command is the launch it types ([scripting.md § Runs the scheduler starts](./scripting.md#runs-the-scheduler-starts)): without `-p` it returns once its agents start, with `-p` it waits for the run's result. Either way it carries the fire, read from the check's `RIMZ_LOOP_FIRE`, as `loop_fire`, and the task's name as `loop_task`, on every agent row it writes and on a `-p` run's record, so `rimz loop show` lists it and `rimz loop stop` stops it ([Stopping a run](#stopping-a-run)), and the bookings lane joins it. A tab it opens is named `loop <task>` (`crates/rimz/src/launcher/execute.rs`), and a fire's command has no pane, so the tab is new and unfocused. The fire's end stops none of its launches: a `-p` run ends by its own rules (its timeout, its turn) or by `rimz loop stop`. The `loop ` prefix keeps a task named `rimzd` out of the daemon-view classification: tab status and the run tab's sidebar bell can surface its waiting agent. The loop panel is a display, repaired by the host ([rimzd.md](../rimzd.md#who-repairs-and-when)), and hosts no runs.

Channel inheritance is the exception for launches under a loop fire, including manual fires. Their channel and bare-role team inference come from the launch checkout (or an explicit launch channel), never the firer's `RIMZ_CHANNEL`: the firer observed the trigger, not a parent asking a child to join its channel. A launch under a loop fire likewise resolves no agent caller from environment or process ancestry: the firer's chain depth, subagent status, and room pin cannot refuse it, and it records neither `launched_by` nor a run `reader`. The scheduled helper retains its ambient channel for delivery-target scoping. Only launches exclude it. A workflow, agent or team task's launch child (`crates/rimz/src/harness/schedule/launch.rs::spawn`) also drops the firer's room pin (`RIMZ_PROJECT_ROOT`, `RIMZ_WORKSPACE_ID`): `WorkspaceResolver::resolve_participant` ranks the pin above the directory, so a manual fire from a pane of another room would otherwise launch there. Without it the child resolves the room from the fire's checkout, an `--each-worktree` checkout included, as a timer fire, which carries no pin, does.

Nobody is watching an unattended run, so it must not wedge forever. `rimz loop add` writes a shell row's `timeout` (`--timeout`, else the machine's `loop.default-timeout`, else two hours, `SCHEDULED_RUN_DEFAULT_TIMEOUT_LABEL`), and the command check runs under it. An agent the command launches is the launch it types, and the row's `timeout` does not reach it: a `-p` run is bounded by its own `--timeout` alone, and a timed-out command ends the fire's run while its launches live on, listed by `rimz loop show`, until they end or `rimz loop stop` stops them.

The evidence survives the pane: the workflow run keeps its journal for `rimz workflow show`, and the `LoopRunRecord` keeps the fire's outcome and the run's report for `rimz loop logs`.

### The compiled graph

`crates/rimz/src/harness/schedule/shell_task.rs::command_definition` turns a `Command` row into an inline workflow graph, scoped `worktree`, that `workflow show <task>` draws: one `[test.command]` check whose `shell` is `exec` followed by the argv, each word quoted back as a shell would read it (`schedule::command_line`), under the row's `timeout`. `pass` routes to `@done`, and `fail`, `timeout`, and `died` to `@failed`. A `test` check runs its script where a `command` node would confine every word holding `/` to the definition directory, so the argv runs as stored.

The check runs through `crates/rimz/src/harness/workflow/script.rs::evaluate`, as a shell check, under the run's own process host, with `RIMZ_LOOP_TASK=<task-name>`, `RIMZ_LOOP_FIRE` set to the run record's `loop_fire` (the fire id, which names its task), `RIMZ_WORKTREE_PATH` set to the run's scope, `RIMZ_LOOP_TRIGGER` carrying the evidence frozen into the run's fire (`RunFire::evidence`, [below](#the-prompt-a-fire-delivers)) when the fire has any, and `RIMZ_LOOP_BOOKED_BY` when the fire carries a booking chain (`script::loop_task_env`). `crates/rimz/src/harness/loop_task.rs::read_fire_env` is the one reader of the fire's environment, used by `rimz agents` and `rimz teams` launches (`dispatch_launch`, `launch_supervised_background`) and by `rimz workflow run`: it reads a fire only when `RIMZ_LOOP_FIRE` parses as a fire id and `RIMZ_AGENT_ID` is absent, so a launch an agent makes in its own pane is never the fire's. A launch it reads gets `RIMZ_LOOP_TRIGGER` appended to any prompt it was given, after a blank line, and the fire's stamps; otherwise it is the launch it types, `-p` only when written. A workflow run started under a fire carries `loop_fire` with no `task`, and the engine exports `RIMZ_LOOP_FIRE` to its scripts. To hand a launch off, so the fire's task neither lists nor stops it, the command drops `RIMZ_LOOP_FIRE` from its environment (the dependabot loop does). Room birth clears the check marker and the fire id so neither can leak into later launches from a human shell.

A command run never enters an agent, message or runs step, so `engine::entered_act` reads it as unacted: replacement and removal cancel its live runs ([Launch memory](#launch-memory)).

A terminal `Watch` outcome takes a separate path with the watch already evaluated: `Fire::prepare_watch` converts the signal's `WatchOutcome` instead of executing anything, and the row's polarity applies. A command watch defaults to `on = "any"`. Polled watches always use that row polarity, with check polarity applied inside the watcher. A `Lost` outcome converts to a failed check, so `any` still delivers it and `on = "success"` skips it. A polarity skip records `skipped` and consumes the ephemeral wait without delivering a message. A `Running` or `NotMet` check-in bypasses polarity and consumption.

### The prompt a fire delivers

`effect_prompt` builds the delivered text. A delivery row's base is its `prompt`, which team arming writes. A command row has none. Nothing is substituted: `{{key}}` is delivered as typed.

A `Command` row with no `watch` goes through `compose_launch` (`runner::Fire::effect_prompt` picks the composer), filled after the backlog reconcile (`runner::Fire::prepare_shell`) from the trigger the fire serves, which the run lock or the reconcile may have switched. The text becomes the evidence of the run's fire (`RunFire::evidence`), which the command reads as `RIMZ_LOOP_TRIGGER`; the run has no prompt. A workflow task's fire (`runner::Fire::prepare_launch`) composes the same text and freezes it into the fire it hands `rimz workflow run`, so that run's commands read it the same way and its agent and message steps get it after the run's `--prompt`. A fire with no event hands nothing. A manual fire with `--signal` is handed that signal (`TaskFire::new`), so it composes the signal row below whatever the task's trigger:

| Evidence | Message |
| --- | --- |
| condition | ``Rule `<name>` fired here. <key>: <reading> · <key>: <reading>``, the readings in evidence order with `unknown` for one with no value |
| signal | ``Rule `<name>` fired here. <subject>``, the `signal_headline` subject followed by each `signal_details` entry after ` · ` |
| none (a clock fire, a hand fire without `--signal`) | nothing |

Every delivery to a running agent (a self wait, a team role binding) and every watch row goes through `compose_wait`: the wait line, the verdict, the evidence, then the loop or team prompt verbatim after a blank line. Durations are elapsed time, not wall-clock.

| Trigger | Wait and evidence lines |
| --- | --- |
| self timer (`rimz wait --in`) | `waited <delay> [<name>]`, one line |
| self clock (`rimz wait --at`) | `waited until <local minute> [<name>]`, one line |
| clock delivery (a `wait` row on a schedule) | `scheduled wait` and `fired [<name>]` |
| watch | `WatchSpec::headline`, `WatchVerdict::label`, the name, and `output: <host path> (<FileSummary::label>)` when a path is present and the file is non-empty. Only command watches say `no output` for an empty file. The tail is never inlined. A file pattern match includes its matched-line preview. |
| signal | `waited on <subject>` and `fired [<name>]`, or `fired after <elapsed> [<name>]` on a self wait (a row with `wait_meta`). `signal_headline` builds the subject per name from the payload, dropping a segment whose key is absent or mistyped. The [subject table](../../reference/cli/loop.md#signals) is the contract. A built-in family adds no line, except `pr.dequeued`'s `queue checks:` line. Any other family adds one `key: value` line per top-level payload field. No line is the payload as JSON. |
| condition | `waited on <expr>`, `held <hold> [<name>]` or `fired [<name>]` (`fired after <elapsed> [<name>]` on a self wait), then one `key: value` line per reading, `unknown` for one with no value |
| a signal, watch, or condition row fired by hand without `--signal` | `fired by hand` (a clock row fired by hand reads as a scheduled timer) |

On a self wait (a row with `wait_meta`), a set label follows the first line's subject as ` · <label>`, before any ` [<name>]` on that line. Self waits carry no note and no armer line. A check-in appends its stop and next-alarm commands.

### The Loop reminder

A command fire launches no agent itself, so it writes no reminder. An agent its command launches carries the fire as `loop_fire` and the task as `loop_task`, and the prompt carries the fire's evidence through `RIMZ_LOOP_TRIGGER` ([The compiled graph](#the-compiled-graph)).

`ReminderSection::Loop` survives for replay: an agent whose durable `LaunchRecord` carries a rendered `loop_section` gets it back on restart, resume, rebirth, molt, and message-driven child resume through `ResumeLaunchPosture::exec_request`, and forks clear it. No fire renders a new one.

### Delivering to a live instance

`wait` pins a task to one live agent when it is armed. `rimz wait` resolves the caller through one `crates/rimz/src/sidebar/produce/mod.rs::resolution_snapshot` and stores its launch id (`agent.launch_key()`, in `crates/rimz/src/cli/wait/add.rs`), and team arming pins the registering member ([Team bindings](#team-bindings)). The stored `wait.handle` equals that agent's `rimz wait` receipt target. The runner resolves the target's current holder over the Audit rows (`schedule::catalog::delivery_holder`, [Targets and holders](#targets-and-holders)) and confirms it is alive, including `ended_at`, before it sends through the ordinary durable message path. A missing or ended agent records `target gone`, and a scheduled fire also removes the row. A manual fire leaves it in place.

| Intent | Header | Dispatch |
| --- | --- | --- |
| Self wait (row has `wait_meta`: a timer, clock, condition, or watch) whose holder has a session | `Type: WAIT` | `Steer`, parking with gate `Any` if a native prompt is open |
| Self wait whose holder is still provisional | `Type: WAIT` | `Boundary { gate: Done }` |
| Any `Trigger::Signal` delivery, including team bindings | `Type: SIGNAL` | `Boundary { gate: Done }` |
| Scheduled loop delivery | `Type: WAIT` | `Boundary { gate: Done }` |

`crates/rimz/src/cli/loop_cmd/run.rs::wake_mode` picks the dispatch. The sender is `@rimz`, and delivery inherits the recipient's [smart-compaction line](./messaging.md#smart-compaction). A boundary delivery reaches an idle agent immediately and parks for a working agent's next `done`. A self wait steers unless the agent has a native prompt open.

A steered wake that meets an open native prompt stays `Queued` with gate `Any` and `last_error: agent is waiting on input in its pane`, then delivers at the next turn boundary after the prompt is answered. The fire records `delivered` with the queued message id and consumes the wait row, as for a missing pane. Turn-completion waits project the in-flight wake as sleeping, keeping `agents wait` open. A check-in parks the same way but leaves its row watching and its command running. For a watch's terminal fire, `crates/rimz/src/harness/schedule/runner/deliver.rs::Fire::prepare_delivery` fills `PreparedDelivery::supersedes` from `crates/rimz/src/harness/schedule/run_log.rs::task_records`. The CLI cancels those messages before dispatching the final wake, so a parked check-in never follows its final wake. A lost history row leaves that check-in to land at the turn boundary. Receivers acknowledge `SIGNAL` and `WAIT` as attributed harness messages, hidden in rendered transcripts and kept in `--json` ([messaging.md § The message header](./messaging.md#the-message-header)).

## Remembered checkouts

A task with `once-per-checkout = true` remembers each checkout it fired in (`TaskEntry::dedupes_checkout`), so its scheduled fires start nothing more in a checkout whose fire did not fail (`FireMark::holds_checkout`). A failed or canceled fire loses its entry (`run_log::forget_unkept_launch`), so the next scheduled fire may start there again ([Launch memory](#launch-memory)). Every other task relies on live run admission at each fire.

### Launch memory

Launch memory is the fire marks on the task's record ([The task record](#the-task-record)): one `FireMark` per firing checkout, holding the fire id, when it fired, whether it counts for `once-per-checkout`, the workflow run it published, the run's scope in the workflow record's `worktree` or `project` words, its recorded result, the kind and target the task declared at the fire, the `rimz` process that made the fire (`opener`), and the launch child a workflow, agent or team fire spawned (`child`), each a `ProcessMark` of pid and start token. Every fire that reaches its launch writes its open mark before it (before `create` for a command fire, before the child spawns for the rest, through `fires::open`, in the same write that binds the task and mints the fire id), so a fire that crashes after `create` still holds its checkout. A command fire whose `create` fails, and a workflow, agent or team fire that fails before its child spawns, takes the mark back and restores the one it displaced (`fires::withdraw`). The settle pass reads the marks without the lock, so it writes an outcome only while the fire's mark is still open on the record (`fires::settle_open`): a fire that withdrew its mark gets no row and no strike from it. `fires::launched` notes the run a command or workflow fire published, when the fire knows its id. A worktree mark is keyed by the scheduler's lexical checkout. A project mark covers every checkout of the task (`TaskRecord::launched`).

A mark holds its checkout for a remembering task (`TaskEntry::dedupes_checkout`) while it counts and its result is open or `completed`, `launched` or `delivered` (`FireMark::holds_checkout`). The run's report closes the mark with the run's result in the same write that moves the strike count (`fires::settle`), so a fire keeps its checkout remembered only when it did not fail: a shell command that exited 0, a workflow run that ended done, or an agent or team launch (a `-p` launch included: its mark closes `launched` at the run's publish, whatever the run does after), until a manual fire replaces the mark. A fire copies its row's `booked_by` onto its mark, and once a one-off's row is consumed the bookings lane finds its fire through the mark on the retired record (`TaskRecords::consumed`).

Task replacement (`loop add` under the same name) and explicit removal both cancel the task's live runs that have not visited an agent, message or runs step (`engine::unacted_task_runs`), which is every command run, each through a detached `rimz workflow cancel`. Removal retires the record with its marks, and also detaches any remaining live workflow runs (`engine::reassign_task`), which continue as independent runs. `TaskCatalog::remove_keeping_runs` removes a task the same way but cancels none of its runs, unacted ones included, and spawns nothing; it returns what the task fired that is still alive (`launches::alive`), read before the record retires, and removes nothing when the task's booking is no longer the one its caller checked. A re-added task gets a new id and so none of the old marks. Rename rebinds the record and moves nothing else, since every mark, run and history row of the task is keyed by its id. A manual fire bypasses dedupe and replaces the mark, and a failed create puts the old mark back. A project mark continues covering all checkouts after a definition changes to worktree scope until removal or a manual fire replaces it.

The planner reads launch memory for remembering tasks, dropping launched checkouts before planning. A condition with no launch entry retries once 5 minutes have passed since that key's last fire stamp, keeping the original hold start, for single-checkout and fan-out tasks alike. This five-minute retry needs no stored field, and no helper writes the condition cache. A run still live makes a retry on the same checkout find the run live. A run that did not end `Done` left no entry, so the retry starts a new one (`crates/rimz/src/harness/schedule/run_log.rs::forget_unkept_launch`. The user rule is [launch memory](../../reference/cli/loop.md#launch-memory)). Failed runs accumulate strikes. An unreadable task record stops every fire ([The task record](#the-task-record)). Forge probes select fan-out scopes by the same `once-per-checkout` rule.

An `each-worktree` project-scoped task takes per-checkout run locks, so a project run that turns terminal between another checkout's memory check and its `create` lets that checkout start a second project run.

### One launch per worktree

For `each-worktree`, the planner expands a task over the owned worktree markers not covered by its launch memory. It expands paused and disabled tasks too, so that arming policy keeps their hold and fired state as it does for an ordinary condition. Runtime condition and fire keys encode `(task, checkout)`, and edge rules are the same as for a single task. The marker path is lexically normalized (`.` and `..` removed, symlinks not resolved) for condition evaluation, PR probes, the hidden helper's `--cwd`, and launch memory, which matches agent rows and subscription paths. It does not pass through `TaskEntry.run_dir`, which resolves configured paths. The helper validates that checkout against the normalized owned markers, keeps it apart, and takes a checkout-specific run lock before its launch-memory recheck. A manual fire selects the deepest owned checkout that contains the caller's cwd, with the same normalized marker path.

Fire planning enumerates owned worktrees once when any fan-out task exists, paused tasks included, while probe selection enumerates only for a relevant live fan-out task. A task reads launch memory only when its row sets `once-per-checkout = true` (`crates/rimz/src/config/loop_.rs::TaskEntry::dedupes_checkout`), and then expands only over unlaunched scopes, including after its run finishes. Otherwise it relies on live run admission at each fire.

`crates/rimz/src/harness/schedule/fanout.rs::inspect` reads owned markers, the task record its caller read once (so `loop show` shares one read with its run projection), the condition cache through `crates/rimz/src/harness/schedule/fire.rs::scope_key`, and the scoped evaluator that firing uses. It shares fingerprint matching with the planner, keeping the configured run directory in the fingerprint while the scope key selects the checkout. A true condition with a matching clock is holding until the hold elapses, then ready. Without a matching clock it is holding since now when a hold is configured, otherwise ready since now. Inspection starts no stored clock, does not predict the scheduler's first-sight or retry tick, writes nothing, and reads forge facts only from the room's cache, gated by the CLI's fresh sidebar heartbeat. The CLI joins capacity waits by checkout (`attention::capacity_waits`, read in `render::worktree_rows`): an Active workflow run of the task that is waiting on capacity shows the shared capacity phrase in the state cell and the structured `capacity_wait` object in JSON. Workflow rows join by run id to `crates/rimz/src/cli/loop_cmd/list.rs::WorkflowRunRow::for_show`, the shared projection for WORKTREES, RUNS, and JSON. It includes marked terminal runs and marked runs whose record and header are both missing, then every unlisted run the task started in its room (`RunRecord::ran_for`, any state), live first and finished newest first. `RunRecord::started_by` stays live-only for `loop list`, and `engine::reassign_task` takes it on removal. A marked run with neither record nor header takes its mark's result as its state (`completed` as `done`, `failed`, `canceled`, any other result by `LoopRunResult::label`), or `gone` when the mark has no result (`crates/rimz/src/cli/loop_cmd/list.rs::result_state`), and offers no `workflow show` command. Active, parked, and failed runs stay visible. Runs in every other state fold. `--all` unfolds older folded launches. JSON always includes every owned checkout. RUNS omits every run named by a worktree row, then folds adjacent finished rows and caps them by `--runs` (`crates/rimz/src/cli/loop_cmd/render.rs::write_workflow_runs`), while JSON retains the full projection and repeats each worktree's matching run object.

## History, strikes, and arming

History is the user-global `~/.rimz/logs/loop-runs.log.jsonl` (`crates/rimz/src/harness/schedule/run_log.rs`), one `LoopRunRecord` per fire that reaches a decision. Two kinds of fire write no row of their own: a fire that starts a workflow run, whose run's report is its one row, and a fire whose run is quiet, which writes none ([Run reports and quiet runs](#run-reports-and-quiet-runs)). [What the scheduler does](#what-the-scheduler-does) lists the exits that write nothing. The log is per user, so history survives a task being edited or removed. `rimz loop show` filters it by the resolved task's room, and `rimz loop logs` and the health reads filter by the current workspace root when it is known. A record with no `root` is visible everywhere.

### The history record

A record carries:

- the resolved task `root`, the result, the mode (`scheduled` or `manual`), the duration, and the error chain
- check evidence: exit code, timeout flag, capped output, and for a watch row the output file's host `output_path`
- the watched command's `WatchVerdict` in `watch`
- the triggering signal's name and payload
- the delivery's durable message id and target, or the supervised run id and transcript path; on an agent or team fire's `launched` row, `target` holds the addresses of what it launched that was alive at the fire (`launches::launched`)
- the last message, cost, and fresh input and output tokens
- optional `late_ms`, on a scheduled fire of a `fire-at` row that `TaskFire::new` constructed two minutes or more past the instant, measured from the instant to that constructor's `now`
- optional `holder`, on a fire refused at the run lock: the holder's `pid` and `started_at`. The stored error names the policy outcome without a pid or a frozen age.
- optional `blocking_run`, on an `overlapped` or `deferred` record for a fire that a live workflow run kept from starting, naming that run. Three writers set it: the task's own run still active (`Fire::prepare_overlap`), a run of the task's workflow started by hand in the fire's checkout, a try (`run --once`) excepted (`Fire::record_hand_started`), and, for a workflow task, a live run in its checkout that refused the launch, which can be another task's run (`Fire::launch_outcome`). The stored error names the run in each case.
- optional `run_lock`, on a record for a fire that held the run lock: that tenure's `pid` and `started_at`, including records the stop and replace ladder writes on the holder's behalf
- on a run's report: the run id, `acted` (whether the run started a step), the summed attempt and evaluation cost, and a served coalesced trigger's nonzero `absorbed` count

The append caps stored copies (`run_log::capped_record`): 4 KiB each of shell output and of every judge reason and error, 2 KiB each of run error text and last message, and a signal payload over 4 KiB collapses to `_truncated`. The log rotates at 4 MiB (`run_log::MAX_BYTES`). The verdict reader tails reasons to 4 KiB at a UTF-8 boundary before assists or prompts consume them.

Optional fields read absent when a row lacks them, `judge` reads empty and is omitted when empty, and `reused` reads false. `LoopRunRecord::stages()` projects a row whose `check` holds an agent into a judge without fabricating a shell, and the writer never puts an agent there. Row polarity and its consumers use `last_verdict()`, the last answered stage.

Rendering: watch stages use `WatchVerdict::label` and `elapsed_ms()`, shell stages use `exit <n>`, `timeout`, or `signal`, and judges render profile, verdict, reason or error, spend, tokens, duration, and reuse. A skipped negative verdict reads `judge declined`, and a positive verdict reads `judge passed` even when skipped. `rimz loop logs` keeps one block per run and prints every stored stage in that block in full, the output path above the shell gutter. Its shared history fold attributes lock-refused fires as counts on their holder's record, or on the record of the run their `blocking_run` names. A spent fire (its holder proved gone by a later tenure of the same lock, or its `blocking_run` naming no record while a later run of its checkout exists) keeps a plain refusal block. Repeated refusals keep the newest member's forensics. Trailing lock refusals stay as blocks in log order, folded only for equal keys and holders. Heard signals keep individual blocks and never take attributed counts.

These functions append to the log: `record_transition`, `record_stopped`, `run_log::report_run`, and `run_log::report_neutral`, plus the launch site's `start failed` row for a helper that never started (in `fire.rs` for the host and the external tick). A fire and an observed sibling signal reach `record_transition`, which appends the row and then moves the task's record; a fire's own row closes the fire's mark and moves its count first, then appends, so a reader that sees the row sees the mark closed. `rimz loop stop`, whose task row may already be consumed, reaches `record_stopped`, which appends a strike-neutral `canceled` row stamped with the stop's root and moves no count. A run's report appends through `run_log::report_run`. No CLI code appends a row. The fire-path append is best-effort: `disk::rotating` logs its own failure at debug and returns, so the `RunTransition::Recorded` that `record_transition` returns means the append was attempted, not that the row reached disk. A report's append is fallible instead, so a failed one is retried ([Run reports and quiet runs](#run-reports-and-quiet-runs)).

### Strikes

A strike is one consecutive failure of a task. The count lives on the task's record ([The task record](#the-task-record)). A run's report moves it in `fires::settle`, and any other decided row through `run_log::note_strike` from `record_transition`. A quiet run's report settles with `Reset` directly, without `classify` ([Run reports and quiet runs](#run-reports-and-quiet-runs)).

1. `strikes::classify` sorts the row into `Strike`, `Reset`, or `Neutral`. A row whose `watch` verdict is not terminal (a `Running` check-in) is `Neutral` before its result is read.
2. A run's report settles by its fire id (`fires::settle`): one write of the task's record moves the count, records the fire id among the ids it has counted (`counted`, the newest 64), closes the fire's mark and disables a task that struck out. A fire id already counted moves nothing, so a second report changes nothing.
3. Any other row goes through `strikes::note`, on the record its row's task id names, retired or not, so a row written after its task retired binds no new record.
4. When the signal was `Strike` and the count reaches the threshold (`strikes::threshold`: the row's `max-strikes`, default `DEFAULT_MAX_STRIKES` = 3, `0` disables), the task is disabled (`arming::disable_if_live`, or `arming::disabled_if_live` inside the settle), which `loop show` then heads with `disabled after N strikes` (`render::write_show_headline`, and the attention reason in `attention::decide`). The `RunTransition::AutoDisabled` this returns sends the strike-out notification (`loop_disabled` handlers and a sidebar toast): `crates/rimz/src/cli/loop_cmd/run.rs::handle_run_transition` for a fire's row, and the hook `run_log::on_loop_disabled` registers for a report.

| Signal | Results |
| --- | --- |
| `Strike` | `failed`, `verify failed`, `timed out`, `error`, `budget exceeded` |
| `Reset` | `completed`, `delivered`, and `launched` without a run id (an agent or team fire, with `-p` or without) |
| `Neutral` | `budget skipped`, `surplus skipped`, `account skipped`, `throttle skipped`, `capacity held`, `takeover blocked`, `overlapped`, `deferred`, `canceled`, `replaced`, `expired`, `target gone`, `start failed`, every `skipped` (`check_skipped`, `signal_skipped`, `workflow_skipped`), `launched` carrying a run id (a workflow run, whose own row follows), and any nonterminal watch check-in |

The table encodes three judgements. A run that ended `failed` is a failure, and a hung run still fails at its step timeout. A run that was stopped (`canceled`, `replaced`) did not fail. A gate that declined to spend money is not a failure. A fire that left no run behind says nothing about the task, so `start failed` is neutral even though every renderer shows it as a failure: a broken timer must not auto-disable the work it failed to run.

A check's answer is not an input: a run is judged by its own result. A `launched` row with a run id is neutral because the run reports later. A stranded run (a run record of an older version, [workflow.md](./workflow.md)) reports from its header through `run_log::report_header` and `run_log::report_neutral`, which append its row, move no count, and consume no `--until` row. `rimz loop enable` clears the count and the counted fire ids (`strikes::clear`). `rimz loop fire` works on a disabled or paused task, for testing.

`LoopRunResult` has 24 variants. `CheckSkipped` and `SignalSkipped` serialize distinctly (`check_skipped`, `signal_skipped`) but both render the label `skipped`: one is a watch whose verdict missed the row's polarity (rendered with the check's outcome), the other a sibling signal the subscription observed without delivering (rendered as `heard`). `deferred` retains a busy trigger, and `replaced` denotes a run stopped for a newer trigger.

#### Adding a run result

A new `LoopRunResult` variant is a durable format change: its `snake_case` name is written to the shared history log, and a binary that does not know it fails to decode that row. Beyond the enum, it needs a decision at each of these places:

- `strikes::classify`, `LoopRunResult::label`, and `loop_cmd::render::loop_result_mark` match exhaustively, so the compiler stops at them. `loop_result_mark` is in the binary crate, so its error appears only once the library compiles.
- `LoopRunRecord::polarity` (good or failure, which the history fold and `loop show`'s verdict read, and which ends the quiet streak) and `LoopRunResult::spawn_exit_code` end in a wildcard arm, so a variant left out compiles as `None` without a decision. Polarity and strikes are separate decisions: `replaced` has failure polarity (the display marks it failed) but is strike-neutral.
- `cli/teams/show.rs` (the subscription cell), `crates/rimz/src/cli/loop_cmd/render.rs::run_status` (the label beside a watch verdict), and three functions in `cli/loop_cmd/run_report.rs` that decide what a manual `loop run` or `loop fire` prints (`manual_early_verdict`, `is_spawn_failure`, `success_result_label`) also end in wildcard arms.
- The [three judgements](#strikes) above: a result that says nothing about the task is `Neutral`.
- `strikes::tests` and `run_log::tests` pin the classification and the label of the existing variants. They do not fail on a new variant, so add its cases. Run them with `cargo xtask test -E 'test(/schedule::(strikes|run_log)::tests/)'` ([gates.md](../../contributing/gates.md) owns the gates).

### Run reports and quiet runs

A workflow run a fire started reports to its task once, when `run_log::collect_run` collects it. `run_log::report_run` reads the typed outcome the engine wrote in the run's record (`store::workflow::RunOutcome`) and builds the row with `run_log::report_row` from that outcome and the `fire_facts` the launcher wrote before `create`, so the report needs no launch row and lands whichever side finishes first. The row carries the run id and `completed`, `failed`, `throttle skipped`, or `canceled`. `report_run` also maps a run whose agent step gave up waiting for capacity to `throttle skipped` (`crates/rimz/src/harness/workflow/engine.rs::failure`). A step a budget refuses waits at its node rather than ending the run, so a workflow run reports no budget row. A command run has no agent step, so the mapping does not reach a fire's own run today. A command run, a `replace` cancel included, reports `completed`, `failed`, or `canceled`.

A report closes the fire's mark and notes its strike in one write before it appends the row, so a reader that sees the row sees the mark closed, and it has landed only once both are durable. A failed append returns an error; the retry's settle moves nothing a second time, since a fire id counts once, before it appends, and history readers fold a repeated row by its run id. After the row lands, a scheduled fire's `--until` row (an ephemeral row with a `deadline`) whose command exited 0 is consumed (`run_log::consume_until`), and a waiting trigger drains.

History readers (`run_log::task_history`, the `loop list` stats fold) drop a logged `launched` row that names a run (an older RimZ wrote one per run), keep the first report per root, task, and run id, and add one neutral `launched` row per run of the task still in the live directory with no report yet. That row is read from the run's `fire_facts`, or for a record without them from its task, id, creation time, and scope checkout (`run_log::in_flight`). The readers then merge the task's quiet summary (`run_log::with_quiet`). The held stats behind `rimz loop watch` cache only the log fold, and reread the live directory and the quiet summary on every refresh.

A quiet run (`store::workflow::RunOutcome::quiet`: done, with `RunRecord.engaged` present and false) whose task row still exists is forgotten at collection instead of reported:

1. `fires::settle` resets the strike count, once per fire id.
2. In that same write, and only when the fire id is new, it adds one to the task's `quiet.count` and `quiet.streak`, and replaces `quiet.last` with the run's `completed` row unless the stored one is newer. That row's `check` is the newest check or command step in the journal that printed anything, or the newest when none did (`run_log::quiet_check`), capped like any row.
3. The waiting triggers drain, `record.json` is unlinked, and the run's home is removed, with no history row and no `Sent` write.

A crash before the unlink leaves the run owed, and the counted fire ids keep the retry from counting twice. A one-shot's run finds its row consumed and is reported as usual. The quiet summary lives on the task's record beside the `scheduled` stamps, so it is retired and rebound with the record, and `loop enable` keeps it. A failure-polarity row, from `record_transition` or a kept report, resets `quiet.streak` (`run_log::end_quiet_streak`, through `fires::reset_streak`).

Readers count quiet fires as good: `runs` adds `quiet.count`, `last` is the newer of the rows' and `quiet.last` (a row wins a tie), and the good streak adds `quiet.streak` unless a failure row is newer than `quiet.last`. Spend, the daily budget gate, and cost summaries read rows only.

`engaged` is latched in `engine::persist`, the one write every transition goes through: false at creation, true in the write that publishes the first attempt that is not a script, or one that carries a message. Withdrawal, a visit reset, restart, and resume keep it. A window or capacity wait before an attempt does not set it. Until it latches, a task's run writes no assist: the engine writes `workflow_start` when it latches, or at a terminal transition other than done. A record without `engaged`, and every hand-started run, keeps the assists it always had.

### The task record

`~/.rimz/loops/tasks.json` holds one record per task id (`TaskId`, `task_<32 hex>`) for every task this machine has fired or armed: the binding that ties it to a catalog row (scope and name), arming (enablement, a bounded pause deadline, and an automatic-disable strike reason), the strike count with the fire ids it has counted, the `scheduled` stamp of each firing checkout's newest scheduled launch (the launch proof a lost `fire-at` runner is judged by), the `quiet` summary, and per firing checkout the last fire mark ([Launch memory](#launch-memory)). `schedule/task_record.rs` is the strict read-only loader the planner, probes, views and sidebar read. `schedule/task_record_store.rs` is the only writer: one read-modify-write under `loops/tasks.lock`, a leaf lock.

A binding's scope is the machine for a config row and the workspace for a project or instance row, so a same-named task in another checkout never inherits an enable. A record is bound on its task's first state write (`TaskRecords::bind`), so a hand-written row reads as default state until it fires or is armed. Rename rebinds the record (`catalog::rebind`), so strikes, arming, fire marks and history (whose rows carry `task_id`) stay with the task. Removal and a one-off's consumption retire it (`catalog::retire`): a retired record keeps its marks, so `rimz loop show <name>` and `loop logs <name>` of a consumed one-off or a delivered wait still find it (`TaskRecords::named`), and the bookings lane its fire. A re-add under the same name mints a new id and inherits nothing. Inserting a delivery deletes a live record no row holds before it takes the name (`instances::insert_delivery`). `rimz gc` retires a live record whose row is gone, drops a settled mark whose checkout is gone, and deletes a retired record once every fire it marked is settled (`TaskCatalog::prune_records`), each only once nothing shows it (`catalog::Shown`). A mark of a gone checkout stays while a launch carrying one of the record's fire ids is alive (`launches::alive`) or a worktree marker carries one, in a room its marks name; a retired record stays for those and also while a row of the current or rotated `loop-runs.log.jsonl` names its task id, so `loop logs <name>` of a consumed one-off or a delivered wait keeps working until history rotates past it. A room whose state or worktrees do not read keeps its records.

The file is strict and versioned. An unreadable file, or one of a newer version, is never read as empty: every fire stops with the file's path and the fix (move it aside, and every task then starts armed with no strikes), `rimz loop list` shows the same error as a warning, and `rimz doctor` shows it as a task record problem.

Each fire mints a fire id (`FireId`, `fire_<task hex>_<32 hex>`) that parses back to its task id. The fire passes it to its run (`RunRecord.loop_fire`) and to a shell command's environment (`RIMZ_LOOP_FIRE`, beside `RIMZ_LOOP_TASK`), so a run reports to its task by id whatever the task is called by then.

Enabling writes the anti-replay edge, and when a timed pause expires its deadline becomes the effective last-fire edge (`ArmState::resolve`). Either way a recurring schedule waits for its next occurrence instead of replaying what it missed while held. A `fire-at` row is the exception: the planner compares its instant with the raw last-fire stamp (`fire::plan`), so a one-shot whose instant passed while it was held fires on the first tick after release.

## The display commands

`loop show` and `loop logs` read history through `run_log::task_history`, which splits fires from heard signals and applies the optional wait arming cutoff. `loop list` and `loop watch` read the same split through the held stats fold (`run_log::HeldStats::stats`, `StatsFold::refresh`). Only `SignalSkipped` rows leave the fire side: both check polarities and every refusal count as fires. Show, logs, and rowless in-flight show use this partition. `rimz stats` uses the same split, counts fires, and has no last fire for a siblings-only task. Team subscription cells therefore fall back to `heard <signal> <age>`, never a skipped run count. The heard summary counts siblings after the newest acting record (all retained history without one), while retaining the newest named sibling as evidence even when the count resets to zero. LAST RUN selects the verdict's acting record, except for a clean launch, and its logs pointer counts fires. `logs --heard` reads the retained unpartitioned order.

### A run in progress

While a consumed one-shot's run holds its lock, `rimz loop show`, `logs`, and `stop` follow the lock instead of the row. `show` searches known rooms. `logs` and `stop` fall back to the caller's project root. `run_control::in_flight_run` reads the newest non-terminal run record for the name that started once the holder took the lock, and only while the lock is held in that root. The lock decides and the record enriches: the record lands after the consume, and a hard-killed runner leaves a non-terminal record behind a free lock, which is no run.

A task with a row is looked up the same way from its own root. Every display of a genuinely executing run says `▸ running` with the time since the holder started: `list` in LAST or DONE's FIRED cell and `watch` in its next cell, and `show` and `logs` with the holder's PID and the run id, in the headline and as the last line. `show` adds the stop hint, and `show --json` carries the same reading under `running`. The running state overrides timing state.

Whether a task has a run in progress has one answer, `crates/rimz/src/harness/schedule/attention.rs::run_in_progress`: the run lock as the caller read it, or else an Active workflow run of the task in the root, since a fire's run outlives its runner and the lock. With an acting result since the row was armed, only a run created after that result's record counts. With none (a first fire, a history of skips or refusals, a re-armed wait whose results predate `armed_at`), any Active run of the task does. It returns `InProgress::Locked` with the caller's holder, or `InProgress::Run` with the run's `created_at` and whether it executes (its record carries no wait). `list` and `watch` (`crates/rimz/src/cli/loop_cmd/list.rs::TaskRow::new`), `show` text and `--json`, the rowless show, `logs`, and `read_room` all call it, and none combines the lock with run records itself.

`show` and `logs` list the room's workflow records for every task with a row, as `list` does, so a row edited mid-run (one that no longer compiles to a workflow, or an unguarded delivery) still finds the run it started.

An executing lock-free run reads `▸ running` from its `created_at` (list's `running_since`), with no PID or run id. A run waiting on its record (a capacity wait, or a deduping guard's decline held inside the run) keeps the timing state and held presentation, and still holds a failure back, so `show`'s verdict drops `failing` for it as for the lock. `stop` keeps `run_control::in_flight_run` for the holder's stop ladder and cancels lock-free runs itself. A consumed one-shot keeps a running DONE row with its real task name while its run executes, under the lock or not, and `watch` keeps its running row with no next fire. Once no run of it executes it is a retired entry.

The two lookups fail differently. A run lock that cannot be read is enrichment: `list`, `show`, and `logs` warn on stderr and render as if no run were in flight (`render::displayed_in_flight`), `watch` repaints without warnings, and `stop` fails rather than reporting no active run. A failed listing of workflow run records is not uniform: `list` substitutes an empty list without a warning, `show` of a task that runs workflows fails, and `show` of any other task substitutes an empty list. An unprobeable lock file no row claims is skipped, and an unlistable locks directory costs `list` one warning per root.

### `loop list`

`rimz loop list` builds an owned per-room model. It is loaded strictly for the caller and best-effort for other roots discovered from machine tasks and instance records. Each root has its own catalog precedence and root-filtered history fold. A record without a `root` counts in every room. Discovery opens no store. Expanded text with self waits opens each room through `Ctx::for_workspace` and reads its resolution snapshot with the command's mux hint as enrichment. Cards name agents over `addressable_agents` of that snapshot. `wait list` takes the same roster from its one resolution snapshot for both its cards and its rows' JSON `parent`. Missing or unreadable rooms fall back to stored handles, and failed pane reads use the resolution snapshot's stamped-pane fallback. JSON adds no store reads.

Missing checkout directories are a display classification, not a durable retirement.

The NEEDS YOU verdict is `crates/rimz/src/harness/schedule/attention.rs::decide`, shared with `loop watch` and the read-only reader `crates/rimz/src/harness/schedule/attention.rs::read_room`, which the sidebar may call once per room for the verdict of every task there. A gone checkout counts only while the task has not fired by `crates/rimz/src/harness/schedule/attention.rs::fired` (any launch entry of a one-off in the loaded ledger, with or without a run, which includes entries folded in from the older `loop-launches.json`), so a fired remembering one-off reads DONE. `failing` yields to a newer run in progress: a held run lock, or an Active workflow run of the task in the root created after the acting failure's record time (`crates/rimz/src/harness/schedule/attention.rs::run_in_progress`), since a fire's run outlives its runner and the run lock. A reported run's record is stamped at the run's end (`terminal_at`), so a run created at or before it, such as an `each-worktree` sibling, is not newer, nor is a Parked run. Once the retry ends and reports, its own result acts. Both producers call that rule over the workflow runs they already listed, and `list`'s row keeps the run it returns for the running display above, so the verdict and the display pick the same run.

`pr_closed` reads the waiting condition's stored readings (`TaskTimingState::Waiting`, written only once the clock pass has stamped the task's first sight) through `crates/rimz/src/harness/when.rs::WhenExpr::closed_pr_term`: an un-negated `pr[...]=merged` term reading `closed` whose expression stays false with every other term met. Routine tasks and fired tasks never raise it.

`no_forge` reads the typed key `RoomReadings` kept on the timing (`TaskTiming::no_forge_key`), never the reason's wording: a Live, unfired, enabled task whose unmet condition has a key unread because its checkout has no supported forge. One-offs and routines both raise it; it clears when the reading changes, and with the room closed there is no forge source, so it is absent. A detached HEAD reads `UnreadReason::Detached` and raises nothing. It ranks after `pr_closed`, and `parked_overrides` leaves it in place. Arming (`wait --when`, `loop add --when`, a `schedule` call's `when`) refuses a known no-forge reading through `crates/rimz/src/harness/schedule/wait.rs::read_when`.

Text and JSON classify catalog and rowless running tasks by lifecycle. Retained one-offs without a row live separately in `retired`, except one whose run executes, which is a rowless running task, and count in watch's done fold, never its table. The compiled task owns lifecycle kind, and terminal records retain it after retirement.

List text pins running DONE rows above the five newest finished entries and folds wake-ups and older DONE entries unless `--all` is explicit. Expanded wake-ups use `crates/rimz/src/cli/wake_view.rs`: self-wait cards include lost rows also shown in NEEDS YOU, then subscriptions collapse by canonical owner. Both wake-up headings count waits and subscriptions separately. `loop watch` keeps its narrower folded-row predicate. List's DONE and watch's done fold share one population and ordering timestamp. `loop watch` excludes running entries from its fold. Last acting results and newest heard siblings come from `LoopRunStats::acting` and `LoopRunStats::heard`, with no second CLI classification. List terminal wrapping is confined to lifecycle-table triggers. Shared self-wait lines are neither clipped nor wrapped by the renderer, and JSON keeps the real names.

Each list load or watch repaint resolves runtime paths and scans heartbeat freshness once per room. It reads the loop timer status at most once, shared by every row and heading, and only when a room it loads is closed. Condition tasks share `crates/rimz/src/harness/schedule/attention.rs::RoomReadings`, built on the first condition row: one room-gated forge cache, one lazy account-window reader, one condition-hold state read, and one read of the fire stamps the freshness rule compares against. `crates/rimz/src/cli/loop_cmd/list.rs::load` resolves each task's root twice, once in the root-filter pass and again while it builds the matching rows. These inputs live only for that repaint. Heartbeat readers outside it remain live. Single-task show and fire observations keep their own context, as does `crates/rimz/src/harness/schedule/attention.rs::read_room`, which builds its own `RoomReadings` and reads each of its other inputs (the catalog, the workflow runs, the launch ledger, the run locks, arming, strikes) once per call for every visible task of the room it reads.

### `loop watch`

`rimz loop watch` wraps next cells and separate attention reasons. It resolves its caller workspace once and admits entry with a fresh heartbeat or a verified caller pin for that room after checking for a terminal, so the room's own panel can start before the first heartbeat. It reloads only that room each frame and suppresses the model's enrichment warnings to keep the panel quiet.

### `loop show`

`rimz loop show` resolves an exact name in the caller's room before the other roots enumerated by `list::room_roots`, loading catalogs rather than the timing-heavy list model. Rowless in-flight runs and retired one-offs precede worktree aliases, which exclude wake-ups. Owner labels come last. Retired one-offs share list's DONE rule: at least one fire and a newest kind-stamped record of `OneOff`, with kind selection shared in `run_log`. Other retained history resolves nothing. A missing name refuses in text and JSON with empty stdout and retained-fire count, latest-fire age, and `loop logs` hints when scanned rooms hold fires. The caller's room wins, otherwise each such room gets a root-qualified hint. JSON requires a task row even for an in-flight run or retired one-off. Ambiguous text views print inspection commands rather than choosing a room or task. Only this read command widens resolution: mutations and `logs` keep the caller's room. A cross-room view names the root those commands need. The rowless scan probes each room's run lock once, warns once on failure, and passes the result to the view without another lookup.

`rimz loop show` renders the compiled lifecycle kind and timing, with the pure-AND count projected only from an observed verdict in that timing. The complete condition expression and hold appear once above the leaf block or fan-out table. Single-checkout leaves carry satisfaction glyphs or a muted question mark with cache-only unread reasons. A negated unread leaf is unknown, not true. Forge age is available only when the latest probe succeeded. LAST RUN omits an empty summary unless the record carries a `run_id` or its header names a manual, signal, or late one-shot fire (`render::write_last_run`). Blank shell output alone is not evidence. It retains fire-time readings but omits an expression equal to the current condition. Full logs retain both. A one-row recent table is omitted only when that row stands for one run, the verdict's acting run, with no folded waited or skipped fires. A `×N` row keeps the table. Manual fire observes the selected checkout solely for its unmet-condition notice, without feeding that observation into scheduled evidence or arming.

`loop show` loads the task's own room catalog and selects rows whose `loop_task` matches its name. An owner-label lookup also selects `team` bindings by full instance or team name and prints the same `SUBSCRIPTIONS` table. A task without fan-out keeps that section: each real task name keeps a row, even when `loop list` folds those subscriptions. One room-filtered run-log fold supplies the newest acting run, otherwise the newest heard signal, using the list's LAST wording. Fan-out tasks omit the section. The section leaves the parent task's health verdict as it is, and `show --json` keeps its fire-only `runs`, the `heard` summary of sibling signals, and an unfolded `worktrees` array.

## The signal vocabulary

A signal is a name, a JSON object payload, a source, and, for watched commands, an outcome. The first three persist, and [`store/event.rs`](../../../crates/rimz/src/store/event.rs) owns them as `SignalName`, `SignalSource`, and `SignalEventPayload`. The outcome does not persist, so the runtime `Signal` and its `WatchOutcome` stay in the harness and convert down through `From<&Signal> for SignalEventPayload`.

`SignalName` is lowercase dot-separated segments, each starting with a lowercase letter or digit and otherwise `[a-z0-9_-]`, at most 64 bytes. The family is the first segment. `rimz events emit --source cli` refuses the `RESERVED_FAMILIES` (`agent`, `wait`, `team`, `ci`, `pr`, `trunk`, `worktree`, `workflow`). The hidden `--source forge` accepts exactly the nine forge names, and `--source git` accepts only `trunk.moved`. Neither authenticates the caller.

| Source | Producer | Names |
| --- | --- | --- |
| `Cli` | `rimz events emit <name> --json '{…}'` | anything the grammar accepts outside the reserved families |
| `Forge` | the sidebar's PR-state refresh, which spawns `rimz events emit --source forge` on a transition ([state.md § Push channels](../sidebar/state.md#push-channels)) | `ci.passed`, `ci.failed`, `pr.opened`, `pr.merged`, `pr.closed`, `pr.behind`, `pr.conflicted`, `pr.queued`, `pr.dequeued` |
| `Git` | the sidebar's project-root trunk lane | `trunk.moved` |
| `Worktree` | successful managed worktree operations, appended and fired in-process | `worktree.created`, `worktree.removed` |
| `Lifecycle` | the elected hook drainer, from the lifecycle events it applies | `agent.started`, `agent.idle`, `agent.waiting`, `agent.failed`, `agent.ended`. `team.idle`, `team.waiting`, `team.failed`, `team.ended` |
| `Lifecycle` | the workflow engine's production host after a committed run write, and the room's workflow pass for a stranded run ([run signals](./workflow.md#run-signals)) | `workflow.moved`, `workflow.waiting`, `workflow.failed`, `workflow.ended` |
| `Team` | `rimz teams flip` and the stage owner's [resume re-wake](./teams.md#resume-re-wake) | `team.stage` |
| `Watch` | `rimz wait watch <name>` at a check-in or terminal command, PID, check, or file outcome, and the host's watch-lost rule | `wait.<task-name>` |

Hook-sourced signals fire when `crates/rimz/src/harness/hook_drain.rs::Drainer::drain` applies the ingress frame through its child, not in the hook process. Selection uses the subscriptions armed at that apply instant. A scoped hook whose host drainer is unreachable applies inline instead. Crash recovery replays keyed durable effects but does not fire lifecycle or team signals again: a fire lost between the lifecycle append and the applied cursor write is not recovered. `rimz events emit` fires in its own process, without replay to late subscribers. A busy task may retain its selected trigger under its overlap policy.

### Forge signals

GitHub-only `pr.behind` and `pr.conflicted` fire for open PRs on entry into the state, or for a changed head while the state persists, without repeating for unchanged heads. Conflict keys use the head where mergeability settled. Their payload is the `pr.merged` context with `state: "open"`, plus `pr_head`, `base` when known, and `behind_by` for `pr.behind` only. `head` stays local. The [PR producer](../sidebar/state.md#push-channels) owns detection and carry-forward. Both names inherit PR-family scoping and `branch`/`path` matching. A matching `pr.merged` subscriber records `SignalSkipped` for either sibling, while a failed match records nothing.

GitHub-only `pr.queued` and `pr.dequeued` follow the same rule with a different key: the queue entry's `enqueuedAt`, or the `createdAt` of the latest removal whose reason is not `merged` and which no later auto-merge request supersedes. They fire on a first standing reading over a continuous target and on a changed timestamp, never for a changed head. A removal already re-armed at first reading is silent. Withdrawing the re-arm restores its key and fires `pr.dequeued` again with the original timestamp. A room that opens on a standing queue state has no prior target stamp, emits nothing, and reads it through `pr.queue`, and a queued PR that merges emits `pr.merged` alone. Their payload is the `pr.merged` context with `state: "open"`, `pr_head` (always the PR head), and `base` when known. `pr.queued` adds `queued_at`, and `pr.dequeued` adds `dequeued_at`, `reason` when supplied, and `queue_checks_url` when the removal names the queue's commit. `ForgeSignal::ALL` alone admits a `--source forge` name, so a variant missing from it is emitted by the poll and refused by the child.

### Trunk and worktree signals

The sidebar trunk lane observes only the room's project-root checkout, using the configured trunk, then `main`, `master`, and `origin/HEAD`. Its five-second runtime cache is published under a dedicated single-flight lock before emitting `trunk.moved` through the detached Git-source emitter. Only a changed SHA on the same resolved trunk name fires. First sight and a renamed trunk selection reset the baseline without a signal. The lane reads only the trunk ref, never HEAD, so an unborn or detached HEAD does not stop it. In the files backend it reads loose refs and `packed-refs` in process with no fork. In a reftable repository it records the stack's `reftable/tables.list` beside the trunk: an unchanged stack under an unchanged trunk setting reuses the recorded trunk with no fork, and otherwise one bounded `git for-each-ref` runs over the trunk candidates. A pass whose refs do not resolve, or whose reftable read fails, carries the prior reading forward (`crates/rimz/src/sidebar/refresh/trunk.rs::produce_trunk_state`), so the next pass that resolves compares against the last SHA it saw. A failed reftable read records no stack, so the next pass reads again. The payload is `trunk`, `from`, `to`, and `repo`.

Worktree creation emits after the Created hook succeeds, never on reuse. Removal emits at retirement, including sweep, not on failed-creation rollback. Both append before firing through the shared in-process helper, with failures warning without failing the completed operation. Payloads carry `name`, `branch`, `path`, and `repo`. Both include `from_pr` when present, creation adds `base` when known, and removal adds `branch_deleted`. Neither family receives an implicit subscription match, and `pr.opened` keeps the PR family's path scope.

### Agent lifecycle signals

`lifecycle_signal` maps real lifecycle edges onto the five agent names. [state snapshots](../agents/model.md#state-snapshots) bypass it:

| Transition | Signal |
| --- | --- |
| `Registered`, `SubagentStarted` | `agent.started` |
| `TurnEnded`, errored | `agent.failed` |
| `TurnEnded`, otherwise | `agent.idle` |
| `AwaitingInput` | `agent.waiting` |
| `Ended`, `Lost`, `SubagentStopped` | `agent.ended` |

`Ended` takes a `Normal` transition: `crates/rimz/src/agents/lifecycle.rs::map_status` fails a `Running` or `Waiting` row and keeps any other status. `Lost` is a legacy replay marker that the state machine classifies as `Ignored` ([`agents/lifecycle.rs`](../../../crates/rimz/src/agents/lifecycle.rs)), yet it still derives `agent.ended`. Every other `Ignored` transition produces no signal. The payload carries `kind`, `session`, `status`, and `errored`, plus `handle` when the card has a name and `parent` for a subagent event. A subscription's `match` can filter on exactly those keys.

### Team signals

`team_lifecycle_signals` derives cohort edges from the same event, right after the `agent.*` derivation and only when the transitioning agent has a `team`. It is pure. The hook calls `team_stage::react_to_lifecycle`, which passes the member row from the audit projection (which retains ended rows) and the complete pending message queue, and hands over the room-wide inputs as closures. The derivation first decides from the event and the member alone whether the edge can name a team signal at all: a terminal edge, a failed turn end, an entry into Waiting, or an entry into rest. A tool use, a turn start, and a rest kept name nothing and read none of the room-wide inputs. Past that it reads the live cohort from `team_cohorts` with the set of sessions holding a pending one-shot wait, and, once it derived a signal name, the room's addressable agents from `Store::snapshot_cached`. The cached snapshot is read at most once per receipt, and only once a name was derived, so a rest entry beside a running peer reads none. A failed read warns and keeps cohort-only handle rendering without suppressing the signal.

| Name | Edge |
| --- | --- |
| `team.waiting` | the member entered `Waiting` from a non-waiting status |
| `team.failed` | the member's turn ended errored |
| `team.idle` | the live cohort is non-empty, every member is at rest (`Idle` or `Success`), and no live member has a queued message or a pending one-shot wait. Emitted only on the false-to-true edge, where the prior view overlays `prior_status` on the member |
| `team.ended` | a terminal event for the member, with no other live member left |

The payload carries `team`, `instance` (`team#channel`), `member` (the qualified handle that tripped it), and `members` with each handle and status. A live agent's handle names only that agent among the room's addressable agents at emit. An ended member whose handle would resolve to another live agent, or to several, uses `@<session id>#<channel>` instead, without the suffix for an agent with no channel. Membership is whatever `team_cohorts` counts as live for that `team#channel`, plus the transitioning member even on a terminal edge. A provider-native subagent's transition derives nothing.

`team.idle` is evaluated only on lifecycle events. Removing a pending wait emits nothing by itself (`wait cancel` checks ownership, while `loop remove` removes the instance row without that check). The owner's next turn boundary re-evaluates the cohort, and with no further lifecycle event the evaluation waits for the next member event.

A member the reaper stops (a pane closed with no lifecycle hook, [`store/writer/reap.rs`](../../../crates/rimz/src/store/writer/reap.rs)) passes through no hook, so it derives neither `agent.ended` nor `team.ended`. Its subscriptions are retired by the reconcile in [Waits](#waits) rather than by a signal: cleanup follows the durable end, and never broadens what an end emits.

`team.stage` comes from `harness::team_stage`, not the cohort derivation, and `rimz events emit` cannot produce it. Its payload carries `team`, `instance`, `from` (absent when the first flip opens the board), `to`, `owner` (absent for `Done`), `by` (a role name, `user`, or `rimz`), optional `note`, `board` (absolute path), and `at` (RFC 3339). A flip writes the board and ledger before appending the signal with `SignalSource::Team`. A re-wake appends the same signal for the current owner with `from == to` and `by = "rimz"`, without editing the board or compacting. The exec wrapper produces it on every resume of a root member (resume, restart, single-member restart, and rebirth), and root-member registration is the backstop for a start that is not a resume. [teams.md § Resume re-wake](./teams.md#resume-re-wake) owns the two triggers and their de-duplication.

The stage owner does not learn of a flip through a subscription. `team_stage` dispatches a `Type: STAGE`, `From: @rimz` message straight to the owner at the `done` boundary: prose naming the flip and a `Note:` line, or for a re-wake, prose telling the owner to continue from the board's last Progress line. When the team declares a leader and the owner is not it, the body ends with the seat's channel rule (report to the stage file, reach the user through the leader, no pane text). `Done` and a self-owned flip send no message, and an owner who is not live is woken by the re-wake when it is resumed. Explicit `team.stage` subscribers fire independently with the loop's signal body, re-wakes included.

### What persists

`rimz events emit`, the wait watcher, stage flips and re-wakes, and the hook's team derivation append a `signal.emit` event through the ordinary store commit ([store.md](../store.md#what-is-in-it)), so `rimz events follow` replays them. `agent.*` signals append nothing extra, because the `agent.lifecycle` record they derive from is already the durable trace. The durable record is the `SignalEventPayload` (name, payload, source), so a watched command's exit status travels in the fire's argv and never reaches the log.

### Firing subscriptions

`fire_signal` delivers a signal to its subscribers, in the emitting process (`crates/rimz/src/harness/schedule/signal.rs::fire_signal_with_wait`):

1. Spawn the workflow wake helper (`signal::wake_workflows`, [workflow.md](./workflow.md)). A lifecycle signal spawns it only when an active run's live session subscribes to that family (`workflow::hears_lifecycle`). Any other signal spawns it when the room has an Active workflow run.
2. Run `retire_ended_sessions` ([Waits](#waits)), which removes the instance rows of durably ended targets.
3. Load the runnable tasks whose resolved root maps to this workspace.
4. `resolve` each task's trigger against the signal, dropping `Ignore` results.
5. Drop an untrusted project row and any task whose arming is not `Live`, so a disabled or paused subscription stays quiet. A dropped `Deliver` is reported as not started.
6. On `Skip`, append a `SignalSkipped` run record carrying the observed signal and spawn nothing. On `Deliver`, spawn a detached `rimz loop run <name> --signal-json <encoded>` and return the name for the emitter to print. A watcher-originated fire waits for a watch task's run instead ([Watched commands](#watched-commands)).

Step 2 is the only instance-row write. A `Skip` leaves the subscription armed, so a sibling observation does not consume a one-shot. The runner consumes a one-shot once its delivery is dispatched, and a standing subscription stays.

There is no signal replay queue: a subscription written one second after the emit misses it. A matching busy task's runner may retain its own trigger in the backlog. Signal firing leaves `lanes/loop-fire.json` untouched. The host may stamp a signal row when it first sees the catalog, but `fire_signal` never consults that stamp. A signal reaches only the subscriptions armed in that workspace at that instant, which is what lets an emitter run with no room open.

### The watch verdict

A watch signal carries a `WatchOutcome`: a `WatchVerdict` plus its evidence (the output tail, the host path of the output file, and its byte size, physical line count, and estimated tokens in `summary`). The verdict is one enum with one renderer. A file pattern match also carries its matched line.

| Variant | `label()` |
| --- | --- |
| `Exited { code: Some(0), elapsed_ms }` | `exit 0 after 4m` |
| `Exited { code: None, elapsed_ms }` | `killed by signal after 3s` |
| `Running { elapsed_ms }` | `still running after 30m` |
| `Met { elapsed_ms, line }` (`met`) | `met after 4m`, adding ``: `<line>` `` when a file pattern matched |
| `NotMet { elapsed_ms }` (`not_met`) | `still not met after 30m` |
| `TimedOut { elapsed_ms }` (read from records only, never produced) | `timed out after 59m` |
| `Lost { detail, elapsed_ms }` | `watcher died after 3m; the command may still be running or may have died with it` |

`WatchVerdict::label` is the only place those words are written. `compose_wait`, `rimz loop logs`, and `rimz loop show` all render through it. `passed()` is true for `Exited { code: Some(0) }` and `Met`. `elapsed_ms()` is the measured run, rendered in seconds under a minute and through `theme::fmt::duration_label` above it. `is_terminal()` is false for `Running` and `NotMet`, the check-ins that bypass polarity, add no strike, and do not consume the row.

For terminal outcomes, `to_check_outcome` folds the verdict into the check machinery: `passed()` becomes the pass bit, `TimedOut` the timeout flag, and the tail the output. A `Lost` outcome's output is the log file's tail, since the label already states the cause.

`WatchOutcome` travels only in the `rimz loop run` argv and the process memory around it, so reshaping it is not a durable-format change. The verdict becomes durable one level up, in the run record's `watch` field.

## Watched commands

`TaskEntry.watch` is an untagged `WatchSpec`: a command string, `{pid}`, `{check, every, on}`, or `{file, grep?, mark?}`. A file mark records size, modification time, device, and inode. No mark means absent at arm time. `WatchSpec::describe` owns trigger text and `headline` owns the delivered first line.

`arm_delivery` stores the arming agent's name (a petname for a launched child) as `WaitMeta.reader`, creates `out/<reader>/<name>.output` with its directory, and spawns a detached `rimz wait watch <name>` with null stdin and stdout, the room's `log/wait-watch.log` (`StatePaths::wait_watch_log`, opened for append through `disk::capped_log::open` and shared by every watcher, [Daemon logs](../diagnostics.md#daemon-logs)) as stderr, and `process_group(0)`, through `child_process::spawn_detached_reaped_as_agent`: the watcher runs the agent's own command, so it keeps the agent's environment, temp unit included, where every other detached child gets the user's `TMPDIR` back.

`signal::run_watcher` takes `locks/loop-watch-<name>.lock` in the room state directory before it reloads and checks the catalog row, which closes the race with a cancel that lands before the watcher starts. The lock holds `{pid, started_at}`, and a second watcher for the same task exits without running the command. Claims, probes, and GC removal reach the lease only under its directory's `lease-gate.lock`. The gate covers the attempt and body I/O, not the lifetime hold. Gated holders publish a complete body before probes can read it, and a transient probe or GC attempt cannot make a starting watcher exit. Gate acquisition waits up to five seconds. A timeout is an error naming the gate path and a `fuser` hint, never another claimant.

The command runs in the task's `dir`, else the linked worktree it was armed from, else the project root. The watcher drains stdout and stderr into the output file and keeps a 4 KiB tail. At arm time, `cli/wait/add.rs` resolves an explicit timeout first, then no timeout when keepalive is enabled and `HarnessConfig::ping_lifetime` admits the caller's published row (falling back to its resolution row when absent), otherwise 30 minutes, independent of `loop.default-timeout`. `DeliveryTrigger::Watch.timeout` is optional and only a present value is persisted. The watcher runs to exit with an optional one-time check-in. Polled watch probes omit that check-in. A persisted timeout applies as written. Ordinary `check` and `verify` kill at their timeout. At the deadline an observed exit wins. Otherwise the watcher fires one `Running` outcome, with the tail and the output file measured so far, and keeps draining until the command exits. The check-in does not kill the command, filter on `on`, consume the row, or change strikes. In `compose_wait`, its verdict gains ` · still watching` before any output segment. `WatchVerdict::label` and loop logs print the plain label. Its body includes `Stop it: rimz wait cancel <name>` and, when a timeout is recorded, `Another check-in: rimz wait --in <timeout>`, a timer independent of the running command.

A watcher-originated fire runs `rimz loop run <name> --signal-json …` and waits for it while still holding the watcher lock, so the check-in delivery cannot overlap the terminal fire. An append or fire failure is logged and the final outcome is attempted anyway. Every other signal emitter spawns its runs detached.

For PID, check, and file specs, `signal::poll_watch` probes then sleeps: the check's `every` interval, or one second for PID and file. PID uses native `kill(pid, 0)` rather than a shell loop: `ESRCH` meets the condition, while success or `EPERM` keeps watching. A check probe runs to exit without a check-in, truncating and rewriting the output file before every run so evidence is the latest run's output. Its spec's `on` chooses success or failure. Exit 126/127 emits `Exited` and ends the wait. Otherwise polled specs emit `Met` on completion and one `NotMet` check-in evaluated between probes. A blocking check defers that check-in.

A file watch compares existence, size, modification time, and identity (`dev`, `ino`) against its arm mark. With `grep`, its `GrepCursor` holds a byte offset and the identity it was read on, starting at the arm mark (zero and no identity if absent). It restarts at zero when the identity changes or the file is shorter than the offset (a same-inode truncate that regrows past the offset within one poll is not detected), and tests only newline-terminated lines using literal case-sensitive matching. It trims a trailing carriage return. A straddling line starts at the arm byte. The whole matched line is written to the output file. `Met.line` is capped at 4 KiB, and the label renders a one-line preview. Relative paths are resolved against the arming cwd and stored absolute. The [file reference](../../reference/cli/wait.md#file---file) owns the user-facing contract.

Cancel removes the row first, then `stop_watcher` sends SIGTERM to the lock holder's process group, stopping the watcher and its command together. Non-positive PIDs are rejected, and an absent process counts as stopped. If a watcher dies without firing, the host's watch-lost rule fires the `Lost` verdict after the 30-second grace, with the output file's tail as evidence.

`signal::wait_output_path` derives `StatePaths::out_reader_dir(wait_meta.reader)/<name>.output` (`out/_unnamed/` for a row with no reader) for arming, watching, and lost-watcher evidence. `WatchOutcome::measured` records the file's byte size, line count, and estimated tokens (`utils::tokens::estimate` over at most the first 1 MiB, scaled by length beyond it), and records the host path as `output_path` in every isolation. A failed measurement warns and records a zero summary, which renders as `· no output` for command watches and no output segment for polled watches, like an empty file. Teardown keeps the file. `rimz gc` prunes it only when there is no running watcher and no write in the seven-day grace. The run record keeps the tail for `rimz loop logs`.

## Waits

A wait is a session-pinned delivery row: a `Deliver` task whose target is one live agent. RimZ writes it through `schedule::arm::arm_delivery`, from `rimz wait` and from team role bindings.

### Targets and holders

The target (`config::TaskTarget`) holds the agent's launch id, which every session of the agent carries, so the row follows the agent through a restart or molt. A row armed before targets held launch ids holds the arming session's id and follows only a swap within its kind.

`harness::schedule::pending::wait_for` matches a row to an agent's row by its launch or session, `target_holder` is the one resolution of a target to the agent's current row, and `holder_key` is the key a target files under: its holder's kind and launch, so a launch target and a legacy row of the same agent share one key.

Readers that group pending waits by target (`SessionWaits::following`, behind snapshot attachment, the orphan sweep, and the stall nudge, and the wake view behind `wait list` and `loop list`) file each row under that key over Audit rows. A Runtime snapshot drops the replaced session's row, so `following` reads the room's Audit rows only when a legacy row matches no row it was given. An agent's own `wait list`, `wait add` and `wait cancel` read its waits through `wait_of`, which asks `target_holder` over the Audit rows first, so a legacy row lists under the holder after a swap within its kind and no longer under the session it replaced.

A fire checks that holder over the Audit rows when it fires (`schedule::catalog::delivery_holder`), and records `target gone` when the agent has ended or, for a legacy row, has molted to another kind. The prepared delivery keeps the row's own target, and `crates/rimz/src/cli/loop_cmd/run.rs::execute_prepared_delivery` resolves the holder again when it sends (`PreparedDelivery::holder`), so a swap between the fire and the send reaches the new session. A session the dispatch finds gone is resolved once more before the fire records `target gone`. On the success path the one-shot row is consumed only once the wake's message record exists. Failure paths consume it too: a scheduled `fire-at` row is removed for any recorded attempt (`Fire::finish_record`), and an errored prepared delivery consumes an ephemeral row before anything is published (`TaskFire::finish_error`). A holder still starting has no addressable session, so its wake is queued under the holder's own name for its first turn boundary rather than steered.

RimZ writes delivery rows to the instance tier through `schedule::arm::arm_delivery`, which `rimz wait` and team arming (`schedule/team.rs`) call. Hand-written configuration rows can also carry a delivery target. A user shell's `wait list` lists them, in text and JSON alike, but an agent's session view does not.

### Arming and dedupe

`schedule::instances::insert_delivery` deletes a live task record no row holds under the instance lock before publishing the row ([The task record](#the-task-record)). A duplicate returns before any delete. `arm_delivery` uses one compare-and-remove rollback for later config-edit or watcher-spawn failures. The rollback can fail in turn, and then the published instance row stays. `TaskCatalog::remove` removes the definition first and then retires the task's record, for every source, so a failed definition edit keeps a user's disable or strike-out. Session retirement keeps its best-effort cleanup order below.

`DeliverySpec` carries a typed trigger, name, prompt, target, and provenance. The provenance decides what the builder accepts:

| Provenance | Accepts | Name |
| --- | --- | --- |
| `SelfWait` | a delay, a one-shot `Schedule::Instant` clock, a once condition without a hold, or a watch spec. No prompt or deadline | minted, workspace-unique `wait-<petname>` |
| `Team(instance)` | a standing signal subscription | generated ([Team bindings](#team-bindings)) |

`SelfWait` is the only provenance that writes `wait_meta`: `armed_at` and the optional `delay`. `crates/rimz/src/harness/schedule/runner/prompt.rs::compose_wait` reads it as the self-wait mark: every self wait's headline ends with ` · <label>` when one is set, a clock self wait reads `waited until <local minute>` with no verdict line, and a condition self wait's verdict is `fired after <elapsed>`. Any other delivery's text keeps no label or elapsed time. `schedule::delivery_owner` classifies records in order: team, resident loop (a row an older RimZ armed with `loop_task`, which no builder writes), self wait, then a plain loop named after its row. Its `Display` is the JSON `owner`: `self`, `loop:<name>` (the row's own name for a plain loop, the declaring task for a resident subscription), or `team:<instance>`. `schedule::watch_lost` is the display reading of a missing watcher and shares the host's `WATCH_LOST_GRACE_SECS`: a row with self-wait metadata reads `starting` through 30 seconds after `armed_at`, then `lost`, and a row without that metadata reads `lost` at once. The host's `Lost` fire measures the same grace from its own first-sight stamp in `lanes/loop-fire.json` (`crates/rimz/src/harness/schedule/fire.rs::plan`), so a display can read `lost` before the host fires. A name that belongs to a project task, or for a team row to a machine task, is refused as configuration-owned.

`rimz wait` accepts a positive delay of any length, an `--at` time (`schedule::resolve_once_at`), a `--when` expression (checked against `when::condition::condition_stages` and the window provider, as `loop add` checks it), a positive `--pid`, a polled `--check`, a `--file` with optional `--grep`, or `--run`, and resolves the live calling agent through `@me`. A user shell cannot arm or cancel. `DeliveryTrigger::Watch` carries the spec, row polarity, and check-in timeout. The timeout is `--check-in` when given. Otherwise it is none when `[harness] cache_keepalive` is on and `ping_lifetime` admits the calling agent, and 30 minutes in every other case (`cli/wait/add.rs`). A check-in sends one still-running notice and never stops the watch. The old `--timeout` flag refuses with a pointer to `--check-in`, which the delay, clock, and condition triggers refuse. A `window.*` term's reading uses `task_login(LaunchLogin::RoomDefault, kind)`, the room's current account for the caller's kind. A repeated `--when` meets the condition dedupe below, which matches a self wait only against another self wait, so the receipt names a `wait-` row. PID watches observe existence, not process identity or exit status, and reject `--on`.

The builder (`arm::build_entry`) applies no selector defaults. A team binding gets its scope defaults and the other-agent lifecycle guard from `team::binding_spec`, which calls `arm::default_signal_matches` with the member as scope ([cli/teams.md § Signal bindings at launch](../../reference/cli/teams.md#signal-bindings-at-launch)). One locked instance mutation then compares live rows of the same class (a self wait, which carries `wait_meta`, or a delivery without it) by target (`pending::same_target`, comparing `holder_key`s over the room's Audit rows: a launch target matches across kinds, a session target matches only within its kind, and a legacy session target matches its agent's launch), parsed selector, normalized matches (absent equals empty), and resolved root. A condition delivery stores one canonical joined clause and a normalized hold, and its dedupe compares the target, clause list, hold, resolved root, and scope (`TaskEntry::run_dir()`), so the same expression on two worktrees makes two subscriptions. A duplicate returns `AlreadySubscribed` and rewrites nothing: not its name, prompt, provenance, or overlays.

Arming and canceling print the caller's self view after the receipt: attention-ordered self waits, with loop and team subscriptions grouped on `also woken by`. The row set follows scope, never format. From a user shell, `wait list` is room-wide and read-only: text and JSON read the room as `loop list` does, hand-written configuration deliveries included, and text shares the expanded WAKE-UPS body with `loop list --all`. From an agent, the self view, JSON, and receipts' `pending` keep the instance-delivery rows for the calling agent, under its launch or a legacy row's session. Every JSON row carries `owner` and launched `parent`. Cancel requires a caller: a name selects any targeted row, while `--all` selects only self waits and stops their watcher groups.

Shell-command previews in `WatchSpec::subject` and `WatchSpec::headline` preserve a trailing unquoted output-redirection clause verbatim and shorten only its command prefix. Without a trailing clause they use `theme::fmt::command_preview`: at most 120 Unicode scalars, keeping the first 60 and last 59 around an ellipsis. Grep patterns, matched lines, and prompt previews use that formatter directly, while stored commands and logs keep the full text.

### Retirement

**A session-pinned instance row never outlives its target's durable end.** Retirement follows that durable fact, not any one producer of it: the lifecycle hook, the exec wrapper's exit stamp, the store reaper, worktree removal, rebirth's unrecovered stamp, and orphan-subagent reclaim all end a session, and only the first is a hook. A new producer needs no retirement code of its own. A row pinned to a launch goes once the agent has ended (`agents::state::agent_end`), even while a session that a failed bound replacement replaced is still open. A row pinned to a session goes when that session ends, and only its session-owned state is released while the agent lives on (`schedule::arm::ended_pinned_sessions`).

`schedule::arm::retire_session` (`crates/rimz/src/harness/schedule/arm.rs::retire_session_in`) works in five steps:

1. Wake the session's hibernating panes, warning on failure.
2. Remove the instance rows pinned to the kind and session, paused and disabled rows included.
3. Stop each removed row's watcher group and retire its task record, warning on failure.
4. Withdraw the session's pending idle-stop request.
5. Clear the session's [raised attention](../agents/model.md#waiting-and-asks) in `records/raised.json` (`store::raised::retire`: its ask, alerts, and human-turn stamps). A closed ask is audited as `ask.closed` with cause `retired`.

Step 2 takes every row pinned to the session. The return is the number of removed rows that nothing arms again: self waits and undeclared delivery rows, never a declared binding. A failure in step 2 returns a `RetireFailure` with a count of zero and nothing removed. A failure in step 4 or 5 returns a `RetireFailure` whose `dropped()` carries the rows step 2 already removed. Retirement never signals the calling process: `stop_watcher` skips a lock whose recorded pid is its own, so a watcher that retires its own row mid-fire finishes that fire instead of killing its process group.

A lifecycle end reaches retirement through the reconcile below, after the durable event and before event signals. `Lost` sets no `ended_at`, so a lost session keeps its rows until its end is recorded. An explicit agent-tree stop calls it for every session of each stopped agent (the members of its launch, so the waits a swap's replaced session kept for the holder go too), after each successful node stop that ends the agent: a stop that closed only a replaced session, while the agent's holder lives on, retires nothing (`crates/rimz/src/launcher/stop.rs::stop_ends_agent`). The exec wrapper runs the reconcile, and archives the agent's parked messages once the agent has ended (`message::deliver::archive_for_ended_agent`), in the same exit tail: for the session it stamps ended, and for a launch it marks failed, since a swap's replacement that fails can end an agent whose old session ended first. A swap (`agents restart`, `agents molt`) retires nothing: the agent's waits and bindings stay armed for the session that holds it now. Once the replacement binds, `schedule::arm::release_replaced_session` thaws the replaced session's hibernation and withdraws its pane's idle stop, and, when the conversation is over (a fresh restart or molt), clears its raised attention. A resumed restart continues the conversation and keeps it.

A wrapper whose session has moved on ends nothing. `resolve_own_agent_end_trace` ends the wrapper's own launch's current row (`address::launch_row` over the audit projection, an ended row included. The launch's live row on the wrapper's own pane first, since an exact-id resume of a cleared conversation can leave one launch live in two panes) and never another occupant of the pane, since a pane outlives its occupants and an earlier occupant the reaper ends just after a resume would outrank the resumed row. A launch row bound to a pane other than the wrapper's own, or to any pane when the wrapper has none, means a superseded wrapper whose replacement has already attached: it appends no `rimz.agent-ended` and retires nothing. A resume whose launch row is absent falls back to its resume target under the same binding rule. The replacement's attach precedes its provider spawn, so any tail that reads after the replacement registered sees the new binding.

`schedule::arm::retire_ended_sessions` is the reconcile that covers every other producer, and the one place the predicate is spelled: an agent row that is not a provider subagent, matches a pinned kind and session, and carries `ended_at`. A session whose agent lives on in another session (a swap's replaced session, judged by `agents::state::agent_end` over the audit rows) loses only what was its own: the hibernation wake, the idle-stop request, and its raised attention. Its rows stay for the holder until the agent ends. It acts on positive evidence only: a session a later lifecycle event revived has no `ended_at` and keeps its rows, a target with no agent row at all is left to gc, and a session the live roster protects for rebirth is never ended in the first place. It is pulled from three points: every real lifecycle hook observation whose commit appended an event, borrowing durable audit rows after that commit (`team_stage::react_to_lifecycle`), `fire_signal_with_wait` before it selects a single task, and the exec wrapper's exit tail (`agents_cmd::exec::settle_ended_agent`). State snapshots bypass this sweep, leaving it to the next real hook or signal fire. An observation that appended nothing (a side conversation's repeat hook, a read-only tool use) published nothing, so the session reaper never ran under it and no end appeared for the reconcile to find. It reads no audit rows and does no fold. The consumer is where the rule has to hold, because the sibling-skip branch returns before the fire's holder check (`catalog::delivery_holder`) and a listener whose family mostly fires siblings would otherwise never meet a liveness gate. The reconcile first reads the sessions named by instance rows, raised asks, alerts, and human turns, idle-stop requests, and hibernation entries (`crates/rimz/src/harness/schedule/arm.rs::retire_ended_sessions_in`). A workspace with none of these returns before it reads the audit rows. Any one of them alone, such as a pending idle stop or a raised ask, is enough to make it read the audit rows and retire that session.

The holder resolution (`catalog::delivery_holder` while the fire prepares, `PreparedDelivery::holder` when it sends) rejects an ended agent, and gc is the backstop for what the reconcile leaves: rows whose target has no agent row at all. An instance row is runnable or it is garbage: gc also reaps an `Instance` row whose action does not compile (a target lost to schema drift can never fire or retire), except one whose compile error is `TaskActionErr::Refused`, which it skips (`TaskCatalog::reap_catalog_deliveries`), while machine `loop.toml` and project `.rimz/config.toml` rows with an invalid action stay listed as `<invalid>` for the user to fix. Hook config, arming, reconcile, and retirement failures are logged as warnings and never fail a fire, hook, exit, or restart, and never reach hook stdout.

### Pending waits

`pending::project_pending_waits` projects armed one-shot delivery rows onto their target agents as `pending_waits`, which the sidebar and `rimz agents list` read. Timers, PID waits, watched commands, polled checks, file watches, and one-shot signal deliveries count. Standing subscriptions and recurring clocks do not. `WatchSpec` maps directly to pending `command`, `pid`, `check` (`command`), or `file` (`path`, `grep`) kinds. No command string is parsed. What a pending wait does to the displayed status is [model.md § Sleeping](../agents/model.md#sleeping), and how a card draws it is [the interface reference](../../interface/sidebar.md). Pending one-shot condition waits project as `PendingWaitTrigger::Condition`, and the sidebar renders their expression and hold with a static wait glyph. A live member's pending one-shot wait also withholds `team.idle` ([Team signals](#team-signals)).

Pending waits also feed `harness::owed::owed_wake` through `TurnWaitView::load`, holding the supervised run fold open at a clean end. Reading the catalog before the queue covers the handoff from an armed row to its wake message. Consuming a row alone does not imply the run completed.

### Team bindings

A team role declares standing subscriptions for its own seat. Each `[[agents.teams.<name>.roles]]` entry has a `signals` array of inline tables with `signal`, an optional string-valued `match`, and an optional `prompt`. The containing role is the receiver. `prepare_team` validates the selectors and explicit other-agent matches for `agent.*`. Each role's complete ordered binding list enters the executable trust hash, and an empty list leaves the hash unchanged, so moving bindings between roles needs a fresh grant.

A fresh `launch_layout` refuses a team binding scoped implicitly to the root checkout's CI or PR state, before any pane or worktree side effect, and names the fixes: an explicit branch or path match, `branch = "*"` for every checkout RimZ watches and every branch a task holds, or `-w <worktree>`. A launch from a linked worktree passes, a `--from-pr` launch skips the check, and resume does not apply it. `team = "*"` or `instance = "*"` disables the cohort default. On `team.*` this includes the four lifecycle signals as well as stage flips. Neither `handle = "*"` nor `session = "*"` satisfies the explicit other-agent requirement for `agent.*`.

After a committed lifecycle `Registered`, the hook calls `team_stage::react_to_lifecycle`, which reads the strict effective trusted config and calls `schedule::team::arm_member` for a root team member, never a subagent. It uses the member's adopted session identity, role, channel, and worktree, so launch, resume, restart, and role re-add share one registration path. All binding specs are built before anything persists. The rows carry `TaskEntry.team = "<team>#<channel>"`, target the member's launch id (`member.launch_key()`), so they follow the member through a swap that changes its kind, and deliver at the next `done` boundary. Building every spec first does not make arming atomic: a persistence failure partway leaves the earlier bindings armed.

Row names are `team-<team>-<channel>-<role>-<signal slug>`, lowercased, with dots and any character outside `[a-z0-9_-]` replaced by `-`. Repeated or colliding slugs within a role get a declaration-order `-<n>` suffix. A collision between channels in one room is accepted. Repeated registration deduplicates, and an already-subscribed manual row is not relabeled as a team row. Automatic arming never replaces machine or project configuration: a generated name that collides with a configured task is reported in hook diagnostics, and the user renames that task before the member re-arms.

## Shared start gates

A loop fire takes neither of these gates itself. Workflow agent steps read both, a workflow task's run included. An agent that a fire launches, from a shell task's command or as an agent or team task, takes no throttle turn either. They live here because their code sits beside the scheduler's. [workflow.md § Admission](./workflow.md#admission) owns the order in which a step reads them and the waits they open.

### The start throttle

`crates/rimz/src/harness/throttle.rs` admits agent starts across every room of one RimZ home, reading the machine-only `[throttle]` table from config.toml. Its one admission caller is the workflow engine: an agent step asks `throttle::try_admit` from `engine::advance` before eviction and launch ([workflow admission](./workflow.md#admission)). A loop fire, a delivery, a check, and an agent launch a fire makes (from a shell task's command or as an agent or team task) take no turn. Such a launch counts in the census below once its row exists, and nothing holds it back.

A step's `throttle = "off"` skips the machine turn, stagger, pressure, memory, disk, and the capacity check, never the two machine caps or the workflow and step limits. A start that is not machine-gated, with no cap configured and no limit of its own, returns `Attempt::Open` without writing anything. Machine-gated starts always take a turn. Workflow steps with their own limits ask the queue even for `off` and skipped starts, and their [limit pass](./workflow.md#admission) runs first.

#### The ticket queue

The queue is a directory, `~/.rimz/loops/throttle/`, behind the lock `~/.rimz/loops/throttle.lock`. A ticket file is named by its enqueue time and a UUID, so a directory listing is the queue order. A ticket records its owner (`pid` and process start token), task string, root, checkout, agent count, optional provider `kinds` and `gives_up_ms`, machine-gated scope, optional limited workflow and step scope, and one of two states. Missing scope fields mean machine-gated with no workflow limit.

| State | Meaning | Removed when (`throttle::sweep`) |
| --- | --- | --- |
| `admitted` | The start reserves its full agent count and any machine or workflow turn while launching. | Its owner is dead, or its `Turn` is dropped unreported. |
| `launched`, with the launch-report time, workspace, and launch reference | The launch committed, and its scopes wind down independently. | Machine scope: the provider reported, `TURN_CEILING` (10 s) passed since the report (`CHECK_CEILING`, 120 s, with a check configured), or the workflow stopped the attempt it launched (`throttle::release_stopped`, from the engine's `agent::finish`. A detached attempt keeps its turn, since its agent still runs). Limit scope: the first sweep after the launch report, since `engine::prepare` published the attempt the run-record census counts before the launch reported. |

A held start leaves no ticket: `try_admit_in` writes one only when a pass admits it, as `admitted`. A recheck that holds a start after its capacity check writes nothing, and the drop of that start's `Turn` removes its ticket. A `waiting` ticket an older RimZ left does not parse, so the next sweep removes it with its warning. A waiting start's durable state is its workflow record's capacity wait instead ([workflow.md](./workflow.md#admission)).

An `admitted` ticket serializes starts that share machine scope or a limited workflow name. Independently, every other `admitted` ticket contributes its full agent count to both machine caps under the queue lock, so two `off` starts cannot race through the last slot. The incoming group must fit as a whole. An automated group larger than either machine cap returns `ThrottleError::Oversized` (`throttle::check_group_size`) naming the key, cap, group size, and fix, before any temporary hold is considered. A workflow start refused this way raises `capacity`, marked `never_fits`, under either capacity setting and before it counts a visit, and a workflow run it ends reports `failed` with a strike. A loop fire's own command run has no agent step, so it never meets this. Cap hold text separates counted rows from reservations (`1 more starting`) and names multi-agent demand (`this start opens 2`).

`queue_hold` holds a start as `queue` while any other admitted or launched ticket that shares its scope is in the queue, ahead of it or behind it: a `skip` run writes its ticket without waiting its turn, so it can land behind a start still running its capacity check, and that start's recheck then holds. The text, `queued: N starts ahead`, counts the tickets ahead in its scope, and at least one. No machine limit reorders tickets. Failing check verdicts lead a joined reason, so a check failure stays visible beside a no-capacity verdict.

`off` starts have no machine FIFO place, so they may take a freed cap slot ahead of a gated start.

#### One admission pass

No admission blocks. `try_admit` decides once per call with the settings its caller read, and a held workflow step tries again on a later advance. A machine-gated, unskipped call first refuses settings that `unreadable` reports, outside the queue lock, and reads the clock after taking the lock. The lock wait is bounded (`admission_lock_wait`), and a workflow admission that times out on it is no reading: it opens a capacity wait held as `queue` only when the run has none open ([workflow admission](./workflow.md#admission)).

Its caller supplies an absolute give-up instant derived from the step's capacity policy and deadline, or none for an unbounded wait. Reloading throttle settings never changes that instant. Once a run has been held, a pass at or past that instant skips it before trying to admit, so a hold that clears at the deadline, or a recheck that wakes late, never starts the run. A capacity check cut at the give-up instant is a `wait deadline reached` hold, so no `Turn` is granted past that bound.

Each pass (`throttle::pass`), under the lock, sweeps the tickets that are over and then decides for its own start only. A ticket that cannot be parsed is removed with a warning, so one damaged file cannot hold every start. An I/O error other than not-found fails the pass with `ThrottleError`.

The pass checks the workflow and step limits first, then the machine queue for gated starts, then both machine caps. Gated starts continue through stagger, pressure, memory, and disk. Every call samples the host limits afresh: `pass` keeps a five-second reuse slot (`SAMPLE_EVERY_MS`), but both calls in `try_admit_in` hand it an empty one. A skipped claim (`Run::skip`) never waits, and records each hold it passed (limit, queue, machine, capacity check) on the attempt for `workflow show`. At most one shared machine turn is `admitted` or `launched` at a time, while independent workflow-only scopes may proceed beside it.

#### The capacity check

After the queue and host limits clear, a machine-gated admission writes its `admitted` ticket, releases the queue lock, and runs `[throttle] check` when one is configured (`throttle::check_groups`, through `check_run::run_command`: `sh -c`, `WatchDeadline::CapacityCheck`). The admitted ticket serializes machine-gated starts while the script runs. Admission then retakes the lock and passes again with its own ticket, so a start that landed during the script cannot invalidate the decision.

The script runs in the starting run's checkout, with `RIMZ_WORKTREE_PATH` set to it. The rest of its environment is `workspace::pin_env` plus `RIMZ_START_KIND`, `RIMZ_START_ACCOUNT` (empty when unresolved), `RIMZ_START_AGENTS`, and `RIMZ_START_TASK`. One check runs per distinct kind and account group, and all must allow the start.

Exit `0` is capacity, `75` is no capacity, and another exit, a signal, a timeout, or a spawn failure is an error. `check-timeout` defaults to `30s`, accepts positive `s`, `m`, and `h` durations, and is capped by the remaining wait budget. A check cut at the give-up instant produces no error verdict. After the script's leader exits, its remaining timeout bounds pipe draining and kills surviving group members. An error reason includes the status or timeout and the first stderr line.

`~/.rimz/loops/throttle-checks.json` caches the latest `at_ms`, `outcome` (`room`, `no_room`, `error`), and `detail` per kind and account, written atomically without fsync under the queue lock. A hold younger than 60 seconds (`CHECK_REUSE_MS`) is reused, and capacity is never reused. The request timestamp precedes the script's run, so time spent checking counts toward freshness. Losing the cache is safe. While a check is configured, `rimz doctor` reports groups whose latest verdict is an error, with a fix naming `[throttle] check` in config.toml.

#### Launch report and release

The turn handle crosses to the launch commit. `crates/rimz/src/launcher/execute.rs::open_fresh` calls `Turn::report_launch` right after the agent launch batch commits, before compiling panes or publishing the supervised run, through `SupervisedRunRequest.throttle_turn`. The report stamps the ticket `launched` and writes the machine, workflow, and step stagger stamps in `loops/start-stamps.json` under the queue lock. A second report, which a verify retry produces, changes nothing. A failed stamp removes the ticket rather than holding the turn for the life of the process.

Only machine-gated launches restart the machine stamp. A `--skip-capacity` run's launches restart the stamps of every scope they are gated by, and `off` launches leave the machine stamp unchanged. Queue tickets and stagger stamps use rename-atomic cache writes without per-launch fsync. The [workflow admission contract](./workflow.md#admission) describes the stamp record.

Nothing in the launching process waits after the report: whichever process sweeps the queue next releases the turn, so a helper never lingers for pacing. The provider has reported when a row carries the launch reference as `launch_id` under another `agent_id` (the hook adopted the provisional row), or when the provisional row is ended, failed, or gone (`throttle::provider_reported`). Launched tickets reserve no counts: the launch batch committed the agent rows before the report, and the machine census sees those rows.

Dropping the last clone of an unreported `Turn` removes its ticket, which is how every error path between admission and commit frees the queue. A process killed outright leaves a ticket whose owner is dead, which the next sweep removes. `throttle::reap`, which the stop ladder calls ([Stopping a run](#stopping-a-run)), sweeps the dead without a ceiling.

#### The agent census

`throttle::open` counts a full agent row when its session is not over, it is not a provider-built-in subagent, and its runtime owner is not `Dead`. A live agent whose last turn errored still counts, and turn status and compaction do not otherwise matter. `max-parallel-agents` counts these rows across `workspace::known_workspaces_read_only()`, and `max-parallel-automation` counts the subset carrying the durable [automation stamp](../agents/model.md#the-rollup). User starts count in the first bucket only. Manual loop and workflow starts, and RimZ launches from an automated agent's pane, count in both. Finished workflow and supervised-run records never remove an open row from the census.

The workspace inventory has limits. A workspace whose `workspace.json` does not read, or that loses the census's dedupe by session name, is not counted, so the machine count can run short. Canonical roots are normalized in memory without the maintenance census's repair writes or locks, and reading every state directory directly would be a new home-wide inventory. A store that cannot be read is a `store` hold naming the workspace, never a short count.

#### Resource readings

A configured pressure limit or memory floor whose source cannot be read is an error. Room judgment records a warning from `throttle::preflight`, and a machine-gated admission returns `ThrottleError::Unreadable`. The key and fix name `throttle.<key>` in config.toml, and pressure also names enabling PSI with `psi=1`. A project `[throttle]` is ignored, and room judgment records it as the skipped setting `throttle`.

Pressure is the `some` line of `/sys/fs/cgroup/<resource>.pressure` at the cgroup namespace root, falling back per resource to `/proc/pressure/<resource>` when the cgroup file cannot be read or parsed, and holds on the larger of `avg10` and `avg60`. Memory is `proc::memory`. Disk is `statvfs` at the launch checkout. `rimz loop show` reads the same path. The ticket keeps the launch checkout as its place. Nothing samples in the background.

`throttle::diagnostic_holds` gives `rimz doctor` fresh needs-a-fix readings without a ticket, the queue lock, a check run, a cache write, a workspace repair, or a diagnostic append. `crates/rimz/src/cli/doctor.rs::collect_loop` supplies machine and instance tasks plus trusted project tasks from every known room (`crates/rimz/src/workspace.rs::known_workspaces_read_only`), skipping blocked project tasks. Only the throttle feed widens: the task table still lists machine and instance tasks. Doctor reads each distinct task write path only when `min-disk` is set, reporting paths below the floor. An `each-worktree` task samples its owned fan-out checkouts instead of its run directory, which `diagnostic_holds` enumerates itself. Unavailable disk samples are left out, as in `throttle::readings`. With either `max-parallel-agents` or `max-parallel-automation` set, doctor probes the home-wide agent census and reports a failed count read. These are present problems, so no held start is required. Doctor JSON adds `loop_tasks.throttle_holds`, each with `hold` (`disk` or `store`) and `text`.

#### Holds and their kinds

A hold's typed cause is one of the twelve `ids::HoldKind` snake-case values: `capacity`, `check_failed`, `queue`, `machine_cap`, `automation_cap`, `stagger`, `workflow_limit`, `step_limit`, `pressure`, `memory`, `disk`, and `store`. `HoldKind::needs_fix()` is true for exactly `check_failed`, `disk`, and `store`. A record without a kind reads as self-clearing. The optional `hold` field keeps the cause in workflow waits, closed waits in workflow history included, and in the legacy condition capacity records below. Both durable readers decode an unknown string as absent through `crates/rimz/src/ids.rs::HoldKind::deserialize_optional` instead of rejecting the record. Retries keep a known kind until a fresh capacity reading replaces it.

An older RimZ also kept condition capacity records in the room. Nothing reads them, and `rimz gc` removes the file ([Records only an older RimZ writes](#records-only-an-older-rimz-writes)).

#### What the views read

`rimz loop list` reads Active workflow capacity waits. Self-clearing holds get HELD rows while their task keeps its normal section and NEXT counts `○ N held`. A task with a run executing instead carries the count beside its running age in its running state text (LAST, or WAITING FOR for a one-off), and NEXT keeps its next fire. A needs-a-fix hold puts the task in NEEDS YOU with its oldest such reason and a doctor hint. JSON keeps the task's section shape and its oldest durable `capacity_wait`, with the optional `hold`. `loop show` suppresses capacity rows for off, not-enabled, or paused tasks, and a checkout running the task hides only its own capacity wait. Sidebar notices use the clock match alone, so a paused task can remain there while the planner keeps its clock.

No loop fire writes a `capacity held` row or stamps `throttle_wait_ms` ([Records only an older RimZ writes](#records-only-an-older-rimz-writes)). A `throttle skipped` row comes only from a run's report. The throttle table, including its command-executing `check`, stays out of the trust hash as [machine policy](./trust.md#what-stays-outside-the-hash): a repository contributes tasks, not `[throttle]`.

### Takeover

A workflow session step's takeover and workflow admission share one occupancy read, `crates/rimz/src/harness/takeover.rs::read`. The caller supplies its runtime-scoped snapshot, with rest certificates and local-session binding, and a `CardStatus` reader before the call. The snapshot also carries resume outcomes for the reader's lazy park evidence. Runtime projection excludes rows whose owner is known dead, with two exceptions: launched children retained with a visible parent, and an unreplaced, bound failed replacement with a provisional id and a positive epoch (`store::runtime::failed_swap_holder`). Neither bypasses the liveness check below. The read resolves the checkout and each owned worktree in two forms, as given and `canonicalize`d where that resolves, and reads the clock after that discovery.

An occupant is the current row of a launch instance (`address::launch_occupants`, so an earlier conversation in the same pane is neither counted nor closed twice) that has no end, is not a provider subagent, has a pane stamp, and has runtime-owner liveness other than `Dead`. The read checks liveness again with `store::runtime::agent_liveness`, because a cached rollup can outlive its owner. `Live` and `Unknown` occupy. The row's lexically normalized working path (`AgentState::working_path`) must be the checkout or inside it by path component, and not inside an owned worktree nested there. Team, channel, and loop task play no part. Both path forms count because a provider hook records the physical cwd while a launch records the marker's lexical one, so a row matches under either form and a nested worktree excludes under either. No pane listing is read, because even an authoritative listing may omit whole live tabs: a pane without a row does not occupy, and a paneless row has nothing to close and is not an occupant. A caller may leave rows out of the read: a workflow run leaves out its own agent starter while it owes that agent the report ([workflow.md § Occupancy and takeover](./workflow.md#occupancy-and-takeover)).

An occupant blocks the takeover when it, or any unended launched child of it (wherever its cwd, with or without a pane stamp), is working: card status `running`, `waiting`, or `paused` (a recoverable provider pause or a RimZ budget park, reported alike as `is paused on a limit`), awaiting input, or compacting. `sleeping`, a parked clean turn, and `failed` (including a non-pausing provider error, a displayed provider pause the card counts as spent, or a resting agent on a model its provider refuses on that account) are settled. Both workflow admission and eviction use this reader, and a settled spent pause is stopped. A takeover can therefore stop a limit-parked agent between its window reset and auto-continue's resume nudge. The read leaves the rows as they are for the stop.

A session step reads the named destination when there is one, otherwise the run's scope. With `takeover`, a working occupant makes the step wait, and settled occupants are stopped once the launch is prepared. With `share`, the step skips the occupancy read and launches beside the occupants. [workflow.md § Occupancy and takeover](./workflow.md#occupancy-and-takeover) owns the wait, the stop judgement, and eviction.

Nothing makes the occupancy check and the pane closes atomic. The window starts at the caller's row read, includes discovery and owner probes, and ends at the closes, and a launch row reads `idle` until its first turn hook lands.

### Idle stop

Idle stop closes an agent that has a pending `rimz agents stop --when-idle` request ([`store/idle_stop.rs`](../../../crates/rimz/src/store/idle_stop.rs)) once it has rested for the requested duration with nothing owed. The decision runs cheap in the producer, then in full in the helper, and once more before the stop:

1. The producer checks the rollup terms and the clock, then spawns `agents idle-stop` at most every 30 seconds per session.
2. The helper runs `idle_stop::decide` again on fresh reads: owed wakes, queued messages, open runs, the seat's board, and pending same-kind ingress stamped after the request.
3. The helper applies the rest and debt terms to every live launched descendant the stop cascades to (`closing_with`). The clock is the root's alone.
4. The helper declines when the run the stop path would select for any of them is not terminal.
5. The helper runs the decision once more before its final request read, and the ordinary stop path follows at once.

Rest is measured from the latest of the request, the turn end, the provider marker `settled_outcome` admits, and the session's last event. That covers a turn only a marker settled, and a failed compaction. The clock keeps sub-second precision, so a stop never lands before the full duration. Provider-native subagents are not a term: a native row leaves `Running` only on its Stop hook, a superseding parent turn, or the three-hour ghost reap.

`idle_stop::started::started` reads what the stop would leave behind, grouped in step with `decide`: holding (what a held stop waits on), closing (live `rimz subagents` descendants that hold nothing), and outliving (peers down the launch chain, walked through the audit rows so an ended peer still leads to its live launches, the teams they launched, and the room's loop tasks, live launches, and non-terminal loop-fired workflow runs whose booking chain names the agent, then the live runs it started with `--detach`). The holding group reads `decide`'s terms through the same predicates (`idle_stop::debt`'s message and run tests, `owed::owing_members`, `owed::owing_teams` and `owed::owes_report_to` under `owed_wake`, the last listing each run the agent started that owes it its report as a `workflow` row), so a stop held on anything other than the agent's own running or parked turn, its clock, a compaction, a continue owed after one, or pending ingress lists what holds it (a failed or paused last turn as a `turn` row), and each thing appears once, in the first group that takes it. A wait-in-flight or prompt-in-flight hold shows as its message row. For an ended agent, `rimz agents show` keeps the outliving group alone. The read writes nothing.

A helper that declines writes nothing, so the request stays armed. Session retirement removes the request ([Waits](#waits)), and a room reset removes every request inside its commit boundary.

The hook drainer withdraws a root session's request when a human-opened `TurnStarted` has a frame timestamp strictly greater than `requested_at`. Supervised children do not withdraw. Team seats and peers with open runs do, but record no spend-ledger user input. The spend-ledger append and withdrawal share one record-aware authorship predicate, excluding Claude task notifications. Comparison and removal take the workspace lock against the current request, so a tie or re-arm after the prompt keeps it. Replay skips both writes because confirmed deliveries cannot be reproduced. A crash between the hook transaction and withdrawal can leave the stop armed, held Busy until the turn ends and the full rest elapses. The helper holds on unapplied same-kind ingress newer than the request, including another session's frame, then re-reads the request after its last decision with no intervening work before stopping. The cursor advances only after frame processing completes, so a prompt is either pending ingress or has finished its withdrawal before that final read.

## The assist log

> **Automation is accountable.** User-benefiting automation appends a durable record of its trigger, evidence, and outcome, and surfaces in `rimz stats`. Internal repairs keep durable diagnostic records ([diagnostics.md](../diagnostics.md)).

The assist log is that invariant's record: `~/.rimz/logs/assists.log.jsonl`, shared by one RimZ home, best-effort append, rotating at 4 MiB to one `assists.log.1.jsonl` predecessor. Readers fold both generations by timestamp. When an append fails, the intervention itself is the operational truth.

The redeem record also carries user-initiated redemptions under reason `manual`, for the credit ledger. They are not counted as automation assists.

`rimz stats` folds both generations, scoped to the active dashboard window, into one rollup of assists that took effect. The same outcome classification filters the default timeline: deliveries, queued child stall notices and team nudges, stops, freezes and deepening steps that reclaimed bytes, relaunches, successful window resets, completed sweeps, successful port opens, and actions that count as recorded. Held or failed attempts are counted as held beside their kind in the timeline header. Deepening steps that reclaimed 0 bytes remain recorded but are neither counted nor held. The dashboard omits held detail and zero-count categories, except that Auto-compact counts requests including held attempts. `rimz stats --json` publishes the rollup without events. `rimz stats --assists` shows the latest 50 effective timeline lines across both retained generations, newest first, folding repeated outcomes within each subject's history of an assist kind into `×N over span` lines (`over span` omitted under one second). `-n` counts lines, `older` counts records outside the shown lines, `-n 0` shows all retained, and `--all` includes held attempts and steps that changed nothing. `--json` keeps one event per record with the same outcome filter, with `-n` and `older` counting records. The complete outcome classification and projection belong to [stats internals](../stats.md#machine-readable-surfaces).

A flip compaction reads `flip compaction` in the event stream and counts toward compact commands sent only when the command was sent. A flip completing does not count a queued command. Only a member leaving its own stage for one another role owns is eligible. `Done` has no owner and never compacts. The effective `[harness] flip_compact` or role `flip-compact` threshold is evaluated before pane availability: a flip below it, or with unknown occupancy, makes no attempt and writes no record. Every attempt records the threshold, including errors and missing-pane skips, and none of these failures fails the flip.

A new smart strategy ships as one accountable slice: define its typed trigger, evidence, and outcome record. Append it from a writer outside the sidebar import graph. Fold it into the stats rollup, and add its variant and writer to the table above.
