# Loop scheduling

> The scheduler: where task definitions live, who keeps time, what one fire does, the workflow a short form compiles to, how signals and waits reach the same machinery, the recovery the host runs, and the assist log that holds every unattended intervention to account. [fleet.md](./fleet.md) is the map for this area. For users, the guide is [loops.md](../../guide/loops.md) and the flag references are [cli/loop.md](../../reference/cli/loop.md), [cli/wait.md](../../reference/cli/wait.md), and [cli/events.md](../../reference/cli/events.md).

## What the scheduler does

`rimz loop` decides when work starts; a workflow decides what the work is. A fire either delivers a prompt to an agent that is already running (an unguarded `wait` row) or starts a workflow run through `harness::workflow::create`: a named workflow, or the inline graph `schedule/compile.rs` builds from the row's short form (its agent, check, judges, verify, and `stay`). The trigger is a clock, a signal selector, a watch spec, or a state condition. `rimz wait` is the agent-facing front end over the same task rows, for delays and watches.

There is no RimZ scheduler daemon. The room host already owns shared data work ([state.md § The room data plane](../sidebar/state.md#the-room-data-plane)), and the host keeps time for loop tasks on its ordinary data tick. For schedules that must run with the room closed, a user can install one OS timer that launches a one-off `rimz loop tick` and exits; it yields every root whose room is open ([The external tick](#the-external-tick)).

Four rules follow from having no daemon, and they explain most of the module.

**Arming is not firing.** A task the host has never seen is stamped with the current time and does not fire. A room opened hours late never replays the occurrences it missed.

**A timekeeper fires each occurrence at most once.** It writes the fire stamp before it spawns the runner, so a hot tick cannot spawn the same occurrence twice, and a per-task advisory run lock stops two runs from overlapping. No lock spans the read, plan, and write of the stamp, so the guarantee rests on one timekeeper per root: a room's single host, or the external tick for a root with no fresh heartbeat ([The external tick](#the-external-tick) names the one window where both act). A start that fails keeps its stamp and the failure is recorded instead: a periodic occurrence is spent and the next tick does not retry it, while a `fire-at` row, which has no later occurrence, is dispatched again once its runner counts as lost ([Host firing](#host-firing)).

**An event fires in the process that produced it.** A clock needs a timekeeper and an event does not: whoever emits a signal resolves the subscribers and spawns their runs itself. Signal and watch triggers therefore work with no room open and never touch `lanes/loop-fire.json`. A signal is never replayed to later subscriptions, but an existing busy task can retain its trigger through its overlap policy ([The signal vocabulary](#the-signal-vocabulary)).

**A fire that reaches a decision appends exactly one history row.** Gated, skipped, overlapped, deferred, expired, delivered, completed, or errored, a fire records one `LoopRunRecord`, and that log is the durable trace of what automation did. A deferred trigger gets a separate terminal row when served, and absorbed triggers are counted on that run. A fire whose helper never started gets a `start failed` row from the launch site, in-process.

Some exits write nothing: the runner's early returns before `TaskFire` takes over ([The external tick](#the-external-tick) lists them), a scheduled fire of a task that remembers its checkout whose launch memory already holds a run ([Launch memory](#launch-memory)), a drained trigger that goes back to wait for the run still holding its scope (`TaskFirePlan::Waiting`), and a drainer that finds a held lock, an empty backlog, an ineligible task, or a task no longer live after claiming a trigger ([Waiting-trigger backlog](#waiting-trigger-backlog)). The memory exit can occur with the run lock already held.

Failures outside the CLI's terminal-error path can also leave a lock tenure unrecorded, for example a failed backlog save after acquiring the lock in `TaskFire::take_backlog`. Ordinary preparation and effect errors go through `record_task_error` instead. Unmatched refused fires for an unrecorded holder appear on a `○ no record` row in `rimz loop show` once later logged evidence of another tenure of the same lock proves that holder gone.

## The task

A task is a name, one action, and one trigger. `TaskAction::from_entry` derives the action from the persisted entry.

| Action | Entry fields | What a fire does |
| --- | --- | --- |
| `Spawn` | `agent = "<cell>"` | starts a run of the compiled graph: any check and judges, then one agent step (`turn`, `until` under `verify`, or `stay`) ([The compiled graph](#the-compiled-graph)) |
| `Deliver` | `wait = { kind, session, handle }` | sends the prompt to one pinned live session through the [message](./messaging.md) path; with a check or judge, starts a run whose message step makes that delivery |
| `CheckOnly` | `check` alone | starts a run of the shell check alone, which ends `completed` on a pass and `failed` otherwise |
| `Workflow` | `workflow = "<name>"` | starts a run for the fire's checkout, silently skips a recorded condition launch, or, for an unrecorded live holder, follows the task's `overlap` policy (`overlapped` naming the run by default) ([workflow.md § Loop tasks](./workflow.md#loop-tasks)) |

The combinations are narrow, and `TaskAction::from_entry` refuses the rest with a `TaskActionErr`. `agent`, `wait`, and `workflow` conflict, and one of `agent`, `wait`, `workflow`, or a shell `check` is required. A workflow task refuses `throttle`, `capacity-wait`, `stay`, `takeover`, `subscribe`, `check`, and `judge`, which belong to the workflow's own steps and checks. `verify` and `account` require `agent`. A judge requires `on` and an `agent` or `wait` action. `overlap` is refused on a wait delivery, an `each-worktree` task, and any one-shot ([Waiting-trigger backlog](#waiting-trigger-backlog)), and `overlap-limit` requires `overlap = "queue"` and a value of at least 1. `rimz loop add --workflow` refuses more at add, as flags (`crates/rimz/src/cli/loop_cmd/add.rs::reject_workflow_flags`): `--stay`, `--takeover`, `--subscribe`, the guard flags (`--check`, `--check-timeout`, `--judge` and its options, `--on`), `--verify`, `--max-attempts`, `--throttle`, `--capacity-wait`, `--timeout`, the launch-shape flags (`--mode`, `--effort`, `--fast`, `--no-fast`, `--account`, `--system-prompt-file`), `--budget`, `--worktree`, `--after-reset` and window conditions, and, with `--each-worktree`, a `--signal`, `--in`, `--once`, or bare `--at` trigger. `--budget-per-day`, `--surplus`, and `--surplus-after` pass. A hand-written workflow row that carries a field add refuses but `from_entry` accepts (`budget`, `timeout`, `mode`, `effort`, `fast`, `worktree`, `system-prompt-file`) still loads, and the fire ignores that field. `budget-per-day`, `surplus`, and `surplus-after` gate each run the task starts (`runner::TaskFire::prepare_workflow_admission`, under the run lock): the daily cap counts reported run costs, plus what each live run reserves (`Definition::reserved_usd`, its agent steps' `budget`), plus the next run's own reservation, and surplus reads the account of every agent step and agent check (`Definition::agent_launches`). Workflow agent steps default to `lifecycle = "until"`, keeping the layout open across turns until the check routes away; `stay` instead keeps it open until the leader exits, and `turn` opts into a one-turn attempt. The loop's `stay` flag compiles to a `stay` agent step. `verify` requires `agent`, because it compiles to the `until` step's check. `max-attempts` requires `verify`, must be at least 1, and compiles to the step's `max-visits` (3 when unset, `run::VERIFY_MAX_ATTEMPTS_DEFAULT`).

A supervised `Spawn` task (without `stay`) names exactly one agent cell: a built-in kind, a profile, or an adapter-supported virtual cell such as `claude-auto` or `codex-yolo`. `rimz loop add` rejects teams, multi-cell layouts, and command cells in this mode, because a supervised task owns exactly one pane.

A manual `rimz workflow restart <run>` restarts only that run's current agent step, not the loop task. Its replacement uses manual admission even on an automatically fired run; subsequent step visits again use the run's automatic admission rules.

`TaskShape::compile` compiles each persisted row into an action result and a timing result independently. A row with a valid action and a malformed schedule stays visible and can be fired by hand, while scheduled firing skips it.

## Where tasks live

Three sources back the catalog.

| Source | File | Holds |
| --- | --- | --- |
| `Config` | `~/.rimz/loop.toml` | per-machine automation, like a crontab; never inherited by a clone |
| `Project` | `<root>/.rimz/config.toml` under `[tasks.*]` | shared automation that travels with the repository; inert until trusted and enabled on this machine |
| `Instance` | `~/.rimz/ws/<workspace-dir>/records/loop-instances.json` | RimZ-owned runtime rows: one-shots, rows with a `deadline`, `once` subscriptions, and every session-pinned delivery, including recurring clocks and standing signals |

The instance store keeps runtime churn out of user config. An agent that arms `rimz wait --in 30m` writes an instance row, not `loop.toml`, and the row retires itself after it fires. `TaskCatalog::load(Some(root))` reads that workspace's instances and `load(None)` reads machine tasks only. Wait rows found in `loop.toml` stay `Config` rows, and machine-scope `rimz gc --all` reaps them.

The machine loader requires an absolute `root` after expanding `~` and `~/` against `HOME` (`/` when unset), without reading the cwd or filesystem. Rows with a missing, empty, or relative root leave `LoopConfig.tasks` for its serde-skipped `skipped_tasks`; their budgets are still validated. Strict and lenient whole-config loads retain one warning per skipped row in `ConfigNotices.skipped_loop_tasks`, and room judgment records it under `loop.tasks.<name>` for the sidebar and doctor. The catalog keeps skipped machine rows outside its visible and runnable maps, retaining their overlay keys and a name-only remove/rename fallback. A same-named visible row still wins; a skipped name remains taken for rename.

Instance mutation requires a readable room record. Without one, `crates/rimz/src/harness/schedule/instances.rs::mutate` treats removal, rename, and session retirement as empty no-ops before taking a lock; inserts and delivery inserts refuse.

A project task cannot make machine-local claims, so loading (`crates/rimz/src/config/effective.rs::reject_project_task_state_fields`) rejects any of `root`, `dir`, `wait`, `wait-meta`, `deadline`, `watch`, `once`, `when`, `for`, `stay`, `each-worktree`, `takeover`, `subscribe`, `loop-task`, and `booked-by` that is present, whatever its value, so `stay = false` refuses too. Conditions and staying layouts are machine-local, so none of their fields enters the project trust hash. Project rows require `every`, `cron`, or `signal`, because a one-shot would have to delete itself from a trust-hashed file.

The [booker record](../../reference/cli/loop.md#where-tasks-are-stored) is built once, when the task is added. `crates/rimz/src/cli/loop_cmd/add.rs::booking_chain` opens the task room's store and resolves the caller against its Audit rows, so a launcher that has ended still reads, and `crates/rimz/src/harness/ancestry.rs::booking_chain` walks `launched_by`, then the subagent parent, and splices in the chain a loop fire stamped on a row (`AgentState::loop_booked_by`), ending the walk there. That chain travels with the launch rather than being looked up by task name, so a fired row that was since consumed, removed, or re-added by another agent still yields the chain of the booking that fired: `crates/rimz/src/harness/schedule/runner.rs` freezes the task's `booked-by` into the run record's fire (`RunFire::booked_by`), the workflow host passes it as `StepLaunch.booked_by`, and `crates/rimz/src/launcher/execute.rs` stamps it as `LaunchParams.loop_booked_by` on every cell of the step's launch, team members included, which carry neither `loop_task` nor `launched_by`. A check of that run gets the same chain as `RIMZ_LOOP_BOOKED_BY` beside `RIMZ_LOOP_TASK` (`crates/rimz/src/harness/workflow/script.rs`), and an agent the check launches takes it from there (`crates/rimz/src/harness/schedule/runner.rs::shape_loop_owned`), since such a launch runs with no agent identity and so has no `launched_by` either. The chain is recorded rather than walked when read because ended rows leave the runtime snapshot the sidebar folds. The stamp is set just before `TaskCatalog::replace_machine`, after the workspace and the action are chosen, and every read failure counts as no caller, so it cannot fail the add or move it. A caller from another room is not among the task room's rows and records nothing.

Placement is told apart by key, not by a version. `rimz loop add` writes `dir` only for a `--workflow` task added from a linked worktree, whose runs and workflow ledger belong to that checkout (`crates/rimz/src/cli/loop_cmd/add.rs::build_task_entry`): a launching or check-only task is scoped at the project root, and its `--worktree` is stored as `fresh-worktree`, a prefix for one new tree per fire. `--stay --worktree` still writes `worktree`, the resident's seat. A stored `dir` keeps its meaning as the guard, condition and history scope (`TaskEntry::run_dir`), as does `worktree` on a non-resident agent row, one reused named tree; waits keep writing `dir` from the arming checkout (`arm::build_entry`). `TaskEntry::task_worktree` is the one reader that chooses between `worktree` and `fresh-worktree`, returning `TaskWorktree::Named` or `TaskWorktree::Fresh`. `TaskAction::from_entry` refuses `fresh-worktree` beside `stay`, `each-worktree`, `wait`, `workflow`, `worktree`, or `dir` with `TaskActionErr::FreshWorktreeField`, so every catalog load rejects such a row.

A `fresh-worktree` fire creates its tree in `crates/rimz/src/harness/schedule/runner.rs::TaskFire::prepare_fire_tree` as the last rung before `create` in `TaskFire::prepare_workflow`: after the run lock, the deadline, admission and the backlog, and after `TaskFire::live_task_run` finds no live run of the task at the project root, so a fire that meets its overlap policy cuts no tree. It goes through `crates/rimz/src/worktree.rs::create_for_loop_fire` (`LaunchBase::Team`, so trunk is fetched first; a fetch failure is kept as `FireWorktree::base_fallback`). The tree lives in `TaskFire.fire_tree`, never in `checkout`: `launch_checkout()` stays the project root. `TaskFire::fire_dir` is the run's scope, so its guards and agent work in the tree, and the inline definition marks the run with `RunRecord.fire_tree`. `crates/rimz/src/store/workflow.rs::RunRecord::firing_checkout` reads the project root for such a run, so overlap (`engine::refuse_existing`), the backlog, the history row's `checkout`, strikes and memory stay keyed on the root. The marker records `loop_task`, and `worktree.created` is emitted when the room's store exists. `TaskFire::remove_unlaunched_fire_tree` force-removes a tree no run took over, from `Drop`, so every return before `create` succeeds (a refused `create` included) removes it, then passes the removal through `crate::worktree::retire_removal` when the room's store exists, so the announced `worktree.created` gets its `worktree.removed`. From `create` on the run owns the tree, and `run_log::report_run` settles it through `runner::settle_fire_tree` whichever collection lands first, the one the ending command runs or the backstop's. Collection reports under the workspace lock, which the removal's store writes take, so settlement is a detached `rimz`: a run that never acted gets `worktree remove --force`, and an acted run gets the keep-assessed `worktree cleanup`, so a clean, landed tree goes and a tree with a pane, dirt or commits stays. A workflow agent does not own its checkout's lifecycle, so its wrapper never cleans the tree; a pane still open at the report keeps the tree until `gc`. The report row carries the launch row's `worktree`. Unattended reclamation holds a marked tree while its task's run lock is held (`crates/rimz/src/cli/worktree_protection.rs::add_fire_trees`, in `for_automatic_gc` only, probing `RunLocks::list` at the marker's repo root, a probe error counting as held), which covers the cut-to-`create` window; the live run holds it after. `rimz loop show` lists the task's remaining marked trees as `KEPT WORKTREES`.

A project task runs commands on whoever pulls it, so it enters the project trust hash ([trust.md](./trust.md)) and needs two approvals. Trust approves the config contents; the machine-local enablement record ([History, strikes, and arming](#history-strikes-and-arming)) approves that task for unattended execution here. `rimz loop add --project` writes an enabled record for its author, and a clone has no record, so the task starts disabled.

### Visible and runnable precedence

The catalog resolves two maps, and the split keeps an untrusted project task honest.

The visible map is what `rimz loop list` shows. A project definition replaces a same-named instance or machine row regardless of trust, rendered under NEEDS YOU as `blocked · project untrusted` or `blocked · project stale`, so the list shows the definition that would win.

The runnable map is what firing reads. A trusted project row replaces a same-named base row; an untrusted one never does, so the base row keeps running. The base is instance rows overlaid by machine rows only within the same resolved root. A machine row rooted elsewhere never displaces a room's same-named instance row.

On durable machine replacement, `config_edit::set_entry` compares the existing and incoming `TaskEntry::resolved_root()` values in the file being edited and refuses a different root, before writing or clearing any instance or overlay state. A missing, empty, or relative existing root takes the remove-first refusal. The root comparison comes first, so re-adding from a directory that the relative root resolves to can still replace it with an absolute root.

An untrusted project row with no same-named base row enters the runnable map, so the refusal happens where tasks execute. `fire::runnable_tasks_for`, which both the host and `fire_signal` call, drops every untrusted project row, and the trust gate in `rimz loop run` refuses one, except that a manual fire on a terminal offers an inline grant. During the untrusted window the user sees the project task, the machine task keeps running, and the two never both fire.

## Triggers

`parse_trigger` compiles the timing half of a row into one `Trigger`.

| Trigger | Entry | Fired by |
| --- | --- | --- |
| `Schedule` | `at`, `every`, `cron`, or `fire-at` | the host tick or the external tick, when `due` says so |
| `Signal` | `signal = "<selector>"`, optional `match = { k = "v" }` | the process that emits a matching signal |
| `Watch` | `watch` as a command string or a PID, check, or file spec | the detached `rimz wait watch` process, or the host's watch-lost rule |
| `Condition` | `when = ["team.stage=Done", "ci=passed"]`, optional `for = "30m"`; `provider = "claude"` when a term reads a window | the clock planner, once per true period, or once total with `once` |

A `SignalSelector` is `Exact(SignalName)` or `Family(String)`, parsed from `a.b` or `a.*` and serialized back to the same string. `*`, `a.b.*`, and `a*` are rejected, and emission refuses wildcards outright.

`parse_trigger` rejects the shapes that cannot mean anything, as `ScheduleErr` variants:

| Error | Shape |
| --- | --- |
| `TriggerConflict` | two trigger families on one row, or `when` with a `deadline` |
| `MatchWithoutSignal` | `match` with no `signal` |
| `OnceWithoutSignal` | `once` with neither `signal` nor `when` |
| `ForWithoutWhen` | `for` with no `when` |
| `BadFor` | a `for` that is not a positive `s`/`m`/`h`/`d` duration |
| `BadWhen` | a `when` clause the condition grammar refuses |
| `WindowWithoutProvider` | a `window.<span>.left` term on a row with no `provider` |
| `BlankMatch` | a match value empty after trimming; the error names the task and key |
| `WatchWithCheck` | `watch` with a separate shell check or judge |
| `BadSignal` | a selector that does not parse |
| `BadWatch` | an empty watched command or check command, an empty file path, or an empty `grep` pattern |
| `BadCheckWatch` | an invalid or zero check interval, or check polarity `any` |
| `ObsoleteCiSignal` | `ci.finished`, or a `conclusion` match on a `ci` selector; the message names `ci.passed` and `ci.failed` |

The clock shapes have their own variants from `parse_schedule`: `NoTime`, `TimeConflict`, `EveryNeedsAt`, `BadEvery`, `BadTime`, `BadOnceAt`, `PastOnceAt`, and the cron errors `BadCron`, `BadCronToken`, `UnsupportedCron`, and `CronNeverFires`.

A `Watch` row is always one-shot, and a `Signal` row is one-shot only with `once = true`. `ephemeral_lifetime` names the rows that retire themselves: any row with no repeating trigger, plus any row carrying a `deadline`, `once = true`, a `watch` spec, or a `fire-at` instant.

`Trigger::resolve` is the whole matching rule, with three outcomes:

| Trigger | `Deliver` | `Skip` | `Ignore` |
| --- | --- | --- | --- |
| `Signal` | every `match` key passes, and the selector is this exact name or this signal's family | every `match` key passes, but an exact selector names another member of the same family | a different family, or a failed `match` key |
| `Watch` | the internal `wait.<task-name>` signal for this row | never | everything else, so one watcher's completion never fires another wait |
| `Schedule`, `Condition` | never | never | always; clocks and conditions are not signals |

A `match` key compares a JSON string payload value to the raw text and any other JSON value to its compact encoding. The whole value `"*"` instead requires that the payload carries the top-level key, including when its value is `null`. Missing keys never match. Every other value is exact, so `feat/*` matches only that literal text. Thus `from = "*"` on `team.stage` excludes the first flip, whose payload omits `from`.

## Schedule shapes

| Shape | Entry | Due when |
| --- | --- | --- |
| One-shot | bare `at = "07:00"`, hand-written or stored by an older `rimz loop add --at` or `--in` | its calendar time arrives; the task then removes itself |
| Absolute one-shot | `fire-at = "<RFC 3339>"`, written by `rimz loop add --in`, a bare `rimz loop add --at`, `rimz loop add --after-reset`, and `rimz wait --in` | the stamp is before the instant and the instant is at or before now; the task then removes itself once a scheduled fire records a result, whatever it is, and a dispatch that records none is dispatched again after five minutes |
| Interval | `every = "15m"` | elapsed time since the last arm or fire reaches the interval |
| Calendar | `every = "weekday"` plus `at = "07:00"` | the first tick at or after the wall-clock time on a matching day, at most once that day |
| Raw cron | `cron = "*/15 * * * *"` | the expression `CronSpec::parse` read once into per-field bit sets matches the current minute, and the last fire was in an earlier minute; `next_after` searches day by day for 8 years (the span that reaches any 29 February), then minute by minute in the first matching day |
| Poll-until | `every = "2m"` with `check`, `on`, an agent action, and `deadline` | the interval elapses, until the check trips the action or the deadline passes |

The day mask accepts `day`, `weekday`, `weekend`, a range such as `mon-fri`, or a list such as `mon,wed,fri`. Calendar times, cron, and `--in` evaluate in the configured `timezone`, or the system zone when it is unset.

The arming stamp sets the edge each shape reads. A calendar task first seen after its time today waits for the next matching day, and a cron task first seen past a matching minute waits for the next match. A tick a few seconds late still fires a calendar task, because the comparison is at-or-after.

`Schedule::next_after` is the display counterpart of `due`. It can return a time at or before now, which means the host fires on its next tick. `TaskTiming::evaluate` layers the display states on top, and the first row that applies wins:

| State | Meaning |
| --- | --- |
| `Blocked(trust)` | a project task awaiting or stale on its trust grant |
| `Disabled(reason)` | a manual or strike disable, or a project task not yet enabled on this machine |
| `Paused(t)` | a bounded pause whose deadline is still ahead |
| `Invalid` | the timing half of the row failed to parse |
| `Listening { name }` | a signal subscription, which has no next time, stamped or not |
| `Watching { spec }` | a watch spec, whose watcher owns the timing, stamped or not |
| `Unarmed` | neither a room host nor the external tick has stamped it; an unstamped `fire-at` row reads its instant instead |
| `Due(t)` | the next occurrence is at or before now |
| `Upcoming(t)` | the next occurrence is in the future |
| `NoOccurrence` | parsed and armed, but no next time: any stamped condition row (a cron whose day of month no selected month has fails to parse instead) |

These are `TaskTimingState` values. For a condition row, `TaskTiming::with_condition` refines `NoOccurrence` from the current verdict and hold state: `Waiting { readings }` for a false verdict, `Unknown { readings }` for an unknown one, `Fired` once the stretch has fired, `Holding { elapsed, hold }` while a `for` hold runs, and `Due(now)` otherwise.

## Host firing

`fire::fire_due_tasks` runs on the host's data tick:

1. Load the runnable tasks for the room's project root, dropping untrusted project rows.
2. Keep only tasks whose normalized `root` maps to this room's `WorkspaceId`, so each room fires only its own tasks. `rimz loop add` writes a canonical absolute root. The machine loader has already skipped roots that are not absolute after home expansion; accepted roots are expanded and canonicalized before the ownership check, display, and execution.
3. Plan every task against `lanes/loop-fire.json`, the per-room map from task name to last-fire timestamp in the workspace runtime directory.
4. Write the new state, then spawn a detached `rimz loop run <name>` with null stdio for each fire. A spawn that fails records a `start failed` row for that task and is left off the fired list; the stamp written in this step stays as it is, and a later pass reads a stamped `fire-at` row by the lost-runner row below.
5. Spawn a detached `workflow advance` for each workflow run of the root that is due, paced by `lanes/workflow-tick.json` ([workflow.md § The tick](./workflow.md#the-tick)). A run is a candidate while it is active, or once finished while it still owes its loop task a report (`RunRecord::owes_loop_report`), in which case its `workflow advance` command only collects it (`run_log::collect_run`), retried with a doubling gap of one minute up to an hour while the report fails to land.
6. Spawn a detached `rimz loop run <name> --drain` for each task with waiting triggers in `records/loop-backlog.json`, at most once a minute per room (`tick_backlog_with`, paced by `lanes/loop-backlog-tick.json`). This is the crash-recovery path of the [waiting-trigger backlog](#waiting-trigger-backlog).

The plan decides each task from its stamp, first matching row wins:

| State | Action |
| --- | --- |
| no stamp, `fire-at` at or before now | fire when live (record now); otherwise keep no stamp |
| no stamp | arm: record now, do not fire |
| stamped, disabled or pause active | keep the stamp unchanged |
| stamped, schedule due | fire: record now |
| stamped `fire-at` row, stamp at or after its instant and at least five minutes old, no run-lock holder, and no scheduled history row but `start failed` since the stamp | lost runner: fire again, record now |
| stamped, watch row with no lock holder after the 30-second grace | watch lost: record now and fire the `Lost` outcome |
| stamped, not due | keep the stamp |

A `fire-at` row is the exception to arm-then-fire: it has no later occurrence, so arming it past due would strand it. `--in` resolves through `schedule::delayed_instant` (the add instant plus the delay, rounded up to the next minute) and a bare `--at` through `schedule::resolve_once_at` (the first matching instant strictly after the add instant), once per add; a stored bare `at` row stays a once-calendar row. A scheduled fire records `late_ms` on its history row when `TaskFire::new` receives a `now` two minutes or more past the instant, one tick plus spawn time, and throttle waits stay in `throttle_wait_ms`. It fires on its first live sight past the instant, and its due check reads the raw stamp rather than `effective_last_fire`, so a pause or disable through the instant fires at the next live tick instead of skipping it. The stamp is written at dispatch, before anything shows the runner ran, and only a recorded attempt removes the row, so a runner lost without a record (a start failure, a scheduled runner that found the row not live, an early error in `run_one`, a crash) would leave the row listed and dead. `fire_tasks` therefore reads the runner of each live stamped `fire-at` row whose stamp is at or after its instant and at least `FIRE_AT_RETRY_SECS` (five minutes) old: the row counts as lost when nothing holds its bare-name run lock (`run_lock::held`, the gated lease probe) and no scheduled row but `start failed` was recorded since the stamp (`run_log::has_recorded_attempt_since`). The planner fires a lost row and stamps now, so a cause that recurs costs one spawn, and one strike-neutral `start failed` row under the transient-scope host, every five minutes, with no cap. `--after-reset` resolves the instant at add through `runner::after_reset`, which runs `window_at_add`'s refusals and then refuses a lifted window, a window with no reset, and `--surplus` on the provider's longest window; a window that has not started resolves to the add instant.

### Condition planning

Conditions use the same planner pass, and only the clock tick evaluates them: a signal never does. `fire_tasks` evaluates readings before the pure planner. The host supplies `CiSource`, and the external tick supplies none. Scope is `TaskEntry::run_dir()`. Board stages come from `scratch::board_stage`, through `when::TeamStageKey`, the one parse of a `team.stage` key. Its branch form reads the board of the checkout `worktree::checkout_on_branch_cached` finds on that branch in the same 60-second `git worktree list` rows `discover_owned_cached` keeps, so evaluation spawns no git per term. CI uses the cache's exact path key: an Open or Merged PR with CI wins, then branch CI, then `none` once a successful probe found neither (unread before one). The host keeps last-known-good CI on failed probes, but a condition does not decide on it. Grammar and unknown/negation semantics are in [Conditions](../../reference/cli/loop.md#conditions).

`fire_tasks` then holds each verdict to the forge freshness rule with `crates/rimz/src/harness/when.rs::Verdict::freshen`, the floor and commit fence workflow checks use (`crates/rimz/src/harness/when.rs::forge_unread`). The floor is the task's stamp in `lanes/loop-fire.json`, its first sight or last planned fire, compared inclusively with `CiSource::checked_at`. Every forge key is unread without a `CiSource`, without a successful latest probe, or with one before the floor; bare `ci` is also unread under the commit fence, whose git reads (`CiSource::ci_fence`) run only for a true verdict on a fresh probe with a known open PR head. `fire_tasks` also skips them for a task whose carried `WhenState` records a fire on the same condition and that cannot fire again on a retry (it does not dedupe its checkout), since a fenced reading and a true one plan alike there; `fanout::inspect` and the CLI readers always run them. Each unread key lands in `Verdict.unread` with its reason and reads `None`, and `freshen` takes the Kleene truth over what remains: a known term that settles the expression still decides it, so `ci=passed || pr=merged` fires on passed CI while `pr` is stale. `plan` fires on true alone and holds an unknown verdict, whichever key is unread (a forge key, `team.stage`, or a window): no fire, its fire stamp and `WhenState` carried unchanged, as for a task that is not live. A false verdict drops the `WhenState`. `fanout::inspect` and the CLI's condition readers call `freshen` with the same stamp (keyed by `fire::scope_key` for a checkout), so `loop show` and `loop list` show a held task as unknown with each unread key's reason.

A `window.<span>.left` term reads through `when::WindowReadings`, which both callers build (the CLI renderers too, room open or not): it reads the room's logins and every account's stored kind-wide windows once, on the first window term of a pass and never on a pass without one, reads each term on the row's `account` when it has one and on the kind's room default login otherwise, and projects `ProviderCapacity::window_of_span` to the pass instant, so a window whose reset has passed reads 100 under the external tick with no fresh cache. A lifted window reads 100. The kind comes from the row's `provider` field, recorded at add by `runner::window_condition_provider` (the CLI's `add`) or by `arm::build_entry` (deliveries), because the host cannot resolve an `--agent` spec per tick; `parse_trigger` refuses a window term on a row without one. The add-time resolver, `runner::window_at_add`, owns every refusal in order (no provider, managed account selection probed through `unresolved_managed_state`, unresolvable login, no reading or an expired one, no window of that span); it reads the stored window unprojected, since projection would turn a stale cache into a full window.

`probe::probe_demand` reads the runnable catalog and arming overlay to select existing directories of Live condition tasks naming a forge key (`ci`, `pr`, `pr.queue`, `pr.mergeable`, or `pr.review`) and each directory's demanded branch selectors. It also selects Active workflow runs whose sealed specs have a forge-reading condition case, a sleep's forge-reading `when`, a run, shell, or agent check declaring a default-scoped `ci`/`pr` wake, or a step subscribing to one, through `crates/rimz/src/harness/workflow/definition.rs::Definition::forge_branches`. Conditions and conditional sleeps contribute their branch selectors; declared wakes and step subscriptions contribute checkout demand only, and an explicit `path` or `branch` match contributes none. Each run demands its canonical `record.scope.path` throughout its Active life, including steps, not only while evaluating that check. A missing project root, failed run listing, or unreadable spec warns and contributes no workflow demand.

Both git-fact and PR producers union these scopes with pane-derived paths, using the same path keys. The PR producer also deduplicates branch targets by origin repository and branch. Their rows live in `PrStateCache.branches[repo][branch]`, independent of checkout rows, and are pruned when no loop or workflow condition demands them. A missing branch row makes the repo due; pending branch CI or a queued branch PR selects its hot tier. Branch rows never enter the path maps or emit signals. A scope without a pane survives target reconciliation while its task is live or its workflow run is Active; demand ends when neither needs it. Activity and focus are pane-driven, but pending CI or a queued PR also selects the hot PR-refresh tier. The `pr` condition reads the link's Open, Merged, or Closed state directly; a missing link after a successful probe reads `none`, a missing source leaves it unread, and there is no branch-CI fallback. `pr.queue` reads the open link's merge-queue fact as `queued` or `dequeued`; without one, an open link whose facts record an auto-merge request reads `armed`, and any other link, including one no longer open, reads `none`, so `pr=open` stays true for a queued or dequeued PR. `when::ForgeKey` parses the optional selector and is the one list of the keys that read the forge cache: the parser and `evaluate` use it directly; `probe_demand` and the CLI's no-room hint ask `WhenExpr::reads_forge`.

`pr.mergeable` reads only a settled mergeability stamped with the open PR's current nonempty head; a carried answer for an older head is unread. The stamp does not include the base: an `UNKNOWN` response after only the base moves can retain a settled reading at the same head. `pr.review` reads the cached draft-first review fact, with never-fetched distinct from `none`. Both require open facts and are unread on Gitea; a successful probe that found no PR, or a merged or closed one, reads `none` for both. PR-fact keys explain a terminal link as no open PR, and unsettled or absent facts on an open link as not reported, never as no CI. The selector, parser suggestions, and wake derivation all use `when::ForgeKey`'s key set. Neither key adds a signal or changes probe cadence.

`lanes/loop-when.json` is a runtime-class map from task name to `{fingerprint, since, fired}`, retained only while true (or held by arming policy), rebuilt from runnable rows each pass. The fingerprint holds the canonical expression, parsed hold duration, and run directory; a missing or mismatched fingerprint starts a new true period. First sight creates only the fire stamp. A standing condition is not an ephemeral task; `once` makes it ephemeral.

| Stamp / arming | Verdict / hold state | Action |
| --- | --- | --- |
| none | any | Stamp now, no evaluation or hold state. |
| stamped, not Live | any | Carry both maps unchanged. |
| stamped, Live | unknown (an unread key of any kind leaves it unsettled) | Carry both maps unchanged; no fire. |
| stamped, Live | false | Drop hold state, carry stamp. |
| stamped, Live | true, no state | Start `{since: now, fired: false}`; apply the next row. |
| stamped, Live | true, not fired | Fire at `now - since >= hold` (absent hold is zero), stamp now, set fired. |
| stamped, Live | true, fired, a task that remembers its checkout (`stay`, or `workflow` with `when`) | Retry once `RESIDENT_RETRY_SECS` (5 minutes) have passed since the last fire stamp: stamp now, keep the hold start and fired bit. |
| stamped, Live | true, fired, any other condition task | Carry; no repeat until a false tick. |

A remembering task whose launch memory holds an entry for the scope never reaches this table: `scoped_tasks` drops that scope from the pass before planning.

Write `loop-fire.json`, then `loop-when.json`, before any spawn. A fire-stamp write failure aborts the pass without spawning. A condition-state write failure suppresses only condition fires, which retry on the next tick; already-stamped clock fires and lost-watch actions still proceed. Runtime teardown resets both holds and the CI cache. One timekeeper per root ([What the scheduler does](#what-the-scheduler-does)) is the synchronization boundary.

`ConditionEvidence` travels in hidden `--condition-json`, renders through `Evidence::Condition`, and is stored as the optional `LoopRunRecord.condition`: canonical `when`, optional `hold`, `held_ms`, and readings (unknown is JSON null). A condition delivery is `Type: WAIT` at the Done boundary, never a synthetic signal.

### The external tick

`rimz loop timer install` writes one user-level systemd timer on Linux or a launchd agent on macOS. Once a minute it runs the hidden `rimz loop tick`, which exits after one pass. The timer is only a clock host: it re-reads configuration every pass and leaves arming, trust, overlap locks, execution, and history to the paths above.

The tick finds roots from machine and instance task entries, the trust grants that contain project tasks, and every room holding a nonterminal workflow run; trust grants are the project-root registry, because an ungranted project task cannot run anyway. For each root it derives the same `WorkspaceId` and runtime paths a room would. A fresh sidebar heartbeat means a host owns the root, and the tick skips it. Otherwise the tick prepares the runtime directories and calls the same planner with the root supplied explicitly, so a root that has never been opened needs no workspace record for its task to arm.

The runners must outlive the tick. Under systemd the tick starts each one through `systemd-run --user --scope`, moving it out of the timer service's cgroup so the runner and any multiplexer server it births survive, and waits up to five seconds to see the child's cgroup change. That route needs the systemd user manager, which a system-level unit, a container, or a sandbox does not have, so before it walks any root the tick asks `systemctl --user show-environment`. That is the same bus connection `systemd-run --user` makes, so it tracks systemd's own rules instead of re-deriving them from the environment. Failing that, the whole pass refuses with the fix named, rather than falling back to a host the runners would not survive: no stamp moves and no row is written, so every due task fires on the first tick after the host is fixed. External runners also get their own process group, on launchd too. Host and signal fires keep their inherited process group, so interactive launch probes cannot stall on background-terminal job control.

An external fire opens the room it needs, through the callback `run_one` passes to `TaskFire::prepare`: after the scope gates, deadline, launch memory, and run lock, and before `create`. A `stay` or agent row births its room on every fire, and a check-only or workflow row on a scheduled fire; a manual workflow fire births one only for a root with no room record. Even a never-roomed root takes its runtime-only run lock first. The birth receives the fire's shell-lookup policy before later attempts lose its run mode. A fresh heartbeat skips the repair, and otherwise it uses the normal detached room entry (durable ownership, the `rimzd` dashboard, closed-agent resume off, no confirmation prompt). That birth ends no top-level agent: the ones the dead session lost stay parked for a later rebirth or explicit resume, while their non-live subagents are closed (`rimz.child-not-resumed`), because a resumed parent relaunches any children it still needs. The runner stays a per-fire supervisor outside the panes until its run starts, and the room hosts the run's agents. These paths leave the room open, so later ticks yield to its host. A `Deliver` fire still requires its pinned live session. A manual `rimz loop fire` returns once its run starts; a manual check-only fire births no room, so in a root with no room it records `start failed` from `create`'s `no room` refusal.

A hand-off that fails records what happened. Because `systemd-run --scope` enrols its own pid and execs in place, a runner that loaded is indistinguishable by pid alone from one that never started: the poll is 25 ms, so a fire that ends at once (overlapped, gated, expired) migrates and exits inside a single poll window, and the tick sees the same "child gone" it sees when the scope was never created. The run log settles it. After a child-gone the tick looks for a scheduled row for that task and root stamped at or after the instant it captured before spawning, and, for a task that remembers its checkout, for a launch-memory entry for the scope (`crates/rimz/src/harness/schedule/fire.rs::recorded_launch`). Either means the run happened and nothing is added. Neither means the run did not start, and one `start failed` row is appended. One fire, one row, in both directions. The row records that observation, not a cause: no row means either that the runner was never spawned or that it exited before it could record anything. The second case is real. `run_one` (`cli/loop_cmd/run.rs`) returns without a row on these early exits:

- an undecodable `--signal-json` or `--condition-json`
- a strict `task_catalog` load rejecting an instance the tick's lenient load tolerated
- the task missing from the catalog
- `--keep` on a workflow task
- a `resident_checkout` refusal
- a project-trust refusal
- a scheduled fire finding the task not `Live` because a `rimz loop pause` landed mid-tick
- an action that does not parse
- a `TaskFire::new` error

Each of those reads as `start failed` on the systemd tick. The five-second cgroup timeout is a warning only: the child is alive there and its outcome is unknown, so claiming either result would be a guess.

A room can be born between the tick's heartbeat check and its state write. In that one-tick window the host and the tick both plan the root against the same `lanes/loop-fire.json`. A planner that reads the stamp after the other's write sees the occurrence spent. When both read before either writes, both spawn a runner: the per-task run lock keeps the two runs from overlapping, but it does not stop the occurrence from running twice.

## One fire

`rimz loop run <name>` is hidden. After CLI trust and action validation it hands the fire to `schedule::runner::TaskFire`, which owns one fire from its start time through exactly one history transition. `TaskFire::prepare` takes one of two paths by the row's `CompiledAction`, and the CLI reports the typed result back.

An unguarded `Deliver` row walks `TaskFire::prepare_wait`: the task's `budget-per-day` (`run_log::daily_budget_gate`), the account, scope-cap, provider, and surplus gates (`prepare_scope_gates`), the run lock, the stored `deadline`, a watch's verdict, then the delivery. Every other row walks `TaskFire::prepare_workflow`, which starts a workflow run. Everything that can refuse cheaply refuses before anything expensive or observable happens.

| # | Gate | Records on refusal |
| --- | --- | --- |
| 1 | a watch's terminal verdict against the row's `on` | `skipped` |
| 2 | for an agent row, the pinned `account`, the room-fleet and provider-account [scope caps](./budget.md#the-fail-fast-gate), and the exact managed-launch provider quota, for each cell a `stay` layout opens (`prepare_layout_scope_gates`); for a row without `stay`, the kind's hooks preflight follows (`prepare_agent_scope_gates`) | `account skipped`, `budget skipped`, or `error` |
| 3 | a stored `deadline` | `expired` |
| 4 | launch memory, on a scheduled fire of a task that remembers its checkout | nothing (`AlreadyLaunched`) |
| 5 | the per-task run lock, the admission lease | `overlapped`, or `deferred` under a retaining policy |
| 6 | the task's `budget-per-day` and `surplus` / `surplus-after`, under the lease (`prepare_workflow_admission`), so a fire they would skip births no room | `budget skipped` or `surplus skipped` |
| 7 | room birth, launch memory again, then gate 6 again under the task's budget lock, where it decides | gate 6's, or nothing |
| 8 | a stop mark naming this holder (`reconcile_backlog`) | `canceled` |
| 9 | `create`, which refuses while the task's run is live in the scope (`WorkflowErr::Exists`) | the `overlap` policy's `overlapped` or `deferred` (`prepare_overlap`) |

A refused fire is spent. Only a scheduled trigger that found the lease held, or found the task's run live at `create`, can enter the [waiting-trigger backlog](#waiting-trigger-backlog), and only under a retaining `overlap` policy. With `overlap` unset or `skip`, that trigger is spent too. A retaining trigger that finds no room in the queue records `overlapped` with `queue full (<count>/<limit>), skipped`. Manual fires never enqueue. The lease covers admission alone: once `create` returns, the fire records `launched` with the run id, appends the `workflow_start` assist, records launch memory for a remembering task, and releases the lease, so the live run, not the lease, is what a later fire overlaps. `replace` cancels the blocking run in a detached `rimz workflow cancel` helper (`TaskFire::cancel_blocker`), and the waiting trigger starts when that cancel command collects the run's report. A drained trigger whose blocker still runs goes back to the head of its queue and writes no row.

Gate 6 trips when the day's reported run costs, plus what each live run of the task reserves (`live_reservation`, read from the run's sealed definition, so a deployed source edited since cannot lower it; an unreadable seal fails the fire rather than count zero), plus the next run's own reservation (`Definition::reserved_usd`, its agent steps' `budget`), would exceed the cap (`run_log::reserved_budget_gate`). A manual fire runs it too. Each checkout of an each-worktree task fires under its own lease, so a capped task's fire also holds the task's budget lock (`launch_ledger_store::hold_budget`) from its deciding read until `create` has published its run, and the next checkout's read counts it. Surplus reads the account of every agent step and agent check (`Definition::agent_launches`), and of each cell a team or multi-cell step launches (`plan::resolve_agent_cells`), on the step's account or the cell's own, as the engine's start groups count them.

Gate 2 resolves the task's login once: the row's `account`, else the room's current account for the kind. The scope caps, the hooks preflight, and the compiled agent step all use that resolution. An explicit pin retains the definition's provider and model, without availability-based tier fallback. Unpinned tasks retain availability-based routing. The gate skips rather than errors because the fix is outside the task: the status cache holds only a room's current account and the accounts its agents run on (`RoomLoginSet::in_use`), so the logged-out skip needs a positive record and an account with none proceeds. A home without trusted hooks passes this gate and fails the preflight as `error`. `TaskFire::finish_error` records a pinned fire's unresolved login as the same `account skipped`, by downcast and with the gate's wording. Every other error, and any error on an unpinned task, stays `error`.

A fire takes no [start throttle](#the-start-throttle) turn itself: each agent step of its run asks for its own turn before eviction and launch, and command steps and checks never do ([workflow admission](./workflow.md#admission)). A manual fire creates its run with `manual` set, so its steps skip capacity waits (a queue-lock timeout aside) while limited steps still claim a turn to count and stamp workflow and step stagger, and it bypasses launch-memory dedupe.

A closed gate adds no strike. The surplus gate fails closed: an account with no window reading keeps it shut, because spending against an unknown budget is the failure the gate exists to prevent.

### Waiting-trigger backlog

`schedule/backlog.rs` is the strict sidebar-safe reader of `records/loop-backlog.json` (version `1`), resolved through `StatePaths::class_path` with `Class::Records`. `schedule/backlog_store.rs` owns locked mutation through `paths.lock_path("loop-backlog.lock")` and `write_temp_then_rename`. Each task key carries `triggers` (`arrived_at`, optional `signal` with name and payload, `absorbed`, and optional `from_arrived_at`) plus optional `stopping` (`pid`, `started_at`, `cause`: `stop`, or `replace` on a mark an older RimZ wrote). Empty tasks with no stop mark are pruned. A stop persists its mark before cancellation or signaling; both the runner and ladder compare the whole holder identity, ignoring stale marks.

Every non-skip run-lock acquisition, enqueue decision, and release shares that backlog lock. An arrival probes the run lock inside the critical section: a lock now free is acquired rather than treating an earlier observation as a refusal. `arrived_at` is the trigger's firing time, not the moment its runner took the backlog lock: racing runners reach the lock out of firing order, and ordering by the lock would merge a range with the wrong `from` or `to`. `signal::fire_signal_with_wait` stamps each emit once and hands that stamp to every subscriber's runner inside `--signal-json`, where `TaskFire::with_arrived_at` carries it; a clock fire, or a signal from an emitter without the stamp, falls back to the runner's start. `TaskBacklog::enqueue` keeps triggers sorted by that stamp, stably, so equal stamps keep lock order. Queue arrivals insert by firing time and run the earliest pending trigger; coalescing arrivals run as the newest, absorbing the slot. Manual fires acquire and release through the same protocol without enqueueing or consuming an existing slot. No non-skip check or effect runs before acquisition, including in a never-roomed root.

Coalesce and replace retain one newest trigger; queue retains up to `overlap-limit`, default `10`. Replace records its `deferred` row naming the blocking run, then cancels that run at once, with no TERM grace, through a detached `rimz workflow cancel` (`crates/rimz/src/harness/schedule/runner.rs::TaskFire::cancel_blocker`, reason `replaced by a newer trigger`). The run's report drains the waiting trigger once the run is terminal, so the replacement never starts beside it. A parked run is canceled the same way, strike-neutral, while coalesce and queue wait for its report. A budget stop ends the run, whose report records `budget exceeded` and drains the next trigger. Merging counts absorbed triggers and keeps the newest signal and payload, except that matching signal names and payload keys other than `from`/`to` preserve the oldest `from` when both carry those two keys. `WaitingTrigger::absorb` orders the pair by firing time whichever arrived second, and records the kept `from`'s firing time in `from_arrived_at`: the slot's own `arrived_at` is the newest trigger's, so a third trigger arriving out of order compares against the `from` already kept rather than overwriting it. The fire reconciles the slot before `create` (`TaskFire::reconcile_backlog`); throttle admission happens inside the run, after the fire has ended. The trigger the fire serves once the run lock and the reconcile have settled it is the one the run's history row names and the one its launch prompt carries: its signal and payload, with the absorbed count only on the row.

On release, a lock-holding runner whose fire neither created a run nor met a live one spawns one fresh `rimz loop run NAME --drain` when triggers wait, then unlocks while still holding the backlog lock, even when nothing waits. This closes the empty-backlog/release gap. A fire that created a run, or deferred behind one, leaves the drain to that run: `run_log::report_run` spawns the drainer once the run reports (`drain_waiting`). The drainer takes the run lock and pops the head under the same lock (`TaskFire::take_backlog`), rechecks arming and trust, then walks the same fire ladder as any fire at its own time. Checks and throttle turns happen inside the run it starts. A non-Live task drops the trigger with no row. A busy or empty drainer also exits without a row. A paced scheduler tick reads the durable backlog and spawns drainers for crash recovery without probing run locks or importing runner mutations into the sidebar graph. Removal and redefinition clear backlog entries; rename moves them. If hand-editing its file removes a task, makes its action fail to compile, or leaves it a task that could not have retained triggers (no `overlap`, `skip`, or a shape that refuses the setting), the next drain drops its entire backlog entry, including any stop mark, under the backlog lock and exits successfully without a history row. Pause and disable keep the record for drain-time disposal.

### The run lock

The run lock is `locks/loop-run-<name>.lock`, separate from `lanes/loop-fire.json`, holding the holder's `{pid, started_at}`. An `each_worktree` fire locks per launch checkout instead, as `locks/loop-run-<name>-<workspace id of the checkout>.lock`, so launches into different checkouts do not overlap. The kernel releases a lock when the runner exits or crashes, and display probes read it without rewriting it. Claims, probes, and GC removal share the directory's `lease-gate.lock`, so a transient probe or GC attempt never makes a fire see `Overlapped`. One snapshot answers for a root: `runner::RunLocks::list` lists the root's `locks/` directory once and probes each `loop-run-*.lock` entry once, keeping every outcome per file, so one entry that cannot be probed costs only the names that claim it. A task claims its bare name and every per-checkout name whose suffix parses as a workspace id, and it is running when any file it claims is held. With several held the snapshot reports the earliest-started holder, a holderless lock last. A held file that none of the root's rows claims is a row-less run, named by the file's whole stem: a supervised one-shot holds only the bare lock, so the stem is the name `show`, `logs`, and `stop` resolve back to that file. The display state, `in_flight_run`, and `stop_task` all answer from the snapshot, and one function spells the file name for the acquiring side and the lookup alike.

### Stopping a run

`rimz loop stop` runs two stops (`crates/rimz/src/cli/loop_cmd/stop.rs::stop`). `runner::stop_task` first stops a fire still holding the admission lease. Then `cancel_workflow_runs` cancels each live workflow run the task started (`RunRecord::started_by`) through `rimz workflow cancel`, going on past a run that fails to cancel and failing the stop with every such error, joined with a pane that stayed open, once all are tried; and each run's own report records its end and starts the next waiting trigger. `stop_task` is keyed by task name and root rather than a loaded row, and the CLI passes a supervised cancellation in as a closure:

1. Look the task's held lock up, including runtime-only locks before room birth; with none held it reports no active run. Re-probe under the backlog lock and persist the holder's stop mark. Every wait follows the marked identity, so an immediate drainer taking the file does not hide the old holder's release.
2. Cancel the newest active supervised run that carries the task's name and wait up to five seconds, unless the holder's recorded action is check-only, which skips this initial wait.
3. Recheck the holder, send SIGTERM, and wait up to five seconds after the signal. The lock stays held throughout.
4. A holder that still owns the lock is not escalated to SIGKILL: the error names its PID and the lock path, and waiting triggers remain. After a release the ladder waits out the rest of the signal grace for the holder to read dead, then reaps the throttle queue.

A mark records that a stop was asked for, not that it took effect. The lease holder reads it under the backlog lock after admission and before `create` (`TaskFire::reconcile_backlog`): a mark naming its holder there starts no run and absorbs no waiting trigger, and the fire records `canceled` and releases, so the drainer serves the trigger. A mark written after that read finds the run created, and `cancel_workflow_runs` stops it.

The runner writes its terminal row and releases under the backlog lock, so a stop cannot mark an already-recorded fire in the record/release gap. That writer always clears a matching mark. The ladder writes only if its mark survives release, through the strike-neutral `record_stopped`. Private run-lock metadata retains the compiled lifecycle kind and action kind, so stop uses the holder's own definition even after its catalog row changes or disappears. The writer spawns a drainer when triggers wait, and `loop stop` reports the waiting count without clearing it.

### Consuming a one-shot row

An ephemeral task removes its own row once `create` returns its run, so a one-shot whose run then fails is not retried; a row with a stored `deadline` instead lives until a run acts, which the run's report decides. A delivery removes the row once dispatch returns, whether it succeeded or errored, so the wake's message record exists before its row disappears and turn-completion waits never see the agent rested in between ([messaging.md § The shared turn reader](./messaging.md#the-shared-turn-reader)). A crash between dispatch and removal leaves the row to fire again. A scheduled fire of a `fire-at` row removes the row in `TaskFire::finish_record`, whatever its result, so a gate skip or an overlap ends it too; a manual `rimz loop fire` leaves it. A spawn that never starts records `start failed` without reaching the runner, and a runner that exits before recording records nothing; either way the row stays, and the pass dispatches it again once the runner counts as lost ([Host firing](#host-firing)). A deadline row expires without delivery once its deadline passes. A watch check-in is nonterminal and leaves the row in place; the final outcome consumes it.

### The start throttle

`throttle.rs` owns start admission across every room of one RimZ home, reading the machine-only `[throttle]` table from config.toml. A loop fire takes no turn itself; the workflow agent steps of the run it starts ask the queue before eviction and launch ([workflow admission](./workflow.md#admission)), and a delivery or a check never does. Task and step `throttle = "off"` skips the machine turn, stagger, pressure, memory, disk, and capacity check, never the two machine caps or workflow/step limits. An ungated start without any applicable cap or limit returns `Open` without writing anything; machine-gated starts always take a turn. Workflow steps with their own limits ask the queue even for manual and `off` starts; their [limit pass](./workflow.md#admission) runs first. A verify retry is the same run and is not gated again.

`records/loop-capacity-waits.json`, resolved with `StatePaths::class_path(.., Class::Records, ..)`, holds condition capacity records: task → checkout → `{since, first, last, count, kinds, reason, hold?, gives_up_at, gave_up}`. No fire writes one, and neither the planner nor any view reads it: a loop run's capacity wait is its agent step's workflow wait. Only catalog rename and removal read the file an older RimZ wrote, through the strict, read-only `launch_ledger::load_capacity`. `launch_ledger_store` writes under `loop-capacity-waits.lock` through the durable rename path. Catalog redefinition and removal clear the task; rename moves it.

The optional `hold` field retains the typed cause in condition capacity records and workflow waits, including closed waits in workflow history. It shares the ticket's twelve `ids::HoldKind` snake-case values: `capacity`, `check_failed`, `queue`, `machine_cap`, `automation_cap`, `stagger`, `workflow_limit`, `step_limit`, `pressure`, `memory`, `disk`, and `store`. `needs_fix()` identifies exactly `check_failed`, `disk`, and `store`; an older record without a kind reads as self-clearing. Both durable readers use `crates/rimz/src/ids.rs::HoldKind::deserialize_optional` to decode an unknown string as absent instead of rejecting the record. Retries preserve a known kind until a fresh capacity reading replaces it. A workflow admission that times out on the queue lock is no reading: it opens a wait held as `queue` only when the run has no capacity wait, and leaves an open one as recorded ([workflow admission](./workflow.md#admission)).

Clearing capacity memory is best effort: a read or decode failure warns with the record path but does not fail the catalog change.

`loop list` joins condition records, live room tickets, and Active workflow capacity waits. Self-clearing starts get HELD rows while their task keeps its normal section and NEXT counts `○ N held`; a genuinely running task instead carries the count beside its running age in its running state text (LAST, or WAITING FOR for a one-off), and NEXT keeps its next fire. A needs-a-fix start puts the task in NEEDS YOU with its oldest such reason and a doctor hint. JSON retains the task's section shape and oldest durable `capacity_wait`, adding optional `hold`. `loop show` suppresses capacity rows for off, not-enabled, or paused tasks, and a checkout running the task hides only its own capacity wait, not other checkouts' waits. Sidebar notices use the clock match alone, so a paused task can remain there while the planner retains its clock.

A task's `capacity-wait`, a positive `s`/`m`/`h`/`d` duration or `forever`, compiles onto its agent step as `admission.give-up`. Unset, the step waits forever whatever the trigger (`crates/rimz/src/harness/workflow/engine.rs`, the `gives_up_at` stamp), and a step that gives up follows its default `on.capacity` route to `@failed`, which the run's report records as `failed`, a strike.

The queue is a directory, `~/.rimz/loops/throttle/`, behind the lock `~/.rimz/loops/throttle.lock`. Each waiting run owns one ticket file named by its enqueue time and a UUID, so a directory listing is the queue order. A ticket records its owner (`pid` and process start token), required task string, root, checkout, agent count, optional provider `kinds` and `gives_up_ms`, machine-gated scope, optional limited workflow/step scope, and one of three states. Missing scope fields mean machine-gated with no workflow limit:

| State | Meaning | Removed when |
| --- | --- | --- |
| `waiting`, with the last blocking reason | The run has not been admitted. | Its owner is dead, or its give-up instant is reached. |
| `admitted` | The run reserves its full agent count and any machine or workflow turn while launching. | Its owner is dead, or its `Turn` is dropped unreported. |
| `launched`, with the launch-report time, workspace, and launch reference | The launch committed; its scopes are winding down independently. | Machine scope: provider report or `10s` since report (`120s` with a check). Limit scope: the first sweep after the launch report, since `engine::prepare` published the attempt the run-record census counts before the launch reported. |

An in-flight ticket serializes starts sharing machine scope or a limited workflow name. Independently, all other `admitted` tickets contribute their full agent counts to both machine caps under the queue lock, so two `off` starts cannot race through the last slot. The incoming group must fit as a whole. An automated group larger than either machine cap returns a typed `ThrottleError::Oversized` naming the key, cap, group size, and fix before considering temporary holds. A refused workflow attempt ends as `died`, never taking `on.capacity`. Cap hold text separates counted rows from reservations (`1 more starting`) and names multi-agent demand (`this start opens 2`). Launched tickets no longer reserve counts: the launch batch has committed the agent rows before `Turn::report_launch`, and the machine census sees those rows; the workflow and step census counts the attempt the run record published before the launch. A launched ticket releases each scope independently. Workflow and step limits never bypass the machine caps and apply without any machine throttle configuration.

`Turn::report_launch` writes machine, workflow, and step stagger stamps in `loops/start-stamps.json` under this lock; dropping an unreported turn writes no stamp. Only machine-gated launches restart the machine stamp. Manual limited launches reserve their workflow scope without waiting, record any skipped limit hold on the attempt for `workflow show`, and restart workflow and step stamps, not the machine stamp; `off` launches also leave the machine stamp unchanged. Queue tickets and stagger stamps use rename-atomic cache writes, not per-launch fsync. The [workflow admission contract](./workflow.md#admission) describes the stamp record.

No admission blocks: `try_admit` decides once per call with the settings its caller read, and a held workflow step tries again on a later advance. A machine-gated call first refuses settings that `unreadable` reports, outside the queue lock, and reads the clock after taking the lock. Its caller supplies an absolute give-up instant derived from the task's capacity policy and deadline, or none for an unbounded wait; reloading throttle settings never changes that instant. Once a run has been held, a pass at or past that instant skips it before trying to admit, so a hold that clears at the deadline, or a recheck that wakes late, never starts the run. Each gated pass, under the lock, sweeps the tickets that are over and then decides for its own ticket only. A ticket that cannot be parsed is removed with a warning so one damaged file cannot disable every loop through repeated error strikes. An I/O error other than not-found still fails the pass with `ThrottleError`; `throttle::held` leaves unreadable tickets out of the display. At most one shared machine turn is `admitted` or `launched`; independent workflow-only scopes may proceed alongside it, and manual limited claims never wait. A waiting `capacity` or `check_failed` hold lets candidates whose provider kinds are disjoint from the hold's `kinds` pass. No other machine limit reorders tickets. `off` starts have no machine FIFO place, so they may take a freed cap slot ahead of a gated waiter. The pass checks workflow/step limits first, then the machine queue for gated starts, then both machine caps; gated starts continue through stagger, pressure, memory, disk, and the off-lock check. A blocked host-limit verdict is reused for up to five seconds unless the settings change; stagger is checked each pass. Workflow limits are sampled separately before machine queue order, and their in-flight scope lasts until the launch is reported.

A queue hold caused only by capacity-scoped waiters inherits their held kinds, so more same-kind waiters do not stop disjoint kinds passing. It also carries the first predecessor's reason for its cause, with `check_failed` taking precedence over `capacity`. If any blocking waiting predecessor needs a fix (`check_failed`, `disk`, or `store`), the follower takes the first such predecessor's kind and text, even beside a held turn or mixed queue barriers. That blocker can belong to another room. Only the provider-only path retains non-empty `kinds`; every other propagated hold has empty `kinds` and never permits disjoint starts to step over it. Failing check verdicts lead a joined reason, so a check failure remains visible even beside a no-capacity verdict. A held turn or another kind of queue barrier never inherits that step-over.

`try_admit` evaluates a candidate at the queue's tail once, returning open, a `Turn`, or a hold with reason text and provider kinds. A hold leaves no ticket. Reaching the run's give-up instant, a check cut there included, is a `wait deadline reached` hold, so no `Turn` is granted past that bound. `look` evaluates the same tail without ever writing a ticket; its check is speculative, not a reservation. Both share the blocking entry's queue and host-limit pass.

After queue and host limits clear, a machine-gated admission writes `admitted`, releases the queue lock, then runs `[throttle] check` through `check_run::run_command` (`sh -c`, `WatchDeadline::CapacityCheck`) when configured. The admitted ticket serializes machine-gated starts while the script runs. Admission and ticket-free inspection resample their limits after off-lock scripts, so an intervening start cannot invalidate the decision. The script receives `run.checkout` as cwd and `RIMZ_WORKTREE_PATH`: the task's `dir` or root, or the selected checkout for an `each-worktree` fire, never a task's named `worktree` or its fire's fresh worktree. The other environment is `workspace::pin_env` plus `RIMZ_START_KIND`, `RIMZ_START_ACCOUNT` (empty if unresolved), `RIMZ_START_AGENTS`, and `RIMZ_START_TASK`. One check runs per distinct kind/account group and all must allow the start. Exit `0` is capacity, `75` is no capacity, and another exit, signal, timeout, or spawn failure is an error. `check-timeout` defaults to `30s` and accepts positive `s`/`m`/`h` durations; the remaining wait budget caps it. A check cut at the give-up instant produces no error verdict. After the leader exits, its remaining timeout bounds pipe draining and kills surviving group members. Guards keep their existing drain policy. Error reasons include the status or timeout and the first stderr line. `~/.rimz/loops/throttle-checks.json` caches the latest `at_ms`, `outcome` (`room`, `no_room`, `error`), and `detail` per kind/account, atomically without fsync under the queue lock. Holds younger than 60 seconds are reused. Capacity is never reused. Request timestamps precede script execution, so time spent checking counts toward freshness. Losing the cache is safe. While a check is configured, `rimz doctor` reports groups whose latest verdict is an error, with a fix naming `[throttle] check` in config.toml.

The turn handle crosses to the launch commit. `Turn::report_launch` stamps the ticket `launched`: `crates/rimz/src/launcher/execute.rs::open_fresh` calls it immediately after the agent launch batch commits, before compiling panes or publishing the supervised run, through `SupervisedRunRequest.throttle_turn`. A second report changes nothing. Nothing in the launching process waits after that: whichever process scans the queue next releases the turn, so a helper never lingers for pacing. The provider has reported when a row carries the launch reference as `launch_id` under another `agent_id` (the hook adopted the provisional row), or when the provisional row is ended, failed, or gone. Dropping the last clone of an unreported `Turn` removes its ticket, which is how every error path between admission and commit frees the queue; a process killed outright leaves a ticket whose owner is dead, which the next pass sweeps. [Stopping a run](#stopping-a-run) says when a stopped run's ticket goes.

`crates/rimz/src/harness/throttle.rs::open` counts a full agent row when it is not ended, it is not a failed provisional launch, its runtime owner is not `Dead`, and it is not a provider-built-in subagent. Live agents whose last turn errored still count; turn status and compaction do not otherwise matter. `max-parallel-agents` counts these rows across `workspace::known_workspaces_read_only()`; `max-parallel-automation` counts the subset carrying the durable [automation stamp](../agents/model.md#the-rollup). User starts count in the first bucket only; manual loop and workflow starts and RimZ launches from an automated agent's pane count in both. Finished workflow and supervised-run records never remove an open row from the census. The workspace inventory retains its limits: a workspace whose `workspace.json` does not read, or that loses the census's dedupe by session name, is not counted, so the machine count can run short. Canonical roots are normalized in memory without the maintenance census's repair writes or locks. Reading every state directory directly would be a new home-wide inventory. A store that cannot be read is a hold naming the workspace, never a short count.

A configured pressure limit or memory floor whose source cannot be read is an error instead: room judgment records a warning from `throttle::preflight`, and a machine-gated fire records `error`. The key and fix name `throttle.<key>` in config.toml, and pressure also names enabling PSI with `psi=1`. A project `[throttle]` is ignored and recorded by room judgment as skipped setting `throttle`. Pressure is the `some` line of `/sys/fs/cgroup/<resource>.pressure` at the cgroup namespace root, falling back per resource to `/proc/pressure/<resource>` when the cgroup file cannot be read or parsed, held on the larger of `avg10` and `avg60`; memory is `proc::memory`; disk is `statvfs` at `throttle::disk_at`: for a task with `worktree`, the target that `worktree::worktree_path` (or `worktree_parent` for a generated name or a `fresh-worktree` prefix) resolves from the task root, measured at its nearest existing ancestor because the worktree is not created yet; otherwise the launch checkout. `rimz loop show` reads the same path. The ticket keeps the launch checkout as its place. Nothing samples in the background.

`throttle::diagnostic_holds` gives doctor fresh needs-a-fix readings without a ticket, queue lock, check execution, cache write, workspace repair, or diagnostic append. `crates/rimz/src/cli/doctor.rs::collect_loop` supplies machine and instance tasks plus trusted project tasks from every known room, using `crates/rimz/src/workspace.rs::known_workspaces_read_only`; blocked project tasks are skipped. Only the throttle feed widens: the task table still lists machine and instance tasks. It reads each distinct task write path only when `min-disk` is set, reporting paths below the floor; an `each-worktree` task samples its owned fan-out checkouts instead of its run directory, which `throttle::diagnostic_holds` enumerates itself. Unavailable disk samples are omitted as in `throttle::readings`. With either `max-parallel-agents` or `max-parallel-automation` it probes the home-wide agent census, reporting a failed count read. These are present problems, not projections of held records, so no currently held start is required. Doctor JSON adds `loop_tasks.throttle_holds`, each with `hold` (`disk` or `store`) and `text`.

No loop fire writes a `capacity held` row or stamps `throttle_wait_ms`; history written by an older RimZ still carries them, and they classify and render as before. A `throttle skipped` row comes only from a run's report (below). The held state is read by `throttle::held` without the lock, since a ticket is replaced by atomic rename. It lists every waiting run of the task with its owner pid and checkout: `in_flight_run` carries the list for `show`, `logs`, and `show --json`, and attaches no run record when the lock's holder is itself one of those waiting runs, since a held fire has started none. `list` and `watch` instead share one `throttle::room_held` read per load, independent of each task's run lock. The renderer (`render::split_held`) shows held in place of running only for the ticket whose pid is the run-lock holder's, and the task's other waiting runs as a count and first reason beside it, so a fan-out never pairs one checkout's reason with another's pid. The throttle table, including its command-executing `check`, stays out of the trust hash as [machine policy](./trust.md#what-stays-outside-the-hash): a repository contributes tasks, not `[throttle]`.

### Where a scheduled run lands

A loop run's agent step launches through the workflow attempt host ([workflow.md](./workflow.md)) in an unfocused tab named `loop <task>`, for a scheduled and a manual fire alike: the launch carries the run's task as `loop_task` (`crates/rimz/src/launcher/execute.rs`). The `loop ` prefix keeps a task named `rimzd` out of the daemon-view classification: tab status and the run tab's sidebar bell can surface its waiting agent. The loop panel is a display, repaired by the host ([rimzd.md](../rimzd.md#who-repairs-and-when)), and hosts no runs. A prompted `rimz agents` launch from inside a check takes `schedule::runner::shape_loop_owned` instead ([scripting.md § Runs the scheduler starts](./scripting.md#runs-the-scheduler-starts)).

Channel inheritance is the exception for loop-owned launches, including manual fires and agents a check launches. Their channel and bare-role team inference come from the launch checkout (the scope directory before resolving a named `worktree`, or an explicit launch channel), never the firer's `RIMZ_CHANNEL`: the firer observed the trigger, not a parent asking a child to join its lane. A loop-owned launch likewise resolves no agent caller from environment or process ancestry: the firer's chain depth, subagent status, and room pin cannot refuse it, and it records neither `launched_by` nor a run `reader`. The scheduled helper retains its ambient channel for delivery-target scoping; only launches exclude it.

A loop run's agent step also gets a timeout it did not ask for. `InlineTask::definition` fills the `turn` or `until` step's `timeout` on every fire, manual included: the task's own `timeout`, else the machine's `loop.default-timeout`, else two hours (`SCHEDULED_RUN_DEFAULT_TIMEOUT`). A `stay` step gets none. Nobody is watching an unattended run, so it must not wedge forever. An agent a check launches takes `shape_loop_owned`'s scheduled shape on every fire, so the same default bounds it unless the launch sets a timeout.

A loop run's agent panes close when the step ends unless the task keeps them (`keep_agent`), as any workflow attempt's do. The evidence survives the pane: the workflow run keeps its journal and step attempts for `rimz workflow show`, and the `LoopRunRecord` keeps the fire's outcome and the run's report for `rimz loop logs`.

### The compiled graph

`crates/rimz/src/harness/schedule/compile.rs::compile` turns a row that is not an unguarded delivery into an inline workflow graph, scoped `worktree`, that `workflow show <task>` draws and `rimz loop eject` writes out as a deployed definition. `TaskEntry::guard()` reads the row's checks: `check = "<shell>"` supplies the shell, and `judge` accepts a table or array in file order. A table under `check` refuses at load (`crates/rimz/src/config/loop_.rs::TaskCheck`) with the one fix to delete the task from the file and re-add it with `rimz loop add`, in a strict load and in the trust decoder. Of the lenient readers, only the machine `loop.toml` read warns as it drops the file; the room instance store (`crates/rimz/src/harness/schedule/instances.rs::load_from`) and the project layer of `crates/rimz/src/harness/schedule/catalog.rs::TaskCatalog::load_lenient` drop it silently. Each judge requires exactly one of `prompt` and `prompt-file`, explicit task `on`, and an `agent` or `wait` action. Watch tasks refuse a separate shell check or judge. The graph is built in `Graph::build`:

| Node | Shape | Routes |
| --- | --- | --- |
| `check` | a `[test.check]` running the row's `check` as `shell`, with its `check-timeout`, else the task `timeout`, else 5 minutes | the row's `on` polarity sends the firing answer to the next node and the other to the decline target; `timeout` and `invalid` go to `@failed`. A check-only row routes `pass` to `@done` and `fail` to `@failed` |
| `judge-<n>` | a `[judge.judge-<n>]` per judge, its prompt in `prompts/judge-<n>.md`, its `timeout` else 5 minutes | the same polarity routes; `invalid` and `timeout` go on to the next node as plain routes, so a judge with no answer after its retry does not stop the run |
| `agent` | the `[agent.agent]` step, its prompt in `prompts/prompt.md` and any `system-prompt-file` in `prompts/system.md`, carrying `effort`, `budget`, `worktree`, `mode`, `account`, `fast`, and `notes`, with the task's `throttle` and `capacity-wait` as `admission.throttle` and `admission.give-up` | `lifecycle = "stay"` with `admission.occupancy` `takeover` or `share`, any `subscribe` wakes, and `then = "@done"`; or `until` with `then = "verify"`, `max-visits` from `max-attempts`, and `cap` to `@failed`; or `turn` with `then = "@done"`. `failed` and `invalid` go to `@failed` |
| `verify` | a `[test.verify]` running the row's `verify` as `shell`, its timeout the task's `timeout` else 5 minutes | `pass` to `@done`, `fail` back to `agent`, `timeout` and `invalid` to `@failed` |
| `deliver` | a `[message.deliver]` step to the pinned session | `then = "@done"`; `undelivered` to `@failed` |

A declining answer ends a run `@done`, except for a task that remembers its checkout (`TaskEntry::dedupes_checkout`). There each declining guard waits by its own bound (`Graph::decline`): the shell check by the resident retry (`RESIDENT_RETRY_SECS`, 5 minutes), and each judge by its own `recheck`. A condition row's decline goes to `held-<guard>`, a condition check that waits while the row's `when` still holds (`holds` and `unknown` wait), and on `ended` to `rearm`, which waits for the condition to hold again for the row's `for` and then starts over at the first check. The guard's bound ends the `held-<guard>` wait and starts over; a judge with no `recheck` waits for the next edge, and `recheck = "0"` ends the run instead. A remembering row without `when` sleeps in a `recheck-<guard>` node for that bound and starts over; a judge there with no `recheck` sleeps untimed in a `hold-<guard>` node, so the live run is the hold, and `recheck = "0"` ends the run. A manual fire cancels a run waiting at a `hold-` node before it creates its own (`crates/rimz/src/harness/schedule/runner.rs::TaskFire::supersede_held_decline`); a redefinition cancels it as an unacted run. The hold lives in the run, so a scheduled fire on the same checkout finds the run live and follows the task's `overlap` policy.

Checks, judges, and verify run as workflow checks ([workflow.md](./workflow.md)): `crates/rimz/src/harness/workflow/script.rs::evaluate_shell` for the shell, the shared judge core for judges, each under the run's own process host. Every check receives `RIMZ_LOOP_TASK=<task-name>` from the run's task (`crates/rimz/src/harness/workflow/script.rs`), so a prompted `rimz agents <cell> "<prompt>"` launched from it becomes a loop-owned supervised run: `-p` is implied, the command blocks for the result, the final message goes to the check's captured stdout, and the exit code reflects the run status. An unprompted launch is refused because there is no turn to complete, and `--bg` is refused because the check must await the result. The conversion does not apply inside an agent pane carrying `RIMZ_AGENT_ID`, where agent ancestry owns child launches. Room birth clears the check marker so it cannot leak into later launches from a human shell.

A fresh judge decline in a task-started run, inline or ejected, appends one `JudgeDecline` assist (`crates/rimz/src/harness/workflow/script/judge.rs::record_decline`). The run's journal keeps each check's answer, and the agent step's brief names the check and its answer (`crates/rimz/src/harness/workflow/brief.rs`); the shell output stays in the run's `work/<seq>.check.log` rather than the agent's prompt.

`verify` is the mirror image of `check`: `check` decides whether a turn starts, and `verify` decides whether it counted, by sending a failing verify back to the same agent step until the visit cap.

A terminal `Watch` outcome takes a separate path with the watch already evaluated: `TaskFire::prepare_watch` converts the signal's `WatchOutcome` instead of executing anything, and the row's polarity applies. A command watch defaults to `on = "any"`; polled watches always use that row polarity, with check polarity applied inside the watcher. A `Lost` outcome converts to a failed check, so `any` still delivers it and `on = "success"` skips it. A polarity skip records `skipped` and consumes the ephemeral wait without delivering a message. A `Running` or `NotMet` check-in bypasses polarity and consumption.

### The prompt a fire delivers

`resolve_effect_prompt` builds the delivered text. The base is `prompt`, or `prompt-file` read at fire time. A relative path in a project task resolves against `<root>/.rimz/`, made absolute when `config::effective` loads it. Any other relative path resolves at fire time against the directory that holds `loop.toml`. `resolve_task_prompt` lets a wait row have no prompt at all, while a `Spawn` row requires one. Nothing is substituted: `{{key}}` is delivered as typed.

A fire of a row with `agent` or `workflow` and no `watch` goes through `compose_launch` (`runner::TaskFire::effect_prompt` picks the composer). The [workflow brief](#the-loop-reminder) already carries the standing frame, so the message is the event and the prompt. A short-form row puts it in its graph's `prompts/prompt.md` (`runner::TaskFire::inline_definition`), compiled before the run lock with the arriving trigger's evidence and filled again after the backlog reconcile (`runner::TaskFire::prepare_workflow`) from the trigger the fire serves, which the run lock or the reconcile may have switched, and a named `workflow` row hands it to its run as the run prompt (`runner::TaskFire::run_prompt`), which each agent step's prompt ends with; a row without a prompt, as an ejected task's is, hands the event line alone, and nothing for a fire with no event:

| Evidence | Message |
| --- | --- |
| condition | ``Rule `<name>` fired here. <key>: <reading> · <key>: <reading>``, the readings in evidence order with `unknown` for one with no value, a blank line, then the prompt. The hold is not repeated: the reminder's trigger clause states it. |
| signal | ``Rule `<name>` fired here. <subject>``, the `signal_headline` subject followed by each `signal_details` entry after ` · `, a blank line, then the prompt |
| none (a clock fire, any hand fire) | the prompt alone |

Every delivery to a running agent (`--wait`, a self wait, a subscription) and every watch row goes through `compose_wait`: the wait line, the verdict, the evidence, then the loop or team prompt verbatim after a blank line. Durations are elapsed time, not wall-clock.

| Trigger | Wait and evidence lines |
| --- | --- |
| self timer (`rimz wait --in`) | `waited <delay> [<name>]` |
| clock delivery (`loop add --wait` on a schedule) | `scheduled wait` and `fired [<name>]` |
| watch | `WatchSpec::headline`, `WatchVerdict::label`, the name, and `output: <host path> (<FileSummary::label>)` when a path is present and the file is non-empty; only command watches say `no output` for an empty file. The tail is never inlined; a file pattern match includes its matched-line preview. |
| signal | `waited on <subject>` and `fired [<name>]`, or `fired after <elapsed> [<name>]` on a self wait (a row with `wait_meta`). `signal_headline` builds the subject per name from the payload, dropping a segment whose key is absent or mistyped; the [subject table](../../reference/cli/loop.md#signals) is the contract. A built-in family adds no line, except `pr.dequeued`'s `queue checks:` line; any other family adds one `key: value` line per top-level payload field. No line is the payload as JSON. |
| condition | `waited on <expr>`, `held <hold> [<name>]` or `fired [<name>]`, then one `key: value` line per reading, `unknown` for one with no value |
| a signal, watch, or condition row fired by hand | `fired by hand` (a clock row fired by hand reads as a scheduled timer) |

Self waits carry no note and no armer line. A check-in appends its stop and next-alarm commands.



### The Loop reminder

A loop run's agents learn what launched them from the workflow brief: the run's origin names the loop task and its trigger clause (`crates/rimz/src/harness/workflow/brief.rs`), which the fire froze in the run's record (`RunRecord::fire`), so editing, renaming or removing the task mid-run leaves the sentence as it was, old task name included, and the reminder section is Workflow ([workflow.md](./workflow.md#prompt-composition)). Their notes are the workflow run's notes folder, `automation-notes/<yyyymmdd>/<HHMMSS>Z-workflow-<task>-<checkout>/`, and the brief names `agent-notes.md` in it; task `notes = false` compiles to the step's `notes`. A run with neither an agent step nor a delivery keeps no folder.

`ReminderSection::Loop` survives for replay: an agent whose durable `LaunchRecord` carries a rendered `loop_section` gets it back on restart, resume, rebirth, molt, and message-driven child resume through `ResumeLaunchPosture::exec_request`, and forks clear it. No fire renders a new one.

### Delivering to a live instance

`wait` pins a task to one exact live kind and session at add time; `--wait @me` and bare `--wait` resolve the caller through the shared CLI resolver. `crates/rimz/src/cli/loop_cmd/add.rs::resolve_delivery_target` takes one `crates/rimz/src/sidebar/produce/mod.rs::resolution_snapshot` with the command's `--mux` hint to resolve the target, name it over addressable peers, and scope signal defaults. The stored `wait.handle` equals that agent's `rimz wait` receipt target; rows armed earlier keep their stored handle. The runner confirms the session is alive, including `ended_at`, before it sends through the ordinary durable message path. A missing or ended session records `target gone`, and a scheduled fire also removes the row. A manual fire leaves it in place.

| Intent | Header | Dispatch |
| --- | --- | --- |
| Self timer or watch (row has `wait_meta`) | `Type: WAIT` | `Steer`, parking with gate `Any` if a native prompt is open |
| Any `Trigger::Signal` delivery, including team bindings | `Type: SIGNAL` | `Boundary { gate: Done }` |
| Scheduled loop delivery | `Type: WAIT` | `Boundary { gate: Done }` |

The sender is `@rimz`, and delivery inherits the recipient's [smart-compaction line](./messaging.md#smart-compaction). A boundary delivery reaches an idle agent immediately and parks for a working agent's next `done`; a self wait steers unless the agent has a native prompt open. That wake stays `Queued` with gate `Any` and `last_error: agent is waiting on input in its pane`, then delivers at the next turn boundary after the prompt is answered. The fire records `delivered` with the queued message id and consumes the wait row, as for a missing pane; turn-completion waits project the in-flight wake as sleeping, keeping `agents wait` open. A check-in parks the same way but leaves its row watching and its command running. For a watch's terminal fire, `crates/rimz/src/harness/schedule/runner.rs::TaskFire::prepare_delivery` fills `PreparedDelivery::supersedes` from `crates/rimz/src/harness/schedule/run_log.rs::task_records`; the CLI cancels those messages before dispatching the final wake, so a parked check-in never follows its final wake. A lost history row leaves that check-in to land at the turn boundary. Receivers acknowledge `SIGNAL` and `WAIT` as attributed harness messages, hidden in rendered transcripts and kept in `--json` ([messaging.md § The message header](./messaging.md#the-message-header)).

## Staying tasks and launch memory

A `stay` row compiles to a `stay` agent step ([The compiled graph](#the-compiled-graph)): its layout stays on until the leader exits, and the run then ends `@done`. The row carries `stay = true` and optionally `each-worktree`, `takeover`, and `subscribe` (the `TeamSignalBinding` table shape), in machine TOML or an instance row. A `stay` row, and a `workflow` row with a `when` condition, remember each checkout they started a run in (`TaskEntry::dedupes_checkout`), so their scheduled fires start at most one run per checkout ([Launch memory](#launch-memory)).

`rimz loop add` resolves the ordinary layout and its prompt leader, keeping `worktree`, mode, effort, and fast overrides. Only subscriptions require the leader's hook preflight. Before it saves an agent task, add validates the effort and fast overrides against every resolved agent cell's kind through `harness::plan::validate_launch_preset`. Unsupported effort and fast save with the direct launch's warning and launch without the setting. The task retains the requested values, so each fire warns again. `--no-fast` is valid on every kind. On a `stay` task add also refuses `--account`, `--max-attempts`, `--verify`, per-task budgets and timeouts, surplus gates, `--system-prompt-file`, `--once`, and `--project`, and `WhenExpr::scope_checkout_key` refuses a condition that reads the scope checkout alongside a named `worktree` destination. Path-matched subscriptions are admitted with that destination. A hand-written row skips these add-time checks and gets the ordinary combination semantics.

### Launch memory

`records/loop-workflow-launches.json` is the one launch memory: it records the run each remembering task (a `stay` task or a condition workflow task, `TaskEntry::dedupes_checkout`) started per checkout, as `{version: 2, tasks: {task: {checkout: {at, run, scope}}}}`, with `scope` using the workflow record's `worktree` or `project` words. A worktree entry uses the scheduler's lexical checkout; a project entry uses the project root and covers every checkout of the task. `TaskFire::record_workflow_launch` writes it once `create` returns; a failed write warns and lands in the `launched` row's error. The run may have been collected by then, so the launcher then applies collection's rule again under the workspace lock (`crates/rimz/src/harness/schedule/run_log.rs::forget_collected_launch`), reading the outcome's `acted`. The run's terminal report (`run_log::report_run`, run by collection) forgets the run's entry when the run ended without reaching its act or failed, so a run whose act ended of its own accord keeps its checkout remembered, and so does a canceled run, acted or not, until a manual fire replaces it.

An older RimZ remembered resident launches in `records/loop-launches.json` (a task and scope checkout to the launch time, leader handle, and optional `destination`). `launch_ledger::load_workflows` folds that file in when the workflow file is absent or at version 1: each launch becomes a `worktree` entry with no `run`, keeping `at`, `leader` and `destination`, and a workflow entry for the same checkout wins. The fold is read-only, so the sidebar graph can run it; the first locked write publishes version 2, and from then the older file is never read. A version above 2 refuses, so an older binary fails closed on a migrated file. An older `records/loop-declines.json` decline cache may sit beside it; nothing reads or writes it.

Reads are strict, including the workflow file's version, because corrupt launch memory must not silently forget a launch. Writes take the file's own lock (`loop-workflow-launches.lock`), reload, prune vanished checkout directories, and publish atomically and durably only when content changes. Run-record GC never prunes launch memory. `launch_ledger` is the read-only half that the sidebar graph imports, and `launch_ledger_store` holds the locked mutations outside it.

Task replacement (`loop add` under the same name) and explicit removal both cancel the task's live runs that have not visited an agent or message step (`engine::unacted_task_runs`), each through a detached `rimz workflow cancel`; a run that launched an agent keeps going. Replacement forgets only the checkouts those canceled runs held (`launch_ledger_store::forget_runs`), so a checkout whose run already reached its agent stays remembered. Removal clears every entry of the task, even after the task changes its trigger or action; a `workflow` or `stay` task refuses removal on unreadable launch memory, while any other task warns and skips that unreadable file. Removal also detaches the remaining live workflow runs, which continue as independent runs and cannot repair the re-added task's entries. The unacted selection reads run records without their locks, so a run entering its agent step at that moment can still be canceled. Rename moves the entries of every task kind but refuses a task holding a folded resident launch (an entry with no `run`), because its leader records the task name. A manual fire bypasses dedupe and replaces the entry only after a new run starts; a failed create leaves the old entry. A project entry continues covering all checkouts after a definition changes to worktree scope until removal or a manual fire replaces that project entry.

The planner reads launch memory for remembering tasks, dropping launched checkouts before planning. A condition with no launch entry retries once 5 minutes have passed since that key's last fire stamp, keeping the original hold start, for single-checkout and fan-out tasks alike. This five-minute retry needs no stored field, and no helper writes the condition cache. A run whose check declines holds inside the run ([The compiled graph](#the-compiled-graph)), so a retry on the same checkout finds the run live; a run that failed, or ended on its own without acting, left no entry, so the retry starts a new one, while a canceled run keeps its entry acted or not (`crates/rimz/src/harness/schedule/run_log.rs::forget_unkept_launch`; the user rule is [launch memory](../../reference/cli/loop.md#launch-memory)). Failed runs accumulate strikes, and budget skips stay strike-neutral. A launch-memory read failure suppresses every remembering task of that root; other tasks keep firing. Forge probes follow the same kind routing for fan-out scopes.

An `each-worktree` project-scoped task takes per-checkout run locks, so a project run that turns terminal between another checkout's memory check and its `create` lets that checkout start a second project run.

### Takeover

A staying step's takeover and workflow admission share one occupancy read, `crates/rimz/src/harness/takeover.rs::read`. The caller supplies its runtime-scoped snapshot, with rest certificates and local-session binding, and a `CardStatus` reader before the call. The snapshot also carries resume outcomes for the reader's lazy park evidence. Runtime projection excludes rows whose owner is known dead, except launched children retained with a visible parent. The read resolves the checkout and each owned worktree in two forms, as given and `canonicalize`d where that resolves, and reads the clock after that discovery.

An occupant is the current row of a launch instance (`address::launch_occupants`, so an earlier conversation in the same pane is neither counted nor closed twice) that has no end, is not a provider subagent, has a pane stamp, and has runtime-owner liveness other than `Dead`. The read checks liveness again with `store::runtime::agent_liveness`, because a cached rollup can outlive its owner; `Live` and `Unknown` occupy. The row's lexically normalized lane path must be the checkout or inside it by path component, and not inside an owned worktree nested there. Team, channel, and loop task play no part. Both path forms count because a provider hook records the physical cwd while a launch records the marker's lexical one, so a row matches under either form and a nested worktree excludes under either. No pane listing is read, because even an authoritative listing may omit whole live tabs: a pane without a row does not occupy, and a paneless row has nothing to close and is not an occupant.

An occupant blocks the takeover when it, or any unended launched child of it (wherever its cwd, with or without a pane stamp), is working: card status `running`, `waiting`, or `paused` (a recoverable provider pause or a RimZ budget park, reported alike as `is paused on a limit`), awaiting input, or compacting. `sleeping`, a parked clean turn, and `failed` (including a non-pausing provider error or a displayed provider pause the card counts as spent) are settled. Both workflow admission and eviction use this reader, and a settled spent pause is stopped. A takeover can therefore stop a limit-parked agent between its window reset and auto-continue's resume nudge. The read leaves the rows as they are for the stop.

A staying step reads the named destination when there is one, otherwise the run's scope (`crates/rimz/src/harness/workflow/engine.rs`). With `takeover`, a working occupant makes the step wait with a `takeover` wait, and settled occupants are stopped together once the launch is prepared, through `agents_cmd::stop_resolved`, which attempts the whole set and waits once for the closed rows' processes; a failed close counts as stopped only when a fresh read finds the row ended and its owner `Dead`, and any other failed stop fails the launch, which the step retries once before it counts a `died` attempt ([workflow.md](./workflow.md#admission)). With `share`, which a staying row without `takeover` compiles to, the step skips the occupancy read and launches beside the occupants. [workflow.md](./workflow.md) owns the wait states and eviction.

Nothing makes the occupancy check and the pane closes atomic. The window starts at the caller's row read, includes discovery and owner probes, and ends at the closes, and a launch row reads `idle` until its first turn hook lands.

### Subscriptions

A staying row's `subscribe` bindings compile to the `stay` step's `subscribe` wakes, which the workflow run arms for its session and forwards while the session lives ([workflow.md](./workflow.md)). An older resident leader keeps its task's name on its durable agent row, and its standing deliveries keep `TaskEntry.loop_task` (`loop-task` on disk) and their `loop-<task>-<agent>-<binding index>` names until the session ends ([Waits](#waits)).

### One launch per worktree

For `each-worktree`, the planner expands a task over the owned worktree markers not covered by its kind's launch memory. It expands paused and disabled tasks too, so that arming policy keeps their hold and fired state as it does for an ordinary condition. Runtime condition and fire keys encode `(task, checkout)`, and edge rules are the same as for a single task. The marker path is lexically normalized (`.` and `..` removed, symlinks not resolved) for condition evaluation, PR probes, the hidden helper's `--cwd`, and launch memory, which matches agent rows and subscription paths. It does not pass through `TaskEntry.run_dir`, which resolves configured paths. The helper validates that checkout against the normalized owned markers, keeps it apart, and takes a checkout-specific run lock before its launch-memory recheck. A manual fire selects the deepest owned checkout that contains the caller's cwd, with the same normalized marker path.

Fire planning enumerates owned worktrees once when any fan-out task exists, paused tasks included, while probe selection enumerates only for a relevant live fan-out task. A condition workflow task expands only over unlaunched scopes, including after its run finishes. Schedule, signal, and watch workflow tasks read launch memory only when their row sets `once-per-checkout = true` (`crates/rimz/src/config/loop_.rs::TaskEntry::dedupes_checkout`); otherwise they rely on live run admission at each fire.

`crates/rimz/src/harness/schedule/fanout.rs::inspect` reads owned markers, the workflow launch memory its caller read once, folded resident launches included (so `loop show` shares one read with its run projection), the condition cache through `crates/rimz/src/harness/schedule/fire.rs::scope_key`, and the scoped evaluator that firing uses. It shares fingerprint matching with the planner, keeping the configured run directory in the fingerprint while the scope key selects the checkout. A true condition with a matching clock is holding until the hold elapses, then ready. Without a matching clock it is holding since now when a hold is configured, otherwise ready since now. Inspection starts no stored clock, does not predict the scheduler's first-sight or retry tick, writes nothing, and reads forge facts only from the room's cache, gated by the CLI's fresh sidebar heartbeat. The CLI joins the folded resident launch rows with their leaders' effective live statuses and subscriptions scoped by run directory. It also joins live capacity records by checkout, showing the shared capacity phrase in the state cell and the structured `capacity_wait` object in JSON only while the record's `since` matches the current condition clock and it has not given up. Workflow rows join by run id to `crates/rimz/src/cli/loop_cmd/list.rs::WorkflowRunRow::for_show`, the shared projection for WORKTREES, RUNS, and JSON. It includes ledgered terminal and gone records, then every unlisted run the task started in its room (`RunRecord::ran_for`, any state), live first and finished newest first; `RunRecord::started_by` stays live-only for `loop list`, and `engine::reassign_task` takes it plus, on a rename, the finished runs still owed their collection. Active, parked, and failed runs stay visible; done, canceled, and gone runs fold alongside inactive older leaders. `--all` unfolds older declines and folded launches; JSON always includes every owned checkout. RUNS omits every run named by a worktree row, then folds adjacent finished rows and caps them by `--runs` (`crates/rimz/src/cli/loop_cmd/render.rs::write_workflow_runs`), while JSON retains the full projection and repeats each worktree's matching run object.

## History, strikes, and arming

History is the user-global `~/.rimz/logs/loop-runs.log.jsonl`, one `LoopRunRecord` per fire that reaches a decision ([What the scheduler does](#what-the-scheduler-does) names the exits that write none). The log is per-user, so history survives a task being edited or removed. `rimz loop show` filters by the resolved task's room, `rimz loop logs` and health reads by the current workspace root when it is known; records with no `root` stay visible everywhere.

A record carries:

- the resolved task `root`, the result, the mode (`scheduled` or `manual`), the duration, and the error chain;
- check evidence: exit code, timeout flag, capped output, and for a watch row the output file's host `output_path`;
- the watched command's `WatchVerdict` in `watch`;
- the triggering signal's name and payload;
- the delivery's durable message id and target, or the supervised run id and transcript path;
- the last message, cost, and fresh input and output tokens;
- `throttle_wait_ms`, how long the start throttle held a fire it then admitted.
- optional `late_ms` on a scheduled fire of a `fire-at` row that `TaskFire::new` constructed two minutes or more past the instant, measured from `fire-at` to that constructor's `now`; throttle wait is not counted in it.
- optional `holder` on fires refused at the run lock, with the holder's `pid` and `started_at`; their stored error names the policy outcome without a pid or a frozen age.
- optional `blocking_run` on `overlapped` and `deferred` records for a fire that found the task's workflow run still active, naming that run; their stored error names it too.
- optional `run_lock` on records for fires that held the run lock, with that tenure's `pid` and `started_at`, including records the stop/replace ladder writes on the holder's behalf.

Append caps stored copies: 4 KiB each of shell output and every judge reason and error, 2 KiB each of run error text and last message, and a signal payload over 4 KiB collapses to `_truncated`. The verdict reader tails reasons to 4 KiB at a UTF-8 boundary before assists or prompts consume them.

Optional fields read absent when a row lacks them, `judge` reads empty and is omitted when empty, and `reused` reads false. `LoopRunRecord::stages()` projects a row whose `check` holds an agent into a judge without fabricating a shell, and the writer never puts an agent there. Row polarity and consumers use `last_verdict()`, the last answered stage. Watch rendering uses `WatchVerdict::label` and `elapsed_ms()`, and shell rendering uses `exit <n>`, `timeout`, or `signal`. Judges render profile, verdict, reason or error, spend, tokens, duration, and reuse. A skipped negative verdict reads `judge declined`; a positive verdict reads `judge passed` even when skipped. `rimz loop show` reads health plus a separate rollup of action runs for guarded work, and `rimz loop logs` keeps one block per run and prints every stored stage in that block in full, including the output path above the shell gutter. Its shared history fold attributes lock-refused fires as counts on their holder's record, or on a `no record` block when a later tenure proves the holder gone. Repeated refusals keep the newest member's forensics; trailing lock refusals stay as blocks in log order, folded only for equal keys and holders. Heard signals keep individual blocks and never take attributed counts.

`LoopRunResult` has 24 variants, and `strikes::classify` sorts each record into one of three outcomes. A record whose `watch` verdict is nonterminal (a `Running` check-in) is neutral before the result is read. `CheckSkipped` and `SignalSkipped` serialize distinctly (`check_skipped`, `signal_skipped`): one is a guard that declined (rendered with the check's outcome), the other a sibling signal the subscription observed without delivering (rendered as `heard`). `deferred` retains a busy trigger; `replaced` denotes a run stopped for a newer trigger. A served coalesced run carries nonzero `absorbed`, omitted otherwise.

| Outcome | Results |
| --- | --- |
| Strike | `failed`, `verify failed`, `timed out`, `error`, `budget exceeded` |
| Reset | `completed`, `delivered`; `launched` without a workflow run id |
| Neutral | `budget skipped`, `surplus skipped`, `account skipped`, `throttle skipped`, `capacity held`, `takeover blocked`, `overlapped`, `deferred`, `canceled`, `replaced`, `expired`, `target gone`, `start failed`, `workflow_skipped`; `launched` carrying a workflow run id; every `skipped`; any nonterminal watch check-in |

No fire writes `capacity held`, `takeover blocked`, `replaced`, or `workflow_skipped`; they classify and render history an older RimZ wrote. A loop run that waited on a busy occupant, or a `replace` cancel, reports `failed` or `canceled` like any other run. A run that ended `failed` because its agent step gave up waiting for capacity (the journal's last decision is the engine's `capacity` route) reports `throttle skipped` instead, with the error `gave up waiting for capacity after <waited>; <reason>`, so a give-up never strikes. The compiled agent step routes a `limited` attempt to `@failed` through its `on.failed` edge, and a run whose last attempt ended `limited` reports as the budget ended it (the engine's terminal outcome, `crates/rimz/src/harness/workflow/engine.rs::failure`, read by `run_log::report_run`): `budget skipped`, strike-neutral, with the launch's refusal as its error, when the budget refused the launch and no agent ran, and `budget exceeded`, a strike, when it stopped a running turn. An unset `capacity-wait` on a scheduled fire of a repeating clock task gives up one second before the next fire, capped at the deadline: the fire computes that instant (`TaskFire::default_capacity_cutoff` in `crates/rimz/src/harness/schedule/runner.rs`) and the run carries it as `RunRecord::capacity_until`, which the engine sets as the hold's give-up when the agent step names no `admission.give-up`, however late the first hold comes.

A check's answer is not an input: a run is judged by its own result. Every `launched` row that names a run is neutral because its run reports later. `run_log::report_run` appends one row per finished task-started run when `run_log::collect_run` collects it, reading the typed outcome the engine wrote in the run's record (`store::workflow::RunOutcome`), carrying the run id, `completed`, `failed`, `throttle skipped`, or `canceled`, the summed attempt and evaluation cost, and `acted` (whether the run started a step), and that report row is classified like any other. `strikes::note_run` counts a run id at most once: it records the id in `loop-strike-runs.json` (the newest 64 per task) before it moves the count, so a crash between the two loses the signal instead of counting it twice. History readers fold a report over its run's `launched` row and over earlier reports of the same run (`task_records`, the `loop list` stats fold). The run advances before its launcher appends the `launched` row, so a fast run's report can land first: the readers then fold the late row into the report, which takes its fire facts, tree and kind.

The table encodes three judgements. A run that ended `failed` is a failure. A run that was stopped (`canceled`, `replaced`) did not fail, and a hung run still fails at its step timeout. A gate that declined to spend money is not a failure at all. And a fire that left no run behind says nothing about the task, so `start failed` is neutral even though every renderer shows it as a failure: a broken timer must not auto-disable the work it failed to run.

`record_transition` appends the history row and then updates the overlays. It and `record_stopped` are the only writers to the log: a fire and an observed sibling signal reach `record_transition`, and `rimz loop stop`, whose task row may already be consumed, reaches `record_stopped`, which appends the strike-neutral `canceled` row stamped with the stop's root and moves no overlay. No CLI code appends a row. The append is best-effort, since `disk::rotating` logs its own failure at debug and returns, so the `RunTransition::Recorded` it returns means the append was attempted before the overlays moved, not that the row reached disk.

When consecutive strikes reach the threshold (`max-strikes`, default 3, `0` disables), the task auto-disables, displays `disabled · N strikes`, and fires `loop_disabled` notification handlers. `rimz loop enable` clears the counter and re-arms. `rimz loop fire` works on a disabled or paused task, for testing.

Three machine-local overlays under `~/.rimz/loops/` hold this state without editing task definitions, each behind an advisory lock that serializes concurrent runners:

| File | Holds |
| --- | --- |
| `loop-arming.json` | enablement, a bounded pause deadline, and an automatic-disable strike reason |
| `loop-strikes.json` | consecutive failure counts, independent of run-log rotation |
| `loop-strike-runs.json` | the workflow run ids each count has taken a signal from, so a re-reported run counts once |

All three key a task by scope: project and instance tasks as `<workspace_id>::<name>`, machine tasks as `machine::<name>`, so a same-named task in another checkout never inherits an enable. Enabling writes the anti-replay edge, and when a timed pause expires its deadline becomes the effective last-fire edge. Either way the schedule waits for its next occurrence instead of replaying what it missed while held.

## The display commands

Every display reads history through `run_log::task_history`, which splits fires from heard signals and applies the optional wait arming cutoff. Only `SignalSkipped` rows leave the fire side: both check polarities and every refusal count as fires. Show, logs, and rowless in-flight show use this partition; stats use the same split, count fires, and have no last fire for a siblings-only task. Team subscription cells therefore fall back to `heard <signal> <age>`, never a skipped run count. The heard summary counts siblings after the newest acting record (all retained history without one), while retaining the newest named sibling as evidence even when the count resets to zero. LAST RUN selects the verdict's acting record, except for a clean launch, and its logs pointer counts fires. `logs --heard` reads the retained unpartitioned order.

`rimz loop show` resolves an exact name in the caller's room before the other roots enumerated by `list::room_roots`, loading catalogs rather than the timing-heavy list model. Rowless in-flight runs and retired one-offs precede worktree aliases, which exclude wake-ups; owner labels come last. Retired one-offs share list's DONE rule: at least one fire and a newest kind-stamped record of `OneOff`, with kind selection shared in `run_log`. Other retained history resolves nothing. A missing name refuses in text and JSON with empty stdout and retained-fire count, latest-fire age, and `loop logs` hints when scanned rooms hold fires; the caller's room wins, otherwise each such room gets a root-qualified hint. JSON requires a task row even for an in-flight run or retired one-off. Ambiguous text views print inspection commands rather than choosing a room or task. Only this read command widens resolution: mutations and `logs` keep the caller's room. A cross-room view names the root those commands need. The rowless scan probes each room's run lock once, warns once on failure, and passes the result to the view without another lookup.

While a consumed one-shot's run holds its lock, `rimz loop show`, `logs`, and `stop` follow the lock instead of the row. `show` searches known rooms; `logs` and `stop` fall back to the caller's project root. `runner::in_flight_run` reads the newest non-terminal run record for the name only while its lock is held in that root. The lock decides and the record enriches: the record lands after the consume, and a hard-killed runner leaves a non-terminal record behind a free lock, which is no run.

A task with a row is looked up the same way from its own root. Every display of a genuinely executing run says `▸ running` with the time since the holder started: `list` in LAST or DONE's FIRED cell and `watch` in its next cell, and `show` and `logs` with the holder's PID and the run id, in the headline and as the last line. `show` adds the stop hint, and `show --json` carries the same reading under `running`. The running state overrides timing state; waiting throttle tickets use the held presentation described above instead. A consumed one-shot keeps a DONE row with its real task name; `watch` keeps its running row with no next fire. It is enrichment on the display commands: when lookup fails, `list`, `show`, and `logs` warn on stderr and render as if no run were in flight, `watch` repaints without warnings, and `stop` fails rather than reporting no active run. An unprobeable lock file no row claims is skipped, and an unlistable locks directory costs `list` one warning per root.

`rimz loop list` builds an owned per-room model. It is loaded strictly for the caller and best-effort for other roots discovered from machine tasks and instance records. Each root has its own catalog precedence and root-filtered history fold; a record without a `root` counts in every room. Discovery opens no store. Expanded text with self waits opens each room through `Ctx::for_workspace` and reads its resolution snapshot with the command's mux hint as enrichment. Cards name agents over `addressable_agents` of that snapshot. `wait list` takes the same roster from its one resolution snapshot for both its cards and its rows' JSON `parent`. Missing or unreadable rooms fall back to stored handles, and failed pane reads use the resolution snapshot's stamped-pane fallback. JSON adds no store reads. Missing checkout directories are a display classification, not a durable retirement. The NEEDS YOU verdict is `crates/rimz/src/harness/schedule/attention.rs::decide`, shared with `loop watch` and the read-only reader `crates/rimz/src/harness/schedule/attention.rs::read_room`, which the sidebar may call once per room for the verdict of every task there. A gone checkout counts only while the task has not fired by `crates/rimz/src/harness/schedule/attention.rs::fired` (the version 2 launch ledger; a fire only the older `loop-launches.json` remembers does not count), so a fired staying one-off reads DONE. `pr_closed` reads the waiting condition's stored readings (`TaskTimingState::Waiting`, written only once the clock pass has stamped the task's first sight) through `crates/rimz/src/harness/when.rs::WhenExpr::closed_pr_term`: an un-negated `pr[...]=merged` term reading `closed` whose expression stays false with every other term met. Routine tasks and fired tasks never raise it. Text and JSON classify catalog and rowless running tasks by lifecycle; retained one-offs without a row live separately in `retired` and count in watch's done fold, never its table. The compiled task owns lifecycle kind, and terminal records retain it after retirement. List text pins running DONE rows above the five newest finished entries and folds wake-ups and older DONE entries unless `--all` is explicit. Expanded wake-ups use `crates/rimz/src/cli/wake_view.rs`: self-wait cards include lost rows also shown in NEEDS YOU, then subscriptions collapse by canonical owner. Both wake-up headings count waits and subscriptions separately; watch keeps its narrower folded-row predicate. List's DONE and watch's done fold share one population and ordering timestamp; watch excludes running entries from its fold. Last acting results and newest heard siblings come from `LoopRunStats::acting` and `LoopRunStats::heard`, with no second CLI classification. List terminal wrapping is confined to lifecycle-table triggers; shared self-wait lines are neither clipped nor wrapped by the renderer, and JSON keeps the real names.

Each list load or watch repaint resolves runtime paths and scans heartbeat freshness once per room. It reads the loop timer status at most once, shared by every row and heading, and only when a room it loads is closed. Condition tasks share `crates/rimz/src/harness/schedule/attention.rs::RoomReadings`, built on the first condition row: one room-gated forge cache, one lazy account-window reader, one condition-hold state read, and one read of the fire stamps the freshness rule compares against. `crates/rimz/src/cli/loop_cmd/list.rs::load` resolves each displayed task's root and run directory once and reuses them for its key, condition, launch lookup, and row. These inputs live only for that repaint; heartbeat readers outside it remain live. Single-task show and fire observations keep their own context, as does `crates/rimz/src/harness/schedule/attention.rs::read_room`, which builds its own `RoomReadings` and reads each of its other inputs (the catalog, the workflow runs, the launch ledger, the start tickets, the run locks, arming, strikes) once per call for every visible task of the room it reads.

`rimz loop watch` wraps next cells and separate attention reasons. It resolves its caller workspace once and admits entry with a fresh heartbeat or a verified caller pin for that room after checking for a terminal, so the room's own panel can start before the first heartbeat. It reloads only that room each frame and suppresses the model's enrichment warnings to keep the panel quiet.

`rimz loop show` renders the compiled lifecycle kind and timing, with the pure-AND count projected only from an observed verdict in that timing. The complete condition expression and hold appear once above the leaf block or fan-out table. Single-checkout leaves carry satisfaction glyphs or a muted question mark with cache-only unread reasons; a negated unread leaf is unknown, not true. Forge age is available only when the latest probe succeeded. LAST RUN omits an empty summary unless its header names a manual, signal, or late one-shot fire; blank shell output alone is not evidence. It retains fire-time readings but omits an expression equal to the current condition; full logs retain both. A one-row recent table is omitted only when that row stands for one run, the verdict's acting run, with no folded waited or skipped fires; a `×N` row keeps the table. Manual fire observes the selected checkout solely for its unmet-condition notice, without feeding that observation into scheduled evidence or arming. Throttle display is absent without limits or a held ticket, and the full display shows avg10 pressure only; admission uses the larger of avg10 and avg60.

`loop show` loads the task's own room catalog and selects rows whose `loop_task` matches its name. An owner-label lookup also selects `team` bindings by full instance or team name and prints the same `SUBSCRIPTIONS` table. A task without fan-out keeps that section: each real task name keeps a row, even when `loop list` folds those subscriptions. One room-filtered run-log fold supplies the newest acting run, otherwise the newest heard signal, using the list's LAST wording. Fan-out tasks omit the section; the `wakes` fact counts armed rows for both kinds and names declared signals even when none remain. The section leaves the parent task's health verdict as it is, and `show --json` keeps its fire-only `runs`, the `heard` summary of sibling signals, and an unfolded `worktrees` array.

## The signal vocabulary

A signal is a name, a JSON object payload, a source, and, for watched commands, an outcome. The first three persist, and [`store/event.rs`](../../../crates/rimz/src/store/event.rs) owns them as `SignalName`, `SignalSource`, and `SignalEventPayload`. The outcome does not persist, so the runtime `Signal` and its `WatchOutcome` stay in the harness and convert down through `From<&Signal> for SignalEventPayload`.

`SignalName` is lowercase dot-separated segments, each starting with a lowercase letter or digit and otherwise `[a-z0-9_-]`, at most 64 bytes. The family is the first segment. `rimz events emit --source cli` refuses the `RESERVED_FAMILIES` (`agent`, `wait`, `team`, `ci`, `pr`, `trunk`, `worktree`). The hidden `--source forge` accepts exactly the nine forge names, and `--source git` accepts only `trunk.moved`; neither authenticates the caller.

| Source | Producer | Names |
| --- | --- | --- |
| `Cli` | `rimz events emit <name> --json '{…}'` | anything the grammar accepts outside the reserved families |
| `Forge` | the sidebar's PR-state refresh, which spawns `rimz events emit --source forge` on a transition ([state.md § Push channels](../sidebar/state.md#push-channels)) | `ci.passed`, `ci.failed`, `pr.opened`, `pr.merged`, `pr.closed`, `pr.behind`, `pr.conflicted`, `pr.queued`, `pr.dequeued` |
| `Git` | the sidebar's project-root trunk lane | `trunk.moved` |
| `Worktree` | successful managed worktree operations, appended and fired in-process | `worktree.created`, `worktree.removed` |
| `Lifecycle` | the elected hook drainer, from the lifecycle events it applies | `agent.started`, `agent.idle`, `agent.waiting`, `agent.failed`, `agent.ended`; `team.idle`, `team.waiting`, `team.failed`, `team.ended` |
| `Team` | `rimz teams flip` and the stage owner's [resume re-wake](./teams.md#resume-re-wake) | `team.stage` |
| `Watch` | `rimz wait watch <name>` at a check-in or terminal command, PID, check, or file outcome, and the host's watch-lost rule | `wait.<task-name>` |

Hook-sourced signals fire when `crates/rimz/src/harness/hook_drain.rs::Drainer::drain` applies the ingress frame through its child, not in the hook process. Selection uses the subscriptions armed at that apply instant. A scoped hook whose host drainer is unreachable applies inline instead. Crash recovery replays keyed durable effects but does not fire lifecycle or team signals again: a fire lost between the lifecycle append and the applied cursor write is not recovered. `rimz events emit` fires in its own process, without replay to late subscribers; a busy task may retain its selected trigger under its overlap policy.

GitHub-only `pr.behind` and `pr.conflicted` fire for open PRs on entry (including first sight), or for a changed head while the state persists, without repeating for unchanged heads. Conflict keys use the head where mergeability settled. Their payload is the `pr.merged` context with `state: "open"`, plus `pr_head`, `base` when known, and `behind_by` for `pr.behind` only; `head` stays local. The [PR producer](../sidebar/state.md#push-channels) owns detection and carry-forward. Both names inherit PR-family scoping and `branch`/`path` matching; a matching `pr.merged` subscriber records `SignalSkipped` for either sibling, while a failed match records nothing.

GitHub-only `pr.queued` and `pr.dequeued` follow the same rule with a different key: the queue entry's `enqueuedAt`, or the `createdAt` of the latest removal whose reason is not `merged` and which no later auto-merge request supersedes. They fire on a first standing reading over a continuous target and on a changed timestamp, never for a changed head. A removal already re-armed at first reading is silent; withdrawing the re-arm restores its key and fires `pr.dequeued` again with the original timestamp. A room that opens on a standing queue state has no prior target stamp, emits nothing, and reads it through `pr.queue`, and a queued PR that merges emits `pr.merged` alone. Their payload is the `pr.merged` context with `state: "open"`, `pr_head` (always the PR head), and `base` when known; `pr.queued` adds `queued_at`, and `pr.dequeued` adds `dequeued_at`, `reason` when supplied, and `queue_checks_url` when the removal names the queue's commit. `ForgeSignal::ALL` alone admits a `--source forge` name, so a variant missing from it is emitted by the poll and refused by the child.

### Trunk and worktree signals

The sidebar trunk lane observes only the room's project-root checkout, using the configured trunk, then `main`, `master`, and `origin/HEAD`. Its five-second runtime cache is published under a dedicated single-flight lock before emitting `trunk.moved` through the detached Git-source emitter. Only a changed SHA on the same resolved trunk name fires. First sight and a renamed trunk selection reset the baseline without a signal. The lane reads only the trunk ref, never HEAD, so an unborn or detached HEAD does not stop it. In the files backend it reads loose refs and `packed-refs` in process with no fork. In a reftable repository it records the stack's `reftable/tables.list` beside the trunk: an unchanged stack under an unchanged trunk setting reuses the recorded trunk with no fork, and otherwise one bounded `git for-each-ref` runs over the trunk candidates. A pass whose refs do not resolve, or whose reftable read fails, carries the prior reading forward (`crates/rimz/src/sidebar/refresh/trunk.rs::produce_trunk_state`), so the next pass that resolves compares against the last SHA it saw; a failed reftable read records no stack, so the next pass reads again. The payload is `trunk`, `from`, `to`, and `repo`.

Worktree creation emits after the Created hook succeeds, never on reuse. Removal emits at retirement, including sweep, not on failed-creation rollback. Both append before firing through the shared in-process helper, with failures warning without failing the completed operation. Payloads carry `name`, `branch`, `path`, and `repo`; both include `from_pr` when present, creation adds `base` when known, and removal adds `branch_deleted`. Neither family receives an implicit subscription match, and `pr.opened` keeps the PR family's path scope.

### Agent lifecycle signals

`lifecycle_signal` maps real lifecycle edges onto the five agent names; [state snapshots](../agents/model.md#state-snapshots) bypass it:

| Transition | Signal |
| --- | --- |
| `Registered`, `SubagentStarted` | `agent.started` |
| `TurnEnded`, errored | `agent.failed` |
| `TurnEnded`, otherwise | `agent.idle` |
| `AwaitingInput` | `agent.waiting` |
| `Ended`, `Lost`, `SubagentStopped` | `agent.ended` |

`Ended` and `Lost` derive their signal even though the state machine classifies a root session's end as an `Ignored` transition ([`agents/lifecycle.rs`](../../../crates/rimz/src/agents/lifecycle.rs) stamps the row in the reducer instead); every other `Ignored` transition produces no signal. The payload carries `kind`, `session`, `status`, and `errored`, plus `handle` when the card has a name and `parent` for a subagent event. A subscription's `match` can filter on exactly those keys.

### Team signals

`team_lifecycle_signals` derives cohort edges from the same event, right after the `agent.*` derivation and only when the transitioning agent has a `team`. It is pure. The hook calls `team_stage::react_to_lifecycle`, which passes the member row from the audit projection (which retains ended rows), the live cohort from `team_cohorts`, the room's addressable agents from `Store::snapshot_cached`, the complete pending message queue, and the set of sessions holding a pending one-shot wait. The cached snapshot is read at most once per receipt, only on the team-signal path; a failed read warns and keeps cohort-only handle rendering without suppressing the signal.

| Name | Edge |
| --- | --- |
| `team.waiting` | the member entered `Waiting` from a non-waiting status |
| `team.failed` | the member's turn ended errored |
| `team.idle` | the live cohort is non-empty, every member is at rest (`Idle` or `Success`), and no live member has a queued message or a pending one-shot wait; emitted only on the false-to-true edge, where the prior view overlays `prior_status` on the member |
| `team.ended` | a terminal event for the member, with no other live member left |

The payload carries `team`, `instance` (`team#channel`), `member` (the qualified handle that tripped it), and `members` with each handle and status. A live agent's handle names only that agent among the room's addressable agents at emit. An ended member whose handle would resolve to another live agent, or to several, uses `@<session id>#<lane>` instead, without the suffix for a lane-less agent. Membership is whatever `team_cohorts` counts as live for that `team#channel`, plus the transitioning member even on a terminal edge; a provider-native subagent's transition derives nothing.

`team.idle` is evaluated only on lifecycle events. Removing a pending wait, which only its owner can do, emits nothing by itself; the owner's next turn boundary re-evaluates the cohort, and with no further lifecycle event the evaluation waits for the next member event.

A member the reaper stops (a pane closed with no lifecycle hook, [`store/writer/reap.rs`](../../../crates/rimz/src/store/writer/reap.rs)) passes through no hook, so it derives neither `agent.ended` nor `team.ended`. Its subscriptions are retired by the reconcile in [Waits](#waits) rather than by a signal: cleanup follows the durable end, and never broadens what an end emits.

`team.stage` comes from `harness::team_stage`, not the cohort derivation, and `rimz events emit` cannot produce it. Its payload carries `team`, `instance`, `from` (absent when the first flip opens the board), `to`, `owner` (absent for `Done`), `by` (a role name, `user`, or `rimz`), optional `note`, `board` (absolute path), and `at` (RFC 3339). A flip writes the board and ledger before appending the signal with `SignalSource::Team`. A re-wake appends the same signal for the current owner with `from == to` and `by = "rimz"`, without editing the board or compacting. The exec wrapper produces it on every resume of a root member (resume, restart, single-member restart, and rebirth), and root-member registration is the backstop for a start that is not a resume; [teams.md § Resume re-wake](./teams.md#resume-re-wake) owns the two triggers and their de-duplication.

The stage owner does not learn of a flip through a subscription. `team_stage` dispatches a `Type: STAGE`, `From: @rimz` message straight to the owner at the `done` boundary: prose naming the flip and a `Note:` line, or for a re-wake, prose telling the owner to continue from the board's last Progress line. When the team declares a leader and the owner is not it, the body ends with the seat's channel rule (report to the stage file, reach the user through the leader, no pane text). `Done` and a self-owned flip send no message, and an owner who is not live is woken by the re-wake when it is resumed. Explicit `team.stage` subscribers fire independently with the loop's signal body, re-wakes included.

### What persists

`rimz events emit`, the wait watcher, stage flips and re-wakes, and the hook's team derivation append a `signal.emit` event through the ordinary store commit ([store.md](../store.md#what-is-in-it)), so `rimz events follow` replays them. `agent.*` signals append nothing extra, because the `agent.lifecycle` record they derive from is already the durable trace. The durable record is the `SignalEventPayload` (name, payload, source), so a watched command's exit status travels in the fire's argv and never reaches the log.

### Firing subscriptions

`fire_signal` delivers a signal to its subscribers, in the emitting process (`crates/rimz/src/harness/schedule/signal.rs::fire_signal_with_wait`):

1. Spawn the workflow wake helper when the room has an active workflow run ([workflow.md](./workflow.md)).
2. Run `retire_ended_sessions` ([Waits](#waits)), which removes the instance rows of durably ended targets.
3. Load the runnable tasks whose resolved root maps to this workspace.
4. `resolve` each task's trigger against the signal, dropping `Ignore` results.
5. Drop an untrusted project row and any task whose arming overlay is not `Live`, so a disabled or paused subscription stays quiet. A dropped `Deliver` is reported as not started.
6. On `Skip`, append a `SignalSkipped` run record carrying the observed signal and spawn nothing. On `Deliver`, spawn a detached `rimz loop run <name> --signal-json <encoded>` and return the name for the emitter to print. A watcher-originated fire waits for a watch task's run instead ([Watched commands](#watched-commands)).

Step 2 is the only instance-row write. A `Skip` leaves the subscription armed, so a sibling observation does not consume a one-shot. The runner consumes a one-shot once its delivery is dispatched, and a standing subscription stays.

There is no signal replay queue: a subscription written one second after the emit misses it. A matching busy task's runner may retain its own trigger in the backlog. Signal firing leaves `lanes/loop-fire.json` untouched. The host may stamp a signal row when it first sees the catalog, but `fire_signal` never consults that stamp. A signal reaches only the subscriptions armed in that workspace at that instant, which is what lets an emitter run with no room open.

### The watch verdict

A watch signal carries a `WatchOutcome`: a `WatchVerdict` plus its evidence (the output tail, the host path of the output file, and its byte size, physical line count, and estimated tokens in `summary`). The verdict is one enum with one renderer; a file pattern match also carries its matched line.

| Variant | `label()` |
| --- | --- |
| `Exited { code: Some(0), elapsed_ms }` | `exit 0 after 4m` |
| `Exited { code: None, elapsed_ms }` | `killed by signal after 3s` |
| `Running { elapsed_ms }` | `still running after 30m` |
| `Met { elapsed_ms, line }` (`met`) | `met after 4m`, adding ``: `<line>` `` when a file pattern matched |
| `NotMet { elapsed_ms }` (`not_met`) | `still not met after 30m` |
| `TimedOut { elapsed_ms }` (read from records only, never produced) | `timed out after 59m` |
| `Lost { detail, elapsed_ms }` | `watcher died after 3m; the command may still be running or may have died with it` |

`WatchVerdict::label` is the only place those words are written; `compose_wait`, `rimz loop logs`, and `rimz loop show` all render through it. `passed()` is true for `Exited { code: Some(0) }` and `Met`. `elapsed_ms()` is the measured run, rendered in seconds under a minute and through `theme::fmt::duration_label` above it. `is_terminal()` is false for `Running` and `NotMet`, the check-ins that bypass polarity, add no strike, and do not consume the row.

For terminal outcomes, `to_check_outcome` folds the verdict into the check machinery: `passed()` becomes the pass bit, `TimedOut` the timeout flag, and the tail the output. A `Lost` outcome's output is the log file's tail, since the label already states the cause.

`WatchOutcome` travels only in the `rimz loop run` argv and the process memory around it, so reshaping it is not a durable-format change. The verdict becomes durable one level up, in the run record's `watch` field.

## Watched commands

`TaskEntry.watch` is an untagged `WatchSpec`: a command string, `{pid}`, `{check, every, on}`, or `{file, grep?, mark?}`. A file mark records size, modification time, device, and inode; no mark means absent at arm time. `WatchSpec::describe` owns trigger text and `headline` owns the delivered first line.

`arm_delivery` stores the arming agent's name (a petname for a launched child) as `WaitMeta.reader`, creates `out/<reader>/<name>.output` with its directory, and spawns a detached `rimz wait watch <name>` with null stdin and stdout, the room's `log/wait-watch.log` (`StatePaths::wait_watch_log`, opened for append and shared by every watcher) as stderr, and `process_group(0)`, through `child_process::spawn_detached_reaped_as_agent`: the watcher runs the agent's own command, so it keeps the agent's environment, temp unit included, where every other detached child gets the user's `TMPDIR` back.

`signal::run_watcher` takes `locks/loop-watch-<name>.lock` in the room state directory before it reloads and checks the catalog row, which closes the race with a cancel that lands before the watcher starts. The lock holds `{pid, started_at}`, and a second watcher for the same task exits without running the command. Claims, probes, and GC removal reach the lease only under its directory's `lease-gate.lock`; the gate covers the attempt and body I/O, not the lifetime hold. Gated holders publish a complete body before probes can read it, and a transient probe or GC attempt cannot make a starting watcher exit. Gate acquisition waits up to five seconds; a timeout is an error naming the gate path and a `fuser` hint, never another claimant.

The command runs in the task's `dir`, else the linked worktree it was armed from, else the project root. The watcher drains stdout and stderr into the output file and keeps a 4 KiB tail. At arm time, `cli/wait/add.rs` resolves an explicit timeout first, then no timeout when keepalive is enabled and `HarnessConfig::ping_lifetime` admits the caller's published row (falling back to its resolution row when absent), otherwise 30 minutes, independent of `loop.default-timeout`. `DeliveryTrigger::Watch.timeout` is optional and only a present value is persisted. The watcher runs to exit with an optional one-time check-in; polled watch probes omit that check-in. A persisted timeout applies as written. Ordinary `check` and `verify` kill at their timeout. At the deadline an observed exit wins. Otherwise the watcher fires one `Running` outcome, with the tail and the output file measured so far, and keeps draining until the command exits. The check-in does not kill the command, filter on `on`, consume the row, or change strikes. In `compose_wait`, its verdict gains ` · still watching` before any output segment; `WatchVerdict::label` and loop logs print the plain label. Its body includes `Stop it: rimz wait cancel <name>` and, when a timeout is recorded, `Another check-in: rimz wait --in <timeout>`, a timer independent of the running command.

A watcher-originated fire runs `rimz loop run <name> --signal-json …` and waits for it while still holding the watcher lock, so the check-in delivery cannot overlap the terminal fire. An append or fire failure is logged and the final outcome is attempted anyway. Every other signal emitter spawns its runs detached.

For PID, check, and file specs, `signal::poll_watch` probes then sleeps: the check's `every` interval, or one second for PID and file. PID uses native `kill(pid, 0)` rather than a shell loop: `ESRCH` meets the condition, while success or `EPERM` keeps watching. A check probe runs to exit without a check-in, truncating and rewriting the output file before every run so evidence is the latest run's output. Its spec's `on` chooses success or failure; exit 126/127 emits `Exited` and ends the wait. Otherwise polled specs emit `Met` on completion and one `NotMet` check-in evaluated between probes; a blocking check defers that check-in.

A file watch compares existence, size, modification time, and identity (`dev`, `ino`) against its arm mark. With `grep`, its `GrepCursor` holds a byte offset and the identity it was read on, starting at the arm mark (zero and no identity if absent); it restarts at zero when the identity changes or the file is shorter than the offset (a same-inode truncate that regrows past the offset within one poll is not detected), and tests only newline-terminated lines using literal case-sensitive matching. It trims a trailing carriage return; a straddling line starts at the arm byte. The whole matched line is written to the output file; `Met.line` is capped at 4 KiB, and the label renders a one-line preview. Relative paths are resolved against the arming cwd and stored absolute. The [file reference](../../reference/cli/wait.md#file---file) owns the user-facing contract.

Cancel removes the row first, then `stop_watcher` sends SIGTERM to the lock holder's process group, stopping the watcher and its command together. Non-positive PIDs are rejected, and an absent process counts as stopped. If a watcher dies without firing, the host's watch-lost rule fires the `Lost` verdict after the 30-second grace, with the output file's tail as evidence.

`signal::wait_output_path` derives `StatePaths::out_reader_dir(wait_meta.reader)/<name>.output` (`out/_unnamed/` for a row with no reader) for arming, watching, and lost-watcher evidence. `WatchOutcome::measured` records the file's byte size, line count, and estimated tokens (`utils::tokens::estimate` over at most the first 1 MiB, scaled by length beyond it), and records the host path as `output_path` in every isolation. A failed measurement warns and records a zero summary, which renders as `· no output` for command watches and no output segment for polled watches, like an empty file. Teardown keeps the file; gc prunes it only when there is no running watcher and no write in the seven-day grace. The run record keeps the tail for `rimz loop logs`.

## Waits

A wait is a session-pinned delivery row: a `Deliver` task whose target is one live agent. RimZ writes delivery rows to the instance tier through `schedule::arm::arm_delivery`, which both `rimz wait` and `rimz loop add --wait` call. Hand-written configuration rows can also carry a delivery target; a user shell's `wait list` lists them, in text and JSON alike, but an agent's session view does not.

`schedule::instances::insert_delivery` clears arming and strike overlays under the instance lock before publishing the row; a duplicate returns before any clear. `arm_delivery` uses one compare-and-remove rollback for later config-edit or watcher-spawn failures, so a failed arm leaves no row. `TaskCatalog::remove` runs its prechecks, then clears overlays before removing an instance definition, so an overlay failure leaves the row and watcher intact. Config and project definitions keep definition-first removal to preserve a user's disable or strike-out if editing the definition fails. Session retirement keeps its best-effort cleanup order below.

`DeliverySpec` carries a typed trigger, name, prompt, target, and provenance. The provenance decides what the builder accepts:

| Provenance | Accepts | Name |
| --- | --- | --- |
| `SelfWait` | a delay or a watch spec; no prompt, separate check guard, surplus gate, or deadline | minted, workspace-unique `wait-<petname>` |
| `Loop` | any trigger; `rimz loop add --wait` builds a clock, signal, or condition delivery | given |
| `Team(instance)` | a standing signal subscription | generated ([Team bindings](#team-bindings)) |

`SelfWait` is the only provenance that writes `wait_meta`: `armed_at` and the optional `delay`. `schedule::delivery_owner` classifies records in order: team, resident loop (a row an older RimZ armed with `loop_task`, which no builder writes), self wait, then a plain loop named after its row. Its `Display` is the JSON `owner`: `self`, `loop:<name>` (the row's own name for a plain loop, the declaring task for a resident subscription), or `team:<instance>`. `schedule::watch_lost` is the display reading of a missing watcher and shares the host's `WATCH_LOST_GRACE_SECS`: a row with self-wait metadata reads `starting` through 30 seconds after `armed_at`, then `lost`, and a row without that metadata reads `lost` at once. The host's `Lost` fire measures the same grace from its own first-sight stamp in `lanes/loop-fire.json` (`crates/rimz/src/harness/schedule/fire.rs::plan`), so a display can read `lost` before the host fires. A name that belongs to a project task, or for a team row to a machine task, is refused as configuration-owned.

`rimz wait` accepts a positive delay of any length, a positive `--pid`, a polled `--check`, a `--file` with optional `--grep`, or `--run`, and resolves the live calling agent through `@me`; a user shell cannot arm or cancel. `DeliveryTrigger::Watch` carries the spec, row polarity, and check-in timeout. The timeout is `--check-in` when given. Otherwise it is none when `[harness] cache_keepalive` is on and `ping_lifetime` admits the calling agent, and 30 minutes in every other case (`cli/wait/add.rs`). A check-in sends one still-running notice and never stops the watch. The old `--timeout` flag refuses with a pointer to `--check-in`. PID watches observe existence, not process identity or exit status, and reject `--on`.

For signal deliveries, the builder applies caller-first, target-fallback defaults and the other-agent lifecycle guard ([cli/loop.md § Caller-scoped defaults](../../reference/cli/loop.md#caller-scoped-defaults)). One locked instance mutation then compares live rows by kind and session, parsed selector, normalized matches (absent equals empty), and resolved root. A condition delivery stores one canonical joined clause and a normalized hold, and its dedupe compares the target session, clause list, hold, resolved root, and scope (`TaskEntry::run_dir()`), so the same expression on two worktrees makes two subscriptions. A duplicate returns `AlreadySubscribed` and rewrites nothing: not its name, prompt, provenance, or overlays.

Arming and canceling print the caller's self view after the receipt: attention-ordered self waits, with loop and team subscriptions grouped on `also woken by`. The row set follows scope, never format. From a user shell, `wait list` is room-wide and read-only: text and JSON read the room as `loop list` does, hand-written configuration deliveries included, and text shares the expanded WAKE-UPS body with `loop list --all`. From an agent, the self view, JSON, and receipts' `pending` keep the instance-delivery rows for the caller's pinned session. Every JSON row carries `owner` and launched `parent`. Cancel requires a caller: a name selects any targeted row, while `--all` selects only self waits and stops their watcher groups.

Shell-command previews in `WatchSpec::subject` and `WatchSpec::headline` preserve a trailing unquoted output-redirection clause verbatim and shorten only its command prefix. Without a trailing clause they use `theme::fmt::command_preview`: at most 120 Unicode scalars, keeping the first 60 and last 59 around an ellipsis. Grep patterns, matched lines, and prompt previews use that formatter directly, while stored commands and logs keep the full text.

**A session-pinned instance row never outlives its target's durable end.** Retirement follows that durable fact, not any one producer of it: the lifecycle hook, the exec wrapper's exit stamp, the store reaper, worktree removal, rebirth's unrecovered stamp, and orphan-subagent reclaim all end a session, and only the first is a hook. A new producer needs no retirement code of its own.

`schedule::arm::retire_session` (`crates/rimz/src/harness/schedule/arm.rs::retire_session_in`) works in five steps:

1. Wake the session's hibernating panes, warning on failure.
2. Remove the instance rows pinned to the kind and session, paused and disabled rows included.
3. Stop each removed row's watcher group and clear its arming and strike overlays, warning on failure.
4. Withdraw the session's pending idle-stop request, under either scope, so a resumed restart does not inherit it.
5. Under `Session` scope only, clear the session's [raised attention](../agents/model.md#waiting-and-asks) in `records/raised.json` (`store::raised::retire`: its ask, alerts, and human-turn stamps). A closed ask is audited as `ask.closed` with cause `retired`.

A `RetireScope` chooses the rows in step 2: `Session` takes all of them, for an identity that will not come back, and `UnrestorableOnly` leaves the declared rows standing (team and resident bindings), for a session that continues under the same id. The return is the number of removed rows that nothing arms again: self waits and `loop add --wait` rows, never a declared binding. A failure in step 2 returns a `RetireFailure` with a count of zero and nothing removed. A failure in step 4 or 5 returns a `RetireFailure` whose `dropped()` carries the rows step 2 already removed. Retirement never signals the calling process: `stop_watcher` skips a lock whose recorded pid is its own, so a watcher that retires its own row mid-fire finishes that fire instead of killing its process group.

Lifecycle `Ended` and `Lost` call it with `Session` after the durable event and before event signals (`Lost` sets no `ended_at`, so that call stays load-bearing); an explicit agent-tree stop calls it after each successful node stop; the exec wrapper calls it for the session it stamps ended, in the same exit tail. `agents restart` calls it once the replaced pane is closed, and picks the scope from the branch it took: a fresh restart mints a new identity and retires the old one whole, while a resumed restart is the same session continuing and takes `UnrestorableOnly`, so the role's declared bindings carry over rather than depending on a re-arm nothing orders against the removal. The restart line reports the count when it is non-zero. A restart that fails before the pane closes retires nothing.

A wrapper whose session has moved on ends nothing. `resolve_own_agent_end_trace` ends the wrapper's own launch's current row (`address::launch_row` over the audit projection, an ended row included; the launch's live row on the wrapper's own pane first, since an exact-id resume of a cleared conversation can leave one launch live in two panes) and never another occupant of the pane, since a pane outlives its occupants and an earlier occupant the reaper ends just after a resume would outrank the resumed row. A launch row bound to a pane other than the wrapper's own, or to any pane when the wrapper has none, means a superseded wrapper whose replacement has already attached: it appends no `rimz.agent-ended` and retires nothing. A resume whose launch row is absent falls back to its resume target under the same binding rule. The replacement's attach precedes its provider spawn, so any tail that reads after the replacement registered sees the new binding.

`schedule::arm::retire_ended_sessions` is the reconcile that covers every other producer, and the one place the predicate is spelled: an agent row that is not a provider subagent, matches a pinned kind and session, and carries `ended_at`. It acts on positive evidence only: a session a later lifecycle event revived has no `ended_at` and keeps its rows, a target with no agent row at all is left to gc, and a session the live roster protects for rebirth is never ended in the first place. It is pulled from two points: every real lifecycle hook observation whose commit appended an event, borrowing durable audit rows after that commit, and `fire_signal_with_wait`, before it selects a single task. State snapshots bypass this sweep, leaving it to the next real hook or signal fire. An observation that appended nothing (a side conversation's repeat hook, a read-only tool use) published nothing, so the session reaper never ran under it and no end appeared for the reconcile to find; it reads no audit rows and does no fold. The consumer is where the rule has to hold, because the sibling-skip branch returns before `delivery_target_alive` and a listener whose family mostly fires siblings would otherwise never meet a liveness gate. The reconcile first reads the sessions named by instance rows, raised asks, alerts, and human turns, idle-stop requests, and hibernation entries (`crates/rimz/src/harness/schedule/arm.rs::retire_ended_sessions_in`). A workspace with none of these returns before it reads the audit rows. Any one of them alone, such as a pending idle stop or a raised ask, is enough to make it read the audit rows and retire that session.

`delivery_target_alive` rejects a session with `ended_at` set, and gc is the backstop for what the reconcile leaves: rows whose target has no agent row at all. An instance row is runnable or it is garbage: gc also reaps any `Instance` row whose action does not compile (a target lost to schema drift can never fire or retire), while machine and project `loop.toml` rows with an invalid action stay listed as `<invalid>` for the user to fix. Hook config, arming, reconcile, and retirement failures are logged as warnings and never fail a fire, hook, exit, or restart, and never reach hook stdout.

`pending::project_pending_waits` projects armed one-shot delivery rows onto their target agents as `pending_waits`, which the sidebar and `rimz agents list` read. Timers, PID waits, watched commands, polled checks, file watches, and one-shot signal deliveries count; standing subscriptions and recurring clocks do not. `WatchSpec` maps directly to pending `command`, `pid`, `check` (`command`), or `file` (`path`, `grep`) kinds; no command string is parsed. What a pending wait does to the displayed status is [model.md § Sleeping](../agents/model.md#sleeping), and how a card draws it is [the interface reference](../../interface/sidebar.md). Pending one-shot condition waits project as `PendingWaitTrigger::Condition`, and the sidebar renders their expression and hold with a static wait glyph. A live member's pending one-shot wait also withholds `team.idle` ([Team signals](#team-signals)).

Pending waits also feed `harness::owed::owed_wake` through `TurnWaitView::load`, holding the supervised run fold open at a clean end. Reading the catalog before the queue covers the handoff from an armed row to its wake message; consuming a row alone does not imply the run completed.

### Team bindings

A team role declares standing subscriptions for its own seat. Each `[[agents.teams.<name>.roles]]` entry has a `signals` array of inline tables with `signal`, an optional string-valued `match`, and an optional `prompt`; the containing role is the receiver. `prepare_team` validates the selectors and explicit other-agent matches for `agent.*`. Each role's complete ordered binding list enters the executable trust hash, and an empty list leaves the hash unchanged, so moving bindings between roles needs a fresh grant.

A fresh `launch_layout` refuses a team binding scoped implicitly to the root checkout's CI or PR state, before any pane or worktree side effect, and names the fixes: an explicit branch or path match, `branch = "*"` for every checkout RimZ watches, or `-w <worktree>`. A launch from a linked worktree passes, a `--from-pr` launch skips the check, and resume does not apply it. `team = "*"` or `instance = "*"` disables the cohort default; on `team.*` this includes the four lifecycle signals as well as stage flips. Neither `handle = "*"` nor `session = "*"` satisfies the explicit other-agent requirement for `agent.*`.

After a committed lifecycle `Registered`, the hook calls `team_stage::react_to_lifecycle`, which reads the strict effective trusted config and calls `schedule::team::arm_member` for a root team member, never a subagent. It uses the member's adopted session identity, role, channel, and worktree, so launch, resume, restart, and role re-add share one registration path. All binding specs are built before anything persists. The rows carry `TaskEntry.team = "<team>#<channel>"`, target the member's exact kind and session, and deliver at the next `done` boundary.

Row names are `team-<team>-<channel>-<role>-<signal slug>`, lowercased, with dots and any character outside `[a-z0-9_-]` replaced by `-`. Repeated or colliding slugs within a role get a declaration-order `-<n>` suffix; a collision between lanes in one room is accepted. Repeated registration deduplicates, and an already-subscribed manual row is not relabeled as a team row. Automatic arming never replaces machine or project configuration: a generated name that collides with a configured task is reported in hook diagnostics, and the user renames that task before the member re-arms.

### Idle stop

Idle stop closes an agent that has a pending `rimz agents stop --when-idle` request ([`store/idle_stop.rs`](../../../crates/rimz/src/store/idle_stop.rs)) once it has rested for the requested duration with nothing owed. The decision runs twice, cheap in the producer and in full in the helper:

1. The producer checks the rollup terms and the clock, then spawns `agents idle-stop` at most every 30 seconds per session.
2. The helper runs `idle_stop::decide` again on fresh reads: owed wakes, queued messages, open runs, the seat's board, and pending same-kind ingress stamped after the request.
3. The helper applies the rest and debt terms to every live launched descendant the stop cascades to (`closing_with`). The clock is the root's alone.
4. The helper declines when the run the stop path would select for any of them is not terminal.
5. The helper runs the decision once more before its final request read, and the ordinary stop path follows at once.

Rest is measured from the latest of the request, the turn end, the provider marker `settled_outcome` admits, and the session's last event. That covers a turn only a marker settled, and a failed compaction. The clock keeps sub-second precision, so a stop never lands before the full duration. Provider-native subagents are not a term: a native row leaves `Running` only on its Stop hook, a superseding parent turn, or the three-hour ghost reap.

A helper that declines writes nothing, so the request stays armed. Session retirement removes the request ([Waits](#waits)), and a room reset removes every request inside its commit boundary.

The hook drainer withdraws a root session's request when a human-opened `TurnStarted` has a frame timestamp strictly greater than `requested_at`. Supervised children do not withdraw; team seats and peers with open runs do, but record no spend-ledger user input. The spend-ledger append and withdrawal share one record-aware authorship predicate, excluding Claude task notifications. Comparison and removal take the workspace lock against the current request, so a tie or re-arm after the prompt keeps it. Replay skips both writes because confirmed deliveries cannot be reproduced; a crash between the hook transaction and withdrawal can leave the stop armed, held Busy until the turn ends and the full rest elapses. The helper holds on unapplied same-kind ingress newer than the request, including another session's frame, then re-reads the request after its last decision with no intervening work before stopping. The cursor advances only after frame processing completes, so a prompt is either pending ingress or has finished its withdrawal before that final read.

| `launch_retry` | exec wrapper, each time it answers a fresh launch's [startup death](./fleet.md#a-startup-death-is-relaunched-first) with another spawn | provider kind, the launch's handle (`label`), the run every attempt shares (`run_id`, absent for a launch without one), which relaunch this is (`attempt`, from 1; absent lines read as 1), the exited process's `exit_code` (absent when a signal killed it), its spawn-to-exit `startup_ms`, whether the new spawn succeeded (`relaunched`), and the spawn error when it did not |

`rimz stats` folds both generations, scoped to the active dashboard window, into one rollup of assists that took effect. The same outcome classification filters the default timeline: deliveries, queued child stall notices and team nudges, stops, freezes and deepening steps that reclaimed bytes, relaunches, successful window resets, completed sweeps, successful port opens, and actions that count as recorded. Held or failed attempts are counted as held beside their kind in the timeline header. Deepening steps that reclaimed 0 bytes remain recorded but are neither counted nor held. The dashboard omits held detail and zero-count categories, except that Auto-compact counts requests including held attempts. `rimz stats --json` publishes the rollup without events. `rimz stats --assists` shows the latest 50 effective timeline lines across both retained generations, newest first, folding repeated outcomes within each subject's history of an assist kind into `×N over span` lines (`over span` omitted under one second). `-n` counts lines, `older` counts records outside the shown lines, `-n 0` shows all retained, and `--all` includes held attempts and steps that changed nothing. `--json` keeps one event per record with the same outcome filter, with `-n` and `older` counting records. The complete outcome classification and projection belong to [stats internals](../stats.md#machine-readable-surfaces).

A flip compaction reads `flip compaction` in the event stream and counts toward compact commands sent only when the command was sent; a flip completing does not count a queued command. Only a member leaving its own stage for one another role owns is eligible; `Done` has no owner and never compacts. The effective `[harness] flip_compact` or role `flip-compact` threshold is evaluated before pane availability: a flip below it, or with unknown occupancy, makes no attempt and writes no record. Every attempt records the threshold, including errors and missing-pane skips, and none of these failures fails the flip.

A new smart strategy ships as one accountable slice: define its typed trigger, evidence, and outcome record; append it from a writer outside the sidebar import graph; fold it into the stats rollup; and add its variant and writer to the table above.
