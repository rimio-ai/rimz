# Workflow engine

A workflow is a durable run through a flat graph of checks and steps. The run record is truth; a wake only asks the engine to read it again. The engine hosts script checks and headless judges, and drives supervised agent attempts through the CLI's `AttemptHost` implementation. A loop task can start runs, and the scheduler tick re-drives every active run so its clock bounds fire on time.

## Where the code lives

- `crates/rimz/src/harness/workflow/engine.rs::advance` owns the locked decision, off-lock evaluation, and sequence-checked settlement loop; `create`, `cancel`, `resume`, and `wake` are the run-control entries in that module.
- `crates/rimz/src/harness/workflow/mod.rs::AttemptHost` separates engine decisions from launch, observation, checkout eviction, and stop operations. `crates/rimz/src/harness/workflow/engine/agent.rs::prepare_end` admits the off-lock stop and `crates/rimz/src/harness/workflow/engine/agent.rs::finish` settles it.
- `crates/rimz/src/harness/workflow/state.rs::Transition` owns locked routing, bound decisions, and hosted-child termination; `crates/rimz/src/harness/workflow/script.rs::evaluate` hosts scripts and judges through one interruptible child-publication boundary.
- `crates/rimz/src/harness/schedule/runner.rs::TaskFire::prepare` starts a run for a `workflow` loop task; `crates/rimz/src/harness/workflow/engine/accounting.rs::transition` turns each persisted transition into its assist or diagnostic record.
- `crates/rimz/src/store/workflow.rs::RunRecord` owns the persisted vocabulary; its module owns the record and journal codecs, not transitions.
- `crates/rimz/src/cli/workflow.rs::run` parses and presents without creating rooms; its private host binds the engine to supervised launches, runtime observations and the stop cascade. `crates/rimz/src/harness/schedule/signal.rs::wake_workflows` is the read-and-spawn signal edge and `crates/rimz/src/harness/schedule/fire.rs::tick_workflows` the read-and-spawn clock edge; `crates/rimz/src/harness/workflow/mod.rs::advance_args` is the one `workflow advance` argv both edges and run creation spawn; `crates/rimz/src/store/gc/classes.rs::collect_owned` owns terminal-home retention.

## Definitions

Machine definitions live at `~/.rimz/workflows/<name>/workflow.toml`. `rimz workflow schema` derives JSON Schema from the same Rust types that deserialize TOML. Every table rejects unknown fields. `rimz workflow validate [dir] [--json]` loads profiles through the machine definition catalog and reports dotted paths, resolved edges, warnings, and errors. Agent rows include `do_background`, derived from the adapter's background-parking coverage. Validation refuses judge profiles whose adapter has no headless launch. It warns about a step without background reporting, a judge sharing its target step's profile, and agent nodes when machine auto-continue is off. Validation never creates a room. A workflow directory must be inside the machine definitions directory. The committed `crates/rimz/tests/fixtures/workflows/babysit-pr/` fixture demonstrates script checks, supervised steps, a judge and signs; it is not installed automatically.

`[workflow]` has required `scope` and `start`, optional `deadline`, and one header edge, `on.deadline`. Start names a check. Scope is `worktree` or `project`: worktree scope uses the selected checkout, and project scope runs every node at the room's project root. Deadlines accept RFC 3339 instants or local civil dates and datetimes. A bare date means local midnight; the record stores the resolved instant.

`[checks.<name>]` has exactly one of `run` or `agent`, optional `prompt-file`, `window`, `timeout`, and `on.<outcome>` edges. An agent requires a prompt file; a window requires an agent and accepts only provider-window terms. The engine supplies `timeout` and `invalid`, each defaulting to `@user`. An edge may name another node, `@wait`, `@done`, `@failed`, or `@user`, except that `on.timeout` cannot wait on its already-expired clock. A check that can wait must have a timeout.

`[steps.<name>]` requires `agent`, `prompt-file`, and `then`, which names a check, never another step or a special target. Optional fields are `window`, `takeover`, `timeout`, positive `max-visits`, and `on.asked` and `on.cap` (both default to `@user`). Step edges cannot target `@wait`, and `on.cap` cannot target the capped step itself. A cycle through steps must contain a visit bound; a check-only cycle must contain a wait edge. Checks and steps share one name namespace.

`run` is an argv parsed with `shlex`, not shell text. Pipes, variable expansion, and redirection belong inside a script. Every word containing `/` names a file relative to the workflow directory: only normal path components are accepted, and canonical resolution must stay inside the directory. Other words, such as `sh` or `uv`, resolve through `PATH`. Files are resolved and hashed again for every evaluation. Checks must be idempotent: a host killed after evaluation but before settlement causes a fresh evaluation, not recovery from its previous stdout.

## Starting and inspecting

`rimz workflow run <name|dir> [-w <worktree>] [--prompt <text>]` validates the parsed bytes it seals before creating a run. Only a single normal path component is a catalog name; `.` and `./` refer to the current definition directory. It requires an existing room (`rimz start` creates one) and serializes the uniqueness check and creation under the room workspace lock. Active and parked runs hold the `(workflow, scope path)` slot; a duplicate is the typed `WorkflowErr::Exists`, which `run` prints as a refusal and a loop fire records as `workflow_skipped`. Worktree scope selects the current checkout or the existing RimZ-owned worktree named by `-w`, never creating one. Project scope always selects the root, ignoring `-w` with a stderr notice; a loop with `each-worktree` creates one project run and skips subsequent fires. Root occupancy uses the same takeover read with owned nested worktrees excluded. The prompt is stored unchanged and exposed in context.

`crates/rimz/src/harness/workflow/mod.rs::ScopeRoots` supplies both paths to `create`. Before reading the definition or prompt, and again under the creation lock, admission compares each existing run's path against the candidate path for that existing run's kind. A held project run therefore wins over a broken definition or a scope-kind edit, without making a worktree run at the root block a different worktree.

Run ids are `wf_` UUIDv7 identities. `list` enumerates active and parked runs across rooms. `show`, `cancel`, `resume`, and hidden `advance` resolve an id from any directory. `show` starts with the work directory, then renders position, bounds, visits, prompt, waiting state, and the journal; JSON is `{dir, record, journal}`. The journal is inspection evidence, never an input to engine decisions.

`cancel` is first-terminal-wins. `resume` refuses terminal runs. A parked run re-enters its current node, or `--at <node>`, with a fresh timeout clock. `--extend visits=+N` adds a run-wide grant to every step's cap; `--extend deadline=<when>` replaces and re-arms the deadline. Extensions without repositioning also apply to active runs.

## Storage and isolation boundary

All paths come from the disk path module. Each room holds `owned/workflows/<run-id>/`:

```text
record.json        current run, version 1
journal.jsonl      append-only transition evidence
workflow.toml      sealed specification bytes
work/              RIMZ_WORKFLOW_DIR, writable by nodes
  context.json     replaced before every evaluation or attempt
  notes/           node-owned cross-node scratch, created with the run
  signs/           live step guidance, created with the run
```

The engine-owned record, sealed spec, and history are outside the node-writable work directory. Notes, signs and claims live under `work/`; the engine reads only `signs/<step>.md`, never notes or claims. Every evaluation and attempt allocates a fresh `seq` from `next_seq` (`crates/rimz/src/harness/workflow/engine.rs::prepare`), a judge retry and a re-run after a dead host included, so keying `notes/` writes by sequence does not make a repeat a no-op: nodes key them by the item they record. Soft reset retains workflow homes. Hard reset removes them, unlike supervised-run records. Class GC removes a terminal workflow's entire home when its record mtime is older than the seven-day owned grace; active, parked, and recent terminal records stay. A home without `record.json`, left by a crash during creation and skipped by every reader, goes once the home directory's own mtime passes the same grace.

The record stores scope, project root, sealed-spec digest and original definition directory, prompt, current node and entry clock, state and park, routed input and key, open wait and recheck time, per-step totals and per-key visits, grants, deadline state, sequence allocator, live host identity, previous attempt, and terminal time. Keys preserve integer versus string identity.

Journal entries carry time, node, optional attempt sequence, and an event: evaluation, attempt, merged wait, engine-bound route, park, terminal, cancel, resume, or signal wake. Evaluations retain the routed object and `origin` (`check` or `engine`, defaulting to `check` for older rows); invalid results also retain a stderr tail. Script and judge evaluations retain the digests published with the attempt's child, whichever process ends the attempt; an evaluation whose child never spawned has no digests. History appends are data-synced before record replacement under the same workspace lock. New run directories sync their new ancestors. A crash between append and record publication can duplicate an entry with the same sequence, never authorize a transition from history. Readers tolerate torn or unknown history rows.

## Evaluation and routing

Scripts and judges are hosted by the short-lived `advance` process, not a supervised run. The record first publishes a live attempt (`kind = script | judge`, sequence, node, start time, host PID and process-start token). Preparation publishes its context under the same workspace lock, so a stale host cannot overwrite a newer attempt's context. The lock is released after the child's identity and evaluation digests are published together, before waiting for output. A second advance leaves a live host alone while no bound is due. A dead or reused hosted identity becomes `canceled` and re-runs free. An agent attempt instead retains its supervised run identity across advances; its host identity owns only launch or stop work.

Scripts have scope checkout cwd, null stdin, the room workspace pin, `RIMZ_WORKFLOW_RUN`, and `RIMZ_WORKFLOW_DIR`. Context contains `run`, `prompt`, `node`, `seq`, `key`, `input`, `output_path` (`work/<seq>.check.json` for judges, null otherwise), `retry`, `signs_path`, and `prev_attempt`. Only steps have `visit` (under the current key) and `visits` (total), including this launch. Previous attempts expose step, outcome, sequence, visit, key, start/end, claim path, handle, supervised run id, HEAD pair, stopped and surviving children, ask or limit evidence, and cost. Unavailable evidence is null.

A check prints exactly one JSON object: required string `outcome`; optional string `reason`, RFC 3339 `recheck_at`, and string or integer `key`; other fields remain payload. Nonzero exit, bad JSON or field types, unrouted or engine-reserved outcomes, invalid recheck time, and missing live script paths route `invalid`. A missing key inherits the run's current key. The full normalized object becomes the target's input. `recheck_at` only delays `@wait` and is clamped to the earlier of the check's entry-time timeout and the run's unfired deadline, so the tick, which never wakes a run before its `recheck_at`, cannot sleep past either bound. A provider-limit reset is clamped the same way.

Before settlement the host re-locks and verifies the live sequence. A stale result writes nothing. `@done`, `@failed`, and `canceled` never change again. `@user` parks with the bound's reason or the check object's reason text. A wait keeps its node and original timeout clock. Repeated identical waits merge in the record (first, last, count, recheck time); leaving the wait appends one summary to history. An early plain advance increases the wait count but does not evaluate.

Every advance checks bounds before waiting. Deadline fires once, with `{outcome: deadline, deadline: T}` as input, then stops gating until extended. A check timeout spans all its evaluations and waits; it routes `{outcome: timeout, node: C, timeout: S}`. A step timeout ends the attempt and follows `then`. A step launch over `max-visits + visit_grant` launches nothing and routes `{outcome: cap, step: S, visits: N, max: M}`. Engine objects inherit the current key.

A running host re-reads the record at the bounded subprocess runner's interrupt cadence. Spawn and publication of the child's group-leader PID, process-start token, and evaluation digests share the workspace lock with cancel and bounds. Any advance or cancel kills the recorded group under that lock before withdrawing the attempt, including when its host is stalled or dead, but only when the child's start token still matches. Missing or changed tokens never authorize a signal. The host reaps its child when it resumes; its stale sequence cannot settle again. Checks remain idempotent, not exactly-once effects: a host can die after a script's effects but before settlement.

One advance continues through transitions until it waits, parks, terminates, encounters a live host, or would evaluate a check twice without a step attempt between. Repeated cap-only routes also yield rather than spin without launching anything. These guards leave the run active for a future wake, which the next tick supplies.

## Agent attempts

Admission checks bounds, the visit cap, the provider window, and checkout occupancy, in that order. A closed window merges a `window` wait. Open turns merge a `takeover` wait; idle occupants without permission to evict merge an `occupied` wait. These waits preserve routed input and key and consume no visit. Occupancy requires an authoritative mux pane listing, not historical pane stamps or cached topology; a failed listing propagates instead of admitting a launch. Absent pane stamps are masked only in the host's private snapshot. Eviction runs off-lock, then admission reads bounds and window again; a successful eviction admits only the immediately following launch, fenced by its next sequence, without another occupancy read. An eviction failure becomes a counted `died` attempt. The pane listing, prompt composition, and `git rev-parse` all run under the lock and take time after the first bound read, so `prepare` takes a fresh clock after them and reads the bounds again: a bound that came due during that work routes and publishes nothing, consuming no visit and no sequence. Only after that second read does an admitted launch count a visit, record HEAD, and publish its context and live attempt, stamped with the fresh clock. Bounds are re-read rather than the work moved off-lock, because admission and publication share the lock on purpose (see above). The window reading is not re-read: it was sampled in the same pass and provider windows move in minutes. A closed window's wait stores its blocking term with the reading in `Wait.detail` (`5h.left=12<42`), which the waiting line prints.

Prompt composition reads the prompt file, an optional `signs/<step>.md`, and the run prompt at every launch, joined by blank lines in that order. A sign's canonical target must remain inside workflow work. Digests use the spec's prompt-file spelling, `signs/<step>.md`, and `prompt`; absent optional text has no digest. Nodes are idempotent. A relaunch may find a dirty checkout left by a stopped attempt and must handle it deliberately.

Completed supervised runs end as `ended`; failed, verification-failed and timed-out runs as `died`; canceled runs as `canceled`; budget-exceeded runs as `limited` with no known reset. A live attempt or its child carrying typed provider-limit evidence ends as `limited`; a blocking ask ends as `asked`. Queued asynchronous questions do not end an attempt. The workflow's own step timeout ends as `timeout`. A deadline ends the attempt as `canceled` and routes `on.deadline` once. Other ends follow `then`, except `asked`, which follows `on.asked` or parks with the ask text and kind.

Every agent end publishes `ending` and saves observation evidence in `prev_attempt` under the workspace lock before stopping. This preserves asks and limits that the stop may retire. The host stops the attempt tree off-lock, samples post-stop spend and HEAD, then re-locks to check the sequence and stopper identity, journal the attempt, and route. No successor launches before stop returns. An advance leaves a live stopper alone and reclaims a dead one, merging staged child evidence with the new stop inventory. Cancel during launch leaves the live launch owner responsible for publishing and stopping the returned run. When the launcher is dead, the engine recovers an unpublished supervised run by its workflow id and attempt sequence and stops it before settlement. Recursive live launched children are stopped first and recorded under `children.stopped`; independently launched peers and team cohorts survive under `children.live`, with their current board stage when available. Stops use the shared cascade without adding workflow-specific lifecycle events; the next visit's fresh pane projection excludes closed panes even while their agent rows remain. Asks are materialized by ask id; provider limits use typed turn-error classes and the affected agent's account and model to read the reset, never provider-text matching. Cost is sampled from the supervised record after stopping; unstamped spend remains null.

Steps launch as detached root supervised runs, never as the advancing agent's children. Their launch identity carries `WorkflowAttemptRef {run, seq, role}` and pins `RIMZ_WORKFLOW_RUN` and `RIMZ_WORKFLOW_DIR` under all isolation levels. Subagents do not inherit this workflow identity. `show` retains its JSON envelope `{dir, record, journal}` and renders attempt handles, short HEAD pairs, costs, stopped and surviving child handles, limit resets, and ask kind and text on a park. Its waiting line also covers step admission waits. Takeover blocker details are best-effort: a failed mux lookup prints `blockers unavailable` without hiding durable state or history.

## Headless judges

Judges use the shared headless profile resolver and launch planner with automatic permission mode. The workflow prompt names `RIMZ_WORKFLOW_DIR`, `context.json`, and `output_path`, and requires exactly one JSON object with the check fields and no prose or Markdown fence. The schema stays open so extra fields remain routed input. Claude enforces it; Codex omits its strict structured-output switch for an open schema and reads the prompt-shaped last message from its output file. Closed schemas, including loop verdicts, retain Codex schema enforcement. The provider's structured value is saved to `output_path`; without one, the engine reads that file. The value goes through the same check-object normalizer as script stdout. Judges are read-only on the scope checkout and its Git admin and common directories: scoped isolation overlays them read-only after all reach rebinds; host isolation enforces the rule only through the prompt. The ordinary root view and required-path rebinds already leave workflow work writable, including a room home under host `/tmp`. Signs are written only under `signs/<step>.md`. Headless permission requests are denied non-interactively, not surfaced as workflow asks. Claude classifies provider limits in its adapter; Codex supplies no typed limit result, so a failed limited Codex judge is `died`.

Folder-trust and adapter minimum-version checks run before taking the workspace lock to spawn the judge. Engine-decided canceled evaluations re-run free. A typed provider limit consumes no retry and waits until the known reset, or the next wake when unknown. A launch refusal, process failure, or missing object is `died`, with the refusal text as `reason` for a launch refusal; an invalid object is `invalid`. Either gets one immediate retry with `context.retry = {outcome, reason}`, then parks as `check`. The run stores `check_retry` and serde-defaulted `check_retry_context`, so retry evidence survives a dead host without reading the journal. Both reset on node entry and parked resume. The check's entry-time timeout spans all evaluations and waits.

## Wakes

Run and resume spawn detached advances; manual `advance` is also available. Every non-lifecycle signal routed through the scheduler's shared firing entry spawns one room helper when active workflow records exist. The signal path only reads records and spawns. The helper clears active runs' `recheck_at` under their workspace lock, journals the signal name, and marks live attempts as `woken` (missing on older records means false). If that check later answers `@wait`, settlement clears its new backoff and immediately re-evaluates once, bypassing the hot-loop guard for that wake. Wakes during the retry can request another pass; without another wake the ordinary guard applies. The helper spawns independent advances so one slow script cannot block other runs' wakes. A bad run warns without blocking later runs, and cross-room discovery similarly skips unreadable rooms. Lifecycle signals deliberately leave waits untouched: ordinary agent turns must not clear every workflow's backoff.

Every newly terminal supervised-run mutation through the harness wakes its workflow after releasing the workspace lock, including provider exits without hooks, wrapper failures, budget parks, timeouts, and rebirth cancellation. A hook-ended non-peer run settles its session spend before waking the workflow, so the advance reads the stamped cost. Room teardown cancels runs without waking workflows; the next advance settles those attempts. Non-terminal lifecycle and turn-error frames carrying `RIMZ_WORKFLOW_RUN` also wake only that run. Rebirth excludes workflow-attempt roots from recovery, cancels their supervised runs, and wakes each workflow to re-decide. Stops never close a supervised run's pre-rebirth pane id in the new session. Child edges carry no workflow pin: their asks and limits are sampled on the next parent edge or tick, within about a minute. There is no signal replay; a lost wake delays progress until the next tick.

## The tick

`crates/rimz/src/harness/schedule/fire.rs::fire_due_tasks` ends every scheduler tick, from the room host or the external timer, by calling `tick_workflows` for the root. It reads the room's run records and spawns `rimz --root <root> workflow advance <id>` for each active run that is due. A run is due when its `recheck_at` is absent or passed. Parked and terminal runs are never spawned. The engine decides everything else (bounds, window, occupancy, a live host): the tick reads `recheck_at` only so that it does not inflate a wait's `×N` count with early advances, and it never clears backoff the way the signal helper does.

Spawns are paced by the runtime cache `workflow-tick.json`, a map of run id to last spawn: at most one spawn per run per 60 seconds (`WORKFLOW_TICK_SECS`), except that a `recheck_at` that passed since the last spawn fires at once. The cache is written before spawning and drops runs no longer active; read and write failures warn and never fail the tick. `fire.rs` is in the sidebar import graph, so it writes only that cache and spawns; the invariant grep keeps it off the writer and the wake socket.

The consequence for workflow authors: a `@wait` without `recheck_at` is re-evaluated about every minute, so a check that wants a slower pace names `recheck_at`. A live step is observed every tick, so a child's ask or provider limit is noticed within a minute.

The external timer's roots (`crates/rimz/src/cli/loop_timer.rs::task_roots`) include every room with a nonterminal run, found through `crates/rimz/src/disk/paths.rs::workflow_runs_under`, so a manual run in a room with no loop task and no sidebar still ticks.

## Loop tasks

A `workflow = "<name>"` task is the fourth loop action (`TaskAction::Workflow`). Its fire takes the run lock, checks the room deadline, births the room when needed, and calls `engine::create` with the task's resolved prompt and `task = Some(<name>)`. It takes no start-throttle turn: the fire starts no agent, and the run's steps launch as supervised runs. A created run is a `launched` history row whose `run_id` is the `wf_` id. A run already holding the scope (active or parked) is a `workflow_skipped` row carrying the existing id, strike-neutral; a finished run does not block. With a sustained-true `when`, the planner re-fires a workflow task at the resident cadence, like `stay`, so an active run collects one skipped row per retry per checkout.

`each-worktree` takes `workflow` as well as `stay`: the fire runs per owned checkout with the checkout's run lock and stamps `checkout` on its row. `stay`, `takeover`, `subscribe`, `check`, and `judge` are refused on a workflow task, each naming the workflow node that owns the concept (`crates/rimz/src/harness/schedule.rs::TaskActionErr::WorkflowField`). The trust hash covers `workflow` (`crates/rimz/src/trust.rs::ExecutableTask`).

`RunRecord.task` is the provenance `rimz loop list` and `rimz loop show` select by, together with the record's project root; a manual run has none, so it appears in `rimz workflow list` and the sidebar but under no task. `loop rename` rewrites it on the task's nonterminal records under the workspace lock through `crates/rimz/src/harness/workflow/engine.rs::rename_task`, leaving terminal records unchanged.

## Attention

`crates/rimz/src/sidebar/enrich.rs::enrich_core` fills `SidebarSnapshot.parked_workflows` from the run records on every fold, producer and consumer alike, through the read-only `store::workflow::list`. The cockpit draws one inert line per entry. The room host refolds every cycle, so a park reaches the live sidebar within one data tick, or when an in-progress cross-tab jump releases the attachment, but the fresh-latest snapshot cache keys on the event-log extent and a park appends no event, so a passive `rimz sidebar snapshot` reader may show it only after the next event.

## Accounting

`crates/rimz/src/harness/workflow/engine/accounting.rs::transition` runs after `persist` publishes a transition and maps the journal entries it wrote. Accounting keys on evaluation origin, not outcome words: a check may legally route `canceled` or `limited`.

| Journal entry | Accounting |
| --- | --- |
| Explicit `Route` | One `workflow_route`, unless the record now waits; suppress the transition's evaluation and attempt accounting. |
| Check-origin evaluation | One `workflow_route`, unless the record now waits. |
| Engine-origin `canceled`, run active | `workflow_rerun` diagnostic, no assist. |
| Engine-origin `limited`, or run canceled | No assist. |
| Other engine-origin evaluation, active with retry context | `workflow_retry` diagnostic, no assist. |
| Other engine-origin evaluation | One `workflow_route` (including a second judge failure parking at `@user`). |
| Attempt end | One `workflow_route`, unless the run was canceled or an explicit route accounts for it. |
| Closed `Wait` | One `workflow_route` to `@wait` at the summary's timestamp, with `count` set to the final merged count, even on cancel. |
| Park or terminal | `workflow_park` or `workflow_end`. |

A still-open wait has no route assist yet; `list`, `show`, and the sidebar carry its live state. Closing a window, takeover, or occupied wait uses the same summary rule. Non-wait route records omit `count`. Explicit-route suppression also prevents a bound's engine evaluation from counting twice. `crates/rimz/src/harness/workflow/engine/agent.rs` appends `workflow_step` after a supervised run is published, and the loop runner appends `workflow_start` on creation. All five assist kinds count under the workflow category in `rimz stats`; diagnostics are rate-limited forensics that stats never reads.
