# The MCP server

`rimz mcp serve` gives a Claude, Codex, or Antigravity agent RimZ's own commands as MCP tools. Its user-facing contract (the tools, their arguments, the protocol methods) is the [`rimz mcp` reference](../reference/cli/mcp.md). This page covers how it is built and what it must keep true.

## Calls run in the server's process

The server runs each tool call in its own process, on a thread of the call's own. `crates/rimz/src/mcp/` speaks the protocol and holds the catalog and the wording, and it reaches RimZ code only through the `crates/rimz/src/mcp/runner.rs::Runner` it is handed. `crates/rimz/src/cli/mcp.rs::run` hands it `crates/rimz/src/mcp_tools/mod.rs::Tools`, which has one function per tool: each calls the library function the tool's command calls and answers with the value that function returns. So a tool does what its command does, with no process started per call, and its answer is that value rather than the command's printed text.

`guide` is the one tool the server answers itself, from the wording it read at its start (below), so it opens no room.

`cargo xtask invariants` holds that boundary with a textual guard (`ensure_mcp_calls_run_in_process` in `xtask/src/invariants.rs`). Over `crates/rimz/src/mcp/` and `crates/rimz/src/cli/mcp.rs`, it refuses a store, config, or room reach, which only the runner may make. Over `crates/rimz/src/mcp_tools/`, it refuses a stdout write, since stdout is the protocol channel, and an exit, since one call must not end the server that answers the others. The process stays small: an idle server holds the parked wrapper's 8 MiB private-memory budget (`mcp_server::an_idle_server_stays_inside_its_memory_budget` in the integration suite).

## The catalog

`crates/rimz/src/mcp/catalog.rs::TOOLS` is the one table of tools. Each `Tool` carries its capability (none for `guide`, which `crates/rimz/src/mcp/catalog.rs::tools_for` adds beside any served capability that has a guide), the command words it runs, its argument schema, and the function that turns arguments into an `Invocation` (argv, working directory, stdin bytes). Everything that lists tools or capabilities reads it: `tools/list` and `rimz mcp tools`, which share one result through `crates/rimz/src/mcp/catalog.rs::tools_list` (the server passes it each capability's `crates/rimz/src/mcp/catalog.rs::LoadMode` from `--always` and `--deferred`, and the command passes none), `rimz agents explain --mcps`, which prints `crates/rimz/src/mcp/catalog.rs::render_listing` over that same result so what it prints is what is served, `--only` parsing through `crates/rimz/src/mcp/catalog.rs::Capability`, `crates/rimz/src/mcp/catalog.rs::serve_args` for the arguments that start a server with chosen capabilities, the reference page's table (`mcp::catalog::tests::the_reference_table_lists_every_tool_under_its_capability`), and the routine-command check (`agents::conformance::every_mcp_tool_command_is_a_routine_command`), which keeps every command a tool runs under an entry of `ROUTINE_RIMZ_PREFIXES`.

Each tool's arguments are a private serde struct with `deny_unknown_fields`, and its schema is derived from that struct with schemars, inlined into one object with `null` dropped from optional fields' types and enums. Deserializing the call's arguments is the shape check. `wait` takes one required `trigger` enum and one required string `value`, so a call without a trigger, which `rimz wait` bare would read as a listing that exits 0, fails the shape check, and two triggers cannot be sent. A struct's `ToolArgs::refusal` adds a refusal only where the command would misread arguments rather than refuse them: a `self_tune` value with no setting (it would slide into the setting slot), a `notes_add` with both a body and a file (the file wins and the body is dropped), and a meta key containing `=` (the CLI splits at the first one). Other rules that span flags (which flag fits which verb or trigger, a `pid` value that must be a number) stay the command's, so the server cannot drift from the CLI.

The argv builder joins every flag value as `--flag=value` and puts every positional after `--`. An agent-supplied string that starts with `-` therefore arrives as data: a note titled `--force`, an LSP target `--help`.

## The wording

The agent-facing text is Markdown under `crates/rimz/src/mcp/tools/`, compiled in by `crates/rimz/src/mcp/wording.rs`: the shared `instructions.md`, `guide.md`, and per capability a one-line `instructions.md`, one file per tool, and a `guides/` folder. A file's identity is its path under that folder, the same path a user's replacement takes under `mcps/` in the RimZ home ([replace the wording](../reference/cli/mcp.md#replace-the-wording)). The skills of the same names keep their own copy in the skills pack for agents without the tools. `crates/rimz/src/mcp/wording.rs::Wording::read` resolves every file once, and its four readers all take the result: the server at its start, the launch plan (`crates/rimz/src/harness/launch_plan.rs::compile`, which turns each warning for the served capabilities into a `LaunchPlanWarning`, so it reaches the pane, the agent's record, and `rimz agents explain`), `rimz agents explain --mcps`, and `rimz mcp tools`. The server's own warnings go only to its stderr, which no user sees, so the launch is where a bad file is reported. The server resolves the home from its own `RIMZ_HOME` and `HOME`, each filled from the parent's environment under `--parent-env`, the same view its one-shots get, since Codex starts it without `RIMZ_HOME` unless `env_vars` names it.

A launch's instructions are `crates/rimz/src/mcp/wording.rs::Wording::instructions` of the capabilities it serves: their sentences on the first line, in capability order, then the shared text. The providers bound that text: Claude Code cuts the instructions and each description at 4,096 characters, Codex shows a deferred tool only the instructions' first line, which RimZ holds to 250 characters (the smaller of the two figures Codex's docs give, neither tested), and Codex compacts an input schema over 5,000 bytes and may replace a `oneOf` or `anyOf` node with `{}`. `crates/rimz/src/mcp/wording.rs::Wording::breaches` is the one check of the text limits: `mcp::catalog::tests::the_text_fits_what_providers_keep` holds the built-in text to it, and `Wording::read` holds each replacement to the same rules, checking the first line and the whole instructions with every capability so a file's verdict does not depend on the launch. A replacement that fails is reported and its built-in text served, so no file switches a tool off. Property descriptions stay short and in Rust, as doc comments the schema is derived from, and an enum's variants carry no doc comments, which would make schemars render a `oneOf`.

### Where long material goes

A tool's description carries what most calls need. Craft and reference material that few calls need (how to write a brief, which kind to pick, a condition grammar) goes in a guide file under the capability's `guides/` folder, which the agent loads with `guide` when the description tells it to. A guide is text, not code, so it can disagree with what the binary accepts; that is accepted, and where the binary has a list to compare against, a unit test holds the built-in guide to it, as `harness::when::tests::the_conditions_guide_names_every_key_the_evaluator_reads` does for the `when` keys.

## The serve loop

`crates/rimz/src/mcp/server.rs::serve` reads newline-delimited JSON-RPC from stdin on the main thread and answers every request inline except a `tools/call` that runs a one-shot, which runs on a thread of its own so calls overlap. Stdout carries protocol lines only, each written whole under the stdout lock.

Calls in flight sit in a map keyed by a sequence number, each with the request id, the `Child` once it has spawned, and a cancelled flag. The reading thread lists a call before it starts the call's thread, so a `notifications/cancelled` read after the call, or the server's end, always finds it: a call cancelled before its spawn kills its one-shot as soon as the spawn returns (`Calls::attach`), and a closed map lists no new call, so nothing spawns once the server is ending. The worker reads the child's stdout to its end (stderr on a side thread, a `notes_add` body written on another), then removes its entry and reaps the child. The result's text is stdout, then a `stderr:` line and stderr when the child wrote any (`crates/rimz/src/mcp/server.rs::result_text`), with `exit code N` appended on a failure, since providers join several content items without a boundary the model can see. A listed child is never reaped, so its pid cannot be reused while `notifications/cancelled` or the server's end may still kill it. A call whose entry was cancelled or killed by the server's end gets no reply.

stdin's end, SIGINT, and SIGTERM close the map, which kills every listed one-shot, and the server exits 0.

Under `--parent-env`, which Codex's registration passes, `serve` reads the parent's environment once at start (`crate::proc::environ` on the parent pid, Linux and macOS) and keeps each variable the server's own environment lacks; every one-shot gets those beneath its inherited environment. Codex starts a server with only the names its `env_vars` lists, and `crates/rimz/src/harness/launch.rs::spawn_env_names` collects them before the login shell's startup files run, so the parent's environment is where the rest live. A failed read logs one warning and adds nothing (`crates/rimz/src/mcp/server.rs::inherited_from`). A provider ends a server by signalling its process group; a watcher that `rimz wait` detached leads its own group and survives (`mcp_server::a_wait_armed_through_the_server_fires_after_its_group_is_terminated`).

Under `--launch-env`, which the rimz plugin's Antigravity entry passes, the CLI reads the selection with `crates/rimz/src/mcp/launch_env.rs::read` before it serves: `RIMZ_MCP_SERVE` becomes the `--only` and mark arguments, and `RIMZ_MCP_CWD` the `cwd` that `serve` keeps in `Calls`, where `run_one_shot` runs every one-shot, joining a call's relative `cwd` onto it. agy starts one fixed server for every session of the account, with the plugin directory as its working directory, so the launch's own directory reaches the server only through this variable. `crates/rimz/src/harness/launch_reminders.rs::LaunchReminders::mcp_launch_env` renders both values from the same served set and marks the launch plan computes, and `crates/rimz/src/harness/launch.rs` sets them on a launch whose adapter answers `LaunchCapability::serves_mcp_from_launch_env` and removes them from every other, so a session RimZ did not launch, or a child it spawns (the Antigravity quota read removes both), serves nothing.

The Codex app-server transport in `crates/rimz/src/agents/adapters/codex/app_server/transport.rs` frames the same protocol, but it sits in `agents`, a later layer than `mcp` in `refactor-target.toml`, and keeps responses only, so the server writes its own few lines of framing.
