# The MCP server

`rimz mcp serve` gives a Claude, Codex, Antigravity, OpenCode, or Pi agent RimZ's own commands as MCP tools. Its user-facing contract (the tools, their arguments, the protocol methods) is the [`rimz mcp` reference](../reference/cli/mcp.md). This page covers how it is built and what it must keep true.

## Calls run in the server's process

The server runs each tool call in its own process, on a thread of the call's own. `crates/rimz/src/mcp/` speaks the protocol and holds the catalog and the wording, and it reaches RimZ code only through the `crates/rimz/src/mcp/runner.rs::Runner` it is handed. `crates/rimz/src/cli/mcp.rs::run` hands it `crates/rimz/src/mcp_tools/mod.rs::Tools`, which has one function per tool: each calls the library function the tool's command calls and answers with the value that function returns. So a tool does what its command does, with no process started per call, and its answer is that value rather than the command's printed text. A command's handler can do part of the job around that library call (rewriting `@me` to the caller, filtering the agents a miss lists to the caller's channel, recording a bounced send), so a new tool's runner is written from a read of the handler end to end, and each such step lands in the runner or moves into the library.

`guide` is the one tool the server answers itself, from the wording it read at its start (below), so it opens no room.

`cargo xtask invariants` holds that boundary with a textual guard (`ensure_mcp_calls_run_in_process` in `xtask/src/invariants.rs`). Over `crates/rimz/src/mcp/` and `crates/rimz/src/cli/mcp.rs`, it refuses a store, config, or room reach, which only the runner may make. Over `crates/rimz/src/mcp_tools/`, it refuses a stdout write, since stdout is the protocol channel, and an exit or abort, since one call must not end the server that answers the others. Over both trees it refuses starting a process, so no call becomes a one-shot again; it admits by name the two restarts of the server itself, `crates/rimz/src/mcp/server.rs::Server::replace` and `crates/rimz/src/mcp_tools/mod.rs::restore_parent_env`. The process stays small: an idle server holds the parked wrapper's private-memory budget of 4 MiB outside huge pages and the relocated image (`mcp_server::an_idle_server_stays_inside_its_memory_budget` in the integration suite; [the figures](./performance.md)).

## The catalog

`crates/rimz/src/mcp/catalog.rs::TOOLS` is the one table of tools. Each `Tool` carries its capability (none for `guide`, which `crates/rimz/src/mcp/catalog.rs::tools_for` adds beside any served capability that has a guide, nor for `tasks`, `join`, and `stop`, which it adds beside any served capability that starts things, `crates/rimz/src/mcp/catalog.rs::Capability::starts_things`: `rimz-wait`, `rimz-subagents`, `rimz-agents`, `rimz-teams`, `rimz-workflow`, and `rimz-loop`), its `crates/rimz/src/mcp/catalog.rs::Purpose`, the command words it stands for (a tool of no capability declares its commands outright, since `stop` stands for one command per kind), its argument schema, the schema of the data it answers with (`crates/rimz/src/mcp/catalog.rs::Tool::output_schema`, listed as `outputSchema`; none for `lsp`, `blackboard_record`, and `guide`, which answer text), and the function that turns arguments into a `crates/rimz/src/mcp/catalog.rs::Call`, the typed request the runner carries out. Everything that lists tools or capabilities reads it: `tools/list` and `rimz mcp tools`, which share one result through `crates/rimz/src/mcp/catalog.rs::tools_list` (the server passes it each capability's `crates/rimz/src/mcp/catalog.rs::LoadMode` from `--always` and `--deferred`, and the command passes none), `rimz agents explain --mcps`, which prints `crates/rimz/src/mcp/catalog.rs::render_listing` over that same result so what it prints is what is served, `--only` parsing through `crates/rimz/src/mcp/catalog.rs::Capability`, `crates/rimz/src/mcp/catalog.rs::serve_args` for the arguments that start a server with chosen capabilities, the reference page's table (`mcp::catalog::tests::the_reference_table_lists_every_tool_under_its_capability`), and the routine-command check (`agents::conformance::every_mcp_tool_command_is_a_routine_command`), which keeps every command a tool stands for under an entry of `ROUTINE_RIMZ_PREFIXES`, so a tool does nothing an agent may not do unasked. There are two exceptions, both over a booking, and neither declares a loop command: a `stop` of a schedule removes the booking, and `schedule` makes one, which `rimz loop add` does only with a permission prompt. `rimz loop add` stays out of the prefixes because a prefix would grant its every flag (a shell task, `--root` of another project, `--project`), and the tool offers only an agent, team, or workflow target in the caller's room, under a name the caller holds. The reference page names both as running unasked.

Each tool's arguments are a serde struct with `deny_unknown_fields`, and its schema is derived from that struct with schemars, inlined into one object with `null` dropped from optional fields' types and enums. Deserializing the call's arguments is the shape check. `wait` takes one required `trigger` enum and one required string `value`, so a call without a trigger, which `rimz wait` bare would read as a listing that exits 0, fails the shape check, and two triggers cannot be sent. `schedule` takes the same flat shape for its trigger (`name`, required `trigger` enum, required `value`, optional `match`, `for`, `repeat`, top-level `worktree`, `overlap`, `max_strikes`) plus required `tool` (`agent`, `team`, or `workflow`) and an open `arguments` object: `crates/rimz/src/mcp/catalog.rs::parse_schedule` checks the schedule's trigger-option and worktree rules, refuses `arguments.worktree` (naming top-level `worktree`), merges top-level `worktree` into `arguments`, runs the named tool's own `ToolArgs` parser and `refusal` (wrapping carried errors so they point at `arguments` without listing `worktree` among expected keys or pointing at `arguments.worktree`), and then applies the refusals particular to a fire (workflow `input` and `detach`, `from_pr` on a repeating `team`, `#lane` on a team name, NUL in any string reaching the stored row, and values a fire's child would parse as a flag or a `rimz agents` verb); at booking time, `crates/rimz/src/mcp_tools/schedule.rs::launch` resolves an `agent` target through `crates/rimz/src/launcher/resolve.rs::resolve_finalized_layout` and refuses `from_pr` on a repeating booking whose target resolves to a team seat. A struct's `ToolArgs::refusal` adds a refusal where the schema cannot say what the call needs, holding the rules the command's flags hold in clap: a `self_tune` value with no setting, a blank `self_molt` prompt, a `notes` with both a body and a file, a meta key containing `=` (a note's meta line splits at the first one), a blank `subagent` profile or prompt, a blank `agent` or `team` name or prompt, two places on `agent`, `fresh` without `worktree`, anything but exactly one place on `team`, a `workflow` name that is a path or a blank `worktree`, a blank `message` receiver or text, a blank `blackboard_flip` stage or note or `blackboard_record` text, and for `lsp` a target, `hints` only with `fix`, a `limit` of at least 1 and not with `all`, and each field only on the verbs whose command takes its flag. A call refused there answers `invalid arguments: ...` and runs nothing. A value the command parses in clap, the runner parses with the same library function (`crates/rimz/src/utils/time.rs::parse_compact_duration` for a duration, `crates/rimz/src/harness/stop_booking.rs::parse_idle_rest` for `when_idle`, `crates/rimz/src/harness/schedule/arm.rs::task_label` for a `wait` label, `crates/rimz/src/harness/workflow/spec.rs::parse_when` for a `workflow` deadline), and the rules the library functions hold answer as that function's failure, so the tool cannot drift from the CLI.

RimZ's own skills (`rimz-*`) ship in the external `rimio-ai/rimz-skills` pack and are found on disk (`crates/rimz/src/agents/skills.rs::enumerate`, `crates/rimz/src/agents/skills.rs::rimz_skills` for launch capability reach, and `crates/rimz/src/agents/skills.rs::available_skills` for `rimz agents validate`); `Capability::ALL` lists only the capabilities with MCP tools, and no code lists the skills-only names; the ones production code names are in `crates/rimz/src/config/definitions/agent.rs::SeatEdits::edit`, which adds `rimz-reflect` to the nonempty authored skills list of every seat on a team that runs the shipped reflect consensus, a `capabilities` seat's included, and grants `rimz-message` and `rimz-blackboard`, for the built-in consensus and the Board writes fragment after it, to every Markdown team seat: each to `capabilities` whenever it lists neither that name nor `rimz` (even beside `skills: []`), else to `mcps` whenever set without that name, `rimz`, or `*`, and `rimz-message` as an optional entry in `skills` (an empty list included) marked `seat_consensus_skill` without a load-time disk lookup; `crates/rimz/src/harness/launch.rs::ExecRequest::settle_seat_skills` settles that entry at launch against the launch's kind, effective environment (login plus trusted project `[[agents]]` env, with named-login overrides winning), and skill inventory, dropping it silently when missing, unreadable, conflicting, or user-only so a seat-added `rimz-message` never refuses load or launch.

Every direct tool's argument reaches its library function as a value, never as argv, so an agent-supplied string that starts with `-` is data: a note titled `--force`, an LSP target `--help`. `schedule` is the one exception: its booking stores the fire's launch tail as argv on the task row, so `crates/rimz/src/mcp/catalog.rs::parse_schedule` refuses NUL and values a fire would read as a flag or a verb, and `crates/rimz/src/mcp_tools/schedule.rs` stores option values in `--flag=value` form.

## Starting things

A tool that starts something (`wait`, `subagent`, `agent`, `team`, `workflow`) follows one pattern, and a new start copies it.

- **The caller is the starter.** The tool opens the room of the call's directory and resolves the caller through `crates/rimz/src/launcher/context.rs::resolve_caller`, the source the command reads: the agent identity in the environment the server inherited, else process ancestry. The library function then records that caller as the thing's starter, the way the command does: a wait as the agent that armed it, a subagent as the launch its `parent_agent_id` names, an agent or a team's seats through the `launched_by` the layout plan writes on every cell, a workflow run as the agent its `starter` names. `crates/rimz/src/mcp_tools/owned.rs` walks that starter chain back to the caller, so `tasks`, `join`, and `stop` act on the thing with no record of the tool's own. A caller RimZ cannot identify is a failure, never a start owned by nobody, and `workflow` also refuses where the run would record no agent as its starter (inside an inline run).
- **Directories come from the call and the caller's record.** The server's process directory is the plugin directory on Antigravity, so it must not pick the room or the child's directory. `subagent` hands `crates/rimz/src/launcher/supervised.rs::launch_background` the room's project root as `SupervisedContext.root`, which the launcher's workspace resolve and room check rank above the directory they start from, and an explicit `cwd` as an absolute path resolved against the server's start directory. A call without `cwd` leaves the child's directory to the launch, as the command does: `crates/rimz/src/launcher/checkout.rs::anchor_caller_workspace` moves it to the caller's recorded checkout, and a caller with no recorded checkout gets the room root, which the root override makes the resolved worktree root whatever the process directory is (`mcp_server::a_subagent_call_launches_a_child_of_the_caller_from_outside_the_room`). `agent` and `team` hand `crates/rimz/src/launcher/layout_launch.rs::LayoutRoom::enter` the same root as `LayoutEntry.root`, and `agent` passes an explicit `cwd` as the same absolute path (`mcp_server::an_agent_call_opens_a_peer_of_the_caller_from_outside_the_room`). Both set `LayoutEntry.caller_repo`, so a caller with a recorded checkout has its workspace moved there by `crates/rimz/src/workspace.rs::ResolvedWorkspace::at_launch_dir`: the room stays the root's, and the repository a worktree is created in is the checkout's, as for `rimz agents` run from the caller's pane with no `--root`. A caller whose checkout lies in another repository gets the tool's cross-repository refusal (`crates/rimz/src/mcp_tools/notices.rs::CollectedNotices`), and no worktree is created (`mcp_server::a_caller_in_another_repository_gets_the_cross_repository_refusal`). A caller with no recorded checkout keeps the room root. The command leaves the field unset, so its `--root` names the room and the repository both.
- **The start goes through the command's own launch.** `launch_background` is the one background supervised launch: prepare, open the pane, and take the launched run, for `rimz subagents` and `rimz agents -p --bg` (through `crates/rimz/src/cli/supervised/run.rs::run_supervised`) and for the tool, whose `Interaction` keeps the refusals of `crates/rimz/src/launcher/mod.rs::Unattended`, so no prompt is asked, and collects each notice's text from `crates/rimz/src/launcher/mod.rs::Notice::line`, the function the CLI prints from. A subagent request is built by `crates/rimz/src/harness/run.rs::SupervisedRunRequest::subagent` on both paths. `agent` and `team` go through the commands' layout launch, `LayoutRoom::enter` then `crates/rimz/src/launcher/layout_launch.rs::launch_layout`, as `--bg --new-tab` reporting to the caller, under the same interaction (`crates/rimz/src/mcp_tools/notices.rs::CollectedNotices`). Before it, `crates/rimz/src/mcp_tools/layout.rs` refuses a spec of the other tool's shape: `agent` a team, a layout of several cells, or a command cell, and `team` anything but a configured team. `workflow` and `rimz workflow run` share `crates/rimz/src/launcher/workflow_start.rs::start`, every refusal of the start up to the created run. The tool starts a deployed workflow by name only and answers once the run exists, without the command's first-pass wait, so an early failure reads through `tasks` and `join`.
- **The answer is the id and how the result comes.** A start answers `crates/rimz/src/mcp_tools/start.rs::Start::running`: the `<kind>:<name>` id, `running`, the `stop` call that ends it, a `report` sentence, and `warnings`, an optional list of the notices the command would print, left out when empty and declared optional in the one start schema. A refusal (a budget, a declined launch, a subagent caller) is a `Failure`, and nothing starts. A failed start carries the notices collected before the failure in the same optional `warnings` list. A layout launch that lands on a live cohort opened nothing the caller owns, so it is a `Failure`; when its brief went to that cohort's leader (`crates/rimz/src/launcher/mod.rs::LaunchOutcome`, `prompt_delivered`) the failure says so and that the brief must not be sent again. `report` says no report comes when the launch opened no reporting run, and names `join` as the way to the answer.
- **The result reaches the caller by the thing's own report.** The server takes no part once the start answers: a wait's watcher sends its message, a subagent's own wrapper sends the `SUBAGENT_REPORT` digest to its parent ([subagents](./harness/subagents.md#the-fleet-report)), an agent's peer run sends `AGENT_REPORT`, a team's Done flip sends `TEAM_REPORT`, and a workflow run's engine sends its `WORKFLOW_REPORT` to an agent starter unless the run is detached, so a server that exits or restarts loses nothing.

## The wording

The agent-facing text is Markdown under `crates/rimz/src/mcp/tools/`, compiled in by `crates/rimz/src/mcp/wording.rs`: the shared `instructions.md`, `guide.md`, and per capability a one-line `instructions.md`, one file per tool, and a `guides/` folder. A file's identity is its path under that folder, the same path a user's replacement takes under `mcps/` in the RimZ home ([replace the wording](../reference/cli/mcp.md#replace-the-wording)). The skills of the same names keep their own copy in the skills pack for agents without the tools. `crates/rimz/src/mcp/wording.rs::Wording::read` resolves every file once, and its four readers all take the result: the server at its start, the launch plan (`crates/rimz/src/harness/launch_plan.rs::compile`, which turns each warning for the served capabilities into a `LaunchPlanWarning`, so it reaches the pane, the agent's record, and `rimz agents explain`), `rimz agents explain --mcps`, and `rimz mcp tools`. The server's own warnings go only to its stderr, which no user sees, so the launch is where a bad file is reported. The server resolves the home from its own `RIMZ_HOME` and `HOME`, each filled from the parent's environment under `--parent-env` (below), since Codex starts it without `RIMZ_HOME` unless `env_vars` names it.

A launch's instructions are `crates/rimz/src/mcp/wording.rs::Wording::instructions` of the capabilities it serves: a first line that introduces the served tools by the phrases of their `Purpose`s without naming each tool (`crates/rimz/src/mcp/wording.rs::first_line`), then each capability's sentence on a line of its own, in capability order, then a one-line sentence stating what every start returns and naming `tasks`, `join`, and `stop` when any served capability `starts_things`, then one naming `guide` when any served capability has guides, then the shared text. No file replaces the first line or the two shared-tool sentences, so their lengths depend only on the catalog. The providers bound that text: Claude Code cuts the instructions and each description at 4,096 characters, Codex shows a deferred tool only the instructions' first line, which RimZ holds to 250 characters (the smaller of the two figures Codex's docs give, neither tested), and Codex compacts an input schema over 5,000 bytes and may replace a `oneOf` or `anyOf` node with `{}`. `crates/rimz/src/mcp/wording.rs::Wording::breaches` is the one check of the text limits: `mcp::catalog::tests::the_text_fits_what_providers_keep` holds the built-in text to it, the first line and shared-tool sentences included, and holds every tool's input schema under 5,000 bytes, and `Wording::read` holds each replacement to the same rules, checking the whole instructions with every capability so a file's verdict does not depend on the launch. A replacement that fails is reported and its built-in text served, so no file switches a tool off. Property descriptions stay short and in Rust, as doc comments the schema is derived from (`crates/rimz/src/mcp/catalog.rs::Tool::argument_text_len` sums every `"description"` string in the input schema, nested ones included), and an enum's variants carry no doc comments, which would make schemars render a `oneOf`.

### Where long material goes

A tool's description carries what most calls need. Craft and reference material that few calls need (how to write a brief, which kind to pick, rare traps, a condition grammar) goes in a guide file under the capability's `guides/` folder, which the agent loads with `guide` when the description tells it to. A guide is text, not code, so it can disagree with what the binary accepts; that is accepted, and where the binary has a list to compare against, a unit test holds the built-in guide to it, as `harness::when::tests::the_conditions_guide_names_every_key_the_evaluator_reads` does for the `when` keys.

## The serve loop

`crates/rimz/src/mcp/server.rs::serve` reads newline-delimited JSON-RPC from stdin on the main thread and answers every request inline except a `tools/call` of a tool other than `guide`, which runs on a thread of its own so calls overlap and a later one may answer first. Before it reads, `serve` copies stdout to a private descriptor that a child does not inherit and points descriptor 1 at stderr (`crates/rimz/src/mcp/server.rs::take_stdout`): the protocol goes out on the copy, each line written whole under one lock, and a stray write on a tool's path lands in the server's stderr, not in the protocol (`mcp::server::tests::a_stray_stdout_write_lands_on_stderr_not_the_protocol`).

The server lives for the agent's session, where a command's process ends with the job. A process-wide memo outlives the call: a tool that writes what one caches (the loop config's `LOOP_MEMO`, the machine config's `LOAD_MEMO`) invalidates it, as every write of a task store does through `crates/rimz/src/config.rs::forget_loop_memos`, and a claim stamped with this process's pid reads as live until the server exits.

Each answer is a `crates/rimz/src/mcp/runner.rs::Answer`, and `crates/rimz/src/mcp/server.rs::tool_result` makes it a result. Data goes out as `structuredContent`, an object that fits the tool's `outputSchema`, with the same JSON as its one text item, for a client that reads only text. Text (`lsp`, `blackboard_record`, `guide`) goes out as the one text item. A failure is a result with `isError` set, whose text item is the JSON object `{"error": ..., "hint": ...}` (`hint` only where the code knows the fix), carried also as `structuredContent`. A failure is a call that could not do its job: invalid arguments, no room at the call's directory, an error from the library function. A verdict is data, so an `lsp check` that finds problems or a query with no result answers as a success.

A call runs inside `crates/rimz/src/mcp/server.rs::run_isolated`, so a panic answers that call's failure and leaves the server and every other call running. The runner reads the agent's identity, the room pin, and the RimZ home once at its start; each call opens the store and config it needs and drops them when it answers. `lsp` and `wait` take a `cwd`, which the runner resolves against the server's start directory when it is relative, and the call acts on that directory alone; a call without one acts on the start directory. `subagent`, `agent`, and an `agent` `schedule` always open the start directory's room: their `cwd` (`arguments.cwd` on `schedule`), resolved the same way, is the launched agent's working directory (translated through `crates/rimz/src/launcher/checkout.rs::resolve_launch_cwd` and stored as the absolute host path on the task row for `schedule` so each fire runs where the call would have), and without one `subagent` starts in the caller's recorded checkout while `schedule` runs at the project root.

Calls in flight sit in a map keyed by a sequence number, each with the request id and a cancelled flag. The reading thread lists a call before it starts the call's thread, so a `notifications/cancelled` read after the call, or the server's end, always finds it. A cancel withholds the reply: a thread cannot be stopped from outside, so the call's work runs to its end, and its answer is dropped (`mcp_server::a_cancelled_call_gets_no_reply_and_the_server_keeps_answering`). The runner is handed a closure that reads the flag (`crates/rimz/src/mcp/runner.rs::Runner::run`), and `join`, the one call that waits, checks it each poll, so a cancelled join frees its thread within half a second and holds no lock across a sleep. A call that finishes after the server's end gets no reply either.

stdin's end, SIGINT, and SIGTERM close the map, and the server exits 0.

A server whose environment pins a room follows that room's build, as the room's other long-lived RimZ processes do. `crates/rimz/src/mcp_tools/mod.rs::Tools` holds a `crates/rimz/src/reload.rs::RoomBuildFollower` for the pinned room, and the read loop asks it through `crates/rimz/src/mcp/runner.rs::Runner::poll_build` whenever its next read is due. A server with no pin does not follow, and one started on another binary than the room records stays on it, since the follower reports only a move after its start. A reported move waits for a quiet point: no call listed (a call stays listed until its reply is written or withheld) and no byte read from stdin left unhandled, which is why the loop reads stdin unbuffered into a buffer of its own and polls it with the follower's next read as its timeout. There the loop reads the build again (`Runner::recheck_build`) and, while it still differs from its own, points descriptor 1 back at the protocol and execs it with the same arguments (`crates/rimz/src/mcp/server.rs::Server::replace`), keeping the pid and both pipes. A failed exec logs a warning, and the server serves on. The new image knows it follows an earlier one when `RIMZ_MCP_FOLLOWED` holds its own pid. It then reaps the children the earlier image left, a `wait` watcher among them, whose handles the exec dropped (`crates/rimz/src/child_process.rs::reap_inherited_children`), so a watcher that ends later does not stay a zombie for the server's life, and it sends `notifications/tools/list_changed` as its first line, which `initialize` declares, so a client reads the tool list again (`mcp_server::a_server_follows_its_rooms_build_in_place_and_announces_its_tools`, and `mcp_server::a_server_swaps_builds_only_when_quiet_and_loses_no_request` for the quiet point). Between `rimz update` and the quiet point the old build may write a store the new build has written, as any long-lived RimZ process may.

Under `--parent-env`, which Codex's registration passes, the server replaces itself once at start with its own binary under the parent's environment beneath its own: each variable its own environment lacks is read from the parent (`crate::proc::environ` on the parent pid, Linux and macOS), and `crates/rimz/src/mcp_tools/mod.rs::restore_parent_env` execs the same binary and arguments with them added. Codex starts a server with only the names its `env_vars` lists, and `crates/rimz/src/harness/launch.rs::spawn_env_names` collects them before the login shell's startup files run, so the parent's environment is where the rest live. A failed read or exec logs one warning, and the server runs on its own environment. A provider ends a server by signalling its process group; a watcher that `wait` detached leads its own group and survives (`mcp_server::a_wait_armed_through_the_server_fires_after_its_group_is_terminated`).

Under `--launch-env`, which the rimz plugin's Antigravity entry and the Pi extension's registration pass, the CLI reads the selection with `crates/rimz/src/mcp/launch_env.rs::read` before it serves: `RIMZ_MCP_SERVE` becomes the `--only` and mark arguments, and `RIMZ_MCP_CWD` the start directory of the runner's `crates/rimz/src/mcp_tools/mod.rs::Tools`, where every call runs, its relative `cwd` joined onto it (`Tools::dir`). agy starts one fixed server for every session of the account, with the plugin directory as its working directory, so the launch's own directory reaches the server only through this variable. `crates/rimz/src/harness/launch_reminders.rs::LaunchReminders::mcp_launch_env` renders both values from the same served set and marks the launch plan computes, and `crates/rimz/src/harness/launch.rs` sets them on a launch whose adapter answers `LaunchCapability::serves_mcp_from_launch_env` and removes them from every other, so a session RimZ did not launch, or a child it spawns (the Antigravity quota read removes both), serves nothing. The same launch sets or clears each variable the adapter's `LaunchCapability::mcp_launch_env` names beside them (Pi's exposure fields, [adapter_pi.md](./agents/adapter_pi.md#rimzs-mcp-server)).

The Codex app-server transport in `crates/rimz/src/agents/adapters/codex/app_server/transport.rs` frames the same protocol, but it sits in `agents`, a later layer than `mcp` in `refactor-target.toml`, and keeps responses only, so the server writes its own few lines of framing.
