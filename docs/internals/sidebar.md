# Sidebar

> See [DESIGN.md](../../DESIGN.md) for the commitments this doc operationalizes, and [the interface reference](../interface/sidebar.md) for what the sidebar looks like on screen — the cockpit, the cards, and the provider dashboard, frame by frame. This doc is the mechanics: how presence, attention, layout, and recovery are computed.

The sidebar is a UI client over the workspace ledger that owns no durable state. It reads through `rimz sidebar snapshot`, writes only its own liveness heartbeat in-process (`rimz::sidebar::write_heartbeat`, a runtime-file write), and never imports a ledger-writer module.

One renderer paints every moment of a session — a bare shell, the first agent, a waiting prompt, a fleet across worktrees, detach and reattach. What changes between those moments is the snapshot, never the renderer. For the felt, phase-by-phase walk-through, see [the experience guide](../guide/experience.md).

## The view-model and its renderers

**The snapshot is the shared view-model, and every decision is made once, here.** The `rimz sidebar snapshot` JSON carries the worktree-grouped row roster (every live pane as a row, agents enriched from the ledger), the attention items, per-agent status and capability, the ranking keys, and timestamps. A renderer is a *projection*: it maps those semantics to glyphs and paints them. It never re-derives which worktree a row belongs to, how rows rank, or which pane runs an agent.

The snapshot command runs in the `rimz` binary, which owns mux access, so it enumerates the session's panes and folds them into the roster before serializing. Every renderer is then a pure JSON consumer — pane presence reaches the screen through the snapshot, never through a mux call of the renderer's own. (The one exception is geometry-only: the native renderer may list panes on resize to count its own siblings for [self-close](#self-close); it never updates the rendered snapshot.) Pane width is the launch path's concern — every sidebar pane is born at the launch's width verdict, `min(30%, max_cols)` resolved once against the launching terminal ([multiplexers.md](./multiplexers.md)), so the renderer never resizes its own pane and a manual resize always sticks.

Two renderers project the same snapshot today, with a third planned:

- **Native pane (default).** The `rimz-sidebar` binary in an ordinary pane — identical on Zellij and tmux, across detach/reattach. The default and the cross-backend fallback.
- **CLI listings.** `rimz feed list` and friends — the same data as text.
- **Zellij plugin rail (planned).** A docked, persistent left rail for Zellij users who opt in. See [Zellij plugin rail](#zellij-plugin-rail-planned).

The per-renderer code is just painting, so visual parity is a maintained discipline rather than shared render code. The one convention they all share is the semantic→glyph mapping — the table drawn in full in [the interface legend](../interface/sidebar.md#reading-the-glyphs), with its design rationale in [DESIGN.md → Attention at a glance](../../DESIGN.md#attention-at-a-glance). The mechanic this doc owns: the glyph carries state by **shape** so it survives `NO_COLOR`, and color only reinforces it. Keep every renderer aligned to that table. Tones are themable data over that fixed grammar: the `[sidebar.theme]` palette overrides ([configuration.md](../reference/configuration.md#theme)) resolve producer-side and ride `snapshot.sidebar` like the provider brand styling, so every renderer of a workspace paints the same tones with no config read of its own.

## Presence model

**Row presence comes from the live pane list, not the ledger.** The snapshot enumerates the session's panes, reads each pane's foreground command and cwd, resolves the cwd to a worktree, and emits **one row per pane** — no pane id is ever shared by two rows. A pane running `zsh` is a dim [process row](#process-rows); a pane an agent stamped is that agent's row. The sidebar's own pane is excluded — it is chrome, not work.

**One pane, one row, bound by the stamped pane id.** A pane's foreground command cannot name the agent — Claude runs under `node`, and two same-kind agents in one worktree read identically. Binding is by identity instead: every `agent.lifecycle` event carries the mux pane id the hook ran inside (`TMUX_PANE` / `ZELLIJ_PANE_ID`), and the snapshot binds each live pane to the one agent that stamped that exact id. Command and cwd never bind a row — a shell the agent dropped back to, or a `git` it spawned, stays a process row. The agent's ledger identity (status, task, model, effort, context enrichments) then enriches that one row.

**The binding ladder.** Joining a session to its pane runs a short ladder, most-certain first:

1. **Stamped pane id (standalone).** Every `agent.lifecycle` event carries the mux pane id the hook read from its own env, so the live pane binds the one agent that stamped its exact id ([`agent_for_pane`](../../crates/rimz/src/ledger/snapshot/panes.rs)). Free and unambiguous; this is the path for every Claude session and every in-pane Codex.
2. **Exact-cwd fallback (lazy-registering agent).** A session of a [lazy-registering agent](./agent.md#the-instance-lifecycle) ([`registers_lazily`](../../crates/rimz/src/agents/descriptor.rs), Codex today) arrives unstamped (no pane id), so as a last resort it binds the live agent pane whose cwd equals its worktree *exactly* ([`lazy_agent_for_pane`](../../crates/rimz/src/ledger/snapshot/panes.rs)); two in one worktree resolve most-recently-active and the [reaper](./agent.md#liveness-and-presence) collapses the stale one. A session whose last activity predates the pane's process start is refused ([`pane_start_allows_bind`](../../crates/rimz/src/ledger/snapshot/panes.rs)) — the producer derives that start from `/proc` for a backend that reports none natively (Zellij: the agent CLI behind the pane's bound root process — the root itself or its single child when a shell hosts it, [`in_pane_agent_start_for_root`](../../crates/rimz/src/remote_control.rs) — re-derived each produce so a re-run in the same pane sheds the prior tenant's stamp; the earliest in-pane `codex` CLI in the cwd, [`in_pane_agent_start`](../../crates/rimz/src/remote_control.rs), covers warmup before the binding lands) and stamps it at pane-frame production, so the published frame carries it and the guard fires on both backends and in both read lanes, the produce fork and the consumer in-process fold — so a stale daemon-mode session never latches onto a freshly-started pane in the same cwd. The match is exact-worktree and lazy-agent-only — a Claude session is always stamped while live, so a missing pane means it is genuinely gone, never rescued.
3. **Idle synthesis / process row.** With no session bound, a wired pane of a lazy-registering agent renders a synthesized idle `○ <kind>` row until the first turn swaps in the real session ([`idle_agent_row`](../../crates/rimz/src/ledger/snapshot/panes.rs), gated by the agent being among the wired lazy kinds); an unwired one stays a process row.

**Why a daemon-routed session is unstamped.** Codex under remote control fires its hooks from the shared per-user app-server daemon, so the hook's env carries no `ZELLIJ_PANE_ID` and `RIMZ_AGENT_PID` records the daemon's pid, shared by every client (why the hook runs off the pane: [transcript.md → Appendix Codex](./transcript.md#appendix--codex)). The session id lives only inside the daemon's owned rollout and its socket traffic; it is in neither the client's environ, cmdline, nor open files, so a client-pid → session join is impossible by construction. Reading the client environ through the mux-reported `pane_pid` recovers only pane ↔ client-pid, never pane ↔ session. cwd is the one key both id spaces share, which is exactly why two clients in one cwd cannot be told apart.

**No live pane, no row.** An agent with no live pane — a subagent, a ghost a kill left in the rollup, a relaunch the [reaper](./agent.md#liveness-and-presence) hasn't collapsed — is data, not presence. It cannot resurrect a row or latch onto a stranger's pane (the Codex daemon bind above is the lone, same-worktree exception). So an exited agent never lingers: its pane closes (gone next snapshot) or reverts to a shell row. There is no `offline` status. A relaunch-in-place is the ghost-bind case: an older session that never fired an exit hook is kept off the fresh pane by ask-supersession ([`agent_hook_session_stale`](../../crates/rimz/src/ledger/snapshot/view.rs)) and collapsed by the reaper, so the new instance's own session binds the pane.

**Remote agents are not shown yet.** A *remote* agent runs only in the daemon with no local pane — `claude remote-control --spawn worktree`, or a Codex thread started from the web. Its session can still reach this workspace's rollup (the hook resolves the ledger from its worktree, and same-repo worktrees share one workspace id), so Rimz often holds its status and worktree, yet it renders nothing: presence is pane-anchored and there is no pane to bind. Showing remote agents needs a presence class that renders from the rollup alone and repurposes the jump — with no local pane to focus, the row's action would open the remote surface or attach the thread into a fresh pane. This is a known gap, unbuilt this round.

**Attention folds onto the agent's pane.** A pending agent ask belongs to the agent's pane, so the snapshot folds the session's single most-relevant pending ask onto that agent's row (`? waiting`, or a braille resolver spinner) rather than adding a second row — a session never stacks more than one row. It un-folds once the agent records activity past the ask, so an ask answered in the agent's own UI returns the row to `running` (see [agent.md → Liveness](./agent.md#liveness-and-presence)). If the agent's pane is absent the ask leaves the sidebar but stays in audit (`rimz feed list --audit`). A script's blocking `feed ask` has no agent pane to fold onto, so it keeps its own standalone row while the waiter is alive.

### Future — disambiguating daemon clients in one cwd

When two or more daemon-routed Codex clients share one worktree, exact-cwd cannot say which instance a new session belongs to. These paths are recorded for when parallel daemon sessions make it worth building; none is implemented:

- **(a) Focus at `SessionStart` — first choice.** The user focuses a pane and presses Enter to send the first prompt, so the pane focused at the instant the binding hook fires is the likely owner. Read the view's active pane already on `PaneRef` ([`is_focused`](../../crates/rimz/src/feed.rs)) at the binding event — or re-add a per-client focus probe (`zellij action list-clients` / `tmux list-clients`) if the per-view mark proves too coarse — and prefer it over a tie.
- **(b) Screen capture — fallback, last.** Dump each idle instance pane and detect which one shows the just-submitted prompt. Effective but invasive — it reads pane content Rimz otherwise treats as opaque ([resolvers own pane I/O](../../DESIGN.md)) — so it stays a last resort.
- **(c) Zellij plugin keypress events.** The planned plugin rail could subscribe to Zellij key events and learn which pane sent Enter at the `SessionStart` instant, binding by the pane id it already knows. Backend-specific (Zellij only), so it complements rather than replaces (a).

Instance liveness needs no new signal: the in-pane CLI is the pane's foreground process, so a daemon-routed *in-pane* session leaves the screen the moment its pane stops reading `codex`, exactly like a standalone one. Rollup hygiene is what the daemon's loaded-thread set governs — an unstamped session's recorded pid is the shared daemon, so process liveness can never reap it, yet a closed conversation lingers in the rollup and would bind its stale stats to a live pane by cwd. The producer reaps it: a daemon-mode session ([owner pid is a codex daemon](../../crates/rimz/src/remote_control.rs)) absent from the app-server's `thread/loaded/list` is dropped before the pane fold ([`drop_dead_daemon_sessions`](../../crates/rimz/src/ledger/snapshot/view.rs)), so it neither renders nor attaches stats. The reap is tri-state and fail-safe — an unreachable daemon or an untrusted list keeps every session, never a mass-reap. The loaded set holds every thread the daemon keeps in memory, a completed one included, so it is rollup hygiene rather than a fresh-pane signal: a relaunched `codex` in a reused cwd is kept off the prior, still-loaded session by the process-start guard above, not the reap.

### Honest reads across a mux hiccup

`list-panes` is a round-trip the mux occasionally answers with an empty body, or with a live pane missing its command or cwd. Three read-side guards keep a momentary glitch from reaching the screen as a lie:

- **Degraded reads carry pane fields forward.** Rather than relabel a known pane as an anonymous row that blinks out next tick, the snapshot backfills any dropped field (command, cwd, process-start) from the last good read of that *exact* pane id — so a reused id reports its own fresh fields. The repair is surgical, unbounded while the pane persists, and runs on both produce paths — the elected producer and a loser falling back to a local produce when the producer wedges — so a raced read renders no anonymous row regardless of which path served the frame.
- **A pane with no readable identity folds no row.** An unbound pane whose command is still unknown after carry-forward — mid-birth, or a first read that raced before any prior entry existed to draw on — renders nothing this frame rather than an anonymous `process` row under `external`; the next read names it. The guard covers only the unbound residue: an agent-stamped pane binds by pane id, not command, so it still renders its agent row, and the pane stays in the published pane list, so the sibling count ([self-close](#self-close)) and the selection baseline see it.
- **The renderer never paints a regression over a stable pane set.** If a transient race the carry-forward missed — a momentarily agentless rollup, a half-written frame — would demote an agent's stamped-pane row to a bare `process`, the renderer holds the last good frame rather than commit the regression, as long as the live pane set is unchanged. A count- and time-bounded escape hatch releases the hold so a *genuine* demotion still surfaces promptly. This is the read-side twin of the ledger's resumable rollup ([Runtime projection](./ledger.md#runtime-projection)): the persisted fold base keeps an agent from vanishing at the source, the gate keeps a one-frame slip from reaching the screen.

When pane discovery itself fails, the renderer keeps the last good snapshot and, once the failure persists, raises the sticky health alert rather than inventing an empty room (see [Reload recovery](#reload-recovery)).

## Ranking and grouping

### Worktree groups

A worktree is total isolation — only same-worktree agents collaborate — so each group is one bounded block under a bold-teal header (the spines and seal are drawn in [the interface reference](../interface/sidebar.md#worktree-groups-and-the-selection-lane)). Two rules the renderer enforces:

- **The header is a jump target** — clicking the name lands on the group's first row — and carries **no status tally**: the cockpit owns the fleet make-up, and each row carries its own glyph.
- **Git stats live on the header, not a row**, so shared-worktree changes never pretend to belong to one agent. The `+/-` churn is the worktree's total change against trunk — committed, staged, and unstaged — from `git diff --numstat <merge-base with trunk> --`, and the `⇡`/`⇣` commit delta is `git rev-list --count` over the same merge-base (`<base>..HEAD` ahead, `<base>..<trunk>` behind), so every number measures from the fork point. A fully-landed worktree — zero commits ahead *and* a zero diff — collapses the cluster to `≡ <trunk>`: nothing left to land, safe to remove. Behind deliberately sits outside that test — the trunk moving on makes a landed worktree no less removable — and the trunk worktree itself (live branch == trunk) never wears the marker, since "landed on itself" carries no information. Zero components drop; empty when no git read reached the group.
- **The trunk resolves per repo, preference first.** The ladder tries the per-machine `[sidebar] trunk` ([configuration.md](../reference/configuration.md#trunk-branch)) when it resolves in the repo, then `main` → `master` → the remote's advertised default; an option-shaped configured name (leading `-`) is never handed to git.

A pane's group is decided by membership in the project's worktrees: a cwd at or under the project root (including `<root>/.claude/worktrees/*`), or inside any checkout `git worktree list` reports (even one parked outside the root), belongs to that worktree. The snapshot enumerates the worktree roots (cached under `WORKTREE_ROOTS_TTL`, re-enumerated immediately on a session boundary) and the reducer runs a lexical containment test against the project root and each worktree root. A cwd that is neither — a home shell, `/tmp`, CI not tied to a worktree — folds into a catch-all that renders as a dim `┄ external ┄┄┄` divider, sorts last unless it holds a waiting/failed agent, and keeps an attention-only tally (`? n` / `! n`). When the git probe finds no worktrees the reducer falls back to the project-root prefix alone.

### Attention ranking and the per-worktree cap

**One principle: the most attention-hungry rises, and nothing else moves.** The status comparator is `status_rank` in [`snapshot/view.rs`](../../crates/rimz/src/ledger/snapshot/view.rs); the order it encodes:

- Within a worktree, rows sort by status bucket: `waiting` → `failed` → `success` → `running` → `idle`. A parked idle agent has no work in flight, so it settles to the very bottom — and a brand-new agent (always idle) therefore appends at the bottom of the calm region, never above finished or working agents.
- The attention buckets (`waiting`, `failed`) sort **oldest-first**: a blocked agent's `last_activity` is frozen, so the longest-overdue rises and `␣` always lands on the oldest blocked pane.
- The calm buckets and bare process rows hold a **stable spawn order** keyed on `pane_process_start` when the backend reports it, else the session's durable `registered_at` (Zellij reports no pane start) — both set-once and untouched by the activity heartbeat, so a working agent never jumps just because it finished a tool, a renamed session never reorders, and a new agent appends at the bottom of its bucket.
- Worktree groups sort by their most-urgent member, with every calm status collapsed to one tier — a calm group holds its place through members' success/running/idle churn, and only genuine attention reorders. Same-tier groups keep a stable order — project worktrees before the `external` catch-all, then the earliest member spawn key, then label.

**The cap protects the calm tail only.** Each worktree shows at most `WORKTREE_ROW_CAP` rows with a dim `+K more`. The cap truncates only calm rows — the bottom-ranked idle tail first; every `waiting`/`failed` agent is exempt and always shown, so the cap can never hide something that needs you.

## Composing the frame

The sidebar is **borderless** — it already lives inside a framed mux pane, so a second border would double-frame it and cost two columns. A title line, faint `─` hairline rules, and a one-cell left gutter (which doubles as the selection lane) carry the structure instead. The on-screen layout is drawn frame by frame in [the interface reference](../interface/sidebar.md); this section owns the invariants behind it.

Three structural rules the layout depends on:

- **Fixed height where it counts.** The repo dashboard (identity, the `◎`/`¤` summary with today's token breakdown, and the count-up spend) and the cockpit make-up reserve their rows whether or not the room has agents, so the body never shifts vertically as agents change *state*. The footer and health alert are bottom-pinned chrome, reserved before the body so they can never scroll off.
- **Three zones, two pinned.** The frame composes as a top-pinned cockpit, a scroll viewport over the worktree groups, and the bottom-pinned chrome (dashboard, ledger, footer, alert). The pinned zones reserve their rows first — bottom, then top — and the viewport takes the remainder, so the cards give way before either pinned zone is clipped. `UiState::scroll_offset` is resolved on every draw — clamped to the zone, then minimally auto-scrolled so the selected card (its group header and expanded subagent lines included, since they share the row's hit-test entry) sits fully in view, a card taller than the viewport pinning its first line to the top — and written back as a draw byproduct, like the hit-test map. A wheel tick pins a manual offset above the auto-follow — the browse pattern one layer down: the pin captures the selection it began over and ends the moment the selection genuinely changes, snapping the view back. Opening `?` jumps the viewport to the zone's tail, where the overlay renders, and the open overlay owns the viewport — auto-follow stays off while it is up, so selection churn beneath it never pulls the view away mid-read; closing it drops any wheel peek and snaps back to the selected card. When the cards overflow, each visible line can carry the `▐` thumb / `▕` track glyph in the right-margin column the content leaves free — part of the composed line, never a new one, and the column reserved in every mode, so the hit-test map stays 1:1 with the frame at every scroll position. Whether the bar paints is the `[sidebar] scrollbar` mode ([configuration.md](../reference/configuration.md#scrollbar)): `always` whenever overflowing, `never` not at all, and the default `auto` only while the viewport is moving — each draw folds the resolved offset into `UiState`'s scrollbar fade as a write-back byproduct, a change stamps the animation phase, and the bar shows through a ~1s settle window after the last move (the baseline lives in the fade rather than `scroll_offset` because a wheel tick mutates the offset before the draw). The fade is ORed into the serve loop's animation gate like the cockpit odometer, so the hide frame always repaints.
- **Counts span the cap, the summary spans the day.** The cockpit make-up buckets sum each group's `status_counts` — counting even agents the cap hides; every `running` agent tallies as working (the thinking sparkle is a per-row head, not a bucket). The summary's line 1 pairs today's facts — the `◎` sessions and the token breakdown read today's window of the JSONL `value_tally`, not the live session sum — and line 2 carries the `¤` live-agent head-count with the count-up spend.

There are no feed-group sections: "Recently answered" and "Recent activity" do not exist here. The sidebar shows only what needs a decision or an action; full history lives in `rimz feed list --audit`. With nothing waiting or failed, the attention line is omitted and a dim first-run hint points at the real next step, keyed on the snapshot's `agent_hooks_ready` flag (an unwired room reads `install hooks: rimz hooks install claude`, a wired room reads `run claude or codex`). The hint clears the instant the first agent or feed item appears, and steps aside under an active health alert — an empty body under a failed fetch is a missing snapshot, not an empty room.

### Agent rows

Each agent is a small stacked card — identity and capability, then the description, the context meter, and (deeper) the token and work stats. The card anatomy and meter grammar are drawn in [the interface reference → the card](../interface/sidebar.md#the-card); the invariants behind it:

- **Selection only appends, never reshapes.** Every line of the resting card renders identically whether selected or not; selection paints the bold `▌` spine over the gutter and *appends* the deeper lines, so the card never reflows on expand. The resting card is identity + description + the `▣` context meter + the `▤` context line; selecting any row appends its subagent list, so the deepest data is one keystroke away.
- **Capability is preferred, never synthesized.** Model display name and effort come from the session's rich [context](./agent.md#rich-context-agentcontext) when present, falling back to the coarse [transcript scalars](./transcript.md); a missing field means "the agent did not report it," never a zero. Model names drop a trailing window qualifier for the row (`Opus 4.8 (1M context)` → `Opus 4.8`); the window itself rides the identity line's dedicated token (`258k`, `1m`). The account-scoped budgets are **not** on the row — they live in the [provider dashboard](#provider-dashboard).
- **Line 1 carries no timestamp.** A blocked `?`/`!` heats with the age clock's quarter-hour ramp — yellow floor, amber past the half hour, red past the hour — its breath quickening on the same steps (slow swell, double-time at amber, a hard blink at red), and a working agent's animated head signals liveness, so a stale row escalates by color and cadence in place rather than by a clock; the one coarse last-activity age rides the context line, pinned right, only once it crosses a full minute, toned by the same age ramp in [the glyph legend](../interface/sidebar.md#reading-the-glyphs) — a delegating parent's age reads the freshest of its own and its children's activity (the [sub-agent fold](#sub-agent-lists)). Width tiers degrade line 1 — a narrow row keeps just the name, wider rows add the model, then effort and an inline todo — while the context meter keeps its label and value at every width.
- **Enrichments are display-only and privacy-gated**, and none drives attention or routing. Context severity is one four-tier ramp — calm blue → yellow → amber → red — taken as the worse of a fill-percentage band and an absolute-token band, each an inclusive lower bound configurable via `[sidebar.context]` ([configuration.md](../reference/configuration.md#context-meter)), so a large-window model calm by percentage still warms by sheer volume. The tier is classified once, in the domain ([`ContextSeverity::classify`](../../crates/rimz/src/feed.rs)) where the config folds onto the snapshot, and stamped on each row (`SidebarRow::context_severity`); the renderer only maps the verdict to a tone. The bar, the `▣` glyph, and the `▤` context-line head all wear that one severity; while the meter rests calm and the per-message breakdown is known, the bar splits into composition segments (cache writes, cache reads, fresh input) and the context line's markers wear the same segment colors — the line is the bar's legend — and once the meter warms the bar goes a single solid severity run. `NO_COLOR` suppresses color only; every bar's heavy/light and filled/hollow shape still carries the meter.

The rows read the fields on [`SidebarRow`](../../crates/rimz/src/ledger/snapshot/view.rs) plus the per-group `status_counts` and git fields (`diff_added`/`diff_removed`, `commits_ahead`/`commits_behind`, `trunk`); that struct is the field catalog. Three projection rules are not evident from it: the renderer prefers the rich `context` blob over the coarse `model`/`effort`/`context_pct` scalars (and falls back when it is absent); an unnamed session's line 2 falls `session name → task → prompt → em dash`, so it keeps a label once the turn ends; and the display preferences ride `SidebarSnapshot.sidebar`, filled by the CLI like `project_root`.

#### Future — agent signals

The stamped verdicts are hook-ready: `ContextSeverity` is classified once and rides each `SidebarRow`, so a future hook flow reads the same tier the sidebar paints. The path is hook-side emission → feed event → resolver: a producer-side detector (or a dedicated hook) emits an [`AgentSignal`](../../crates/rimz/src/feed.rs) — `ContextSeverity { from, to }` on a tier crossing, `Attention { status }` on entering an attention state — into the existing **feed**, the decision bus the resolver chain already drains ([resolvers.md](./resolvers.md)); an enrolled resolver matches the signal and acts (`rimz pane send /compact` at amber), exactly as the pane-send reference resolver acts on a recognised prompt today. Resolvers + the feed are the bus; the typed verdict and signal shape exist now, while emission and handling are deliberately unbuilt.

#### Sub-agent lists

The expanded card lists the subagents the agent spawned this turn — each leading with the agent-row head vocabulary (the thinking sparkle while the child's `phase` reads reasoning, the working fill while it acts, the static `✓`/`!` verdict once it finishes) plus its type and, when Claude's `subagentStatusLine` has reported it, the description of what the parent asked it to do, with the token spend `◇`, the child's model and reasoning effort, and elapsed work on a second indented line: the clock-fill glyph `◔`→`◉` over a fixed three-cell `m`/`h` label (`<1m` under a minute, never seconds), toned by the parent's age ramp, so the right-pinned clusters stack into one column across children. A subagent has no pane of its own, so it never renders as its own row ([Presence model](#presence-model)); instead the rollup carries each child's `parent_agent_id` and the snapshot nests it under its parent at projection time. The list orders by **creation time ascending** (`started_at`, undated children last, id tiebreak) — spawn order, stable across refreshes, where an activity-keyed sort reshuffled on every tick. The list is **expanded-only**, so selection still only appends and the card never reflows. Retention is **turn-scoped**: a still-running child is always shown, and a *finished* child holds its `✓`/`!` verdict on the list — however long ago it finished — clearing only when the parent starts its next turn (its work predates the parent's `turn_started_at`). A child whose parent row is absent is an orphan and never renders.

The description, token count, and start time are paneless enrichment a child cannot publish for itself: the feed harvests them from Claude's `subagentStatusLine` (Claude-only) into a per-child sidecar, and [`with_subagent_context`](../../crates/rimz/src/ledger/snapshot/view.rs) folds them onto the child's `AgentState` by `(kind, agent_id)` before projection — mirroring `with_agent_context`. The fold lands on the rollup, not the projected `SidebarSubAgent`, so it survives the group rebuild. Elapsed work is frozen at projection (`now − started` while running, `last_activity − started` once finished). The model, reasoning effort, and turn phase ride the other channel — the child's own lifecycle events, carried forward on its `AgentState` like the parent's — so they show wherever an event named them, sidecar or not (Claude reports a child's effort on its `SubagentStop`, so the effort token typically lands as the child finishes). A child with none of it — a Codex child, or a Claude child before its first render — degrades to the bare type line.

**Child activity counts as the parent's.** At the same projection chokepoint ([`fold_child_activity_onto_parents`](../../crates/rimz/src/ledger/snapshot/view.rs), after the nest, before the displayed-status projection) the freshest child `last_activity` advances the parent row's *displayed* clock — so the card's age stays honest while the children work, and the stall check reads the folded value (a parent whose child just finished never false-stalls). The fold is display-only and twice-guarded: the rollup keeps the parent's own clock (so [`agent_moved_past_ask`](../../crates/rimz/src/ledger/snapshot/view.rs) still recovers a settled ask and a blocked parent stays waiting), an attention row's frozen heat is never re-clocked, and a [turn-death marker](./agent.md#liveness-and-presence) always beats a still-ticking child.

### Process rows

A pane no agent has stamped renders a bare command row: a lead glyph then the program it runs (`zsh`, `vim`, `cargo`), the whole row one DIM weight step below the agent cards — rows sort agents-first, and that soft weight (a modifier, so it survives `NO_COLOR`) is what reads the worktree's command tail apart from the agents above it. The program is read past a `sudo` wrapper and through a `node`/`npx` launcher to the script it runs, so `sudo npm install -g @openai/codex` reads as an `npm` install (never a codex agent) while `node …/codex` reads as the pre-enrichment codex host. The lead reads like an agent card's: a hollow `○` in the idle agent's quiet green for an idle pane — a shell, an editor, or the pre-enrichment agent host (`node`/`claude`/`codex`) — and the working braille spinner in the agents' clay for a pane doing genuine work like a build or a test, so live work reads at a glance. An **active** pane anchors its primary line on the shell that owns it (its root process, read from `/proc/<pane_pid>/comm`) so the line stays put as commands come and go, and carries the live command in full on a second line. At L2 (≥44 cols) width the row right-pins `C  n%  M  nG  ⇅  nM/s` on line 1 — CPU, RSS, and combined VFS I/O rate as one dim fixed-width grid, each figure right-aligned in its slot and a not-yet-sampled metric blank-filling it, so the cluster never wanders as values change — sampled by the producer from the shell's single foreground child (falling back to the shell pid) on its own [sampling cadence](#enrichment-cadences); rates blank until the second sample (two-sample rates need a prior reading), the whole cluster absent on non-Linux. Both reads key off the pane's root pid: tmux reports it natively (`#{pane_pid}`), and Zellij reports none, so the producer derives it from `/proc` ([`backfill_zellij_pane_pids`](../../crates/rimz/src/cli/sidebar.rs)) — every pane root is a direct child of the session's `zellij --server <socket>` process (socket named after the session), and Zellij reports a pane's foreground command as that process's cmdline, so a pidless pane matches the server forest's one process with that exact cmdline (the working directory breaks a tie between same-command candidates; a unique match binds without a cwd check, since an agent may chdir into its worktree) and walks up to the direct server child. An ambiguous pane — two idle shells in one cwd — abstains and shows no stats: no stats beats a stranger's stats, and an active pane's foreground cmdline is almost always unique. No capability line, no attention count; a process row never enters the cockpit tallies. It is still a jump target, and once an agent's hook stamps that pane id the same pane becomes that agent's row.

### Jump — the row is the link

You don't read where to go; you go. Selecting a row focuses that agent's pane via the `pane` ref on the snapshot — no mux pane number is ever printed. Both renderers share one key model:

- `↑/↓` select a row; `↵` jumps to the selected pane.
- The mouse wheel scrolls the card viewport without moving the selection ([Composing the frame](#composing-the-frame)); the next selection change snaps the view back to the selected card.
- `1`–`9` jump by the row's visible ordinal.
- `␣` jumps to the *next item that needs you* — the next `waiting`/`failed` row in ranking order — without first selecting it. The fleet-scale triage key, bound only inside the Rimz session so it never touches the user's global mux config.
- `←`/`→` cycle the [provider dashboard](#provider-dashboard)'s tab — a manual pick above the selection-derived default, no row or focus movement.
- `x` dismisses the sticky [health alert](#reload-recovery) once it has recovered; an active failure re-arms it.
- `r` reloads the tab: when a freshly-installed build is on disk it re-execs the renderer in place (the keypress scope of `rimz reload`); otherwise it forces an immediate refetch, so `r` always pulls live data and un-sticks a tab whose producer has stalled.
- `?` toggles a legend-and-keys overlay, so the glyph vocabulary is learnable in place.

The native renderer focuses the bound pane directly, in process (`rimz::mux::backend_for(..).focus_pane`) on a detached thread; a click anywhere in a row's multi-line block jumps via a hit-test line map the renderer emits in lockstep with the body. **The jump is one-way and moves no local state**: the focus command is all that crosses to the mux — both backends switch tab/window implicitly — and the highlight follows on a later fold, once the derived baseline reads the new focus back from the mux. **Every jump reconciles pane id *and* `pane_process_start`**, so a reused id never silently focuses a stranger — it self-corrects on the next snapshot rather than blocking the jump. The row routes you to the pane; the prompt and its approve/deny live in the agent's pane, where the full context is. A script's `feed ask` is the exception: it chose Rimz as its surface, so its declared options are answerable on the row.

#### How the highlight stays on the right pane

**Selection is derived state, scoped to the sidebar's own tab.** The baseline is the own view's **active working pane** — the non-sidebar sibling carrying the per-view `is_focused` mark ([multiplexers.md → Two kinds of focus](./multiplexers.md#two-kinds-of-focus)), filtered to a visible row — re-queried from the mux on every fold (`SidebarOwnView::active_pane_id` → `app::reconcile_selection`). Same-tab by construction, defined whether or not a client is viewing the tab, and one deterministic value per tab however many clients attach — which is the only shape a sidebar pane (shared content, one buffer for every viewer) can render. Selection cannot desynchronize, only lag a frame: an external tab switch or focus move lands on the next fold, and a `None` derivation (the sidebar itself focused, or a non-row active pane) *holds* the last baseline rather than blanking it. Selection is keyed by pane identity, not row position (`UiState::selected_pane`), so a status-churn reorder re-anchors the highlight to the same pane.

One transient local layer rides above the baseline:

- **Browse** (`↑`/`↓`) pins a pick *without* moving focus and may roam every visible row — another tab's included, so any card is one keystroke from expanding. It ends when the derived baseline genuinely changes from the value captured when browsing began; an inert (`None`-derivation) frame never ends it.

A jump (click / `↵` / digit / `␣`) moves no local state: it fires the one-way focus command and the highlight follows on a later fold, once the derived baseline reads the new focus — a deliberate trade of instant echo for one source of truth. Cross-tab, the destination tab's sidebar needs no signal at all: its own baseline derives the jumped pane from its view's `is_focused` mark — in the common one-working-pane tab it is already there — and the source tab reconverges on its next fold the same way. A jump mid-browse leaves the pick in place, so the highlight holds still until the baseline takes over on the same pane.

### Provider dashboard

The 5-hour and 7-day budgets are **account-scoped, not session-scoped** — every session of a provider shares one account's budget — so they lift off the rows into a pinned per-provider dashboard at the bottom, bracketed by hairline rules above the footer. With several accounts the dashboard is **tabbed**: its top hairline becomes a tab rail — the agent-kind labels set into the rule — over one block at a time, so the budgets read one account deep instead of stacking; a single account keeps its bare block under a plain rule, no rail. How each panel's account, plan, metered flag, and stable windows are sourced and aggregated is [account.md](./account.md) (which also owns the stable tab order and the cap); this section owns only the painting and the tab focus.

- **Tab focus is derived, with a manual layer.** The active tab follows the selected pane's provider — the selected row's agent kind, falling to the first tab for a process pane or an empty selection — so glancing at the dashboard reads the account behind the agent you're on. `←`/`→` (wrapping) or a click on a tab label pins a manual pick above that default; the pick ends exactly like a [browse](#how-the-highlight-stays-on-the-right-pane): when the selection-derived kind *genuinely* changes from the value captured at pick time (a process-row selection derives nothing and holds it), or when its panel leaves the dashboard. Each tab label — the kind slug, first-char-capitalized — wears its provider brand color; the active one paints as a chip (dark ink on its brand fill) notched into the rail between `┤ ├` caps, so the pick survives `NO_COLOR` by the cap shape. Every tab reserves its two cap cells — painted as rail fill when inactive — so a pick re-notches in place and never shifts a label. The rail names the account, so the tabbed block's header drops the product name and reads plan-first (`Claude Max · v2.1.158`), indented to the stats column directly over the `◎` line.
- **Mana bars and the shared grid.** Budget bars use a light segmented style (`▰` filled = remaining, `▱` track) and drain green → yellow → amber → red by remaining budget (amber is the clay tone the age and context ramps share); each window's label (`5h`/`7d`/`30d`) wears its bar's color. The label slot and the `↻ reset` column are fixed-width, so every provider bar shares one front and one end column and the dashboard reads as one aligned grid. A fully-spent window turns its whole track red rather than faint, and a spent longer window gates the shorter ones — an exhausted `7d` forces the `5h` row to the same red, no countdown. Below a narrow width the emblem drops and the bars run full-width.
- **The stats line speaks the ledger vocabulary.** Each block's first body line reads today's `◎` session count then the `◇ ↘ ↗ ◌` token breakdown — the fleet ledger's exact format, scoped to the provider, the `◍` cache-write figure omitted like the ledger rows' — with the spend pinned right.
- **Brand styling is config-driven**, resolved producer-side from `[sidebar.providers.<kind>]` over built-in defaults — see [configuration.md](../reference/configuration.md#provider-dashboard).
- **Remote control is a flag, not a row.** `claude remote-control` is host infrastructure, so the snapshot filters its pane out of the room and the Claude block pins a violet `⇅ rc` flag when `[remote_control] claude` is on. Codex has no host pane.
- **The fleet ledger seals the bottom.** Below the last account block (or, with no block, its own hairline) a two-row ledger pins above the footer — the trailing-week `W:` row over the trailing-month `M:` row — fed by `SidebarSnapshot::value_tally` (the [`SpendTally`](../../crates/rimz/src/agents/spending.rs) the spending enrichment computes). Each row reads `◎ sessions  ◇ total ↘ input ↗ output ◌ cache-read  $spend` behind a one-cell lead pad, every numeric field right-aligned into one shared grid so the `W:`/`M:` labels stack and each column lines up. The figures are **static** — the precise one-decimal token form, the exact record beside the cockpit's coarse live read; today's headline `$` lives in the cockpit and is the only count-up. The windows escalate `today → week → month`.
- **The cockpit spend counts up.** Today's fleet `$` (its own right-pinned line under the `◎`/`¤` summary) **climbs** on an increase — `UiState::tally` (`render/odometer.rs`) holds one eased roll, the producer-side fold seeds its target on every refresh, and the renderer reads the eased value at `animation_phase` with a brief brighten as it settles. The roll keeps the fast tick warm only while in flight (the serve loop ORs `TallyAnim::any_rolling` into its animation gate), so a settled figure costs nothing; a decrease (today's UTC-midnight reset) and the first paint snap, never roll — including when the decrease arrives via a stale step. The fleet figures step at most once per `SPENDING_TTL` (the [enrichment cadence](#enrichment-cadences)); the eased roll is what absorbs the coarser step. The figure is presentation only — the [`SpendTally`](../../crates/rimz/src/agents/spending.rs) is the truth, the roll a transient overlay toward it.

The tabs are the panel's only hit targets — a click on one switches the tab in place, never a jump; everything else in the dashboard stays inert in the hit-test map. The renderer emits the tab geometry in lockstep with the frame (`UiState::tab_hits`, the tab rail's twin of the row `line_map`), and the rail holds to one screen row — a tab that would overflow the panel width drops whole, label and hit together, so the map never desyncs however many kinds register.

## The runtime loop

### Launch model

`rimz`, `rimz start`, and cwd-based `rimz attach` ensure the workspace session exists, then launch one sidebar pane best-effort before entering or printing the attach command. Both backends run the same native renderer through `rimz sidebar serve`:

- **Zellij** is born from a layout — a left `rimz-sidebar` pane at the launch's width verdict plus a focused terminal — which doubles as the default tab template, so every tab is born with a sidebar. Rimz touches the layout only at creation; an existing session is a no-op.
- **tmux** splits a left sidebar into the initial window, and an `after-new-window` hook re-runs the same split so every later window is born with its own sidebar — the tab-template parity Zellij gets from its layout.

Launch is **idempotent by heartbeat**: before opening a pane Rimz scans `runtime/heartbeat/sidebar.*.json` and treats only readable, current-protocol, fresh files as live, so a crashed or upgraded sidebar does not suppress relaunch. A launch lock serializes the check-then-spawn so concurrent attaches to one session don't each spawn a daemon, and the sweep removes orphaned heartbeats and sockets a SIGKilled sidebar left behind.

`rimz reload` is **user-wide and cwd-independent** — it runs from anywhere, even outside a session. It enumerates every workspace under the state dir (`known_workspaces`) and, for each whose mux session is live, converges it to **one healthy sidebar per working view**: it re-execs onto the freshly-installed binary every live sidebar whose on-disk binary differs from the one it is running — a sidebar already on that build compares byte-identical and refetches in place instead, so an unchanged install never churns its pane — closes duplicate or unresponsive sidebar panes (any a fresh heartbeat does not claim by pane id, graced by two heartbeat windows for a just-added pane whose serve process is younger than its first heartbeat — so back-to-back reloads never churn what the previous run added), converges a kept sidebar that sits off the layout's dock — moved back to the left column and resized toward the layout width, renderer untouched — with a tolerant trigger (off the left column, or wider than both 45% of the tab and the `max_cols` cap) so a healthy layout-born width — including a cap-wide fixed birth on a narrow client — is never churned (tmux births every sidebar left at width synchronously, so convergence is Zellij-only repair), re-adds a sidebar to any working view left without one — discovering the mounted pane from the live pane list rather than trusting the spawn command's output, and undoing an add whose pane never mounts so a failed add leaks neither a stray pane nor a paneless renderer pair (Zellij's `new-pane` answers before the mount: [multiplexers.md → Zellij backend caveats](./multiplexers.md#zellij-backend-caveats)) — collapses an orphan sidebar-only view — a wedged renderer whose working siblings all closed but which never self-closed — by closing its sidebar pane, and reaps orphaned sidebar *processes* whose pane the mux no longer lists — all in place, never rebirthing the session, so the user's panes survive. The daemon view (`rimzd`, a sidebar beside the managed hosts) converges the same way — a missing sidebar is re-added beside its hosts — but is never collapsed: its hosts are managed, not work, so it can never read as a sidebar-only orphan. On Zellij the view classifies by its tab name plus each pane's spawn command (`terminal_command`), the two signals `list-panes` still reports after the Claude host re-execs. A workspace whose session has stopped has its stale heartbeat/socket files and leftover daemons swept instead. Each pass is best-effort and run-once; a view that fails to gain a sidebar is logged and left alone. On Zellij an add into a *detached* session is deferred rather than attempted — the detached screen thread drops the mount while the spawned renderer keeps running, so reload reports the deferral and the next reconcile against an attached client adds it; tmux mounts splits detached, so it never defers.

### State access

**Data access splits by role** (see [performance.md → Principles](./performance.md#principles)). One **producer** per workspace — the eldest live renderer (UUIDv7 ids sort by birth) — forks the one `list-panes` + git round-trip and publishes the coalesced pane list:

```text
rimz sidebar snapshot --workspace-id <id> --exclude-pane-id <own>
```

Every other per-tab renderer is a **consumer**: it reads that published frame **in process** (`read_published_snapshot`), folding only its own-pane exclusion — no subprocess, no `list-panes`/git, no ledger lock. The **rollup** is read separately and event-fresh from `latest.json` (`consumer_rollup`, the read-only twin of `Ledger::snapshot_cached`; both are lock-free) and folded over those panes.

This decoupling is the freshness fix: a `ledger_delta` repaints a status change or a new agent in an existing pane within one wakeup, independent of the slower `list-panes` cadence that governs only genuine pane open/close. A stalled producer can never freeze a tab, and recovery is the election's job, not the consumers': a dead or wedged elder's heartbeat ages out within one TTL, the next-eldest renderer becomes the producer on its next cycle, and every other consumer keeps folding the held pane frame with the event-fresh rollup — status stays live across the handoff, only pane presence ages by a few seconds. Because exactly one renderer produces at any moment, even a duplicate that slips the launch lock costs one cache read, not a second mux round-trip.

Each renderer refreshes its own heartbeat **in process** (`rimz::sidebar::write_heartbeat`, never a `rimz` fork per tick) and binds `sock/sidebar.<instance_id>.sock`; the heartbeat carries the workspace and session ids, the mux backend, the instance id, the protocol version, the wakeup socket path, the pane it paints (so `rimz reload` can tell a live sidebar from a duplicate or an unclaimed pane), and the last-seen timestamp.

Data fetch is **push-primary**: a `ledger_delta` wakeup (any ledger write, plus the statusline context-sidecar push) drives the refetch, and a slow backstop closes missed wakeups and catches pane/git drift the mux never signals. The render layer is a fixed-timestep loop on its own clock: a fold marks the frame dirty and the loop paints at most once per `ANIMATION_FRAME` boundary, coalescing every change that landed mid-frame into one paint and never forking a fetch, so the spin stays smooth regardless of fetch latency. The same wall-clock phase drives every motion: the working/thinking spinners, the cockpit spend count-up, the `?`/`!` attention breath (slow while yellow, quickening with the age heat up to the red blink), and the idle loading-dots cue. Dirty folds and fast work motion run at 100ms; cosmetic attention/loading motion runs at 300ms — the red blink flips every 300ms by design, so it samples cleanly on that grid; a fully calm room falls back to the slow data tick.

On a truecolor terminal a **color-only effects pass** (`render/effects.rs`, tachyonfx over the composed buffer) runs inside the same draw, after the paragraph render: the attention glow lifts the lightness of a `?`/`!` row's glyph, name, and gutter spine on the breath's own phase triangle, and brief one-shot flashes mark transitions — a card entering `waiting`/`failed`, an ask resolving, a rate limit lifting, a new card arriving, the spine under a freshly landed selection. Transitions are detected by diffing each frame's rows and selection against the last observed frame (`EffectState`, riding `UiState` like the spend tally; the first observation records without spawning), and every effect re-resolves its target from the hit-test `line_map` each frame, so it follows its row through reorders and scrolling and drops when the row leaves the screen — the pinned cockpit and bottom chrome map to no row, so card effects can never reach them. The pass is gated on `Theme::effects_enabled` (`COLORTERM` truecolor, `NO_COLOR` off, and the `[sidebar] glow` flag — on by default, riding the snapshot like the theme) and mutates cell colors only, never a glyph — locked by the `effects_pass_never_changes_the_composed_text` golden guard, so the composed grammar and every `.snap` stay byte-identical with the pass on or off. A decaying flash keeps the fast tick warm via `EffectState::any_active` (the tally's twin in the serve-loop gate); the continuous glow rides the 300ms cosmetic cadence the breath already holds. Input is the synchronous exception: a keypress or click paints on the spot so it feels instant. A terminal resize is also a wakeup — a watcher turns `SIGWINCH` into a socket nudge — and repaints through that synchronous input path instead of reading as a blank pane until the next tick. A resize that *grows* the pane is the one deferral: it holds the paint until the [self-close](#self-close) verdict resolves, so the sidebar never paints at the grown width on its way out; a shrink or same-width resize still repaints at once. Ledger wakeups skip heartbeats whose `protocol_version` mismatches the current sidebar protocol; `rimz doctor` reports the mismatch so reload issues are visible after upgrades.

### Enrichment cadences

The display enrichments run on their own clocks, each gated by a persisted stamp ([performance.md → The 2026-06 enrichment cadence pass](./performance.md#the-2026-06-enrichment-cadence-pass)). This is the staleness budget each figure may show — the triage reference when a figure "stopped moving"; presence, status, attention, and the ask flow are not enrichments and stay event-fresh.

| Figure | Source | Staleness bound | Where felt |
| --- | --- | --- | --- |
| cockpit `$` count-up, `◎`/`◇` summary, `W:`/`M:` ledger | fleet spending walk | ≤ `SPENDING_TTL` (15s) | the eased odometer roll absorbs the step; the UTC-midnight decrease still snaps when it arrives via a stale step |
| per-session `$`, context meter, tokens | statusline push | near-real-time — **unchanged** | the sole near-real-time cost channel stays push-driven |
| worktree header `+`/`-`, `⇡`/`⇣`, `≡` | git probes | ≤ `DIFF_STATS_TTL` (5s) while the worktree is hot (a running agent row, or one active within `GIT_ACTIVITY_WINDOW`); ≤ `DIFF_STATS_IDLE_TTL` (60s) idle | a human hand-editing a worktree no agent is working |
| grouping of a brand-new checkout | `git worktree list` | immediate on a session boundary (the `--min-pane-cache-ms` floor); ≤ `WORKTREE_ROOTS_TTL` (60s) otherwise | a worktree added with no agent started in it |
| process-row `C`/`M`/`⇅` | `/proc` sampling | ~3s rates (`METRICS_SAMPLE_TTL`), values carried forward between samples | a new pane's first figures land within one window, its two-sample rates one window later |
| provider budgets, plan, login | accounts probe / broker | 10min success / 10s retry — **unchanged** | — |

### Self-close

A sidebar shares its tab with the user's working pane(s) and has no reason to outlive them. Each snapshot fold counts the panes in its view from the read-only pane list the renderer already needs; the periodic self-close watchdog requests that shared snapshot path, so consumers do not fork their own mux probes. Resize events run a metadata-only fast probe against that list so a sidebar that expands after the last sibling exits can close before the next data fold. Both paths identify the sidebar's own pane from the mux env var and never use `pane capture`/`send`. Once it has seen at least one sibling, a later drop to zero means the last working pane exited: the renderer exits and its `close_on_exit` pane closes. A startup latch keeps it from exiting before the terminal pane first appears. This is backend-agnostic. When pane discovery itself stays broken the sibling count is unknowable, so a degraded renderer leaves through the give-up exit in [Reload recovery](#reload-recovery) instead.

Closing the last sibling first grows the sidebar to the freed full width, so the close is choreographed to avoid a one-frame full-width flash: a grow resize holds its repaint until the sibling-count verdict lands. A "close" verdict exits without ever painting the grown frame; a "stay" or unknowable verdict releases the hold and paints at the new size. The verdict arrives fast — the probe fires immediately and the resize also pulls a fresh snapshot — so the held paint is a sub-frame deferral, never a visible stall.

### Reload recovery

The sidebar keeps the last successful snapshot across iterations. When the snapshot fetch or the in-process heartbeat write fails — a missing binary, a vanished ledger directory, a transient mux hiccup — the loop:

1. Reuses the last snapshot for the current draw, falling back to an empty placeholder only when nothing has loaded yet (a cold start after a workspace move).
2. Absorbs a single flaky fetch silently — the last good frame already covers it, so one blip never flashes a banner.
3. Once the failure persists past the debounce, raises a sticky **health alert** pinned to the bottom edge (status-bar style) — `! Sidebar degraded for 8s: snapshot failed: ledger not found` — with a monotonic "for Ns". The body is truncated before the alert is ever clipped, so the notice can never scroll off.
4. On recovery, lingers as a dim `⚠ last alert 8s ago … · x dismiss` notice rather than erasing, so a failure that flickered past is still visible; `x` dismisses it, a fresh failure re-arms it. While the alert is active the body — first-run hint, footer, help overlay — steps aside and lets the alert speak alone.
5. Gives up if the failure never clears. The common deleted-binary case self-heals (the snapshot fork re-resolves to the installed `rimz` on `PATH` each tick); give-up is the backstop for a failing heartbeat write, a vanished ledger, or no `rimz` on `PATH` at all. A renderer continuously degraded past `GIVE_UP_AFTER_DEGRADED` is non-functional and — once its heartbeat goes stale — invisible to `rimz reload` and ledger wakeups, so it exits rather than freezing on a stale frame; reload/attach then rebuilds a current-build sidebar against the live panes, and a lone orphan with no working pane simply disappears.

This is the degraded twin of [self-close](#self-close): self-close fires when the view empties, give-up when the view can no longer be read at all. The decision logic is the pure function `app::compute_next_state`, which folds each fetch outcome into a debounced, sticky `Health` (`failure_streak` plus an optional `Alert`); the loop applies its `RenderState` verbatim. `rimz-sidebar` defaults tracing to `off` so warnings do not corrupt the terminal UI — set `RUST_LOG` when debugging the renderer.

## Resume-on-rebirth

When a session dies — laptop reboot, a multiplexer-server crash, or a Rimz-initiated rebirth of a stuck room — the agent processes are gone but the ledger remembers them. Rimz brings them back: any session birth re-seeds the prior agents as running panes, so the room comes up where the user left off instead of empty. This is Rimz-owned, transcript-based continuity — deliberately not Zellij session serialization, which resurrects every command pane `start_suspended` and so reads as unhealthy (the catch-22 [`session_serialization` stays off](./multiplexers.md#zellij-backend) to avoid).

The planner ([`src/resume.rs`](../../crates/rimz/src/resume.rs)) is pure over the durable agent rollup. The cli reads the **audit** projection (`RuntimeScope::Audit`) — the one that keeps the dead-process agents a runtime read expels, which is exactly the set a rebirth must restore — and excludes the sessions the user ended cleanly (`agent_tombstones_for_events`). `plan_resume` then keeps each root agent that was bound to a pane in this session and still carries a session id and an on-disk worktree, collapses a relaunched agent (same kind + worktree) to its newest session the way the [supersession reap](#presence-model) does, orders by recency, and caps the fleet (config `resume.max`, default 8; overflow is reported, never silently dropped). Each survivor becomes a `ResumePane` carrying the adapter's resume argv — `claude --resume <id>`, `codex resume <id>` (`AgentAdapter::resume_command`).

The backend seeds those panes at birth and stays ignorant of agents and the ledger: Zellij spells one `sidebar | agent` tab per pane into the birth layout (command panes born running, never suspended), tmux opens one `sidebar | agent` window each via the `after-new-window` hook — focus lands on the freshest agent so attach drops the user onto it. The restored agents come back **idle**: `--resume` rehydrates the conversation without a prompt, so no tokens are spent until the user types. Each agent's own `SessionStart` fires with `source: "resume"`, coalescing back onto the same `(kind, agent_id)` rollup row and re-stamping its new pane, so the sidebar rebinds the row with no new identity. `--no-resume` (or `resume.on_rebirth = false`) opts out for a deliberately fresh start; a workspace with nothing recoverable births exactly the bare working room.

## Notifications

Native notifications are best-effort polish; the ledger remains authoritative. Opt-in per workspace via `[notifications]` in project or per-machine config. Notify on: an agent entering `waiting`, a resolver picking up or handing off, a bridge falling back to native prompt, an item answered, an agent resuming after waiting, or an agent staying `waiting` past a threshold.

**Coalesce, then escalate.** Several agents entering `waiting` together produce one notification (*"3 agents need you · query-engine"*), not one each; an agent that stays `waiting` past the threshold earns a single nudge, not a stream. **A notification routes you to the pane.** Its text names *who* needs you and *what task* — the prompt itself stays in the agent's pane. Activating one focuses the terminal best-effort and pre-selects that row, so even when the OS cannot focus an exact pane the sidebar already has it highlighted for the jump. A missed notification loses nothing; the ledger and the attention line stay authoritative.

## Zellij plugin rail (planned)

This section is the design spec for a planned renderer — tracked in the [roadmap](../contributing/roadmap.md), unbuilt today. Zellij users will opt in to a wasm plugin that presents the same view-model as a docked, persistent left rail (`[layout.zellij]` in [configuration.md](../reference/configuration.md)). The native pane stays the default and fallback; the rail only changes presentation, never correctness, and lays the view-model out to its own pane geometry — so there is no pre-rendered frame to ship and no resize protocol.

- **Reference.** Model it on Zellij's bundled `strider` plugin: a docked side pane that ingests host data asynchronously, keeps `State` separate from per-section view structs, scrolls a bounded list, and handles key + mouse. Mirror its split — state in one module, a render fn per worktree group, pure layout helpers shared.
- **Async ingestion through the host.** A wasm plugin cannot block on a subprocess, so it never runs `rimz` inline: it calls `run_command(&["rimz", "sidebar", "snapshot", "--json", "--workspace-id", <id>], ctx)` and receives `Event::RunCommandResult`, with the `ctx` map tagging each request so the handler matches its response. Parse stdout into the view-model; on non-zero exit, keep the last good snapshot and raise the same sticky health alert as the native loop. Stay read-only on the ledger — never a ledger-writer import.
- **Wakeups arrive as pipes; a timer backstops them.** `zellij pipe --name rimz::feed` lands in `fn pipe()` and kicks a fresh snapshot `run_command`; a `set_timeout` keepalive re-fetches on the slow poll so a missed pipe never strands the rail. Subscribe to `RunCommandResult`, `Key`, `Mouse`, `Timer`, and `PermissionRequestResult` — `run_command` needs the one-time `RunCommands` grant.
- **Actions cross the CLI boundary, never an import** (read-only constrains the import graph, not the process tree): jump → `focus_pane_with_id(...)` after stripping the `zellij:` prefix and reconciling `pane_process_start`; answer a `script` item → `run_command(&["rimz", "feed", "resolve", …])`.
- **Lifecycle.** Workspace id and the `rimz` binary path arrive in the `load()` `configuration` map, mirroring strider's `caller_cwd`. The rail writes no heartbeat — Zellij owns its liveness, and an idempotent `launch-or-focus-plugin` dedupes by URL + config and docks it left into a live session, which a CLI-launched pane cannot reach after birth. That docked pane plus `launch-or-focus-plugin` is what makes it "non-killable": it resists accidental loss and the next `rimz` / attach re-summons it.
