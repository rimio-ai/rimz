# Multiplexers

> See [DESIGN.md](../../../DESIGN.md) for the commitments this doc operationalizes.

Zellij and tmux carry different communities, and Rimz serves both as first-class backends — same ledger, same bridge, same CLI, same sidebar model, tested against one matrix. The multiplexer owns terminal mechanics (panes, views, attach/detach, scrollback, layout, resurrect); Rimz owns workspace state. This doc holds the Rimz-side contracts; the upstream surfaces live in the externals mirrors, [zellij-reference.md](../../externals/mux-adapter/zellij-reference.md) and [tmux-reference.md](../../externals/mux-adapter/tmux-reference.md).

## Backend selection

[`auto_detect_backend`](../../../crates/rimz/src/mux/selection.rs) picks the backend, first match wins:

1. the `--mux <name>` flag,
2. the active environment (`ZELLIJ` / `ZELLIJ_PANE_ID`, then `TMUX` / `TMUX_PANE`),
3. the installed binary, Zellij preferred when both are present.

Selection is stable across worktrees: every worktree of one repo resolves to the same session on the same backend.

## `MuxBackend`

One trait, [`MuxBackend`](../../../crates/rimz/src/mux/mod.rs), holds every backend-specific operation — session lifecycle, pane listing and I/O, focus, sidebar and tab layout, presence install, and health/recovery. Everything correctness-critical sits above it, identical across backends: the ledger, the per-request decision sockets, the resolver heartbeat, the wakeup socket, the feed and event schemas, the trust gate, the agent hooks.

**Parity is the rule, fast paths are the exception.** A backend-only capability is always a latency hint layered over shared truth — never a correctness requirement. If a feature exists only on Zellij, the tmux backend passes the same matrix without it. Cross-backend policy (the one-sidebar-per-view planner and plan-execution accounting in [`reconcile.rs`](../../../crates/rimz/src/mux/reconcile.rs), the sizing math in [`width.rs`](../../../crates/rimz/src/mux/width.rs)) stays pure and above the backends; each backend collects inputs and executes the plan.

The CLI hands `open_tab` backend-neutral pane argv and layout geometry. Agent resolution, prompts, and worktree cleanup are already compiled into the argv (`rimz agents exec …`), so the backend stays ignorant of agent kinds and worktree ownership. The layout IR lives in [harness.md](../agents/harness.md#the-layout-ir); worktree cleanup is in [worktree.md](../agents/worktree.md#cleanup).

### The identity pin

Session birth stamps the room's identity (`RIMZ_WORKSPACE_ID`, `RIMZ_PROJECT_ROOT`, via [`pin_env`](../../../crates/rimz/src/workspace.rs)) into the session environment, so every pane — and every agent and its in-pane hook children — inherits the workspace it lives in. A daemon-routed hook that misses the pin recovers it from the in-pane agent process ([agent.md](../agents/agent.md#hooks-resolve-the-room-they-live-in)).

Each backend pins at its own birth seam. tmux sets the pair on `new-session` and re-asserts it idempotently on every ensure, so panes born later still carry it; the same seam stamps `COLORTERM=truecolor` when the launching terminal advertises it, because tmux births panes under `tmux-256color` with an empty `COLORTERM` and room apps read RGB capability from the session environment. Zellij carries the pair on the spawning client's environment, and the per-session server plus every pane fork from there, so inheritance is transitive — but Zellij has no post-birth re-assert, so a session born before the pin existed keeps its old environment and its participants fall back to the static resolution ladder. Rebirth re-pins on both backends, and resume tabs are ordinary layout panes, so a re-seeded agent inherits the pin like any other.

### Pane metadata

`list_panes` reports each pane's **foreground command**, optional **spawn command**, **cwd**, view, and id. The sidebar uses foreground for display, spawn for stable identity when present, and cwd for worktree grouping ([sidebar.md → Presence model](./sidebar.md#presence-model)). Foreground and cwd are cross-backend; spawn is Zellij-only and stays optional. The parity floor for presence is **command + cwd**, which both backends meet. On Zellij the foreground and cwd fields are version-spanning ladders — the adapter takes the first non-empty field across the names Zellij has emitted — and a layout-named `rimz-sidebar` pane always reports `rimz-sidebar` as its foreground so it filters as chrome even when Zellij omits the command fields.

Neither backend reports a per-pane process start, so Rimz derives `pane_process_start` itself from `/proc` ([produce/panes.rs](../../../crates/rimz/src/sidebar/produce/panes.rs)) and uses it as the reused-id reconciliation key. The key chiefly guards Zellij, whose pane ids recycle; tmux `%id`s are never reused within a server lifetime. The pane PID is only the walk root and metrics binding — a pane's PID is its shell, not the agent it launched — so agent liveness instead uses the agent's own PID, captured best-effort by its hook ([agent.md](../agents/agent.md)).

### Two kinds of focus

`list_panes` reports `PaneRef.is_focused`, the backend's **per-view focus candidates**. On Zellij this is a per-tab remembered last-focus mark: reconnect and floating churn can stack several marks in one tab, and background tabs carry their remembered mark too. For the tab an attached client is viewing, the producer anchors `TabFrame.active_pane` to `client_view`'s focused pane, the converged single-focus truth. Unviewed tabs use the presence plugin's transition-resolved `active_panes` value when available, then deterministic arbitration into one structural `TabFrame.active_pane`; the raw marks stay visible for diagnostics.

This resolved per-view value is the focus signal the sidebar uses for selection — each tab's sidebar derives its selection baseline from its own view's active working pane ([sidebar.md](./sidebar.md#how-the-highlight-stays-on-the-right-pane)). It is one deterministic value per tab however many clients attach: when the user is viewing the tab it comes from their focused pane, otherwise it names the pane they would land on. **Per-client** focus exists on both backends and anchors the viewed tab while still resolving to one pane per tab, so the shared sidebar buffer renders one highlight for every viewer.

`client_view` is the per-client seam the producer reads once per pane-frame tick. It returns the focused pane per attached terminal client plus a presence summary: human-client count on both backends, and `last_input_ms` only on tmux. tmux gets that timestamp from `#{client_activity}` in the same `list-clients` fork and filters `ignore-size` clients so Rimz's presence watch stays outside the human attach count. Zellij's `list-clients` exposes attached terminal clients but no idle clock, and global input interception would consume the user's keys, so Zellij presence is attach-only: attached reads active, no terminal clients reads detached.

`focus_pane` is the one-way jump primitive, and it lands cross-view on both backends — Zellij switches to the containing tab directly, the tmux backend selects the window then the pane. Either way a jump is one client invocation with no follow-up state.

### Focus key

The sidebar's in-pane keys only fire when the sidebar pane is focused, so a room-scoped chord (`[sidebar] focus_key`, default `Alt+p`) reaches it from any pane. The keystroke lands in whatever pane is focused, so the multiplexer intercepts it; both backends run [`rimz sidebar focus --toggle`](../../reference/cli.md), which focuses this session's `rimz-sidebar` pane (or, when already on it, returns to a working pane). Rimz registers the chord at session birth best-effort, so a convenience key never blocks a room. The chord is parsed once by [`FocusChord`](../../../crates/rimz/src/mux/focus_key.rs) (`Alt`/`Ctrl`, `M-`/`C-` and `-`/`+` separators).

The two backends bind it differently because a tmux binding and a Zellij binding reach a pane differently. tmux binds a server-global root-table key that bakes in no room identity and resolves the pressing pane's session at keypress. Zellij keybinds route through the presence plugin: Rimz passes the chord in the plugin's load configuration, and the plugin binds it — once it holds the Reconfigure grant — to a runtime-only `MessagePluginId` action that messages its own plugin id, reaches the exact loaded instance from any pane, keeps the user's `config.kdl` unchanged, and resets when the session ends; a user who declines Reconfigure can bind the same pipe by hand. `Alt` is the default because it survives the terminal, Zellij's locked mode, and tmux's prefix; `off` or empty registers nothing.

## Pane and view IDs

Raw IDs stay inside the backend adapter, where the native command expects them (Zellij `terminal_3`, `plugin_1`; tmux `%3`). Everywhere else they travel **normalized** — `zellij:<raw>`, `tmux:<raw>` — through env vars (`RIMZ_PANE_ID`), feed items, snapshots, and CLI arguments. [`pane_from_env_value`](../../../crates/rimz/src/mux/mod.rs) is the one env→ID mapping.

`ViewId` names the view (tab/window) holding a pane by the pane-list identity Rimz observes on every fast path — Zellij tab position (`tab_1`), tmux window id (`@3`). `PaneRef.view_id` is the flat read-side seam; the producer lifts it into `TabFrame.view_id` so sidebar-per-view bookkeeping runs over typed topology.

**A view id is never the view's on-screen label.** Zellij's default tab names are themselves number-shaped (`Tab #16`), so matching a positional `tab_15` against a tab *named* "Tab #15" joins two unrelated id spaces and lands on the wrong tab in any session that has closed one. The label is sticky, minted at tab creation; `PaneRef.view_name` carries it for display only. Resolve "which tab holds this pane?" through the pane id — never by matching a view id against a label.

## Zellij backend

A Zellij layout applies only at session birth, and a layout is the only way to place a left, sized pane at creation, so Rimz owns the birth layout and treats live repair as convergence back to that layout: close stray sidebars by id, add a missing sidebar in place, move it left, and shrink it to the session's fixed birth width. `ensure_session` is a no-op (Zellij creates sessions lazily); the sidebar launch owns first birth through `attach --create-background` with a generated layout. `<room-options>` combines the Rimz-owned invariants and the optional `[zellij]` keys the user sets in Rimz config; each maps onto a Zellij `options` flag ([reference → options catalog](../../externals/mux-adapter/zellij-reference.md#options-catalog)), and newer flags are version-gated so an older host degrades to its default rather than aborting. The room invariants and the config model are in [configuration.md → multiplexer room options](../../reference/configuration.md#multiplexer-room-options).

**Mouse passthrough and tab focus.** Birth and attach still pass `options --mouse-click-through true` and `--focus-follows-mouse false` as a birth-window hint, but Zellij XORs boolean CLI options against values already set in the user's `config.kdl`, so CLI flags cannot express an absolute room invariant for every user. The presence plugin applies Rimz's resolved `[zellij]` `focus_follows_mouse` and `mouse_click_through` values through `reconfigure(..., false)`, whose KDL path merges onto the live config absolutely and never writes the user's file. With the defaults, Zellij 0.44 sends the first click through because click-through is on and focus-follows-mouse is off; a single click both focuses the sidebar pane and reaches the renderer, so a jump lands on the first click rather than the second. Rimz leaves `advanced_mouse_actions`, `mouse_hover_effects`, `mouse_mode`, and global `pane_frames` to `config.kdl` unless the user sets those keys in Rimz config. Each versioned flag is gated to the release that added it ([reference → options catalog](../../externals/mux-adapter/zellij-reference.md#options-catalog)) and best-effort: older Zellij does not know it, so Rimz omits it and degrades to the host defaults. The renderer's selection model treats the resulting `from-pane → sidebar → target` focus transition correctly — see [sidebar.md → selection](./sidebar.md#jump--the-row-is-the-link). Zellij remembers each tab's active pane; on a later tab switch the presence plugin classifies the switched-to tab after the focus marks settle. A tab restored to `rimz-sidebar` broadcasts `focus-stranded` so the renderer that owns the stranded pane refocuses its remembered working pane. A tab restored to work broadcasts `focus-changed`, matching tmux's realtime control-mode focus signal and letting the now-viewed sidebar repaint before the producer's next `client_view` pull. When attached clients are viewing distinct panes, the renderer skips the refocus because focus ownership is ambiguous and `focus-pane-id` would steal another client.

**Serialization off.** Rimz disables Zellij session serialization on every birth and attach. Resurrection is worse than useless here: agents and scripts cannot restore their running state, so a resurrected room comes back as a wall of held command panes with a dead mouse ([reference → session serialization](../../externals/mux-adapter/zellij-reference.md#session-serialization-and-resurrection)). With it off, a crashed server's session simply vanishes and the next start births a clean, running room; Rimz owns rebirth instead ([resume-on-rebirth](./sidebar.md#resume-on-rebirth)).

**Session metadata off.** Rimz also passes `disable_session_metadata true` on every Zellij birth and attach. That stops Zellij's periodic `session-metadata.kdl` rewrite and command-discovery `ps` loop; `Absent` and `Exited` still converge through the same clean-rebirth gate, so disabling the metadata sidecar changes CPU cost rather than room semantics.

**The birth layout** shapes every tab the same — a left `rimz-sidebar` pane and a focused terminal, above a one-row compact-bar plugin — through a `new_tab_template` plus explicit birth tab(s). The sidebar pane is borderless and `close_on_exit`, so work-pane frames can be styled while sidebar hit-testing starts at row 0 and the pane disappears when its process exits. The birth size carries the session-birth width verdict (`min(30%, theme.display.max_cols)`, resolved once by [`width.rs`](../../../crates/rimz/src/mux/width.rs)) into the layout itself: detached birth tabs spell the verdict as a percentage of the probed width, while the `new_tab_template` spells it as a fixed column count, because a fixed width wider than a detached session's small default geometry kills the session at layout-apply. In-place add, repair, and `rimz agents` tab opens recover the canonical column count from the live `new_tab_template`; when Zellij cannot report the template, they fall back to consensus among live docked sidebar panes. Repair shrinks only sidebars wider than that value; narrower survivors stay until the view is reopened. `auto_layout` stays on so a `rimz-work-area` swap layout pins the fixed sidebar and rebalances the work area for any pane count; no-direction opens re-tile three-or-more work panes into even columns.

**Birth shape branches** on the session's liveness, reported by `zellij list-sessions`:

- **Live** — the session already carries its sidebar and owns every resize and split since. A trusted sidebar heartbeat makes `open_sidebar` a no-op; a stale heartbeat rebuilds only an inspected live room, leaving an uninspectable one to the reset path.
- **Exited** (`EXITED - attach to resurrect`) — Rimz prefers a clean rebirth (delete, then create from the layout) over resurrecting held command panes. With serialization off this state stops being minted, but the branch stays as defence for sessions serialized before the flag landed.
- **Absent** — first birth: create from the layout.

**The pre-attach health gate.** `open_sidebar` is best-effort and can be skipped or fail, so it cannot be the only thing standing between the user and a resurrecting attach. `ensure_clean_session` is the authoritative gate `rimz start` and the attach flows run immediately before building the attach command: on Zellij it probes the pane list and treats a held command pane (the resurrection fingerprint) as not-clean, deleting and rebirthing an absent, exited, or inspected-suspended room while leaving a clean live room untouched. A live room whose listing times out is uninspectable, so Rimz reports it stuck and requires the reset path before any destructive teardown. A Zellij IPC socket-path overflow is a separate environment precondition: it is classified as `SocketPathTooLong`, reset is not offered, and `rimz doctor` prints the shorter-directory fix.

**Reset.** A room that cannot be auto-healed needs an explicit destructive reset. `rimz reset` (and the single-confirm auto-offer on a stuck room) tears the session down, purges the serialized-session cache, reaps stale sidebar runtime files, sweeps orphaned servers and leaked daemons scoped to this user and session, then rebirths. Without a terminal to confirm, `rimz start` fails fast with the fix rather than destroying a session unattended.

**Daemon and resumed births.** `rimz start` always carries the `rimzd` daemon view, so `open_sidebar` births a two-tab layout — the daemon dashboard first, then the focused working tab — because Zellij has no CLI to reorder tabs after birth, so leading position is fixed in the birth layout. A reborn session also re-seeds its remembered agents: the birth layout spells one `sidebar | agents…` tab per worktree, each agent a command pane running its resume CLI in that worktree, focus on the freshest. Born in a fresh layout they start running, never suspended — the same reason serialization is off. The same renderer handles plain, daemon, and resumed births.

### Zellij presence channel

The producer's pane poll gets a push fast path on Zellij: a headless wasm plugin ([`rimz-presence-zellij`](../../../crates/rimz-presence-zellij/), embedded into every build: release binaries embed a fresh `build-plugin` artifact, and the crates.io crate embeds the vendored `crates/rimz/presence/` wasm refreshed by `cargo xtask plugin-refresh` and guarded by `cargo xtask invariants`) subscribes to Zellij's pane and tab manifests plus command and close events, and pokes `rimz sidebar wake` with typed payloads — pane opened/closed, command changed, focus changed, and `focus-stranded` (a switched-to tab that restored focus to its sidebar). A tab switch onto a working pane also pushes `focus-changed`, plus the same settle verify the pane-focus shortcut uses, giving Zellij the realtime focus parity tmux gets from control mode. Each wake after the first manifest may also carry a compact `--topology` payload from the plugin's live roster; before that the producer falls back to `zellij action list-panes -j -a`. The CLI refreshes the presence stamp, writes `pane-topology.json` when present, and broadcasts a typed `SidebarEventEnvelope` to every fresh heartbeat: overlay events paint on arrival, topology events also ask the producer for a verifying frame, and the published `snapshot.json` lets consumers refold from cache. The taxonomy and fusion rules are in [state.md](./state.md).

Poke discipline keeps the channel quiet: the first change pokes immediately, duplicates inside a 100ms floor collapse, each accepted change schedules one settle poke so a command-change cannot strand the pre-change command, a 60s keepalive holds the stamp fresh while idle, title-only events stay filtered, and a focus move onto the sidebar pane emits an identity-bearing `FocusChanged` patch naming that pane so the focused renderer resumes animation immediately while authoritative own-view visibility confirms on the next produce. The plugin subscribes to `RunCommandResult` and drains every reply to its `run_command` pokes; the keepalive also carries WASM memory pages, uptime, completed-command count, and Zellij version into the rotating `plugin-presence.log.jsonl`, the leak-investigation surface for separating plugin linear-memory growth from Zellij-native RSS growth. The first manifest after load names every pre-existing pane the poll already covers, so an attach never floods card-create pokes.

Loading is Rimz-owned, never the user's `config.kdl` (a layout cannot load plugins). Every attach-shaped flow fires an idempotent `zellij … pipe --plugin`, the one load verb that works on a clientless session, and `rimz reload` additionally converges a running instance onto a freshly installed wasm. Load-time configuration pins the workspace, session, absolute `rimz` path, and runtime mouse options; the artifact path is canonicalized because Zellij keys the permission grant on the exact string. The plugin is gated to Zellij ≥ 0.44; an older host, a missing artifact, or a denied permission reads as poll mode, and `rimz doctor`'s presence row names the first failing precondition. Permissions (`ReadApplicationState` + `RunCommands` + `Reconfigure`) are the user's, granted once and cached by Zellij; `Reconfigure` applies the mouse options and the optional focus keybind at runtime without writing `config.kdl`. The security boundary is in [security.md](../../guide/security.md#the-zellij-presence-plugin).

### Zellij backend caveats

These are the upstream quirks the backend works around; the upstream surfaces themselves are in the [reference](../../externals/mux-adapter/zellij-reference.md).

- **Minimum version is 0.41.0**, the floor `rimz doctor` reports as `meets_min_version`; newer capabilities are gated individually: Zellij ≥ 0.42 enables `stack-panes`, ≥ 0.43 enables `advanced_mouse_actions`, and ≥ 0.44 enables the presence plugin plus `mouse_click_through` and `mouse_hover_effects`. Older supported hosts degrade on each gated feature rather than aborting the room.
- **Plugin keybinds pause briefly on 0.44.x.** Zellij's upstream `KeybindPipe` completion path can freeze the UI for about one second before a plugin keybind acts; the focus-key jump still lands.
- **Pane IDs are positional, not stable.** Zellij exposes no stable per-pane CLI handle; ids can be reused as panes close and reopen, which is why feed items carry `pane_process_start` so reconciliation can refuse a stale match.
- **Session names are short and path-unique** (`rimz-<basename-slug>-<hash6>`), keeping the room human-scannable while staying under Zellij's macOS AF_UNIX socket budget and distinguishing same-basename roots. When the recorded and current derived names diverge, `rimz start` retires the stale session before rebirth.
- **`new-pane` answers before the pane mounts, and action stdout can cross clients.** The printed pane id is allocated before the screen thread mounts the pane (a detached session drops the mount entirely), so reconcile treats it as a hint, discovers the mounted pane by listing the target tab, and cleans up only a pane a fresh listing proves is a newly-created `rimz-sidebar`.
- **`new-pane` can mount into a nested row.** A directional add still anchors to the focused layout node, so a sidebar can report `x=0` with a work pane spanning beneath it; every add verifies the full-height left-column band and repairs only the narrow nested shape it creates.
- **`list-panes -j` reports identity and geometry, not live process state**, and on 0.44.3 pays an enrichment round trip Rimz does not use. Rimz derives cwd, pid, and process start through `/proc` and treats the spawn command as identity; the presence plugin's topology cache carries what Rimz needs, leaving the CLI JSON as the correctness fallback.
- **Named-session actions can print a session-not-found banner with exit 0.** A `--session <name>` action against an absent, exited, or still-registering session prints `Session '<name>' not found...` and an active-session list across stdout or stderr; Rimz classifies it as `MuxErr::SessionNotFound`, and best-effort sidebar reconcile and daemon view launch defer quietly while the pre-attach gate owns rebirth.
- **A detached server can drop pane lifecycle processing until the next attach** — notably a last-pane exit and the relayout after a sibling closes. Reconcile defers adds on detached sessions, and the renderer's tab-empty self-close rides its data-tick backstop rather than resize delivery alone.
- **A configless server births a setup wizard that silently drops `new-pane` mounts** (layout-born panes mount normally). The test harness seeds a config at the home-relative path Zellij prefers; in production a first-ever user dismisses the wizard once and a dropped mount is retried by reconcile.
- **The layout file outlives the create call** — Zellij parses `--default-layout` asynchronously, so Rimz keeps the temp layout on disk until the panes materialize, then deletes it.
- **Every tab is born with an explicit focused terminal, not `children`** — a `children` placeholder nested in a split is never auto-filled, which would strand focus on the sidebar alone.
- **Control commands are time-bounded.** Every [`CommandSpec`](../../../crates/rimz/src/mux/command.rs) run waits at most `COMMAND_TIMEOUT` (30s) then SIGKILLs the child — a wedged `zellij action` busy-loops at 100% CPU when its server dies and would otherwise hang the caller forever. A healthy command answers in milliseconds, and callers treat mux commands best-effort, so the bound degrades rather than blocks.
- **Per-test server isolation in CI.** Tests construct the backend with a private runtime dir (Zellij locates its server socket under `XDG_RUNTIME_DIR`), the parity counterpart of tmux's `with_socket`. Every command flows through the single `ZellijBackend::cmd` chokepoint, so one field threads isolation everywhere.

## tmux backend

The sidebar runs as a managed pane: `open_sidebar` splits a left sidebar into the initial window at the session's fixed birth width and installs a session-scoped `after-new-window` hook that re-runs the same split in every window opened later — tmux has no tab template, so the hook is how it matches the Zellij birth-tab plus `new_tab_template` parity. Every view is born with a left sidebar and a focused right terminal, and `reconcile_sidebars` recovers the canonical width from the live hook before re-asserting it, so `rimz reload` repairs panes without clobbering the session's birth verdict. The hook pins the verdict as an absolute column count so later windows are born at the start width whatever the terminal has grown to; `target_cols` runs only during the launch probe that creates that verdict. When `open_tab` runs while tmux's latest client is narrower than another attached client, it resizes the freshly-born window up to the widest attached client, re-asserts the hook-docked sidebar to the hook's recorded fixed birth width before splitting agent columns, then restores tmux autosizing so the tab keeps reflowing. Layouts compile to tmux command sequences from the same layout IR Zellij uses.

`ensure_session` applies the per-machine `[tmux]` room options in one batched client call, and the `after-new-window` hook replays window options before docking the sidebar so later windows match the birth window. Session and window options stay scoped to the Rimz session; server-scoped options (clipboard, rich-key handling, focus events) are runtime-global because tmux has no per-session equivalent. The batch appends `*:extkeys` to `terminal-features` whenever extended keys are enabled, and registers root-table `S-Enter` / `M-Enter` bindings that inject the configured modified-Enter sequence so agents receive soft newlines even when they do not request modifyOtherKeys. On tmux 3.5.x, the same extended-key mode trades clean multiline clipboard paste; tmux 3.6 preserves paste bytes while modified keys reach agents as CSI-u. The per-option semantics and Rimz's values are in the [reference → options](../../externals/mux-adapter/tmux-reference.md#options); the config model is in [configuration.md](../../reference/configuration.md#multiplexer-room-options).

When Rimz owns `pane-border-status`, it also writes a `pane-border-format` that floods the `rimz-sidebar` pane's border row with spaces, so work panes carry titled frames while the sidebar reads frameless, the tmux analog of Zellij's borderless sidebar. tmux borders are inter-pane separators plus an optional top or bottom status row; tmux does not draw the outer window edge, so a closed four-edge pane frame remains Zellij-only.

The pane is best-effort: a fresh sidebar heartbeat suppresses producer relaunch, while a missing, stale, unreadable, or protocol-mismatched heartbeat lets `rimz start` / `attach` open a new pane. tmux has no resurrection, so `ensure_clean_session` is a no-op and there is no docked-rail upgrade — the managed pane is tmux's only renderer. For supervised agent panes the producer derives the wrapper spawn command from `/proc`, paralleling its `pane_process_start` derivation, so lazy-registering agents bind and panes group by worktree as on Zellij.

### tmux presence fast path

The producer holds one size-excluded control-mode client ([`PresenceWatch`](../../../crates/rimz/src/mux/tmux/presence.rs)) with a single `refresh-client -B` subscription, and maintains an in-memory roster. Subscription lines emit typed `PaneOpened` / `CommandChanged` / `FocusChanged` overlays with normalized ids; a focus move onto the sidebar pane emits an identity-bearing `FocusChanged` naming that pane so the focused renderer resumes animation immediately while authoritative own-view visibility confirms on the next produce; a `%window-pane-changed` notification emits `FocusChanged` for the window's new active pane immediately, so pane-click focus follows without waiting for the ≤1/s subscription coalescing while the subscription remains the confirming backstop; a `%session-window-changed` notification emits `FocusChanged` for the switched-to window's active pane and unfocuses the previous window's active pane; lines that lack enough identity stay as `PanesChanged` nudges; window-close and layout shrinkage emit `PaneClosed`. Each overlay reaches every fresh sidebar immediately, the producer verifies structural changes with a fresh frame, and the watch refreshes the presence stamp on attach and on each classified line — putting tmux in the same event-mode pane TTL as Zellij while the stream is alive.

The watch rides the control-mode contracts in the [reference → control mode](../../externals/mux-adapter/tmux-reference.md#control-mode): it attaches with `ignore-size,no-output`, holds stdin open (closing the pipe detaches the client), writes only `refresh-client -B` from its command allowlist, drains notifications promptly because tmux force-exits a stale reader, and drops `$TMUX` from the child env so a nested attach is not refused. The writable attach keeps tmux 3.7 `send-keys` usable when a headless session's presence watch is the sole attached client. A dead, refused, or idle watcher degrades to exactly the poll, and the producer respawns with backoff — the parity rule in action: **fast paths are backend-optional; the poll is presence truth on both backends.**

While a backend's presence stamp is fresh, the producer stretches its pane-cache TTL (~13× fewer `list-panes` forks), and topology changes still repaint through typed overlays plus the verify/publish pair; the stamp going stale reverts to the steady poll within the freshness window. The budget math is in [performance.md](../health/performance.md).

### Notification passthrough

Desktop notifications are terminal-local: the sidebar renderer writes OSC 777 and BEL bytes into its pane, SSH carries them to the local terminal, and the terminal decides whether to show a banner or play a sound. tmux forwards the OSC path when `allow-passthrough` is on (Rimz's default, wrapped as DCS passthrough). Zellij currently drops notification OSCs, so `[notifications].desktop = "auto"` disables OSC there and notification handlers stay the portable channel. The full contract is in [notifications.md](./notifications.md).

### tmux backend caveats

- **Minimum version is 3.5.0**, set by the room options `ensure_session` applies across supported hosts (`extended-keys-format` landed in 3.5); the batched sequence fails at the first unknown option. The command surface alone needs only 3.2. `extended-keys`, `*:extkeys`, and the `S-Enter` / `M-Enter` root bindings activate across supported versions; tmux 3.5.x re-encodes bracketed-paste newlines under rich-key mode, and tmux 3.6 removes that paste cost. `rimz doctor` reports floor compliance.
- **Server-less `list_sessions` is empty, not an error** — tmux exits non-zero with `no server running` before the daemon starts; the backend swallows that shape and returns an empty `Vec`, matching the Zellij contract.
- **The sidebar self-closes** the same way it does on Zellij — through the normalized `rimz pane list` — so a lone sidebar removes itself when its window's last working pane exits. The `after-new-window` hook runs `split-window` (not `new-window`), so it never recurses.
- **Resumed agents open as windows** — one `new-window` per remembered channel, named `#<channel>` and born `sidebar | agents…` as the hook docks the sidebar. `new-window -n` turns off automatic-rename, so the name is a stable idempotency key and a re-run never doubles a channel.
- **Per-test server isolation in CI.** Tests construct the backend with a private socket (`with_socket`) to keep each test's server off the user's default; production inherits the system socket.

## Common contract

What both backends deliver:

- **Detach and reattach are multiplexer features** — Rimz does not reimplement them.
- **Runtime correctness needs no visible sidebar** — hooks, the bridge, and `rimz feed ask` work headless.
- **The renderer is interchangeable and optional** — the native pane is the default on both backends; correctness never depends on which renderer (or none) is attached.
- **The ledger survives host restart; processes do not**, unless a host supervisor is wired (tmux-resurrect, Zellij resurrect, systemd).
- **`rimz doctor` reports** the selected backend, versions and floor compliance, PATH-visible backend binaries, backend server-log excerpts, feature availability, sidebar liveness, Rimz runtime socket headroom, the server socket path, Zellij IPC socket headroom when selected, and any degraded modes.
