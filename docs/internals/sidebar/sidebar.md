# Sidebar

> See [DESIGN.md](../../../DESIGN.md) for the commitments this doc operationalizes, and [the interface reference](../../interface/sidebar.md) for what the sidebar looks like on screen — the cockpit, the cards, and the provider dashboard, frame by frame. This doc is the mechanics: how presence, attention, layout, and recovery are computed.

The sidebar is a UI client over the workspace ledger that owns no durable ledger state. It reads in process — the consumer fold for every tab, the produce pipeline (`rimz::sidebar::produce`) on the elder — writes only runtime display files (its own liveness heartbeat, read-mark receipts, `unread.json`, the elder's producer caches, and the room-local live-spend baseline sidecar), and never imports a ledger-writer module. Snapshot producer code may refresh disposable runtime sidecars, such as Codex's stat-gated local context cache, but those files are display caches rebuilt from provider state rather than ledger truth.

One renderer paints every moment of a session — a bare shell, the first agent, a waiting prompt, a fleet across worktrees, detach and reattach. What changes between those moments is the snapshot, never the renderer. For the felt, phase-by-phase walk-through, see [the experience guide](../../guide/experience.md).

## The view-model and its renderers

**The snapshot is the shared view-model, and every decision is made once, here.** The `rimz sidebar snapshot` JSON carries the worktree-grouped row roster admitted by the pane frame (every renderable live pane as a row, agents enriched from the ledger), the attention items, per-agent status and capability, the ranking keys, and timestamps. A renderer is a *projection*: it maps those semantics to glyphs and paints them. It never re-derives which worktree a row belongs to, how rows rank, or which pane runs an agent.

The snapshot command runs in the `rimz` binary, which owns mux access, so it enumerates the session's panes and folds them into the roster before serializing. Every renderer is then a pure JSON consumer — pane presence reaches the screen through the snapshot, never through a mux call of the renderer's own; even [self-close](#self-close) counts its siblings from the shared pane frame rather than a probe of its own. Pane width is the launch path's concern — every sidebar pane is born at the launch's width verdict, `min(30%, max_cols)` resolved once against the launching terminal ([multiplexers.md](./multiplexers.md)), so the renderer never resizes its own pane and a manual resize always sticks.

Two renderers project the same snapshot today:

- **Native pane (default).** `rimz sidebar serve` in an ordinary pane — identical on Zellij and tmux, across detach/reattach. The default and the cross-backend fallback.
- **CLI listings.** `rimz feed list` and friends — the same data as text.

The per-renderer code is just painting, so visual parity is a maintained discipline rather than shared render code. The default semantic→glyph vocabulary is the table drawn in full in [the interface legend](../../interface/sidebar.md#reading-the-glyphs), with its design rationale in [DESIGN.md → Attention at a glance](../../../DESIGN.md#attention-at-a-glance). The mechanic this doc owns: the glyph carries state by **shape** so it survives `NO_COLOR`, and color only reinforces it. Keep every renderer aligned to that table unless the workspace snapshot carries per-machine `[theme.animations]` overrides ([theme.md](../../reference/theme.md#animations)); those overrides theme display heads without changing ranking, routing, heat, or unread semantics. Tones are themable data over the snapshot theme path: `[theme]` selects palette depth and scheme, optional slot overrides win, and `[theme.display]` carries display behavior such as `glow`; the renderer resolves depth because terminal capability is local.

## Presence model

**Row presence comes from the live pane frame, not the ledger.** The producer enumerates the session's panes, assembles them into `PaneFrame` tabs/windows, reads each pane's foreground command and cwd, resolves the cwd to a worktree, and the fold emits **one row per admitted pane** — no pane id is ever shared by two rows. Producer validation rejects implausible Ok reads before publication: an empty frame, a frame missing the renderer's own pane, and one-read large shrinks are held or verified while the prior frame remains the cache; a pane omitted by a fresh read carries forward only when root-process liveness or same-tab evidence still proves it belongs to the room. `pane_admits_card` is the admission rule: it admits work panes and names each excluded class — the caller's own pane, sidebar chrome, and the remote-control/app-server hosts. A pane running `zsh` is a dim [process row](#process-rows); a pane an agent stamped is that agent's row. A just-born pane whose cwd is still unknown folds no external row for its birth frame, so `/proc` or the next mux read can place it in the right group. On both backends the pane list is push-nudged — tmux by the control-mode watch, Zellij by the presence plugin ([multiplexers.md](./multiplexers.md#zellij-presence-channel)), whose close, command, and focus events fuse as zero-latency overlays ([state.md](./state.md)) — with the producer's poll as backstop truth.

**One pane, one row, bound first by the stamped pane id.** A pane's foreground command alone cannot name the agent — Claude can run under `node`, and two same-kind agents in one worktree read identically. Binding is by identity first: every `agent.lifecycle` event carries the mux pane id the hook ran inside (`TMUX_PANE` / `ZELLIJ_PANE_ID`), and the snapshot binds each live pane to the one agent that stamped that exact id. Command and cwd form only a guarded recovery path after no stamp claims the pane: the command must classify as that agent kind, the cwd must equal the agent worktree exactly, and the pane process-start guard must admit the bind. A shell the agent dropped back to, or a `git` it spawned, stays a process row. The agent's ledger identity (status, task, model, effort, context enrichments) then enriches that one row.

**The binding ladder.** Joining a session to its pane runs a short ladder, most-certain first:

1. **Stamped pane id.** Every `agent.lifecycle` event carries the mux pane id the hook read from its own env, or the recovered pane stamp written at ingestion, so the live pane binds the one agent that stamped its exact id ([`agent_for_pane`](../../../crates/rimz/src/ledger/snapshot/panes.rs)). For lazy-registering agents, the bind also reconciles the live pane's process start and foreground command before it wins; a stale recovered daemon stamp whose session predates a reborn pane falls through to the later cwd-recovery steps. A genuine session rebirth also draws a durable `session.rebirth` boundary in the ledger — pane ids restart at zero on rebirth, so every prior stamp names a dead pane; the fold clears them all at the boundary, and the per-pane process-start proof above remains the backstop for stamps the boundary cannot see (a rebirth Rimz never performed). When two live root sessions share one Codex pane, the rollout head decides the split case before this tiebreak: a same-live-pane fresh conversation (`/clear` / `/new`, no `forked_from_id`) reaps the prior session producer-side after prompt-start recovery stamps the new daemon-routed root onto that focused occupied pane, while a same-process in-pane thread fork (`/side` / `/btw`, with `forked_from_id`) stays live and the pane's card follows the **primary** (earliest-`registered_at`) session. A genuine relaunch is a new process whose predecessor the process-start guard above has already evicted, so it still takes over the card.
2. **Recovered pane stamp (daemon-routed lazy agent).** A daemon-routed [lazy-registering agent](../agents/agent.md#the-instance-lifecycle) can start with no hook env pane id, so hook ingestion recovers a durable stamp before appending the first root lifecycle event. It reads the same repaired pane frame the producer publishes — cache rotation, Zellij pid/cwd backfill, and process-start stamping included — then filters to same-cwd, same-kind panes that no other live session's stamp still plausibly owns. One eligible candidate stamps directly; focus only disambiguates plural candidates, with per-client focus (`zellij action list-clients` / `tmux list-clients`) ahead of per-view `PaneRef.is_focused`. If the first prompt event is for a new Codex root and every otherwise-eligible focused candidate is already occupied by another Codex root, recovery may share the occupied pane so `/clear` / `/new` and `/side` / `/btw` get the same-pane proof the rollout-head reap needs; an already-known unstamped root and non-prompt registration never get this fallback. Ambiguous focus, no eligible pane, a pane another non-Codex session's fresh stamp still owns, or a late event for an already-stamped session leaves the event unstamped. Each attempt appends probes, candidates, reject reasons, and outcome to `binding.log.jsonl`.
3. **Exact-cwd recovery.** An unstamped session binds the live agent pane whose command classifies as that kind and whose cwd equals the session worktree *exactly* ([`agent_pane_for_pane`](../../../crates/rimz/src/ledger/snapshot/panes.rs)). This is the normal pane join for a daemon-routed lazy session and the rebirth repair for a non-lazy session whose stamp was cleared while its process kept running. Reborn/resumed Codex panes win first: the producer reads the `codex resume <session-id>` argv from the pane's root process or single foreground child into `PaneRef.resumed_session_id`, and a matching session binds that pane before heuristics even when its old stamp is stale. The remaining same-cwd sessions pair globally, newest session first, to the latest known pane process start that is at or before the session's first event; residual ambiguity binds deterministically by sorted starts and pane ids, and the producer appends the candidate set to `binding.log.jsonl`. A session whose last activity predates the pane's process start is refused ([`pane_start_allows_bind`](../../../crates/rimz/src/ledger/snapshot/panes.rs)), so a stale session never latches onto a freshly-started pane by reused id or same cwd. The producer stores pane process starts on `PaneProcess.started_at`, deriving an exact root/child start from `/proc` when a backend reports none natively and assigning a cwd-derived agent start only when one unresolved pane and one unaccounted in-cwd CLI start remain; ambiguous cwd starts abstain, and duplicate carried cwd starts are cleared instead of republished as an earliest floor across panes. A bare `node` pane is deliberately ambiguous and waits for the next hook; a foreign-uid elevated-agent marker refuses the bind and stays a process row.
4. **Idle synthesis / process row.** With no session bound, a wired pane of a lazy-registering agent renders a synthesized idle `○ <kind>` row until the first turn swaps in the real session ([`idle_agent_row`](../../../crates/rimz/src/ledger/snapshot/panes.rs), gated by the agent being among the wired lazy kinds); adapter launch defaults may fill the model/window tokens so a Codex pane shows its configured model with `272k` immediately. Non-lazy agents never idle-synthesize. An unwired lazy pane or an unbound non-lazy pane stays a process row.

**Why a daemon-routed session can be unstamped.** Codex under remote control fires its hooks from the shared per-user app-server daemon, so the hook's env carries no `ZELLIJ_PANE_ID` and `RIMZ_AGENT_PID` records the daemon's pid, shared by every client (why the hook runs off the pane: [adapter/codex.md → Session registration](../agents/adapter/codex.md#session-registration-and-launch-quirks)). The session id lives only inside the daemon's owned rollout and its socket traffic; it is in neither the client's environ, cmdline, nor open files, so a client-pid → session join is impossible by construction. Reading the client environ through the mux-reported `pane_pid` recovers only pane ↔ client-pid, never pane ↔ session. Rimz therefore binds daemon-routed local sessions from live pane candidates, explicit resume commands, and pane process-start ordering, with cwd as the shared scope rather than the sole key.

**No live pane, no row.** An agent with no live pane — a subagent, a ghost a kill left in the rollup, a relaunch the [reaper](../agents/agent.md#liveness-and-presence) hasn't collapsed — is data, not presence. It cannot resurrect a row or latch onto a stranger's pane; exact-cwd recovery binds only a live same-kind command in the exact worktree and only when the process-start guard admits it. So an exited agent never lingers: its pane closes (gone next snapshot) or reverts to a shell row. There is no `offline` status. A relaunch-in-place is the ghost-bind case: an older session that never fired an exit hook is kept off the fresh pane by ask-supersession ([`agent_hook_session_stale`](../../../crates/rimz/src/ledger/snapshot/view.rs)) and collapsed by the reaper, so the new instance's own session binds the pane. The reaper collapses an older same-pane root when the newer one is a **provably different process** (a relaunch), or for Codex when the newer root is stamped to the same live pane and its rollout `session_meta` has no `forked_from_id` (a `/clear` / `/new` fresh conversation). A paneless same-worktree sibling never stands in for that pane. A same-process in-pane thread fork (Codex `/side` / `/btw`) carries `forked_from_id`, survives the producer-side reap, and stays pinned to the earliest-registered primary.

**Remote agents are not shown yet.** A *remote* agent runs only in the daemon with no local pane — `claude remote-control --spawn worktree`, or a Codex thread started from the web. Its session can still reach this workspace's rollup (the hook resolves the ledger from its worktree, and same-repo worktrees share one workspace id), so Rimz often holds its status and worktree, yet it renders nothing: presence is pane-anchored and there is no pane to bind. Showing remote agents needs a presence class that renders from the rollup alone and repurposes the jump — with no local pane to focus, the row's action would open the remote surface or attach the thread into a fresh pane. This is a known gap, unbuilt this round.

**Attention folds onto the agent's pane.** A pending agent ask belongs to the agent's pane, so the snapshot folds the session's single most-relevant pending ask onto that agent's row (`? waiting`, or a braille resolver spinner) rather than adding a second row — a session never stacks more than one row. It un-folds once the agent records activity past the ask, so an ask answered in the agent's own UI returns the row to `running` (see [agent.md → Liveness](../agents/agent.md#liveness-and-presence)). If the agent's pane is absent the ask leaves the sidebar but stays in audit (`rimz feed list --audit`). A script's blocking `feed ask` stamps the pane it runs inside (the per-pane mux env survives into the CLI) and renders only while the current frame admits that pane: on a pane that resolves to an agent row the ask folds onto that row (the agent keeps its identity line), an agent-less pane renders the bare standalone ask card, and two pending asks naming one pane collapse to the newest — one pane, one row. Outside any pane (CI, cron), or once the pane leaves the frame, the ask remains rollup metadata served by `rimz feed list`, not a jumpable card.

### Daemon Client Disambiguation

When two or more daemon-routed Codex clients share one worktree, cwd scopes the candidate set and the binding ladder chooses the owner:

- **Single candidate at hook time.** If the repaired live frame leaves exactly one same-cwd Codex pane that no other fresh stamp owns, the hook writes that pane id onto the lifecycle event immediately.
- **Focus for plural candidates.** If several candidates remain, hook ingestion probes client-focused panes first and falls back to the per-view `PaneRef.is_focused` mark only when the client-focus probe fails. The selected pane is written into the lifecycle event as a normal pane stamp, so later projection uses the same exact-id path as a standalone agent.
- **Projection fallback.** A pane launched as `codex resume <session-id>` binds that session exactly. Otherwise, remaining unstamped sessions pair newest-first to the latest candidate pane start that could have hosted the session; irreducible ambiguity uses the deterministic sorted order and logs the candidate set.
- **Binding log.** Hook recovery attempts and producer fallback pairings append to `binding.log.jsonl`, so a silent daemon hook still leaves an inspectable record of probes, rejects, selected pane, or ambiguity.

Instance liveness needs no new signal: the in-pane CLI is the pane's foreground process, so a daemon-routed *in-pane* session leaves the screen the moment its pane stops reading `codex`, exactly like a standalone one. Rollup hygiene is what the daemon's loaded-thread set governs — an unstamped session's recorded pid is the shared daemon, so process liveness can never reap it, yet a closed conversation lingers in the rollup and would bind its stale stats to a live pane by cwd. The producer reaps it: a daemon-mode session ([owner pid is a codex daemon](../../../crates/rimz/src/remote_control.rs)) absent from the app-server's `thread/loaded/list` is dropped before the pane fold ([`drop_dead_daemon_sessions`](../../../crates/rimz/src/ledger/snapshot/view.rs)), so it neither renders nor attaches stats. The reap is tri-state and fail-safe — an unreachable daemon or an untrusted list keeps every session, never a mass-reap. The loaded set holds every thread the daemon keeps in memory, a completed one included, so it is rollup hygiene rather than a fresh-pane signal: a relaunched `codex` in a reused cwd is kept off the prior, still-loaded session by the process-start guard above, and a same-pane `/clear` / `/new` is re-pinned by the rollout `forked_from_id` reap.

### Honest reads across a mux hiccup

`list-panes` is a round-trip the mux occasionally answers with an empty body, a partial pane set, or a live pane missing its command or cwd. Four read-side guards keep a momentary glitch from reaching the screen as a lie:

- **Degraded reads rotate and repair process fields.** Rather than relabel a known pane as an anonymous row that blinks out next tick, the producer joins the fresh `PaneState.current` to the last published process for that *exact* pane id. Stable command/root identity fills raced-null command, cwd, and process-start fields; a command or root-pid change rotates the prior current process into `previous` and keeps the fresh process clean. The pid is never rotation-carried — only the metrics layer restores it, behind its `starttime` pid-reuse guard. A pane whose fresh read left cwd empty but whose root pid is known has it repaired from `/proc/<pane_pid>/cwd` (`backfill_pane_cwds`) before the publish, so a just-born pane groups under its worktree on first appearance; only an empty cwd is filled, and a brand-new Zellij pane with no pid waits one `METRICS_BACKGROUND_SAMPLE_TTL` or uses the `rimz agents exec … --worktree-path` argv fallback, which also covers non-Linux. The repair is surgical, unbounded while the pane persists, and runs at pane-frame production before the elder publishes the shared frame, so every renderer sees the same repaired pane fields.
- **Live omitted panes carry forward with proof.** A fresh frame that loses panes first forces a direct mux re-pull with any cached topology treated as stale. If the re-pull still omits a prior pane, the producer carries that prior `PaneState` only while liveness proves the pane still exists: the prior carried pid and start ticks, the metrics root-pid/starttime binding, or the prior current pid must still match `/proc` as a non-zombie process; the renderer's own pane carries by identity; pidless same-tab siblings carry only beside a carried sibling whose root process was proven live. Carried panes keep their old tab/window shape, mark `PaneFrame.carried_panes`, and publish a `pane_carry_forward` diagnostic with a prior/offending frame pair. If the forced re-pull refutes the initial omission, the producer records `pane_carry_refuted` with the initial offending frame instead. The carry expires after `PANE_CARRY_TTL` and records `carry_forward_expired`, so a real pane exit drops promptly once the process proof is gone; close overlays still hide carried closed rows immediately while the verified producer frame catches up.
- **A pane with no readable identity folds no row.** An unbound pane whose command is still unknown after the frame rotation — mid-birth, or a first read that raced before any prior entry existed to draw on — renders nothing this frame rather than an anonymous `process` row under `external`; the next read names it. The guard covers only the unbound residue: an agent-stamped pane binds by pane id, not command, so it still renders its agent row, and the pane stays in the published pane frame, so the sibling count ([self-close](#self-close)) and the selection baseline see it.
- **The renderer never paints a regression over a stable pane set.** The renderer gate is a last-resort latency hold; frame plausibility lives in the producer and row identity lives in projection. If a transient race the carry-forward missed — a momentarily agentless rollup, an old producer's empty stamped frame, or a frameless fallback after a frame-backed render — would erase or demote a stable row set, the renderer holds the last good frame rather than commit the regression. An agent-to-process demotion is held for the same pane only when the foreground command is unchanged or missing, the phantom-flicker or no-evidence signature; a command change means the agent exited in place and the pane returned to its shell, so the renderer commits it immediately. Count- and time-bounded escape hatches release held demotions and empty stamped frames so genuine exits still surface promptly when command evidence is absent. This is the read-side twin of the ledger's resumable rollup ([Runtime projection](./ledger.md#runtime-projection)): the persisted fold base keeps an agent from vanishing at the source, the producer keeps implausible frames out of cache, and the gate keeps a one-frame slip from reaching the screen.

When pane discovery itself fails, the renderer keeps the last good snapshot and, once the failure persists, raises the sticky health alert rather than inventing an empty room (see [Reload recovery](#reload-recovery)).

## Ranking and grouping

### Worktree groups

A worktree is total isolation — only same-worktree agents collaborate — so each group is one bounded block under a bold-teal header (the spines and seal are drawn in [the interface reference](../../interface/sidebar.md#worktree-groups-and-the-selection-lane)). Two rules the renderer enforces:

- **The header is a jump target** — clicking the name lands on the group's first row — and carries **no status tally**: the cockpit owns the fleet make-up, and each row carries its own glyph.
- **Git stats live on the header, not a row**, so shared-worktree changes never pretend to belong to one agent. The `+/-` churn is the worktree's total change against trunk — committed, staged, and unstaged from `git diff --numstat <merge-base with trunk> --`, plus the line count of its untracked files (read from the status probe under a shared per-refresh byte budget, binaries counting nothing like numstat's `-` cells), so work `git diff` is blind to still reads as churn — and the `⇡`/`⇣` commit delta is `git rev-list --count` over the same merge-base (`<base>..HEAD` ahead, `<base>..<trunk>` behind), so every number measures from the fork point. The Rimz worktree marker's `base_ref` separates pristine from merged: `HEAD == base_ref`, clean, and zero ahead/behind renders `≡ <trunk>`; clean, content-landed, and `HEAD != base_ref` renders the merge glyph plus `<trunk>` and no stats, even after fast-forward, squash, rebase, or merge-commit landing. Dirty, ahead/behind, unmarked, or trunk-moved fresh forks render as diverged. Local rebase/merge/cherry-pick state from git paths (`rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`) ranks above all PR markers and keeps the numeric stats visible. A producer-only `pr-state.json` probe calls `gh` or `tea` on a long TTL and consumers only read the cache; the trunk-glyph ladder is reconciling > local merged > PR merged > PR closed > PR open > plain branch. Gitea/Forgejo list output reports merged PRs as closed on some servers, so Rimz does one best-effort `tea pr <n>` detail read to upgrade closed to merged and otherwise leaves the marker closed. The trunk worktree itself (live branch == trunk) wears no pristine/merged verdict, since "landed on itself" carries no information. Zero components drop; empty when no git read reached the group.
- **The trunk resolves per repo, preference first.** The ladder tries the per-machine `[sidebar] trunk` ([configuration.md](../../reference/configuration.md#sidebar-rendering)) when it resolves in the repo, then `main` → `master` → the remote's advertised default; an option-shaped configured name (leading `-`) is never handed to git.

A pane's group is decided by the room's **group roots**, enumerated by the [root class](../../reference/cli.md#start-and-attach-a-workspace) (cached under `WORKTREE_ROOTS_TTL`, re-enumerated immediately on a session boundary): a repo room's group roots are its checkouts from `git worktree list` (even one parked outside the root); a directory room's are its **depth-1 child git repos** — one `read_dir`, a child qualifies when `<child>/.git` exists as a directory or a pointer file; a marker room follows whichever its root actually is (`.git` at the root means repo semantics). The reducer runs a lexical containment test and keys each in-room pane on the **deepest group root that contains its cwd**, so every pane of one checkout or child repo shares one pod — with one carve-out: a repo room's own checkout keeps per-path pods, so a nested worktree the enumeration hasn't caught up with never folds into the main pod. A deeper repo (`<root>/org/repo`) is not enumerated and folds into the room's root pod — the v1 depth rule; deeper scans need a depth and ignore policy before the fan-out is worth paying. In a non-repo room the panes the root itself claims form the name-only **root pod** (`SidebarWorktreeKind::Root`): the directory's basename in bold, no `⑂` fork glyph, no git story, excluded from every git read, and a stale branched row never relabels it. A cwd outside every group root — a home shell, `/tmp`, CI not tied to a worktree — folds into a catch-all that renders as a dim `┄ external ┄┄┄` divider, always sorts last — below even the inactive groups — and keeps an attention-only tally (`? n` / `! n`) so an out-of-project ask still surfaces from the tail. When the probe finds no group roots the reducer falls back to the project-root prefix alone — a marker-less scratch room degenerates to exactly one root pod.

### Attention ranking and the per-worktree cap

**Within a worktree agent cards lead, process rows form the command tail, and agent-card order reads in three layers: unseen work first, live work over dormant, then the most attention-hungry within each.** The comparators are [`compare_rows` and `compare_groups`](../../../crates/rimz/src/ledger/snapshot/view/layout.rs); the order they encode:

- **Layer 1 — unread leads.** A row turns *unread* when it enters `success`, `failed`, `waiting`, or `paused`, and no read mark reaches that episode ([read receipts](#unread-and-read-receipts)). The row stays in this band until you read it, even if the agent returns to `running` or `idle`, so unread is exactly the inbox of results, asks, and parked recovery states you have yet to see. Unread rows hold the top until seen, oldest-first, however they would rank below.
- **Layer 2 — active, then inactive, then external.** An agent row stays *active* until its `last_activity` ages past the inactive window — one hour by default, set per machine with `[agents.attention] inactive_after_secs` ([configuration.md](../../reference/configuration.md#sidebar-rendering)). Past that window the row is *inactive* and sinks beneath every live agent row whatever its status: one hour of silence is the same boundary the agent's own prompt cache crosses, so a card that has gone cold reads as cold and steps out of the way of the work in front of you. Process rows are exempt because their activity clock is foreground-process start rather than attention; an idle shell stays live presence, then seats below every agent card. The `external` catch-all — out-of-project shells and CI — forms a third partition that always tails, below even the inactive rows.
- **Layer 3 — the most attention-hungry rises, and nothing else moves.** Inside the agent partition rows order by attention requirement: `waiting` → `failed` → `paused` → `success` → `running` → `idle`; process rows are always last. Attention rows (`waiting`/`failed`/`paused`) sort **oldest-first** — a blocked agent's `last_activity` is frozen, so the longest-overdue rises and the `␣` triage key walks them in that order; a parked paused row stays visible attention but is not a read-space-key target. Calm rows (`success`/`running`/`idle`) and process rows hold **pane creation order** — the mux's own monotonic pane ordinal, ascending — so two equally-idle agents read in the order the backend laid their panes out (Claude's pane born before Codex's reads Claude-above-Codex), a working agent never jumps because it finished a tool, a renamed session never reorders, and a fresh pane appends at the bottom of its bucket.
- **Groups carry the same three layers, read off their most-urgent member.** A group rises to layer 1 while it holds an unread row, partitions active/inactive by its liveliest member, and within a partition leads with that member's attention bucket. Every calm status collapses to one rank there, so a calm group holds its place through its members' success/running/idle churn — only unread, attention, liveness, or external state reorders it. Same-rank groups keep their earliest member's pane-creation order, then label; `external` groups tail unconditionally, regardless of any attention member they hold.

Pane creation order replaces the earlier spawn key (`pane_process_start` with a `registered_at` fallback): that key read a different clock for each agent — Codex's process start against Claude's hook registration — and inverted co-launched panes whenever the two sources disagreed. The pane ordinal is one signal both agents share and matches what you see in the mux, so the sidebar order tracks the pane order until you reorder the panes yourself.

**The cap protects visible work.** Each worktree caps only its idle/process tail, showing up to `WORKTREE_ROW_CAP` rows from that tail with a dim `+K more` for the hidden remainder. Active, blocked, paused, finished, and focused rows are exempt and always shown, so a row that may need unread convergence or a direct jump target never disappears behind the count. A live process row also stays visible when it is the group's only live member, keeping the group in the live band while the ordinary inactive idle tail trims behind `+K more`. Inactive success rows stay visible for unread convergence.

## Composing the frame

The sidebar is **borderless** — it already lives inside a framed mux pane, so a second border would double-frame it and cost two columns. A title line, soft-gray `─` hairline rules, and a one-cell left gutter (which doubles as the selection lane) carry the structure instead. The on-screen layout is drawn frame by frame in [the interface reference](../../interface/sidebar.md); this section owns the invariants behind it.

Three structural rules the layout depends on:

- **Fixed height where it counts.** The repo dashboard (identity, the `◎`/`¤` summary with the configured headline token breakdown, and the count-up spend) and the cockpit make-up reserve their rows whether or not the room has agents, so the body never shifts vertically as agents change *state*. The footer and health alert are bottom-pinned chrome, reserved before the body so they can never scroll off.
- **Three zones, two pinned.** The frame composes as a top-pinned cockpit, a scroll viewport over the worktree groups, and the bottom-pinned chrome (dashboard, ledger, footer, alert). The cockpit ends with a pinned blank when cards are present, and the bottom chrome opens with one when a provider dashboard is present, so cards keep a fixed row of breathing room from both pinned zones while scrolling. The pinned zones reserve their rows first — bottom, then top — and the viewport takes the remainder, so the cards give way before either pinned zone is clipped. `UiState::scroll_offset` is resolved on every draw — clamped to the zone, then minimally auto-scrolled so the selected card (its group header and expanded subagent lines included, since they share the row's hit-test entry) sits fully in view, a card taller than the viewport pinning its first line to the top — and written back as a draw byproduct, like the hit-test map. A wheel tick pins a manual offset above the auto-follow — the browse pattern one layer down: the pin captures the selection it began over and ends the moment the selection genuinely changes, snapping the view back. A freshly-arrived actionable unread outranks the selection for the auto-follow: the viewport snaps to that row (it ranks to the top, so the snap reaches the top) and holds there — overriding selection-follow — until you engage (any keystroke, wheel, or jump dismisses it) or it stops being the [lead](#sub-agent-lists) (answered, read, or displaced by an older unread, which arms a fresh snap). The edge fires once per fresh lead, so a lead you dismissed is never re-snapped while it lingers, and a manual scroll pin is respected, so a new unread mid-browse never yanks the view. A pinned `↑ N need you` banner sits at the foot of the cockpit while any actionable unread waits — always visible regardless of scroll, toned by the lead's status — and routes a click to the lead (oldest) row through the line map, like a worktree header, so the agent that needs you stays one keystroke or click away even after you scroll past it. Opening `?` replaces the card body with a centered keys-and-legend block at the top of the body zone, suppresses the scrollbar, and lets the block own the viewport while it is up, so selection churn beneath it never pulls the view away mid-read; closing it drops any wheel peek and snaps back to the selected card. When the cards overflow, each visible line can carry the `▐` thumb / `▕` track glyph in the right-margin column the content leaves free — part of the composed line, never a new one, and the column reserved in every mode, so the hit-test map stays 1:1 with the frame at every scroll position. Whether the bar paints is the `[theme.display] scrollbar` mode ([configuration.md](../../reference/configuration.md#sidebar-rendering)): `always` whenever overflowing, `never` not at all, and the default `auto` only while the viewport is moving — each draw folds the resolved offset into `UiState`'s scrollbar fade as a write-back byproduct, a change stamps the animation phase, and the bar shows through a ~1s settle window after the last move (the baseline lives in the fade rather than `scroll_offset` because a wheel tick mutates the offset before the draw). The fade is ORed into the serve loop's animation gate like the money odometer rolls, so the hide frame always repaints.
- **Counts span the cap, the summary spans the spend window.** The cockpit make-up buckets sum each group's `status_counts` — counting even agents the cap hides; every `running` agent tallies as working (the thinking head is a per-row head, not a bucket). The summary's line 1 pairs headline facts — the `◎` sessions and the token breakdown read `[sidebar] spend_window` from the JSONL `value_tally`, not the live session sum — and line 2 carries the `¤` live-agent head-count, the steady unread count when non-zero, and the count-up spend.
- **The make-up line is the body's filter.** Each non-zero bucket is a click target that narrows the cards to its status; re-click clears, and a zero bucket emits no hit ([the look](../../interface/sidebar.md#zone-1--the-cockpit)). The keyboard-only unread lens uses the same storage and predicate but has no cockpit hit target. The renderer emits the bucket geometry in lockstep with the frame (`UiState::make_up_hits`, riding beside the dashboard's `tab_hits`; top-block hits are already absolute — the cockpit starts at screen row 0 — so they skip the bottom block's base translation). The pick (`UiState::make_up_filter`) is renderer-local display state over one shared predicate, `row_passes_filter`, consumed by both the body composer and the selection walkers — so the hit-test `line_map`'s row ordinals and the selection's indices can never drift. The cockpit counts stay full-fleet while the body narrows, and `reconcile_selection` clears the pick the moment its full-fleet count reaches zero — the body's twin of a dashboard tab pick ending when its panel leaves. A jump (`Enter`, `␣`, `1`–`9`, a card click) clears the pick as it fires: a status lens or unread lens is one tab's transient view, so it never outlives the jump that leaves the tab, and every tab's body opens at show-all when focus returns.

There are no feed-group sections: "Recently answered" and "Recent activity" do not exist here. The sidebar shows only what needs a decision or an action; full history lives in `rimz feed list --audit`. With nothing waiting or failed, the attention line is omitted and an empty room keeps the body clear under the cockpit and footer. An active health alert takes the body alone — an empty body under a failed fetch is a missing snapshot, not an empty room.

### Agent rows

Each agent is a small stacked card — identity and capability, then the description, the context meter, and (deeper) the token and work stats. The card anatomy and meter grammar are drawn in [the interface reference → the card](../../interface/sidebar.md#the-card); the invariants behind it:

- **Density resolves before row lines.** `[theme.display] card_density = "auto"` keeps the standard card shape: identity + description + the `▣` context meter + the `▤` context line, with subagents on the selected row. `expanded` keeps those same resting lines and shows subagents on every parent card. `compact` trims resting agent cards by status — idle to identity, running/waiting to identity + description + meter, paused/success/failed to identity + description — while the selected compact card opens to the full auto shape.
- **Auto and expanded selection only append, never reshape.** Every line of the resting card renders identically whether selected or not; selection paints the bold `▌` spine over the gutter and *appends* the deeper lines, so the card never reflows on expand. Compact is the scoped exception: a resting compact card is intentionally shorter, and selecting it reflows it up to the full card so the focused pane still carries the complete context read.
- **Capability is preferred, never guessed.** Model display names come from the session's rich [context](../agents/agent.md#rich-context-agentcontext) when present, falling back to local model scalars; a synthesized idle lazy-agent row may use an adapter-owned launch default until the session reports its model. Reasoning effort prefers the hook/ledger scalar because that is the user's configured value, with context only as a fallback ([transcript/local scalars](../agents/agent.md#two-sources)). A missing field means "the agent did not report it," never a zero. Model names drop a trailing window qualifier for the row (`Opus 4.8 (1M context)` → `Opus 4.8`); the window itself rides the identity line's dedicated token (`258k`, `1m`). The account-scoped budgets are **not** on the row — they live in the [provider dashboard](#provider-dashboard).
- **Line 1 carries no timestamp.** A blocked `?`/`!` starts at the yellow floor and heats continuously with the age clock through the warn→caution→alarm ramp, while its blink follows one clamped tempo: slow when fresh, faster as it ages — a hard 2-pole strobe by design. An unread `waiting`, `failed`, `paused`, or `success` row blinks its lead glyph, name, and description together on the deeper blink until read, using the row's status tone. The cockpit make-up `?`/`!`/`⏸`/`✓` buckets blink only while a matching row is unread, on that oldest unread row's age-paced cadence; the unread count, read buckets, and per-bucket counts hold still. A working agent's animated head signals liveness; a running row that records no activity past the configurable stall window (30 minutes by default, `[agents.attention]`) projects to `!`, while an existing attention row escalates by color and cadence in place rather than by a clock. The one coarse last-activity age rides the context line, pinned right, only once it crosses a full minute, toned by the same age ramp in [the glyph legend](../../interface/sidebar.md#reading-the-glyphs) — a delegating parent's age reads the freshest of its own and its children's activity (the [sub-agent fold](#sub-agent-lists)). Width tiers degrade line 1 — a narrow row keeps just the name, wider rows add the model, then effort — while the context meter keeps its label and value at every width.
- **Enrichments are display-only and privacy-gated**, and none drives attention or routing. Context severity is one four-tier ramp — calm green → yellow → amber → red — taken as the worse of a fill-percentage band and an absolute-token band, with `[theme.display.context_meter]` stops for where green starts warming and where yellow, amber, and red are reached ([configuration.md](../../reference/configuration.md#sidebar-bands)), so a large-window model calm by percentage still warms by sheer volume. The tier is classified once, in the domain ([`ContextSeverity::classify`](../../../crates/rimz/src/agents/state.rs)) where the config folds onto the snapshot, and stamped on each row (`SidebarRow::context_severity`); the renderer maps the row's position inside those stops to a continuous tone. The bar, the `▣` glyph, and the `▤` context-line head all wear that one tone, and when the per-message breakdown is known the bar splits into composition segments (cache reads, cache writes, fresh input) whose markers also appear on the context line — the line is the bar's legend. `NO_COLOR` suppresses color only; every bar's heavy/light and filled/hollow shape still carries the meter.

Rows are base identity plus one card payload: [`AgentCard`](../../../crates/rimz/src/ledger/snapshot/row.rs) for lifecycle/ask/context fields, or [`ProcessCard`](../../../crates/rimz/src/ledger/snapshot/row.rs) for command/process metrics. The grouped snapshot adds per-group `status_counts` and git fields (`diff_added`/`diff_removed`, `commits_ahead`/`commits_behind`, `trunk`, `trunk_sync`, `pr_state`). Three projection rules are not evident from the field catalog: the renderer prefers the rich `context` blob over the coarse model/context scalars but prefers `row.effort` over `context.effort`; Codex line 2 starts with app-server `thread preview → thread name`, then absent Codex thread metadata and other agents fall through `session name → task → prompt → em dash`, so rows keep a label once the turn ends; and the display preferences ride `SidebarSnapshot.sidebar`, filled by the enrichment fold like `project_root`.

#### Unread and read receipts

Unread state is a durable runtime episode set plus runtime read receipts. The elder opens `unread.json` episodes for rows whose displayed status is `success`, `failed`, `waiting`, or `paused` when no read mark reaches the row's `last_activity`; every producer and consumer fold derives `SidebarRow::unread` from that file plus merged read marks. The first reconciliation when `unread.json` is absent opens current attention rows silently, so attaching to an already-busy room shows unread cards without replaying a push storm. The fold stamps the durable unread bit before row ranking and capping, so a row that recovers to `running` or `idle` still stays visible and emphasized until read.

Focusing the row's pane writes a renderer-owned receipt to `read-marks/sidebar.<instance_id>.json` with `row_id → cleared_at_ms` and clears the current frame locally; focus-clear applies only when the tab's active pane is also one of the panes an attached client is actually viewing, so background tabs keep unread until visited or explicitly marked. Switching into a tab writes the same renderer-owned receipt for every unread sibling in that tab and traces those clears as `tab_view`; the sweep fires only on the off-screen→on-screen edge, so staying on a tab leaves a newly-unread sibling unread until you leave and return, and attaching to an already-viewed tab seeds the latch without sweeping. `rimz sidebar mark-read` writes the room-durable `read-marks/manual.json` receipt for scripts and tests and removes any open episode that receipt reaches. Every fold loads all read-mark files and merges the maximum clear time per row; a receipt clears an unread episode only when `cleared_at_ms >= episode_ms`, so an old focus clear cannot erase a later turn. The renderer or CLI that writes the receipt traces the human clear as `focus`, `tab_view`, or `mark_read`; the elder prunes read-reached episodes from `unread.json` without a second clear trace and traces only row-gone pruning. The `m` key marks the selected row read **without focusing** it: the renderer writes the same durable manual receipt, clears the row locally for an instant repaint, and refetches so the next produce re-derives it read; the elder prunes the episode. `M` (and `rimz sidebar mark-unread`) opens a new episode through the shared [`sidebar::unread::mark_rows_unread`](../../../crates/rimz/src/sidebar/unread.rs) — the one mark-unread write path, used by the CLI and the renderer alike — stamped at `last_activity.max(now)` so no read receipt can reach it and the elder's reconcile keeps it, which is what makes the write safe from any tab, elder or not. Renderer receipt files are disposable runtime sidecars that outlive renderer exit long enough for peer folds; orphan sweep and `rimz gc` remove stale files only after the owning sidebar heartbeat has expired. The manual receipt is not tied to a sidebar heartbeat, so a detached-room `mark-read` survives until the room runtime is reset or collected. Cross-tab convergence is bounded by the next data fold, typically one pull tick or a wakeup-triggered fold.

#### Future — agent signals

The stamped verdicts are hook-ready: `ContextSeverity` is classified once and rides each `SidebarRow`, so a future hook flow reads the same tier the sidebar paints. The path is hook-side emission → feed event → resolver: a producer-side detector (or a dedicated hook) emits an [`AgentSignal`](../../../crates/rimz/src/agents/state.rs) — `ContextSeverity { from, to }` on a tier crossing, `Attention { status }` on entering an attention state — into the existing **feed**, the decision bus the resolver chain already drains ([resolvers.md](../agents/resolvers.md)); an enrolled resolver matches the signal and acts (`rimz pane send /compact` at amber), exactly as the pane-send reference resolver acts on a recognised prompt today. Resolvers + the feed are the bus; the typed verdict and signal shape exist now, while emission and handling are deliberately unbuilt.

#### Sub-agent lists

The expanded card lists the subagents the agent spawned this turn — each leading with the agent-row head vocabulary (the thinking head while the child's `phase` reads reasoning, the working fill while it acts, the static `✓`/`!` verdict once it finishes) plus its type and, when Claude's `subagentStatusLine` has reported it, the description of what the parent asked it to do, with the token spend `◇` (the card's whole-unit figure), the child's model and reasoning effort, and elapsed work on a second indented line — the metadata composes one per-card grid, the figure right-aligned and the model padded to the widest sibling with a missing field blank-filling its slot, and the clock-fill glyph `◔`→`◉` over a fixed three-cell `m`/`h` label (`<1m` under a minute, never seconds), toned by the parent's age ramp — so the second lines stack into columns across children. A subagent has no pane of its own, so it never renders as its own row ([Presence model](#presence-model)); instead the rollup carries each child's `parent_agent_id` and the snapshot nests it under its parent at projection time. This is a display-layer rule: the rollup retains children with the parent, and the sidebar projection reapplies the turn-scoped list boundary before painting them. The list orders by **creation time ascending** (`registered_at`, the rollup's spawn/registration instant; children with none last, id tiebreak) — spawn order, stable across refreshes, where an activity-keyed sort reshuffled on every tick. Density decides where the list paints: `auto` and `compact` show it on the selected parent, and `expanded` shows it on every parent. Retention is **turn-scoped** with the ghost-session TTL as the no-boundary backstop: a live running child stays listed while it belongs to the parent's current turn, and a *finished* child holds its `✓`/`!` verdict on the list until the parent records the next stamped prompt boundary (its work predates the parent's `turn_started_at`); parked starts, including Claude's wake and a rare real prompt entered before the parked turn resolves, resume the current boundary, so the verdict remains listed through that parked cycle. A context reset that rests the agent stamps the boundary the same way a fresh prompt does: a manual `/compact` (a `CompactionEnded` landing on idle) and a `/clear` (`Registered`) each advance `turn_started_at`, so the parent's prior-turn children clear the moment it compacts or clears. Automatic compaction mid-turn resumes the same turn and holds the boundary, so an in-flight turn keeps its children. If the parent never recorded a turn boundary, the same generous TTL prevents a finished child from lingering forever. A child whose parent row is absent is an orphan and never renders.

The description, token count, and start time are paneless enrichment a child cannot publish for itself: the feed harvests them from Claude's `subagentStatusLine` (Claude-only) into a per-child sidecar, and [`with_subagent_context`](../../../crates/rimz/src/ledger/snapshot/view.rs) folds them onto the child's `AgentState` by `(kind, agent_id)` before projection — mirroring `with_agent_context`. The fold lands on the rollup, not the projected `SidebarSubAgent`, so it survives the group rebuild. Elapsed work is frozen at projection (`now − started` while running, `last_activity − started` once finished). The model, reasoning effort, and turn phase ride the other channel — the child's own lifecycle events, carried forward on its `AgentState` like the parent's — so they show wherever an event named them, sidecar or not (Claude reports a child's effort on its `SubagentStop`, so the effort token typically lands as the child finishes). A child with none of it — a Codex child, or a Claude child before its first render — degrades to the bare type line.

**Child activity counts as the parent's.** At the same projection chokepoint ([`fold_child_activity_onto_parents`](../../../crates/rimz/src/ledger/snapshot/view.rs), after the nest, before the displayed-status projection) the freshest child `last_activity` advances the parent row's *displayed* clock — so the card's age stays honest while the children work, and the stall check reads the folded value (a parent whose child just finished never false-stalls). The fold is display-only and twice-guarded: the rollup keeps the parent's own clock (so [`agent_moved_past_ask`](../../../crates/rimz/src/ledger/snapshot/view.rs) still recovers a settled ask and a blocked parent stays waiting), an attention row's frozen heat is never re-clocked, and a [turn-death marker](../agents/agent.md#liveness-and-presence) always beats a still-ticking child.

### Process rows

A pane no agent has stamped renders a bare command row: a lead glyph then the program it runs (`zsh`, `vim`, `cargo`), the whole row one step below the agent cards — rows always sort agents-first, and that recessed tier (a DIM-weighted lead and the gray `body` tone on the name, which falls back to the DIM weight under `NO_COLOR`) is what reads the worktree's command tail apart from the agents above it. The program is read past a `sudo` wrapper and through a `node`/`npx` launcher to the script it runs, so `sudo npm install -g @openai/codex` reads as an `npm` install (never a codex agent) while `node …/codex` or `node …/claude/cli.js` reads as the pre-enrichment agent host. A launcher process name alone is not identity: bare `node` waits for a script path, and `/proc/<pid>/comm` is a fallback only for precise agent process names, never for generic launchers. The lead is `ProcessState`: idle panes use the quiet hollow `○`, busy panes use the working braille spinner, and stuck panes use the attention `!` when `/proc` reports a zombie or repeated uninterruptible sleep. An **active** pane anchors its primary line on the shell that owns it (its root process, read from `/proc/<pane_pid>/comm`) so the line stays put as commands come and go, and carries the live command in full on a second line. At L2 (≥44 cols) width a working or stuck row right-pins `C  n%  M  nG  ⇅  nM/s` on line 1 — CPU, RSS, and combined VFS I/O rate as one fixed-width grid, each marker in its own DIM-weighted tone (`C` sky, `M` sage, `⇅` violet), each figure right-aligned in its dim slot, so the grid reads whole from the first visible reading and the cluster never wanders as values change; an idle `○` shell or editor stays bare even when sampled values exist. The producer samples from the shell's single foreground child (falling back to the shell pid) on its own [sampling cadence](./state.md#pull-tick-table), and the whole cluster stays absent until CPU, memory, and I/O have all reported: two-sample rates need a prior reading, partial reads stay hidden, and non-Linux has no cluster. Both reads key off the pane's root pid: tmux reports it natively (`#{pane_pid}`), and Zellij reports none, so the producer derives it from `/proc` ([`backfill_zellij_pane_pids`](../../../crates/rimz/src/sidebar/produce/metrics.rs)) — every pane root is a direct child of the session's `zellij --server <socket>` process (socket named after the session), and Zellij reports a pane's foreground command as that process's cmdline. Known/restored roots are claimed first and removed from sibling candidate sets; a pidless pane then matches the server forest's one remaining process with that exact cmdline (the working directory breaks a tie between same-command candidates; a unique match binds without a cwd check, since an agent may chdir into its worktree) and walks up to the direct server child. An ambiguous pane — two idle shells in one cwd — abstains and shows no stats: no stats beats a stranger's stats, and an active pane's foreground cmdline is almost always unique. No capability line, no attention count; a process row never enters the cockpit tallies. It is still a jump target, and once an agent's hook stamps that pane id the same pane becomes that agent's row.

When a pane's foreground command starts through `sudo`, `su`, or `doas`, the producer runs a bounded descendant scan below the pane root. If it finds a known agent CLI running as another real uid, by cmdline or precise `/proc/<pid>/comm`, the row relabels to that agent kind, carries a dim `(<user>)` marker, and keeps the wrapper command on the detail line, for example `claude (root)` above `sudo su`. The row remains a process row: it contributes no cockpit tally or provider-dashboard account, and the elevated hint never rewrites `pane.command`, so cwd recovery and idle synthesis refuse it as a foreign-user agent.

### Jump — the row is the link

You don't read where to go; you go. Selecting a row focuses that agent's pane via the `pane` ref on the snapshot — no mux pane number is ever printed. Both renderers share one key model:

The full key table is the [interface legend](../../interface/sidebar.md#jump--the-row-is-the-link); the mechanics it leans on live here.

- `↑/↓`/`k`/`j` browse the selection, `K`/`J` and `g`/`G` jump it across worktrees and to the ends, and `↵`/`l`, a digit `1`–`9`, or a click jump (focus the pane). The mouse wheel scrolls the card viewport without moving the selection ([Composing the frame](#composing-the-frame)); the next selection change snaps the view back.
- `n`/`N` (and `␣`, an alias for `n`) walk the *inbox* — the next/previous item that needs you, unread needs-a-look rows oldest-episode-first then read attention rows oldest-first — and focus it. One directional walk over a single ordered candidate list ([`step_attention_index`](../../../crates/rimz/src/sidebar_pane/app/selection.rs)), bound only inside the Rimz session so it never touches the user's global mux config.
- `m`/`M` mark the selected row read / unread without focusing ([read receipts](#unread-and-read-receipts)).
- `←`/`→` cycle the [provider dashboard](#provider-dashboard)'s provider tab; `x` dismisses the recovered [health alert](#reload-recovery); `r` reloads (re-exec on a fresh on-disk build, else a forcing refetch); `?` replaces the body with the centered keys-and-legend block.

While a make-up bucket or the unread lens is picked ([Composing the frame](#composing-the-frame)), the visible universe is the filtered one — selection, the inbox walk, `1`–`9`, clicks, and the scroll auto-follow all walk only the matching rows.

The room-scoped **focus key** reaches the sidebar from any pane: `[sidebar] focus_key` (default `Alt+p`) is a toggle that runs `rimz sidebar focus --toggle`. tmux binds it at session birth as a root-table `bind-key`; Zellij runs it from the presence plugin's `focus_sidebar` pipe ([multiplexers.md → Focus key](./multiplexers.md#focus-key)).

The native renderer focuses the bound pane directly, in process (`rimz::mux::backend_for(..).focus_pane`) on a detached thread; a click anywhere in a row's multi-line block jumps via a hit-test line map the renderer emits in lockstep with the body. The jump records a local `FocusChanged` intent beside the one-way mux focus command, so the highlight moves in the next fold even when a backend's raw focus marks are contested. **Every jump reconciles pane id *and* `pane_process_start`**, so a reused id never silently focuses a stranger — it self-corrects on the next snapshot rather than blocking the jump. The row routes you to the pane; the prompt and its approve/deny live in the agent's pane, where the full context is. A script's `feed ask` is the exception: it chose Rimz as its surface, so its declared options are answerable on the row.

#### How the highlight stays on the right pane

**Selection is derived state, scoped to the sidebar's own tab.** The baseline is the own `TabFrame`'s **active working pane** — the non-sidebar sibling named by `TabFrame.active_pane` ([multiplexers.md → Two kinds of focus](./multiplexers.md#two-kinds-of-focus)), filtered to a visible row — re-derived from the frame on every fold (`SidebarOwnView::active_pane_id` → `app::reconcile_selection`), and retargeted between pulls by a fused `FocusChanged` overlay ([state.md → Fusion Rules](./state.md#fusion-rules)), so on Zellij the highlight follows a focus move on arrival rather than on the next pane read. When a client is viewing the tab, `TabFrame.active_pane` comes from that client's focused pane; when the tab is unviewed, it comes from plugin focus or deterministic fallback. Same-tab by construction and one deterministic value per tab however many clients attach — which is the only shape a sidebar pane (shared content, one buffer for every viewer) can render. Selection cannot desynchronize, only lag a frame: an external tab switch or focus move lands on the next fold, and a `None` derivation (the sidebar itself focused, a non-row active pane, or an already-baselined own view whose raw focus marks are contested) *holds* the last baseline rather than blanking it. Selection is keyed by pane identity, not row position (`UiState::selected_pane`), so a status-churn reorder re-anchors the highlight to the same pane.

One transient local layer rides above the baseline:

- **Browse** (`↑`/`↓`) pins a pick *without* moving focus and may roam every visible row — another tab's included, so any card is one keystroke from expanding. It ends when the derived baseline genuinely changes from the value captured when browsing began; an inert (`None`-derivation) frame never ends it.

A jump (click / `↵` / digit / `␣`) fires the one-way focus command and records the same pane as a local focus transition. Cross-tab, the destination tab's sidebar receives the broadcast transition and its own baseline still derives from the next resolved view focus; the source tab reconverges on its next fold the same way. A jump mid-browse leaves the pick in place, so the highlight holds still until the baseline takes over on the same pane.

### Provider dashboard

Provider budgets are **account-scoped, not session-scoped** — every session of a provider shares one account's included windows and paid-usage state — so they lift off the rows into a pinned per-provider dashboard at the bottom, bracketed by hairline rules above the footer. With several accounts the dashboard is **tabbed**: its top hairline becomes a tab rail — the agent-kind labels set into the rule — over one block at a time, so the budgets read one account deep instead of stacking; a single account keeps its bare block under a plain rule, no rail. `[theme.pets] enabled = true` keeps provider dashboards tabbed while provider blocks exist, with provider labels packed left and one renderer-local pet column overlaid to the right of the active block ([pets.md](./pets.md)); with no provider blocks, the pet renders alone in the dashboard area. How each provider panel's account, plan, metered flag, stable windows, and paid/API row are sourced and aggregated is [provider.md](../agents/provider.md) (which also owns the stable provider order and the cap); this section owns only the painting and the tab focus.

- **Tab focus is derived, with a manual layer.** The active tab follows the selected pane's provider — the selected row's agent kind, falling to the first tab for a process pane or an empty selection — so glancing at the dashboard reads the account behind the agent you're on. `←`/`→` (wrapping) or a click on a tab label pins a manual provider pick above that default; the pick ends exactly like a [browse](#how-the-highlight-stays-on-the-right-pane): when the selection-derived kind *genuinely* changes from the value captured at pick time (a process-row selection derives nothing and holds it), or when its tab leaves the dashboard. Each provider tab label — the kind slug, first-char-capitalized — wears its provider brand color; the active provider paints as a chip (dark ink on its brand fill, bold). The rail's glyphs are identical whichever tab is active — every tab reserves a rail cell and a pad space on each side of its name — so a pick moves as fill and weight alone, never a glyph; under `NO_COLOR` the fill drops and `┤ ├` caps paint into the active tab's reserved cells as the pick's shape. The rail names the account on provider tabs, so the tabbed block's header drops the product name and reads plan-first (`Claude Max · v2.1.158`), indented to the stats column directly over the `◎` line.
- **Mana bars and the shared grid.** Budget bars use a light segmented style (`▰` filled = remaining, `▱` track in the dim chrome) and drain green → yellow → amber → red by remaining budget on the `[theme.display.budget_bar]` zones ([configuration.md](../../reference/configuration.md#sidebar-bands); amber is the caution rung for stepped budget and context severity); each included window's label (`5h`/`7d`/`30d`) wears its bar's tone and the `↻ reset` value reads at the quiet soft tier. The label slot and the value column are fixed-width, so every provider bar shares one front and one end column and the dashboard reads as one aligned grid. A fully-spent window turns its whole track red rather than the resting gray, and a spent longer window gates the shorter ones — an exhausted `7d` forces the `5h` row to the same red, no countdown. Paid extra usage uses `ex`, API-key spend uses `api`, and unknown or uncapped paid usage keeps the same dim empty track with `∞` in the value slot. Below a narrow width the emblem drops and the bars run full-width.
- **The stats line speaks the ledger vocabulary.** Each block's first body line reads the configured headline `◎` session count then the `◇ ↘ ↗ ◌` token breakdown — the fleet ledger's exact format, scoped to the provider, with cache creation folded into `↘` input — and the spend pinned right. The row stays one row across wide, normal, and narrow layouts; normal and narrow drop the `↘`/`↗` split only when the provider column would otherwise crowd, and the narrowest header also drops version trivia before clipping the account facts.
- **Brand styling is config-driven**, resolved producer-side from `[theme.providers.<kind>]` over built-in defaults — see [theme.md](../../reference/theme.md#provider-styling).
- **Remote control is a flag, not a row.** Remote-control hosts are infrastructure, so the snapshot filters the Claude host pane and the Codex app-server broker out of the room and paints a violet `⇅ rc` flag on the provider block instead. The flag has two sources: Rimz's `[remote_control]` auto-launch toggle for that kind, and a provider-owned pane-session setting when the descriptor declares pane remote control (Claude's `remoteControlAtStartup`). `rimz start` preflights configured hosts and refuses with the fix when an installed Claude host is blocked by settings, version, or auth; a missing Codex standalone install is skipped, and `rimz doctor` reports the install fix.
- **The fleet ledger seals the bottom.** Below the last account block (or, with no block, its own hairline) a `Total:` delimiter pins above trailing-week `W:` and trailing-month `M:` totals fed by `SidebarSnapshot::value_tally` (the [`SpendTally`](../../../crates/rimz/src/agents/spending.rs) the spending enrichment computes). Wide rows read `◎ sessions  ◇ total ↘ input ↗ output ◌ cache-read  $spend` behind a one-cell lead pad, with `↘` input including Claude/Pi cache creation and every numeric field right-aligned into one shared grid so the `W:`/`M:` labels stack and each column lines up. Normal and narrow provider blocks use the taller layout: a blank row above `Total:`, two token rows with `W:`/`M:` session clusters left and token stats right, then a third row with `W: $...` left and `M: $...` right. The figures are **static** — the precise one-decimal token form, the exact record beside the cockpit's coarse live read; the count-ups live above, the configured headline `$` in the cockpit and each card's `$cost`. The windows escalate `headline → week → month`.
- **The money counts up.** The cockpit headline `$` (its own right-pinned line under the `◎`/`¤` summary) and each agent card's `$cost` **climb** on an increase as an eased odometer roll: every jump sweeps an ease-out cubic across a fixed six-click window — each click two base frames, so 200ms per click and 1.2s end to end on the default grid, whether the jump is three cents or five dollars — so big first steps decay into a penny-sized landing on the exact two-decimal figure (a small jump lands early once rounding reaches it), with a one-click brighten as it settles. `UiState::tally` (`render/odometer.rs`) holds the cockpit's roll and `UiState::cost_rolls` one per card — keyed by the row's durable id and pruned with the roster — the producer-side fold seeds every target on each refresh, and the renderer reads the eased value at `animation_phase`. A roll keeps the animation tick warm only while in flight (the serve loop ORs both `any_rolling`s into its animation gate, and money-only motion samples on the matching money grid, `refresh_ms × CLICK_PHASES` — [state.md → Render Cadences](./state.md#render-cadences)), so a settled figure costs nothing; an unchanged target re-observed is a no-op — refolds land on every ledger wakeup, and re-anchoring would snap a climb in flight and erase the settle flash — while a decrease (calendar-day or session reset) and the first paint snap, never roll. **The cockpit's headline tracks the cards live**: its target is `SidebarSnapshot::today_spend_live_usd` — the walked figure plus each live session's overshoot over the room-local baseline captured when the shared walk stamp advances ([`today_spend_live_usd`](../../../crates/rimz/src/agents/spending.rs), applied by `apply_live_today_spend` in both the producing CLI and the consumer fold) — so a context sidecar push retargets the headline in the same fold that moves the card's `$cost`, and each `SPENDING_TTL` shared walk re-publishes the exact floor while each room refreshes its own `live-spend-baselines.json` sidecar (the [enrichment cadence](./state.md#pull-tick-table)); a session that ends mid-window rests the headline back on the walked floor until the next walk absorbs its spend. The figure is presentation only — the [`SpendTally`](../../../crates/rimz/src/agents/spending.rs) and the per-session cost are the truth, the roll and the overlay transient layers toward them.

The tabs are the panel's only hit targets — a click on one switches the tab in place, never a jump; everything else in the dashboard stays inert in the hit-test map. The renderer emits the tab geometry in lockstep with the frame (`UiState::tab_hits`, the tab rail's twin of the row `line_map`), and the rail holds to one screen row — a tab that would overflow the panel width drops whole, label and hit together, so the map never desyncs however many kinds register.

## The runtime loop

### Launch model

`rimz`, `rimz start`, and cwd-based `rimz attach` ensure the workspace session exists, then launch one sidebar pane best-effort before entering or printing the attach command. Both backends run the same native renderer through `rimz sidebar serve`:

- **Zellij** is born from a layout — a left `rimz-sidebar` pane at the launch's width verdict plus a focused terminal — which doubles as the default tab template, so every tab is born with a sidebar. Rimz touches the layout only at creation; an existing session is a no-op.
- **tmux** splits a left sidebar into the initial window, and an `after-new-window` hook re-runs the same split so every later window is born with its own sidebar — the tab-template parity Zellij gets from its layout.

Launch is **idempotent by heartbeat**: before opening a pane Rimz scans `runtime/heartbeat/sidebar.*.json` and treats only readable, current-protocol, fresh files as live, so a crashed or upgraded sidebar does not suppress relaunch. A launch lock serializes the check-then-spawn so concurrent attaches to one session don't each spawn a daemon, and the sweep removes orphaned heartbeats, sockets, and read-mark receipts a SIGKilled sidebar left behind.

`rimz reload` is **user-wide and cwd-independent** — it runs from anywhere, even outside a session. It enumerates every workspace under the state dir (`known_workspaces`) and, for each whose mux session is live, converges it to **one healthy sidebar per working view**: it sends the version-stable `reload` control word to live sidebars, waits for build-stamped heartbeats to prove each located pane is now running the on-disk binary, and feeds only current-build heartbeat claims into the reconcile fallback so a renderer that misses the in-place reload is closed and re-added. A sidebar already on that build compares byte-identical and refetches in place instead, so an unchanged install never churns its pane. The same pass closes duplicate or unresponsive sidebar panes (any a fresh current-build heartbeat does not claim by pane id, graced by two heartbeat windows for a just-added pane whose serve process is younger than its first heartbeat — so back-to-back reloads never churn what the previous run added), converges a kept sidebar that sits outside the full-height left dock — moved back to the left column, the one-right-column nested row stacked into the right column on Zellij 0.42.0 and newer, the same narrow shape closed and verified-readded on older supported Zellij builds when in-place repair cannot verify the dock, and resized toward the layout width — with a tolerant trigger (off the left column, a tiled terminal intruding into the sidebar's column band, wider than the configured `max_cols` cap, or under the cap but wider than 45% of the tab) so a healthy layout-born width — including a cap-wide fixed birth on a narrow client — is never churned (tmux births every sidebar left at width synchronously, so convergence is Zellij-only repair), re-adds a sidebar to any working view left without one — discovering the mounted pane from the live pane list rather than trusting the spawn command's output, verifying the same full-height dock, and cleaning up only a mounted fresh sidebar pane proven by listing so a cross-talked stdout hint cannot close user work (Zellij's `new-pane` answers before the mount: [multiplexers.md → Zellij backend caveats](./multiplexers.md#zellij-backend-caveats)) — reports any persistent working-but-mis-docked sidebar, collapses an orphan sidebar-only view — a wedged renderer whose working siblings all closed but which never self-closed — by closing its sidebar pane, and reaps orphaned sidebar *processes* whose pane the mux no longer lists — all in place, never rebirthing the session, so the user's panes survive. The daemon view (`rimzd`, a sidebar and configurable content beside the managed hosts) converges the same way — a missing sidebar is re-added beside its content/hosts area — but is never collapsed: its hosts are managed, not work, so it can never read as a sidebar-only orphan. On Zellij the view classifies by its tab name plus each pane's spawn command (`terminal_command`), the two signals `list-panes` still reports after the Claude host re-execs. A workspace whose session has stopped has its stale heartbeat/socket files and leftover daemons swept instead. Each pass is best-effort and run-once; a view that fails to gain a sidebar is logged and left alone. On Zellij an add or geometry repair in a *detached* session is deferred rather than attempted — the detached screen thread drops mounts and relayouts while spawned renderers keep running, so reload reports the deferral and the next reconcile against an attached client performs it; tmux mounts splits detached, so it never defers.

### State access

Data flow is [state.md](./state.md)'s domain: the node model, producer election, the published-file inventory, typed realtime events and push channels, fusion, render cadences, and the pull-tick cadence table (values in [`sidebar/timing.rs`](../../../crates/rimz/src/sidebar/timing.rs)).

This doc keeps the liveness contract: each renderer writes its own heartbeat in process and binds a per-instance wakeup socket; heartbeats carry workspace, session, mux, instance id, protocol version, socket path, pane id, build id when ready, and last-seen timestamp. The renderer receives the fused `SidebarSnapshot`; selection, self-close, reload recovery, and drawing stay in this doc.

### Drawing and effects

Base composition owns the row animation: the gentle read pulse is an OKLab lightness ramp on the row glyph (quantized to xterm tones in 256-color mode), while the deeper unread blink hard-toggles the lightness between the resting tone and a bright crest, held bold the whole cycle — a 2-pole square wave, not a swell — across the lead glyph, the card name, the description, and the make-up `?`/`!`/`⏸`/`✓` buckets, so the unread blink reads as a clear on/off in every depth; `NO_COLOR` keeps the shape plus the on-pole bold weight. A **color-only effects pass** (`render/effects.rs`, tachyonfx one-shots) runs inside the same draw, after the paragraph render, only for transition flashes — a card entering `waiting`/`failed`, an ask resolving, a pause lifting, a new card arriving, the spine under a freshly landed selection. Transitions are detected by diffing each frame's rows and selection against the last observed frame (`EffectState`, riding `UiState`; the first observation records without spawning), and every effect re-resolves its target from the hit-test `line_map` each frame, so it follows its row through reorders and scrolling and drops when the row leaves the screen. The pass is gated on `Theme::effects_enabled` (`NO_COLOR` off, plus the `[theme.display] glow` mode riding the snapshot) and mutates cell colors only, never a glyph — locked by the `effects_pass_never_changes_the_composed_text` golden guard, so the composed grammar and every `.snap` stay byte-identical with the pass on or off. Base palette depth is separate: ``theme.mode` = "auto"` emits RGB tones on truecolor terminals and quantized 256-color tones elsewhere. A terminal resize is also a wakeup — a watcher turns `SIGWINCH` into a socket nudge — and repaints through the synchronous input path; the one deferral is the grow-resize hold described under [self-close](#self-close).

### Self-close

A sidebar shares its tab with the user's working pane(s) and has no reason to outlive them. Each snapshot fold counts the panes in its view from the shared pane frame; topology signals, including Zellij `PaneClosed`, ask the elected producer for a fresh frame, and the producer's `PaneFramePublished` event makes consumers refold it immediately without forking their own mux probes. The count reads the published frame alone — a fused `PaneClosed` overlay deletes its card on the spot but never moves the sibling count, so an exit verdict always rests on a producer-verified frame ([state.md → Fusion Rules](./state.md#fusion-rules)). The periodic self-close watchdog requests the same shared snapshot path as a poll backstop. The fold identifies the sidebar's own pane from the mux env var and never uses `pane capture`/`send`. Once it has seen at least one sibling, a later drop to zero means the last working pane exited: the renderer exits and its `close_on_exit` pane closes. A startup latch keeps it from exiting before the terminal pane first appears. This is backend-agnostic. When pane discovery itself stays broken the sibling count is unknowable, so a degraded renderer leaves through the give-up exit in [Reload recovery](#reload-recovery) instead.

Closing the last sibling first grows the sidebar to the freed full width, so the close is choreographed to avoid a one-frame full-width flash: a grow resize holds its repaint until an accepted pane-frame fold carries the sibling-count verdict, either through an explicit fresh-pane result or through a pane observation stamp at or after the resize signal. A "close" verdict exits without painting the grown frame; a "stay" or unknowable verdict releases the hold and paints at the new size. A lost wakeup or continuously rejected frame cannot suppress drawing forever: the grow hold expires after `RESIZE_PAINT_HOLD_CEILING` (2s), at which point the renderer may paint the grown frame while the normal self-close watchdog continues requesting the verdict. Shrinks and same-width resizes remain immediate redraw signals while the normal producer-fresh pane path verifies topology.

### Reload recovery

The sidebar keeps the last successful snapshot across iterations. When the in-process produce or the heartbeat write fails — a vanished ledger directory, a dead mux, a transient discovery hiccup — the loop:

1. Reuses the last snapshot for the current draw, falling back to an empty placeholder only when nothing has loaded yet (a cold start after a workspace move).
2. Absorbs a single flaky fetch silently — the last good frame already covers it, so one blip never flashes a banner.
3. Once the failure persists past the debounce, raises a sticky **health alert** pinned to the bottom edge (status-bar style) — `! Sidebar degraded for 8s: snapshot failed: ledger not found` — with a monotonic "for Ns". The body is truncated before the alert is ever clipped, so the notice can never scroll off.
4. On recovery, lingers as a dim `⚠ last alert 8s ago … · x dismiss` notice rather than erasing, so a failure that flickered past is still visible; `x` dismisses it, a fresh failure re-arms it. While the alert is active the body, footer, and help overlay step aside and let the alert speak alone.
5. Gives up if the failure never clears — a failing heartbeat write, a vanished ledger, a mux that stays dead. A renderer continuously degraded past `GIVE_UP_AFTER_DEGRADED` is non-functional and — once its heartbeat goes stale — invisible to `rimz reload` and ledger wakeups, so it exits rather than freezing on a stale frame; reload/attach then rebuilds a current-build sidebar against the live panes, and a lone orphan with no working pane simply disappears.

Carried pane truth and gate holds are visible without becoming health failures. A snapshot whose pane frame includes carried panes paints a dim bottom notice such as `⚠ pane source degraded · 2 carried panes · 8s` under the dashboard and above the footer, while the body, footer, and provider dashboard stay live. When the renderer gate holds a successful-but-regressive fetch behind the last good frame, it paints `⚠ pane updates held · empty pane frame`, `frameless update`, or `agent demotion` from the same bottom notice layer and logs the matching `gate_hold`/`gate_release` diagnostics. The `agent demotion` notice marks a command-unchanged phantom flicker or missing command evidence; an in-place agent exit whose foreground command changed commits without the notice. A sticky health alert supersedes these notices because a broken fetch is a stronger condition than a repaired partial read or held regression.

This is the degraded twin of [self-close](#self-close): self-close fires when the view empties, give-up when the view can no longer be read at all. The decision logic is the pure function `app::compute_next_state`, which folds each fetch outcome into a debounced, sticky `Health` (`failure_streak` plus an optional `Alert`); the loop applies its `RenderState` verbatim. `rimz sidebar serve` defaults tracing to `off` so warnings do not corrupt the terminal UI — set `RUST_LOG` when debugging the renderer.

## Resume-on-rebirth

When a session dies — laptop reboot, a multiplexer-server crash, or a Rimz-initiated rebirth of a stuck room — the agent processes are gone but the ledger remembers them. Rimz offers to bring them back: an involuntary session birth prompts to recover prior agents as running panes grouped into `#channel` tabs, defaulting yes, so the room can come up where the user left off instead of empty. Non-interactive starts recover. This is Rimz-owned, transcript-based continuity — deliberately not Zellij session serialization, which resurrects every command pane `start_suspended` and so reads as unhealthy (the catch-22 [`session_serialization` stays off](./multiplexers.md#zellij-backend) to avoid). `rimz reset` is a manual fresh start and does not recover agents.

The planner ([`src/resume.rs`](../../../crates/rimz/src/resume.rs)) is pure over the durable agent rollup. The cli reads the **audit** projection (`RuntimeScope::Audit`) — the one that keeps the dead-process agents a runtime read expels, which is exactly the set a rebirth must restore — and excludes the sessions with a durable end trace (`agent_tombstones_for_events`). `plan_resume` then keeps each root agent that was bound to a pane in the incarnation that died — its stamp survived the rebirth-boundary clear, so a non-`None` pane in the workspace-scoped rollup is exactly that proof — and still carries a session id and an on-disk worktree, collapses a relaunch that re-used a pane to its newest stamp the way the live binding and [supersession reap](#presence-model) do — the pane is the unit of identity, so two same-kind agents concurrently live in one worktree each keep their own pane — orders by recency, groups survivors by worktree, and caps the fleet (config `resume.max`, default 8; overflow is reported, never silently dropped). Each worktree becomes one `ResumeTab` named `#<channel>`; each pane inside it runs the supervised exec wrapper — `rimz agents exec <kind> --resume <id> --close-pane-on-exit` plus the carried launch identity (`--agent-name`, `--agent-profile`, `--agent-role`, `--agent-team`) — which injects the launch env every launcher applies ([trust.md → Launch-time application](trust.md#launch-time-application)) and then spawns the adapter's resume argv: `claude --resume <id>`, `codex resume <id>` (`AgentAdapter::resume_command`). A candidate whose worktree has disappeared is written as `agent.ended` and left out of the report, so the noise does not repeat. Planning runs first, then the birth appends the `session.rebirth` boundary that unstamps the prior incarnation's panes ([the binding ladder](#presence-model)) — so the plan reads the stamps it keys on, and the reborn room starts with a stamp-free rollup the resumed agents re-stamp through their own `SessionStart`.

When recovery is accepted, the backend seeds those tabs at birth and stays ignorant of agents and the ledger: Zellij spells one `sidebar | agents…` tab per worktree into the birth layout (command panes born running, never suspended), tmux opens one `sidebar | agents…` window each via the `after-new-window` hook — focus lands on the freshest channel and its freshest agent so attach drops the user onto it. The restored agents come back **idle**: `--resume` rehydrates the conversation without a prompt, so no tokens are spent until the user types. Each agent's own `SessionStart` fires with `source: "resume"`, coalescing back onto the same `(kind, agent_id)` rollup row and re-stamping its new pane, so the sidebar rebinds the row with no new identity and team members keep their `@role` address plus team membership. `--no-resume` (or `resume.on_rebirth = false`) opts out for a deliberately fresh start; a workspace with nothing recoverable or declined recovery births exactly the bare working room.

## Notifications

Notifications are best-effort polish over the same attention model this document describes; the ledger remains authoritative. The elected producer opens durable unread episodes, applies `[notifications].triggers`, debounce, focus suppression, and burst coalescing to newly opened episodes, then spawns matching notification handlers and broadcasts `SidebarEvent::Notify`. A renderer that has relayed an initial terminal notification re-rings local unread `waiting`/`failed` rows at the configured reminder cadence until they clear.

The renderer writes terminal-local OSC/BEL bytes outside the draw cycle. tmux can forward desktop banners through SSH with passthrough enabled; Zellij currently uses notification handlers for portable delivery. The full contract lives in [notifications.md](./notifications.md).
