# The sidebar data plane

> This page owns how the sidebar gets its data: which renderer reads what, what it publishes where, how realtime events overlay it, and how stale any value can be. [sidebar.md](./sidebar.md) owns what the sidebar does with the data (binding, grouping, ranking, the serve loop, recovery). [store.md](../store.md) owns the durable truth underneath and the runtime directory the caches share. [multiplexers.md](../multiplexers.md) owns the backend push channels, [providers.md](../agents/providers.md) the account caches and window fusion, [performance.md](../performance.md) what the plane costs, and [diagnostics.md](../diagnostics.md#inspecting-live-card-state) how to inspect a live card.

## The shape of the problem

A room holds one store and one sidebar pane per tab. One room host per mux session paints every one of those panes, several times a second, so each session's data plane has exactly one owner ([room admission](../multiplexers.md#room-admission)).

Half the inputs are cheap. The store rollup is `snapshots/latest.json` when its recorded generation matches the durable record, its log offset equals the live log's length and its `SNAPSHOT_VERSION` matches (`crates/rimz/src/store/snapshot/assemble.rs::read_fresh_latest`, [store.md → truth and cache](../store.md#truth-and-cache)), and otherwise an incremental fold of the log through the host's warm rollup cursor (`crates/rimz/src/sidebar/consumer.rs::rollup_snapshot`). The runtime sidecars and lane caches are small JSON files behind stat gates.

Every producer and consumer enrichment fold also probes the wrapper-held hook-drainer outage leases through `crates/rimz/src/harness/drainer_outage.rs::read`. The snapshot's optional `hook_drainer_outage` carries the earliest start as a `jiff::Timestamp` in `since`, converted once from the runtime record's `since_ms`, and the agents in start order. Free, unreadable, malformed, and unknown-version leases contribute nothing. Changes to that set are content, never a clock-only update. Diagnostic logs are not an input.

The other half are expensive. The pane roster costs a multiplexer IPC round trip or a plugin hop, git costs forks per worktree, and provider accounts, usage, and pricing cost subprocesses and network. Paying those once per tab per tick would saturate the mux server and the machine, and a room sits idle most of the time anyway.

Three rules resolve that, and the rest of this page follows from them.

1. The store is truth, and the sidebar's lanes are cache. Each lane rebuilds from the store plus a fresh read, is written temp-file-plus-rename without fsync, and can be deleted at any moment ([store.md → write classes](../store.md#write-classes)). The one exception is `records/live-roster.json`, which shares the cache write class but rebuilds from nothing: rebirth recovery reads it ([coordination and receipts](#coordination-and-receipts)). The `cargo xtask invariants` check `xtask/src/invariants.rs::ensure_sidebar_library_boundaries` rejects any `store::writer`, run-wake, or broker path in `crates/rimz/src/sidebar/`, `crates/rimz/src/wakeup/`, and the harness modules the sidebar imports (the list is in that function), so the data plane is read-only on the store. The check matches text over those paths only: `crates/rimz/src/sidebar_pane/` is outside it, and a harness module the sidebar starts importing is unguarded until it joins the list.
2. One host per session pays the shared reads. Its data plane folds once for all subscribed panes, does the external work once, and publishes runtime caches for CLI readers. New attachments seed from its last delivered fold in memory.
3. Realtime events carry latency, never truth. A wakeup datagram lets a change paint now instead of at the next poll. A dropped datagram costs staleness bounded by the next producer pull, never a wrong verdict.

```text
     store rollup                         expensive external reads
     latest.json + log                    mux panes · git · providers
           │                                     │ host production
           │                          retained panes + agent projection
           │                          heavy-lane caches (also CLI refresh)
           └─────────────────┬───────────────────┘
                             ▼
                    host fetch worker
                    ordered workspace fold (enrich)
                             │
                    per-attachment projection
                             │
    realtime events ────────▶│◀────────────── focus intent
    room-shared overlay     ▼
                fuse_owned(pulled, events, intent, now)
                   pure: no IO, subprocess, or clock read past `now`
                             │
                       SidebarSnapshot ──▶ paint
```

## The room data plane

Every tab's sidebar pane runs one `rimz sidebar serve` supervisor, and one `rimz sidebar host` per mux session paints all of them. The panes of a session share one process, one data plane, and the host's room socket for external events. Each pane still has its own heartbeat, bounded wake channel, and frame loop. Shared capability and geometry probes can hold those loops while sampling.

### The room host and its attachments

The supervisor keeps the pane's tty and hands the host only the pane's output. It holds raw mode and mouse capture for its whole lifetime, including first-start failures and the gaps between attach rounds. While attached it reads keys, clicks, and resizes and forwards them as raw input words. The host ([`host.rs`](../../../crates/rimz/src/sidebar_pane/host.rs)) is detached from every terminal and runs one attachment per pane ([`app/attachment.rs`](../../../crates/rimz/src/sidebar_pane/app/attachment.rs)), each on its own thread with its own `LoopState`, geometry, width control, and frame painter, which holds a [pixel slot](./pets.md#image-ids-and-slots) only while the host permits the pane images: a fresh client sample places it on a client's screen, or a sidebar jump lands on it. The host resolves each key against the routed [client view](#client-views)'s UI mode and the current snapshot's in-pane keymap (`keys`, resolved from `[keys.sidebar]`) ([motion keys](./sidebar.md#selection-and-jump)).

| Owned by | What |
| --- | --- |
| Supervisor, one per pane | Terminal modes, the input and resize reader, the attach connection, self-close confirmation against the mux, the pane-liveness probe, its own re-exec onto a new build. |
| Attachment, one per pane, in the host | The heartbeat (`instance_id` the supervisor's, `pane_id` the pane's, `build` the host's, `size` read from the pane fd), bounded wake channel, frame loop, geometry, own-tab marking, width control, self-close, render caches and last-painted hit maps. |
| Host, one per session | The room event socket and the data plane ([`app/plane.rs`](../../../crates/rimz/src/sidebar_pane/app/plane.rs)): one fetch worker, one cache refresher, one tmux watch and hidden-view sweep, one transcript watch, one observer writer, and the client-view registry under one mutex with an immutable published record. |

The plane also owns shared width memos, separate from the client-view mutex: Zellij's stamped topology table and tmux's single session-wide geometry attempt. Every attachment retains its own width-control state and inputs. tmux idle backstops share successes and failures for `IDLE_RETRY` (5 seconds). Structural floors and floorless requests keep their live-read freshness ([width](../multiplexers.md#width)).

An attachment has no terminal state of its own to touch. Geometry comes from `tcgetwinsize` on the pane fd and is read again on every `resize` word. A pane the mux has not laid out yet reports `0x0`: its heartbeat carries no `size`, and nothing is drawn until the first resize sizes it. A write error on the fd, which is how a closed pane first shows, closes the attachment exactly as the supervisor's end of stream does. A panic in one attachment closes that attachment alone.

The host's environment is the session's minus pane-scoped attribution, lane, and supervisor instance identity ([`supervise/host_link.rs`](../../../crates/rimz/src/sidebar_pane/supervise/host_link.rs)). Its spawner sets the room pin from the argv workspace's record, using the canonical root that `workspace::verify_pin` returns, never the supervisor's inherited pin. Two failures stop the spawn:

- A supervisor with no readable workspace record stops before spawning or writing diagnostics. It prints one stderr line naming the workspace and `rimz start`, then exits 0 (`crates/rimz/src/sidebar_pane/supervise.rs::run`).
- A readable record that cannot verify the room pin starts no host. The supervisor appends a timestamped line with the workspace and reason to the host log (its own log sink is off while it renders), then shows a notice naming that log and retries.

One fold serves every pane. The fetch worker publishes the renderer-independent workspace into the host's views, and each attachment projects it for its own pane when it reduces. Tab names, the live roster, unread reconciliation, and notifications are decided once on the room fold. Each attachment still decides whether a notification rings in its own tab.

Projections share the fold's agent-scaled data through `Arc`: the room rosters (`agents`, `fenced_sessions`, `resume_outcomes`), pane bindings, the group vector, group rows, and each agent card. Pane-local fields and worktree roots stay owned. Pane-side code calls `Arc::make_mut` only after a read shows that the write changes that collection or card, so unchanged data stays shared.

A new attachment paints room content before its first fetch completes. Under one lock it subscribes and captures `Views.fold` with the current publication revision, and it projects that seed for its own pane and refresh override. A scratch borrow (a pane neither resolved to a client nor visible) applies the seed through the normal fusion and gate path as an interim cached snapshot, before draining wakeups. A shared client view drops it once the host has published, which a captured fold implies (`crates/rimz/src/sidebar_pane/app/loop_state.rs::LoopState::apply_latest_snapshot_with_seed`). That borrow's catch-up in `crates/rimz/src/sidebar_pane/app/loop_state/shared.rs::ViewAccess::with` instead replays the publications the view has not reduced, traced `seed: false`, and a view already current paints the content it holds. A visible new sidebar on a warm host takes this path. A seed completes no fetch. The attachment's first request still corrects it, since every request runs a worker cycle even when the shared worker has nothing new to fold. A warm host seeds with no age bound, stamp pairing, or incarnation guard. A cold host paints the placeholder until its first publication. Both backends share this rule.

The own view gates selection. A frame that predates this attachment's pane yields `own_view: None`, and `crates/rimz/src/sidebar_pane/app/state.rs::session_focus_baseline` then withholds focus. The snapshot's `focused_pane` stays as folded for fusion and watched-state. Neither the seed nor a later cached fold of that frame derives selection or clears unread from the withheld focus, so a selection established on this pane holds its last baseline. An arriving view follows the [client-view rule](#client-views). Even with its own view present, `session_focus_baseline` requires the focused pane to be a row before it can seat a new baseline. A missing own view is expected briefly at room or tab birth. `fold_decided.own_view` in the [focus trace](../diagnostics.md#the-focus-trace) shows the transition. An attachment that never sees its own pane cannot follow focus.

The supervisor carries a selection baseline across host replacement. At its first sized composition an attachment can seed the baseline its supervisor carried, but only into a view that has none, and a hidden pane cannot seed a different pane's view. Reattachment to a live host keeps the full view. Host replacement loses full views and keeps only these pane-keyed baseline hints. The [first-frame live check](../../contributing/sidebar-live-check.md#first-frame-of-a-new-tab) records the remaining seat lag and the attribution recipe. Selecting the previous tab's pane is a regression, not an accepted first frame.

### The attach wire

The host listens on a stream socket in the runtime `sock/` directory, named by a digest of the mux and session name. A supervisor connection is one pane, and end of stream from either side detaches it. The same listener accepts one-shot card commands, without a pane or output fd.

1. Hello. The supervisor sends one JSON line and, riding the same message as `SCM_RIGHTS`, its stdout. The fields are `protocol` (`rimz.sidebar-attach.v1`), `instance_id`, the required `pane_id` (the supervisor's own pane, and a hello without it is malformed), `supervisor_build`, the optional `baseline_pane` (a pane id such as `"tmux:%6"`), the pane's `tick_seconds` cadence (also required), and its `refresh_ms` launch override when set.
2. Reply. The host answers `{"accept":{"build":"…"}}` or `{"reject":{"reason":"…"}}`. The named reasons are `protocol` (another wire version), `build` (the host is leaving for a newer build), and `capacity` (the host already holds `MAX_ATTACHMENTS`, 512). Any other text is a host-side failure.
3. Stream. After an accept, the host writes JSON control lines and the supervisor writes bare newline-terminated input words, starting with `resize`.

| Host control | Sent when | Supervisor effect |
| --- | --- | --- |
| `{"control":"self-close"}` | The pane's tab looks empty. | Confirms against the mux before closing the pane. |
| `{"control":"reload"}` | The host is leaving for another build. | Detaches and reattaches to the next host. |
| `{"control":{"baseline":"tmux:%6"}}` | The selection baseline changes (`null` forgets it). | Remembers it for the next hello and carries it through re-exec. The attachment continues. |

The host seeds the baseline before the first fold and compares it once per loop turn, counting the hello's value as already reported. Old hosts ignore the optional hello field, and old supervisors ignore an unknown control.

The input words are `resize`, `press:<mods>:<code>`, `mouse:left:<col>:<row>`, `scroll:up`, and `scroll:down`. The host decodes only `\n`-terminated lines, ignores unknown ones, and sends decoded input to the attachment's channel. EOF or a read error detaches, and a final chunk without `\n` at EOF is discarded undecoded: it can only be a torn word's fragment. A supervisor write times out after the forwarder's 250 ms stop poll. Each word reaches the stream whole or not at all: a timeout before its first byte drops that word and forwarding continues, while a timeout or error after any of its bytes, the initial `resize` included, ends the forwarder as a stream failure, so the round ends as a [lost host](#host-unavailable) rather than joining a fragment to the next word.

A connection that closes without a hello is dropped silently, which is what the socket GC's liveness probe looks like.

### Card commands

[`commands.rs`](../../../crates/rimz/src/sidebar_pane/commands.rs) exposes `request_card(mux, session, request)`. The first newline-terminated JSON object has a `command` tag instead of the hello's fields: `walk` with `direction` (`next` or `prev`) and `worktree`, `slot` with `n`, `last`, `filter_needs_you` with `toggle`, or `close_target` with an optional `pane`. The host never admits this connection as a pane. It returns one JSON line and closes: `{"reply":"done"}`, `{"reply":"refused","reason":"…"}`, or `{"reply":"close_target","agent":{"kind":"…","agent_id":"…","pane":"tmux:%6"}}` / `{"reply":"close_target","pane":"tmux:%6"}`. Every close target carries the row's pane, including an agent card that has no bound session yet. Done commits the reduction and its queued effects, not focus landing. The client uses `UnixStream::connect`, then bounds writes and reply reads against one five-second deadline established before connecting. The kernel connect call has no separate timeout. A missing host, EOF or timeout names `rimz sidebar repair`.

The acting view is the one held by **every attached, non-departed client in the latest resolved sample**. No clients, different views, or a client's tab without a sidebar refuse without changing any selection. An unresolved sample keeps the last resolved routes. Input timestamps never choose a client. Delivery uses the sidebar pane already mapped to that view, then checks the same view and pane again under the views lock after preparation, before catch-up or routing. A request whose view changed while queued refuses instead of moving a view. The highlight, not the calling pane or channel-scoped handle, supplies a close target. The host only names it and never stops a process or writes store data. A `close_target` that names its `pane` (`rimz sidebar close --pane`, which the in-pane `d d` runs) skips the agreement: `Views::command_target_for` routes it to the first ready client's view, whatever tab that client views, the named pane supplies the target, and the reduction leaves that view's help overlay and search draft alone, since the view is not the presser's.

Every refusal reason starts with `sidebar <command>: `, where the command is `walk`, `slot`, `last`, `filter needs-you`, or `close` (`crates/rimz/src/sidebar_pane/commands.rs::CardRequest::refused`). A destination between attachments returns `refused` with `sidebar view is not ready; try again` after that prefix. A full or disconnected input lane, or a request still unreduced at its four-second deadline (the client's five seconds minus `CARD_REPLY_WAIT`), returns `refused` with `sidebar busy; try again`. The deadline answers the queued input under the same mutex as its reduction, so the pane cannot also reduce a timed-out request. A reduction that already committed keeps its verdict even if reply delivery is late. The host reserves the remaining second of the client's budget to write the reply, rather than closing silently and turning a transient no-op into a host fault. These host refusals write a reply and focus trace, without adding a pane notice. A `d d` pressed in the pane still shows one: the `rimz sidebar close` it spawns prints the refusal on stderr, and `key_spawn::run_reporting` turns the first stderr line into the pane notice whatever the exit status.

Commands close help and cancel only a live search draft, retaining the committed query. Walk visits paned top-level rows in the visible roster, wraps, and skips child entries, older entries and folded rows. Worktree walk chooses the first paned row of the next or previous nonempty group, also wrapping. Selection moves in the same reduction as the focus effect, so repeated requests advance even before the first focus lands. A pending click-style pick holds through late landings of earlier jumps. The baseline still reconciles normally, previous-card history holds its input-time value, and only native client consensus confirms its landing. A dispatched pick also releases after its own nonce was observed and then replaced or retired, or on a newer external focus anchor. Sidebar workers carry a separate originating-input stamp for replacement, so an earlier jump dispatched late cannot be mistaken for a newer external focus. An acknowledgement against the retained pre-dispatch sample is not evidence of replacement. The pending pick expires on the first fold at least 2.5 seconds after input, the focus-anchor freshness bound. Pending input keeps backstop folds active, so expiry needs no new focus event. Expiry releases the pick, rollback and browse state, not the focus anchor: an applied anchor with unchanged native observations becomes a fence through the normal intent lifecycle instead of restoring the old focus. Worker acknowledgements are keyed to their originating input, including retained copies, so a late completion cannot release a newer pick. That identity survives an early native focus event until the pending pick releases. Superseded dispatches release only their originating input, including retained copies, without a failure alert. Every jump uses the normal layout freeze and focus-failure rollback. Slots use the room-wide pane-birth numbering, even when a lens or fold hides the target. Needs-you set/toggle persists through the existing shared-filter path. Setting an empty or already-active lens refuses with a no-op reason, without writing.

Each view remembers one previous card in host memory. An explicit focus input between distinct cards advances it at reduction, using the prior pending target or otherwise the baseline, mapped to the owning card's pane. Pending-input folds preserve that history through intermediate landings. Without a pending input, baseline moves between distinct row panes still advance it. Non-row focus and repeats do not. `last` jumps to that pane, so even unlanded jumps toggle the pair. A departed row refuses, a failed jump restores the pre-input previous card alongside the baseline, and host replacement forgets this history. A refusal reduced by a pane uses a recovered alert, without masking an active health fault. An unresolved refusal has only the reply and focus trace.

### Host unavailable

The host is the only painter, so the supervisor refuses early when it could never reach one. First, `crates/rimz/src/cli/sidebar.rs::serve` refuses outside a mux pane: `rimz sidebar serve` runs only in the sidebar pane the room spawns. Inside a pane, after the no-room check, `crates/rimz/src/sidebar_pane/supervise.rs::run` refuses non-terminal stdout with `error: rimz sidebar serve: stdout is not a terminal; the sidebar pane command must run in a pane` on stderr and a non-zero exit. An unavailable `RuntimePaths` likewise exits non-zero with its `PathErr` message. These checks precede socket or terminal-mode work. The supervisor then initializes the runtime directories before starting a host, and the detached command uses the shared runtime root as its working directory.

Every other failure to reach the host follows one notice-and-retry path: a failed start, an unanswered socket (`HOST_WAIT`, 2 seconds), a rejected hello, an unreadable or late reply (`REPLY_WAIT`, 5 seconds), a lost attachment, and an attached round whose input forwarder stopped. A forwarder whose terminal event source failed ends the round as `terminal input stopped`; one whose write to the stream failed ends it as a lost host. A host word or end of stream read in the same poll decides the round instead. The supervisor clears the screen and homes the cursor with plain stdio control bytes, then writes two uncolored lines in raw mode with `\r\n`: `sidebar: <cause>` and `retrying in <N>s`. It writes only after a failed round, never before the first attempt or while attached, and the next attachment paints over the notice. N is the upcoming backoff in whole seconds, at least 1. Delays double from 1 second to 60 seconds and reset after an attachment has run for a stable minute. A workspace-record change interrupts the wait.

| Cause shown | Diagnostic `cause` |
| --- | --- |
| `host did not start (<error>); see <host log path>` | `start_failed` |
| `no host answered` | `no_answer` |
| `host rejected this pane: <reason verbatim from Reply::Reject>` | `rejected` |
| `host reply unreadable` | `reply_unreadable` |
| `host went away` | `lost` |
| `terminal input stopped` | `input_lost` |

Each failed round emits the identity-rate-limited `sidebar_host_unavailable` record with the cause, reason, attached duration when an accepted attachment was lost or its input stopped, and upcoming retry delay ([diagnostic fields](../diagnostics.md#supervisor-kinds)). A lost host costs even a mature attachment a one-second notice before retrying.

Terminal modes survive every exit except a confirmed self-close. Self-close restores them. SIGTERM, pane-gone cleanup, and build exec preserve them for the pane handoff. An attachment's close removes its runtime files, and a stopping supervisor also removes its per-instance files.

### Host lifetime and reload

The supervisor that finds no host takes the session's spawn lock and starts one. It runs the room's verified recorded build, or its own executable when no verified target is available. The host's stderr is appended to `log/sidebar-host.<session key>.log` under the room's state directory, so a host that fails at startup leaves its error there.

At startup the host calls `setsid` and raises its open-file soft limit toward the hard limit (`crates/rimz/src/sidebar_pane/host.rs::raise_open_file_limit`). The target is 65,536, retried at macOS's 10,240, and a refusal warns in the host log. The sizing reason is on `OPEN_FILE_TARGET`. The host then holds the session's host lock for life. A second host for the same session waits out its predecessor (`SUCCESSION_WAIT`, 12 seconds) and exits if that one stays.

The host leaves in four ways:

- Idle. With no connection for ten seconds it exits.
- Reload. When the workspace record names a verified build other than its own, or a batch of reload requests finds a byte-different target, it removes its sockets, sends `reload` on every stream, and waits until its attachments have let go or `DRAIN_GRACE` (10 seconds) passes, whichever comes first. Supervisors then find no host and start the recorded build's.
- Lane death. When the fetch worker or the cache refresher thread ends, which only an unwind does while the host serves, the host notices within one poll (1 second). It logs an error naming the lane, removes its sockets, closes every stream without a control word, admits no pane, and leaves after its attachments let go or `DRAIN_GRACE` passes. Each supervisor reads a lost host, shows `host went away`, and starts the next host on its backoff curve, so a panic that repeats every cycle cannot spin hosts.
- Teardown. The room teardown sweep kills it like any other process carrying the session's tokens.

A supervisor re-execs itself onto the recorded build once its attachment has run the stable window under a host of that build.

Reload requests reach the host inbox directly: room reload words and envelopes, and a pane's `view.reload` action (`R`) after UI-mode resolution. The host drains all queued requests into one comparison per turn. An identical or missing target forces one hard refresh without blanking panes.

### Shared lanes

The host starts its lanes when its first pane subscribes. The fetch worker skips an empty subscriber set, and the cache refresher skips a pass with no pane. The fetch worker and the cache refresher are essential: neither returns while the host lives, and the end of either ends the host ([lane death](#host-lifetime-and-reload)). The other lanes are latency or enrichment behind the fetch backstop, and the host keeps serving without them. Heartbeats remain per-pane liveness and wakeup hints, never ownership votes.

| Thread | Owns |
| --- | --- |
| Fetch worker (essential) | Pane and workspace publication, group roots, notifications, unread reconciliation, and tab-status names. |
| Mirror dispatcher | Ranked hidden-layout offers, with four shared slots and a 150 ms input-rest deadline. |
| Cache refresher (essential) | Consumes the fetch worker's sampled fold for TTL-gated git, PR, accounts, usage, credits, cohort effort and unattended recovery. Due tasks, messages and daemon-view repair still run when fold acquisition fails ([rimzd.md](../rimzd.md#who-repairs-and-when)). |
| tmux control-mode watch | One tmux presence stream for the session. |
| Transcript watch | Filesystem watches on live sessions whose adapters declare transcript-tail context. |
| Observer writer | Frame-anomaly emission and real-world cross-checks when diagnostics are enabled. |

Host replacement is supervised, not elected. Account-global spending keeps its separate lifetime lock and socket ([spending.md](../agents/spending.md#one-walk-per-namespace)).

Four host-wide samples serve every attachment:

- Hidden-view fitting (tmux only). The tmux watch kicks it when its own watch attaches, a terminal client attaches to or switches into the watched session, a window is born, or the current window's layout changes. Client changes into other sessions on the server and hidden layout changes do not kick it. After 500 ms without a kick, the host starts a paced run, freshly reading stale hidden windows before every slice. It orders them by the hidden-mirror queue's painted tab frame: left neighbour, right neighbour, previous tab, then outward (left first on ties). Unknown views retain the read's MRU order. With no painted view the whole read stays MRU. Each slice takes a prefix costing at most 150,000 estimated lines, counting each window's normal-screen history plus 1,500 lines of fixed overhead, and at most eight windows. An over-budget first window goes alone. After the read and fit return, the next slice waits at least 250 ms or nine times the slice's entire wall time, whichever is longer. A window is attempted only once per run, including failed or skipped fits. Already fitted windows disappear from the fresh reads. A changed target ends the run and starts another with an empty attempted set. Kicks and the host-wide 150 ms input-quiet deadline are checked after read/preparation, immediately before `MuxBackend::fit_views`: a kick ends the run and restarts the 500 ms settle, while input discards that read and defers without ending the run. A slice due while that deadline is still ahead waits it out before reading, so continuous input costs no tmux reads. An in-flight slice finishes. Its cadence floor survives a kick. A completed or interrupted run that attempted any windows writes one aggregate diagnostic, including its last-known unattempted remainder. A user jump still freshly checks and fits its one stale destination immediately before the paint handshake, without waiting for the sweep's cadence. The in-tmux size guard skips an already fitted window without unzooming it. Manual windows and sessions without a sizing client are excluded, and each fit preserves the window-local sizing policy ([mux geometry](../multiplexers.md#attach-and-the-terminal)). Zellij runs neither this worker nor its geometry subprocesses.
- Graphics capability (tmux only). Probes share a plane-owned ten-second sample of the rendering clients, process ancestry, version, and per-pane passthrough options. A session-wide pane listing keeps each pane's permission. A pane born after the sample, or an unavailable listing, uses a targeted query. Passthrough escalation and fd-derived cell aspect stay pane-local.
- Diagnostics observation. With diagnostics enabled, the fetch worker extracts one shared observation signature before local projection, and the writer detects common anomalies once. Attachments detect their own committed roster and clicked-card displacement after paints. With no writer, commit signatures are skipped. Attribution and evidence scope are in [diagnostics](../diagnostics.md#the-commit-point).
- Machine pressure. The fetch worker classifies one room-host PSI reading per cycle and shares the resulting stall notice with every attachment.

## One fetch cycle

An attachment's loop reads no data itself. It blocks in `recv_timeout` on its bounded wake channel, using the timeout as its frame clock, and requests folds for pane-local observations. Shared folding and side effects run on the worker. Local projection and the clock-only decision run when a view reduces.

Once per cycle, `FoldInputs::read` reads the room host's machine/container pressure with no host-data or view lock held. Each resource prefers the cgroup namespace's pressure file, falling back to proc. The classified whole-percent `stall` list is retained with the cycle inputs and stamped by `FetchWorker::publish_fold` onto both interim and final folds before attachment projection. Its displayed values are content, not clocks: a stall-only change repaints. The CLI producer and the published-pane read used by one-shot `sidebar frame` each stamp their own reading. Other passive folds, including `sidebar snapshot --no-produce`, do not sample pressure and leave the list empty.

### Requests

A `FetchRequest` carries a mode and an optional pane-cache floor:

| Field | Meaning |
| --- | --- |
| `Normal` mode | The ordinary wakeup. Production is attempted at most once per data tick. |
| `FreshPanes` mode | The producer produces regardless of frame age. Raised by agent birth and death. |
| `HardRefresh` mode | The host produces regardless of frame age. Raised by reload and manual recovery. |
| `min_pane_cache_ms` | A floor that rejects any pane cache older than the signal that asked for it, which is how birth and death beat the pane TTL. |

The plane requests at most one fold per room event as it records it (`RoomEvents::dispatch` in [`app/plane.rs`](../../../crates/rimz/src/sidebar_pane/app/plane.rs)): fresh panes for topology and agent birth or death, ordinary for a `FocusChanged` (its cycle folds the focus into the pane frame's per-tab `work_pane`, see [the pane frame](#the-pane-frame)), none for width, filter, notification, focus actions, or other overlays, and ordinary otherwise. A `FocusChanged` that lands on a hibernated agent's pane also starts the paced wake helper (`crates/rimz/src/harness/hibernate.rs::wake_focused`, [hibernate.md → focus wakes](../harness/hibernate.md#focus-wakes)).

Panes send attach, own reveal or stranded focus, resize, and local read marks. Gate escape, tab-read dwell, freeze expiry, and self-close deadlines send only while no pane request awaits completion.

The worker merges waiting requests (strongest mode, latest pane-cache floor) in `drive` ([`app/fetch.rs`](../../../crates/rimz/src/sidebar_pane/app/fetch.rs)), so a storm costs the running cycle plus one more. It rests for `FOLD_FLOOR` (250 ms) after each cycle returns, and requests that arrive while a cycle runs or rests merge into the next batch. No mode bypasses the rest, and a request after at least 250 ms idle starts at once. Disconnecting all senders still lets a batch in hand finish.

The worker owns the data backstop. Its tick is the shortest `rimz sidebar serve --tick-seconds` among subscribed panes (default 1, floored at 1 s by `tick_for`). A room is watched when the published views record has any mapped pane or any resolved client's pane. With no requests, the worker runs an ordinary cycle one tick after the previous return while watched, or after `max(tick, UNWATCHED_FOLD_INTERVAL)` (5 s) otherwise. The backstop starts after the first cycle. With no subscribers the worker blocks for a request. A timeout re-reads membership, watched state and attention deadlines before deciding, so an old watched deadline does not force an unwatched cycle.

Requests stay prompt in either room. A pending notification batch or armed room reminder also wakes the worker at its due, never before the 250 ms floor. Each owner reports its due in wall milliseconds. The wait converts it with a fresh wall/monotonic clock pair. A due at or before the preceding cycle's start retries one data tick after that cycle returns, rather than spinning at the floor after a failed fold. A due that lands after a cycle has decided, and before it returns, starts the next cycle at the floor. Eventless status boundaries, silent capacity-cache changes, pane metrics and recovery from a lost wakeup wait up to 5 s by default while unwatched. Reveal paints retained content immediately without changing scroll, expansion or card order, then requests fresh panes.

### The cycle

One cycle runs these steps on the worker ([`FetchWorker::run_cycle`](../../../crates/rimz/src/sidebar_pane/app/fetch.rs)):

1. Fast fold. Fold the event-fresh rollup over the retained panes and agent projection, plus sidecars and heavy-lane files. The fast fold reads neither `snapshot.json` nor `agent-projection.json`.
2. Production decision. `ProducerCadence::start_attempt_if_due` starts ordinary production when no attempt started in the current data tick and the retained frame is at least one tick old or unavailable. `FreshPanes` and `HardRefresh` bypass that cadence.
3. Publish the fast fold. It is final when no production follows, and interim when one does.
4. Produce. When due, `PaneProducer` reconciles panes and publishes the produced fold as final. A failure publishes a failed outcome.
5. On every final fold, before publication: reconcile attention stamps and then unread episodes through `sidebar::engine::reconcile_final_fold`, which then re-sorts the groups on both, take the frame-stream observation, derive the live roster from a produced fold, and evaluate notifications and reminders. An interim fold takes the observation and writes no runtime record.
6. Publish, then wake subscribers. After that, a produced final writes `records/live-roster.json`, and the worker delivers the evaluated notifications: it runs any notification command handlers itself, then fans `Notify` out to the attachments.

`PaneProducer` owns its prior frame, metrics history, and presence-attempt clock, and seeds the frame and history once at host start. A fresh prior avoids mux listing, while a stale one runs candidate, confirmation and carry, and acceptance. Only fresh acceptance publishes topology and commits native-tenant, hold-check and settled-resume state. A held prior keeps all three unchanged. The settled-resume memo keeps each agent pane's settled no-id answer from the [resume walk](./sidebar.md#the-binding-ladder) under its hosted process's pid, start and command line, and each candidate prunes it to the panes it lists. Metrics and presence keep their own cadences. For the [hibernated hold](#cadences), a pane's native listing PID and spawn command must match the previous listing, not its repaired process fields. Unverified panes get full repair and the normal metrics cadence. One decision gates both metrics and process repair. A due sample retains its guarded binding and rate baseline. Between checks the prior process fields carry forward while listing fields stay fresh. Held panes stay in the start census, so due siblings cannot claim their stamps. A due held check rides the next topology frame on the lane's existing cadence, never bypassing retained topology. Metrics-only passes keep verified held panes skipped. Hook one-shot binding reads always repair fully. Tab-status renames follow the ownership rules in [multiplexers.md](../multiplexers.md#tab-names), and a failed mux rename stays best-effort.

Every published fold becomes `Views.fold`, the seed for new attachments, and a failure keeps the previous one. Accepted producer inputs reach shared memory before publication, even when a later fold fails.

A produce runs behind a panic guard. An unwind costs one failed outcome, the loop holds its last good frame, and the next cycle refolds cold from a fresh rollup cursor instead of trusting a base the panic may have torn. A panic anywhere else in the cycle (the fast fold, the input read, a publication) ends the worker, and the host then leaves through [lane death](#host-lifetime-and-reload).

### Publication and replay

The host's views keep three publication slots for the room: the newest final success, the newest interim, and the newest failure ([`Views`](../../../crates/rimz/src/sidebar_pane/app/views.rs)). A successful final clears the interim and failure slots, and an interim never displaces an unread final. Under the views lock, publication advances the revision, reconciles a new frame's membership, and expires retained views. Releasing the guard publishes the record before a final sets completion latches for the subscribers present at cycle start, with Release ordering, then sends wakes. The drain consumes completion with Acquire ordering before reading the record, so a set latch always comes with the completing publication. A subscriber that joined mid-cycle can reduce that publication but gets no completion or wake from it. Publication never waits for tty output.

A cursor replays what its consumer has not seen: the newest unseen final success, otherwise the newest unseen interim, then the newest unseen failure. Wakes are hints. Frame maintenance reads the published record even when a full wake channel dropped one.

Replay compares before it applies. `Cursor::replay` projects the fold through the seed's routine for the reducing attachment's own pane and refresh override, then compares the result with its last successful projected baseline. Equality includes the shared focus anchor and body lens, and ignores only the snapshot clock, generation time, pane observation and production stamps, and the input sampling instant. Equal content with live permission applies clock-only: it advances clocks, stamps, the self-close watchdog, and paint scheduling, and skips full fusion, gate and health commits, receipts and dwell, selection, filter, order, and freeze reconciliation, spend rolls, self-close, anchor observations, and focus-repair retry. Idle presence ages with that clock. Every request still runs a worker cycle, and final-fold notification evaluation, unread persistence and pruning, and link recovery still run.

Clock-only permission is read live at replay and is blocked by any of: a failure, a gate episode, an active overlay, a freeze, a read dwell, an empty-tab confirmation, a pending focus repair, an input obligation, or a changed set of focused row panes. Client membership can change outside projected snapshot content. Both replay sites compare it with the view's captured holds before allowing reuse, so focus entry and release still reconcile without a selection change. Completion is independent of content reuse. A rejected final requests nothing, and the gate asks again once its deadline is due.

Each shared view has its own cursor and baseline. A pane that reduces with no routed view uses its own Scratch scope, with a separate cursor and baseline. Seeds do not prime the Scratch baseline, and a shared drain clears it, so the next Scratch reduction is full once. Local input invalidates the Scratch baseline, and identity-free nudges do not.

Before publication, the worker compares shared collections once against the preceding fold and reuses equal Arcs. Replay checks their identity before small metadata, and pane-local exclusions or older baselines fall back to structural equality. Shared views project and compare under the views lock, and the worker never compares a consumer's baseline. A co-viewer whose view is current does not reduce again.

### Hidden attachments and reveal

A hidden attachment is settled when the published record shows its pane neither mapped nor resolved, visibility evidence says hidden with no active optimism, and the borrow is not input. It reads that record without taking the views lock. Each attachment caches the record Arc and checks its generation, loading at most once per changed generation. Unchanged reads only load the generation atomic. The record holds the revision, outcome slots, fold, mapped and resolved pane sets, the sidebars the last fresh client sample places on a client's screen (the on-screen reading for [image permits](./pets.md#image-ids-and-slots)), and the hidden-mirror target and source painter as of the latest views release, and is never withdrawn. A mapped hidden pane first takes the locked path to unpaint, then becomes settled.

A settled hidden attachment leaves its cursor unread until reveal, with no time bound. A deferred drain builds no projection and advances neither cursor nor baseline. It remembers the examined publication revision and caches the own-view preview by frame Arc and pane. Unchanged wakes clone no outcomes and rebuild no preview. A new revision on the same frame reuses that preview but reads the new fold's viewed panes. Reconciliation obligations are checked on every drain, even without a new revision. It consumes completion and refreshes the self-close watchdog only when completion is present. The preview reads the selected unseen success, not the seed slot, which may hold an interim behind an unread final.

Separately, a settled hidden pane mirrors the layout of the most recently active painted view, in its own geometry. A composition publishes a new layout sequence only when its target card and group placements, zone heights, content height, scroll extent or presentation toggles change. The layout key (`crates/rimz/src/sidebar_pane/render/ui_state.rs::LayoutKey`) compares `anchored_rows` (cards only), `group_placements`, `top_height`, `bottom_height`, `content_height`, and `scroll_max`. The toggles are every `PresentationToggles` member, compared as one value. Content height catches the last card growing or shrinking even when the roster fits and its scroll extent stays zero. Group placements record the key and signed zone-relative first line of each drawn group overlapping the target window, catching a card-less group (a rowless run or open-PR group) moving or scrolling while no card moves. The record's target is that view's id and sequence. Releasing a changed target updates the host-wide mirror queue without reading subscribers or sending a pane wake. The dispatcher reads its bound subscriber registry outside the views lock and marks unmapped, unresolved subscribers pending. Numbers, clocks, eased scroll frames and layout-preserving selection changes leave the sequence unchanged and schedule no new mirror. A rename or status change mirrors only when it changes that layout key.

A new target or changed pane size makes a mirror due, without a per-pane timer. A routed frame whose wheel viewport is still gliding does not count as a settled mirror, so its pane catches up if it goes hidden mid-gesture. The dispatcher sleeps on a condition variable and offers at most four slots, counting both untaken offers and paints in flight. Every user input on any attachment holds new grants until 150 ms after that input, longer than the wheel's 100 ms glide. Hidden resize does not hold the queue. Input refreshes that rest stamp after preparation, at the clock used for its synchronous paint, so slow preparation cannot outlast the glide's gate. Input revokes untaken offers, while granted paints finish. Both the offer and its take check rest. Offers expire after four seconds. Each fill ranks from the latest frame: the source painter's left neighbour, right neighbour, previous tab, then outward by ordinal distance over the sorted distinct positions in the frame, with the left tab first at ties. Missing positions follow in subscriber-map order. An unknown current position puts every pane in that order. The queue remembers only the current and previous tab. An absent current leaves both unchanged, and Zellij tab ids follow position across reorders. A structural publication at rest is offered immediately, while one during input publishes its target immediately but waits to paint until rest.

Every mirror holds a grant through terminal output. After taking it, the pane takes the views lock once, rechecks routing and settled state, and clones the latest source view and content. An already-current target and size skip painting. A later target can compose the same cells if its content was mirrored before the source painted it. An empty mirror diff writes nothing unless the frame clears the pane or carries graphics. Composition and asset work happen outside the lock, with the clone's scroll settled to its target and one-shots cleared. All write-backs stay on the discarded clone. The mirror updates pane-local hit geometry, painted rows and caches, and clears the click guard, but takes no membership, reduces nothing, advances no cursor or baseline, and grants neither watching optimism nor arrival effects. It draws the clone's selection. Under the default Auto card density, arrival at a different agent opens that card and shifts every row below it down by its growth. The source's selected card stays open under the arrival hold, so the rest of the layout matches the mirror. The same exit, empty confirmation, paint/resize holds and jump fence gate it as a routed paint. A blocked or unsized pass requests no offer and only withdraws an outstanding one. A refused grant frees its slot without requeuing itself. The next allowed due pass requests another offer, including the Tick when a jump lease releases. A settled pass with no new target, size or offer takes neither the views lock nor the queue lock. With no painted view, nothing mirrors and hidden panes keep their last frame.

A mirror draws no image and holds no slot, on either backend. It sends no kitty graphics (no transmissions, deletes or sweep), draws an empty box of the pixel pet's footprint, the cell meter, the text budget bar and the text emblem, and returns the pane's [pixel slot](./pets.md#image-ids-and-slots) once its frame is written. A pane holding a slot is therefore due one mirror even when its mirrored target and size are current. Arrival takes a slot again once the host permits the pane images (a client sample places it on screen, or a sidebar jump lands on it), sweeps it, and transmits every image it shows; until then it draws the empty box, the cell meter, the text budget bar and the text emblem. A hidden pane holding a slot while the room has no painted view returns the slot in its next pass and paints nothing.

These conditions apply a hidden publication at once instead of deferring it:

- an unseen failure
- a changed own view
- a pending reveal
- optimistic watching
- a bounded obligation: exit, a gate episode, a health failure, a tab-read dwell, an empty-tab confirmation, focus repair, or pending input focus

Freeze and overlay baselines do not prevent deferral. Input flushes before acting, and hidden resize does not. Revealing focus, owned notification targets, own stranded focus, and owned focus intents also flush, and the plane records overlays before that decision. Width and body-filter events keep their local effects without draining. Unread reminder timing belongs to the worker.

A reveal catches up the routed client view before composing its first frame in the destination's geometry. An unpainted view, or a view changing panes, counts as an arrival when the view has painted before or the pane has already made an advancing projection into its current views registry. That includes a never-painted view's first reveal after a hidden fold, whether observed or evidenced by input. A never-painted view on a pane's first advancing projection (visible from birth) arms nothing, and non-advancing borrows do not count.

An arrival marks the destination dirty even when its copied view already reduced the newest publication, so its first paint does not depend on another content change or animation. It arms the tab-read dwell and holds the last painted order, not a hidden fold's order. Without a painted order it holds its first frame's order. Replaying an older hidden fold cannot cancel a newer arrival's dwell or viewing latch, and an existing hold keeps its deadline. Spend accrued while the view was unpainted settles at reveal, which keeps the spend ratchet. A continuously painted view moving tabs keeps its roll, and joining incumbent viewers neither restarts their roll nor re-arms their hold.

### Client views

A client view is one human client's presentation state, kept by the host so that it follows the client between tabs. `crates/rimz/src/sidebar_pane/app/views.rs::Views` owns fetch content, the seed fold, shared replay baselines, membership, and retention. `crates/rimz/src/sidebar_pane/render/ui_state.rs::ViewState` holds the portable presentation, and `crates/rimz/src/sidebar_pane/app/view_state.rs::ViewContext` its reconciliation state. Selection, scroll, relative row anchors, open cards and other toggles, focus-rank holds, timed freeze, spend rolls, receipts, and tab-read dwell travel together. [Focus holds](./sidebar.md#the-layout-freeze) follow every live client's working pane. Consensus still controls selection, not the held set. Active keys are bounded by focused panes. Released keys survive only through the timed freeze and only while their pane owns a row. The optional `PresentationToggles::inactive_peek` holds a nonzero page count while open and starts absent for a new view or host. It travels like every other toggle across focus changes, tab arrivals, and hidden mirrors. Forks copy its pages and inactive expansions. Each copy then toggles independently. `crates/rimz/src/sidebar_pane/app/selection.rs::toggle_inactive` discards the pages and inactive group expansions on close and anchors selection on both edges. Its key and click dispatch then request `ViewportIntent::RevealInactive`: a chip reveal over an authoritative offset. The next paint reveals the chip and clamps to the new scroll maximum. Full views live in memory only: the attach wire, snapshots, and the room filter format carry none of it.

On its first advancing borrow, a view arriving from another pane leaves its selection behind if the newest published fold's frame does not list the destination yet: the baseline, browse pick, selected pane and index, entry cursor and the focus it follows, drawn selection, and cards held open by selection. Everything else still travels. The pane also takes the frame's own view on both the view's current snapshot and its retained overlay baseline, including the missing own view at that arrival, before catch-up replay or event fusion. A synthetic fold therefore cannot restore the previous pane's own view. A frameless arrival cannot distinguish a new pane from a jump and keeps its selection. A listed jump destination keeps the selection it carries. Same-pane re-arrivals and non-arrival borrows preserve an established pane's hold across a transient missing own view.

The pane loop reaches a view only through `crates/rimz/src/sidebar_pane/app/loop_state/shared.rs::ViewAccess`, which lends it explicitly to `crates/rimz/src/sidebar_pane/app/loop_state.rs::PaneState`. Each borrow takes its overlay cut, then reads the record immediately before deciding whether to lend scratch to a settled hidden pane. Other borrows take the views lock and decide again under it. Only a routed painter consumes the shared view's one-shots or writes back geometry-derived placement. Scratch renders cannot, and hidden mirrors discard their clone's write-backs. Terminal writes, mux commands, read-mark I/O, asset loads, and other module locks stay outside this guard. After unlocked preparation (asset loads between a paint's two borrows, or the fold a stale paint loads), the routed painter re-reads the record, routing and latest fold before composing. A publication that maps a pane after its settled decision takes effect on that publication's pending Snapshot wake.

A resolved client sample changes membership by four rules:

| Sample shows | Result |
| --- | --- |
| A client still on the pane it viewed | It keeps its view, and clients arriving on that pane join it. |
| A client arriving on a pane no one views | Its view comes with it. |
| Co-viewers splitting to several panes | The view forks once per destination. A whole-group move keeps one view. |
| A same-sample swap | No client joins a view another client just vacated. |

tmux clients are always co-located, while Zellij clients may view different tabs. When co-viewers disagree on working-pane focus, selection holds its last baseline rather than following an unrelated client.

Between samples, an attributable `FocusChanged` advances selection and parked state in the same fold. Every tmux event is attributable, because focus is session-wide. On Zellij, the sampled clients on the event pane's tab must all belong to that view, otherwise sampled focus stands. Before the first resolved sample, native focus supplies the baseline.

A departed client's view is retained for `[sidebar] afk_after_secs` (15 minutes by default), timed on a monotonic clock from the publication carrying the fresh sample that dropped it, not the first reader. Expiry runs at publication, and also on focus landing and evidence routing, so a retained view may remain in memory up to one publication interval longer. If co-viewers remain, the departed client keeps a frozen copy. A return under the same client id before expiry resumes it. A view its clients leave for other views at a fresh sample is dropped then, unless a client (live or departed) still holds it or a pane still paints it. A new client joins incumbent viewers, or takes the most recently active unexpired live, held, or anonymous view. With none, it starts at scroll zero with no selection and no carried hold, and native working-pane focus can then derive a new baseline. When its pane has folded before, as on a reattach after expiry, its first paint is an arrival. Activity advances only on routed input or pane arrival, never on folds, paints, or repeated samples. An unresolved sample (retained Zellij rows or an empty tmux map) changes no membership and starts no departure.

Input and observed visibility can establish a view before the client map catches up. A painting pane with no resolved viewer routes in this order ([`Views::route`](../../../crates/rimz/src/sidebar_pane/app/views.rs)):

1. The sole attached client's view, when that client has no pane assignment yet.
2. The most recently active view no other painting pane holds, provided a client holds it or it has received input. A view a departed client holds qualifies only while no client is attached (a reattach whose new client the sample has not yet listed), and is then forked rather than taken: beside an attached client it would freeze the state from the departure in place of that client's current view. An anonymous paint-only attachment does not supersede a viewer's current state. Copying another view's presentation does not copy its input provenance.
3. A copy of the most recently active painting view an attached client holds, else of the most recently active painting view, else of the most recent retained view.
4. A fresh default.

An anonymous view stays live while painted. If no client adopts it, its retention window starts when its last painter leaves. Resolved departure cancels the old pane's input and focus optimism, so a hidden paint cannot create a newer anonymous view that overrides the client's next arrival. New input remains viewing evidence, and a fold without a frame observes nothing. A view that evidence established after the last resolved sample, and that no sampled client held, survives the next sample: a client arriving on its pane joins it, even when the view the client left carries newer input from a co-viewer. Without another attached client holding that source, newer source activity wins over the earlier landing's copy, preserving repeated card picks through a late native arrival.

Unpainted views do no work. Hidden resize alone changes no view and neither grants nor revokes watching optimism, but queues the current painted target at the new size. A hidden, held, or anonymous unpainted view performs no reductions or receipts. Each painted view owns one tab-read dwell, cancelled on departure. View mutations wake no unrelated panes. A changed layout target is offered to hidden mirrors by the shared dispatcher at rest.

### The fold spine

Production and published-cache reads run one ordered spine in [`enrich.rs`](../../../crates/rimz/src/sidebar/enrich.rs), so the two paths cannot drift. It forks no subprocess and writes no cache file: it projects what is already on disk.

`enrich_workspace` is the renderer-independent half. Its order matters in four places:

- Adapter wiring is set before any pane-backed projection, because wiring gates idle-agent synthesis.
- Activity sidecars land before the pane overlay, so row age, ranking, waiting guards, and the stall window see the per-tool timestamp instead of the coarser turn-grained event time. The same record carries the open run of identical tool-name-and-argument signatures. A different tool or any other progress event clears it, and adapters without structured tool input leave detection off.
- Workflow records and their sealed specifications project before the pane overlay. The overlay admits cards and seeds groups with live runs and open PRs. Later git and PR facts, group labels, and presentation sorting also enrich groups with no panes.
- Attention stamps derive after displayed-status and stuck-stage projection, before the final presentation sort. Read receipts and unread state never write that record.

The same half stamps two group fields that the CLI and the sidebar both render. `SidebarWorktreeGroup.team` is the unique non-empty team among the group's rows (`cohort_team`): rows without a team are ignored, and two distinct teams leave it empty. After cached git facts set each group's live branch, `SidebarWorktreeGroup.label_qualifier` names every foreign place's repo folder and qualifies colliding labels with the shortest distinguishing trailing path suffix (`disambiguate_group_labels`). A qualifier that would repeat its group's label is not set, so a foreign checkout's own lane, labelled by its folder, carries none.

A frame-backed fold builds a group when it has rows, an Active or Parked deployed workflow run whose scope resolves outside `external`, or an open PR on a listed root ([group creation](./sidebar.md#worktree-groups)). `workflows::seeds` skips a run whose `RunRecord.origin` is `RunOrigin::Inline`, a loop task's compiled graph, so such a run seeds no group, strip, or step-agent binding; a record written before origins existed reads as `Deployed`. Runs use the rows' `GroupResolver` with their scope path and no lane or branch, so a run joins the one group its path resolves to. The newest `created_at` wins when runs share a group. Pane exclusion and realtime pane-close fusion keep a rowless group while its run remains live or its PR open. Terminal records seed nothing on the next fold. The group's optional `workflow` projection carries the run id, workflow name, scope path, state, main-rail nodes and their step/check kinds and reached flags, current node with the same kind and reached flag, detour parent, visits and cap verdict, no-card word, duration origin and optional hold limit, node-entry and creation clocks, and step-agent provider/session identity. Each group also carries an optional `place` (path and `foreign` flag), and the snapshot carries the root-to-channel `worktree_channels` map beside `worktree_roots`. Channel backing derives from that place, not a persisted projection flag.

[`enrich/workflows.rs`](../../../crates/rimz/src/sidebar/enrich/workflows.rs) projects the records already read for group seeds and throttle notices. Each sealed `workflow.toml` is parsed through the bounded, stat-gated `KeyedParseCache` and the same strict parser as workflow inspection (`harness::workflow::parse`). A second bounded cache reads the journal only when its file stamp changes and retains the parsed entries. Each pass folds the reached names from them with `harness::workflow::hops` and `harness::workflow::reached`, shared with the CLI rails, passing the record's held session so a saved closing verdict that is still waiting marks nothing reached. An unchanged run adds one journal stat and no parse. A missing or unreadable journal leaves every non-current mark future. Enrichment starts no process. The rail is the spec walk's non-detour order, or empty when the current node is unreachable or the spec unreadable. A held session supplies the current step and node-entry clock. The shared `RunRecord::session_attempt` and `RunRecord::step_agent` resolve the root agent by `(run, sequence, Step)`, preferring the attempt's leader handle. Git and PR projection and refresh admission all read `SidebarWorktreeGroup::git_checkout`, which returns the resolved place for Worktree and Channel groups and nothing for Root or External. A rowless Parked checkout therefore keeps the normal git and PR refresh path without recovering a path from rows or run scope.

`project_local` is the renderer-local half: classify session presence against this renderer's clock, resolve this renderer's own view, and drop its own pane from the roster. Snapshot clones share agents, fenced sessions, pane bindings, resume outcomes, the group vector, and group rows through copy-on-write handles. Sidebar chrome is absent from the roster, so normal local projections copy no shared collections. Exclusions, overlays, and unread write-back detach the group vector only when needed, and then detach only changed row collections. Presentation sorting leaves already-sorted groups and rows shared. An armed layout freeze may detach the group vector and every group's rows to keep the user's frozen ordering. Sharing changes neither the JSON representation nor the renderer's snapshot interface.

A frameless fold, which a cold fast lane or a CLI caller wanting rollup metadata gets, leaves `panes_produced_at_ms` null and `worktree_groups` empty while store metadata still paints.

### Attention stamps

`lanes/attention.json` is the sidebar-owned runtime ordering record, with `v` set to `rimz.attention.v1`: `cards` maps a launch id (or the row id without a launch) to `{ "zone": "top" | "calm", "at_ms": <milliseconds> }`. Its only writer is `sidebar::engine::reconcile_final_fold`, called by the host fetch worker and by testkit playback on final folds; it writes only when the fold carries a pane frame, cached or produced. Reconciliation reads displayed `attention_status()` after stall, permission-review, stuck-stage and child projections, before `observer.extract` and publication, then derives stamps onto that same fold, which the entry re-sorts once the unread reconcile has written its bits, so a group's inactive state reads the episodes that fold opened. The observer explains order changes by zone, band and stamp, not by calm status churn.

A calm first sighting inherits the pane's stored `at_ms` when its tenant is `process` and its incarnation matches: both `seen_ms` values agree, or either is unknown. A first sighting in the top zone, an `agent`-tenant slot, or a known mismatch instead seeds from the card's birth (`registered_at`), falling back to that snapshot's `now`. Once recorded, only a top↔calm crossing restamps, at the first host reconciliation that sees it. Neither unread nor read marks enter the calculation. `/clear`, linked compaction and resumed sessions keep the launch key. A fresh launch gets a fresh key. Entries absent from current rows remain until their stamp is strictly older than the shared fourteen-day retention, so a recently ended card can resume without losing its order. Frameless folds neither open, restamp nor prune entries.

The same file's `panes` maps normalized pane ids (`tmux:%3`, `zellij:terminal_3`) to `{ "at_ms": <ms>, "tenant": "agent", "active_ms": <ms>?, "seen_ms": <ms>? }` or `{ "at_ms": <ms>, "tenant": "process", "active_ms": <ms>, "seen_ms": <ms>? }`. `seen_ms` records the pane's `first_seen_at_ms`. It is omitted when unknown and defaults to absent in older files. An agent writes its reconciled card stamp into its pane slot, except an unbound agent row keyed by its pane id (a Zellij wrapper pulled before `bound`), which records neither its own card entry nor the slot over a matching process slot, so the bound card that follows still inherits it. While the card renders inactive or archived it also records `last_activity` as `active_ms`. Hot cards omit that key, and older entries default to absent. Later folds with the same cooled activity write nothing. A process replaces a slot only when both sightings are known and differ, never because its order stamp predates the pane's birth. When either sighting is missing the slot survives. A known sighting fills an absent one. A process with no slot or a replaced slot starts with both stamps at birth. Birth is process `last_activity` when the pane has `pane_process_start` or `first_seen_at_ms`, otherwise the fold clock. An agent→process exit keeps `at_ms` and the agent's recorded `active_ms`, or starts activity at the exit fold when that key is absent. A continuing process changes neither, even while busy. A cooling and exit between final folds can leave no recorded cooled activity, so that shell starts hot. The record is not rewritten per hook to eliminate this window. Slots remain while their pane is present or their order stamp is within the same retention. Entries persist only when changed. Legacy files without `panes` load empty slots. An older host rewriting the file drops slots, causing one birth-based reorder on upgrade, not a read failure. The version stays `rimz.attention.v1`.

Enrichment reads the record on every fold and derives `SidebarRow.attention_at_ms` before presentation sorting. A card whose displayed zone differs from its entry, or that has no entry, gets the stamp the next reconciliation would record (the fold's `now`, the inherited process slot, or its birth) without a write. Process rows likewise derive the next pane slot and age their sinks from `active_ms` using the snapshot's attention windows. Interim publications, published-cache readers and the CLI roster therefore rank as the following final fold will (`crates/rimz/src/sidebar/attention.rs::AttentionStamps::derive`). Missing, unreadable, malformed or wrong-version records are a silent cold start at birth stamps, including after runtime teardown or reboot. Writes use the cache temp-then-rename helper. Hosts for different mux sessions may race, as for unread episodes. A lost crossing is reconciled again on the next fold. The store rollup is unchanged.

### The pane frame

`lanes/snapshot.json` publishes the topology everything else enriches. [`PaneFrame`](../../../crates/rimz/src/sidebar/frame.rs) carries tabs and panes, each pane with its current and rotated-out previous process record, child pids, and sampled resource metrics. It also carries `viewed_panes`, the session `focused_pane` register, and client presence. Only the host writes it ([`produce/panes.rs`](../../../crates/rimz/src/sidebar/produce/panes.rs)), together with `lanes/metrics-sample.json`. The host folds its retained frame, and passive readers read the publication. One-shot inspection and recipient resolution always run a private cached-consistency mux listing and the same repair and acceptance ladder, sampling into throwaway history without publishing panes, metrics history, or agent projection.

Each tab also carries `work_pane`, the non-sidebar pane of that tab the host last saw holding a client's focus, shared by the tab's clients on both backends. Split, zoom, and return from the sidebar go to it through `rimz::pane::work_pane_behind`, which validates it against the caller's own listing and falls back to the first work pane in the sidebar's view. Three inputs move it. The first is a fresh client view at assembly, stamped when the view was sampled (the listing's `observed_at_ms` when the listing carried it, else the start of the direct client read); a withheld Zellij sample counts only for the pane the focus ladder admitted from it, such as a pane a native split just made. The second is a presence re-sample's client views, stamped with `sampled_at_ms`, where a change publishes. The third is every `FocusChanged` the plane records, the pane left behind before the pane focused. Recorded events queue on the views record, and the cycle each one requests folds them into the retained frame before its fast fold and publishes the frame when a remembered pane moved, so the next fold and `lanes/snapshot.json` both carry it within that fetch cycle. A memory-only stamp per tab keeps an event older than the pull that last set the tab from overriding it. Assembly carries a tab's `work_pane` by pane id to whichever tab now holds it, and drops it once the pane closes or turns sidebar; an older frame without the field reads as none. Limits: a key pressed on the sidebar before the host has published the focus event that brought the user there (one fetch-worker cycle, normally under half a second) uses the previously remembered pane, and so does a key pressed before the host's listing holds a pane made a moment earlier, since a focus event for that pane waits for the next produced frame; a focus event lost on the best-effort wire is repaired only by a pull that sees a work pane focused; on Zellij the events derive from sampled client focus, so a pane held under a few hundred milliseconds can be skipped, and `pane.focus.next` emits no pane update upstream; with no sidebar host running the memory stops moving, and a stale entry degrades to the first-pane rule.

Three properties matter downstream:

- It is the card-admission boundary. A pane absent from the frame renders nothing, whatever the store says about it.
- `observed_at_ms` is the fusion supersession baseline. It records when the pane source saw the topology, not when the producer wrote the file.
- It carries one monotonic topology stamp. A topology publication bumps it, and metrics and presence publications keep it. The fetch worker's tab-rename memo reads it to tell a new topology from a repeat.

The producer repairs raced-null processes, missing cwds, and briefly omitted panes before publishing. Those guards are [sidebar.md → Honest reads across a mux hiccup](./sidebar.md#honest-reads-across-a-mux-hiccup).

The rules live in providers.md: how readings from different sources and times fuse and when a refill is confirmed ([Window fusion](../agents/providers.md#window-fusion)), how an entry displays after its reset, including named quotas and model sub-caps that read unknown until reported again, and which account a live reading may join ([Persistence across idle sessions](../agents/providers.md#persistence-across-idle-sessions)), and when a fusion verdict pulls the next direct read forward ([Refresh cadences](../agents/providers.md#refresh-cadences)). Only the producer confirms a refill or requests that early read, and consumers hold the persisted value. The sub-cap tick is drawn in [the interface reference](../../interface/sidebar.md).

### PR state

`lanes/pr-state.json` answers, for each listed worktree root but the project root and each checkout the room shows or a [loop or workflow demands](../harness/loops.md#condition-planning), which pull request belongs to it and what CI says. The record and reader are `forge::pr_state`. The producer-only probe that writes it is [`sidebar/refresh/pr.rs`](../../../crates/rimz/src/sidebar/refresh/pr.rs), which shells out to `gh` or `tea`. A checkout whose inputs say it has no forge target (no git checkout or a removed common directory, a detached HEAD, no `origin` URL, or an origin no forge CLI serves) is bound to `<unsupported>` and gets no link, and the file may still carry its bookkeeping and probe stamps. A checkout whose discovery read failed (an unreadable git file or common directory, or a `git symbolic-ref` or `git remote get-url` that failed or timed out) is retryable instead: it keeps its prior link, binding, head CI, and demanded branch rows. An unborn branch (a fresh `git init`, `git switch --orphan`) is neither: it is an ordinary target with no head commit yet.

Demand reaches past the room's panes. Every listed worktree root but the project root is probed whether or not a group shows it, so a worktree that only its open pull request holds keeps its reading, and its forge signals fire like any other checkout's. Live loop conditions, and active workflow runs with forge-reading condition cases or default-scoped `ci`/`pr` wakes, keep their scope checkouts probed without panes, and workflow demand lasts through steps. Conditions can also demand branch rows in `branches[repo_key][branch]`, resolved through the scope checkout's `path_repos` entry, without a checkout of the selected branch. A branch row holds an optional PR link and optional head CI. Branch rows use the runtime-cache publication path, keep the prior row when that branch's reading fails, and are pruned when demand ends. Signals remain checkout-only.

#### Which PR a checkout owns

A link belongs to one checkout incarnation. Each link is stamped with its PR head branch and the RimZ worktree marker's creation time (`TargetStamp`), so a branch switch or a recreated managed worktree drops the old link and resolves again.

| Candidate | Attaches when |
| --- | --- |
| Open PR | Its branch matches, since a live push updates it. |
| Merged or closed PR, managed worktree | It was created no earlier than the marker, within `TERMINAL_PR_CLOCK_SKEW` (5 minutes). A missing marker or forge timestamp accepts it. |
| `--from-pr` checkout | Its named PR, always. |
| Any PR, trunk checkout | Never, so a same-named fork branch cannot attach a false badge. |

An open link also carries a display-only `stack`, projected as the worktree group's `pr_stack`. Both forges supply a repository-wide open set: GitHub adds one `open` alias to the first batch, counting against its 100-alias budget, and Tea adds `base` to its existing list fields without another request. Cross-repository PRs never join the stack. From the linked PR, the walk follows base-to-head downward, choosing the highest PR number for duplicate heads, and head-to-base upward. It stops below at the diff-stats trunk (an `origin/`-prefixed name included), and above at a fork, keeping all fork members in ascending PR-number order as the last level. Each direction stops at eight levels or a repeated PR number. Below is stored bottom-first and above nearest-first, and neither includes the own PR. Member URLs use the repository's normal PR URL form. Non-open links have empty stacks, and failed open-set reads keep prior stacks. The stack never takes part in CI or transition decisions. The cockpit's open-PR count counts its members, each distinct `(url, number)` once. GitHub's first 100 open PRs and Tea's list and server page limits can leave a shorter stack on busy repositories.

#### CI verdicts

The CI verdict comes from the most specific commit:

| Target | Verdict source | Commit kept with the verdict |
| --- | --- | --- |
| Open PR | The PR head's check rollup on GitHub, or combined status read by branch on Gitea. | `PrLink::ci_sha`: the GitHub rollup's `commit.oid`, or the Gitea response's `sha`, when supplied. |
| Merged PR | The merge commit's checks, falling back to the PR head's when the merge commit has none. GitHub rereads it on every due probe, so a CI rerun moves the verdict. Tea stops rereading an owned merged link once its verdict settles. | `PrLink::ci_sha`: GitHub's `mergeCommit.oid` when its rollup answered, otherwise the PR rollup's `commit.oid`. On Gitea, the `sha` of whichever combined-status response answered. |
| Path without a PR, trunk included | The exact local HEAD commit, stored in the `branch_ci` map. | The local head queried, kept in `head_seen`. |

`ci_sha` is absent when the verdict or its commit is unknown. Older cache files without it still load with an unknown CI commit.

Gitea answers a commit that no check reported on with `state: "pending"`, `total_count: 0`, and `statuses` null or empty. `forge::parse_tea_combined_status` reads that response as no verdict and no commit, so a PR without CI draws no CI marker and never joins the pending hot tier. A response that reports any status, by count or by record, keeps its aggregate `state`, and so does one without a `total_count`.

#### When a repository is probed

A repository is due when its tier TTL has passed, when a target's HEAD differs from the last seen HEAD, or when a target has never been probed. The tier is `PR_STATE_HOT_TTL` (20 seconds) when any of its worktrees is hot, focused, has a pending verdict, or has an open PR in the merge queue, and `PR_STATE_TTL` (5 minutes) otherwise. Branch rows join the uncached and pending or queued hot tiers without synthetic paths reaching disk. A probe in which any target's reading fails counts as failed for the repository and backs off from `PR_STATE_RETRY_TTL` (30 seconds), doubling up to the tier TTL. Each target whose reading failed keeps its last-known-good link and head CI, while the targets read in that pass publish their fresh readings. A retryable discovery failure is timed apart from any repository by its `discovery_failures` entry, keyed by checkout path: the path is rediscovered when that entry backs off the same way from `PR_STATE_RETRY_TTL` up to the path's tier TTL, and it adds no due input to a repository meanwhile. The entry is cleared once discovery finds a target or a definitive absence, or the path leaves demand.

GitHub resolves a due repository with one `gh api graphql` request that aliases every branch lookup and every distinct HEAD commit. It splits into further requests only past `GH_BULK_MAX_ALIASES` (100). The count is two per checkout PR lookup, three per demanded branch (PR, facts, head ref), and one each for a distinct HEAD and the optional repository open set. Each branch lookup includes an open-only facts alias in that same request.

Tea lists open PRs once per repository and reads combined commit status per open branch. It runs per-PR reads only for a path that drops off the open list while its prior link is open, merged without a settled verdict, or no longer owned. Demanded branch targets also share one all-state list per repository pass, from first sight. Terminal candidates use the detail API, and head CI uses the branch ref. A target whose PR reading fails gets no CI read in that pass, so its carried link keeps its prior verdict.

#### Transitions become signals

Each publication is diffed against the previous one ([`refresh/pr/transitions.rs`](../../../crates/rimz/src/sidebar/refresh/pr/transitions.rs)):

| Change | Signal |
| --- | --- |
| A link leaves the open state | `pr.merged` or `pr.closed` |
| A continuous target gains an owned open PR without a prior owned open link of the same number | `pr.opened` |
| An open GitHub PR is behind its live base (`behindBy > 0`), on entry or a changed forge head | `pr.behind` |
| An open GitHub PR has settled conflicting mergeability, on entry or a changed settled-at head | `pr.conflicted` |
| An open GitHub PR is in the merge queue, on entry or a later `enqueuedAt` | `pr.queued` |
| An open GitHub PR has a queue removal not superseded by a re-arm, for a reason other than `merged`, on entry, a later removal, or withdrawal of the re-arm | `pr.dequeued` |
| A PR's CI verdict, or a PR-less path's verdict for a commit the branch added (trunk exempt), settles to passing or failing | `ci.passed` or `ci.failed` |

A transition counts only for a target read successfully in this pass whose stamp is continuous. `target_seen` holds the stamp of a target's last successful reading. A failed reading keeps it only while it still names the target. A branch switch or a failed reading therefore emits nothing, a success after a first-sight failure is first sight, and a success after a failed pass under the same stamp compares against the last successful reading. In a Tea repository, one target's failed reading does not hold back its siblings' signals. PR links must belong to that stamp, and terminal PR transitions still require a prior open link. A PR-less path emits only for a commit the branch added: a known HEAD matching the worktree marker's base commit, or the cached merge base (an ancestor of the resolved trunk), is inherited and emits nothing. Trunk targets are exempt, and unknown facts keep emission on. The badge still shows the inherited verdict.

The payload carries `path`, `branch`, and `repo`, plus `number` and `url` when known. `pr.*` also carries `state`. For `ci.*`, `head` is the verdict's commit (`PrLink::ci_sha`, or the PR-less read's `head_seen`), never a fallback to the local head for a PR. `pr.*` keeps the local worktree HEAD. A known nonempty `head` adds a `checks_url` built from the target's `RemoteRepo` (GitHub's `/commit/<head>/checks` page, Gitea's commit page). An unknown commit omits both fields. The producer stays read-only: it spawns a detached `rimz events emit --source forge`, which appends the event durably and fires subscribed loop and wait tasks ([loops.md](../harness/loops.md#the-signal-vocabulary)).

#### GitHub open-PR facts

Open GitHub links cache the forge head, base name, behind count, last settled mergeability with its settled-at head, auto-merge request presence, and a draft-first review fact. The facts alias requests `headRefOid`, `mergeable`, `isCrossRepository`, `isDraft`, `reviewDecision`, and `baseRef { name compare(headRef: <branch>) { behindBy } }` only for open PRs, alongside the queue fields below. `auto_merge` defaults to false and is omitted when false. `review` is omitted when unknown and otherwise stores `draft`, `changes_requested`, `required`, `approved`, or `none`. A draft wins over the decision. On a non-draft PR, a null decision is `none`, while missing draft facts leave review unknown. Non-open links carry no facts, and Tea supplies none, so Tea emits none of the four GitHub-only signals.

`pr.behind` and `pr.conflicted` key on a per-head value: the forge head when `behind_by > 0`, or the settled-at head when mergeability is conflicting. A nonempty next key different from the prior key fires. A missing, unowned, non-open, or fact-free prior link has no key, so first sight on a continuous target fires too. Repeated readings do not fire, and leaving and re-entering the state can fire again for the same head. Both payloads carry the PR context with `state: "open"`, `pr_head` (the key), and `base` when known. Only `pr.behind` adds `behind_by`. `head` stays the local worktree HEAD, not the forge head.

`UNKNOWN` mergeability carries the prior settled value forward only for an owned link with the same PR number, even after a push changes the forge head. A later settled conflict at that new head can then fire once.

`crates/rimz/src/forge/pr_state.rs::PrLink::current_mergeability` reads a settled answer only for an open link whose nonempty forge head matches the answer's head. The condition evaluator uses that reading, and `crates/rimz/src/sidebar/enrich.rs::project_pr_state_map` projects a current conflict to `SidebarWorktreeGroup::pr_conflicting`. Trunk groups, groups with no checkout or link, and Gitea links without open facts project false. The field colours the cockpit PR count and supplies the header conflict marker, never a CI verdict.

A local PR-head change nudges a probe immediately. A carried answer at the old head reads unknown until GitHub settles. A base move alone waits for the repository's tier TTL: 20 seconds for a hot, focused, pending-CI, or queued target, otherwise 5 minutes. If GitHub still answers `UNKNOWN`, the previous same-head answer remains visible until a later probe settles, so a base-created or base-cleared conflict can take one or more tier TTLs to appear. The [`pr.mergeable` condition](../../reference/cli/loop.md#conditions) describes the same head-keyed limit.

The behind distance is scoped to its own PR. Null `baseRef` or `compare` means unknown distance and never fires `pr.behind`. Fork PRs never fire `pr.behind`, because the comparison resolves the head branch name in the base repository, while their mergeability still applies. A `reviewDecision` error under a requested `facts<i>` alias leaves only that PR's review unknown, except that a draft still stores `draft`. It does not blank review on another alias. Other non-queue errors under a requested facts alias leave that PR's distance unknown without failing the repository probe, even when `gh` exits nonzero. An error on non-null `isDraft` nulls the node, leaving no open facts. Review and auto-merge presence are read fresh on each successful probe, never carried forward. Other GraphQL errors, missing data, and command timeouts fail the probe.

#### Merge-queue facts

An open GitHub link also caches one merge-queue fact, `queue`, read inside the same facts alias through `mergeQueueEntry { enqueuedAt }`, `autoMergeRequest { enabledAt }`, and the latest `RemovedFromMergeQueueEvent` (`createdAt`, `reason`, `beforeCommit { oid }`):

```json
"queue": { "state": "queued", "at": "2026-10-03T12:28:46Z" }
"queue": { "state": "dequeued", "at": "2026-10-03T12:46:03Z", "reason": "failed_checks", "commit": "3ba93ec…" }
```

This fact is the only trace of a queue failure. The queue runs CI on its own commit, which neither the PR head rollup nor a local HEAD rollup sees. A present queue entry is `queued`, stamped with its `enqueuedAt`, regardless of any auto-merge request. With no entry, the latest removal is `dequeued`, stamped with the event's `createdAt`, unless the PR was re-armed (an auto-merge request enabled after the removal). That request's `enabledAt` must parse strictly later than `createdAt`. A tie, a missing or null `enabledAt`, or an unparseable timestamp on either side leaves the removal standing. While re-armed, the queue fact is absent and `pr.queue` reads `armed` from the stored auto-merge presence. `reason` is GitHub's string verbatim when supplied, and `commit` is the queue's own commit, absent when GitHub names none. A removal whose reason is `merged` is no fact: the PR is about to read merged, and `pr.merged` is its only signal whichever of the two the poll sees first. `dequeued` holds until the PR is queued again, re-armed, merged, or closed. A push alone does not clear it. A poll that returns no facts node drops the fact rather than carrying it.

`pr.queued` and `pr.dequeued` key on the fact's timestamp under the same continuity, ownership, and successful-reading rules as the head-keyed pair, so a first reading on a continuous target fires and a repeated reading does not. A removal already superseded by a re-arm has no fact and never announces `pr.dequeued`, even on first reading. If that re-arm is withdrawn, the removal stands again and fires `pr.dequeued` with the original `dequeued_at`. A fresh room starts from an empty cache, so its first poll only stamps the target, and a standing `queued` or `dequeued` is never announced there. `pr.queue` is how it is read. Their payload keeps `pr_head` as the PR head and puts the timestamp in `queued_at` or `dequeued_at`. `pr.dequeued` adds `reason` when supplied and, when the fact has a commit and the remote builds one, `queue_checks_url`.

Queue errors fail the whole repository probe. A GraphQL error whose path reaches `mergeQueueEntry`, `autoMergeRequest`, or `timelineItems` fails it, since a nulled entry or request would otherwise surface a stale removal. The prior links carry and nothing emits, while a `compare` error stays scoped and keeps the queue fact. A server whose schema lacks any of these fields rejects the whole query, so the repository probe fails there.

### Sidecars

Per-session sidecars (`agent_context/`, `subagent_context/`, `agent-activity/`, `active-time/`) are the one exception to producer ownership. Hook and statusline runs write the context and activity records, hooks update the active-time accumulators under per-record locks, and the host's transcript watcher refreshes transcript-tail context between hooks ([push channels](#push-channels)). The shared host fold reads context and activity behind stat-gated parse caches. The [hibernated hold](#cadences) retains each key's last value without a stat between checks, preserving its parse memo. A due unchanged sidecar costs one stat and no parse. Removing a key drops its hold clock and memo. The one-shot `rimz sidebar` producer read ([`produce_snapshot_with_refresh`](../../../crates/rimz/src/sidebar/produce/mod.rs)) clears all keyed hold clocks after refreshing heavy lanes, so its second fold rechecks sidecars, ledgers and parks.

## Realtime events

Wakeup datagrams carry `SidebarEventEnvelope` ([`wakeup/events.rs`](../../../crates/rimz/src/wakeup/events.rs)): a schema version, the workspace id, an optional session scope, a sender timestamp, an optional pane-observation timestamp, and the typed event. A `rimz sidebar wake` that accepted a Zellij topology puts that topology's `produced_at_ms` in `panes_observed_at_ms` on every event in the batch. Topology-less and stale wakes, tmux, and other senders omit it. Structural width decisions use that observation as their proof floor, falling back to `sent_at_ms`. Focus repair, focus ordering, and overlay supersession still use send time.

`session_name` is the scope. `Some` targets the one mux session whose pane ids the event names. `None` reaches every room host of the workspace, which is how store deltas and reloads travel. The host drops an event for another workspace or session once. Reload words and envelopes reach the host inbox directly. The plane records every other envelope once, then fans it out to subscribers' bounded wake channels for pane-local reactions and producer verification. The host's tmux watch and body-filter saves use the same in-memory ingress without a datagram.

Events divide by what the receiver does with them:

- Overlay events land in the in-memory event store and change what the next fuse paints. Exactly four qualify: `PaneClosed`, `CommandChanged`, `FocusChanged`, and a `PaneOpened` that carries a command.
- Nudges and actions are consumed on arrival. Some ask the producer for a verifying pull, some drive a renderer action, and none touch the overlay store.

The plane owns one overlay store ([`event_store.rs`](../../../crates/rimz/src/sidebar/event_store.rs)), shared by its attachments and diagnostic observer. Each pane fuses its own projected baseline against it. The store keeps one slot per key (per pane per event kind, plus one focus slot), latest stamp wins, capped at 256 entries. Each entry records `sent_at_ms`, used for supersession against the pane frame, and the host's receipt time, used for expiry after `EVENT_STORE_TTL` (12 seconds, inclusive). A late pane cannot extend that lifetime or reinsert an expired overlay. The overlay cut a [view borrow](#client-views) takes is a clone of the store that shares its entry vector by reference count, so a cut copies no events. An append, prune, or cap that changes the store detaches the vector and leaves every outstanding cut as it was, and an append identical to the stored entry changes nothing.

A pane keeps its baseline only while a fold applies an overlay or focus intent, or while the gate holds a rejected pull. The next pull or synthetic fold that finds neither overlay nor intent releases the baseline. Event expiry alone does not trigger a fold or repaint.

### Event taxonomy

| Event | Payload | What the receiver does | Emitter |
| --- | --- | --- | --- |
| `PaneClosed` | `pane_id` | Delete every row bound to the pane. Highest precedence in fusion. | Host presence projector |
| `CommandChanged` | `pane_id`, `command` | Overlay the command until a pull verifies the pane's row shape. | Host presence projector |
| `FocusChanged` | `focused` and `unfocused` pane id lists | Set `SidebarSnapshot::focused_pane` to the current pane and mark it viewed. A transition naming only the prior pane clears the register. | Host presence projector, from client-derived Zellij focus or tmux pane and view focus |
| `PaneOpened` | `pane_id`, optional `command` | Nudge a producer verification pull. Admits no card on its own. | Host presence projector |
| `PanesChanged` | none | Nudge a producer pull: topology moved, identity unknown. Mark structural evidence and prove a pending width baseline, without re-arming convergence. | Projector fallback, or an incomplete tmux layout |
| `StoreDelta` | optional event method and lifecycle signal | Refetch the rollup. A session start or end also requests fresh panes. | Store and context-sidecar writers ([store.md → wakeups](../store.md#wakeups)) |
| `FocusIntent` | target `pane_id`, nonce | Fold the durable focus anchor at once, unless the same nonce was already folded through the host push. | Renderer jumps |
| `FocusStranded` | owning sidebar `pane_id`, generation, client views | Focus repair in the matching renderer (see below). Other renderers ignore it. | Host presence projector, from a settled Zellij switch or a tmux window switch |
| `WidthTargetChanged` | none | Re-read the room-runtime width share, resolve it against this renderer's view, and converge only its own pane. | The resolver or renderer that published a new target |
| `BodyFilterChanged` | none | Re-read the whole body lens and adopt pick and committed query without a producer fetch, leaving any local draft intact. | A renderer that changed the lens or auto-cleared its empty pick |
| `Notify` | `title`, `body`, target panes, `recheck_unread`, kind | Raise the desktop notification and the tab bell. `recheck_unread` gates the bell on row-unread, not the desktop notification. Never fused into rows ([notifications.md](./notifications.md)). | The fetch worker, after it has run any notification command handlers itself |
| `Reload` | none | Observe the durable workspace target: a changed host build drains attachments for reattach, and an unchanged build refetches in place. Supervisors poll the record independently. | `rimz reload` |

`FocusStranded` repair keeps the renderer's baseline if that is a live visible work sibling, and otherwise picks the leftmost sibling. Distinct observed client views leave focus alone, because `focus-pane-id` is session-global. The repair reads the strand's sample on Zellij and the pulled `client_views` on tmux, never fused focus or intents. It is dropped after `FOCUS_STRANDED_EVENT_TTL` (2 seconds), so late delivery cannot yank focus.

On tmux, a direct pane-focus transition never lists sidebar chrome in `unfocused`, so focus leaving a sidebar arrives as `unfocused: []`. A window switch is different: it names the previous window's active pane as the prior pane whatever its role, so a sidebar can appear in `unfocused` there (`crates/rimz/src/sidebar/presence/tmux.rs::TmuxPresenceState::switch_window`).

`Reload` also travels as a bare control word, so it reaches a renderer whose event schema predates the current one. Pane rows carry no focus bit: focus lives only in the session register.

### What triggers a mux-derived event

Neither backend constructs a `SidebarEvent`. Both normalize what they see into presence transitions, and the shared projector ([`presence/projector.rs`](../../../crates/rimz/src/sidebar/presence/projector.rs)) decides the event.

| Room change | Event | How each backend sees it |
| --- | --- | --- |
| A pane joins the room | `PaneOpened` | Zellij diffs a new terminal id out of the announced manifest. tmux takes the first non-seeding subscription line naming an unknown pane. |
| A pane's command changes | `CommandChanged` | Zellij compares the pane command across two live manifests. tmux reads the changed command field of a subscription line. |
| A pane leaves the room | `PaneClosed` | Zellij finds the terminal id absent from the new manifest. tmux takes a window-close line, or a pane missing from the layout roster. |
| Focus moves between panes | `FocusChanged` | Zellij projects session focus from client observations. tmux takes a newly active subscription pane or a pane-changed line only in a session's current window, seeded at attach from the pane seed's session id and window-active flag (falling back to any window only if no current-window seed arrived). A hidden window's active pane is window-local state, kept for a later view switch. |
| A view switch lands away from a sidebar | `FocusChanged` | Zellij settles the switch generation. tmux takes the window-changed line. |
| A view switch lands on a sidebar that has a working sibling | `FocusStranded` | The same inputs, classified by the landed pane's role. |
| The layout cannot be read whole | `PanesChanged` | tmux only: a window holding a floating pane, or a layout line that fails to parse. |
| Topology moved but no typed event resulted | `PanesChanged` | The projector's fallback, from either backend. |
| A divider drag resizes panes, roster unchanged | `PanesChanged` on Zellij, nothing on tmux | The Zellij plugin hashes pane position and column count, so a drag republishes an announced manifest with no roster, command, or focus diff. The tmux subscription carries no geometry. |
| RimZ's own width nudge resizes panes, roster unchanged | `PanesChanged` on Zellij, nothing on tmux | The resize republishes the same no-diff manifest as a divider drag. |

The divider-drag row has a consequence: a renderer that reads `PanesChanged` as structural evidence reads a Zellij divider drag as structure moving. Width control still latches that marker, so Zellij drags still snap back rather than pinning the room share. A nudge's echo carries the same event, so `PanesChanged` never re-arms convergence or interrupts an armed drag classification. It proves geometry only while the baseline proof is pending.

Each observation also carries event eligibility by pane role, which keeps each backend's established stream:

| Pane role | Zellij | tmux |
| --- | --- | --- |
| Work pane | All events | All events |
| Sidebar | No open. Close, command, and direct focus. | Direct focus only |
| Launch chrome | All events (an open carries no command) | None |

Launch chrome is `rimz agents` followed by an implicit launch spec, the `launch` verb, or launch options before the spec. Every other agents subcommand and alias, hidden helpers included, and `-h` or `--help` remain ordinary commands. Zellij scrubs only launch chrome. A command overlay containing only the bare program name `rimz` leaves the pulled rows intact until the next pull supplies argv. It never guesses whether that command launches an agent. Other command overlays remain immediate. For ordinary tmux RimZ commands this postpones the busy row by one data tick while watched, or up to the five-second backstop while unwatched.

View switches follow their own rule on both backends: landing on launch chrome emits `FocusChanged`, and landing on a sidebar with a working sibling emits `FocusStranded`.

### Push channels

A push channel lets a change a writer already knows about reach every renderer within one wakeup instead of a poll window. The producer's pull stays the structural backstop behind all of them.

- Store and sidecar writers post a `StoreDelta` after every durable write or context-sidecar merge, so status, tokens, and cost repaint within one wakeup.
- The Zellij presence plugin publishes topology snapshots and client observations through `rimz sidebar wake`. That CLI process accepts one writer under the topology lock, derives focus, runs the projector, publishes `lanes/pane-topology.json`, and stamps `live/presence.stamp`. Its events reach the host over the room socket. What the plugin sends, how often, and how competing writers are fenced and retired is [multiplexers.md → The Zellij presence plugin](../multiplexers.md#the-zellij-presence-plugin).
- The tmux control-mode watch, run by the host, keeps only out-of-order stream state, maps subscription and focus lines into the same transitions, stamps `live/presence.stamp`, and feeds the same projector. The plane records its events once and fans them out in memory to subscribed panes ([multiplexers.md → The control-mode presence watch](../multiplexers.md#the-control-mode-presence-watch)).
- The host's transcript watcher ([`transcript_watch.rs`](../../../crates/rimz/src/sidebar_pane/app/transcript_watch.rs)) watches each live session whose adapter declares `transcript_tail_context` (Codex, Copilot, Cursor, Droid, Grok, Kimi, and Kiro), and runs the stat-gated refresh on write to cover mid-turn gaps between progress hooks. Every five seconds it folds its cursor and stats the sidecar directory before deciding whether to rescan records. An unchanged log extent and directory mtime skip the roster rebuild for up to 60 seconds, which bounds coarse-mtime misses. Due held keys wait for an ordinary rebuild. Their deadlines and thaws never reopen the gate. A rescan reads the cached hibernation record and context sidecars only for the rollup rows that have not ended, so an orphan sidecar costs nothing. Hibernated rows follow the [per-agent hold](#cadences), retaining their cached targets and OS watches without sidecar metadata reads between checks. Those watches remain ready through a thaw without a rescan. A failed watch registration leaves the gate open for the next five-second retry, which can reuse a held target without rereading it. A watcher that never starts costs nothing. The producer-tick refresh remains the backstop, on the same hibernated cadence.
- The host's cache refresher ([`cache_refresh.rs`](../../../crates/rimz/src/sidebar_pane/app/cache_refresh.rs)) ticks on the data cadence without a rollup cursor or a fold of its own. It reads the room's data tick after each sleep, so a pane that joins or leaves during the sleep moves that pass's freshness and wait budget and the next sleep. It consumes the worker's newest successful fold when its sample age is strictly below the room's backstop interval plus one refresher tick, measured before input reads. The extra tick avoids racing the backstop's in-flight fold. Otherwise it sends one ordinary request and waits at most one tick for the first publication sampled after the request. A failure or timeout skips heavy lanes until the next pass. Cold start waits the same way for the worker's first fold, which may be frameless. Heavy lanes act on that fold's clock, up to 6 s old while unwatched or 2 s while watched at the default tick. They emit [forge signals](#pr-state) and [trunk signals](../harness/loops.md#trunk-and-worktree-signals). Regardless of fold acquisition, the pass fires due loop tasks (including the watch-lost backstop for a dead `rimz wait` watcher), wakes due scheduled messages and runs due daemon-view repair against the latest retained frame, with fresh wall time. A heavy-lane panic is isolated, and the next tick retries from the worker's fold and heavy-lane caches.

### What presence data drives

Focus buys a fast tick for the work the user is watching. The producer folds `PaneFrame.viewed_panes` into the snapshot. Git edit-sensitive facts for the viewed worktree and process metrics for the viewed pane run on the focused tier, while commit-shaped git facts and every background worktree and pane stay on their slower cadences. The other side effects gated on `viewed_panes` are listed in [multiplexers.md → Who is looking at what](../multiplexers.md#who-is-looking-at-what).

Client presence is classified against the reader's `now_ms` by `SidebarPresence::classify`: `Detached` when no human client remains, `Idle` once input has been quiet for `[sidebar] afk_after_secs` (15 minutes by default), and `Active` otherwise. Both backends supply per-client clocks: tmux's `client_activity` and Zellij's plugin-observed human `UserAction` stamps, joined to attached clients. CLI actions and buttonless mouse motion do not advance the clock. With no known input stamp, an attached room stays `Active` until input supplies one. Remote rooms honour the same setting. On both backends it also bounds [departed-view retention](#client-views).

On both backends, while a client is attached, the producer re-samples presence and client modes every `PRESENCE_SAMPLE_TTL` (1 second), even before an input clock is known. It records `presence_probed_at_ms` in memory before sampling, so failed attempts also suppress bursts, and a restart loses at most that throttle window. An unchanged sample does not rewrite `lanes/snapshot.json`, and pane publications send no self-wake. A mode change updates `client_modes` without refreshing the topology age. A failed fallback focus probe carries the prior presence and viewed panes from the retained frame.

## Fusion rules

Fusion is pure over pulled truth, the event store, and `now_ms`. It runs on the render thread on every paint that has an overlay or intent to apply. An unmodified pull goes straight to presentation.

Supersession comes first. The baseline is `panes_observed_at_ms.or(panes_produced_at_ms)`, and an event no newer than the pane observation is skipped, because the pull already saw later truth. The exception is a `PaneClosed` naming a carried pane, which applies at any age: the frame held that pane on process evidence without seeing it, so nothing in the frame supersedes the close. The close also retires the carried-pane notice.

The surviving overlays then apply in precedence order:

1. `PaneClosed` deletes rows and clears a listed child's matching pane binding, returning its entry click to the parent. If it names `focused_pane`, the register clears and the renderer keeps its last highlight.
2. `CommandChanged` overlays the command on panes that survived step 1 and were already admitted, as one tenant transition in `SidebarSnapshot::overlay_pane_command`. A bare single-word `rimz` waits for the pulled argv, and a pane that already shows the command is left as pulled, its process start included. When the command projects no row, or projects an agent of the kind the row already runs (bound or idle), the tenant stays: the row keeps its card and enrichment, and only its pane command changes and its process start clears. Any other projection (another agent kind, a process row on exit to the shell, an agent replacing a process) is a new tenant: the projected row replaces the old one and inherits only the pane slot, which is the attention stamp, the old worktree path when the projection has none, the sinks when the new row is a process row, and the unread mark when the new row is an agent under the same id. Everything else, a bound card's due messages included, starts fresh until the next pull.
3. The newest `FocusChanged` sets or clears the session register, as in the taxonomy. With one observed client, a singleton focus replaces its old `viewed_panes` until the next pull, so the departed tab stops painting at once. Unknown or multiple clients keep the conservative union, and client-view membership changes only on a resolved sample. With one observed client, a singleton focus away from this sidebar also cancels its optimistic resize and focus watching.
4. A requested focus intent lands last and outranks both the pulled register and `FocusChanged` for `FOCUS_ANCHOR_FRESH` (2.5 seconds), provided its pane is an admitted row's own pane or a listed child's. This presentation overlay adds to `viewed_panes`, not the observed `client_views`, and cannot make a strand's client-ambiguity guard defer repair.

`PaneOpened` creates nothing: it asks the producer for a verified frame. A wrong verdict from a missed event lasts until the next producer pull. A skewed sender clock can stamp an event later than the following pane observations, so it can outlive several pulls, but expiry runs on the receiver's clock, so it never lasts past `EVENT_STORE_TTL` (12 seconds) after receipt.

## Focus intent

A RimZ-initiated focus action, a user jump or an automatic repair, is a two-phase intent in `lanes/focus-anchor.json` ([`mux/focus_anchor.rs`](../../../crates/rimz/src/mux/focus_anchor.rs)), a rename-atomic runtime record written without fsync. The one exception, a bare jump after a Zellij focus-taking directional split, is in [multiplexers.md → jumping to a pane](../multiplexers.md#jumping-to-a-pane). The two phases are:

- `Requested` is written and broadcast with `FocusIntent` before the one-way mux focus command.
- `Applied` records that the mux accepted the command, without reseeding presentation. Native confirmation and fencing read this phase.

### The anchor record

The file is workspace-wide and client-scoped. It carries a nonce, the session, the target pane, the origin, the exact pre-action client map, an optional input stamp, an optional card placement, and the frozen row order from the source frame. The version is `rimz.focus-anchor.v4`. Its optional `placement {row_id, viewport_row, held}` is the card's own first line relative to the source scroll-zone top, signed when clipped above, together with the ids open by hold or selection in that source frame. A missing `held` defaults to an empty set, and an empty set is omitted. Readers also accept v3, ignoring its line offset and yielding no placement. Other versions are ignored.

For every caller, `issued_at_ms` is stamped after taking the anchor lock and sampling native clients. `applied_at_ms` stamps actual mux acceptance, independently of request work or dispatch delay.

The optional `input_at_ms` carries the originating sidebar input's instant, converted to wall time before detaching the worker. Other callers omit it, and older records default it to absent. Only pending-pick replacement reads it, falling back to `issued_at_ms` when absent. Confirmation, freshness, anchor ordering and identity continue to use request or acceptance time, not input time. The field is omitted when absent and needs no version bump: older readers ignore it.

The fetch worker reads the anchor once per fold cycle and shares that observation with every projection, alongside the room body filter. The painter resolves focus against its view's clients and applies jump placement only in the owning or initiating view. Confirmation, read intent, and gate and health reduction travel with that view. Read sweeps load the current room mark record through the stat-keyed parse cache. Explicit actions and event-only folds read live state. Retiring an observed intent always compares its nonce with the live file, so a newer intent written after the shared read cannot be cleared by an older fold. A retirement lands in the view whose borrow queued it (`crates/rimz/src/sidebar_pane/app/loop_state/shared.rs::ViewBorrow`, its `target`): a hidden pane's Scratch fold retires in Scratch, never in a shared view an earlier read routed to.

### Verdicts

Native client observations resolve the intent, with the pre-action client map as the fence. [`observation_outcome_from`](../../../crates/rimz/src/mux/focus_anchor.rs) checks these rows in order, and the first match wins. Fresh means within `FOCUS_ANCHOR_FRESH` (2.5 seconds) of the request or, for an applied intent, of acceptance.

| Order | Condition | Verdict | Effect |
| --- | --- | --- | --- |
| 1 | The observation names another session or no session, or the target left the roster. | `Invalidated` | Drop the overlay. A sidebar filters out another session's anchor before judging it, so it never presents, invalidates, or retires that anchor. |
| 2 | Requested, and fresh. | `Present` | Keep presenting the target. |
| 3 | Requested, and stale. | `Invalidated` | The request was abandoned. Drop the overlay. |
| 4 | Applied, with no `applied_at_ms`. | `Invalidated` | The record lacks its acceptance stamp. Drop the overlay. |
| 5 | Applied, client presence unknown. | `Present` while fresh, then `Fence` | Yield unknown instead of restoring stale evidence. |
| 6 | Applied, and no client remains or the client id set changed. | `Invalidated` | Detach or replacement. Drop the overlay. |
| 7 | Applied, and every observed client views the target pane. | `Confirmed` | The action landed. Retire the intent. |
| 8 | Applied, and the client map moved somewhere other than the target. | `Superseded` | Something else took focus. Drop the overlay. |
| 9 | Applied, and the pre-action map is unchanged. | `Present` while fresh, then `Fence` | Keep presenting, then yield unknown. |

A requested intent ignores the client map: only an applied one is judged against it.

### Placement and the click guard

A jump carries the clicked card's painted position so the destination can land it on the same row. The sidebar captures a visible clicked card's own first line relative to its scroll-zone top, and a pane-backed child uses its parent card. The placement carries the opening set it was measured under: held expansions plus the last drawn selection. The destination composes its landing frame from that set instead of its own holds and previous selection. This one-paint carry is a geometry fact about the source frame.

- A same-host jump lands in the initiating client's view without reinstalling order or restarting its hold. Carried order is a fallback only for external or recovered anchors without a live source view.
- An off-screen repair and non-sidebar focus carry no placement.
- With a placement, a fresh request queues positioning for the next draw using the destination's zone top. Without one, it leaves the viewport anchored.
- Only a focus requested by this view's own input may reveal an off-screen card, and acceptance cannot apply the same request stamp twice. A newborn card under the derived focus is revealed by reconciliation instead, without authority ([composing the frame](./sidebar.md#composing-the-frame)).

Portable anchors stay relative to the scroll zone. Each pane keeps its signed absolute painted placements, correction-clamp facts, and banner visibility for local observation.

Clicks resolve against the painted rows, never a newer roster. Each draw writes the projected roster's row ids beside its hit map, and a row click resolves the painted id in the current roster rather than a newer roster's ordinal. A departed id is swallowed without changing selection, ending search, or re-arming the freeze. The screen-edge keys `H` and `L` resolve the painted window's first or last id the same way. When that row has departed they take the nearest painted row inward that is still listed, and with none left they do nothing. A watched non-input paint that moves a previously painted card keeps the preceding hit frame for 400 ms. Further moves keep that first frame and deadline, clicks at exactly 400 ms use the current frame, and an input paint clears the guard. Unwatched paints clear the guard and never arm it. A birth reveal's glide counts as a move the user did not make: its frames neither clear the guard nor read as input, while a wheel glide's frames do. Resize delivery shares the redraw path but is not user input: while watched, it keeps an active guard and can arm one when its paint moves a card. The loop owns the monotonic deadline, and rendering only writes geometry back.

The shared input cut is stamped before its reads. A pane's later focus-anchor observation takes precedence over older cuts. An actual retirement fences their pre-jump focus unless a later native focus event supersedes it, and ordinary anchor absence does not fence native focus. A later local filter observation or write makes older filter sync non-authoritative. A later cut still converges missed events, and the complete snapshot still passes through fusion, gate, health, and local application. Receipt lookup reads the current room record, so an old cut cannot renew a clear for unchanged activity.

### The cross-tab handshake

A user jump to another tab in the same host waits for the destination to paint before it focuses, so the user never sees the old frame in the new tab. Same-tab jumps and automatic repairs skip all of this.

1. Push. The source writes the `Requested` anchor and also pushes it to the attachments that own its target ([`app/focus_push.rs`](../../../crates/rimz/src/sidebar_pane/app/focus_push.rs)). The host resolves them once, after the fit and immediately before the offers, from its published fold and without the views mutex: an attachment other than the source owns the target when its own view in the fold's frame (`SidebarOwnView::from_frame`) is the target's pane or lists it among its working panes, the rule each peer applies to itself. The first owner in the target tab's pane order holds the jump's landing until the send instant plus `FOCUS_RESUME_WATCH_WINDOW`, while the jump is current. With no owner (no frame, a target no tab lists, or no attachment but the source in its tab) the host offers nobody, names no landing, and dispatch follows at once; the destination paints on arrival. Peers fold its target, optional card placement, and frozen order once per nonce across push and datagram.
2. Fit (tmux only). Before the offers, tmux freshly probes the destination and fits it if stale. Zellij adds no geometry probe or fit.
3. Wait. The source waits off the render loop until the destination's frame is written, every offered peer has released, or the deadline at click + 500 ms passes. Request work and any fit spend that same budget. A fit never resets the deadline, and a fit that uses it up leaves no paint wait.
4. Dispatch. The source sends the mux focus command with the existing nonce check.

A push has priority over ordinary inbox wakeups and carries the anchor value as an arrival observation without reading the file. When folded, older shared cuts yield to it and newer reads supersede it. The owner tries the existing gated paint inside the push handler, ahead of maintenance. Each peer answers with one verdict ([`crates/rimz/src/diag/focus_trace.rs::PushVerdict`](../../../crates/rimz/src/diag/focus_trace.rs)):

| Verdict | When |
| --- | --- |
| `painted` | The destination wrote a frame with the owning card selected, its placement consumed, and its card on the requested row. |
| `displaced` | The destination consumed the placement but the card painted on another row or not at all. |
| `not_destination` | The pushed peer's own fold does not own the target (a publication newer than the host's read moved it), or the anchor names another session. |
| `exiting` | The attachment is closing. |
| `expired` | The push's deadline passed before a qualifying paint. |
| `superseded` | A newer click replaced this push. |

`painted` and `displaced` release the source's paint wait. A pushed peer keeps its own ownership check after its drain and fold: when its fold disagrees with the host's read, it answers `not_destination` and gives its watch mark back, and the landing named for it is not revoked but ends at its deadline or with a newer jump. An attachment the host did not offer the push receives only the `FocusIntent` event, which a settled hidden pane declines at its `event_needs_fold` gate.

A fitted push also carries the expected rows per destination pane. Both cached-frame and parked acknowledgements then require the last painted height to match the attachment's own expected rows. A missing expectation, including an absent own-pane entry, keeps the ordinary predicate. Acknowledgement does not check columns, because sidebar width control may change them after a fit. When the fit actually reasserted the sidebar's legit width, the own-pane expectation also carries the columns tmux laid out. A resize landing at exactly that rows-by-columns size bypasses the held-grow paint hold, and a push arriving after the resize releases an engaged hold only at that exact size. Rows-only expectations and mismatching sizes keep the ordinary hold path.

A resize paint hold, empty-tab confirmation, or exit can prevent acknowledgement, and the wait cap still permits dispatch. If every offered handle drops, including a failed destination delivery, dispatch can proceed before the cap. While a lease is active, a loop ignores early or obsolete focus datagrams until the current pushed nonce is registered, and ordinary paints also wait for that nonce to fold. The push carries the durable anchor, so this avoids painting an older request before the current request thread reaches its store.

Every handshake records its source outcome and per-peer stages in [`audit/focus.log.jsonl`](../diagnostics.md#push-handshakes), after dispatch and bounded late-report collection. A `FocusIntent` missed outside this push path waits for the next event or pull while the file stays unresolved. If it was already retired, the first native-focus fold moves the highlight without revealing the card.

Automatic repairs append to the account-global `focus-repairs.log.jsonl` at command acceptance (`AcceptedUnconfirmed`) or failure, and again when observation confirms, supersedes, or invalidates the action. Dispatch records carry the final live fence sample in `observed` and the request count in `attempts`. Abandonment and later resolution records use zero attempts and no fence sample. Records without these fields read as an empty sample and one attempt.

### Jump leases

The host's jump lease orders user focus requests, including same-tab jumps, so a detached worker starting late cannot overwrite a newer intent. It is armed on the source loop before the synchronous click paint, with a monotonically increasing click sequence, the target pane, and the click + 500 ms deadline. It fences obsolete pushes and paints and does not suspend room work. Each loop consumes its priority push before ordinary inbox work and maintenance. Input has a separate bounded lane of 64 wakeups, which keeps input order even when the room inbox is full. Release wakes every attachment once.

| Focus source | Lease effect |
| --- | --- |
| A cross-tab focus click or key | Arms a newer lease and push. |
| Same-tab focus input | Cancels the active jump and its pending pushes, then arms an ordered lease without pushing, fitting, or waiting for a peer paint. |
| Automatic repairs, CLI focus, the hibernate writer | No lease, and no effect on an active one. |

Input still catches up the routed view, and resize updates pane geometry without changing hidden views. Only user focus input supersedes an active lease.

Click sequence, not detached-thread arrival order, fences in-host requests. The current-sequence check and the request store are serialized against other in-host jump requests. A newer click also cancels an older paint wait. Checkpoints after fitting, and under the focus-anchor lock before each mux dispatch attempt, stop obsolete work, including supersession during the lock wait or retry delay. The paint consumer retires obsolete parked pushes even when the newer target is elsewhere. Request failure releases before rollback is enqueued, dispatch releases on return, and a drop guard covers early returns and unwinding. Releasing an old sequence cannot clear a newer one.

### The paint clock

Data cadence and paint cadence are separate clocks, which is why the sidebar stays responsive while the data layer runs slow. The fetch worker's 250 ms post-cycle rest bounds data folds even under continuous requests and adds up to 250 ms of card-state latency. The production data-tick gate is separate. Input, resize, and overlay paints do not wait for the worker. The data backstop is the fetch worker's watched-aware idle interval ([requests](#requests)), so `refresh_ms` changes paint cadence, never pull cadence.

The attachment's `LoopClock` owns transition time and effect policy. Production uses wall time, while the testkit scenario player drives the same loop with virtual time and external effects disabled.

`[theme.display] refresh_ms` sets the base render grid, `DEFAULT_REFRESH_MS` (100 ms) by default, clamped to 16 through 1000 ms. It rides `snapshot.theme.display`, so the renderer uses the default until the first fold and picks up config changes on later folds without reading config itself. Money rolls sample every `refresh_ms * CLICK_PHASES` (two base frames), matching the odometer's current-grid frame count. Effect lifetimes stamp typed driver-clock milliseconds in `ViewState::frame_ms` and read age as `now_ms / refresh_ms − stamp_ms / refresh_ms`, saturating at zero, so a config rescale moves both readings together. A raise still counts an age already measured in fewer, longer frames, so a fade or roll that closed less than its window × (new − old `refresh_ms`) before the raise can show again until that window ends. Running agents, drawn compacting heads, and busy processes request the base grid. Other resting row motion requests `BREATH_ANIMATION_FRAME` (120 ms), never faster than the base grid. Compacting wins the head only on non-actionable rows, so waiting and failed rows retain their status head and cadence.

Frame-sequence heads keep a per-view step beside the driver-clock phase. The first routed composition holds at step zero and records its phase. A later routed composition advances by exactly one iff its stamped phase is greater than the phase at the last advance under the same `refresh_ms`: paints in the same phase hold, a late paint never skips frames, and a co-viewer whose clock read landed just before another pane crossed a boundary stamps a phase one behind and holds. A changed `refresh_ms` rescales the phase (a raise lowers it), so that composition holds and re-anchors rather than freezing the head until the phase catches up. A head's speed divisor holds each frame for one, two, or three steps. Co-viewers share the step and its phase. Split and group moves carry both with the view. Hidden mirrors read the source step without advancing it, and a composed frame whose terminal write fails still counts. Playback's cosmetic pin supplies the step too and pins pet frame time to zero outside motion windows. Money rolls and scrollbar fade stay on the unpinned frame clock. Cyclic effects and steady pet tracks keep sampling the phase.

Input paints synchronously off the grid. Keys, clicks, and resize keep their per-wakeup paint, and non-wheel user viewport changes snap. A destination focus push also tries its gated paint on arrival, before maintenance, without bypassing resize holds, empty-tab confirmation, exit, or watched and frame-deadline checks. A relevant overlay event fuses and paints on arrival, and a burst of events coalesces to one paint per base frame.

The wheel glides. Consecutive queued wheel ticks apply in arrival order and coalesce into one paint, and a non-wheel wakeup ends the run and is processed next. Each tick clamps the target to the last drawn range, which keeps reversals at either edge without recomputing geometry between ticks. The visible viewport eases toward that target over 100 ms on a 16 ms grid independent of `refresh_ms`, then returns to the base grid while the scrollbar fades. Position derives from elapsed driver milliseconds since the view's animation start (`ViewState::frame_ms`), so a late frame skips ahead rather than stretching the glide. Another wheel run accumulates on the target and restarts from the currently visible row. The input paint pulls the next grid boundary within one current animation interval. Card-anchor corrections snap too, but translate the remaining wheel flight without restarting it or waking the auto scrollbar. A birth reveal of at most one viewport also glides on this ease, exempt from the selection-change snap for its paint, and wakes the scrollbar; an arrival mid birth glide lands it without making the offset authoritative.

A sidebar in an unviewed tab suspends animation and emits no frame bytes for plain data changes, including when the session is detached. Structural changes to a painted view queue hidden mirrors through the four-slot dispatcher, immediately at rest or after the 150 ms input pause. Hidden panes schedule no mirror deadline of their own. Their own publications still wait in the views as described in [hidden attachments and reveal](#hidden-attachments-and-reveal). Freeze expiry does not cap a hidden pane's timeout or request a fold, and an unpainted view cancels its tab-read dwell. Watched freeze expiry still wakes and requests a fold to restore live rank except for still-focused cards and their groups. A focus release arms a fresh settling freeze at that fold's instant, even when co-viewer disagreement leaves selection unchanged. Hidden resize updates geometry and queues an available target but neither reveals the pane nor changes a view, and the grow-resize self-close hold gates mirrors too. Input before the sampled client map catches up routes through the evidence rule in [client views](#client-views), so an older retained sample cannot undo it. An unknown own view still counts as watched for paint, though not for images. Hidden capture semantics are owned by [sidebar.md](./sidebar.md#from-store-to-screen).

The focus-marker dwell also caps `LoopState::frame_timing` while watched, even when otherwise idle. At its deadline the dwell itself makes a paint due, independently of a later ordinary frame boundary. Once ready, the marker holds no expired timer, and the next focus move re-arms it.

## Failure modes

Each degradation has one owner, and none leaves a wrong verdict that outlives the next pull, except an event a skewed sender stamped in the future, which is bounded by the event TTL instead.

| Failure | Why it is survivable | Recovery |
| --- | --- | --- |
| Missed event | Events are latency hints. | The producer's next pull. |
| Dead host | Supervisors keep the room holds and each pane's tty. | The spawn lock admits one replacement host, and each pane reattaches. |
| Clock skew | Event expiry uses receiver time, so no event lives forever. | A future-stamped event can mis-order an overlay across several pulls, and expires `EVENT_STORE_TTL` (12 s) after receipt. |
| Cold host: no fold yet | Memory starts empty with each host. | The placeholder remains until the first fold. |
| Panicking produce | The panic guard catches the unwind and discards the fold cursor. | One failed outcome. The next cycle refolds cold. |
| Panicking fetch worker or cache refresher outside a guard | The host notices the ended lane within one poll and closes every stream without a word. | Each supervisor shows `host went away` and starts a fresh host on its backoff curve. |
| Unreadable store or panes | The serve loop holds its last committed frame. | A sustained failure raises the sticky health alert. The attachment stays open and the worker's data backstop keeps folding until completed production recovers ([sidebar.md → Degraded reads](./sidebar.md#degraded-reads)). |
| Hook drainer unreachable for 10 seconds | The wrapper's runtime lease keeps the affected cards identifiable without reading diagnostics. | A separate drainer alert keeps the rest of the sidebar usable. After a 3-second recovery hold it lingers until dismissed. |

`crates/rimz/src/sidebar_pane/render/ui_state.rs::ViewState::hook_drainer_alert` is separate from refresh health. Every committed producer or cached fold activates it from `hook_drainer_outage`, or marks an active episode recovered at that fold's snapshot clock when the fact is absent. Later absent folds preserve the recovered stamp. Failed reads do not recover it. `Esc`, as its last layer, clears only a recovered drainer episode, while retaining its existing refresh-alert behavior. A view hidden for the entire lease lifetime misses the line. One revealed after its lease clears marks it recovered on reveal. The [recovery hold](../harness/fleet.md#resident-wrapper) (`RECOVERY_HOLD` in `crates/rimz/src/harness/drainer_outage.rs`) gives visible views time to observe a crossed outage. Host restart loses lingering view state, but doctor retains the durable evidence.

`Esc`, as its last layer, clears refresh health and any recovered drainer alert in the shared host view. Co-viewers share that dismissal. An active drainer alert remains until it recovers. Workflow parks carry no bottom-notice or dismissal state.

Every accepted anomaly path writes a typed diagnostic before it falls back, holds, suppresses, or exits. Flicker, duplicate rows, or a phantom external group each map to a record in `diag.log.jsonl`. `rimz doctor` shows the recent tail, and [diagnostics.md](../diagnostics.md) names the taxonomy.
